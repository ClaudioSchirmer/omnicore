OmniCore

Go framework for DDD + CQRS microservices

github.com/ClaudioSchirmer/omnicore Go ≥ 1.21 Fiber v3 · pgx v5 · mongo-driver v2 · kafka-go

Overview

OmniCore is a Go library that provides all the technical and architectural infrastructure for building microservices with Domain-Driven Design and CQRS following the idiomatic Go pattern. Services import the module and automatically gain: typed validation, atomic persistence with outbox, guaranteed auditing, multi-language, structured logging, CQRS pipeline, and a standardized HTTP layer via Fiber.

Philosophy: the framework orchestrates the critical flows (validation, transaction, outbox, audit, translation, HTTP response) and lets the developer focus exclusively on the business rules. Essential functionality cannot be forgotten — the framework guarantees it.

What the framework does

Domain Layer

  • Embeddable BaseEntity with signature, mode, notification context
  • Sealed ValidEntity (Insertable/Updatable/Archivable/Deletable/Unarchivable/Batch)
  • Rules DSL with IfInsert/IfUpdate/IfDelete/IfInsertOrUpdate
  • AggregateRoot with status tracking (Constructor/Added/Changed/Removed) + type-guarded top-level primitives (AddAggregateChild, ChangeAggregateChild, RemoveAggregateChild, ReplaceAggregateChildrenOf)
  • AggregateRootProvider — opt-in for atomic aggregate-aware persistence and children auto-validation. AggregateChildren() declares the aggregate boundary; primitives reject VOs of undeclared types
  • Generic ValueObject[T] + EnumValueObject[T]
  • Typed ID validating UUID
  • Schema validator with 5 types (String/Int/Float/Bool/UUID)
  • Typed notification system (25+ built-in types)

Application Layer

  • Pipeline dispatcher with exception/panic capture
  • Generic Result[T] (Success/Failure/Exception)
  • Fluent DSL: OnSuccess, OnFailure, OnException
  • AppContext with UUID + Language per request
  • Multi-language Translator (PT_BR + ENG + ES + FR + DE + IT + NL built-in)
  • persistence.Writer[T] port with Insert/Update/Archive/Unarchive/Delete carrying the WriteOption[T] variadic for in-TX lifecycle hooks (afterBegin / beforeCommit); threads *AppContext end-to-end so the persistence layer can carry the actor + thread id + cancellation
  • MessageDTO.NotificationKey — typed identity preserved post-translation

Infrastructure Layer

  • infra.Postgres — pgx pool with Insert/Update/Archive/Unarchive/Delete + Pool() accessor
  • Atomic outbox in the same SQL transaction
  • Transparent aggregate-aware — one transaction covers root + children + a single outbox row
  • infra.MongoDB — driver with Upsert/Delete
  • SyncEngine — Kafka consumer reads metadata from headers/key (Debezium Outbox Router native); DELETED always → delete; ARCHIVED → compose+upsert by default (document survives with deleted_at populated, mirroring PostgreSQL), delete when the view opted in via DeleteOnArchive(); UNARCHIVED → upsert
  • Composer omits the deleted_at IS NULL filter by default; DeleteOnArchive() views apply the filter on root + every embed (cascade)
  • UpstreamSubscriber — materializes upstream events into a local Mongo collection and ripples recompose to every view embedding it via FromMongo
  • ViewDefinition with fluent builder (Embed/EmbedMany/DeleteOnArchive)
  • Audit pipeline — every successful write produces an AuditEvent routed by audit.destinations: database writes an audit_events row inside the same TX as the data row + outbox row (atomic source of truth); slog emits a flat top-level slog line post-commit (observability echo). Plus SlogPublisher for domain events.

Web Layer

  • Response/Error/ErrorMessage standardized JSON shape (with notificationKey + semantic)
  • RespondFromResult[T] — renders Result[T] as HTTP; status derived from each notification's Semantic()
  • NotificationSemantic — transport-agnostic enum (Validation/NotFound/Conflict/Forbidden/Unauthorized/Unavailable) declared by the notification itself
  • RespondFromError — discriminates error via NotificationCarrier
  • Helpers: RespondWithSuccess/NotFound/BadRequest/...
  • Middleware: CORS, Logger, RateLimit, Recover
  • ParseBody, ParseID
  • HandleQueryWithParams / HandleQueryWithID — read-side wrappers; allowlist via query:"..." filter:"ops" struct tags; mandatory projector func(map[string]any) R (fwresponses.AutoFromDoc[R] tag-driven default, fwresponses.RawDoc passthrough, or consumer's Response{}.FromDoc); view:"<docKey>" tag overrides the source key when doc and wire names diverge; Response.Pagination top-level
  • NewQueryParser / ParseCriteria / BindPath / RespondSchemaViolation / ProjectPage / RespondPaged — building blocks for manual query handlers (same allowlist + sparse-render guard + path-binding + envelope as the auto wrappers)
  • path:"<name>" struct tag — universal URL-segment binding; every Request DTO field tagged is populated from c.Params("<name>") before ToCommand / ToQuery; symmetric to json:/query:/filter:; supported by every wrapper with a Request DTO

AppContext middleware

bootstrap.Run automatically registers fwweb.AppContextMiddleware() as a default middleware. Per request, it populates *configuration.AppContext with:

  • ID — UUID from the X-Request-ID header (or a new one if missing/invalid). Always returned in the response for correlation.
  • Language — prefix match of Accept-Language against the configuration.Language enum (built-ins: pt→LangPTBR, en→LangENG, es→LangES, fr→LangFR, de→LangDE, it→LangIT, nl→LangNL). Default LangENG — header absent or naming a language the framework does not ship a catalog for both resolve to English.
  • Identity — the authenticated principal of the request (*configuration.Identity). Populated by the auth middleware after a successful JWT validation; nil when the route is public, auth.mode=disabled, or the middleware has not yet run. See microservice.<profile>.yaml for how to wire the auth: block.

In any Fiber handler:

func myHandler(c fiber.Ctx) error {
    ctx := fwweb.AppContext(c)  // *configuration.AppContext
    // ctx.ID(), ctx.Language()
    if id := ctx.Identity(); id != nil {
        // id.Subject, id.Issuer, id.ExpiresAt, id.Claims (map[string]any)
    }
}

configuration.Identity carries the standard JWT claims Subject (sub), Issuer (iss), ExpiresAt (exp), plus a raw Claims map[string]any for custom claims (roles, email, tenant, …) — the framework does not opine on which custom claims a service expects.

Extra request-scoped state beyond Identity (e.g., feature flags resolved per request) goes in middleware AFTER the default, via ctx.Set(key, val).

Authentication middleware

When auth.mode: jwt in microservice.<profile>.yaml, bootstrap.Run auto-registers fwweb.AuthMiddleware right after AppContextMiddleware. Every request is validated end-to-end before it reaches a Feature route; on success the middleware populates AppContext.Identity. When auth.mode: disabled, the middleware is not registered at all — there is no runtime cost and Identity() stays nil.

Validation flow

  1. publicRoutes bypass. Exact METHOD /path match against auth.publicRoutes — health/ready probes, login endpoints, anything else the service declares. Match → request proceeds without auth.
  2. Bearer extraction. Reads Authorization: Bearer <token> (scheme match is case-insensitive). Empty or malformed → MissingAuthorizationNotification, 401.
  3. Local JWT validation. Signature verified against jwksUrl (preferred, supports rotation via MicahParks/keyfunc) or publicKeyPem (RSA/ECDSA/Ed25519 in SubjectPublicKeyInfo form). The alg header must be in the configured allowlist (default RS256, ES256, EdDSA); iss must match auth.jwt.issuer; aud must contain auth.jwt.audience; exp must be in the future after applying leewaySeconds.
  4. Identity attachment. On success, AppContext.SetIdentity attaches a *Identity carrying Subject/Issuer/ExpiresAt and a copy of the raw claim map (so handler mutations cannot leak back). The middleware also calls AppContext.SetBearerToken(token) with the verified raw JWT — consumed exclusively by the forward-bearer httpclient auth provider. Handlers should keep reading Identity() for principal data; BearerToken() is for downstream credential propagation, not for parsed claim access.

Error responses

Failures use the same response envelope as other framework rejections, translated to the request's Accept-Language, with Semantic = Unauthorized → 401:

ScenarioNotificationKey
No Authorization header, or header doesn't match Bearer <token>MissingAuthorizationNotification
Token malformed, signature mismatch, wrong iss/aud, disallowed algInvalidTokenNotification
Token exp in the past (after leeway)ExpiredTokenNotification

Expired is split from Invalid so clients can branch on refreshing the token vs. re-authenticating from scratch.

External validator (revocation check)

When auth.externalValidator is set, the middleware adds one more step after local validation passes: an outbound HTTP call to the IdP (RFC 7662 introspection endpoint or any compatible API). This catches revoked tokens — a JWT that locally still has a valid signature and an unexpired exp claim can already be revoked at the IdP, and only the IdP knows.

Cache is opt-in, default off. Set cacheTtlSeconds to a positive integer to enable an in-memory positive-only cache keyed by the SHA-256 hash of the bearer token (the raw token is never stored). Only successful validator answers are memoized — negative answers and transport errors deliberately bypass the cache so a revocation is honored on the very next request. The trade-off: tokens that were already cached as valid can keep passing for up to TTL seconds after they get revoked at the IdP. Default 0 disables the cache entirely and every authenticated request calls the IdP.

Success check

The response body is parsed as JSON, then success.jsonPath (dot notation, e.g. $.active or $.data.is_active) is matched against success.expectedValue. Equality is Go's == on any: types and values must both match (true != "true"). Path not found, type mismatch, or value mismatch → reject (401 InvalidTokenNotification).

Fail mode

failMode: closed (default) rejects the request on any validator-side error — transport failure, timeout, non-2xx status, malformed body. Safer: a token whose validity cannot be confirmed is not honored.

failMode: open swallows transport-level errors when the local pre-validation already passed — useful when the IdP is operationally fragile and you prefer availability over instant revocation. Explicit "not active" answers still reject under failMode: open; only ambiguous validator errors are suppressed.

Audit log carries the actor

Every AuditEvent emitted by the framework — both the audit_events row written in-TX by the database destination and the slog line emitted post-commit by the slog destination — includes the authenticated principal of the request: Subject (JWT sub), Issuer (JWT iss), and an opt-in subset of custom Claims (tenant_id, roles, etc.) declared in auth.auditClaims. Anonymous requests (auth disabled, public route, background job) surface as actor: "anonymous" in the slog line and as NULL in the row's actor column (the partial index audit_events_actor_idx excludes them so identified-actor queries stay on a narrow path).

// Audit line shape
{
  "msg": "audit",
  "threadId": "5f25...",
  "actor": "user-42",                    // JWT sub (or "anonymous")
  "actorIssuer": "https://idp.example",  // JWT iss (omitted when empty)
  "actorClaims": {                       // omitted when allowlist is empty or no claim matched
    "tenant_id": "acme",
    "roles": ["admin"]
  },
  "action": "Insert",
  "class": "User",
  "export": {
    "header": { ... },
    "data":   { "id": "...", "fields": {...}, "children": {...} }
  }
}

The fan-out is automatic for both Auto Command Handlers and manual handlers — every write goes through repo.Method(ctx, valid, opts...) on the persistence.Writer[T] port, and ctx IS the request *AppContext. infra.Postgres reads the actor from the same context, builds the AuditEvent, writes the row in-TX, and emits the slog line post-commit. A manual handler does not need to touch any new API to benefit from the actor information.

Domain events emitted via infra/events.SlogPublisher mirror the same pattern (actor + actorIssuer) but never carry actorClaims — the audit allowlist is the only place that can broaden the claim surface logged, by design.

Token issuance

The framework only validates — it does not mint tokens. The IdP (Keycloak, Auth0, an in-house auth service, etc.) issues tokens; each service consumes them. Login endpoints, refresh, and credential storage live in the IdP or in a dedicated auth service.

Authorization

Authentication is solved by AuthMiddleware populating AppContext.Identity from the verified JWT. Authorization — what the authenticated principal is allowed to do — travels through three concentric layers, each with its own surface. All three consume AppContext.Identity() and surface rejections through the canonical envelope with HTTP 403. The framework does NOT enforce identity at the infra layer.

Layer 1 — declarative gate via RequirePermission

The single canonical way to gate a route on a permission. The same option covers the three route registration paths (canonical via *Spec siblings, manual-with-pipeline with hand-rolled RouteSpec, raw via MountRaw):

// Canonical
fwopenapi.Mount(d.OpenAPIRegistry, users, fiber.MethodPost, "/",
    insertH, insertSpec,
    fwopenapi.Doc{Summary: "Create a user", Tags: tags},
    fwopenapi.RequirePermission("users:write"))

// Raw (free-form / vendor-shaped handlers)
fwopenapi.MountRaw(d.OpenAPIRegistry, app, fiber.MethodGet, "/whoami",
    whoamiHandler,
    fwopenapi.RawSpec{Summary: "Whoami", Tags: tags},
    fwopenapi.RequirePermission("users:profile:read"))

On receiving the option, Mount/MountRaw patches spec.RequiredPermission AND wraps the handler with the framework's permission gate which short-circuits with the canonical 403 envelope carrying MissingPermissionNotification when Identity.HasPermission(p) returns false. The OpenAPI generator appends **Required permission:** `<p>` to the description ONLY when the runtime gate is actually enforcing (auth.mode: jwt AND auth.authorization.enabled: true) — under disabled or jwt-without-authz the value stays on spec.RequiredPermission for introspection (codegen, contract diffs), but the description suffix is suppressed so the spec never advertises a constraint the server is not honoring.

The 403 entry is auto-emitted in /openapi.json on every non-public route when auth.mode: jwt is in effect, independent of whether RequirePermission is declared — any authenticated route can produce a Forbidden outcome via Layer 2 or Layer 3.

Permission string format: resource:action (Auth0 / AWS / Stripe convention). The IdP emits a permissions claim carrying an array of strings; Identity.HasPermission(p) matches with three rules:

Claim entryMatches request
users:readexactly users:read
users:*any users:<anything>
*:*any request (super-admin)

Wildcards on the caller side panic at runtime. ctx.Identity().HasPermission("users:*") is a programming bug — the claim wildcards; the route declares the exact action. Compose "any of A or B" with explicit OR over concrete actions.

Master switch — auth.authorization.enabled. Default false. When false, the runtime gate no-ops (handlers run regardless of RequirePermission) AND the spec's **Required permission:** `<p>` description suffix is suppressed — so the documentation never advertises a constraint the server is not honoring. The value stays on spec.RequiredPermission for introspection (codegen, contract diffs), and the 403 auto-emission still applies whenever auth is on. Flipping the YAML to true turns on both enforcement AND the description suffix together, so spec and runtime stay in sync.

Boot-time enforcement. When authorization.enabled: true, bootstrap scans the Registry AFTER Wiring.BeforeServe and BEFORE openapi.Register — every non-public route MUST declare RequirePermission(...), else the boot panics with the offender list. A parallel scanRouteRegistration runs whenever Wiring.OpenAPI != nil (independent of authz) and panics on any Fiber route registered outside Mount/MountRaw — the canonical channel is structural to the framework.

Layer 2 — programmatic rule in BuildRules

Rules that depend on the specific resource state, the principal's claims, or the relationship between them. Anything Layer 1's static "needs permission X" cannot express ("only the owner can archive", "cannot delete the last admin", "email cannot change after activation unless admin").

Every write verb routes through domain.GetXxx → BuildRules BEFORE the SQL fires. The actionName parameter tells the entity which verb is firing ("GetInsertable" / "GetUpdatable" / "GetPartialUpdatable" / "GetArchivable" / "GetUnarchivable" / "GetDeletable"); the rule body branches on it. The identity-derived value reaches the entity via the Command's mapper — the canonical place to translate ctx.Identity() into business-named transient fields.

// Command mapper — application layer, the only layer that may translate ctx
// into business-named entity fields. Transient fields carry `transient:"-"`
// (domain's own declaration that the field is runtime-only) so the framework's
// reflection-based persister skips them on read and write.
func (*ArchiveUserCommand) ApplyTo(ctx *configuration.AppContext, u *User) {
    if id := ctx.Identity(); id != nil {
        if email, _ := id.Claims["email"].(string); email != "" {
            u.RequestingPrincipalEmail = email
        }
        u.RequestingPrincipalIsAdmin = id.HasPermission("users:admin")
    }
}

// BuildRules — domain layer, branches by actionName to scope the check
// to specific verbs. Notification carries SemanticForbidden → 403.
func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfUpdate(func() {
        if actionName == "GetArchivable" && u.RequestingPrincipalEmail != "" {
            if u.Email != u.RequestingPrincipalEmail && !u.RequestingPrincipalIsAdmin {
                r.AddNotification("ID", domain.ArchiveNotAllowedNotification{})
            }
        }
    })
}

Layer 3 — tenant scoping (cross-cutting)

Multi-tenant isolation — a principal in tenant A cannot see or modify resources of tenant B. Three pieces, all wired by the same yaml block:

  • Claim presence gate at the middleware (auth.authorization.tenant.required: true) — after JWT validation succeeds, AuthMiddleware rejects any non-public request whose Identity.TenantID() returns empty, with TenantMissingNotification (403) before any handler runs. Uniform across the service.
  • Reads — Query.ToCriteria(ctx) injects crit.Filter["tenant_id"] = ctx.Identity().TenantID(). When the middleware gate is on, the value is guaranteed non-empty.
  • Writes — the Command's mapper populates entity.TenantID; BuildRules enforces that the resource's TenantID matches the principal's claim, emitting TenantMismatchNotification (403) on mismatch.
func (q *FindUserByParamsQuery) ToCriteria(ctx *configuration.AppContext) fwqueries.ReadCriteria {
    crit := q.WireCriteria
    if t := ctx.Identity().TenantID(); t != "" {
        crit.Filter["tenant_id"] = t
    }
    return crit
}

Identity helpers

func (i *Identity) HasPermission(p string) bool
func (i *Identity) TenantID() string

Both are nil-safe. HasPermission tolerates multiple claim shapes ([]string, []any, space-separated, comma-separated); panics on caller-side wildcards. TenantID tolerates string, []string{one}, []any{one} shapes; anything else returns "". The parsed permissions set is cached on the Identity after the first call.

Why defense-in-depth at infra is deliberately absent

Postgres.Insert/Update/Archive/Unarchive/Delete and MongoViewReader.ReadPage/ReadByID execute what the application layer validated; they do not pronounce identity. Adding a ScopeFilter knob to RepoConfig would force the infra adapters to know domain concepts (tenant, owner, role) — violating the dependency ruler and creating two sources of truth for the same rule. A bug bypassing BuildRules or ToCriteria(ctx) is a domain/application bug, fixed at that layer — not papered over by infra duplication.

Rules DSL — IfXxx and actionName dispatch

Rules (domain/rules.go) exposes a mode-scoped DSL inside BuildRules: five IfXxx closures, each gating its body on the current EntityMode. The framework picks the mode; the caller picks the actionName (third parameter on every Get* entry point). Auto handlers pass the canonical PascalCase string ("GetInsertable", etc.); manual handlers may pass any string. Service code branches by actionName inside the closure when a rule should fire only for a specific verb (typical use case: archive-only invariants under IfUpdate) or only for a specific endpoint flavor (e.g. "AdminCreate" vs canonical "GetInsertable").

r.IfInsert(func() { ... })
r.IfUpdate(func() { ... })          // fires for PUT, PATCH, Archive, Unarchive
r.IfDelete(func() { ... })
r.IfInsertOrUpdate(func() { ... })  // fires for Insert + every Update verb
r.IfDisplay(func() { ... })         // see "key facts" below — inert today

Key facts

  • Archive and Unarchive fire IfUpdate, not a dedicated IfArchive. Both run in ModeUpdate with a distinct actionName so the existing DSL covers state-transition verbs without growing the closure surface. Branch by actionName when archive-specific logic is needed (e.g. if actionName == "GetArchivable" { ... }).
  • actionName is case-sensitive. The Get* family emits PascalCase ("GetInsertable"); IsValid emits lowercase "isValid". Custom callers passing their own actionName (e.g. "AdminCreate" for stricter validation) must match the string exactly inside BuildRules.
  • AggregateValueObject.BuildRules receives the SAME actionName as the root. runAggregateValidations propagates the root's actionName verbatim when firing the AVO closures per child — so an AVO branching on actionName == "GetArchivable" matches the verb archiving the aggregate.
  • IfDisplay is inert in the canonical dispatch. ModeDisplay is the default mode of a freshly constructed BaseEntity, but no framework path calls NewRules(ModeDisplay, ctx). The closure exists in the DSL for symmetry; using it today produces dead code unless an external caller wires its own dispatch.

Aggregate Persistence (transparent dispatch)

Entities that need to persist a root together with collections of child value objects opt-in by implementing domain.AggregateRootProvider. The framework then guarantees atomicity without changing the public API: pg.Insert/Update/Archive/Delete/Unarchive detect the metadata and dispatch to the aggregate-aware path automatically.

Opt-in interface (Phase 19 + Phase 20)

type AggregateRootProvider interface {
    GetAggregateRoot() *AggregateRoot

    // Phase 20: explicitly declares which types belong to the aggregate.
    // Sample instances (zero value) are enough — framework reads classNameOf via reflect.
    AggregateChildren() []AggregateValueObject
}

Phase 19 simplified the interface by removing table/FK declaration from the domain — children types discovered via reflection on root.AllAggregateItems(); child table and FK inferred from the Go typeName via convention (PluralizeSnake(PascalToSnake(typeName)) for the table; PascalToSnake(rootType) + "_id" for the FK). Per-Repository override via fwinfra.RepoConfig (ChildTableOverrides, ChildFKOverrides) when the convention doesn't fit.

Phase 20 gave the root back authority over the aggregate boundary without reintroducing infra into the domain. AggregateChildren() declares which types belong to the aggregate — this is a domain definition (orthodox DDD), separated from "which table/FK" (infra, still inferred by convention). The top-level primitives AddAggregateChild, ChangeAggregateChild, RemoveAggregateChild and ReplaceAggregateChildrenOf consult this list and reject VOs of undeclared types by emitting InvalidAggregateChildNotification (422 Validation). The old methods AggregateRoot.AddAggregateItem/ChangeAggregateItem/RemoveAggregateItem were demoted to internal use (addAggregateItem etc.) — only AggregateConstructor (DB load path, with types coming from infra's WithChild[V]) and the top-level primitives (after the type-guard) use them. ReplaceAggregateItemsOf was renamed to ReplaceAggregateChildrenOf.

AggregateValueObject requires BuildRules(actionName string, svc Service, r *Rules) — signature identical to Entity.BuildRules — plus GetID(). Infra extracts columns via reflection on exported fields. Tag transient:"-" is the domain's own declaration that a field is runtime-only (request input, computed value, in-memory cache, runtime bookkeeping) and the framework skips it on read and write; the ID field is skipped on INSERT/UPDATE (DB-gen + WHERE clause); the FK to the root is injected by infra.

Universal symmetric cascade (Phase 19)

Operations on the root cascade symmetrically and universally — no per-child HardDelete flag:

  • Archive(root) → Archive on all active children
  • Unarchive(root) → Unarchive on all archived children (requires domain.ArchivedFinder on the Repository to hydrate the aggregate)
  • Delete(root) → Delete on all children via FK ON DELETE CASCADE in the schema
  • Update(root) with items StatusRemoved → Archive of those specific items

Domain methods on the root (Phase 20)

Children mutations go through root methods named in the domain vocabulary (AddAddress, ChangeAddress, RemoveAddress, ReplaceAddresses) — never directly through the AddAggregateChild & co. primitives from commands. This is what makes the root the consistency boundary:

  • Tell, don't ask — command says "User, add this address", not "User, let me mess with your internal list"
  • Invariants spanning children live in root methods (duplicate, "cannot remove the last one", cross rules)
  • Ubiquitous vocabulary — AddAddress is business language; AddAggregateChild is framework jargon
  • Service injected per method when needed — no global plumbing in the framework. AddAddress's svc enables external lookups (e.g., "is this ZIP code already in use by another user?") without touching the primitives' contract
Construction-time notifications survive to the boundary. Root methods must call domain.EnsureInitialized(u) on the first line. Without it, notifications emitted in the constructor (e.g., duplicate detection in AddAddress) would be silently lost because BaseEntity.AddNotification is a no-op when notifCtx == nil (the natural state of an entity freshly constructed via &User{}; GetInsertable only initializes the context LATER). resetEntity called by getInsertable/getUpdatable/getDeletable does not clear the NotificationContext — notifications accumulated during construction survive until checkAllNotifications. IsValid (re-check) calls Clear() explicitly before re-validating. The type-guarded primitives also call ensureRootInit internally as defense in depth.

Optional inline validation (Phase 20)

By default, AVO's BuildRules runs at the boundary (GetInsertable/Update/Delete) via runAggregateValidations — same lifecycle as the root's BuildRules. Mutations accumulate, validation runs once. For those who want immediate feedback inside a root method, the framework provides domain.ValidateAggregateChild(root, item, actionName, svc) bool: runs item.BuildRules with a NotificationContext scoped just like the boundary would; returns true if it passed. Pitfall: if you use it inline AND the item enters the collection, the boundary runs BuildRules again and produces a duplicate notification. Use one path OR the other per item.

In-TX side effects via lifecycle hooks

The framework exposes two lifecycle slots on every write verb (Insert / Update / Archive / Unarchive / Delete) — both fire INSIDE the persister's TX, so a hook can write companion rows, denormalizations, or extra outbox events atomically with the framework's own writes. The names anchor on the TX verbs themselves so the consumer reads the trigger directly:

SlotPositionUse case
afterBeginINSIDE the TX, BEFORE any framework write (data + outbox + audit)Acquire an advisory lock; consult adjacent state under serializable isolation; enforce a cross-aggregate precondition the data write itself depends on.
beforeCommitINSIDE the TX, AFTER all framework writes, BEFORE COMMITEmit an extra outbox row with a different event_type; write a denormalization row; perform a cross-table read-then-write that needs the post-write state of the aggregate.

A non-nil error returned by either slot rolls back the entire TX. domain.NotificationCarrier identity is preserved end-to-end — a typed notification returned from the hook reaches the wire envelope verbatim, at the notification's own HTTP status. A panic inside the hook propagates through pipeline.Run's defer/recover and renders as 500; defer tx.Rollback() fires automatically.

The persister always emits a slog.Warn("persistence.hook.error", verb, hookSlot, entityType, threadId, error) line on every hook error as a best-effort observability echo; the line is non-blocking, so a slog handler failure never masks the rollback.

The Auto Command Handler detects each via type assertion at the top of Handle and forwards the method values as WriteOption[T] closures to the Writer.Method(ctx, valid, opts...) call.

Manual handler path (closure passed at the call site)

The same persister surface serves the manual path — the closure is supplied directly via persistence.WithAfterBegin[T](fn) / persistence.WithBeforeCommit[T](fn) as trailing options on the repo.Method(ctx, valid, opts...) call. There is one canonical persister surface; Auto and manual differ only in how the closures originate (Cmd method vs explicit closure).

Application stays SQL-free on the manual path too — persistence.TxHandle is a sealed marker with no public methods, so the closure cannot pronounce SQL through it by construction. The canonical shape is a port declared in application/ (or domain/) whose method receives a persistence.TxHandle; the port's adapter in infra/ calls fwinfra.UnwrapPgxTx(tx) to recover the live pgx.Tx and owns the SQL + table name. TxHandle — sealed marker

Hooks receive the framework's TX as persistence.TxHandle — a sealed interface with no public methods. The single sealing method on it is unexported, so the only implementation is the framework's own pgxTxHandle in omnicore/infra/, which carries the live pgx.Tx privately. Application code cannot read or write SQL through the handle by construction.

The canonical (and only) shape for an in-TX side effect from a hook:

  1. Declare a port in application/ (or domain/) — a pure Go interface whose method receives a persistence.TxHandle parameter.
  2. Implement the port in infra/ — the adapter calls fwinfra.UnwrapPgxTx(tx) pgx.Tx to recover the underlying transaction and owns the SQL + table name. UnwrapPgxTx lives in infra/, so only adapters in that layer can call it.
  3. Inject the port on the Cmd (or manual handler) and call it from the hook closure. The framework's TX is honored end-to-end; the application layer never pronounces SQL.

UnwrapPgxTx panics with a descriptive diagnostic if passed a foreign TxHandle implementation — defensive, never reached against framework-issued handles because the interface is sealed. Advanced pgx features (CopyFrom, SendBatch, Prepare) are reachable from the adapter via the unwrapped pgx.Tx, but constraint-binding translation (infra.ConstraintBinding) is not applied at this surface — it lives at the Repository level for the parent entity's declared constraints.

Aggregate-path symmetry

Both persister paths — flat (non-aggregate entities) and aggregate (entities implementing AggregateRootProvider) — fire the hooks at the same analogous positions, with the same generic signature, the same firing cardinality (single firing per repo.Method() call, granularity B, matching outbox and audit row cardinality). The hook receives the root entity with all aggregate children reachable via the usual domain.GetCurrentItemsOf[VO] helpers. Consumer code does not know which dispatch path the persister took.

Old-state snapshot

Domain owns the “what did the entity look like before this write?” snapshot. The framework's Get* functions capture it automatically; BuildRules consumes it via the typed helper domain.Old[T](e) T; the audit builder consumes it to compute changes (kind=delta) or to emit snapshot (kind=snapshot on Delete). Powers both transition-aware invariants in the domain and timeline reconstruction in audit.

Read the old state inside BuildRules

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfUpdate(func() {
        if old := domain.Old(u); old != nil {
            if old.Email != u.Email && u.Activated {
                r.AddNotification("Email", EmailLockedAfterActivationNotification{})
            }
        }
    })
}

For aggregates, domain.Old(u) also exposes the prior children via the usual helpers (e.g. domain.GetCurrentItemsOf[Address](&domain.Old(u).AggregateRoot)). Use it to express invariants spanning the boundary across the transition.

How the snapshot is captured

  • Update / Patch (closure form): domain.GetUpdatable[T](loaded, apply, svc) and domain.GetPartialUpdatable[T](loaded, apply, svc) snapshot the entity before running the apply closure. The mutation happens inside the domain function — the caller passes cmd.ApplyTo or cmd.ApplyPartiallyTo directly (signature func(T)). Auto handlers do this automatically; manual handlers follow the same pattern.
  • Delete / Archive / Unarchive: domain.GetDeletable / GetArchivable / GetUnarchivable snapshot at function entry (no mutation step in these flows). Old() returns the entity in its pre-transition state — used both in BuildRules (e.g., r.IfDelete rule using the loaded balance) and for audit forensics.
  • Insert: NO snapshot. A freshly created entity has no prior state by definition. Inside BuildRules, domain.Old(u) returns the typed zero value; defensive code with if old != nil guards Update-only rules.

What the clone looks like

The clone is produced via a JSON round-trip (encoding/json) — only exported fields cross. Private BaseEntity/AggregateRoot state (notifCtx, events, signature) is intentionally NOT cloned, so the clone is a read-only “ghost”: calling mutator domain methods on it is a silent no-op because its notifCtx is nil. The aggregate path also deep-copies the items map so Old() reflects the children as they were before mutation.

Custom infra escape hatch

Implementations that bypass the framework's Get* path (raw SQL building an Updatable by hand — not exposed by the public API today, but conceptually) will not have Old() populated. On Update the audit builder's changes degrade to every column with from: null; on Delete it falls back to the live source's snapshot. Graceful degrade, not error.

    // lifecycle hooks would land as trailing variadic options on this call.
    return h.repo.Insert(ctx, insertable)
}

BaseRepository[T] — 5 ready-made writes + New() T

The service embeds fwinfra.BaseRepository[T] and gains Insert/Update/Archive/Unarchive/Delete without writing a line — plus New() T, which materializes the constructor of T (consumed by UnarchiveCommandHandler and available for any scenario needing an empty entity). FindByID is the service's responsibility (see AggregateLoader).

type UserRepository struct {
    fwinfra.BaseRepository[*User]
    loader *fwinfra.AggregateLoader[*User]  // for FindByID
}

newUser := func() *User { return &User{} }  // single factory source

base := fwinfra.BaseRepository[*User]{
    Postgres:  pg,
    NewEntity: newUser,                       // mandatory: feeds Repo.New()
    Constraints: map[string]fwinfra.ConstraintBinding{
        "users_email_active_idx": {Notification: EmailAlreadyExistsNotification{}, Field: "email"},
    },
}

NewEntity is mandatory. New() panics with a clear message if nil — it's a configuration bug detected at boot/first call, not in a hot request. The same factory is typically shared with the AggregateLoader to avoid duplication.

ContextName is optional. When empty, derived from the Go type T via reflect (T=*User → "User") — that's the framework's convention. Set explicitly only when you need to customize (e.g., two Repositories over the same entity with distinct names in the notification context).

Unique violations (PG code 23505) are translated into *InfrastructureError carrying the typed notification — no manual mapPGError. Unregistered constraints, codes other than 23505, and non-pgconn.PgError errors return raw.

BaseAggregateRepository[T] — canonical composition

Almost every aggregate-aware Repository has the same shape: BaseRepository[T] (writes) + *AggregateLoader[T] (FindByID/FindArchivedByID). fwinfra.BaseAggregateRepository[T] bundles both and promotes the trivial wrappers — the service no longer declares FindByID and FindArchivedByID manually. The common case fits in 8–10 lines. 

type UserRepository struct {
    fwinfra.BaseAggregateRepository[*User]
}

func NewUserRepository(pg *fwinfra.Postgres) *UserRepository {
    r := &UserRepository{
        BaseAggregateRepository: fwinfra.NewBaseAggregateRepository[*User](
            pg, func() *User { return &User{} },
        ),
    }
    r.Constraints = map[string]fwinfra.ConstraintBinding{
        "users_email_active_idx": {Notification: EmailAlreadyExistsNotification{}, Field: "email"},
    }
    fwinfra.WithChild[Address](r.Loader)   // children via public Loader
    return r
}

var (
    _ persistence.Writer[*User]    = (*UserRepository)(nil)
    _ domain.Repository[*User]     = (*UserRepository)(nil)
    _ domain.ArchivedFinder[*User] = (*UserRepository)(nil)
)

FindByID and FindArchivedByID come promoted via embed; New() and the 5 writes also come from BaseRepository via embed. The *AggregateLoader[T] is exposed as a public Loader field — call WithChild[V], WithChildScanner, WithRootScanner, WithConfig on it directly.

When NOT to use it (keep the old pattern of direct embed BaseRepository[T] + carrying *AggregateLoader[T] separately): custom magic pattern where the Loader is not the canonical source of FindByID (e.g., read replica + main, materialized view). Manual and composite coexist — choose per Repository.

AggregateLoader[T] — loading aggregates with the criteria engine

The AggregateLoader loads live domain aggregates (root + children) from PostgreSQL through the entity search engine: you hand it a criteria.Query and it returns the entity ready for a command. Two entry points — FindOne(ctx, *criteria.Query) (one match, or RecordNotFound; more than one is an error) and FindAll(ctx, *criteria.Query) (a slice; children batched). It has its own SQL engine: it inspects your entity via reflection, discovers the columns, generates the SELECT and populates the struct — you write neither the SQL nor the scanner. For exotic decoding the auto-scan doesn't cover (JOIN, CASE, COALESCE) there is a manual-scanner escape hatch; both scan modes coexist.

Loading by criteria — FindOne / FindAll

omnicore/criteria is a small, pure DSL (stdlib only) you compose in Go inside your infra repository. It is the developer-facing, compile-time way to load the authoritative aggregate — distinct from the Mongo read side, which is the end-user-facing query facade over the eventually-consistent projection. Your repository interface stays in business vocabulary (FindByID, FindByEmail, …); the engine is how the infra implementation fulfills it. 

// Primary-key shortcut (assumes the ID↔id convention):
u, err := repo.FindOne(ctx, criteria.ByID(id))

// Any alternate key — no hand-rolled SQL:
u, err := repo.FindOne(ctx, criteria.Where(criteria.Eq("Email", email)))

// Boolean composition + order + limit; FindAll returns []*User (children batched):
users, err := repo.FindAll(ctx, criteria.Where(criteria.And(
    criteria.Eq("TenantID", t),
    criteria.Or(criteria.Eq("Status", "active"), criteria.ILike("Name", "bob%")),
    criteria.IsNull("DeletedReason"),
)).OrderByDesc("CreatedAt").Limit(50))

// Archived scope (soft-delete gate) lives on the Query, not in the predicate:
archived, err := repo.FindOne(ctx, criteria.ByID(id).OnlyArchived())

Operators: Eq/Ne/In/Nin/Gt/Gte/Lt/Lte/Like/ILike/IsNull/NotNull, combinators And/Or/Not (nestable), and sugar Contains/StartsWith/EndsWith (case-insensitive, wildcards escaped) + Between. Field names are your Go field names ("Email"), resolved to columns by the same convention auto-scan uses (snake_case, or RepoConfig.FieldOverrides). Values are always parameterized; a domain.ID value is unwrapped automatically. FindByID / FindArchivedByID (promoted by BaseAggregateRepository) are themselves thin wrappers over FindOne(criteria.ByID(id)) — one SQL-building path for every load.

Automatic scan mode (recommended default)

No scanner passed. The loader inspects the entity's exported fields and the children's, assembles SELECT col1, col2, ... FROM table WHERE id=$1 AND deleted_at IS NULL and writes directly into the field addresses via row.Scan. Private fields (including all those of AggregateRoot and BaseEntity that your entity embeds) are ignored by reflection — they don't leak into SQL. 

// User with 4 exported domain fields
type User struct {
    domain.AggregateRoot      // embed; private fields, invisible to the engine
    Name  string
    Email string
    CPF   string
    Phone *string             // nullable: pointer maps directly to NULL
}

// FindByID / FindArchivedByID promoted via embed — zero manual wrappers.

SELECT id, name, email, cpf, phone FROM users

-- Per child registered in WithChild (FindAll batches with fk IN ($1,$2,...))
SELECT user_id, id, label, street, number, complement, neighborhood, city, state, zip_code, country
  FROM addresses

Nullables

NULL-able columns map to pointer types in the domain (*string, *int64, *time.Time). pgx writes NULL when the pointer is nil; reads NULL as nil on auto-scan. Recommended boundary convention: empty JSON input becomes nil via a local helper (e.g., NilIfEmpty(s string) *string in your service's commands package).

The first call pays the reflection (~µs); subsequent calls do direct lookup and row.Scan writes into the field address with no intermediate allocations. Manual mode (escape hatch)

When the query needs something the engine does not generate — JOIN with another table, CASE/COALESCE, aggregate SQL expressions, lookup by non-id field, external materialized view — you provide the scan function via WithRootScanner and/or WithChildScanner. The loader keeps handling children dispatch and AggregateConstructor; only the decoding is up to you. 

// Manual mode runs SELECT * — scan id first (the framework no longer injects
// it on the criteria path) and SetID, then decode the rest however you like.
r.loader = fwinfra.NewAggregateLoader[*User](pg, factory).
    WithRootScanner(func(row pgx.Row) (*User, error) {
        u := &User{}
        var id, firstName, lastName string
        if err := row.Scan(&id, &firstName, &lastName /* …, &u.Email, etc */); err != nil {
            return nil, err
        }
        u.SetID(domain.NewID(id)) // REQUIRED: FindOne/FindAll recover the id via GetID()
        u.Name = firstName + " " + lastName
        return u, nil
    })
// Address keeps auto:
fwinfra.WithChild[Address](r.loader)

Auto and manual coexist per typeName: for the same child, the manual scanner wins over auto when both are registered. The manual mode uses SELECT * (compatible with custom queries you may write).

Manual root scanner + FindOne/FindAll: the scanner must populate the entity id (scan it and call SetID). The criteria path has no input id to inject (unlike the old by-id load), so the framework recovers the id via GetID() after your scanner runs — an empty id is a configuration error. Auto-scan reads the id back automatically; only the manual path carries this requirement.

Errors and edge cases

  • Root not found → *DomainError with RecordNotFoundNotification (→ 404 HTTP via Semantic mapping).
  • More than one match in FindOne → error ("expected one"): the contract is a single match; use FindAll or a more specific criterion.
  • Aggregate without children — omit WithChild/ WithChildScanner and the load only does SELECT root.
  • Entity without exported domain fields in auto mode: FindOne/FindAll return a descriptive error suggesting WithRootScanner (typically a bug — an entity with no data at all is rare).
  • Type registered in WithChildScanner without an entry in AggregateChildren() — silently ignored (compatible with evolving aggregate).
Result: with ~40 lines of code per entity you get typed validation and i18n, atomic transaction with outbox, structured audit, event publication, standardized HTTP response and automatic error translation per AppContext.Language(), and FindByID comes for free via auto-scan.

Auto Command Handlers

For trivial CRUD — the logic fits entirely on the Entity via BuildRules — the framework provides ready-made generic handlers. The service writes only the Command — ToEntity(ctx) / ApplyTo(ctx, t) / ApplyPartiallyTo(ctx, t) on the way in AND FromEntity(ctx, t) TResult on the way out, both as methods on the Cmd struct. The wire layer finishes the projection with Response.FromResult(Result) Response. No handler struct to write.

For CRUD with extra rules (cross-service IO, injected domain services), keep writing a manual Handler — they coexist in the same API.

The 6 handlers

Every Cmd implements input boundary + output boundary as methods on its own struct. FromEntity(ctx, T) TResult is required on all 6 verbs — bodyless verbs (Archive/Unarchive/Delete) typically declare TResult = fwresults.None and have FromEntity return fwresults.None{}.

PUT vs PATCH is HTTP rule, not convention. PUT replaces the entire resource → all fields mandatory; PATCH updates partially → each field optional. The framework enforces it via type: UpdateCommand[T, TResult] (PUT, ApplyTo) and PartialUpdateCommand[T, TResult] (PATCH, ApplyPartiallyTo) are distinct interfaces, consumed by distinct handlers. UpdateCommandHandler embeds the pipeline.FullBody marker that activates strict body check in the Fiber wrapper — missing field → 422 with one RequiredFieldNotification per field before dispatch.

Strict body via marker pipeline.FullBody

Handlers that need to require all Cmd fields present in the JSON body embed the empty struct pipeline.FullBody. The enforceFullBody() method is unexported — only those embedding the marker satisfy the FullBodyEnforcer interface, preventing accidental satisfaction outside the package. 

type UpdateCommandHandler[T, Cmd, TResult] struct {
    pipeline.FullBody  // marker — wrapper activates strict body check
    Repo    persistence.Writer[T]
    Service domain.Service     // optional — see "Domain Service via Auto handler"
    // No Auditor field — audit is owned by infra.Postgres, configured at boot.
    // No Project field — projection lives on the Cmd as cmd.FromEntity(ctx, T) TResult.
    // In-TX side effects opt in via Cmd's optional AfterBegin / BeforeCommit
    // methods — the handler detects them via type assertion and threads them as
    // WriteOption[T] to the Repo.Update call.
}

The wrappers HandleCommandWithBody{,ID} type-assert to FullBodyEnforcer at construction and, when present, reflect on *TReq (Request DTO) once (cached by reflect.Type) to list exported fields (skipping anonymous embedded and json:"-" tags). Per request: json.Unmarshal of the body into map[string]json.RawMessage + set diff; missing field → 400 with 1 RequiredFieldNotification per field via the normal pipeline (semantic SemanticSchema).

Closed rule — no per-field opt-out. Those who want flexibility use PATCH (handler without marker). PUT is the strict contract.

Fiber route wrappers

Wire format (JSON) is separated from application vocabulary: web/requests/ in the service carries the Request DTOs with json:"..." tags and a ToCommand() method (no ctx — web boundary is dumb mapping); application/commands/ carries the pure Commands without JSON. AppContext reaches the application layer through cmd.ToEntity(ctx) / ApplyTo(ctx, T) / ApplyPartiallyTo(ctx, T) — symmetric with the read side's Query.ToCriteria(ctx). The Command (or Query) is the only layer that may translate identity-derived claims into business-named entity fields (or persistence criteria). The current wrappers:

  • fwweb.HandleCommandWithBody(pipe, sample, responseProjection, h, status) — endpoint with body, without path ID (POST). Allocates TReq via new, validates schema, calls req.ToCommand() on the web→application boundary (no ctx — Request DTO is body-only), Dispatch (handler receives ctx and forwards to cmd.ToEntity(ctx)).
  • fwweb.HandleCommandWithBodyID(pipe, sample, responseProjection, h, status) — endpoint with body, with path ID (PUT/PATCH). Same + cmd.SetPathID(c.Params("id")) before Dispatch.
  • fwweb.HandleCommandWithID(pipe, responseProjection, h, status) — endpoint without body, with path ID (Archive/Unarchive/Delete). Does not call Bind().Body(), does not inspect FullBody.

The responseProjection is a func(TResult) TResp — typically a method value like requests.InsertUserResponse{}.FromResult. For endpoints with no projection, pass fwresponses.NoBody (a func(fwresults.None) fwresponses.None) and use fwresults.None as the handler's TResult.

The whole family starts with HandleCommand — suffixes communicate what the endpoint accepts (body, ID, both). The wrapper always dispatches a Command; Request is only the wire DTO that becomes a Command via ToCommand(ctx) at the boundary.

Body behavior in HandleCommandWithBody{,ID}:

  • Strict handler (FullBody marker): missing body → 400 (all fields missing, semantic Schema); malformed JSON → 400 with SchemaViolationNotification; type mismatch → 400 with SchemaViolationNotification carrying the field's JSON path; missing field → 400 with one RequiredFieldNotification per field.
  • Lenient handler (no marker): missing body OK (Request zero-value); malformed JSON → 400 with SchemaViolationNotification; partial body OK.
HTTP error semantics: 400 = wire contract violated (Request schema doesn't match); 422 = domain rejects values (notifications via BuildRules). Semantic distinction in the notification type: SemanticSchema → 400, SemanticValidation → 422. Wire notifications (Phase 21): SchemaViolationNotification (always Schema) + RequiredFieldNotification{}.WithSemantic(SemanticSchema) (same domain struct, semantic overridden per-instance).

Request ≡ Command shape ruler: required field → string on both (absence in JSON triggers 400 before dispatch); optional field → *string on both (ToCommand is 1:1 assignment without normalization). Uniform pointer Cmd pattern

The handler's second type param is always *Cmd (not Cmd by value). Reason: SetPathID needs a pointer receiver to mutate; using uniform *Cmd (even on Insert) keeps a single mental model. ToEntity/ApplyTo may have a value-receiver OR a pointer-receiver — Go promotes value-receiver methods to the pointer type.

Manual path (cross-service, side effects)

Handler with external IO, injected domain service, or complex orchestration: continues to be a struct that implements pipeline.Handler[*Cmd, TResult] — exactly as before. TResult is whatever application-layer value the handler returns; the route's responseProjection then maps it to the wire TResp. It is registered on the route with the same HandleCommand/HandleCommandWithID.

Domain Service via Auto handler (optional Service field)

The 6 Auto handlers expose an optional Service domain.Service field. When set, it is propagated to the entity's BuildRules (which receives the service as the second argument). This enables infra-dependent queries inside domain rules without falling back to the manual path — e.g., uniqueness invariant that needs a DB query. 

// Domain — interface declarada no pacote da entity, embeda ServiceBase.
type UserService interface {
    domain.Service
    EmailExists(email string, excludeID domain.ID) bool
}

func (u *User) RequiresService() bool { return true }

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Email != "" {
            if us, ok := svc.(UserService); ok && us.EmailExists(u.Email, *u.GetID()) {
                r.AddNotification("Email", EmailAlreadyExistsNotification{}, u.Email)
            }
        }
    })
}

// Wire-up — handler gets the service injected.
users.Post("/", fwweb.HandleCommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[*User, *InsertUserCommand, commands.InsertUserResult]{
        Repo: repo, Service: userService,
    }, fiber.StatusCreated))

Compat: leaving Service nil keeps default behavior (entity receives nil in BuildRules). Pre-existing handlers don't break.

Where Service is consumed: BuildRules runs on every write — Insert (mode Insert), PUT / PATCH (mode Update), Archive and Unarchive (also mode Update with distinct actionName values "GetArchivable"/"GetUnarchivable" — service branches on actionName inside IfUpdate when an archive-specific rule is needed), and Delete (mode Delete). The Service field is the same on all 6 handlers; RequiresService() true on the entity raises ServiceIsRequiredNotification when the field is nil and the handler is invoked.

Defense in depth: the BuildRules check does not replace unique constraints in the DB — between EmailExists and the COMMIT there is room for a race condition. The unique index + ConstraintBinding on the Repository remains the atomic enforcement. The domain check gives a cleaner error message on the happy path and keeps the rule declared where one would expect.

UnarchiveCommandHandler asymmetry

UnarchiveCommandHandler does NOT call FindByID (record is archived; Repository.FindByID filters WHERE deleted_at IS NULL by convention). Instead, it obtains an empty sample via Repo.New(), sets the path ID, and generates Unarchivable. Cascade of archived children is via direct SQL in aggregate_persister.unarchiveAggregate.

The asymmetry is internal to the handler: the wire-up in routes.go is identical to the other Auto handlers — only Repo (audit emission is handled automatically by infra.Postgres). Repo.New() T is a mandatory method of both the domain.Repository[T] read port and the persistence.Writer[T] write port; anyone using BaseRepository[T] injects a single NewEntity func() T into the constructor (typically the same factory shared with the AggregateLoader) and New() comes promoted via embed.

Child cascade (aggregate)

Children of an AggregateRoot don't have their own outbox event or Mongo op — granularity B means one outbox row per aggregate operation, and the read side re-composes the whole doc from the root's event. What children DO have, per row, is per-status SQL emitted by applyChildChanges + cascade SQL emitted by archiveAggregate/unarchiveAggregate/deleteAggregate, and a per-row audit op that mirrors the SQL fingerprint identically to the root verb.

The SQL-grounded vocabulary — one rule, no exceptions

Reading the two tables top-to-bottom, the rule the framework follows is:

Audit verb (root) and audit op (child) both echo the SQL fingerprint of the row-level change. Identical SQL ⇒ identical audit token. Distinct SQL ⇒ distinct audit token. Consumer intent (PUT vs PATCH, archive cascade vs PUT-replace soft-delete) lives in the actionName field at the root and in the verb field on the surrounding event; the per-row op/verb stays anchored to what physically hit the database.

This gives consumers a forensically honest record: an audit log entry saying op="archived" always means "this row still exists in the DB with deleted_at populated, can be restored", regardless of whether the trigger was a PATCH /archive or a PUT-replace. Same way op="deleted" always means "this row is gone, only the cascade/snapshot in the audit can reconstruct what it was". Future tooling for reversal of state changes (rebuilding the prior aggregate from audit) only needs to know the SQL contract, not the verb hierarchy of every endpoint that ever produced the change.

Query side (CQRS)

The query side serves reads (GET) symmetric to the command side: Request → Query → Handler on the read path mirrors Request → Command → Handler on the write path. Reads come from MongoDB (pre-composed view) and support dynamic filters, cursor pagination, sorting, field projection, and text search — all derived from the query string and the ViewDefinition.

The wire boundary lives in two HTTP wrappers in web/:

  • fwweb.HandleQueryWithParams(pipe, sample, projector, h) — paged listing (GET /users). Validates the query string against the Request DTO's query:"X" filter:"ops" tags, assembles a queries.ReadCriteria, calls req.ToQuery(criteria) — pure body mapping at the boundary, no ctx. AppContext reaches the application layer through q.ToCriteria(ctx), which the framework's FindByParamsQueryHandler[*Q] calls before forwarding to ViewReader.ReadPage — where JWT-derived overlays (tenant id, owner id) layer onto the criteria. Success projects each page.Items document via projector and returns the standard Response envelope with data as the projected items array and pagination as a top-level field.
  • fwweb.HandleQueryWithID(pipe, sample, projector, h) — by-id lookup (GET /users/:id). Only ?includeArchived=true is reserved; any other query parameter produces 400. Calls req.ToQuery() (no ctx), injects the path id via q.SetPathID(...), dispatches via FindByIDQueryHandler[*Q] which calls q.ToCriteria(ctx) and forwards both id + criteria (IncludeArchived flag + any JWT overlay) to ViewReader.ReadByID — symmetric DTO with ReadPage. Projects result.Value() via projector; not-found produces 404 with RecordNotFoundNotification. An overlay filter that filters the doc out is indistinguishable from absence at this layer: both surface as 404.

The projector (third argument) is mandatory and has signature func(map[string]any) R. Three canonical projectors ship with the framework:

The view: tag — explicit source-key override (rare). The projector consumes two tags on the Response struct. json:"<wire>" is the standard encoding/json contract — names the field on the outgoing JSON. view:"<docKey>" is the explicit override — names the field inside the view document when the framework default does not fit. The default doc key is domain.PascalToSnake(jsonName), the same convention the framework uses on the Postgres write side (ZipCode → column zip_code). So json:"zipCode" defaults to doc field zip_code, matching the composer's snake_case output without any tag declaration. Declare view: only for exotic schemas where the doc name truly diverges:

Consumers typically declare a typed FindXxxResponse struct in web/requests/find_xxx_request.go (co-located with the Request) and pair it with fwresponses.AutoFromDoc[FindXxxResponse] at the route. The Response type carries the wire contract; the helper carries the projection logic.

Allowlist via struct tags

Each filter field on the Request DTO declares its set of allowed operators via the filter:"eq,in" tag. The wrapper inspects the type (cached by reflect.Type in a module-level sync.Map) and rejects any query-string key outside the declared set with 400 SchemaViolationNotification. Reserved pagination/control keys (limit, after, before, sort, fields, search, includeArchived) are declared with only the query:"..." tag (no filter tag) — recognized only at the top level, never inside an embed group.

Nested embed groups

A struct-typed field carrying query:"prefix" (no filter:) is an embed group — the walker recurses, and every leaf below it produces a wire key prefixed by prefix.. Symmetric with the Response side, where nested structs project nested doc paths via AutoFromDoc.

Sparse responses via ?fields=

Opt-in field projection — the consumer asks for a subset of the Response shape and the framework strips everything else end to end. The Request DTO opts in by declaring Fields *string `query:"fields"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, three things happen automatically:

  1. Boot guard. At wrapper construction (HandleQueryWithParams / HandleQueryWithParamsSpec), the framework walks R recursively and panics if any exported field is not *T (or a slice/map) and does not carry ,omitempty in its json tag. The panic diagnostic names every offending field path (FindXxxResponse.addresses.zipCode: missing ,omitempty…) — fail loud at boot so the contract cannot ship.
  2. Allowlist + wire→doc translation. Each comma-separated token in ?fields= is validated against the Response DTO's declared wire paths and translated to the corresponding Mongo doc path via the same convention used elsewhere on the read side (domain.PascalToSnake by default, view: tag override per segment). Unknown tokens emit 400 with SchemaViolationNotification on field fields[<bad>]. Nested paths are walked segment-by-segment, so ?fields=addresses.zipCode projects to Mongo as {"addresses.zip_code":1}, and ?fields=addresses projects the whole subtree.
  3. Auto-exclusion of _id. Mongo always returns _id unless excluded. When the wire fields list does not include id, the framework adds _id: 0 to the projection so the typed Response stays clean (no phantom id the consumer didn't ask for). When id is among the tokens, no _id: 0 is added — Mongo returns both id and _id, and AutoFromDoc's existing fallback (id ← _id when id absent) keeps the wire output stable across both cases. Mongo's projection rules allow _id: 0 to be mixed with inclusion entries — it is the only permitted exclusion in an otherwise- inclusion projection.

Why the boot guard? Mongo strips the unwanted columns from the document; the projector (AutoFromDoc[R] by default) populates only the fields it finds in the doc; the remaining fields stay at their zero value. For pointer fields with omitempty, encoding/json elides them on the wire. For non-pointer fields (or pointer fields missing omitempty), the zero value still renders ("name":"", "addresses":[]), defeating the point of ?fields=. The contract enforced at boot is the cheapest way to keep wire output coherent with what the consumer asked for.

The boot guard is opt-in by declaration: a Request DTO that does not carry query:"fields" imposes no constraint on its Response type; the HandleQueryWithParams wrapper paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the guard — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?fields= token becomes an inclusion entry verbatim, no allowlist, no translation, no _id: 0 auto-exclusion. The canonical surface is the HandleQueryWithParams wrapper.

Sortable response paths via ?sort=

Symmetric to ?fields=: the consumer asks the framework to order results by Response-declared paths and the wrapper validates + translates the tokens end to end. The Request DTO opts in by declaring Sort *string `query:"sort"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, two things happen automatically:

  1. Allowlist + wire→doc translation. Each comma-separated token is stripped of an optional - prefix (descending; bare token = ascending), validated against the Response DTO's declared wire paths, and translated to the corresponding Mongo doc path via the same convention used by ?fields= (domain.PascalToSnake by default, view: tag override per segment). Unknown tokens emit 400 with SchemaViolationNotification on field sort[<token>]; the rejected token is surfaced verbatim including any - prefix the consumer sent. The resulting SortField{Field: docPath, Desc: bool} entries land on ReadCriteria.Sort and the canonical MongoViewReader emits the corresponding bson.D on findOpts.SetSort.
  2. Boot warning when sort is declared. The wrapper has no way to verify from its construction site that the Mongo view declares indexes covering the sortable paths — the ViewDefinition lives in the consumer's ReadableFeature.Views(), separated from the route registration. When Sort opt-in is detected and a typed Response is in scope, the framework emits a single slog.Warn at boot listing every sortable wire path so the operator can compare it against the view's .Indexes(…) declaration in the same boot pass and add covering indexes (fwinfra.Index / fwinfra.Compound) where missing — sort queries against non-indexed fields scale poorly on large collections.

There is no boot guard analogous to fields' pointer + omitempty rule. ?sort= only consumes the wire→doc path map; the Response shape is not constrained by it. When fields is also opt-in, the existing guard still fires — it is the fields-side rule, untouched by sort.

The allowlist is opt-in by declaration: a Request DTO without query:"sort" does not get the allowlist (and does not consume the ?sort= wire key); HandleQueryWithParams paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the allowlist — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?sort= token becomes a SortField verbatim (no allowlist, no translation, no boot warning). Keyset pagination via ?after= / ?before= + per-view ?limit= ceiling

The read side is keyset-paginated over (sort_value..., _id). The cursor encodes the value tuple of the boundary doc (last for forward, first for backward) and the reader walks from that point. The reader always appends _id ASC as the stable tiebreaker so the result set is deterministic across pages even when the underlying collection is being written to concurrently; consumer-declared ?sort= fields layer in front of the _id slot. The ?before= path queries Mongo in inverted sort order and reverses the slice in Go so the caller always sees the canonical requested order.

Cursor format. Opaque to consumers — base64(URLEncoding) of {"v":1, "k":[<sort_values..>, "<_id>"], "h":"<context_sha256>"}. URL-safe so + / / are never produced in the encoded string. The v field carries the schema version (currently 1); a future bump rejects older cursors with the same 400 envelope so the consumer surfaces the drift instead of navigating against a stale layout. The h field is the canonical SHA-256 of the issuing call's full listing context (queries.HashContext) — every axis that shapes the result set the cursor walks: Filter + Sort (field + Desc per entry, declaration order matters) + Search + IncludeArchived. Empty (omitted on the wire) when the issuing call carried the canonical default context (no filter, no sort, no search, archived excluded).

Cursors are scoped to the full listing context. A cursor only navigates correctly inside the result set that issued it. The wrapper validates len(cursor.K)-1 == len(criteria.Sort) (structural pre-check protecting the reader's keyset builder) AND cursor.H == HashContext(filter, sort, search, includeArchived) (covers every listing axis) after parsing the query string. Any mismatch — sort field added/removed/ reordered, sort direction flipped, filter value changed, ?search= value changed, ?includeArchived= flipped — is rejected with 400 SchemaViolationNotification on the cursor's wire key (after or before). Stateless by design: there is no server-side session, no per-cursor TTL, no token store. The whole "is this cursor still valid?" check runs in the wrapper against the wire request alone. Cursors persist arbitrarily — across requests, across browser tabs, across user devices — as long as the deploy's schema version and the full listing context match.

The strict check exists to convert silent consumer-side bugs (frontend changes one knob, server returns wrong/empty results, user blames the data) into loud, explicit failures with a clear remediation: "request page 1 of the new context".

Symmetric envelope. The reader emits NextCursor and PrevCursor on every non-terminal page in both forward and backward navigation, so a UI can drive both "next" and "previous" buttons symmetrically. HasNext / HasPrev reflect the actual presence of more docs in either direction.

Per-view ?limit= ceiling — single cascade, three levels. Every paged GET is bounded by a resolved-at-read-time ceiling computed in this order:

  1. ViewDefinition.MaxLimit(N) — declarative per-view override (fwinfra.View("users").MaxLimit(500)). Applies uniformly to every endpoint consulting the view, regardless of how many handlers point at it — the cap describes the cost of reading this specific dataset, not of any single endpoint.
  2. cfg.Query.MaxLimit — yaml-supplied service-wide default (microservice.<profile>.yaml: query: { maxLimit: 200 }).
  3. Framework constant 100 — conservative fallback when neither is declared.

The resolved ceiling is always > 0. When the consumer sends no ?limit=, the reader returns up to that ceiling (no separate hardcoded default page size). When the consumer sends ?limit=N and N ≤ resolvedMax, that value wins. When N > resolvedMax, the reader rejects with 400 LimitExceededNotification carrying the effective ceiling as FieldValue so the consumer can show "max is X" without parsing the translated message.

MaxLimit(N) does NOT participate in RebuildHash / ArtifactHash — the cap is operational state, not projection shape. Bumping it neither triggers a Mongo rebuild nor requires a Version(N) bump.

Count-only mode via ?onlyTotal=true

Boolean reserved control key. When set to true the wrapper short-circuits the read into a count primitive — the reader runs CountDocuments against the assembled Filter (including identity-derived overlays, the archived gate, and any ?search=) and the wire envelope carries solely pagination.total. No documents are materialized, no projection is applied, no cursor is decoded. The use case is a frontend that needs the total count of a filtered subset (pagination calculation, "matches" badge) without paying for the document fetch.

Like every reserved control key on the read side, ?onlyTotal= is opt-in per endpoint: the consumer declares OnlyTotal *bool `query:"onlyTotal"` on the Request DTO. Endpoints that did not declare it reject the wire key with the canonical 400 — same posture as ?fields= / ?sort= / ?includeArchived=.

Conflict matrix. The listing-only reserved controls have no meaningful effect when no documents are emitted, so combining them with onlyTotal=true is a consumer-side bug. The wrapper rejects the combination with 400 SchemaViolationNotification on field onlyTotal[<conflict>]. Filter leaves (declared via filter:"ops") plus ?search= and ?includeArchived= stay valid — counting a filtered subset is the canonical use case.

String operators come in case-sensitive and case-insensitive variants — the i prefix is the case-folded twin. The consumer declares whichever set the endpoint accepts (filter:"eq,startswith,icontains" means exact, prefix, and case-insensitive substring); operators outside the declared list are rejected with 400. Numeric operators (gte/lte/gt/lt) have no i variant by design — case-folding has no meaning on ordinal comparisons.

User-supplied values feeding the regex operators are escaped via regexp.QuoteMeta so wire metacharacters are treated as literals — ?name.contains=a.b*c matches the literal string a.b*c, never the regex pattern. The iin and inin operators emit a queries.RegexMatchList sentinel that MongoViewReader translates into {$in: [bson.Regex, ...]} / {$nin: [bson.Regex, ...]} — Mongo requires the native regex type inside $in, so the translation is owned by the infra adapter rather than emitted from the wire layer.

Multiple operators on the same field are AND-ed. When the wire delivers more than one operator targeting the same field (e.g. ?age.gte=18&age.lte=65 or ?name.startswith=Bob&name.icontains=ob), the wrapper folds the clauses into a queries.MultiClause sentinel on ReadCriteria.Filter[field] instead of overwriting the previous entry on the map. MongoViewReader expands the sentinel into a top-level $and array — each clause becomes a {field: translatedValue} entry so every declared operator is honored simultaneously. A single operator on a field stays as the plain {field: value} shape so Mongo indexes remain usable without an outer $and.

1. Define the ViewDefinition

Canonical case (single aggregate, convention matches): fwinfra.ViewOf[*T]() infers Mongo collection, root table, and EmbedMany from the children declared in T.AggregateChildren(). Custom pattern (cross-service via cache, external materialized view) still via fluent View(name).Root(...).EmbedMany(...) — they coexist. 

// internal/views/customer.go
package views

import (
    "github.com/ClaudioSchirmer/omnicore/infra"
    appdomain "github.com/ClaudioSchirmer/myservice/domain"
)

// Canonical path — 1 line. Infers collection "customers", root table
// "customers" and EmbedMany from the children declared in
// Customer.AggregateChildren().
var CustomerView = infra.ViewOf[*appdomain.Customer]()

// Custom pattern — fluent when crossing bounded contexts via UpstreamSubscription
// (cross-service Embed is NOT derivable from the aggregate). FromMongo resolves to
// the local Mongo collection materialized by the framework's UpstreamSubscriber on
// each upstream event (see "Cross-service composition" below).
var SaleView = infra.View("sales_view").
    Root("sales").
    Embed("customer", infra.FromMongo("customers").On("customer_id")).
    EmbedMany("items", infra.From("sale_items").On("sale_id").
        Embed("product", infra.FromMongo("products").On("product_id")),
    ).
    Indexes(infra.Index("customer_id"))   // boot guard §8.1 requires the join field index

// Drop archived rows from the projection — opt in via .DeleteOnArchive().
// Default behavior (flag absent): ARCHIVED outbox events compose+upsert the
// document (survives with deleted_at populated, mirroring PostgreSQL
// symmetrically) and the composer omits the WHERE deleted_at IS NULL filter
// on every fetch. With .DeleteOnArchive(): ARCHIVED removes the document
// from Mongo and the composer applies the deleted_at filter on the root
// AND on every embed source — the flag governs the whole aggregate
// projection (no per-embed override). The hot-tier choice for services
// that don't need archived data on the read side.
//
// Reader semantics are unchanged: ReadByID / ReadPage default to
// IncludeArchived=false at the Mongo layer, so consumers still have to
// pass ?includeArchived=true (or the equivalent on their Request DTO) to see
// archived documents. On a default (keep) view the document is present
// and returns; on a DeleteOnArchive view the document is absent and the
// reader returns 404 — the explicit consequence of opting into hot-tier.
//
// Hard DELETE always removes the document from Mongo regardless of the
// flag (it covers soft delete only).
var HotTierUserView = infra.ViewOf[*appdomain.User]().DeleteOnArchive()

2. Declare the Request DTO (allowlist) + Query (transport)

The Request DTO lives in web/requests/ and declares the wire allowlist through struct tags. ToQuery is pure body mapping with no ctx — the web→application boundary stays dumb. The Query lives in application/queries/ and owns its persistence shape end to end via ToCriteria(ctx) — that is where *AppContext is consumed and where JWT-derived overlays (tenant id, owner id) layer onto the ReadCriteria.Filter. 

// internal/web/requests/find_users_by_params_request.go
package requests

type FindUsersByParamsRequest struct {
    // Allowlist (consumer declares which fields and operators are accepted).
    Name  *string `query:"name"  filter:"eq"`
    Email *string `query:"email" filter:"eq,in"`
    City  *string `query:"city"  filter:"eq"`

    // Reserved pagination/control keys — no filter tag.
    Limit           *int64  `query:"limit"`
    After           *string `query:"after"`
    Before          *string `query:"before"`
    Sort            *string `query:"sort"`
    Fields          *string `query:"fields"`
    Search          *string `query:"search"`
    IncludeArchived *bool   `query:"includeArchived"`
}

// ToQuery is the web→application boundary — pure body mapping, no ctx.
// The wrapper has already parsed the query string into `criteria`.
func (r FindUsersByParamsRequest) ToQuery(
    criteria queries.ReadCriteria,
) *appqueries.FindUserByParamsQuery {
    return &appqueries.FindUserByParamsQuery{Criteria: criteria}
}

// internal/application/queries/find_user_by_params_query.go
package queries

type FindUserByParamsQuery struct {
    pipeline.QueryBase
    Criteria fwqueries.ReadCriteria
}

// ToCriteria(ctx) is the read-side equivalent of the write-side
// ToEntity(ctx) — the only layer below the web boundary that may consume
// *AppContext. JWT-derived overlays (tenant id, owner id) layer here onto
// the wire criteria; the framework's FindByParamsQueryHandler calls
// ToCriteria(ctx) and forwards the result to ViewReader.ReadPage.
func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,
) fwqueries.ReadCriteria {
    crit := q.Criteria
    // Example: tenant_id is a custom claim attached to ctx.Identity().Claims
    //   if id := ctx.Identity(); id != nil {
    //       if v, ok := id.Claims["tenant_id"]; ok {
    //           if crit.Filter == nil { crit.Filter = map[string]any{} }
    //           crit.Filter["tenant_id"] = v
    //       }
    //   }
    return crit
}

// By-id companion — same pattern. The Query owns IncludeArchived + JWT overlays
// inside its ToCriteria(ctx); the Request boundary is body-only.
type FindUserByIDRequest struct {
    IncludeArchived *bool `query:"includeArchived"`
}
func (r FindUserByIDRequest) ToQuery() *FindUserByIDQuery {
    arch := false
    if r.IncludeArchived != nil { arch = *r.IncludeArchived }
    return &FindUserByIDQuery{IncludeArchived: arch}
}

type FindUserByIDQuery struct {
    fwqueries.QueryBaseWithID
    IncludeArchived bool
}

// ToCriteria(ctx) returns the same DTO used by FindByParamsQuery — the
// ViewReader port has a single ReadCriteria contract. ReadByID honors
// Filter (overlays) + IncludeArchived; Limit/Sort/After/Before/Search/
// Projection are ignored by ReadByID by design.
func (q FindUserByIDQuery) ToCriteria(
    _ *configuration.AppContext,
) fwqueries.ReadCriteria {
    return fwqueries.ReadCriteria{IncludeArchived: q.IncludeArchived}
}

// ContextName seeds the NotificationContext of the 404 emitted when the
// document is missing. Returning "User" aligns the read 404 with the
// singular identity the write side already emits (Insert/Update/Delete
// notifications carry the same "User" context). Returning "" lets the
// handler fall back to the view name.
func (q FindUserByIDQuery) ContextName() string { return "User" }

5. Manual query handlers — same building blocks

Routes that need a custom shape (alternative identifier, vendor-specific lookup, bespoke envelope) opt out of the wrapper but still get the canonical allowlist + envelope by composing the building blocks the wrapper itself uses. Two helpers cover the query-string allowlist depending on whether the Response is typed:

  • fwweb.NewQueryParser[Req, Resp]() — typed Mount-time parser when the Request opts into ?fields= / ?sort= AND the Response is typed. Construction runs the same boot scan HandleQueryWithParams runs internally: sparse-render guard on the Response (panic when any field at any depth is not *T or a slice/map with ,omitempty), slog.Warn advisory listing every sortable wire path so operators can compare against the Mongo view's index declaration, plus extractProjectionSchema for runtime wire→doc translation. Per-request parser.Parse(c) returns the same (criteria, badField, ok) shape as ParseCriteria but with allowlist enforcement and translation enabled. Constructed once per route and reused; schema caches are shared with the canonical wrapper.
  • fwweb.ParseCriteria(c, requestDTO) — un-typed escape hatch for handlers that have no typed Response (RawDoc projectors, vendor-shaped envelopes) OR whose Request does not opt into ?fields= / ?sort=. Same reflection-based allowlist applies, but the projection schema is nil so reserved keys land in pass-through mode (tokens verbatim, no _id:0 auto-exclusion, no snake_case translation).

Canonical manual list shape (typed Response opting into ?fields= / ?sort=):

// At Mount time — once per route. Boot scan fires here:
// fields-side guard + sort-side slog.Warn + projection-schema build.
listParser := fwweb.NewQueryParser[requests.FindXxxCustomRequest, requests.FindXxxCustomResponse]()

g.Get("/", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindXxxCustomRequest
    // Same allowlist + wire→doc translation HandleQueryWithParams runs
    // internally.
    crit, badField, ok := listParser.Parse(c)
    if !ok {
        // Canonical 400 envelope with SchemaViolationNotification — same
        // shape consumers already parse from the auto path.
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }

    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if !result.IsSuccess() {
        return fwweb.RespondFromResult(c, result, fiber.StatusOK)
    }
    // Same envelope HandleQueryWithParams emits — items projected per doc,
    // top-level pagination block.
    return fwweb.RespondPaged(c, fiber.StatusOK, result.Value(),
        fwresponses.AutoFromDoc[requests.FindXxxCustomResponse])
})

By-email lookup shape — chain BindPath before the parser:

byEmailParser := fwweb.NewQueryParser[requests.FindXxxByEmailRequest, requests.FindXxxByEmailResponse]()

g.Get("/:email", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindXxxByEmailRequest
    // Same path-binding the wrappers run internally — populates fields
    // tagged `path:"<name>"` from c.Params("<name>").
    if badField, ok := fwweb.BindPath(c, &req); !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    crit, badField, ok := byEmailParser.Parse(c)
    if !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if result.IsSuccess() {
        return fwweb.RespondWithSuccess(c, fiber.StatusOK,
            fwresponses.AutoFromDoc[requests.FindXxxByEmailResponse](result.Value()))
    }
    return fwweb.RespondFromResult(c, result, fiber.StatusOK)
})

Projection is shared infrastructure. Manual query handlers should pair with fwresponses.AutoFromDoc[R] (tag-driven default) or fwresponses.RawDoc (passthrough) — the same projectors the canonical wrappers consume. Hand-rolling a FromDoc that walks doc["id"], doc["name"], etc. is a redundant rewrite of what AutoFromDoc already does (json:/view: tags, _id → id fallback, PascalToSnake source-key translation, nil→empty-slice normalization). Declare a consumer R{}.FromDoc method only when the projection needs logic AutoFromDoc cannot express (derived fields computed from multiple doc keys, conditional shaping, ctx-aware projection).

For envelopes that need sidecar fields (custom keys outside data/pagination), use fwweb.ProjectPage instead of RespondPaged and build the Response struct by hand — the projector and the pagination cursor are still framework-managed.

6. path: tag — universal URL-segment binding

Every Request DTO field tagged path:"<name>" is populated from the matching Fiber URL segment (c.Params("<name>")) before ToCommand / ToQuery runs. Closes the asymmetry between the canonical wrappers (which only auto-bind :id via the pipeline.CommandWithID / queries.FindByIDQuery interface) and routes with custom identifier segments (:email, :tenantId, …) or compound paths (/tenants/:tenantId/users/:id). 

// Read by-email — single segment route
type FindUserByEmailRequest struct {
    Email           string `path:"email"`
    IncludeArchived *bool  `query:"includeArchived"`
}
func (r FindUserByEmailRequest) ToQuery(crit fwqueries.ReadCriteria) *queries.FindUserByEmailQuery { ... }

// Compound route — both segments via tag
type UpdateOnTenantRequest struct {
    TenantID string `path:"tenantId"`   // /tenants/:tenantId/users/:id — :id still via interface on WithBodyID
    Name     string `json:"name"`
}

Per-wrapper behavior — :id-binding wrappers (HandleCommandWithBodyID, HandleQueryWithID) panic at boot if the Request declares path:"id" (it would set the same value twice); Group A wrappers (HandleCommandWithBody, HandleQueryWithParams) accept path:"id" for compound routes — map cmd.SetPathID(r.ID) inside ToCommand. HandleCommandWithID has no Request DTO and is excluded from path-binding entirely.

Manual fiber.Handler closures opt out of the wrappers — call fwweb.BindPath(c, &req) explicitly (same helper as ParseCriteria). See omnicore-example-users/web/user_custom_routes.go for the canonical example of BindPath → Bind().Body() → ToCommand → Dispatch.

Supported field types: string, signed/unsigned ints of any width, float32/float64, bool, uuid.UUID, domain.ID. Pointer/slice/struct types are rejected at boot. Conversion failure returns 400 SchemaViolationNotification with the segment name.

FullBody interaction. The strict-body check in HandleCommandWithBody{,ID} skips fields carrying a path: tag — their value comes from the URL, not the body. Declaring both path:"X" and json:"X" on the same field is a boot panic; the same value cannot come from two sources.

Group A wrapper + ID-requiring handler warning. When HandleCommandWithBody / HandleQueryWithParams (no :id auto-bind) is paired with an ID-requiring auto handler (Update/PartialUpdate/Archive/Unarchive/Delete) AND the Request DTO declares no path: tag at all, the wrapper logs a single slog.Warn at construction time. Catches the misconfiguration of "I expected the wrapper to populate the ID" — the runtime guard handlers.RequirePathID still catches the actual failure if the warning is ignored. FindByIDQueryHandler is excluded from the warning because its Group A wrapper does not compile with the handler's constraint.

Runtime guard. Each ID-requiring auto handler calls handlers.RequirePathID(<pathID>, "<HandlerName>") as the first line of Handle. Empty path ID → developer-focused panic, caught by pipeline.Run's defer/recover, surfaced to the wire as 500 InternalServerErrorNotification; full diagnostic on slog. Each handler also embeds pipeline.PathIDRequired so the wrappers can detect the requirement via type assertion at construction time (zero per-request cost).

Persistent failure registry. Every ripple failure (discover / compose / upsert stage) is upserted into the framework PG table omnicore_upstream_failures alongside the slog line and the in-memory counter. The natural key (subscription_topic, view_name, upstream_id, local_id, stage) turns retries into attempt increments — the table mirrors live state, never grows monotonically. A recompose round that finishes without errors for (view, upstream_id) automatically marks any pending rows under that coordinate as resolved (resolved_at = NOW()). Writes are best-effort: any PG error on Record/Resolve is logged at slog.Warn and discarded — the consumer's Kafka offset still advances, preserving the failure-isolation contract.

Operational queries (SQL on B's framework PG):

-- Currently stale entities:
SELECT subscription_topic, view_name, upstream_id, local_id, stage, attempt,
       last_attempt_at, error
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
ORDER BY last_attempt_at ASC;

-- Top offending views (recurring failures may indicate a deterministic Composer bug):
SELECT view_name, count(*) AS pending
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
GROUP BY view_name
ORDER BY pending DESC;

Retry surface. UpstreamSubscriber.RetryPendingFailures(ctx) (retried int, err error) is the public runtime API: it lists pending failures by the subscriber's topic, deduplicates by upstream_id, and re-runs ripple for each unique id. Idempotent — a successful re-ripple calls ResolveUpstreamFailures, so the next call against a drained slate is a no-op. The framework owns the primitive; the consumer decides how to expose it (in-process ticker, authenticated HTTP endpoint, or admin RPC).

Inspection CLI. omnicore-admin upstream-list-failures [--topic <name>] [--view <name>] [--format text|json] [--limit N] is the read-only triage tool: runs in B's process (loads microservice.${APP_PROFILE}.yaml), reads the table, prints text or JSON. The CLI binary has no Wiring of B and cannot call RetryPendingFailures — actual retry lives on the runtime API above.

bootstrap.Run wires fwweb.ErrorHandler(deps.Pipeline) into fiber.Config.ErrorHandler, so every error escaping a route, middleware, or panic recovery surfaces as the canonical Response envelope — same JSON shape consumers already see from RespondFromResult. Four branches:

  • NotificationCarrier escapes — translated against AppContext.Language() and emitted with the status derived from each notification's Semantic() (same path RespondFromResult uses on Failure).
  • Fiber router 404 (no matching route) → RouteNotFoundNotification in context "Route" with METHOD /path echoed on field; mapped via SemanticNotFound → 404.
  • Fiber 405 (path matches but the HTTP method does not) → MethodNotAllowedNotification in context "Route" with METHOD /path echoed on field; mapped via SemanticMethodNotAllowed → 405.
  • Fiber 413 (body exceeds the configured BodyLimit) → PayloadTooLargeNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticPayloadTooLarge → 413.
  • Any other error (recovered panic, unexpected error, any other *fiber.Error code) → InternalServerErrorNotification in context "Server"; mapped via SemanticInternal → 500. The panic value and stack trace are logged by fwweb.Recover() via slog.Error with method, path, panic, and stack attributes, and never reach the wire envelope. Services that need custom HTTP semantics MUST emit a NotificationCarrier with the appropriate Semantic() rather than calling fiber.NewError — the "one canonical path" rule still applies.

Root vs Aggregate Value Object uniformity

Validating root and AVO uses the same signature, the same DSL, and the same emit. actionName is propagated to both through the same chain (validateForInsert/Update/Delete → root's BuildRules → runAggregateValidations → each AVO's BuildRules). It allows rule branching by action flavor on both sides. 

// Root — User
func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Name == "" {
            r.AddNotification("Name", domain.RequiredFieldNotification{})
        }
        if u.Email != "" && !validEmail(u.Email) {
            // optional value becomes FieldValue — echo of the rejected input in the response
            r.AddNotification("Email", InvalidEmailNotification{}, u.Email)
        }
    })
}

// Aggregate child — Address — identical signature

    r.IfInsertOrUpdate(func() {

How it works — no new interface per entity

  1. Rules carries the ctx. NewRules(mode, ctx) packages the EntityMode + NotificationContext. r.AddNotification/r.AddNotificationMessage delegate to the internal ctx. For root, the ctx is the entity's own e.NotificationContext(). For AVO, the ctx is a Scoped(NameSegment(collection), IndexSegment(i)) view of the root's ctx.
  2. Collection name inferred by convention. runAggregateValidations iterates root.AllAggregateItems() and uses PluralizeSnake(PascalToSnake(typeName)) ("addresses", "order_items") as the collection segment name. Same convention infra uses for the child table, so the wire field name matches the persistence layout without a new interface on the service.
  3. Acronym-aware toLowerCamel render: Name→name, CPF→cpf, ZipCode→zipCode, URLPath→urlPath. Strings already in lowercase pass through ("id"→"id") — the legacy FieldName: "id" in mode validators remains intact.
  4. Wire layer (web/from_notifications.go, application/notifications/convert.go) reads m.ResolveFieldName() with precedence Override > rendered Path > FieldName.

Controlling the wire field name

Three paths feed ResolveFieldName(). Pick by lifetime of the rule — entity-wide and stable, per-request and conditional, or no override at all.

PathWhere it livesWhen to reach for it
Default emission r.AddNotification(name, n) inside BuildRules The Go identifier already matches the wire name (after acronym-aware toLowerCamel). The most common case — no extra plumbing needed.
BaseEntity.AddFieldNameAlias(orig, new) Domain method on the entity (e.g. inside a constructor or a method called before validation runs) The renaming is a stable rule of the entity — every message about orig, regardless of which handler triggered it, should surface as new on the wire. NotificationContext.ChangeFieldName(orig, new) Imperative call in a manual handler (or anywhere the consumer holds the *NotificationContext) The renaming is conditional / per-endpoint — only this specific flow renames the field. Field labels — translated human identifier per field

The wire field and the audit field are technical identifiers — stable but not human-readable. Reading audit rows — audit.FindByID and audit.FindByAggregate

Two canonical helpers retrieve audit rows from the audit_events table when the destinations list includes database: 

// Forensic single-row lookup — you saw an id in the slog echo and want the full row.
ev, err := audit.FindByID(ctx, deps.Postgres.Pool(), eventID)
if errors.Is(err, audit.ErrAuditNotFound) {
    // no row with that id — partition pruned? archived?
}

// Timeline by aggregate — index-served by audit_events_entity_timeline_idx
// (entity_type, aggregate_id, occurred_at DESC). Newest first.
events, err := audit.FindByAggregate(ctx, deps.Postgres.Pool(), "User", userID.String())

    // walk the row's lifetime
}

Both helpers consume the minimal pgExec interface — *pgxpool.Pool, *pgxpool.Conn, *pgx.Conn, and pgx.Tx all satisfy it — so calls inside and outside an open transaction share the same surface. The returned *AuditEvent mirrors what the persister wrote: top-level columns map directly; the payload jsonb blob is unmarshaled back into Snapshot / Changes / Children.

Caveats: FindByID issues a multi-partition index scan because the PK is composite (id, created_at); the common case (recent rows from a slog id) is fast, but archived partitions add cost — pass created_at explicitly via raw SQL when the lookup goes deep. FindByAggregate returns every matching row; aggregates with very long timelines should slice the result downstream or call raw SQL with explicit LIMIT / OFFSET. JSON round-trip on the payload returns float64 / string / bool / map / slice — assert on stringified values, not on Go-typed scalars.

Interaction with AddFieldNameAlias / ChangeFieldName

Label resolution operates on the Go field name the rule passed: r.AddNotification("Email", n) reads the label tag on the Email struct field. Wire renames affect only FieldName rendering — AddFieldNameAlias("Email", "primaryEmail") makes the wire say "field": "primaryEmail" while "fieldLabel" stays the translation of the tag on Email. The two surfaces are independent on purpose: alias renames the technical identifier; label translates the human identifier. Both reach the wire together but resolve through different paths.

Manual emission via AddNotificationMessage

Consumer code that builds a NotificationMessage directly (rare escape hatch for Err/FuncName/Override cases) carries LabelKey == "" by default and gets no fieldLabel on the wire. Setting msg.LabelKey = "<catalogKey>" explicitly on the manual message reaches the same render path the canonical r.AddNotification uses.

Why backend, not frontend

Frontends typically own the labels of their forms (offline-capable mobile apps ship with their own i18n bundle). Backend-side labels exist because notifications reach the user via channels other than the frontend — e-mail, SMS, push, audit logs — where there is no JS engine to interpolate. Frontend i18n bundles and backend label catalogs are independent surfaces with independent owners; they describe the same field from different sides. There is intentional, controlled duplication between them.

Cache subsystem

omnicore/infra/cache is the framework's generic byte-level key-value cache subsystem. The cache.Cache port is the single contract consumer code, domain services, infrastructure adapters, and the outbound httpclient all consult — there is no per-component cache anymore. Two canonical implementations ship: in-process LRU+TTL via cache.NewMemory, Redis via cache.NewRedis. Consumers wanting a different backend (Memcached, Valkey, Hazelcast, …) implement the same cache.Cache interface and inject the implementation via bootstrap.Wiring.Cache / bootstrap.Wiring.SharedCache.

Interface

type Cache interface {
    Get(ctx context.Context, key string) ([]byte, bool, error)
    Set(ctx context.Context, key string, value []byte, ttl time.Duration) error
    Delete(ctx context.Context, key string) error
}

Intentionally narrow — Get returns (value, true, nil) on hit / (nil, false, nil) on miss / (nil, false, err) on transport failure; Set accepts ttl == 0 as "no expiration"; Delete is idempotent (missing keys are not an error). No Has (use Get); no Clear (operator-owned via the backend's CLI); no batch ops.

Typed JSON helpers sit outside the interface so backends don't have to think about Go types:

func cache.GetJSON[T any](ctx, c cache.Cache, key string) (T, bool, error)
func cache.SetJSON[T any](ctx, c cache.Cache, key string, value T, ttl time.Duration) error

Both tolerate a nil Cache and degrade to no-op (miss / no-op write) so feature code that opts the cache in-or-out via YAML doesn't need a nil guard around every call site.

Two cache instances per service — Private and Shared

The framework exposes TWO cache.Cache instances on bootstrap.Deps:

  • Deps.Cache — service-private. Populated when the top-level cache: YAML block is declared (any store including memory). Use for anything scoped to this service — domain memoization, computed-value caching, the outbound httpclient response cache (the framework wires its own middleware to consume this same instance).
  • Deps.SharedCache — cross-service. Populated only when cache.shared: is declared. Use for keys other services in the cluster are expected to read — feature flags coordinated across services, cluster-wide rate limits, sessions consumed by an API gateway.

The distinction is enforced at the dependency-injection level, not via a flag on Set/Get. Code that wants to write a shared value writes to Deps.SharedCache; code that doesn't is structurally unable to. Default safety: Deps.SharedCache is nil unless declared — feature code touching it MUST guard explicitly. The httpclient response cache uses Deps.Cache (private) unconditionally.

cache.shared.store: memory is REJECTED at boot. An in-process LRU cannot honor cross-service reads; the framework forces the operator to pick redis or custom for the shared cache.

Which combination has which scope

The scope of a cached value is decided by TWO axes, not one. The slot (Deps.Cache vs Deps.SharedCache) decides who is allowed to read it — the same service, or any service in the cluster. The backend (memory vs redis/custom) decides where the bytes live — inside this one process, or in a shared store that survives restarts and is visible to every replica. Cross those two axes and three meaningful combinations fall out:

Scope you wantSlotBackendWhat it means concretely
Only this microservice instance (per-process, per-pod) Deps.Cache memory In-process LRU+TTL. Each replica has its own copy; entries are lost on restart and never visible to another pod. The only combination that is local to a single running instance.
This microservice, independent of the instance (shared across all its replicas, survives restarts) Deps.Cache redis (or custom) All replicas of the service read/write the same backend; entries survive restarts. The service's own keyPrefix namespaces the keys so other services don't read them — private to the service, but not tied to any one instance.
Shared between different microservices (cross-service) Deps.SharedCache redis (or custom) Populated only when cache.shared: is declared. Intended for keys other services in the cluster read — feature flags coordinated across services, cluster-wide rate limits, sessions consumed by an API gateway. memory is rejected at boot here.

Two practical notes. First, the two slots can point at the same Redis instance — what separates "private to the service" from "shared across services" is the slot + the keyPrefix (${SERVICE}-cache vs ${TEAM}-shared), not a second server. Second, the only structural rule the framework enforces at boot is that cache.shared.store may never be memory — an in-process LRU cannot, by definition, be shared across services. Everything else is the operator's choice.

YAML — top-level cache: block

cache:
  store: memory                     # memory (default) | redis | custom
  maxEntries: 10000                 # only memory; default 10000
  redis:                            # required when store: redis, rejected otherwise
    addr: ${REDIS_ADDR:localhost:6379}
    password: ${REDIS_PASSWORD}
    db: 0
    keyPrefix: "${SERVICE}-cache"
    failMode: open                  # open (default) | closed
    timeoutMs: 100                  # per-op timeout against Redis; default 100ms

  shared:                           # OPTIONAL second cache instance
    store: redis                    # redis | custom — memory rejected at boot
    redis:
      addr: ${SHARED_REDIS_ADDR}
      keyPrefix: "${TEAM}-shared"
      failMode: open
      timeoutMs: 100

When the top-level cache: block is omitted entirely, Deps.Cache stays nil — the httpclient cache layer bypasses, and cache.GetJSON/SetJSON degrade to no-ops. Services that don't need caching pay zero cost.

Backend selection cascade

The same matrix applies independently to cache.store and cache.shared.store. Mismatched wiring fails the boot with a structural-coherence error:

  • store: memory (or unset) + no Wiring.Cache → in-process LRU runs.
  • store: memory or store: redis + Wiring.Cache injected → boot panic ("declare store: custom to use Wiring.Cache").
  • store: redis + no Wiring.Cache → go-redis backed adapter built from redis: sub-block.
  • store: custom + no Wiring.Cache → boot panic ("Wiring.Cache required").
  • store: custom + Wiring.Cache injected → injected instance runs.

cache.shared.store: memory is additionally rejected at boot — only redis and custom are accepted for the shared cache.

Redis adapter — failMode

The framework's Redis backend (cache.NewRedis(*RedisConfig)) resolves the configured failMode internally:

  • open (default) — swallows transport errors, emits slog.Warn "cache.redis.transport.error" with {op, key, error, failOpen}, and returns (nil, false, nil) on Get / nil on Set/Delete. The caller sees a miss; the call proceeds as if the cache were disabled for that request.
  • closed — propagates the error verbatim. The middleware (or consumer code) surfaces it.

Logical misses (redis.Nil) and corrupted entries are NOT errors — they always behave as miss regardless of failMode. The connection is lazy — Redis unreachable at boot does NOT block New(); the first Get/Set surfaces the failure through failMode.

Late injection — Wiring.Cache and Wiring.SharedCache

Wiring.Cache and Wiring.SharedCache are the escape hatches for cache.store: custom. The framework resolves them AFTER the wire(deps) callback runs, so consumer code that constructs the custom backend can use any infrastructure available to features (additional connections, secrets manager handles, …). The httpclient picks up the late-resolved private cache via httpclient.HttpClient.SetCache (atomic pointer swap; no chain rebuild).

Common patterns

  • Read or write a private cache value: value, ok, err := cache.GetJSON[Profile](ctx, deps.Cache, "user:42:profile") / cache.SetJSON(ctx, deps.Cache, "user:42:profile", v, 5*time.Minute)
  • Read or write a shared cache value: same helpers but against deps.SharedCache — guard against nil first if the operator may have omitted cache.shared:
  • Plug a custom backend (Memcached / Valkey / Hazelcast / …): implement cache.Cache, declare cache.store: custom (or cache.shared.store: custom) in YAML, inject the implementation via bootstrap.Wiring.Cache / bootstrap.Wiring.SharedCache
  • Disable the cache entirely: omit the top-level cache: block. Deps.Cache and Deps.SharedCache stay nil; httpclient cache middleware short-circuits as "bypass"

Validation guarantees at boot

httpclient.New(cfg) runs applyDefaults then Validate before constructing any transport. Issues are accumulated and emitted in a single error so the operator sees the whole list on one boot attempt:

  • services.<name>.baseURL required + must parse as an absolute URL
  • services.<name>.endpoints must declare at least one endpoint
  • endpoints.<name>.method required + must be one of GET/POST/PUT/PATCH/DELETE/HEAD (case-insensitive)
  • endpoints.<name>.path required + must start with /
  • requestCodec / responseCodec must be one of json, xml, or form-urlencoded
  • acceptableStatus values must be in 100..599
  • timeout must be non-negative
  • per-block validation runs for auth, retry, cache, circuitBreaker, tls, pool, redaction, and idempotency (see the dedicated subsections below for the exact rules each one enforces)

Reserved keys

Two blocks documented in the original design schema remain reserved and rejected by Validate at boot: signing (HMAC signing — pending) and responseStream / responseSSE (streaming — pending). The parser accepts every YAML shape for those keys and the validator emits a phase-naming error so operators never silently opt into behavior that is not yet wired. Every other block from the original schema (auth, authProviders, retry, cache, circuitBreaker, pool, tls, redaction, idempotency) is fully implemented.

Defaults cascade

Headers compose defaults → service → endpoint (last write wins) at construction time, so the request path performs zero map lookups against the declarative YAML. Timeout cascades service → defaults → 30s framework fallback. Pool defaults applied to every per-service http.Transport:

  • MaxIdleConnsPerHost: 100
  • MaxConnsPerHost: 200
  • IdleConnTimeout: 90s

Per-service pool: overrides are reserved for the TLS / connection-pool phase.

Codecs

The codec registry is package-private — there is no httpclient.RegisterCodec and no consumer-facing extension surface. Three codecs ship today:

  • json (default) — encoding/json; Content-Type application/json
  • xml — encoding/xml; Content-Type application/xml; struct fields use xml:"..." tags
  • form-urlencoded — net/url.Values.Encode; Content-Type application/x-www-form-urlencoded. Accepts url.Values, map[string]string/map[string][]string, or struct (field name lowercased by default; override with form:"key[,omitempty]"). form is the short alias on the tag side.

A YAML or tag that names an unknown codec rejects at boot.

InlineAuth — credentials supplied per call

YAML-declared auth providers (oauth2-client-credentials, bearer-static, basic, etc.) cover the case where the framework knows the credentials at boot time — one client of the upstream, one provider declared, picked by every call. InlineAuth is the inverse case: the credentials are runtime values the framework cannot know in advance.

Canonical motivation: a webhook delivery service that has thousands of customer rows in the DB, each carrying its own Bearer token / API key / Basic password. Registering one named YAML provider per customer is not viable; instead the handler reads the customer row and passes the credential inline on each call.

Struct shape:

type InlineAuth struct {
    Bearer string      // → Authorization: Bearer <Bearer>
    APIKey *APIKeyAuth // → custom header (default X-API-Key)
    Basic  *BasicAuth  // → Authorization: Basic base64(Username:Password)
}

type APIKeyAuth struct {
    Header string  // header name; defaults to "X-API-Key" when empty
    Value  string  // required
}

type BasicAuth struct {
    Username string  // required
    Password string  // required
}

Exactly one scheme must be set. The framework picks whichever of Bearer / APIKey / Basic is populated. Setting zero schemes (a non-nil *InlineAuth with all three empty/nil) or more than one returns *HttpError{Cause: ErrTokenAcquire} before dialing — the framework refuses ambiguous shapes rather than guessing.

What each scheme produces on the wire:

SchemeOutbound headerHeader value
Bearer: "abc123"AuthorizationBearer abc123
APIKey: &APIKeyAuth{Value: "k"}X-API-Key (default)k
APIKey: &APIKeyAuth{Header: "X-Tenant-Key", Value: "k"}X-Tenant-Keyk
Basic: &BasicAuth{Username: "u", Password: "p"}AuthorizationBasic dTpw (base64 of u:p)

Precedence vs YAML providers. Setting InlineAuth alongside AuthProvider in the same CallConfig is allowed — InlineAuth wins, the named YAML provider is ignored for that call. This makes "override the service's default provider only for this customer" a single-field change.

Observability. The slog observation field authProvider logs inline:bearer, inline:apikey, or inline:basic so dashboards can split inline calls from named-provider calls without parsing extra fields.

Middleware integration. The framework materializes InlineAuth into an ephemeral auth.AuthProvider internally and runs it through the same auth middleware (position 3 of the chain). Every other layer — logging, idempotency, cache, retry, breaker, transport — behaves identically to a YAML-provider call.

What does NOT come with InlineAuth. Inline credentials are static for the duration of one call: there is no token cache (the credential was already supplied), no single-flight (no acquisition happens), no revocationOnUnauthorized retry (no provider to invalidate). Those features only make sense for OAuth-style flows where the framework owns the token lifecycle. If you need OAuth client-credentials per customer dynamically, declare a credentials-exchange provider in YAML with requestFieldsFromCtx instead — that path does have a per-identity token cache.

End-to-end webhook example:

// Handler receives an inbound event; loads the destination customer's
// webhook config from the DB; delivers the event to the customer.
func (h *EventDeliveryHandler) Handle(ctx *configuration.AppContext, evt OrderEvent) error {
    cust, err := h.customers.Load(ctx, evt.CustomerID)
    if err != nil {
        return err
    }
    _, err = httpclient.Call[deliverEventRequest, struct{}](
        ctx, h.http,
        "webhooks", "deliver",         // placeholder endpoint in YAML
        deliverEventRequest{Body: evt.Payload},
        httpclient.WithConfig(httpclient.CallConfig{
            // URL + method + path from the customer's stored config
            BaseURL: cust.WebhookHost,
            Method:  cust.WebhookMethod,   // "POST" / "PUT" / "PATCH"
            Path:    cust.WebhookPath,

            // Credentials from the customer row — no YAML provider per customer
            InlineAuth: customerAuthToInline(cust.AuthConfig),

            // Per-customer retry policy (some are flaky)
            Retry: &httpclient.RetryOverride{
                MaxAttempts:  cust.MaxAttempts,
                Backoff:      "exponential-jitter",
                InitialDelay: 200 * time.Millisecond,
                MaxDelay:     10 * time.Second,
                RetryOn:      []string{"502", "503", "504", "network", "timeout"},
            },
        }),
    )
    return err
}

// customerAuthToInline picks the right scheme based on what the customer
// stored. Returns nil when the customer chose unauthenticated webhooks.
func customerAuthToInline(cfg CustomerAuthConfig) *httpclient.InlineAuth {
    switch cfg.Kind {
    case "bearer":
        return &httpclient.InlineAuth{Bearer: cfg.Token}
    case "apikey":
        return &httpclient.InlineAuth{APIKey: &httpclient.APIKeyAuth{
            Header: cfg.HeaderName,  // empty → defaults to X-API-Key
            Value:  cfg.APIKey,
        }}
    case "basic":
        return &httpclient.InlineAuth{Basic: &httpclient.BasicAuth{
            Username: cfg.Username,
            Password: cfg.Password,
        }}
    }
    return nil
}

The YAML endpoint webhooks.deliver is a placeholder: it declares method: POST and path: / (defaults) just so the YAML schema validates; every dimension that matters at runtime comes from CallConfig. The handler is the only place that knows the call crossed the network — the middleware chain, logging, redaction, and metrics treat it identically to any other outbound call.

RetryOverride fully replaces the endpoint's YAML retry policy when non-nil — no field-level merging. The framework defaults fill any field the caller leaves zero (MaxAttempts falls back to the enabled-default 3, Backoff falls back to exponential-jitter). The POST/PATCH safety gate still applies: even an override forcing MaxAttempts > 1 is clamped to 1 unless the endpoint declares idempotency.

2. Additive runtime injection

  • WithExtraHeader(key, value) — per-call header on top of the cascade
  • WithExtraQuery(key, value) — per-call query parameter

Pure runtime concerns the YAML cannot anticipate (per-call tenant id generated in the handler, ad-hoc query parameter). Not overrides of any YAML field — true additions on top of the cascade.

3. WithClientCert(tls.Certificate)

Binary tls.Certificate value, not a YAML-declarable string. Builds an ephemeral cloned transport so the registry's pool stays clean. Use for vault-rotated certs delivered via the secrets manager.

Why not include TLS minVersion / cipher suites / CA bundle / pool sizes in CallConfig? Those are bound to the http.Transport materialized once at New. Overriding them per-call would require rebuilding the transport for that single call, invalidating the connection pool and defeating keep-alive. Declare those in YAML and reboot to change.

Flow:

  1. Resolve the service + endpoint from the YAML (unknown name → descriptive error before dialing).
  2. Apply InvokeOptions cumulatively.
  3. binding.BuildRequest assembles the *http.Request (path placeholders, query, headers, body).
  4. Correlation headers are injected from AppContext.ID(): ThreadIDHeader and RequestIDHeader both carry the same value (the codebase has a single per-request identifier).
  5. Per-call extras layer on top (header overrides existing, query appends).
  6. service.httpClient.Do(req) dials.
  7. Response body is read in full, the slog observation is emitted (one record per call), then the response is decoded.

Status branching:

  • 2xx → decoded Resp, nil error.
  • Status in the endpoint's acceptableStatus or in WithAcceptableStatus(...) → decoded Resp and *HttpError{Acceptable: true}. The consumer uses IsAcceptableStatus(err, codes...) to branch.
  • Other non-2xx → zero Resp and *HttpError.
  • Transport failure / decode failure → zero Resp and *HttpError with Cause wrapping the underlying error.

Error model

type HttpError struct {
    Service, Endpoint string
    Method, URL       string
    Status            int
    Headers           http.Header
    Body              []byte
    Duration          time.Duration
    Cause             error
    Acceptable        bool
    Attempt           int  // attempt index — the retry middleware increments this on every retry
}

Helpers:

  • IsAcceptableStatus(err error, codes ...int) bool — true only for *HttpError{Acceptable: true} whose Status matches one of codes (or any acceptable status when no codes are given).
  • IsRetriable(err error) bool — true for 502/503/504, timeouts, DNS failures, generic net.OpError. False for caller cancellation, ErrCircuitOpen, and ErrTokenAcquire — both terminate the retry loop instead of burning attempts on a stuck breaker / IdP.
  • IsCircuitOpen(err error) bool — pattern-matches ErrCircuitOpen; returns true when the breaker rejected the call without dialing.

Sentinels: ErrRequestBuild, ErrResponseDecode, ErrTokenAcquire, ErrCircuitOpen — all active.

Framework defaults always applied (cannot be removed):

  • Headers (canonical MIME names): Authorization, Proxy-Authorization, Cookie, Set-Cookie, X-API-Key.
  • Query keys (case-insensitive): token, api_key, access_token, signature, code.
  • Body JSONPath: no defaults — operators opt in to mask sensitive request/response fields.

Body redaction. Best-effort JSON: the framework tries json.Unmarshal, walks each configured dot-notation path (e.g. $.user.password), replaces the leaf with "[REDACTED]", and re-encodes. Non-JSON bodies and parse failures fall through verbatim — the slog line never fails because of a redaction step.

Query redaction. URL query parameters whose key (case-insensitive) matches any entry in the policy's queryKeys set have their value replaced with "[REDACTED]" in obs.URL before the slog line is written. The path and unlisted parameters survive unchanged.

The original headers, bodies, and URL on the wire are never modified — redaction only affects what slog observes.

Middleware chain

Call dispatches every request through a fixed middleware chain. The order is canonical, not configurable by service or by call — there is one path that every outbound call traverses.

Chain layers (active when the relevant config block is present):

PositionLayerWhat it does
1 (outermost)correlationMiddlewareInjects X-Thread-Id and X-Request-ID from AppContext.ID(), records obs.ThreadID and the configured header name, threads the per-service redaction policy onto the observation
2loggingMiddlewareCaptures request body, times the round-trip, buffers and captures response body, emits the single slog observation record, recovers downstreamThreadId from the response
3authMiddlewareApplies the resolved auth provider; honors revocationOnUnauthorized by invalidating + re-applying on 401
5idempotencyMiddlewareGenerates a UUIDv7 (source ctx) or attaches the supplied key (source explicit); the header persists across retry attempts
6cacheMiddlewareGET/HEAD-only LRU+TTL cache; short-circuits on hit so retry doesn't run; honors Cache-Control: no-store / max-age
8 (outer of breaker)retryMiddlewareLoops up to maxAttempts, replays the body on each attempt, applies the configured backoff and Retry-After
7 (inner of retry)breakerMiddlewarePer-(service, endpoint) state machine. Sits inside retry per Q7: each retry attempt counts as a breaker observation
9 (terminal)transportMiddlewareDials via the per-service http.Client (own http.Transport, own pool, own TLS config)

Positions 4 (HMAC signing) is reserved for a future phase. The chain ordering inverts the design's Section 15 numbering for breaker (7) vs retry (8) to honor Q7's decision that each retry attempt counts as a breaker observation — see the "Circuit breaker" subsection.

A middleware that short-circuits (e.g. a cache hit) returns without calling next; the chain stops there. Layers form a stack: pre-work happens on the way down, post-work on the way back up.

Retry

The chain inserts the retry middleware at position 8 — between the (future) breaker and the terminal transport. Configuration is declarative:

httpClient:
  defaults:
    retry:
      maxAttempts: 3
      backoff: exponential-jitter      # constant | linear | exponential | exponential-jitter
      initialDelay: 100ms
      maxDelay: 5s
      retryOn: [502, 503, 504, network, timeout]
      respectRetryAfter: true

  services:
    keycloak:
      baseURL: https://kc.example.com
      endpoints:
        getUser:
          method: GET
          path: /users/{id}
          retry:
            maxAttempts: 5             # endpoint overrides defaults field by field

Cascade: endpoint values override defaults field by field; framework defaults fill the gaps. When neither block is declared, the policy is single-attempt (no retry).

Backoff strategies (n is the 1-indexed attempt; the sleep happens after attempt n failed and before attempt n+1):

StrategyFormula
constantinitialDelay
linearinitialDelay * n
exponentialinitialDelay * 2^(n-1)
exponential-jitter (default)random(0, min(initialDelay * 2^(n-1), maxDelay)) (full jitter)

All durations are capped at maxDelay. respectRetryAfter honors RFC 7231 Retry-After headers (seconds or HTTP-date) and caps them at maxDelay too.

retryOn accepts numeric status codes and the sentinels network, timeout, dns. Caller cancellation (context.Canceled) is never retried even when timeout/network would otherwise match.

POST/PATCH gate. Non-idempotent methods are restricted to maxAttempts: 1 by default. Declaring an idempotency: block on the same endpoint unlocks higher attempt counts — the upstream sees the same idempotency key on every retry attempt and dedupes. Without idempotency:, a retry: {maxAttempts: 2+} on POST/PATCH aborts boot.

The body is replayed on each attempt from obs.RequestBody (the logging middleware buffers it at chain position 2), so request handlers see the same payload byte-for-byte every time.

Cache

The chain inserts the cache middleware at position 6 — before retry, so a hit short-circuits without traversing the retry loop. The backend is the framework's top-level cache subsystem (see the Cache subsystem section for the cache: YAML block, the cache.Cache port, and the memory / redis / custom backends). The httpClient.defaults.cache: block keeps only the POLICY knobs — whether the layer runs, the default TTL, Cache-Control honoring, per-endpoint cache: { ttl, varyOn } and cacheAcceptable.

httpClient:
  defaults:
    cache:
      enabled: true                   # default true
      defaultTTL: 5m                  # framework default 5m
      honorCacheControl: true         # default true

  services:
    keycloak:
      baseURL: https://kc.example.com
      endpoints:
        getUser:
          method: GET
          path: /users/{id}
          cache:
            ttl: 1m                   # endpoint-specific TTL
            varyOn: [header:Accept-Language, query:tenant]
          acceptableStatus: [404]
          cacheAcceptable: false      # default false; opt-in to cache 404 etc.

Cascade: an endpoint with a cache: block participates in caching, subject to defaults.cache.enabled AND a non-nil Deps.Cache at boot. Endpoint ttl overrides defaults.defaultTTL; the framework default fills in when neither sets a value. When the operator omits the top-level cache: block entirely, the httpclient cache layer is silently disabled (the middleware short-circuits as "bypass").

Cacheable methods. Only GET and HEAD enter the cache. Any other method bypasses unconditionally (obs.CacheStatus = "bypass"). The validator rejects cache: on POST/PATCH/PUT/DELETE endpoints at boot.

Storable responses. 2xx responses are stored by default. Responses whose status appears in acceptableStatus (e.g. 404 on a presence check) are stored only when cacheAcceptable: true on the endpoint — opt-in by design.

Key formula. service|endpoint|method|path|sortedQuery|h:hash(value)...|q:hash(value).... Query parameters are sorted alphabetically so ?a=1&b=2 and ?b=2&a=1 hash to the same key. varyOn accepts header:Name and query:Name entries; values are SHA-256 hashed so they never leak verbatim into the key. The service segment guarantees no cross-service collision when several services share a Redis DB; the backend's keyPrefix (declared on the top-level cache.redis: block) adds an extra namespace scope across deployments.

Cache-Control honoring (when honorCacheControl: true):

  • Cache-Control: max-age=N overrides the configured TTL with N seconds
  • Cache-Control: max-age=0 short-circuits the store entirely (the byte-cache layer treats ttl == 0 as "no expiration", the opposite of what the upstream asked for, so the middleware skips persistence)
  • Cache-Control: no-store or no-cache prevents storing the response

Per-call overrides. WithoutCache() bypasses the cache for one call without touching configuration; WithCacheKey(key) overrides the computed key (rare — typically for tenant-aware key schemes).

Wire shape. The middleware persists an internal cacheEntry JSON envelope (body, headers, status, contentType, contentLength, expiresAt) through the byte-level cache.Cache port. Stored entries remain operator-debuggable via the backend's CLI (e.g. redis-cli GET <key> + json.loads).

Observation. obs.CacheStatus is "hit", "miss", or "bypass" in the single slog record per call. The cache backend (when Redis) additionally emits slog.Warn "cache.redis.transport.error" on transport failures so operators see the underlying problem regardless of the backend's failMode.

Circuit breaker

The chain inserts the circuit breaker middleware INSIDE the retry middleware — so the retry loop observes the breaker on every attempt. The state machine is per (service, endpoint) pair; configuration is shared at defaults.circuitBreaker (the design does not document per-endpoint overrides).

httpClient:
  defaults:
    circuitBreaker:
      enabled: true             # default true (when block present)
      failureThreshold: 5       # default 5 consecutive failures trip
      successThreshold: 2       # default 2 successes in half-open close
      openFor: 30s              # default 30s recovery window

State machine. closed → open → half-open → closed:

  • Closed: every call passes through. A success resets the failure counter. failureThreshold consecutive failures transition to open.
  • Open: every call is rejected with *HttpError{Cause: ErrCircuitOpen} without dialing. After openFor since the open transition, the next call is admitted as the half-open probe.
  • Half-open: one probe at a time (subsequent concurrent half-open requests are rejected as open). Each success counts toward successThreshold; reaching it transitions to closed. Any failure transitions back to open.

Failure attribution. Transport errors and 5xx responses count as failures; 2xx responses count as successes. 4xx is treated as a success — a client-side rejection is not an upstream health signal.

Chain ordering — explicit deviation from design Section 15. The design lists circuitBreaker (7) outer of retry (8). Open question Q7 of the design then explicitly decides that each retry attempt counts as a breaker observation. That decision is only achievable when the breaker sits INSIDE retry — otherwise the breaker sees a single retry-exhausted outcome per call. The implementation honors Q7: the layer slice ends with retry → breaker → transport. The framework documentation is the source of truth on chain order.

When the breaker rejects a call, shouldRetry returns false on ErrCircuitOpen so the retry loop terminates without burning attempts on an open breaker.

Observation. obs.BreakerState reflects the state in effect for the call ("closed"/"open"/"half-open").

Idempotency

The chain inserts the idempotency middleware at position 5 — after logging, before cache and retry. Header injection runs once per call; the header is set on the *http.Request and persists naturally across retry attempts because the retry middleware replays the same request with a fresh body reader. The shared header is what lets the upstream dedupe retried writes.

endpoints:
  charge:
    method: POST
    path: /charges
    idempotency:
      header: X-Idempotency-Key       # required; outbound header name
      source: ctx                     # ctx (default) | explicit
    retry:
      maxAttempts: 3                  # POST allowed because idempotency is configured

Source semantics.

  • source: ctx (default) — the framework generates a UUIDv7 per call (sortable by creation time for upstream dedup logs). The same key is reused across all retry attempts of the same call.
  • source: explicit — the caller must supply the key via WithIdempotencyKey(key). Missing key returns *HttpError{Cause: …requires WithIdempotencyKey} before dialing.

POST/PATCH retry unlock. The retry phase restricts non-idempotent methods to maxAttempts: 1 by default. Declaring idempotency: on the endpoint signals that the framework can safely retry — the upstream sees the same key on each attempt and dedupes. The boot validator accepts retry: {maxAttempts: 2+} on POST/PATCH only when idempotency: is present; the runtime resolveRetryPolicy mirrors the same gate.

AppContext propagation. When the context implements Set(key, value any) (AppContext does), the middleware writes the chosen key under httpclient.idempotency-key. Consumers that need to thread the same value to a parallel pipeline (audit, custom middleware) can read it via AppContext.Get(httpclient.AppContextIdempotencyKey).

Observation. obs.IdempotencyKey carries the key into the single slog record per call when active.

Static and ctx fields are merged into a single body; on a same-named field, ctx wins. Per-tenant single-flight collapses concurrent first-time-misses for the same tenant; different tenants run independently.

Security tradeoff. The per-tenant cache holds bearer tokens in memory keyed by identity hash. Same surface area as the single-tenant cache, just multiplied by tenant count. Pair with revocationOnUnauthorized so a tenant's revoked session does not linger.

oauth2-client-credentials details.

authProviders:
  keycloak-svc:
    type: oauth2-client-credentials
    tokenEndpoint: https://kc.internal/realms/main/protocol/openid-connect/token
    clientId: ${KC_CLIENT_ID}
    clientSecret: ${KC_CLIENT_SECRET}
    scope: ["api.read", "api.write"]
    audience: pay.example.com           # optional
    tokenCache:
      source: jwt-exp                   # jwt-exp | response-field | ttl
      skew: 30s                         # default 30s buffer before expiry
      singleFlight: true                # default true
    revocationOnUnauthorized: true      # default false; opt-in

The token endpoint is called via POST application/x-www-form-urlencoded with the standard grant_type=client_credentials body. The response's access_token is cached per-provider; concurrent cache misses collapse to a single endpoint call via single-flight.

Token TTL source.

  • jwt-exp — the framework decodes the JWT payload (no signature verification — the upstream IdP signed it) and reads the exp claim.
  • response-field — extract the expiry from the token endpoint's JSON response via dot-notation JSONPath (e.g. $.expires_in) with unit: seconds|millis|iso8601 (default seconds).
  • ttl — explicit duration (e.g. ttl: 10m).

In all three cases the cached entry is treated as expired skew seconds before its actual expiry, so the next call refreshes preemptively rather than racing against the upstream clock.

revocationOnUnauthorized. When true, a 401 from the resource server triggers the auth middleware to call provider.Invalidate(), re-acquire a fresh token, and dispatch the original request one more time. The retry happens inside the auth middleware — independent of the retry middleware's policy — so a cached-but-stale credential recovers transparently. Default is false because the optimistic-then-refresh path adds one round-trip on every 401 from the upstream; only opt in when the IdP supports key rotation or revocation paths that can outpace the cache TTL.

forward-bearer details. Reads the verified raw JWT the framework's AuthMiddleware stored on the inbound request via AppContext.SetBearerToken. The token is never cached — it IS the inbound user's credential, and caching would require keying by a hash of the token, risking cross-user contamination. Without a bearer on the AppContext (public route, auth.mode=disabled, background job), the provider returns an Apply error that the middleware wraps in ErrTokenAcquire; shouldRetry returns false on that sentinel so the call fails fast instead of looping.

attach block.

attach:
  as: header                    # header (default) | query | cookie
  name: X-API-Key               # header/query/cookie name
  format: "Bearer {token}"       # optional; {token} placeholder
  value: literal                # header-static only

Defaults apply when omitted: as: header, name: Authorization (for bearer-static/basic), format: Bearer {token} (for bearer-static). basic ignores format because the value already contains the scheme.

Per-call override. WithAuthOverride(providerName) substitutes the provider for one call. Unknown names produce *HttpError{Cause: ErrTokenAcquire} before dialing.

Q5 short-circuit. When a provider returns an error from Apply, the middleware wraps it in *HttpError{Cause: ErrTokenAcquire} and shouldRetry returns false on that sentinel — burning retry attempts on a stuck IdP would only add load. Static providers never trigger this path; dynamic providers (forward-bearer, oauth2) will use it.

Observation. obs.AuthProvider carries the provider name on every slog record when auth is active.

Streaming — download, upload, multipart, SSE

Four streaming surfaces bypass the default "buffer the whole body" path.

Download streaming (responseStream: true)

YAML marks the endpoint; Resp must be httpclient.StreamResponse. The framework hands the open response body to the caller — the caller MUST close it.

endpoints:
  downloadReceipt:
    method: GET
    path: /receipts/{id}/pdf
    responseStream: true
type Req struct { ID string `http:"path,id"` }
resp, err := httpclient.Call[Req, httpclient.StreamResponse](ctx, c, "pay", "downloadReceipt", Req{ID: "ch_42"})
if err != nil { return err }
defer resp.Body.Close()
_, err = io.Copy(out, resp.Body)

StreamResponse.ContentLength is -1 when the upstream uses chunked transfer.

Upload streaming (http:"body,stream" tag)

Field type is io.Reader. The framework pipes the reader to the wire without buffering. Content-Type comes from a http:"header,Content-Type" field or WithExtraHeader. Used for arbitrary binary uploads.

type UploadAvatarRequest struct {
    UserID string    `http:"path,id"`
    Body   io.Reader `http:"body,stream"`
    Mime   string    `http:"header,Content-Type"`
}

Multipart upload (http:"body,multipart" tag, httpclient.Multipart value)

Combines text fields with file streams. The framework writes the multipart body through an io.Pipe, so file content is never fully buffered.

type UploadDocRequest struct {
    UserID string             `http:"path,id"`
    Body   httpclient.Multipart `http:"body,multipart"`
}
req := UploadDocRequest{
    UserID: "u42",
    Body: httpclient.Multipart{
        Fields: []httpclient.MultipartField{{Name: "category", Value: "id-proof"}},
        Files: []httpclient.MultipartFile{{
            Name: "file", Filename: "passport.pdf", MimeType: "application/pdf",
            Content: openedFile,
        }},
    },
}

Server-Sent Events (responseSSE: true)

YAML marks the endpoint; Resp must be httpclient.SSEResponse. The framework spawns a goroutine that parses the upstream's text/event-stream per the WHATWG EventSource spec and delivers events on a buffered channel. The caller MUST call Close() to stop the goroutine and release the connection. Accept: text/event-stream is auto-injected when the request struct does not set it.

resp, err := httpclient.Call[Req, httpclient.SSEResponse](ctx, c, "stream", "subscribe", Req{Topic: "orders"})
if err != nil { return err }
defer resp.Close()
for ev := range resp.Events {
    handle(ev) // ev.ID, ev.Event, ev.Data, ev.Retry
}

Reconnection is the caller's responsibility — the framework does not re-dial when the stream ends. The upstream's retry: hint is surfaced on SSEvent.Retry so the caller can honor it.

HMAC request signing

Per-service signing: block declares an HMAC request-signing policy compatible with payment gateways, Twilio-style webhooks, and AWS SigV4-lite upstreams. The framework injects timestamp + content-sha256 + signature headers on every outbound request, with re-signing per retry attempt so each dial carries a fresh timestamp.

services:
  payment:
    baseURL: https://pay.example.com
    signing:
      type: hmac-sha256                       # required (only supported in this phase)
      keyId: ${PAY_KEY_ID}                    # optional
      keyIdHeader: X-Key-Id                   # required when keyId is set
      secret: ${PAY_SIGNER_SECRET}            # required
      signedHeaders:                          # required, non-empty
        - host
        - x-date
        - x-content-sha256
        - x-idempotency-key
        - content-type
      timestampHeader: X-Date                 # required
      timestampFormat: rfc1123                # optional; rfc1123 | iso8601 | unix-seconds
      contentSHA256Header: X-Content-SHA256   # optional; default X-Content-SHA256; "-" to disable
      signatureHeader: X-Signature            # required
      signaturePrefix: ""                     # optional; e.g. "HMAC-SHA256 "

Canonical string (AWS SigV4-lite shape):

METHOD\nPATH\nQUERY_CANONICAL\nHEADERS_CANONICAL\nSIGNED_HEADERS_LIST\nSHA256_HEX(BODY)
  • METHOD — uppercased HTTP verb
  • PATH — URL path component (no query); empty path becomes /
  • QUERY_CANONICAL — sorted alphabetically by key; each key=value URL-encoded; repeated keys sorted by value
  • HEADERS_CANONICAL — for each header in signedHeaders (lowercased + sorted): name:trimmed_value\n; multi-value headers joined by ,
  • SIGNED_HEADERS_LIST — signedHeaders joined by ;
  • SHA256_HEX(BODY) — lowercase hex of SHA256(body); SHA256 of empty input when body is absent (e3b0c4...)

Signature: hex(HMAC_SHA256(secret, canonical)). Lowercase hex output. Written to signatureHeader with signaturePrefix prepended.

Chain position 8 — inner of retry and breaker, just before transport.

  • Inner of retry → each attempt re-signs with a fresh timestamp (idempotent on the upstream side when the idempotency key is in signedHeaders).
  • Inner of breaker → a rejected attempt does not waste signing work.
  • Outer of transport → the request that actually dials carries the signature headers.
  • Cache hits (short-circuit at position 5) skip signing entirely — correct, because no dial happens.

What can be in signedHeaders. Only headers that are present when signing runs (position 8): host, authorization (set by auth at position 3), x-idempotency-key (set by idempotency at position 4), content-type / any header from the defaults/service/endpoint cascade, WithExtraHeader / CallConfig overrides, plus the framework-injected timestampHeader and contentSHA256Header. Headers added by anything downstream of position 8 (none today) cannot be referenced.

Auto-redaction. The framework automatically adds signatureHeader and keyIdHeader (when set) to the per-service redaction policy — the values are redacted in slog observations but transmitted untouched on the wire. The redaction cascade is union-only; operators cannot un-redact.

Per-call override: none. Signing is part of the API contract; change the YAML and reboot.

Composition pattern

Application handlers never depend on *httpclient.HttpClient directly. The DDD layering is:

  1. bootstrap.Deps.HttpClient exposes the registry singleton.
  2. Each feature constructs an infra/external/<svc>.go service struct, passing d.HttpClient to its constructor (e.g. appexternal.NewIdPService(d.HttpClient)).
  3. The infra service struct holds the typed Call surface (request/response DTOs with http:"..." tags, mapping vendor→domain) and exposes business-vocabulary methods.
  4. The handler in application/handlers/ depends on the infra service struct and calls business methods — it never imports httpclient and never knows the call crossed the network.

Swapping HTTP for gRPC or a fake never touches application/.

Outbound error handling

A *HttpError returned by httpclient.Call does not implement domain.NotificationCarrier. That is deliberate: only the consumer knows whether a 404 from Keycloak is "the user does not exist in our domain" (→ 404 with a typed not-found notification), "the gateway is misconfigured" (→ 502), or "the upstream is down" (→ 503). The framework refuses to guess.

The flow inside a Command/Query handler is the canonical one — every outbound failure that is not translated by the handler falls through to pipeline.Run's default branch:

  1. Handler calls the infra/external/<svc>.go service struct → receives *HttpError.
  2. Handler returns the error verbatim → pipeline.Run tests against NotificationCarrier, the test fails, the error becomes Result.Exception.
  3. RespondFromResult on the Exception branch emits 500 InternalServerErrorNotification with the English default message; the underlying cause stays on the server log and never leaks to the wire.

That is the correct outcome for an untranslated failure — same posture the framework already takes for any panic or non-carrier escape from a handler. To surface a different status with typed identity, the handler translates the *HttpError into a service-defined notification before returning, exactly like it would for a domain rejection. Pair a custom Notification declaring Semantic() with one of the wrappers documented in Quick reference → Error helpers (exception.SingleNotificationError / exception.FieldErrorWithCause for application handlers; infra.FieldErrorWithCause when the translation lives inside the adapter):

// service-defined notifications — each carries its own Semantic
type KeycloakUserNotFoundNotification struct{ domain.ApplicationNotificationBase }
func (KeycloakUserNotFoundNotification) Semantic() domain.NotificationSemantic {
    return domain.SemanticNotFound  // → 404
}

type KeycloakUnavailableNotification struct{ domain.ApplicationNotificationBase }
func (KeycloakUnavailableNotification) Semantic() domain.NotificationSemantic {
    return domain.SemanticUnavailable  // → 503
}

// handler — translates the outbound failure into the service's domain vocabulary
func (h *FetchUserHandler) Handle(ctx *configuration.AppContext, cmd *FetchUserCommand) (UserResult, error) {
    user, err := h.kc.FetchUser(ctx, cmd.ID)
    if err != nil {
        var httpErr *httpclient.HttpError
        if errors.As(err, &httpErr) {
            switch {
            case httpclient.IsAcceptableStatus(err, 404):
                return UserResult{}, exception.SingleNotificationError(
                    "Keycloak", "id", KeycloakUserNotFoundNotification{})
            case httpErr.Status >= 500 || httpErr.Status == 0:
                // 5xx OR Status==0 (transport / breaker open / token acquire) → 503
                return UserResult{}, exception.FieldErrorWithCause(
                    "Keycloak", "service", err, KeycloakUnavailableNotification{})
            }
        }
        // anything the handler chooses NOT to translate falls through to 500 InternalServerError
        return UserResult{}, err
    }
    return projectUser(user), nil
}

The returned *ApplicationError implements NotificationCarrier, so pipeline.Run lands on the Failure branch, RespondFromResult reads each notification's Semantic(), and the wire envelope carries the right status plus the typed notificationKey the client can branch on — symmetric with how a domain BuildRules rejection reaches the wire. No respondWithError helper lives in the consumer; the same canonical envelope flows for every failure mode.

Translate inside the adapter when the mapping is fixed. When the same upstream status always maps to the same domain semantic regardless of caller, the infra/external/<svc>.go struct itself can wrap the *HttpError via infra.FieldErrorWithCause(...) and expose a typed sentinel (e.g. ErrKeycloakUserNotFound) — the handler just checks errors.Is. Keep this for mappings that are part of the adapter's contract (a missing user is a missing user); leave caller-specific translation in the handler. Both paths produce a NotificationCarrier; the trade-off is where the policy lives.

The 500 fallback is a feature, not a gap. Any outbound failure the handler does not explicitly translate stays a 500 — the same envelope that surfaces a panic, a nil-pointer dereference, or any other escaped error. A consumer-facing 500 with no further detail is the framework saying "this code path was not designed to handle this outcome"; it surfaces as a bug to fix in the handler, not as a number to negotiate over the wire. Treat 5xx envelopes from your own service as missing translations: add the switch arm + the typed notification.

Service discovery — BaseURLResolver

The per-service baseURL in YAML covers the common case — one static URL per service per environment. For dynamic routing (Consul, Kubernetes Service DNS, per-tenant URL maps, region-aware failover) register a BaseURLResolver:

type BaseURLResolver interface {
    Resolve(ctx context.Context, service string) (string, error)
}

client, err := httpclient.New(cfg, httpclient.WithResolver(myResolver))

When a resolver is registered, every call consults it before dialing — implementations are responsible for their own cache / refresh policy; the framework does not memoize.

Cascade with the YAML:

Schema implication. services.<name>.baseURL is optional in YAML — services that delegate routing to a resolver leave it empty. A non-empty value is still validated as an absolute URL at boot so typos surface immediately. The "both empty" error happens at call time, with the service name in the message.

Reference impl. StaticBaseURLResolver is a map[string]string that returns the entry verbatim and "" for unknown services (fall-through). Useful in tests and for static per-environment maps the YAML cannot express directly:

resolver := httpclient.StaticBaseURLResolver{
    "keycloak": "https://kc.east.example.com",
    "payment":  "https://pay.east.example.com",
}
client, _ := httpclient.New(cfg, httpclient.WithResolver(resolver))

Per-request routing via AppContext. The ctx passed to Resolve is the same one the framework will use for the dial — AppContext satisfies it, so a resolver can read Identity(), Get("key"), or any custom value the caller stored on the context. Per-tenant routing is the canonical example:

type TenantResolver struct{ Mapping map[string]string }

func (r TenantResolver) Resolve(ctx context.Context, service string) (string, error) {
    if appCtx, ok := ctx.(*configuration.AppContext); ok {
        if tenantID, _ := appCtx.Get("tenant.id").(string); tenantID != "" {
            if url := r.Mapping[service+"|"+tenantID]; url != "" {
                return url, nil
            }
        }
    }
    return "", nil // fall back to YAML
}

The handler stores the tenant id on AppContext before calling out (typically via service middleware after AppContextMiddleware); every outbound call automatically reaches the right upstream without per-call wiring. The same pattern works for feature-flag-driven routing, A/B testing, region failover, on-behalf-of-user calls.

Versioning / path prefix via the resolver. The resolver returns a baseURL that is concatenated with the endpoint's YAML path verbatim, so a path prefix lives naturally in the baseURL — useful for API versioning, per-tenant URL prefixes, gradual cutover between v1 and v2. The endpoint path: /users in YAML stays unchanged; only the resolver decides what comes before it:

// Endpoint declared as: path: /users
// Per-tenant version selection via the resolver.
func (r VersionResolver) Resolve(ctx context.Context, service string) (string, error) {
    if appCtx, ok := ctx.(*configuration.AppContext); ok {
        if tier, _ := appCtx.Get("tenant.tier").(string); tier == "early-adopter" {
            return "https://api.example.com/v2", nil // → https://api.example.com/v2/users
        }
    }
    return "https://api.example.com/v1", nil         // → https://api.example.com/v1/users
}

Path placeholders are runtime by design. The endpoint's path template (/users/{id}) lets the request DTO supply placeholder values via http:"path,name" tags — that is the canonical "same endpoint, parameter varies per call" surface and never needs the resolver. Path templates that vary in shape across calls are not supported at runtime — declare each as its own endpoint in YAML and let the caller choose by endpoint name, so log/audit/observability stay tied to one HTTP semantic per endpoint name.

Per-call escape hatch — WithConfig(CallConfig{BaseURL: "..."}). Some shapes of dynamic routing do not fit the resolver pattern cleanly because the URL comes from the current request rather than from ambient context. The canonical cases:

  • Webhook callbacks — the target URL arrives inside the request payload ({"callback_url": "..."}).
  • Payload-driven sharded routing — the shard identifier comes from the request body, not from AppContext.
  • OAuth federation — the IdP URL is discovered per request rather than known at boot.
  • Migration scripts / CLI tools — a one-off binary that needs to target a specific endpoint without wiring a resolver.
  • Integration tests — pointing at an httptest.Server without constructing a resolver around it.

For these, the per-call CallConfig.BaseURL takes precedence over both the resolver and the YAML — the URL is used as-is for this call only; the next call goes back through the normal cascade. Webhook callbacks typically need to vary method and path too — set CallConfig.Method and CallConfig.Path alongside; per-customer credentials come through CallConfig.InlineAuth. For cross-cutting ambient routing (per-tenant, per-region, feature-flag-based) the resolver is still the right tool — it centralizes the decision and runs on every call without per-call wiring.

Also out of scope. A refresh interface (the resolver owns its lifecycle) and framework-level memoization of resolver returns (the resolver decides what is cheap to recompute).

Integration events

The cross-service async-messaging surface — the canonical write-side counterpart to the sync httpclient + the read-side UpstreamSubscription paths. Producers emit typed events into the local integration_events table (atomic with the data write when invoked from a BeforeCommit hook closure with WithTx(tx)); subscribers consume Kafka messages via the framework's Receiver registry, route each payload through the same pipeline.Handler[TCmd, TResult] HTTP routes consume, and dedup per consumer group via omnicore_integration_processed.

The package omnicore/infra/integration (imported as fwintegration) carries the full producer + subscriber surface. Vocabulary follows the canonical pub/sub literature: publishes (events this service emits) + subscribes (events this service consumes) layered on the same integration: YAML block.

Producer — fwintegration.Dispatch

fwintegration.Dispatch(ctx, "userActivated", UserActivatedPayload{Email: email},
    fwintegration.WithTx(tx),                  // atomic with data row + outbox + audit
    fwintegration.WithAggregateID(userID),     // required when YAML declares `aggregate:`
    fwintegration.WithCorrelation(corrID),     // optional — defaults to ctx.CorrelationID()
    fwintegration.WithCausation(causID),       // optional — defaults to ctx.CausationID()
)

YAML:

integration:
  publishes:
    events:
      userActivated:
        eventType: UserActivated   # wire header value
        aggregate: User            # optional — omit for standalone events
        version: 1                 # optional — defaults to 1

Lazy validation. An unknown eventKey at the first Dispatch call site surfaces as ErrIntegrationEventNotConfigured — same posture httpclient adopts for unknown service/endpoint references. The empty publishes block stays a valid steady state for services that only consume integration events; a typo on the producer side fails at the call site with a clear diagnostic rather than break the boot of an otherwise-functional service.

WithTx is the atomicity hook. Threaded from inside a BeforeCommit hook closure where the framework already opened the TX for the entity write. The integration_events row lands in the same Postgres TX as the data row + outbox + audit; any error from Dispatch aborts the entire TX (the persister's defer tx.Rollback(ctx) runs). Without WithTx, the row commits via single-statement autocommit on the package's PG pool — independent of any other write. Multiple Dispatch calls inside the same TX produce N rows in integration_events, all atomic with the data write; BIGSERIAL id reflects call order.

Framework auto-fills event_id (uuid.New() per row), thread_id (ctx.ID()), actor (ctx.ActorSubject() — non-empty by contract, falls back to "anonymous"), created_at (NOW()). correlation_id and causation_id default to ctx.CorrelationID() / ctx.CausationID() when the receiver pipeline populated them — events emitted inside a receiver handler automatically carry the inbound trace chain.

No domain coupling. Domain events (intra-context, observability) and integration events (cross-context, infra primitive) stay conceptually separate. The domain layer never imports fwintegration; the dev places the Dispatch call wherever in application/ or infra/ makes business sense — typically inside a Cmd's BeforeCommit closure for atomic emission, or at standalone call sites (system startup, background job completion) without WithTx.

Handler invariance — HTTP and Kafka are interchangeable transports

The handler registered on the receiver is the same pipeline.Handler[TCmd, TResult] instance an HTTP route consumes. The sample DTO carries ToCommand() (same convention web Request.ToCommand follows). Migrate an endpoint from HTTP to async event-driven without rewriting the handler. Expose the same use case via both transports during a transition window. React to events with handlers proven via HTTP integration tests.

Per-message pipeline (no outer TX)

  1. Read event_id from header (or msg.Key).
  2. Pre-check omnicore_integration_processed — hit → ack Kafka, skip handler (already processed by this consumer group).
  3. Build a fresh *AppContext for the invocation: ID() = new UUID; ActorSubject() = inbound actor header (falls back to "anonymous"); CorrelationID() = inbound correlation_id header or event_id fallback; CausationID() = event_id.
  4. Unmarshal payload into a freshly-allocated sample DTO, call ToCommand(), dispatch the resulting Cmd via the registered handler.
  5. Handler success → INSERT INTO omnicore_integration_processed ... ON CONFLICT DO NOTHING → ack Kafka.
  6. Handler error → RecordIntegrationFailure(...) row written; Kafka offset still advances (failure isolation contract).

Each Repo.Method opens its own short TX as in the HTTP path — no framework-managed outer TX, no persister branch, no AppContext mutation for transaction injection. HTTP↔Receiver symmetry at the persistence layer.

Idempotency contract — at-least-once

Framework provides best-effort dedup via omnicore_integration_processed keyed by (event_id, consumer_group). The race window of milliseconds between handler COMMIT and the dedup INSERT may produce a double-invoke after a crash. Handlers consumed by a Receiver MUST be idempotent by design — recommended patterns:

  • UPSERT via INSERT ... ON CONFLICT DO UPDATE on PG writes (matches the framework's existing BaseRepository.ConstraintBindings posture).
  • Natural-key constraints on PG writes — the second invoke trips the unique violation and the framework translates it via the registered ConstraintBinding.
  • Idempotency keys at the external side for side effects to non-PG systems (email provider, payment provider, downstream HTTP API). Same pattern Stripe / Twilio / GitHub webhooks adopt — pass the event_id as the upstream idempotency key.

The architectural trade-off accepted: an outer TX wrapping handler execution + dedup INSERT would close the race window at the cost of long-lived TX, connection pool pressure, replication lag risk. Pinning idempotency to the handler design keeps the framework's per-Repo-Method short-TX discipline intact.

Failure registry — omnicore_integration_failures

Every handler failure is persisted to omnicore_integration_failures, mirroring omnicore_upstream_failures for parity in operator tooling. Schema:

Audit routing — audit.destinations

Every successful write produces one AuditEvent (granularity B: the aggregate is the event unit, identical to the outbox row). audit.destinations controls where it lands:

  • database → audit.InsertAuditEvent writes a row to the audit_events table inside the same pgx.Tx as the data row + outbox row. The row IS the audit — atomic with the write by construction. Source of truth for compliance and forensics: if COMMIT succeeded, the audit exists in PG.
  • slog → audit.EchoSlog emits a flat top-level slog line after COMMIT. Read-side echo for observability; lossy if the shipper drops events, but the PG row remains the authority. Format is unchanged from the previous best-effort posture — ELK pipelines and dashboards continue working without changes.
YAMLEffect
destinations: [slog, database] (default; block absent) Both active — recommended posture. Atomic durability + cross-service ELK consolidation.
destinations: [database]Only the PG row. Lowest log volume; pair with SQL dashboards.
destinations: [slog]Only the slog line. Matches the framework's pre-redesign best-effort posture.
destinations: []Explicitly disables audit. Table stays provisioned by migration 0001 but no row is written; no slog line is emitted.

Unknown destination tokens (destinations: [kafka]) and duplicates (destinations: [slog, slog]) abort the boot with a diagnostic naming the offender — operator typos surface at startup, not as silent runtime drift. audit.destinations is the only audit knob; the auth.auditClaims allowlist controls which JWT claims appear inside the AuditEvent's payload and stays under auth: because it is a security concern (whitelist what leaves the JWT envelope), not a routing concern.

Interpolation supports three forms inside ${...}:

  • ${VAR} / ${VAR:default} — environment variable (Spring Boot style). Env value wins when set and non-empty; otherwise the default after : is used. Default may contain : freely (regex [^}]*). No :default and env unset → empty string. Env misses are silent — they support dev defaults.
  • ${file:/abs/path} — file contents read once at boot. A trailing \n or \r\n is trimmed; everything else is preserved verbatim, so PEM blocks and similar multi-line payloads round-trip. Missing file or any I/O failure aborts the boot with the path in the error.
  • ${vault:store/path#field} — delegated to the registered bootstrap.SecretResolver. Without a registered resolver the default returns ErrUnsupportedResolver and the boot aborts. Plug a real implementation (HashiCorp Vault, AWS Secrets Manager, …) via bootstrap.RegisterSecretResolver(impl) at process init.

The reserved names file and vault shadow same-named env vars inside ${...} — env-var conventions are uppercase, so the collision is theoretical. file: and vault: failures are strict (boot aborts) on purpose: a missing file or unresolved secret in production is an operational bug, not a silent empty-string default.

Mandatory fields: service, postgres.dsn, mongo.uri, mongo.database, kafka.brokers, kafka.syncGroupId. bootstrap.LoadConfig fails with an error listing missing ones.

The auth: block is optional and defaults to {mode: disabled} when absent — convenient for local development under APP_PROFILE=dev, but rejected at boot under any other profile so prd cannot ship without authentication wired. When mode: jwt, the schema requires issuer + audience + exactly one of jwksUrl / publicKeyPem; the externalValidator sub-block is optional. The external-validator cache is opt-in via cacheTtlSeconds and default off — see the Authentication section for the revocation-vs-throughput trade-off.

Limitations: no recursion (${A:${B:c}} doesn't work — 1 pass); default cannot contain literal }; when the value can be ambiguous with bool/null in YAML, use double quotes.

Programmatic load (rarely needed — bootstrap.Run does it under the hood):

cfg, err := bootstrap.LoadConfig()         // reads APP_PROFILE, selects microservice.<profile>.yaml
cfg, err := bootstrap.LoadConfigFrom(path) // explicit path; no profile guard

API

  • bootstrap.Run(wire func(Deps) Wiring) error — default path. Loads yaml, builds singletons, calls wire, registers default middlewares, brings up HTTP, runs until SIGINT/SIGTERM.
  • bootstrap.Build() (Deps, *Config, error) — only builds deps, without serving. Useful for tests or custom lifecycle.
  • bootstrap.Serve(ctx context.Context, deps Deps, wiring Wiring) error — uses pre-built deps. Does not import translations nor start the SyncEngine — those using manual Build/Serve handle that.

Types

bootstrap.Deps — built singletons: Config, Logger, Postgres (already configured with audit destinations + claims via WithAudit), Mongo, Translator, Pipeline, ViewReader (queries.ViewReader), HttpClient (*httpclient.HttpClient; nil when microservice.<profile>.yaml carries no httpClient: block), OpenAPIRegistry (*openapi.Registry; nil when Wiring.OpenAPI is unset — openapi.Mount / openapi.MountRaw treat a nil registry as a Fiber-only passthrough). Audit is not an explicit dependency — every Postgres.Insert/Update/Archive/Unarchive/Delete emits the configured destinations automatically (in-TX audit_events row for database, post-commit slog line for slog).

bootstrap.Wiring — service declarations: Translations []translation.Module, Features []bootstrap.Feature, BeforeServe func(*fiber.App, Deps) error (optional), OnShutdown func(context.Context) error (optional), OpenAPI *openapi.Config (optional — opt-in to /openapi.json + Swagger UI; see "OpenAPI / Swagger UI").

bootstrap.Feature — interface every service capability implements: Mount(app *fiber.App, deps Deps). Each feature knows how to register its own routes.

bootstrap.ReadableFeature — opt-in for the read side: Feature + Views() []*infra.ViewDefinition. Bootstrap automatically collects the views from every ReadableFeature declared in Wiring.Features and passes them to the SyncEngine. A slice (not a single view) covers the case where a feature exposes multiple projections (e.g.: users + users_summary).

The composition layer (Feature struct + Wire + main) is separated from the DDD layers: domain/ (pure rules), application/ (commands/handlers), infra/ (domain ports implementation), web/ (owner of the routes). The feature's Mount delegates to web.MountXxx instead of registering routes directly — preserves the DDD ruler "web owns the routes". Where the composition layer lives in the filesystem is the service's decision — the framework only wires up via bootstrap.Run(wireFn).

Common layouts (all supported, none required):

  • Consolidated: bootstrap/ (package main) with main.go + wire.go + <aggregate>_feature.go side by side. Run: go run ./bootstrap. It's the layout used by omnicore-example-users (canonical reference)
  • Go cmd/ convention: cmd/<binary>/main.go + separate package (app/, boot/, etc.) for Wire and Features. Useful for services with multiple binaries
  • Flat: main.go at the root + Wire/Features in a sibling package. Useful for small services

Migrations and CDC artifacts (Debezium connector JSONs, registration scripts) may live at the root (migrations/, debezium/) or co-located with the owning layer (infra/migrations/, infra/debezium/). The example uses the co-located form — semantically they are infra concerns (Postgres schema, CDC config); Go ignores non-.go files in package directories. Override the path via migrations.dir in microservice.<profile>.yaml.

What the framework does behind the scenes

  1. Reads APP_PROFILE from the environment and loads ./microservice.${APP_PROFILE}.yaml (or $OMNICORE_CONFIG_PATH override); rejects boot if auth.mode=disabled under any profile other than dev
  2. signal.NotifyContext(SIGINT, SIGTERM)
  3. infra.NewPostgres + infra.NewMongoDB (defer Close in reverse order)
  4. translation.Default(), pipeline.New(tr).WithLogger(logger), infra.NewMongoViewReader; configures audit on the Postgres adapter via pg.WithAudit(&cfg.Audit, logger, cfg.Auth.AuditClaims)
  5. wire(deps) returns the service's Wiring
  6. validateWiring — rejects boot if Features == nil && BeforeServe == nil (nothing to serve)
  7. Translator.Import of modules in Wiring.Translations
  8. Migrations (ValidateDownExists + Up) if cfg.Migrations.AutoRun=true
  9. collectViews(wiring.Features) — aggregates Views from ReadableFeatures; rejects boot if 2 features declare the same view name (captures Mongo collection collision)
  10. Log "feature registered" per feature with flag readable: true|false
  11. SyncEngine.Start only if there are collected views (services without CDC don't connect Kafka)
  12. Fiber app + default middlewares fwweb.Recover(), fwweb.Logger(), fwweb.AppContextMiddleware(), and fwweb.AuthMiddleware when auth.mode: jwt
  13. GET /health registered automatically (response {"status":"ok"}) — k8s/docker liveness probe without the service programming anything
  14. f.Mount(app, deps) for each feature in declaration order
  15. Wiring.BeforeServe(app, deps) if set (escape hatch for routes/middlewares outside the Feature model)
  16. app.Listen(cfg.HTTP.Addr) in a goroutine; awaits ctx.Done()
  17. HTTP drain in 10s (app.ShutdownWithContext); then Wiring.OnShutdown if set

Custom health (DB ping, external dependencies) must be exposed on another route (/healthz, /ready) via feature or BeforeServe — the framework's /health is pure liveness.

JSON logger on stdout at Info level is the only default. Anyone needing a custom logger (file, datadog) uses Build() + Serve() with their own slog.Logger in Deps, or registers in BeforeServe.

Manual lookup

Most translation in OmniCore is automatic — the Pipeline runs Translator.GetOr on every NotificationKey of the response envelope using AppContext.Language(), and the consumer writes zero lookup code. The escape hatch — for strings that flow outside the Notification path (email subjects, audit lines, human-readable messages on a custom Response, fallback copy for a missing UI string, etc.) — is to call the Translator directly.

The Translator is a process-wide singleton

translation.Default() returns a singleton guarded by sync.Once. On the first call it builds an empty *Translator and imports the seven built-in Core* Modules (CorePTBR, CoreENG, CoreES, CoreFR, CoreDE, CoreIT, CoreNL) — at that point it only knows framework Notification keys.

bootstrap.Run calls translation.Default() once and then imports every translation.Module declared in Wiring.Translations into the same instance. After boot the singleton carries framework + service catalogs in a single map; any code path that needs to translate fetches it without going through dependency injection:

import fwtranslation "github.com/ClaudioSchirmer/omnicore/application/translation"

// In any place that has *AppContext on hand:
subject := fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailSubject", "Welcome")

The fwtranslation alias follows the workspace's fw<segment> convention (fwinfra, fwweb, fwqueries, fwresults, fwresponses) — used whenever the framework's short package name could collide with a consumer package of the same name. The reference example uses the plural translations package and therefore needs no alias in its existing files; doc examples here adopt fwtranslation for unambiguity.

The three lookup methods

MethodSignatureWhen to use
GetOr(lang, key, fallback string) stringDefault. Missing key → returns the fallback silently. Most handlers want this.
Get(lang, key string) (string, error)You want to know a key is missing — for alerting on incomplete catalogs, or when the fallback is expensive to build. Error is always *NotFoundError (carries Language + Key).
Has(lang, key string) boolYou're branching code based on existence (e.g. "if there is a rich HTML version, send rich; otherwise plain text").
 
// GetOr — common case
subject := fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailSubject", "Welcome")

// Get — alert on missing key, build fallback dynamically
subject, err := fwtranslation.Default().Get(ctx.Language(), "WelcomeEmailSubject")
if err != nil {
    var nf *fwtranslation.NotFoundError
    if errors.As(err, &nf) {
        slog.Warn("missing translation", "key", nf.Key, "lang", nf.Language)
    }
    subject = buildFallbackSubject(user)
}

// Has — branch on existence
if fwtranslation.Default().Has(ctx.Language(), "WelcomeEmailBodyHTML") {
    body = renderHTML(fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailBodyHTML", ""))
} else {
    body = renderPlain(fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailBody", "Welcome."))
}

Where to call from

  • Manual handler — directly inside Handle(ctx, cmd). ctx.Language() is the request's language; the handler does not need to receive the Translator via DI.
  • Auto Command Handler — the canonical hook is the Command at both boundaries: Cmd.ToEntity(ctx) / ApplyTo(ctx, t) / ApplyPartiallyTo(ctx, t) on the input side, and Cmd.FromEntity(ctx, t) TResult on the output side. All four receive *AppContext and live in the application layer (Cmd is the only layer allowed to translate ctx-derived data into business fields). The handler exposes no projection field — the projection method lives on the Cmd alongside its input mapping.
  • Background job / outbox consumer — no *AppContext. Pass the language explicitly: fwtranslation.Default().GetOr(configuration.LangPTBR, key, fb). The recipient's preferred language usually comes from the entity (e.g. user.PreferredLanguage), not from a request header.
  • Domain BuildRules — do not. The domain layer cannot import application/translation; emit a typed Notification and let the Pipeline translate it via the same singleton on the way out. This keeps domain/ pure (zero IO, zero application imports).

Keys live where the Notifications do

The singleton has no separate "manual keys" bucket — adding one is a single line in any translation.Module the service already registers. The same customerENG.Translations() map that carries "EmailAlreadyExistsNotification" for the Notification path also carries "WelcomeEmailSubject" for the manual path:

func (customerENG) Translations() map[string]string {
    return map[string]string{
        // Notification key — consumed automatically by the Pipeline
        "EmailAlreadyExistsNotification": "Email already registered.",

        // Manual key — consumed by Translator.GetOr / Get / Has
        "WelcomeEmailSubject":            "Welcome to our service",
    }
}

Keys are arbitrary strings — the framework only imposes a convention for Notifications (struct name via reflection). Manual keys can follow any naming scheme; a common pattern is a domain-style prefix (EmailSubject.Welcome, Audit.UserRestored) to keep them visibly distinct from Notification keys in the catalog. To add a key to N languages, add the same key with translated values to each language's Module — boot importing all of them populates the singleton with one combined map.

No DI, no extra fields on the handler struct, no extra parameter on Mount. Default() after boot is the canonical access point — there is one Translator per process and it already knows everything Wiring.Translations declared.

Parameterized notifications

Notifications carry runtime-driven variables into their translated messages without exploding the catalog into one entry per value. Canonical use case: a length / count / amount that varies per tenant or per request configuration, surfaced verbatim inside the user-facing message ("excede o tamanho máximo de 100 caracteres", where 100 comes from per-tenant config).

Declaration — tvar struct tag

The framework reflects over the notification's exported fields tagged tvar:"<name>" and exposes them as the variables {<name>} substitutes against in the catalog string. The struct field name is irrelevant; only the tag value matters.

type NameMaxLengthExceededNotification struct {
    domain.DomainNotificationBase
    MaxLength int `tvar:"maxLength"`
}
// ENG catalog
"NameMaxLengthExceededNotification": "Name exceeds the maximum allowed length of {maxLength} characters.",
// PTBR catalog
"NameMaxLengthExceededNotification": "O nome excede o tamanho máximo permitido de {maxLength} caracteres.",

Multiple fields produce multiple placeholders. Pointer fields are dereferenced (nil renders as empty string). Unexported fields are skipped — the framework can only walk the exported surface. The reflection plan is cached per reflect.Type in a module-level sync.Map, so repeated emissions of the same notification type pay one type lookup + field reads.

Escape hatch — TranslationVars() method

When the variables cannot be expressed as tvar tags (unexported state, computed values, ctx-aware shaping), declare an optional method:

type SensitiveLimitNotification struct {
    domain.DomainNotificationBase
    threshold int  // unexported — invisible to tag reflection
}
func (n SensitiveLimitNotification) TranslationVars() map[string]string {
    return map[string]string{"threshold": strconv.Itoa(n.threshold)}
}

The method replaces (does not merge with) the tag-based extraction. Detected via type assertion (domain.TranslationVarsProvider), so notifications without it pay nothing.

Per-emit override — Vars on NotificationMessage

When the same notification type ships with default vars from its tags but a specific call site needs to inject additional or overriding values, pass them via the per-emit Vars map. The Rules DSL exposes the helper:

r.AddNotificationWithVars(
    "Name",
    NameMaxLengthExceededNotification{MaxLength: u.NameMaxLength},
    map[string]string{"context": "premium-plan"},
    u.Name,                                  // optional value variadic — same as AddNotification
)

Resolution order at render time (per-emit wins on key collision): tag-derived vars (or TranslationVars() output) ← per-message Vars.

Context label vars — SetVars on NotificationContext

The wrapping context label ("User", "Order") goes through the same Translator as messages. Carry runtime variables for the label itself via:

ctx := domain.NewNotificationContext("UserOf{tenantId}")
ctx.SetVars(map[string]string{"tenantId": "acme"})
// catalog: "UserOf{tenantId}": "Usuário de {tenantId}"
// resolved label on the wire: "Usuário de acme"

Empty map and nil both clear the slot. Scoped views forward to the root — ContextVars() always reads from the root of the chain, mirroring how the message Path prefix composes.

Translation surface — Render and Interpolate

func (t *Translator) Render(lang configuration.Language, key string, vars map[string]string) string
func Interpolate(s string, vars map[string]string) string
  • Render(lang, key, vars) resolves the catalog message + interpolates. Scanner accepts the literal placeholder {<name>} where <name> matches [A-Za-z_][A-Za-z0-9_]*; sequences that do not match ({1bad}, {not closed, isolated {) are written verbatim. Missing catalog key → returns key as fallback AND emits slog.Warn("translation.key.missing", ...) once per (lang, key) tuple. Missing placeholder in vars → leaves the literal {name} in the output AND emits slog.Warn("translation.var.missing", ...) once per (lang, key, placeholder) tuple. Both warns dedupe via a process-level sync.Map. vars == nil and vars == {} behave identically: no substitution, no missing-var warn.
  • Interpolate(s, vars) is the substitution-only step (no catalog lookup). Missing placeholders are left literal without firing warn-once — Interpolate has no (lang, key) context to attribute the miss to.
  • Get(lang, key) and GetOr(lang, key, fallback) remain the canonical no-interpolation lookups, for synthetic notifications without vars (e.g., MissingPermissionNotification in PermissionGate, InternalServerErrorNotification in RespondWithInternalServerError).

Pipeline integration

application/notifications/convert.go::ToContextDTOs resolves vars automatically through domain.MessageVars(msg) and ctx.ContextVars(), then renders via Translator.Render instead of Get. Auto Command Handlers, manual handlers, and audit/events paths inherit the new behavior without code changes — the substitution lives at the boundary that already translates.

Backwards compatibility

Notifications without tvar tags AND without TranslationVars() produce nil from ExtractVarsFromTags → Render behaves identically to Get. Catalog entries without placeholders pass through the scanner unchanged. The new Vars field on NotificationMessage and contextVars on NotificationContext default to nil. No existing call site needs editing.

OpenAPI / Swagger UI

The framework generates an OpenAPI 3.1.0 document from the same Go types the HTTP wrappers already consume — Request DTOs (with json:/path:/query:/filter: tags), Response DTOs (with json:/view: tags), the pipeline.FullBody marker, the HasPathID interface assertions. No swag init, no hand-written YAML, no separate annotations: the spec is a reflection-driven projection of the routes the consumer already wired.

Enable the spec

One line on the wire callback opts in:

func Wire(d bootstrap.Deps) bootstrap.Wiring {
    return bootstrap.Wiring{
        Translations: []translation.Module{...},
        Features:     []bootstrap.Feature{NewUsersFeature(d)},
        OpenAPI: &openapi.Config{
            Title:       "My Service",
            Version:     "1.0.0",
            Description: "Reference microservice for the OmniCore framework.",
            Servers: []openapi.Server{
                {URL: "https://api.example.com", Description: "Production"},
            },
            Contact: &openapi.Contact{Name: "Maintainer", Email: "ops@example.com"},
            License: &openapi.License{Name: "Apache-2.0", URL: "https://apache.org/licenses/LICENSE-2.0"},
        },
    }
}

openapi.Config is the operator-facing identity of the generated document; the framework folds it into the spec's info + servers blocks at boot. Every field beyond Title + Version is optional and omitted from the rendered spec when zero:

With OpenAPI set:

  • Deps.OpenAPIRegistry becomes a non-nil *openapi.Registry threaded into every Feature.Mount(app, deps) call.
  • The framework auto-registers GET /openapi.json + the Swagger UI route (default GET /docs; configurable via openapi.uiPath in the YAML — see "Operator-tunable serving" below) after every feature has mounted.
  • GET /health goes through openapi.MountRaw automatically so it appears in the spec.
  • When auth.mode: jwt is active, the AuthMiddleware.publicRoutes list is auto-extended with GET /openapi.json + the resolved UI path, so the documentation surface never sits behind the bearer wall.

Leaving Wiring.OpenAPI nil keeps everything off: Deps.OpenAPIRegistry stays nil, no spec routes are registered, and openapi.Mount / MountRaw become Fiber-only passthroughs (zero documentation cost).

Operator-tunable serving

Wiring.OpenAPI carries the spec identity (Title, Version, Description, Servers, Contact, License) because that is code-time information about WHAT the service exposes. The operational bits — where the Swagger UI is mounted and whether / redirects to it — live in microservice.<profile>.yaml under openapi: so they can vary per environment without a recompile:

openapi:
  uiPath: /docs           # default: /docs. Path where Swagger UI is served.
  rootRedirect: false     # default: false. When true, GET / → 302 uiPath.
  • Block is optional. Absent → defaults (canonical /docs, no redirect). Present but Wiring.OpenAPI is nil → ignored (no spec means no UI to redirect to).
  • uiPath moves the Swagger UI route. /openapi.json stays canonical because it is internal plumbing the UI fetches — tooling that scrapes the spec relies on a predictable path. Validated at boot: must start with /; must not collide with /openapi.json or /health.
  • rootRedirect, when true, registers GET / → 302 uiPath. Registration happens AFTER feature mounts and BeforeServe, so a service that owns / wins by registration order; the framework logs slog.Warn and skips on collision. Under auth.mode: jwt the redirect route is added to publicRoutes automatically so opening the host root in a browser does not trigger a 401.

Language selector (Swagger UI dropdown)

By default Swagger UI does not let the operator choose what Accept-Language goes on the wire — every "Try it out" call ships whatever the browser sent. openapi.Config.LanguageSelector bool (default false) opts into a global dropdown at the top of the rendered page that injects Accept-Language into every request via Swagger UI's requestInterceptor. Useful to exercise translated error messages without juggling a curl command per language.

OpenAPI: &openapi.Config{
    Title:            "MyService API",
    Version:          "1.0.0",
    LanguageSelector: true, // turn it on; bootstrap fills the rest
}

Wiring.Translations is mandatory. Independent of LanguageSelector, the boot guard validateWiring rejects an empty Wiring.Translations slice — notifications, error envelopes (ErrorMessage.Message), and audit fields all flow through the Translator; running with an empty Translator silently produces blank strings in production. Loud-at-boot is the chosen failure mode: every consumer declares at least one translation.Module.

The dropdown content lives on openapi.Config.Languages []LanguageOption ({Label, Value} pairs). Under bootstrap.Run the slice is auto-populated from Wiring.Translations when LanguageSelector=true AND the consumer left Languages empty:

  • Bootstrap walks Wiring.Translations and dedupes by configuration.Language — a service that registers both the framework's CorePTBR and its own apptrans.PTBR() collapses to a single PT_BR entry.
  • The microservice has the final word on which languages appear in the dropdown — registering only apptrans.PTBR() shows only PT_BR, even though translation.Default() loads seven behind the scenes.
  • English-first default. When LangENG is among the surviving entries, the bootstrap rotates it to position 0 so HTML's natural <select> behavior makes English the dropdown's default selection. Declaration order is otherwise preserved (after the rotation). When ENG is absent, declaration order is preserved as-is — the first declared language wins the default slot.
  • Each surviving entry emits {Label: lang.String(), Value: lang.HTTPPrefix()} — Label is what the operator sees in the <option> tag (e.g. PT_BR, ENG), Value is what gets written to the Accept-Language header (e.g. pt, en) and matches the prefix AppContextMiddleware reads at the request boundary.
  • LangUnknown and any language with an empty HTTPPrefix() are skipped (an empty Accept-Language on the wire would be meaningless).

Adding a 5th language to the service is just "register a new translation.Module" — the dropdown picks it up on the next boot without touching openapi.Config.

Override path. An explicit non-empty Languages slice on openapi.Config bypasses auto-discovery — useful for manual Wire flows that bypass bootstrap.Run, or for relabeling entries. The framework does not apply ENG-first rotation on an explicit slice (the consumer is in control of order):

OpenAPI: &openapi.Config{
    Title:            "MyService API",
    Version:          "1.0.0",
    LanguageSelector: true,
    Languages: []openapi.LanguageOption{
        {Label: "English", Value: "en"},
        {Label: "Português", Value: "pt"},
    },
}

Empty Languages after auto-discovery → no selector rendered. A service that opts in but whose Translations all map to languages with an empty HTTPPrefix() still boots normally — the /docs page is byte-identical to the no-selector baseline (no extra CSS, no extra DOM, no requestInterceptor). Label/Value are HTML-escaped on render, so consumer-controlled strings cannot inject script into the page.

Manual handlers with a typed Request DTO

A handler that hand-rolls its dispatch (Bind().Body() → ParseCriteria → BindPath → ToCommand → Pipeline.Dispatch) still owns the same kind of DTOs the canonical path owns. openapi.Mount covers them too — pair it with fwopenapi.RouteSpecOf[TReq, TResp](status) so the consumer just names the Request / Response DTOs:

fwopenapi.Mount(d.OpenAPIRegistry, group, fiber.MethodPost, "/",
    customInsertUser(d.Pipeline, repo, svc),
    fwopenapi.RouteSpecOf[requests.InsertUserCustomRequest, responses.UserCustomResponse](
        fiber.StatusCreated),
    fwopenapi.Doc{Summary: "Create (manual showcase)", Tags: []string{"Users — manual"}})

For state-transition endpoints (DELETE → 204, archive/unarchive returning the envelope without a data field), pass fwresponses.None as TResp — the spec assembler recognizes the sentinel and emits the envelope without data, mirroring the canonical wrappers' fwresults.None / fwresponses.NoBody pairing:

Consumers that need RouteSpec.Strict or RouteSpec.HasPathID (rare on the manual path — neither marker is auto-derivable from the hand-rolled handler) build a hand-written RouteSpec literal instead. RouteSpecOf is the common-case shortcut, not the only path.

For a manual paged GET that emits via fwweb.RespondPaged, pair the same openapi.Mount with the paged sibling fwopenapi.RouteSpecOfPaged[TReq, TResp]. The flag flips the success envelope to data: array<TResp> + pagination: $ref(PaginationInfo) so the rendered spec matches the wire shape — same flag the canonical HandleQueryWithParamsSpec sets automatically:

    fwopenapi.Doc{Summary: "List users (manual showcase)", Tags: []string{"Users — manual"}})

The ?onlyTotal=true runtime variant (envelope collapses to pagination: TotalOnlyPagination{total} and drops data) is documented in prose on each paged operation's Doc.Description — the spec's success schema stays the canonical listing shape so Swagger UI's default render isn't cluttered with a oneOf union on the common path.

Parameter extraction — path, query, header

The framework derives parameters from the route's Fiber path AND the Request DTO's struct tags. Five mechanisms feed the rendered parameters[] block:

  1. Fiber path → {name} templating. Every :name segment in the route's Fiber path becomes {name} on the OpenAPI path. /users/:id/archive renders as /users/{id}/archive; /tenants/:tenantId/users/:id renders as /tenants/{tenantId}/users/{id}.
  2. Request DTO path:"X" tag. Each tagged field of the Request DTO emits one parameters[].in=path entry with the field's reflected type driving the schema. The same field is skipped from the body schema.
  3. Auto-stubbed :id. When RouteSpec.HasPathID is true (every framework wrapper that auto-binds :id) AND the Request DTO didn't tag path:"id", the spec assembler adds a string-typed id path parameter automatically. Combined with custom path tags so compound routes like /tenants/:tenantId/users/:id document every segment without per-route configuration.
  4. Request DTO query:"X" filter:"ops" tag. Each leaf emits one query parameter per declared operator: query:"name" filter:"eq,in,startswith" produces ?name, ?name.in, and ?name.startswith (the bare eq form has no suffix; every other operator surfaces as name.<op>). The same field is skipped from the body schema.
  5. Nested embed groups. A struct-typed Request field carrying query:"prefix" (no filter:) is an embed group — every leaf below contributes a wire key prefixed by its parent. Example: Addresses AddressFilter \`query:"addresses"\` with City *string \`query:"city" filter:"eq,istartswith"\` inside renders ?addresses.city + ?addresses.city.istartswith.
  6. RawSpec.Parameters. Raw routes declare each parameter inline via PathParam / QueryParam or a Parameter literal. The framework normalizes Required=true for every InPath entry at registration time.

Operator coverage — the operators a filter: tag may declare match the operators HandleQueryWithParams recognizes at runtime: eq (default, no suffix), ne, in, nin, gte, lte, gt, lt, startswith, contains, ieq, ine, iin, inin, istartswith, icontains. Each surfaces as its own query parameter in the rendered spec.

Spec lifecycle — Registry, Components, lazy build

The framework builds the spec lazily and caches it for the lifetime of the service. The relevant types:

  • Registry — collects every Operation registered via Mount / MountRaw. One per service (constructed by bootstrap.Run when Wiring.OpenAPI is non-nil). Preserves insertion order so the rendered spec mirrors the order features were wired (useful for diff-friendly snapshots and for Swagger UI's sidebar layout). Last-write-wins on (METHOD, path) collisions.
  • Components — the dedup pool for named-struct schemas the schema generator encounters while walking the type graph. Owned by the Registry and shared across every route. Same named struct referenced from N different DTOs surfaces ONCE in components.schemas; every site emits a $ref: #/components/schemas/<Name> pointer.
  • Spec — the lazily-built document. Built on the first call to Build() or MarshalJSON(); subsequent calls return the cached byte slice. Safe for concurrent use; the spec is immutable for the lifetime of the value, matching the "registry assembled at boot, served forever" pattern.
  • Self-referential types. A struct that owns a pointer to itself (linked list, tree, anything with a *Self field) does not infinite-loop the generator. The first encounter inserts a placeholder under the type's name in Components BEFORE walking its fields; the recursive site finds the placeholder and emits the $ref on its way back up.

Boot-time guarantees

Everything that can be checked at boot, is — so the operator finds out about a broken declaration at start time, not when a consumer opens /docs:

  • OpenAPI uiPath validation. Must start with /; must not collide with /openapi.json or /health. Violations abort boot with a descriptive error.
  • Examples validated against types. Every Doc.RequestExamples + every success-status Doc.ResponseExamples + every RequestBody.Examples + every typed ResponseSpec.Examples is run through json.Marshal + json.Unmarshal with DisallowUnknownFields at Mount / MountRaw time. A typo aborts the boot with "openapi: example <name> on <METHOD path> <slot>: <reason>".
  • Error-status examples loosely validated. Examples on non-success statuses are only checked for JSON validity (the ErrorEnvelope shape is shared and accepts arbitrary errors[] content). The boot still rejects payloads that aren't JSON-marshalable.
  • Per-property example: tag parsing. Failure to parse the tag value against the field's reflected type → boot panic naming the struct + field.
  • Path parameter completeness. A struct field carrying path:"name" that does not match any :name segment on the route, OR a :name segment without a tag AND without HasPathID, surfaces a runtime parameter-stub mismatch (visible in the rendered spec) — the framework does not boot-validate the alignment today, but the runtime BindPath rejects the request at first call.

The framework treats the operation's SuccessStatus as the "happy" envelope and automatically wraps each example's Value in the canonical Response envelope (success:true, status, description, data:<value>).   • Coexist with the default: declare any number of named entries ("happyPath", "duplicateEmail", …) — the framework's canonical envelope appears alongside them under "default" in the dropdown.
  • Override the default: declare "default" explicitly with a custom Value — the explicit entry wins.
  • Remove the default: declare "default" with an empty Value (fwopenapi.Example{}) — the canonical entry is omitted from the rendered spec.

When the consumer declares nothing for an error status, the renderer preserves the pre-Phase-2 shape: a singular example field carrying the framework's canonical envelope. This is backwards-compatible — no existing route gains an unintended dropdown.

Boot-time validation. Every Value is validated once at Mount / MountRaw time. Auth declarations

When auth.mode: jwt, the framework calls openapi.Register with WithAuth(AuthContext{PublicRoutes: ...}). The rendered document gains:

  • components.securitySchemes.bearerAuth (http / bearer / JWT).
  • security: [{bearerAuth: []}] on every operation that is NOT public.
  • An automatic 401 Unauthorized entry in the operation's responses block.

An operation is treated as public when Doc.Public / RawSpec.Public is true OR when its METHOD /path appears in auth.publicRoutes from microservice.<profile>.yaml — the same allowlist AuthMiddleware enforces at runtime.

Hidden vs Public

  • Hidden=true: the operation is excluded from the rendered spec entirely. Still registers on Fiber so the route works at runtime; only the documentation surface omits it. Use for internal upstream / scaffolding routes that have no business appearing in a public spec.
  • Public=true: the operation appears in the spec WITHOUT security: [{bearerAuth: []}] and WITHOUT the 401 entry. Use for routes that genuinely bypass auth (health probes, OIDC discovery proxies, identity demos).

Migrations

Framework manages numbered SQL migration files, with up/down, versioning via its own table, and dirty state recovery. Wrapper over golang-migrate/migrate v4 — we don't reimplement lock/recovery/parsing.

Filename convention

migrations/
  0002_init.up.sql          # service schema
  0002_init.down.sql        # reverse (mandatory)
  0003_add_phone.up.sql
  0003_add_phone.down.sql

Version 1 is reserved for the outbox (injected by the framework via embed.FS in omnicore/infra/migration/embedded/0001_outbox.{up,down}.sql). Services start at 0002+ — do not write outbox SQL manually; the framework guarantees an identical signature across all services (Debezium depends).

Default behavior at boot

  • bootstrap.Run applies all pending migrations before serving HTTP when cfg.Migrations.AutoRun=true (default)
  • Order: wire(deps) → ValidateDownExists → Up(framework) → Up(service) → SyncEngine → serve
  • Migration failure prevents the service from starting (boot returns error)
  • Each migration runs in an isolated transaction — failure = rollback + dirty=true persisted in the tracking table
  • .down.sql mandatory (validated at startup); may be a no-op when reverse is technically infeasible

Tracking

Two separate tables, created automatically by golang-migrate on first execution (no embed SQL for them):

TableWho writesContains
omnicore_framework_migrationsFramework (embedded outbox)version 1
omnicore_migrationsService (files in cfg.Migrations.Dir)version 2+

Separate tables avoid version collision — framework and service may both have "version 1" without conflict.

Each table stores only (version BIGINT PRIMARY KEY, dirty BOOLEAN). The .down.sql is not stored — it is read from disk/embed at Down(N) time.

API

// dir is any path relative to CWD — "./migrations" is just the YAML default
mgr := migration.New(pg.Pool(), "./migrations")
mgr.Up(ctx)              // applies pending (framework + service)
mgr.Down(ctx, 1)         // reverts N service migrations
mgr.Status(ctx)          // (version uint, dirty bool, err error) — service only
mgr.Pending(ctx)         // ([]uint, error) — versions on disk but not yet applied
mgr.Force(ctx, 5)        // recovery: marks version=5, dirty=false
mgr.ValidateDownExists() // checks .down.sql counterpart for each .up.sql

Profile-aware default and strict mode

cfg.Migrations.AutoRun resolves to true under APP_PROFILE=dev and to false under any other profile when the YAML leaves it unset. An explicit YAML value (true or false) wins regardless of profile.

Under the strict default in non-dev profiles, bootstrap.Run does NOT apply migrations automatically. Instead it reads mgr.Status and mgr.Pending and:

  • If dirty=true: aborts boot with a diagnostic naming the version + the Force recovery option.
  • If Pending returns non-empty: aborts boot with a diagnostic listing every pending version + the current DB version + the operator's recovery options (flip autoRun=true + restart, or run the migration out of band).
  • Otherwise: logs "migrations up to date (strict mode)" and proceeds.

Recovery (dirty state)

A migration that fails mid-way leaves dirty=true persisted. Subsequent Up calls fail until Force(version) is called. Force does not create/undo schema — it only resets the tracking pointer. The operator must manually fix the DB state first.

Pool adapter

Adapter pgxpool.Pool → *sql.DB via pgx/v5/stdlib.OpenDBFromPool. The package's official comment guarantees that Close() on the sql.DB does not close the pool — every open/close of migrate.Migrate is isolated, the pool stays alive for the rest of the service.

Mongo schema evolution

Symmetric to the Postgres migration policy, but operating on Mongo read-side projections rather than the PG schema. Covers drift detection between the code-declared ViewDefinition shape and the materialized Mongo collection state, the rebuild trigger, cleanup of orphan fields and documents, and concurrency protection across rolling-deployed pods. The control plane lives entirely in PostgreSQL — the omnicore_mongo_views table created by framework migration 0001. Mongo collections carry only domain data — no framework-reserved _ids.

View versioning

Every ViewDefinition declares a mandatory Version(N) (positive integer). The version is the developer-intent signal — bump it whenever the rebuild-relevant declarative state changes (root table, embeds, DeleteOnArchive, $jsonSchema, collation, capped, time-series). Index-only changes do NOT require a bump.

fwinfra.View("users").
    Version(3).                                                    // ← mandatory
    Root("users").
    EmbedMany("addresses", fwinfra.From("addresses").On("user_id")).
    Indexes(fwinfra.Index("email").Unique())

Version(N) participates in RebuildHash, so the framework detects:

  • Forgot-to-bump — same version in code AND registry but hashes differ → DriftForgotToBump → boot aborts unconditionally (the version is the only intent signal; no escape).
  • Downgrade — code version < registry version → DriftDowngrade → boot aborts unless mongo.rebuild.allowDowngrade: true opts in.

Spec hash

Every ViewDefinition exposes three deterministic SHA-256 hashes:

v.RebuildHash()   // version + rootTable + embeds + DeleteOnArchive + $jsonSchema +
                  // collation + capped + time-series
v.ArtifactHash()  // Indexes only — changes flow through ApplyMongoSpecs, no rebuild
v.Hash()          // Combined identity stamped on the registry row

Hashes are stable across runs and processes — the canonical serializer sorts map keys, normalizes numeric types, normalizes time-series granularity to lowercase, and sorts the index list by deterministic key.

The framework migration 0001 creates the table alongside outbox. Every managed view has one row keyed by view_name:

Partial index omnicore_mongo_views_status_idx ON status WHERE status <> 'done' keeps "show every rebuild mid-flight" queries on a constant-cost path.

Hybrid concurrency primitive

The rebuild path uses two PG-side primitives in tandem:

  • pg_advisory_lock — mutual exclusion across the cluster; auto-release on connection disconnect; no TTL math. Acquired on a pinned pgxpool.Conn via infra.TryAcquireViewLock(ctx, conn, viewName).
  • Status column on the registry row — 'done' | 'processing', with started_at/pid/host populated during a rebuild. Survives crashes (forensic signal) and exposes "what's mid-rebuild?" via plain SQL.

State machine (driven exclusively by ExecuteRebuild):

done  ──UPDATE status='processing', started_at=NOW(), pid, host──>  processing
                                                                    │
                                                            (rebuild executes)
                                                                    │
processing  ──UPDATE status='done', version, hashes, applied_at,
              started_at=NULL──>  done

Crash recovery: if a pod dies between the two transitions, the advisory lock auto-releases on TCP close. The next boot acquires the lock cleanly, reads the row, sees status='processing' AND it just acquired the lock → emits slog.Warn "previous rebuild died at started_at=X, pid=Y, host=Z; taking over" → re-runs BeginRebuild (overwrites started_at/pid/host with own values) → proceeds normally.

Rebuild execution

SyncEngine.ExecuteRebuild(ctx, plan, cfg) runs the sequence on one view, on a pinned pgxpool.Conn:

  1. pool.Acquire(ctx) — pin the connection for the lock's lifetime.
  2. TryAcquireViewLock — if false, read holder via pg_locks+pg_stat_activity, abort with descriptive error.
  3. Defer lock release + connection release.
  4. Detect takeover: if plan.Registry.Status=='processing', emit slog.Warn before the next write.
  5. BeginRebuild — UPDATE registry to status='processing', started_at=NOW(), pid, host.
  6. slog.Info "view.rebuild.start".
  7. Cleanup orphan fields (skip on empty collection): aggregation full-scan ($objectToArray + $unwind + $group) returns observed top-level field names; sample-Compose on ≤5 real Postgres ids returns expected; $unset the difference.
  8. Snapshot existing _id set.
  9. Compose+upsert from Postgres in batches of 1000. Each upsert decrements the snapshot.
  10. Orphan reconciliation: delete (deleteMany the leftover snapshot) or warn per cfg.Orphan.
  11. EndRebuild — UPDATE registry to status='done' + new hashes + applied_at=NOW(), captures previous_* from row's current state via the SQL itself. Last data write.
  12. slog.Info "view.rebuild.end" with counts + duration.

Two fast-path siblings for non-rebuild cases: SyncEngine.InitRegistryOnly (DriftFreshInit under autoRun=true — writes the initial registry row; no rebuild loop) and SyncEngine.RefreshRegistryArtifactOnly (DriftArtifactOnly under autoRun=true — UPDATE-only; indexes already reconciled by ApplyMongoSpecs).

YAML

mongo:
  uri: ...
  database: ...
  rebuild:
    autoRun: check          # check | true | false — default by profile: dev=true / else=check
    orphan: delete          # delete | warn — default delete
    allowDowngrade: false   # default; opt-in for canary / blue-green rollback flow

Strict YAML decoding on mongo.rebuild — unknown keys abort boot, including the removed lockTTL field. Consumer yamls must drop the line.

OMNICORE_MONGO_FORCE_REBUILD=true continues to govern only index divergence in ApplyMongoSpecs (drop+recreate divergent indexes). It does NOT trigger the rebuild path defined here and never drops collections.

Invariants

  1. ValidEntity is only constructed by the domain package — unexported entity() method.
  2. Outbox always in the same SQL transaction — guaranteed by infra.Postgres.
  3. Audit always runs at the persister — every Postgres.Insert/Update/Archive/Unarchive/Delete emits the configured destinations (in-TX audit_events row + post-commit slog echo).
  4. Lifecycle hooks fire INSIDE the TX — afterBegin at position A (before any framework write); beforeCommit at position D (after data + outbox + audit, before COMMIT). Single firing per repo.Method() call regardless of aggregate child count. Non-nil error rolls everything back; NotificationCarrier identity reaches the wire envelope verbatim.
  5. Notifications are typed structs, never strings.
  6. Domain has no IO — only types, validation, rules.
  7. NotificationCarrier is the cross-layer contract for errors.
  8. Kernel notifications embed the base of the correct layer (Domain/Application/Infrastructure).
