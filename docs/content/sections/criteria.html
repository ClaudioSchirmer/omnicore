Criteria — the query DSL

omnicore/infra/db/criteria is a small, pure DSL (stdlib only) you compose in Go inside your infra layer. It is the developer-facing, compile-time way to ask the authoritative store a question — distinct from the Mongo read side, which is the end-user-facing query facade over the eventually-consistent projection. Your repository interface stays in business vocabulary (FindByID, FindByEmail, …); criteria is how the infra implementation fulfills it.

It emits no SQL of its own. You compose a tree; the translator renders it in the active dialect.

// Primary-key shortcut (the fixed ID↔id convention):
u, err := repo.FindOne(ctx, criteria.ByID(id))

// Any alternate key — no hand-rolled SQL:
u, err := repo.FindOne(ctx, criteria.Where(criteria.Eq("Email", email)))

// Boolean composition + order + limit; FindAll returns []*User (children batched):
users, err := repo.FindAll(ctx, criteria.Where(criteria.And(
    criteria.Eq("TenantID", t),
    criteria.Or(criteria.Eq("Status", "active"), criteria.ILike("Name", "bob%")),
    criteria.IsNull("DeletedReason"),
)).OrderByDesc("CreatedAt").Limit(50))

// Archived scope (the DeletedAt gate) lives on the Query, not in the predicate:
archived, err := repo.FindOne(ctx, criteria.ByID(id).OnlyArchived())

Who consumes it

One tree, every relational entry point — which is why the vocabulary is worth learning once:

  • the AggregateLoader — FindOne, FindAll, Exists, Aggregate, AggregateBy;
  • a DirectRepository, with the same read verbs, and as the predicate of its writes (UpdateOne, Delete, Archive, UpdateAll, …);
  • a relational view, which compiles the wire request into this same tree.

Names are Go field names

A criteria never mentions a column. Field names are your Go field names ("Email"), resolved by the same TableSchema the write path and the scanner use — declared there as Field("Email", "email"). A name the schema does not declare is an error at compile time, never a guess. The fields a read join declares answer under the Go name you chose for them, so a join field filters and sorts like any other.

Values are always parameterized — never concatenated — and typed by the schema, not by shape: a probe against a domain.ID-typed field binds in the dialect's native id form (uuid text on Postgres, BINARY(16) on MySQL, RAW(16) on Oracle) even when you hand it a bare string. A string-typed field is text, always.

Two behaviors worth knowing because they are decisions, not accidents. An empty set is a predicate, not an error: In(f) with no values matches nothing and Nin(f) with none matches everything — the same semantics MongoDB gives $in:[]/$nin:[], so the two read backings agree. And the sugar escapes your value: Contains("Name", "50%") matches the literal 50%, not "starts with 50" — Like/ILike take the raw pattern instead, and EscapeLike is exported for when you assemble one yourself.

The query envelope

The concerns that are not part of the boolean predicate are set fluently on the Query: OrderBy / OrderByDesc (declaration order = ORDER BY order), Limit(n) (the row cap; 0 = no cap), Offset(n) (the row skip; 0 = none), and the archived scope — IncludeArchived() / OnlyArchived(), with active-only as the default. 

// Offset pagination — page 3 of 50/page:
page3, err := repo.FindAll(ctx, criteria.Where(criteria.Eq("TenantID", t)).
    OrderByDesc("CreatedAt").Limit(50).Offset(100))

Offset renders in each engine's native form (LIMIT n OFFSET m on Postgres/MySQL, OFFSET m ROWS FETCH NEXT n ROWS ONLY on Oracle/SQL Server). Because a row skip over an arbitrary physical order is meaningless — and SQL Server's OFFSET…FETCH mandates it — a non-zero Offset requires both a positive Limit and at least one OrderBy; violating either is a loud error on FindAll, never a silently wrong page. It applies to FindAll only. For end-user-facing listings prefer the read side's keyset pagination; reach for Offset here when you are iterating the authoritative aggregate on the write side.

The archive gate is not part of the predicate. The where-tree stays DeletedAt-agnostic and the scope decides what happens around it — which is why an archived record is unreachable to every verb but Unarchive without a single handler writing deleted_at IS NULL. A schema that declares no DeletedAt has no marker column, so no gate is emitted at all.

Subqueries — comparing against another SELECT

Everything above compares a column against a value. A subquery makes the right-hand side the result of another SELECT, which is what reaches the questions no list of literals can answer: the roles a user holds directly or through their groups, the users with at least one active phone, the row carrying the newest revision.

The operator set does not change — eq, ne, gt, gte, lt, lte, in and nin all take a subquery the moment the operand can be one. Only EXISTS is genuinely new, because it has no left-hand side at all. 

// users who hold at least one ACTIVE phone — the 1:N reverse filter
users, err := repo.Loader.FindAll(ctx, criteria.Where(
    criteria.Exists(criteria.Sub(schemas.PhoneSchema().AsDirectSchema()).
        Where(criteria.Eq("UserID", criteria.Outer("ID")))),
))

Sub(source) opens the nested SELECT; the fluent setters describe it.

Correlation — Outer is a value, not a builder

Outer(goField) refers to a field of the enclosing statement. It travels as an ordinary comparison value, which is why correlation costs no new operators: every builder that takes a value takes an outer reference, In, Gte, Between and Contains included. 

criteria.Eq("RoleID", criteria.Outer("ID"))

It reaches exactly one level — the immediately enclosing scope. SQL itself would resolve an unqualified name against the innermost scope that happens to have it, silently picking a different table when two levels both declare the field. This framework declares names instead of inferring them, so a reference that does not resolve one level up is refused rather than searched for further out.

The archive gate is automatic here too

A subquery is scoped like every other read. When its source schema declares DeletedAt, the framework adds that table's deleted_at IS NULL to the subquery's own WHERE — you never write it. When the source declares no archive marker there is no column to gate on and nothing is emitted.

Worked example — permissions through roles and groups

Anchored on the join table with read joins forward to roles and permissions, the whole authorization read is one statement: 

q := criteria.Where(criteria.Or(
    // roles the user holds directly
    criteria.InSub("RoleID",
        criteria.Sub(schemas.UserRoleSchema().AsDirectSchema()).Select("RoleID").
            Where(criteria.Eq("UserID", userID))),

    // roles the user holds through a group
    criteria.InSub("RoleID",
        criteria.Sub(schemas.GroupRoleSchema().AsDirectSchema()).Select("RoleID").
            Where(criteria.InSub("GroupID",
                criteria.Sub(schemas.UserGroupSchema().AsDirectSchema()).Select("GroupID").
                    Where(criteria.And(
                        criteria.Eq("UserID", userID),
                        criteria.Exists(criteria.Sub(schemas.GroupSchema().AsDirectSchema()).
                            Where(criteria.Eq("ID", criteria.Outer("GroupID")))),
                    ))))),
))

Five archive gates ride along — the anchor's and one per subquery — and none of them is written above.

A join that only filters is a subquery. Written by hand, that query joins user_groups and groups inside the second subselect. Neither contributes a column to the result: they are there to filter, and filtering is what IN and EXISTS say. The rewrite is the standard semi-join transformation and every engine's planner moves between the two forms. It generalizes, because a subquery projects one column, so that column comes from one table: make that table the source and everything else in the original join is a filter.

One table per subquery, and the type says so

A Sub reads a single table, so it takes a schema that is a single table: a Direct schema. Any other schema is refused at the call, because a node handed to a subquery could only be read in part — and a part taken in silence is what this framework refuses everywhere else.

Every schema becomes one, at the call site, where you can see the reduction happen:

criteria.Sub(schemas.PhoneSchema().AsDirectSchema()).Select("UserID")

AsDirectSchema() returns a copy reduced to its own table — the anchor's columns, its id, its managed slots, its composite decompositions — with children, siblings and the shared base dropped. The schema you called it on is untouched. An aggregate root, an aggregate child, a role, a shared base and a Direct schema all convert, so requiring it costs no reach.

Two kinds do not convert, and say why:

  • a sibling borrows its owner's primary key (declaring ID on it is refused), so on its own it is not a row source — and reducing its owner gives the OWNER's table, not the sibling's; to read that table standalone, declare it with core.NewDirectSchema naming the shared id column;
  • an external schema names an upstream service's mirrored collection, which is not a table on this connection at all.

The one thing no reduction can give you is a column of another table: SUM(a.qty * b.price) has no subquery form here. Everything reachable by filtering does.

The result is an ordinary Direct schema, so it can also anchor a DirectRepository — which writes one statement with no outbox, audit row, revision guard or cascade. That is a real escape hatch over an aggregate's table, and it is left open on purpose: the framework says clearly what the Direct path does not carry, and does not forbid a decision it can carry out correctly.

Writes, and the one engine difference

A subquery works in the predicate of an UPDATE or DELETE as well. MySQL is the one supported engine with a restriction, and it is narrow: a statement may not read its own target table from a subquery (error 1093, "You can't specify target table 'x' for update in FROM clause"). The framework refuses exactly that case on MySQL, at compile time, naming the engine — a subquery over any other table renders there like everywhere else, and the other three engines have no restriction at all.

What the SQL looks like

A subquery's source is always rendered under a derived alias (phones_sq1 — the table, its nesting depth), and every column inside it is qualified by that alias. That is not cosmetic: an unqualified column in a subquery whose own table lacks it binds silently to the enclosing table in SQL, which is the classic NOT IN footgun. Qualifying always makes accidental correlation impossible and makes a subquery over the same table as the statement correct by construction. 

EXISTS (SELECT 1 FROM phones phones_sq1
         WHERE phones_sq1.user_id = users.id
           AND phones_sq1.deleted_at IS NULL)

The enclosing statement renders its own columns exactly as it did before — a subquery beside it changes nothing. Bound arguments are numbered in emission order across every nesting level, so positional dialects ($1, :1, @p1) stay correct.

This whole DSL is an infrastructure API, not a wire vocabulary. Only Go code builds a criteria — an end user's filter is the Request DTO's filter: allowlist, which some layer above deliberately declared and which the read side compiles into this tree. Nothing reaches Sub from an HTTP, GraphQL or gRPC filter, so the Mongo and relational read backings cannot diverge on something one can express and the other silently ignores.
