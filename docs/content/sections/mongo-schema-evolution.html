Mongo schema evolution

Symmetric to the relational migration policy, but operating on Mongo read-side projections rather than the relational schema. Covers drift detection between the code-declared ViewDefinition shape and the materialized Mongo collection state, the rebuild trigger, and concurrency protection across rolling-deployed pods. A full rebuild runs online, blue-green: it builds a fresh physical collection from the relational source while the live one keeps serving, keeps it current with in-flight writes, verifies it, then flips readers to it atomically — no downtime, no half-built collection ever exposed. The control plane lives in the relational backend — the omnicore_mongo_views table created by framework migration 0001, with the blue-green slot pointers added in migration 0002 (present in the Postgres, MySQL, SQL Server and Oracle dialects alike) — and is backend-neutral: drift reads go through the engine's Querier/Dialect and the rebuild mutex through AcquireRebuildLock. View collections carry only domain data (plus the reserved _-prefixed revision watermarks); the one framework-owned Mongo collection is the projection-state registry, omnicore_projection_state — base-revision records and document tombstones (see Table schema) — which lives OUTSIDE the slot machinery: it is never versioned, never rebuilt, and survives every flip (its tombstones expire by TTL; the SyncEngine provisions the index at start).

Three-mode control model

Both migrations.autoRun and mongo.rebuild.autoRun carry the same closed-set enum: check | true | false.

Profile-aware defaults: dev → true, any other profile → check. Explicit yaml value (string "check"/"true"/"false" OR bare YAML bool true/false) wins.

View versioning

Every ViewDefinition declares a mandatory Version(N) (positive integer). The version is the developer-intent signal — bump it whenever the rebuild-relevant declarative state changes (root table, embeds, DeleteOnArchive, $jsonSchema, collation, capped, time-series). Index-only changes do NOT require a bump.

query.View("users").
    Version(3).                                                    // ← mandatory
    Schema(UserSchema()).                                          // ← mandatory; addresses (.Child) auto-project
    Indexes(query.Index("email").Unique())

Version(N) participates in RebuildHash, so the framework detects:

  • Forgot-to-bump — same version in code AND registry but hashes differ → DriftForgotToBump → boot aborts unconditionally (the version is the only intent signal; no escape).
  • Downgrade — code version < registry version → DriftDowngrade → boot aborts unless mongo.rebuild.allowDowngrade: true opts in.

Spec hash

Every ViewDefinition exposes three deterministic SHA-256 hashes:

v.RebuildHash()   // version + rootTable + embeds + DeleteOnArchive + $jsonSchema +
                  // collation + capped + time-series
v.ArtifactHash()  // Indexes only — changes flow through ApplyMongoSpecs, no rebuild
v.Hash()          // Combined identity stamped on the registry row

Hashes are stable across runs and processes — the canonical serializer sorts map keys, normalizes numeric types, normalizes time-series granularity to lowercase, and sorts the index list by deterministic key.

Relational control plane — omnicore_mongo_views

The framework migration 0001 creates the table alongside outbox. Every managed view has one row keyed by view_name:

view_name              TEXT PRIMARY KEY
version                INTEGER NOT NULL CHECK (version > 0)
rebuild_hash           VARCHAR(64) NOT NULL
artifact_hash          VARCHAR(64) NOT NULL
combined_hash          VARCHAR(64) NOT NULL
previous_version       INTEGER
previous_combined_hash VARCHAR(64)
previous_applied_at    TIMESTAMP
status                 TEXT NOT NULL DEFAULT 'done' CHECK (status IN ('done','processing'))
started_at             TIMESTAMP                    -- NULL when status='done'
pid                    TEXT                         -- holder pid during 'processing'
host                   TEXT                         -- holder host during 'processing'
applied_at             TIMESTAMP NOT NULL
applied_by             TEXT NOT NULL                -- "<svc>@pid:<n>" or "manual-reconcile-*"
code_version           TEXT                         -- OMNICORE_CODE_VERSION env
active_collection      TEXT                         -- migration 0002: physical slot serving reads; NULL = the bare <view> collection
shadow_collection      TEXT                         -- migration 0002: slot being built; NON-NULL turns on dual-apply cluster-wide

Partial index omnicore_mongo_views_status_idx ON status WHERE status <> 'done' keeps "show every rebuild mid-flight" queries on a constant-cost path.

The active-slot pointer. A view has a logical name and two physical slots, <view>__0 and <view>__1; active_collection names the one currently serving reads. A NULL pointer means the bare <view> collection is active — the pre-blue-green state every existing deployment starts in, so migration 0002 needs no data backfill. The physical set a view resolves to is therefore {<view>, <view>__0, <view>__1}, three states only until the first flip; storage is bounded at two collections per view forever (no accumulation, no version-named collections to garbage-collect). Every read site resolves view → active slot through an in-memory pointer cache — the registry is read only at boot and on a slow per-lease refresh, never per query, because the pointer changes only on a flip.

Hybrid concurrency primitive

The rebuild path uses two primitives in tandem:

  • A backend-neutral advisory lock — mutual exclusion across the cluster; auto-release on session disconnect; no TTL math. Acquired on a pinned session via engine.AcquireRebuildLock(ctx, viewName), implemented per dialect: Postgres pg_advisory_lock on a pinned pgxpool.Conn, MySQL GET_LOCK(name, 0), SQL Server sp_getapplock and Oracle DBMS_LOCK (ALLOCATE_UNIQUE + non-blocking REQUEST) each on a pinned *sql.Conn. The returned RebuildLock exposes Acquired()/Holder() and a Querier() bound to the pinned session, so the status writes run on the connection that owns the lock.
  • Status column on the registry row — 'done' | 'processing', with started_at/pid/host populated during a rebuild. Survives crashes (forensic signal) and exposes "what's mid-rebuild?" via plain SQL.

State machine (driven exclusively by ExecuteRebuild):

done  ──UPDATE status='processing', started_at=NOW(), pid, host──>  processing
                                                                    │
                                                            (rebuild executes)
                                                                    │
processing  ──UPDATE status='done', version, hashes, applied_at,
              started_at=NULL──>  done

Crash recovery: if a pod dies between the two transitions, the advisory lock auto-releases when the session drops. The next boot acquires the lock cleanly, reads the row, sees status='processing' AND it just acquired the lock → emits slog.Warn "previous rebuild died…; taking over" → re-runs BeginRebuild (overwrites started_at/pid/host with own values) → proceeds normally. A crashed driver may also have left a shadow_collection set and a half-built shadow collection on Mongo; the takeover clears the flag (ending any lingering dual-apply) and drops the abandoned shadow before starting fresh, so no pod keeps writing an orphaned slot.

Blue-green online rebuild

A full rebuild never mutates the live collection. It builds the fresh shadow slot from the relational source while the active slot keeps serving, keeps the shadow current with in-flight writes via dual-apply, verifies it, then flips readers to it with a single registry write and reclaims the retired slot. Two framework properties make this clean: reads go through the active-slot pointer (the flip is one metadata write), and event apply is idempotent — the SyncEngine recomposes the whole aggregate from the source on every event — so the backfill and the live stream may overlap freely, and dual-apply needs no watermark/dedup bookkeeping.

Dual-apply. While a rebuild is in flight (shadow_collection set), every pod fans each recompose and delete into BOTH the active and the shadow slot — because in a consumer group any pod may consume the event for a given aggregate. A shadow write is bounded-retried; if it keeps failing the rebuild is aborted cluster-wide (flag cleared, shadow discarded) rather than failing the live path — the active write and the consumer offset always advance.

The activation fence. Dual-apply must be active on every pod BEFORE the backfill reads anything, or an event applied to the active slot only — after the backfill passed that aggregate — would leave the shadow permanently gapped. This is a bounded-staleness lease, not a stop-the-world barrier: each pod re-reads the pointer at least once per lease before applying and stops consuming rather than apply with a stale view; the driver sets the flag and waits one lease before backfilling, so every live pod has observed it.

Rebuild execution

SyncEngine.ExecuteRebuild(ctx, plan, cfg) runs the blue-green sequence on one view, on a pinned session:

  1. engine.AcquireRebuildLock(ctx, viewName) — pin a session and take the lock; abort with lock.Holder() if another pod holds it; defer lock.Release.
  2. Takeover: if the row is status='processing', slog.Warn; if it also carries a stale shadow_collection (crashed driver), clear the flag and drop the abandoned shadow.
  3. BeginRebuild — status='processing', started_at/pid/host on the lock's pinned-session Querier().
  4. Provision the shadow slot (the inactive one) to the declared shape — indexes, validator, collation/capped/time-series.
  5. Record the shadow on the registry row (shadow_collection) — turning on dual-apply cluster-wide — and wait one lease so every pod's fence has observed it.
  6. Backfill the shadow from the relational source through a bounded producer/consumer pipeline: the streaming root-id scan cuts fixed-size batches (mongo.rebuild.batchSize, default 1000) and hands them to a pool of workers (mongo.rebuild.workers, default 4), each of which set-based-composes its batch and bulk-upserts it — so the relational scan+compose overlaps the Mongo write and independent batches run in parallel. Aggregates that change during the backfill are carried in by dual-apply.
  7. Verify before any reader can see the shadow: reverse completeness (delete shadow documents whose root no longer exists — the tail reconcile of the backfill/delete race), forward completeness (recompose any live source id the shadow is missing — auto-correcting a dropped dual-apply write), and a bounded value sample comparing field shape. On failure the shadow is discarded and the flag cleared — the flip never happens, readers keep serving the untouched active slot.
  8. Flip — one registry write moves active_collection to the shadow and clears shadow_collection; readers resolve to the new slot.
  9. EndRebuild — status='done' + new hashes + applied_at, capturing previous_* from the row's current state. Last hash write.
  10. Settle & reclaim — wait one lease so dual-apply is off everywhere, then drop the retired slot (best-effort; a leaked collection is drop-and-recreated by the next rebuild).

Because the shadow starts empty there is nothing to reconcile against a prior shape — a removed field is simply never composed, a deleted source row simply never written; the one residual case (a row deleted during the backfill, after it was read) is caught by verify's reverse pass. At boot the same online sequence runs, but in the BACKGROUND: /livez comes up immediately (so a long rebuild is never killed by a liveness probe) while /readyz stays 503 until the rebuild finishes and the projection consumer joins — the pod is alive but out of rotation until its read model is ready. While it waits, the 503 body's reason names the view under rebuild and its position in the run (e.g. initializing: rebuilding view "users_view" (2/5)), so an operator who curls the probe sees exactly what the pod is waiting on; before the first view starts (the drift-reconcile window) it reads the generic initializing: view rebuild in progress. A fatal rebuild error exits the process non-zero (the orchestrator restarts it), exactly as the old synchronous boot did. A pod that boots while another instance already holds the rebuild lock is a FOLLOWER: it does not abort — it serves the current active slot and picks up the driver's flip at runtime via the resolver's lease refresh.

Incremental vs full, and rollback. The blue-green path is the full rebuild (a Version bump or the operator RebuildAllViews). The operator ad-hoc RebuildView/RebuildViewSince patch the live collection in place (upsert-only — no orphan hazard) and do not use blue-green. Reverting the framework past migration 0002 drops the pointer columns; the older binary reads the bare <view> collection and, if a flip had already retired it, sees it as a wiped projection and recovers it from source via its existing DriftMongoWiped path — automatic under autoRun=true (dev), while under the check default the wipe surfaces as the same §14.7 boot diagnostic any wiped collection would, which the operator clears (set autoRun=true or run the reconcile) before the pod serves.

Two fast-path siblings for non-rebuild cases: SyncEngine.InitRegistryOnly (DriftFreshInit under autoRun=true — writes the initial registry row; no rebuild loop) and SyncEngine.RefreshRegistryArtifactOnly (DriftArtifactOnly under autoRun=true — UPDATE-only; indexes already reconciled by ApplyMongoSpecs).

YAML

mongo:
  uri: ...
  database: ...
  rebuild:
    autoRun: check          # check | true | false — default by profile: dev=true / else=check
    orphan: delete          # delete | warn — retained for compatibility; the blue-green shadow is always cleaned before the flip, so this no longer suppresses deletion
    allowDowngrade: false   # default; opt-in for canary / blue-green rollback flow
    pointerLeaseSeconds: 15 # 0 = framework default (15s). The bounded-staleness lease of the activation fence: how long the driver waits for every pod to observe the dual-apply flag before backfilling, and the post-flip settle before reclaim. Also bounds a boot rebuild's fence waits — lower it on single-pod / dev to shrink that window.
    workers: 4              # 0 = framework default (4). Concurrent compose+write workers driving the backfill pipeline: each composes a batch of roots and bulk-upserts it into the shadow, batches fan across workers so the relational scan+compose overlaps the Mongo write. The relational pool must carry at least workers+1 connections (the streaming root-id scan pins one).
    batchSize: 1000         # 0 = framework default (1000). Root ids composed + bulk-upserted per batch. Larger batches cut SQL/Mongo round trips at the cost of more memory per in-flight batch; keep each comfortably under Mongo's 16MB command envelope.

Strict YAML decoding on mongo.rebuild — unknown keys abort boot, including the removed lockTTL field. Consumer yamls must drop the line.

OMNICORE_MONGO_FORCE_REBUILD=true continues to govern only index divergence in ApplyMongoSpecs (drop+recreate divergent indexes). It does NOT trigger the rebuild path defined here and never drops collections.

       previous_version, previous_applied_at
