DirectSchema — the engine, anchored on a table instead of an aggregate

The relational engine is reachable through exactly one door: an aggregate. Criteria in four dialects, COUNT/SUM/AVG/MIN/MAX, GROUP BY, existence probes, ordered windows, read joins — all of it hangs off a repository bound to a domain.Entity. DirectSchema opens the same engine onto a plain table. The table is the anchor and the write unit; DirectRepository reads and writes it with the vocabulary you already know.

It is not a second engine. The reads run through the same TableSchema.Resolve, the same criteria compiler, the same declared joins and the same aggregate DSL an AggregateLoader runs through; the writes run through the same statement builders, the same dialect seam and the same generated identity the entity write path uses. What is absent is what belongs to an aggregate — and the absence is the whole point.

The two axes — what it drops, and what it keeps whole

"One table" is the honest description of the WRITE and a misleading one for the READ, so it is worth separating the two axes a repository can reach along.

Vertical — dropped entirely.

An aggregate is a composition downward: a root plus its children, its 1:1 satellites and its shared identity, persisted together in a single transaction with the outbox row, the audit event and the revision guard that make the set one unit. A Direct write has none of it. One statement, one table, no cascade — Child, Sibling and SharedBase are refused at declaration precisely so the shape cannot promise what it will not do.

Horizontal — kept whole.

A read reaches sideways through declared traversals: read.InnerJoin / read.LeftJoin off the anchor, filling fields, answering predicates, ordering, and serving as GROUP BY keys. That is the same reach an aggregate repository has, with the same rules, and none of it is given up here. A Direct read can absolutely touch several tables; a Direct write never does.

So the defining property is not the number of tables in the statement — it is that there is no aggregate and no entity. Nothing here has invariants the framework protects, a lifecycle it drives, or a read model it feeds. What it has is a table, and an engine pointed at it.

Why it exists

Because not every table is a domain concept. A job queue, an import ledger, a lookup table, an outbox of your own, a per-tenant counter: rows the service maintains by hand, with no invariant to protect, no lifecycle to drive and no projection to feed. Modelling one as an entity means paying for machinery that describes nothing about it — a root, rules, modes, a revision token, an outbox row nobody consumes, an audit trail of an operational detail — and, worse, it tells the next reader that this table means more than it does.

And because a business rule usually wants a fact, not an entity. How many active children does this aggregate have, does a row with this key already exist, what do they total over the window — questions whose answer is a scalar. The aggregate DSL has answered them for a long time, and until now only for whoever held an entity's repository.

Three shapes had no supported path, and each one pushed the developer to the same place: hand-written SQL against the neutral transaction, re-deriving placeholders, identifier quoting and id encoding per dialect, with the Go field names of the three-name model dropped along the way.

  • A control table maintained by hand — a query, an insert, an update, a delete, and nothing else.
  • A fact taken from a table that belongs to someone else — counting an aggregate's children without loading them, probing existence before a write, summing over a window inside a rule.
  • A single-table write inside the current transaction — a control row stamped from a lifecycle hook, which has to commit, or roll back, with the write that caused it.
The reuse boundary, stated once.

A Direct repository anchors only on a Direct schema. An entity's schema is refused there — and is entirely welcome as a join target, because a traversal only reads. That is how a control table joins users through the very schema the User entity already declares, without any risk that a criteria-keyed DELETE orphans a child or an UPDATE steps over the revision guard a view depends on.

Declaring one

Same *TableSchema every other path consumes, born from its own constructor. There is no conversion step: the declaration is the descriptor the framework understands. 

func ImportJobTable() *core.TableSchema {
    return core.NewDirectSchema[ImportJob]("job_queue").
        ID("id").                       // mandatory — identity stays domain.ID, as everywhere
        Field("Status", "status").
        Field("Source", "source").
        Field("RunAt", "run_at").
        Field("OwnerID", "owner_id").
        DeletedAt("deleted_at").        // optional — enables the scope gate and Archive/Unarchive
        CreatedAt("created_at").
        UpdatedAt("updated_at")
}

The anchored struct must declare an exported ID domain.ID. An aggregate root carries its id privately in BaseEntity and the loader stamps it through SetID; a plain row has neither, so the id is a field like any other and is scanned like any other column. Without it, a row read back would carry no identity and could not be the target of the next write — silently. 

type ImportJob struct {
    ID       domain.ID   // mandatory
    Status   string
    Source   string
    RunAt    time.Time
    OwnerID  domain.ID

    OwnerName string     // filled by a declared join, never persisted
}

The other way to get one — reducing a schema you already have

NewDirectSchema declares a table that never had an aggregate. The second road starts from a schema that does: TableSchema.AsDirectSchema() returns a COPY of any schema limited to its own table, with the children, siblings and shared base dropped and the original untouched. 

read.InnerJoin(schemas.CustomerSchema().AsDirectSchema()).On("customer_id")
criteria.Sub(schemas.PhoneSchema().AsDirectSchema()).Select("UserID")

It exists because two consumers put exactly one table in their FROM — a read join's target and a criteria subquery's source — and therefore take a Direct schema rather than a node they could only read in part. The full rules, including the two kinds that do not convert, are on TableSchema.

A reduced schema is an ordinary Direct one: it reads through this repository, and it can anchor a write here as well — with everything a Direct write does not carry (§writing), against a table whose aggregate normally provides all of it. That combination is a deliberate escape hatch, not an oversight.

How it differs from its neighbours

The framework has five schema constructors. They are told apart by two independent questions:

ConstructorWhat it mapsWritten?
NewTableSchema[T]An entity's table — root of an aggregate, with children, siblings, a shared base and the revision guard available to it.yes, through the aggregate path
NewSiblingSchema[T]A 1:1 secondary table sharing its owner's primary key. No lifecycle of its own.yes, by its owner
NewSharedBaseSchemaAn identity table several role schemas deduplicate onto.yes, by its roles
NewExternalSchemaAn upstream service's columns, consumed as a view source. Type-less.no — read only
NewDirectSchema[T]A table of this database with no aggregate and no entity behind it. It is the write unit and the read anchor; a read may still traverse outward from it.yes, directly
Direct vs External — different axes, no overlap.

NewExternalSchema names whose the data is: another service's, read-only, a Mongo view source. NewDirectSchema names how the data is modelled: a table with no aggregate over it — and it is read and written, here, in this database.

The repository

The schema goes into the constructor and no row factory is needed: the schema is already anchored to the row type, so the type is cross-checked at construction and a row is allocated by reflection. An entity needs its factory because BaseEntity has to be initialized; a plain row has nothing to initialize. 

jobs := read.NewDirectRepository[ImportJob](eng, ImportJobTable()).
    WithJoins(
        read.InnerJoin(userinfra.UserSchema()).On("owner_id").Field("OwnerName", "name"),
    )

eng is the core.RelationalEngine every repository in the service already receives. WithContextName and WithConstraints chain onto it exactly as their counterparts sit on an entity repository — a unique-constraint violation still surfaces as the typed notification rather than a raw driver error.

The joins are declared here, on the repository, exactly as an aggregate repository declares them — same verbs, same rules (an InnerJoin over a non-nullable key, a LeftJoin into a pointer, one foreign key per traversal so two of them may reach the same table). The …InChild forms do not exist here for the one reason that matters: there is no child.

Writing

Values is keyed by Go field name, resolved through the schema — no physical column name is ever written above infra/. Every write runs inside a transaction (its own, or the caller's under InTx), which is where the affected-row count comes from uniformly on every engine. Whatever the read may traverse, a write touches the anchor table and nothing else: one statement, no cascade, no second table. 

id, err := jobs.Insert(ctx, write.Values{"Status": "pending", "RunAt": t, "OwnerID": owner})

n, err := jobs.Update(ctx, write.Values{"Status": "expired"},
    criteria.Where(criteria.And(
        criteria.Eq("Status", "pending"),
        criteria.Lt("RunAt", cutoff),
    )))

err = jobs.UpdateOne(ctx, write.Values{"Status": "failed"}, criteria.ByID(id))

n, err = jobs.Delete(ctx, criteria.Where(criteria.Lt("RunAt", ninetyDaysAgo)))
err = jobs.DeleteOne(ctx, criteria.ByID(id))

n, err = jobs.Archive(ctx, criteria.Where(criteria.Eq("Source", src)))
n, err = jobs.Unarchive(ctx, criteria.Where(criteria.Eq("Source", src)))

err = jobs.Upsert(ctx, write.Values{                      // keyed on a conflict target,
    "Source":     src,                                    // not on the identity
    "Outcome":    "FAILURE",
    "TotalCount": write.Stamp,                            // += 1, server-side
    "FirstSeen":  write.OnInsert(write.Stamp),            // dated once, never re-dated
    "RepeatedAt": write.OnUpdate(write.Stamp),            // only a SECOND arrival has one
    "LastAt":     write.Stamp,                            // the operation's instant
    "LastIP":     ip,                                     // overwritten on conflict
}, write.OnConflict("Source", "Outcome"), write.KeepArchiveStateOnConflict())

n, err = jobs.UpdateAll(ctx, write.Values{"Status": "cancelled"})   // the deliberate sweep
n, err = jobs.DeleteAll(ctx)

Insert returns the identity the framework minted (UUID v7), so the caller is never left without it. UpdateOne/DeleteOne fail unless exactly one row was affected: zero rows raises the same typed RecordNotFound an entity write raises when its row is gone, and more than one is refused with nothing committed.

A write may consist of stamp verbs and nothing else. A bare write.Values{"Attempts": write.Stamp} emits attempts = attempts + 1 and is a complete write — the increment is a state change the SERVER computes, and the counter is the only column that carries it. The clearing verbs say the same: zeroing a counter and closing a window ({"CurrentCount": write.StampEmpty, "WindowStartedAt": write.StampNull}) is the whole transition, with nothing left over to date beside it. The one shape refused is an empty Values, which binds no column at all and leaves the statement with no SET to render.

Upsert is the one write keyed on something other than the identity: it inserts when nothing matches the key write.OnConflict(...) names, and updates the row that does — in one statement, so two callers racing on the same key cannot both decide the row is missing. Each Values slot declares what happens on a conflict, and the cases are the kinds of column an upsert has:

SlotOn insertOn conflict
an ordinary valueboundoverwritten with the proposed value
write.Stamp on a stamped TIME columnthe operation's instantthe operation's instant
write.Stamp on a stamped COUNTER (StampedCounterField)1col = col + 1, computed server-side

write.OnInsert(write.Stamp) on a stamped columnthe operation's instant (or 1 on a counter)untouched
write.OnUpdate(v)absent — the column takes its DEFAULTbound

write.OnInsert and write.OnUpdate scope a slot to ONE half of the statement — the row it creates, or the row it finds — and each takes a stamp verb as readily as a value. That pairing is the only way to write a column with the framework's own instant on exactly one of the two paths: write.OnInsert(write.Stamp) dates a creation and never re-dates it (a bare write.Stamp would refresh it on every conflict), and write.OnUpdate(write.Stamp) dates only the collision. The caller cannot compute that instant itself — under relational.clock: db it is read from the very transaction the statement runs in — which is precisely why the request travels as a marker instead of a value. write.StampNull and write.StampEmpty scope the same way.

Two things to know about them. An OnUpdate column is left out of the proposed row entirely, so it has to tolerate absence on the creating path: NOT NULL with no DEFAULT makes that path fail, and that is the table's contract to settle. And both wrappers are refused everywhere but an Upsert — on a plain Insert every column is insert-only already, on an Update there is no insert path, and on the conflict key itself scoping says either nothing or something the MERGE dialects reject outright.

The key is named per call, by Go field name, because one table legitimately has more than one way to be conflicted on and four of the five engines take the key on the statement itself. MySQL is the exception, and it cannot be emulated: ON DUPLICATE KEY UPDATE fires on ANY unique key the row violates, not the one named here. On a table with a single unique key the behavior is identical everywhere; with more than one, MySQL may resolve a conflict the other engines would have let fail. Declare one unique key per upserted table and the difference disappears.

A schema declaring DeletedAt must also declare write.UnarchiveOnConflict() (the conflict clause sets deleted_at = NULL) or write.KeepArchiveStateOnConflict() (it does not touch the column). This is the one write that cannot be archive-gated — INSERT … ON CONFLICT has no WHERE for its conflict target, so an archived row still holds the unique key and still absorbs the write, invisibly to every read. Both answers are defensible, so neither is a default. Note that unarchiving does not reset anything: counters continue from where they were, so a flow that must start over needs the old row deleted, not archived.

A stamped COUNTER (StampedCounterField, declared on the schema like any other column) is what makes an upsert able to count: the increment is col = col + 1 evaluated by the server under the row's lock, so two callers landing on the same key at the same moment cannot both read the old value and both write back the same number. It counts per ROW, never across the table — a shared generator handing out values unique to the whole table is a sequence, which is a different thing MySQL and SQLite have no portable form of. Its new value is the server's and the framework does not read it back, so the counter is absent from the outbox payload; nothing downstream suffers, because a Direct write feeds no view in the first place.

It returns only an error. A row count would have to mean the same thing on every backend and it does not — MySQL reports 2 for a conflicting upsert and 1 for an inserting one, while the others report 1 for both — and reporting which path ran would need a RETURNING/OUTPUT clause MySQL has no equivalent for.

Reading

job, err := jobs.FindOne(ctx, criteria.ByID(id))
job.ID            // scanned like any other column
job.OwnerName     // came from users.name through the InnerJoin

list, err := jobs.FindAll(ctx, criteria.
    Where(criteria.And(
        criteria.In("Status", "pending", "retrying"),
        criteria.Contains("Source", "2026-08"),
        criteria.Eq("OwnerName", "acme"),   // a JOIN field in the predicate
    )).
    OrderBy("RunAt").
    OrderByDesc("AttemptCount").
    Limit(50).
    Offset(100))

archived, err := jobs.FindAll(ctx, criteria.Where(nil).OnlyArchived().OrderBy("RunAt"))

ok, err := jobs.Exists(ctx, criteria.Where(criteria.Eq("Source", src)))

total    := read.Count()
attempts := read.SumInt("AttemptCount")
err = jobs.Aggregate(ctx, criteria.Where(criteria.Eq("Status", "pending")), total, attempts)

groups, err := jobs.AggregateBy(ctx, crit, read.By("Status"), read.Count())

The vocabulary is the loader's own — read.Count, read.SumInt, read.By, read.GroupResult are the same constructors, not new ones. Nothing is added on top: there is no FindByID and no Count shortcut, because on the aggregate side both exist only as adapters to a port (domain.Reader[T], the view layer's reader) and neither is engine vocabulary. The canonical spellings are FindOne(ctx, criteria.ByID(id)) and Aggregate(ctx, q, read.Count()).

Inside the current transaction

InTx returns a copy of the repository bound to the framework's open transaction, so its reads see that transaction's uncommitted rows and its writes commit — or roll back — with it. The repository built once at boot is never mutated by one request. 

func (h *ImportHandler) beforeCommit(ctx *configuration.AppContext, tx persistence.TxHandle, id domain.ID) error {
    _, err := h.jobs.InTx(core.UnwrapTx(tx)).Insert(ctx, write.Values{
        "Status": "pending", "Source": "user:" + id.Value(), "OwnerID": id,
    })
    return err
}

Counting an aggregate's children

A child table gets its own Direct schema. The filter costs nothing extra: Resolve already answers ParentID, exactly as it answers CreatedAt, UpdatedAt and DeletedAt. 

func UserPhoneTable() *core.TableSchema {
    return core.NewDirectSchema[UserPhoneRow]("user_phones").
        ID("id").
        ParentID("user_id").
        Field("Number", "number").
        DeletedAt("deleted_at")
}

total := read.Count()
err := phones.Aggregate(ctx, criteria.Where(criteria.Eq("ParentID", userID)), total)

The restrictions — each one, and why

RefusedWhere it failsWhy
Child, Sibling, SharedBase on the schema Panic at declaration, naming the call These compose DOWNWARD, and that is the aggregate's job: root and children persisted together, in one transaction, with the outbox row, the audit event and the revision guard that make an aggregate an aggregate. A Direct write has none of those by design, so declaring the shape here would promise something it cannot keep. Reaching SIDEWAYS is untouched — that is what the joins are for.
An entity/sibling/shared-base/external schema as the repository's anchor Panic at construction One rule, no ambiguity — and no risk of a criteria-keyed DELETE orphaning children or an UPDATE stepping over the revision guard a view depends on. As a join target the same schema is welcome: a traversal only reads.
A schema with no ID(column), or a row type with no ID domain.ID Panic at declaration / construction Identity is not optional and is not inferred. Without the field, a row read back has no identity.
"ID" inside Values Error before any statement Identity is minted by the framework (UUID v7) and returned by Insert. One origin, everywhere.
"CreatedAt" / "UpdatedAt" / "DeletedAt" inside Values Error before any statement The framework stamps the timestamps from the operation's own instant, and the archive transition has its own verbs — writing the column directly would bypass them.
An Upsert with no write.OnConflict(...) Error before any statement The key that decides whether the row already exists is the statement's whole premise; the framework will not guess it from the schema.
An Upsert on a schema declaring DeletedAt, with no archive policy Error before any statement Every other verb is gated on deleted_at IS NULL; an upsert cannot be, because its conflict target takes no WHERE — an archived row still holds the unique key and still absorbs the write. Declare write.UnarchiveOnConflict() or write.KeepArchiveStateOnConflict(): both are defensible, so neither is a default.
A real value in a stamped slot of Values Error before any statement A stamped column's value is the framework's, never the caller's — the write operation's instant for a stamped TIME column, the server-side increment for a stamped COUNTER. The diagnostic teaches the marker: pass write.Stamp to ask for it.
write.Stamp on a plain field Error before any statement A plain field takes its value from Values, so stamping it would silently do nothing.
A write with an empty predicate (criteria.Where(nil)) Error before any statement, on every write verb A criteria assembled conditionally that came out empty would become a full-table sweep, and the call site would not show it. The deliberate sweep has its own verb — UpdateAll / DeleteAll — which says so where it is read.
A scope on the criteria handed to Archive/Unarchive Error The verb is the scope: archive gates on active rows, unarchive on archived ones. Accepting a second declaration would mean silently ignoring one of them.
A second match on FindOne Error (a LIMIT 2 probe) The contract is "expected one"; picking a row silently hides a developer mistake.
Joins into a child (InnerJoinInChild / LeftJoinInChild) Not offered There is no child. The reach here is horizontal — the root's own traversals — and that is all a table has.

What it does not do — and what that costs

No outbox row, no audit event, no domain events, no revision guard, no old-state snapshot, no cascade, no lifecycle hooks.

A Direct write is a SQL command, not an aggregate write. The consequences are concrete and worth stating plainly: a Direct write never feeds a Mongo view (no outbox row means no CDC, no projection), it leaves no audit trail, and it carries no optimistic concurrency — two concurrent updates are last-writer-wins. Update and Delete are multi-row and report a count; there is no 404/409 split beyond the …One verbs' not-found.

Where it must not be used: anything with business rules, a lifecycle, events, or a projected read model. That is an entity, and the aggregate repository is its home. Reaching for a Direct repository there trades every guarantee the write path makes for a shortcut.

What it does keep, because it goes down the same funnel: the criteria vocabulary in every dialect, the single field-resolution surface, the declared read joins with their full reach, the archived scope gate, the framework-generated identity, the typed unique-violation notification, and the transaction. The horizontal axis is untouched; only the vertical one is gone.
