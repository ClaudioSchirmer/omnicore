CommandHandler

The CommandHandler is the processing unit for a write (POST/PUT/PATCH/DELETE). In the recommended pattern, it is a struct that implements pipeline.Handler[TReq, TRes] and is dispatched via pipeline.Dispatch.

Full flow of a POST

Example: POST /customers with body {"name":"John","email":"j@x.com"}.

HTTP Request │ ▼ Fiber middleware: builds AppContext(UUID + Language) │ ▼ Route handler: parses body → CreateCustomerCommand │ ▼ pipeline.Dispatch(p, ctx, cmd, handler) │ └─► defer/recover (panics → Exception) ▼ CreateCustomerHandler.Handle(ctx, cmd) │ ▼ customer := &Customer{Name: cmd.Name, Email: cmd.Email} │ ▼ domain.GetInsertable(customer, nil, "GetInsertable") │ ├─► ensureInit: creates NotificationContext("Customer") │ ├─► resetEntity: clears state, generates a new signature │ ├─► validateForInsert: │ │ ├─► customer.BuildRules() ← your rules │ │ ├─► checkService (if RequiresService) │ │ ├─► modeAllowed: checks Modes() │ │ ├─► id check: insert cannot carry an ID │ │ ├─► runValueObjectValidations │ │ └─► runAggregateValidations │ ├─► checkAllNotifications → if errors: return *DomainError │ └─► build Insertable with metadata │ (signature, entityName, dateTime, events) │ ▼ opts := []WriteOption[*Customer]{} (derived from cmd.AfterBegin / cmd.BeforeCommit when declared) │ ▼ repo.Scope(ctx, opts...).Insert(insertable) │ └─► engine.Insert(ctx, insertable, schema, hook): │ BEGIN TX │ ▸ afterBegin(ctx, customer, txHandle) ← position A (rolls back on error) │ INSERT INTO customers (...) │ INSERT INTO outbox (...) ← atomic! │ IF cfg.Audit.Includes(database): │ ▸ audit.InsertAuditEvent(ctx, tx, ev) ← source of truth (audit_events row) │ ▸ beforeCommit(ctx, customer, id, txHandle) ← position D (rolls back on error) │ COMMIT │ (POST-COMMIT, best-effort:) │ ├─► IF cfg.Audit.Includes(slog): │ │ └─► audit.EchoSlog(ctx, logger, ev) ← flat slog "audit" line │ └─► publisher.PublishAll(ctx, entity.Events()) ← domain events from RegisterEvent (SlogPublisher default; no-op if none) │ ▼ pipeline returns Result[ID] = Success(id) │ ▼ web.RespondFromResult(c, result, fiber.StatusCreated) │ ▼ HTTP 201 Created { "success": true, "status": 201, "description": "Created", "data": "generated-uuid" }

The flow above runs identically whether you wire the route with the framework's ready-made generic handlers or hand-write every step. Pick the path:

  • Auto command handlers — the canonical path: a one-line generic handler plus the Command's ToEntity/FromEntity boundary. The Automatic × Manual table there maps each step above to who owns it.
  • Custom command handler — the same flow wired by hand (a manual pipeline.Handler + explicit routing), naming the facilitator available at each step. Same envelope, pipeline, atomic outbox, audit, and notification semantics — the escape hatch is for wiring control, not a poorer tier.

Composition types — what the write side declares

The read side serves composed documents; the write side is where each composition's raw material is declared. This catalog carries only the primitives with a genuine write-side declaration — the schema-shaped ones a command handler's TableSchema gives rise to. The read-side-only kinds are deliberately absent: ComposedView joins existing views at read time and declares nothing here, and UpstreamSubscription is a cross-service async materialization — both live in the read-side composition catalog, not this one. One summary per kind; the full contract lives in each canonical section:

KindWhat the write side declares / emitsCanonical reference
Aggregate projection Only the TableSchema the repository already declares (root + siblings + .Child(...)). Every write emits one outbox event per aggregate; the SyncEngine recomposes the projection. Nothing view-specific to write. TableSchema
Embed / EmbedMany Nothing new on the write path — the embed reads a MATERIALIZED source (an upstream mirror or a local view) at compose time. The source's own writes (or upstream events) trigger the recompose ripple; the view declares the leg via JoinUpstream(...)/JoinView(...) and the join via .On(...). TableSchema
SharedBase The shared base + role schemas (NewSharedBaseSchema, .SharedBase(...) on each role). Role writes converge the base lifecycle; role/base events recompose the identity document (projected read-side by a SharedBaseView). TableSchema
