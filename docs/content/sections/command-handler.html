CommandHandler

The CommandHandler is the processing unit for a write (POST/PUT/PATCH/DELETE). In the recommended pattern, it is a struct that implements pipeline.Handler[TReq, TRes] and is dispatched via pipeline.Dispatch.

Full flow of a POST

Example: POST /customers with body {"name":"John","email":"j@x.com"}.

HTTP Request │ ▼ Fiber middleware: builds AppContext(UUID + Language) │ ▼ Route handler: parses body → CreateCustomerCommand │ ▼ pipeline.Dispatch(p, ctx, cmd, handler) │ └─► defer/recover (panics → Exception) ▼ CreateCustomerHandler.Handle(ctx, cmd) │ ▼ customer := &Customer{Name: cmd.Name, Email: cmd.Email} │ ▼ domain.GetInsertable(customer, nil, "GetInsertable") │ ├─► ensureInit: creates NotificationContext("Customer") │ ├─► resetEntity: clears state, generates a new signature │ ├─► validateForInsert: │ │ ├─► customer.BuildRules() ← your rules │ │ ├─► checkService (if RequiresService) │ │ ├─► modeAllowed: checks Modes() │ │ ├─► id check: insert cannot carry an ID │ │ ├─► runValueObjectValidations │ │ └─► runAggregateValidations │ ├─► checkAllNotifications → if errors: return *DomainError │ └─► build Insertable with metadata │ (signature, entityName, dateTime, events) │ ▼ opts := []WriteOption[*Customer]{} (derived from cmd.AfterBegin / cmd.BeforeCommit when declared) │ ▼ repo.Scope(ctx, opts...).Insert(insertable) │ └─► infra.Postgres.Insert(ctx, insertable, schema, hook): │ BEGIN TX │ ▸ afterBegin(ctx, customer, txHandle) ← position A (rolls back on error) │ INSERT INTO customers (...) │ INSERT INTO outbox (...) ← atomic! │ IF cfg.Audit.Includes(database): │ ▸ audit.InsertAuditEvent(ctx, tx, ev) ← source of truth (audit_events row) │ ▸ beforeCommit(ctx, customer, id, txHandle) ← position D (rolls back on error) │ COMMIT │ (POST-COMMIT, best-effort:) │ ├─► IF cfg.Audit.Includes(slog): │ │ └─► audit.EchoSlog(ctx, logger, ev) ← flat slog "audit" line │ └─► publisher.PublishAll(ctx, entity.Events()) ← domain events from RegisterEvent (SlogPublisher default; no-op if none) │ ▼ pipeline returns Result[ID] = Success(id) │ ▼ web.RespondFromResult(c, result, fiber.StatusCreated) │ ▼ HTTP 201 Created { "success": true, "status": 201, "description": "Created", "data": "generated-uuid" }

The flow above runs identically whether you wire the route with the framework's ready-made generic handlers or hand-write every step. Pick the path:

  • Auto command handlers — the canonical path: a one-line generic handler plus the Command's ToEntity/FromEntity boundary. The Automatic × Manual table there maps each step above to who owns it.
  • Custom command handler — the same flow wired by hand (a manual pipeline.Handler + explicit routing), naming the facilitator available at each step. Same envelope, pipeline, atomic outbox, audit, and notification semantics — the escape hatch is for wiring control, not a poorer tier.
