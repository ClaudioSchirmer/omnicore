Handler invariance

A handler in OmniCore is written once and stays invariant across the surface it is attached to. The handler carries the business logic; the surface — an HTTP route, a broker receiver, a CSV download, an Excel download, a GraphQL field, a gRPC procedure — decides only the shape of what goes in and what comes out. You do not rewrite a handler to serve a new channel; you attach the same handler to another wrapper.

The principle: a handler is a pure pipeline.Handler[TReq, TRes]. It never learns which surface invoked it. The request context (*AppContext) is the single, uniform vehicle on every surface, so identity, language, cancellation, and authorization overlays apply the same way whether the request arrived over HTTP, off a broker topic, or as a gRPC call. Convenience is the payoff: a new demand is a new attachment, not new logic.
Every way to attach a handler. Two families, each interchangeable across more than one surface — the same handler instance, no rewrite:
  • Command handlers (the write side) attach to HTTP/JSON, to the broker (integration events), as a GraphQL mutation, or as a gRPC unary RPC.
  • Query handlers (the read side) attach to HTTP/JSON, to a CSV download, to an Excel download, as a GraphQL query, or as a gRPC unary RPC.

Command handlers

One pipeline.Handler[TCmd, TResult] (an Auto Command Handler or a hand-rolled one) serves a synchronous HTTP endpoint and an asynchronous cross-service broker receiver from the same instance. The wire payload is adapted to the same Cmd by each side's DTO ToCommand(); everything below the boundary — BuildRules validation, the sealed ValidEntity, the transactional outbox, the audit row — is identical. 

// one handler instance
h := &handlers.InsertCommandHandler[*User, *commands.InsertUserCommand, commands.InsertUserResult]{Repo: repo}

// attach to HTTP (sync request/response)
fwweb.CommandWithBody(d.Pipeline,
    requests.InsertUserRequest{}, requests.InsertUserResponse{}.FromResult,
    h, fiber.StatusCreated)

// attach the SAME h to the broker (async, cross-service event)
reg.From("partners").On("partnerOnboarded", requests.PartnerOnboardedRequest{}, h)

// ...or as a GraphQL mutation (input object reflected from the Request DTO)
gql.Register(fwgraphql.MutationWithBody[requests.InsertUserRequest](
    "createUser", requests.InsertUserResponse{}.FromResult, h))

// ...or as a gRPC unary RPC (pb ↔ DTO bridge compiled at Register)
grpcReg.Register(fwgrpc.CommandWithBody[usersv1.CreateUserRequest, usersv1.CreateUserResponse](
    usersv1connect.UsersServiceCreateUserProcedure,
    requests.InsertUserRequest{}, requests.InsertUserResponse{}.FromResult, h))

The async path additionally gets the framework's canonical guarantees — transactional emission via fwintegration.Dispatch(...WithTx(tx)) from a BeforeCommit closure, at-least-once delivery with per-consumer-group dedup, and an operator-driven retry surface — without the handler being aware of any of it. Migrating an endpoint between transports, or exposing it on both at once, never touches the handler. See Integration events. The gRPC attachment likewise adds only surface concerns — the pb ↔ DTO bridge compiled and boot-checked at Register, the internal-plane auth posture, the Semantic→code mapping — while dispatching to the very same handler instance. See gRPC.

Query handlers

One pipeline.Handler[TQ, queries.Page] (Auto or hand-rolled) feeds a JSON list, a CSV download, and an Excel download from the same instance and the same Request DTO — the same filter allowlist, the same ?fields= narrowing, the same ?search / ?sort / ?includeArchived, the same ToCriteria(ctx) authorization overlays. Only the rendering differs. 

// one handler instance
h := &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery]{
    Reader: d.ViewReader, View: view.Name()}

// attach to HTTP/JSON (paged envelope)
fwweb.QueryWithParams(d.Pipeline,
    requests.FindUsersByParamsRequest{},
    fwresponses.AutoFromDoc[requests.FindUsersByParamsResponse], h)

// attach the SAME h to a CSV download — view + d.Export carry the rest
fwweb.QueryAsCSV(d.Pipeline,
    requests.FindUsersByParamsRequest{}, view, d.Export, h,
    export.WithDelimiter(';'))

// ...or to an Excel (.xlsx) download
fwweb.QueryAsXLSX(d.Pipeline,
    requests.FindUsersByParamsRequest{}, view, d.Export, h,
    export.WithSheetName("Users"))

// ...or as a GraphQL query returning a Relay connection
gql.Register(fwgraphql.QueryWithParams[requests.FindUsersByParamsRequest,
    requests.FindUsersByParamsResponse](
    "users", "User", h))

// ...or as a gRPC unary RPC (shared omnicore/v1 criteria components → the same ToQuery)
grpcReg.Register(fwgrpc.QueryWithParams[usersv1.ListUsersRequest, usersv1.ListUsersResponse](
    usersv1connect.UsersServiceListUsersProcedure,
    requests.FindUsersByParamsRequest{},
    fwresponses.AutoFromDoc[requests.FindUsersByParamsResponse], h))

CSV and Excel share a single format-neutral export core — the column plan (ViewDefinition.ExportPlan()), the hierarchical walk (export.Generate), the labelKey headers, the ?fields= pruning — and differ only by a pluggable web/export.Encoder. Adding a third format is a new encoder, not a new wrapper. See Auto query handlers → Tabular export.

The gRPC list wire reaches the SAME ToQuery / ToCriteria(ctx) path: its per-view request message is composed from the shared omnicore/v1/query.proto components (PageRequest, SortField, a FieldMask read mask, the typed filter wrappers), and the Request DTO's filter: tags remain the single operator allowlist on both wires — clause emission delegates to the same queryschema core the REST/OpenAPI/GraphQL surfaces use, so operator semantics cannot drift. Only file-download rendering (CSV/XLSX) stays REST-only. See gRPC.

Why it matters

The value is not the individual wrappers — it is that they all converge on the same handler contract. A product asks for "the users list, but as a spreadsheet"; you add one QueryAsXLSX line pointing at the query handler you already have. A partner integration needs your "create user" use case driven off their broker topic instead of an HTTP call; you register the existing command handler on a receiver. A sibling service needs to call that same use case synchronously over the internal plane; you register it on the gRPC surface — one declarative line, the same handler. No business logic is copied, no validation is re-implemented, no audit/outbox guarantee is re-derived — because the handler never moved. The surfaces are interchangeable precisely because the handler is invariant.
