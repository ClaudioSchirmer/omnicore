Value objects — ValueObject, EnumValueObject and the composite kind

A value object is a self-validating domain primitive: a field with a rule attached, so the rule lives in exactly one place instead of being copy-pasted into every aggregate that carries the field. Two kinds are split by who owns the rule; a third is split by how many fields the value spans — the sections below.

ValueObject[T] — the raw kind. A primitive whose rule is bespoke — a regex, a length cap, a format check (Email, Phone, ZipCode, Document). It writes its own IsValid.

type ValueObject[T any] interface {
    Value() T
    IsValid(fieldName string, ctx *NotificationContext) bool
}

EnumValueObject[E, T] — the closed-set kind. A primitive backed by an int or a string whose valid values are a fixed set. It does NOT write IsValid — it declares its members and the framework validates membership.

type EnumValueObject[E comparable, T comparable] interface {
    comparable
    Value() T
    Values() []E
    UnknownNotification() Notification
}
The composite kind — a value that spans several fields. Address{Street, City, ZipCode}, Money{Amount, Currency}, Period{From, To}: a struct that owns its rule like a raw value object but declares no Value(), because there is no single scalar to return. It is a plain domain type — the framework adds no interface and no marker — and the TableSchema is the only place that knows it is stored across several columns. Its own section is below.

Value objects — the raw kind

What to declare

Own the rule and the notification it emits; stay mode-less and root-less (an Email is a valid Email regardless of which aggregate carries it). Two methods: Value() T (the underlying primitive) and IsValid (the rule). Declaring the field as this type is all you do — the framework discovers and validates it.

type Email string

func (e Email) Value() string { return string(e) }
func (e Email) IsValid(fieldName string, ctx *domain.NotificationContext) bool {
    if e == "" {
        ctx.AddNotification(fieldName, domain.RequiredFieldNotification{})
        return false
    }
    if !emailRegex.MatchString(string(e)) {
        ctx.AddNotification(fieldName, InvalidEmailNotification{}, string(e))
        return false
    }
    return true
}

Validation is automatic (both kinds)

You never wire value-object validation by hand — this applies to raw VOs AND enums. The framework discovers a struct's VO fields by reflection and validates them, identically for a root entity AND for an aggregate value object, on every write (insert, update, delete, archive, unarchive):

  • Every exported field whose value is a value object runs its IsValid (raw) or its membership check (enum), keyed by the Go field name. A nil pointer field is skipped (absent). Declaring the field as a VO type IS the declaration — no registration step.
  • An aggregate value object (a child — Address, Dependent, …) gets the same treatment: after the framework runs the child's BuildRules it discovers and validates the child's VO fields in a collection-scoped context, so an invalid Address.ZipCode surfaces as addresses[0].zipCode. The child's BuildRules carries only its non-VO rules.

Adjusting the automatic pass — Ignore & Force

Validation is automatic and you normally write nothing here. The framework discovers VOs by reflection over the entity's exported top-level fields and validates each one on every write — that already covers the overwhelming majority of cases. The two *Rules methods below are the exceptions, both available on the r handed to every BuildRules (root and aggregate value object alike).

Skip one — r.IgnoreValueObject("Field"). The field is discovered automatically, but you want it excluded in a specific mode. Call it inside a mode gate, and the exclusion applies only to that mode:

r.IfDelete(func() {
    r.IgnoreValueObject("Email") // Email is auto-validated, but not on delete
})

Add one the pass can't reach — r.ValidateValueObject(name, vo). The reflection walks only exported fields whose own value is a value object, and it does not recurse. Three kinds of value object are therefore invisible to it, and only these need to be named by hand:

  • An element inside a slice or map — Tags []vos.Tag: the pass sees the Tags field (a slice, not a VO) and stops there; Tags[0] is never reached.
  • An unexported field — reflection skips non-exported fields entirely.
  • A computed VO that is not a field at all — a value you assemble on the fly from other data (there is no struct field for the pass to discover).

For any of those, hand the VO to r.ValidateValueObject(name, vo) — name is the field label it reports under; it takes a raw VO or an enum directly. (This is the successor of the old BaseEntity.AddValueObject.)

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    // slice element — not auto-discovered:
    r.ValidateValueObject("PrimaryTag", u.Tags[0])

    // computed — assembled here, no struct field exists for it:
    phone := vos.Phone(u.AreaCode + u.LocalNumber)
    r.ValidateValueObject("Phone", phone)
}

Field labels

The label of a field lives on the aggregate's struct tag (labelKey:"UserEmailField"), next to the field — never inside the value object. The framework resolves it at emit and stamps it on the notification, and the audit pipeline writes the same key. A value object never decides how a field is presented to a consumer.

Enum value objects

What to declare

A closed classification set. E is the enum type, T its underlying scalar. You declare four things and the framework does the rest:

  • the const block with explicit values — an int (stable number) or a string (the wire/persisted token). The zero value (0 / "") is the Unknown sentinel and is never a member.
  • Value() T — the underlying scalar (mirrors a raw VO's Value()).
  • Values() []E — the member set (Unknown excluded). Go has no runtime metadata for a named type's constants (this is why stringer exists), so it is declared per enum.
  • UnknownNotification() — the notification emitted when a value is outside the set.
type Relationship string // string-backed → Value() string. An int enum would be Value() int.

const (
    RelationshipUnknown Relationship = ""       // zero sentinel — never a member
    RelationshipSpouse  Relationship = "spouse"
    RelationshipSon     Relationship = "son"
)

var relationshipMembers = []Relationship{RelationshipSpouse, RelationshipSon}

func (r Relationship) Value() string           { return string(r) }
func (r Relationship) Values() []Relationship   { return relationshipMembers }
func (r Relationship) UnknownNotification() domain.Notification { return UnknownRelationshipNotification{} }

No hand-written IsValid. The value is valid iff it is one of Values(); the Unknown sentinel and any out-of-range value fail. Membership validation is automatic — the same auto-discovery that runs raw VOs (see Validation is automatic above).

Parse a wire value — EnumByValue

domain.EnumByValue[E](raw any) E maps a raw int or string (straight off the wire) to the matching member, or the zero Unknown sentinel when nothing matches. It is the closed-set gate at the boundary: unknown input converges to Unknown, which the automatic validation then rejects (422). Use it in the command's ApplyTo to build the entity.

u.UserProfile  = domain.EnumByValue[vos.UserProfile](1)         // int 1  → UserProfileAdmin
d.Relationship = domain.EnumByValue[vos.Relationship]("spouse") // "spouse" → RelationshipSpouse
_              = domain.EnumByValue[vos.UserProfile](99)        // junk    → UserProfileUnknown (fails validation)

The underlying value — Value()

The inverse of EnumByValue: the member's raw scalar, for building the response in FromEntity.

u.UserProfile.Value()  // int    → 1
d.Relationship.Value() // string → "spouse"

Translate a value — EnumDescriptionKey + Translator.EnumDescription

An enum value renders per-locale through the translation layer. The domain exposes a stable key; the boundary translates it with the request language — the domain never translates.

  • domain.EnumDescriptionKey(v) → "<Type>.<value>" — "UserProfile.1" (int), "Relationship.spouse" (string).
  • translator.EnumDescription(lang, v) resolves that key with the request language, falling back to the key itself when no catalog entry exists. Register the value keys in your catalogs like any other key.
translator.EnumDescription(appCtx.Language(), u.UserProfile) // "Administrator" / "Administrador" (or "UserProfile.1")

Validate membership — ValidateEnum

Normally you never call this — membership validates automatically off the entity's fields. domain.ValidateEnum(e, fieldName, ctx) is the standalone entry for a value that is not a plain field: it returns whether e is a declared member and emits the UnknownNotification when it is not (the sentinel or an out-of-range value).

Members, Unknown & comparison

  • v.Values() — the declared member set ([]E, Unknown excluded).
  • v.UnknownNotification() — the notification for an invalid value.
  • v == vos.UserProfileAdmin — an enum value is comparable; compare it directly, no accessor needed.
Layer boundary. The domain declares value objects and their notification/description keys; the human string is produced at the pipeline boundary by the translation layer with the AppContext language. A value object never resolves a translation itself.

Composite value objects

DDD allows a value object to carry more than one field, and some concepts are only expressible that way — a rule between two fields (To after From, an amount paired with its currency) has nowhere to live on a single-scalar type. A composite value object is exactly that: a struct that owns its rule.

What to declare — nothing new

There is no third interface and no marker method. A composite is a struct that declares IsValid and does not declare Value(). The entity carries it as an ordinary field, and the framework's automatic pass discovers and validates it exactly like any other value object.

type Period struct {
    From time.Time  `labelKey:"PeriodFromField"`
    To   *time.Time `labelKey:"PeriodToField"`
}

// The cross-field rule — the thing a single-scalar value object cannot express.
func (p Period) IsValid(fieldName string, ctx *domain.NotificationContext) bool {
    if p.To != nil && p.To.Before(p.From) {
        ctx.AddNotification("To", PeriodEndsBeforeStartNotification{})
        return false
    }
    return true
}

type Contract struct {
    domain.AggregateRoot
    Salary vos.Money    // mandatory
    Trial  *vos.Period  // optional
}

A composite must declare IsValid (a boot failure otherwise) and must not declare Value(). That single method is the discriminator the framework uses to tell the kinds apart, so it can correct you either way: declaring a composite with Field(...) tells you to decompose it, and decomposing a scalar or enum value object tells you to use Field(...). Expose a canonical rendering under any other name (String(), Format()).

The parts of a composite are validated inside its own IsValid — the entity's pass validates the composite, not its interior. A part that is itself a value object validates by calling it: a.ZipCode.IsValid("ZipCode", ctx). Emitting on a part's name (ctx.AddNotification("Street", …)) resolves that part's labelKey from the tag inside the value object, so a part-level notification carries a label without the entity declaring anything.

How it is stored — the schema decomposes it

The TableSchema is the only place that knows the value object occupies several columns. It resolves the entity field by type, and each part is a field ↔ column pair like any other:

NewTableSchema[Contract]("contracts").
    ID("id").
    Composite(core.NewCompositeValueObject[vos.Money]().
        Field("Amount",   "salary_amount").As("SalaryAmount").
        Field("Currency", "salary_currency").As("SalaryCurrency")).
    Composite(core.NewCompositeValueObject[vos.Period]().
        Field("From", "trial_from").As("TrialFrom").
        Field("To",   "trial_to").As("TrialTo")).
    CreatedAt("created_at")

Each part is registered under its exposed logical name — its own name inside the value object by default, or whatever .As(...) renames it to. Those are the same keys a hand-flattened field would produce, which is the point: nothing downstream learns that a composite exists. Criteria, the audit timeline, the projected document, the read DTO, filters, orderBy, ?fields=, OpenAPI, GraphQL, gRPC and the tabular export all see plain fields. The full declaration surface, the aliasing rule and every boot guard live in Table schema.

Absence — the one rule that spans the parts

A composite held by value is mandatory, but only as a whole: it has no aggregate NULL rule, and each part follows its own Go type exactly as a scalar value-object field does — a non-pointer part scanning NULL is a loud error, a pointer part scanning NULL is nil.

A composite held as a pointer is optional, and there the group decides first: writing nil writes NULL to every part column, and on read every part column NULL reconstructs as nil — the per-part rules are not consulted at all. Any part carrying a value makes the composite present, and then a NULL on a non-pointer part is a half-written row and a loud error.

NULLNULLTrial == nil — absent

An optional composite therefore requires every one of its part columns to be NULL-able in the DDL. The framework cannot check your migration; it can only report the row it cannot honor.

Migrating off flat fields costs nothing. An entity that today carries Street/City loose at its root moves to Address vos.Address + Composite keeping the same columns, and pins the exposed names with .As("Street")/.As("City"). Nothing outside the domain changes — filters, DTOs, exports, the projected document and the existing audit history all stay valid — so there is no migration and no view rebuild. Introducing NEW columns, or changing an .As(...), is a different matter: that changes the projection's shape and needs a Version(N) bump (see Mongo schema evolution).

Persistence & the read side

A value-object field persists as its underlying scalar — the value Value() returns — and is reconstructed as the VO on the way back. You declare the field with the VO type on both the domain entity and the TableSchema (Field("Email", "email") with Email vos.Email); the framework does the rest, at every schema position (root, sibling, shared-base, aggregate-child, child-sibling):

  • Write — the persister unwraps the VO to its underlying before binding, so the SQL driver only ever sees a plain string/int (never the named type, which drivers handle inconsistently — this is exactly why a bare named type is otherwise rejected). The same unwrapped value flows into the outbox payload and the audit timeline. A nil nullable VO (*vos.Phone) binds as SQL NULL.
  • Read — a relational load reconstructs the field: a raw VO is a type conversion (vos.Email(col)); an enum converges through membership — a stored value outside the declared set (a tampered or legacy row) reconstructs as the Unknown sentinel, never a phantom member. Reconstruction does NOT re-validate (validity is a write-boundary concern, like domain.ID).
  • Both read backings — the value round-trips identically whether the read is served from the Mongo projection or straight from the relational SoR (RelationalSource): the projected document carries the underlying scalar, and the response DTO field (which may itself be typed vos.Email — or a plain string; both are valid) is populated by the same reflection, with the enum converge applied so the wire matches the entity.
  • Every surface — REST, GraphQL and gRPC bind a VO request field and render a VO response field natively (JSON/Kind-based); OpenAPI and the GraphQL SDL describe a VO by its underlying scalar type; CSV/XLSX export the underlying value.

The one rule for the two scalar kinds: a value object declared with Field(...) is a named type over a single supported scalar (type Email string, type UserProfile int). The underlying must belong to the closed persistable set (see Table schema); a VO over an unsupported underlying is a boot failure at the Field(...) call. A value object whose value spans several fields is the composite kind above — declared with Composite, where the same closed-set rule then applies to each part.

Standardized value in, standardized value out. The REST/GraphQL/gRPC boundary accepts and returns one canonical representation regardless of language — the underlying scalar. EnumDescription stays a deliberate, manual, per-request helper for showing a localized label; it is never woven into persistence or audit, which store the raw value.
