Views — the read-side declaration

A view is to the read side what a TableSchema is to the write side: a single, explicit declaration of a read model's structure — its root, its composition, its indexes, and how it stays current. It lives in the infra/db/query layer and is declared with query.View(...), query.SharedBaseView(...) or query.ComposedView(...). The query side is the read operation (criteria, filters, pagination) — this section is the read declaration.

CQRS by construction: a view materializes into a MongoDB document (the two materialized kinds) kept eventually consistent with the relational source of truth by the framework's write→read spine (outbox → CDC relay → broker → SyncEngine → Mongo). The read side serves documents, not aggregates. One declaration drives compose, the reader's Go↔column translation, index provisioning and the rebuild hash — nothing is inferred (mirroring the TableSchema philosophy).

The three view constructors

Every read model is declared through exactly one of three constructors. Two materialize (a CDC-fed Mongo collection the SyncEngine keeps in sync); the third joins at read time and stores nothing:

ConstructorRoot — where it is fed fromWhat it projectsMaterialized?
query.View(name) A regular table — an aggregate root or a role table (derived from the attached schema). The aggregate's own data, decomposed automatically from its TableSchema — root fields flat, .Sibling tables merged flat, 1:N .Child children nested — plus any Embed/EmbedMany/EmbedInChild of a materialized source (an upstream mirror or another local view). Yes — write time
query.SharedBaseView(name).Schema(base) A shared base identity (core.NewSharedBaseSchema). The all-in-one identity: base fields flat, base children nested, one sub-document per .Role(...) (each role's siblings flat, its children nested) — plus any Embed/EmbedMany. Yes — write time
query.ComposedView(name) A Primary(...) view — regular OR shared-base. The primary read exactly as a direct read would, enriched at read time with Link/LinkMany legs — internal views AND external collections. No new collection. No — read time

When each view updates — the projection fan-out

A materialized view is kept current by the SyncEngine, driven by writes to the schema(s) it is built on:

  • query.View — every write to the aggregate whose table it roots on recomposes it. The trigger is the schema's table, so a write to users updates every view rooted on users: declare five views over the User schema and one user update refreshes all five, each into its own collection — independent Version, indexes and shape, same source event.
  • query.SharedBaseView — updated by writes to the base identity and to any of its declared roles. Editing the shared Person fields, or writing through the User role, or through the Employee role, all recompose the one person document (role events fan out to it by the base id).
  • query.ComposedView — never “updated”: it is not materialized. It reads its primary and legs fresh on every query, so it always reflects the current state of the views it composes.

A view that EMBEDS another source (Embed/EmbedMany/EmbedInChild — an upstream mirror or another local view) also recomposes when that source changes — the recompose-ripple — so the embedded segment stays current alongside the aggregate's own data. When the source is a local view, the trigger is the SyncEngine's own write to it, so the two fan-outs chain: a write updates the source view, which refreshes every view materializing it, hop by hop along an acyclic graph. The mechanics are in How views stay current below.

query.View — the aggregate's own projection

The plain view reuses the SAME TableSchema the write repository declares, so the composer (physical columns into Mongo) and the reader (Go field ↔ column back) agree on every name across write and read. The aggregate's own closure — root scalars, .Sibling tables (merged flat), 1:N .Child children (nested arrays), a .SharedBase identity (merged flat) — projects automatically from that schema; you declare only the root schema, the mandatory Version(N), and the indexes the read endpoints rely on. The root table is derived from the schema — there is no separate root declaration to keep in sync. 

func UserView() *query.ViewDefinition {
    return query.View("users").
        Version(1).
        Schema(UserSchema()).   // addresses (a .Child of UserSchema) auto-project as "Addresses"
        Indexes(
            query.Index("document"),
            query.Index("email"),
            query.Index("created_at").Desc(),
            query.TextIndex("name", "email").DefaultLanguage("english"),
        )
}

SharedBaseView — the all-in-one identity

A SharedBaseView is rooted at a shared base (core.NewSharedBaseSchema): one Mongo document per shared identity (e.g. a Person) carrying the base's shared fields FLAT at the root, the base's native children nested at the root, and one sub-document per declared role (e.g. User, Employee) with that role's private fields, its siblings merged flat and its own children nested. It is the read-side mirror of the write side's shared-base normalization — where a plain query.View rooted at a role table shows ONE specialization, this view shows the whole composed identity.

The base is attached through .Schema(base) — exactly like a regular view attaches its root schema — and it must come before the first .Role(...) (each role is validated against the base). _id is the base's deterministic PK; the document's soft-delete gate is the base's (the identity hides only when its last active role archives). An absent role is an explicit null segment; an archived role stores its deleted_at and is stripped on default reads unless ?includeArchived. Everything a regular view declares applies unchanged (Version participates in the rebuild hash — the role set included — indexes/validators, MaxLimit, DeleteOnArchive, embeds). 

func PersonView() *query.ViewDefinition {
    return query.SharedBaseView("persons").
        Schema(PersonBase()).                  // the core.NewSharedBaseSchema identity
        Role(UserSchema()).                    // repeatable — the role set is open-ended
        Role(EmployeeSchema()).
        Version(1).
        Indexes(
            query.Index("document"),           // the natural key
            query.TextIndex("name", "email").DefaultLanguage("english"),
        )
}

Fan-out: the SyncEngine subscribes to the base topic AND every role table's topic, so a write to the base or to any role recomposes the one person document (the base id resolved from the role event's stamped ids). The base's own NewSharedBaseSchema declaration — its natural key, orphan policy and children — lives under TableSchema (the write-side declaration); this view only composes it.

Document shape

{
  "_id":      "<UUIDv5(document)>",          // the base's deterministic PK
  "document": "52998224725",                  // base fields — FLAT at the root
  "name":     "Ana Souza",
  "Addresses": [ ... ],                       // base-children — nested at the ROOT (shared across roles)
  "User":     { "user_name": "ana", "email_notification": true },   // role segment: fields + siblings flat
  "Employee": { "employee_number": "E-77",                          // role segment
                "Dependents":   [ { "dep_name": "Rita", ... } ],    // role children — nested INSIDE the segment
                "JobHistories": [ ... ] }
}
  • _id = the base PK — UUIDv5(naturalKey), stable under both role link models (shared-PK and separate-FK).
  • Role segments are named by the role's Go type ("User", "Employee") — the same derivation rule nested children use, minus the pluralization: a role is a single optional sub-document, not a collection. The wire name comes from your Response DTO's json tag (json:"user"), exactly like every other field.
  • An absent role is an explicit null segment — the store upserts via $set, so a vanished role must overwrite its stale segment. Response DTOs declare role fields as pointers with omitempty (the sparse-render contract), so a null segment simply disappears from the wire.
  • Base fields never repeat inside a segment; a role's siblings merge flat inside its segment; a role's own children nest inside it, keyed on the role row's own PK.

Role selection — the identity's current specialization

A role segment is ONE specialization, never a list — it follows the DOMAIN, not the relational rows. A SharedBaseView models a party-role: an identity that plays a role. Each role segment therefore holds exactly one sub-document — the identity's current representative for that role: the active row if one exists, otherwise the most recently deactivated (archived) one. This holds regardless of the link model — whether the role links through a separate FK (SharedBase(base, "person_id"), which may accumulate archived remnants) or shares the base's id as its own PK (SharedBase(base, "id"), capped at a single row). The relational table may hold many role rows for one identity; the projected document still shows the one current specialization. Need the identity plus a LIST of N role rows instead? Keep this write model and add a read-time ComposedView that LinkManys the role's own view onto the person by its FK — it yields the full list at read time, without changing the SharedBase model.

Under the separate-FK model with active-only uniqueness (see the two DDL uniqueness contracts above), an identity may carry archived role remnants NEXT TO one active row. The composer picks the row that represents the specialization's current state:

  1. the ACTIVE row (fk = baseID AND deleted_at IS NULL) — the one-active-role invariant caps it at one;
  2. otherwise the most recently archived remnant (ORDER BY deleted_at DESC), stored WITH its soft-delete timestamp — hidden on default reads, surfaced by ?includeArchived=true;
  3. otherwise the explicit null segment.

Remnant HISTORY is deliberately not enumerated in the person document — the role views with ?includeArchived cover it. A role without SoftDelete has no archived state; a single FK fetch decides its segment.

Lifecycle & sync

  • Document gate = the base's soft-delete. The base archives only when its last active role archives (write-side convergence), so the root deleted_at gate hides the person exactly when every specialization is archived. DeleteOnArchive() means "drop the document when the BASE archives" — and archived role rows stop composing at all.
  • Role events recompose the person document. The SyncEngine subscribes to every role table's topic (mandatory: a role's ARCHIVE/UNARCHIVE emits only the role event — the base convergence is SQL without its own outbox row). The base id it recomposes for comes straight from the event payload's _ids.base_id — the write side stamps it on every role event, so the resolution touches no database. The SharedBaseView document is then recomposed from the relational source (the base row plus its role rows): the cross-row archived-remnant pick is why this view keeps the composer instead of the payload-direct projection.
  • Purge convergence. When the last role's DELETE also purges the identity (DeleteWhenUnreferenced), the recompose finds no base row and removes the person document.
  • Base events route as root events (the base IS this view's root table): INSERTED/UPDATED upsert, DELETED removes, ARCHIVED honors DeleteOnArchive().

Reading it

Everything a regular view offers applies unchanged — the same Auto query handlers, filter-operator vocabulary, keyset pagination, ?fields= sparse render, ?includeArchived, field-level Restrict(), GraphQL exposure and CSV/XLSX export. Role sub-fields address through the segment: ?user.userName=ana, ?employee.dependents.relationship=daughter, sort and projection likewise. On a default read an ARCHIVED role's whole segment is hidden (the single-map counterpart of the archived-entry strip on child collections); ?includeArchived=true surfaces it with its deletedAt. Exports render each role as a nested branch (role fields + siblings, then its child collections), never repeating the base columns.

Rules & validation

  • The .Schema(...) must be a core.NewSharedBaseSchema declaration — attached exactly like a regular view's root schema, and validated at boot. Each Role must be a type-anchored schema declaring .SharedBase(...) back to the SAME base table with an equivalent declaration (checked when the role is declared, so .Schema(base) comes before the first .Role(...)); a wrong-kind schema or a role-less view is a boot error.
  • The base-kind gate is symmetric. The two constructors are type-exclusive in both directions: a SharedBaseView rejects a plain core.NewTableSchema (above), and a regular query.View rejects a core.NewSharedBaseSchema root — a shared identity is projected only through SharedBaseView(name).Schema(base).Role(...), never a plain view. Either mis-wire is a fatal boot error, so a shared-base schema can never be silently flattened into an ordinary view document.
  • Segment collisions (role vs base-child vs embed) are boot errors, like every other double-producer segment.
  • The role set participates in the rebuild hash: adding/removing a role, or changing any part of a role's schema closure, without bumping Version(N) is detected as forgot-to-bump and aborts boot — same contract as every rebuild-relevant change (see Mongo schema evolution).
  • The external opt-ins below (Embed/EmbedMany/EmbedInChild) apply here too, joined on the base PK at the root.
When to declare one. A SharedBaseView complements — never replaces — the role views: keep users/employees for the per-role surfaces and add the person view when a consumer needs the whole identity in one read (a 360° profile, a back-office screen, a data export). It is one more projection over the same CDC stream: no extra writes, one more recompose per role event.

The external schema — the view-exclusive declaration

A view is the ONLY place a type-less schema exists: core.NewExternalSchema(collection), attached to a view through query.JoinUpstream(...). Unlike a write-anchored NewTableSchema[T] (bound to a Go type, validated at construction), an external schema has no Go struct — its physical columns belong to an upstream service's Mongo collection (or a derived projection) that another team owns. Being type-less is the very signal that marks a source as EXTERNAL; there is no separate FromMongo constructor.

On an external Field(goName, column[, labelKey]) the left side is the logical Go name the local view's Response/criteria speak; the right side names the upstream's physical column. It is validated by bijection (no two fields share a column) but against no type — there is none. Because there is no Go type to derive the segment names from, the leg constructor takes them explicitly: JoinUpstream(schema, goName, externalName) — both mandatory, in TableSchema.Field order (Go first, external second). The join column is named on the verb via .On(column), never on the leg. 

// The upstream users service is mirrored locally (see Service-to-service);
// this type-less schema describes THAT collection's columns.
query.JoinUpstream(
    core.NewExternalSchema("upstream_users").
        PK("id").
        Field("Name", "name").
        Field("Email", "mail"),       // logical Go name ↔ upstream column
    "Buyer", "buyer")                 // Go segment, doc segment — both REQUIRED
// … then on the verb:  Embed(buyer).On("buyer_id")   // parent FK → source PK (1:1)

Embed and EmbedMany — composing external data

The two materialized constructors (View and SharedBaseView) reach OTHER data through an embed. Embed(leg).On(col) is 1:1 (a single sub-document, null when unresolved); EmbedMany(leg).On(col) is 1:N (an array, empty when none). Both take a leg built with query.JoinUpstream(core.NewExternalSchema(...), goName, externalName). The verb names the join column via the mandatory terminal .On(col) — the FK lives on the parent for 1:1 and on the leg (child) for 1:N — and the verb's multiplicity, not the declaration, fixes which side holds it.

An embed source is always MATERIAL — never an aggregate's own data, never a composition. Two leg kinds qualify, and only two: query.JoinUpstream(core.NewExternalSchema(…), …) (a locally materialized upstream mirror) and query.JoinView(view, …) (a registered LOCAL view — see Embedding a local view below). An aggregate's own children, siblings and shared base already decompose out of the declarative schema, so declaring them as an embed would be a redundant second path (a write-anchored embed source is a fatal boot error). A ComposedView is not a source in either family: it stores nothing, so there is no collection to read and no write to signal on. A boot guard (§8.3) still rejects a JoinUpstream leg whose collection happens to name a local view — that leg carries no view to signal on and no subscription materializes it; declare the view leg with query.JoinView instead.
A leg never nests an embed of its own — depth comes from the SOURCE VIEW's declaration. A leg exposes no Embed/EmbedMany builder, so embed-of-embed is not expressible and fails to compile. An upstream mirror is therefore always a leaf: it is a raw collection with no declaration of its own (the composition on the producing side happened before it was published). A JoinView source, by contrast, is a full view — whatever IT embeds arrives materialized inside the segment, so a chain products → sales → dashboard is expressible and stays fresh: every write to a view signals the views that materialize it, hop by hop. The one hard rule is that the graph must be acyclic — a loop would recompose forever, so it is a fatal boot error naming the exact cycle.

The embedded segment is kept fresh by the recompose-ripple: when the source changes — an upstream mirror receiving an event, or a local view being written by the SyncEngine — every dependent view that embeds it is recomposed surgically, per element. To find the documents a change affects, a 1:1 Embed scans the view by the parent's join column and an EmbedInChild scans it by the <childSegment>.<fk> path; each therefore requires a covering index on that path, declared with .Indexes(query.Index(...)) and verified at boot. An EmbedMany needs no such index — it reads the parent id straight from the changed child's own foreign key. Declaration, the ripple, the failure registry and the channel decision matrix live under Service-to-service.

Every family names its join column on the verb via .On(column) — the FK always points at the other side's PK/_id; the verb's multiplicity fixes which side holds it (1:1 → parent/primary, 1:N → child/leg), so the same leg plugs into an Embed (re-materialized) and a Link (read-time). The two segment names (Go and doc field) live on the leg constructor (JoinUpstream/JoinView), both mandatory.

The symmetry, in one line. Join* says WHERE the data comes from (JoinView = a local view, JoinUpstream = a mirror of another service's data); Embed* vs Link* says WHEN you pay for the join — on every WRITE (materialized, kept fresh by the ripple) or on every READ (composed per request, nothing stored). Both leg kinds plug into all six verbs, so the two questions are answered independently.
Composing your OWN internal aggregates — three paths, one choice each. Data already inside one aggregate — its children, siblings, or shared-base identity — projects automatically (declare the schema, nothing else). To join two separate internal aggregates into one read model: a SharedBaseView when they share an identity (the party-role pattern); an Embed/EmbedMany/EmbedInChild over a JoinView leg when you want the join materialized (pay on write, read one document); or a read-time ComposedView when you want it composed per request (pay on read, store nothing). The materialized path is the one to reach for when the joined shape is read far more often than it changes — which is the usual case for a read model.

Embedding a local view — query.JoinView as an embed source

A JoinView leg materializes a registered local view inside another one. Declaring it is the only change from an external embed — the source view you already have becomes the leg: 

// The product view already exists — it is the leg.
func ProductView() *query.ViewDefinition {
    return query.View("products").Version(1).Schema(ProductSchema()).
        Indexes(query.Index("code"))
}

func SaleView() *query.ViewDefinition {
    return query.View("sales").Version(1).Schema(SaleSchema()).
        Embed(query.JoinView(ProductView(), "Product", "product")).On("product_id").
        Indexes(query.Index("product_id"))   // the ripple's reverse scan
}

What keeps it fresh. Every write the SyncEngine applies to a view document asks one question — "is this view materialized inside another one?" — and, when it is, runs the same recompose-ripple an upstream mirror change runs. The refresh is in-process and happens after the source document is written, so it never reads a stale source; a view nobody embeds costs one map lookup. Because the ripple itself writes a view document, the question is asked again for that document: a chain propagates hop by hop with no extra declaration.

Version coupling — the source's shape cannot change behind your back. A JoinView leg folds the source view's Version(n) into the embedding view's rebuild identity. Bump the source and the embedder's hash moves too, so the boot's forgot-to-bump guard fires on the embedder and its documents are rebuilt against the new shape instead of keeping copies of the old one. Bump both, deploy once.

Rebuilds are ordered for you — source first. A rebuild composes its segments by reading the source through the active-slot pointer, and that pointer switches only at the source's own flip. Rebuilding sales while products is mid-rebuild would therefore materialize products' pre-flip content and finish stale — with nothing left to repair it, since rebuild writes raise no embed signal (a rebuild of millions of documents must not fan out millions of ripples). This is the COMMON case, not an exotic one: bumping a source's Version moves every embedder's hash too, so both land in one rebuild run. So the framework sequences them itself: the boot's rebuild list and RebuildAllViews both run in embed-dependency order (every source before the views materializing it, transitively along the chain), and a view whose source this instance did not bring to a flip — another pod is driving it — is DEFERRED rather than rebuilt against the old content; the instance driving that source holds both plans and rebuilds the pair in order. Views that embed no view keep their declaration order.
What still needs you: an ad-hoc rebuild of a single view. The operator entry points that rebuild ONE named view (RebuildView / RebuildViewSince) do exactly what you ask and nothing more — they have no dependency list to reason about. Rebuilding a SOURCE that way refreshes its own collection but does not refresh the copies already materialized in its dependents (again: rebuild writes raise no signal), so follow it with a rebuild of each dependent, or run RebuildAllViews, which is ordered. A Version bump never needs this care: it is the ordered path.
Archived data is hidden automatically — everywhere, under one rule. A default read hides ARCHIVED content in every segment of the document, and ?includeArchived=true brings all of it back at once. There is no per-family exception: a native child collection, a SharedBaseView role, a materialized Embed (1:1 or 1:N, over a local view or an upstream mirror), an EmbedInChild enrichment and a ComposedView leg all behave the same way.

The one condition is the SOURCE SCHEMA. A segment is filtered if — and only if — the schema behind it declares SoftDelete(column). That declaration is what tells the framework the source HAS an archived state and which column carries it; without it there is nothing to filter on and the segment is never touched. So the behavior is not a property of the verb you used, of the leg kind, or of whether the data is materialized: it is a property of the declaration. 
// This source has an archived state → its segment is filtered on a default read.
core.NewExternalSchema("upstream_products").
    PK("id").
    Field("Name", "name").
    SoftDelete("deleted_at")     // ← the declaration that switches the rule on

// This one does not → its segment is always returned as stored.
core.NewExternalSchema("upstream_regions").
    PK("id").
    Field("Name", "name")        // no SoftDelete: no archived concept, no filtering
For an upstream mirror, declaring it is only half the job. The column must also survive the subscription's filter: allowlist — otherwise the archive marker never reaches the mirror and there is nothing to filter on, however the schema is declared. The boot cross-checks the two and aborts on the contradiction (§8.5), for every consumer of the mirror: a view that embeds it and a ComposedView that links it.

What "hidden" means, per shape. Hiding is always content-level, never row-level — the document itself always comes back, because a segment is a LEFT join:

  • a 1:1 segment (an Embed, an EmbedInChild enrichment, a role) becomes the explicit null — the same value it carries when the reference is unresolved;
  • a 1:N segment drops the archived elements and keeps the rest, in the declared order;
  • the root document's own deleted_at is different in kind: that gate runs inside the Mongo query, so an archived document does not appear at all (it also governs counts and pagination).
What is archivedSource declares SoftDelete?Default readWith ?includeArchived=true
The EMBEDDING document itself its own root schema Not returned — the root gate, applied in the query. Returned.
A native CHILD collection entry the child schema The entry is dropped from the array. Returned, carrying its stamp.
A SharedBaseView ROLE the role schema The role segment becomes null. Returned.
The SOURCE behind a 1:1 Embed the embedded view's / mirror's schema The segment becomes null. Returned.
An element of a 1:N EmbedMany the embedded view's / mirror's schema The element leaves the array. Returned, in the declared order.

Anything whose source declares no SoftDelete — Returned as stored, always. No declaration, no archived concept, no filtering — the flag is a silent no-op there, never an error.

When you want archiving to REMOVE the reference for good — not merely hide it behind a flag — declare DeleteOnArchive() on the SOURCE view. Archiving then deletes the source document outright, the removal signals through the ripple, and the segment becomes the explicit null (or the element leaves the array) for every reader, with or without ?includeArchived. Hiding is a READ decision the consumer can lift; DeleteOnArchive() is a WRITE decision the source's owner makes once.

Ordering a materialized 1:N segment — EmbedMany.OrderBy

EmbedMany(leg).OrderBy(column).Desc().On(fk) declares the element order of the stored array. Without it the array keeps whatever order the writes produced — the default, unchanged for every view that declares none. 

EmbedMany(query.JoinView(SalePartsView(), "Parts", "parts")).
    OrderBy("slot").           // a column of the SOURCE documents
    On("kit_id")

The order is materialized, not applied at read time: the array is already stored sorted, so a read pays nothing for it. What makes that safe is that every writer of the segment sorts through the SAME server-side operator — the first compose, the rebuild backfill and the surgical ripple all emit one $sortArray stage, so a late-arriving element lands in its position instead of at the end, and concurrent writers converge on the identical array. (Sorting the composed array in Go instead would mean two implementations — Go's byte order versus the server's, which honors the view's declared collation — and the divergence would surface as an intermittent rebuild-verify failure.) The sort is total: the declared column, then _id, because a tie left unbroken would let two writers store different arrays for the same state. Declaring or changing an order is projection shape: it moves the rebuild hash, so it needs a Version(N) bump.

There is deliberately no per-parent ceiling to go with it. A cap on a MATERIALIZED array would discard elements permanently: when a kept element is later deleted, the element that should be promoted in its place was never stored, and the surgical edit cannot know it — only a full recompose per change could, which defeats the cheap incremental path. A ceiling therefore belongs to the read-time twin, LinkMany on a ComposedView, which rebuilds its array per request and can bound it honestly. That is the one knob the two families do not share.

Requires MongoDB 5.2+ ($sortArray). Only views that DECLARE an order emit it — an unordered EmbedMany produces the same stages it always did, so an older server keeps working for everything else.

Who controls what — wire vs declaration

Same split as the read-time twin, different answers — and the differences are exactly where materializing changes the semantics. The end user steers the query string; the developer fixes at declaration time everything that is baked INTO the stored document:

Fatal boot, never silent. The embed family aborts the boot with an explanatory message on every declaration that exceeds the contract: a write-anchored embed source (an aggregate's own data already projects), a JoinUpstream leg whose collection has no matching UpstreamSubscription — or names a local view, which is JoinView's job (§8.3); a JoinView leg naming a view no ReadableFeature contributes; a cycle in the view→view embed graph (printed as the exact loop); a missing covering index — on the parent join column of a 1:1 Embed, on <childSegment>.<fk> for an EmbedInChild, or on the join column of the source view for an EmbedMany over a JoinView leg; an OrderBy column that is not a column of the embedded source; .Desc() without OrderBy; an empty .On(...); a segment colliding with a root field, a child collection or another segment; and an EmbedInChild whose schema is not a native child of the view root.

EmbedInChild — enriching a child array

Where Embed and EmbedMany compose off the root document, EmbedInChild(childSchema, leg).On(col) composes one level down: every element of a native aggregate-child array gains a 1:1 sub-document resolved from a foreign key the element itself carries. It is the read model for the "list of X with the name of Y on each line" shape — a sale view whose line items each store a product_id and read back with the product beside it. The write side keeps the element normalized (it stores only the foreign key); the enrichment exists only in the projection, kept current by the same recompose-ripple that keeps a root embed fresh. 

view.EmbedInChild(SaleItemSchema(),
    query.JoinUpstream(core.NewExternalSchema("upstream_products"), "Product", "product")).
    On("product_id")

childSchema is a child of the view root — declared with root.Child(...) on a query.View, or on the base of a SharedBaseView (a role's own children are not a target). The leg is either kind, exactly as a root embed — query.JoinUpstream(core.NewExternalSchema(...), goName, externalName) for an upstream mirror or query.JoinView(view, goName, externalName) for a local view — and its .On(column) on the verb names the join column each child element carries, resolved against the leg's _id — with goName the Go field the sub-document reads back under. The enrichment is a first-class part of the projection: it is filtered, sorted and pruned with ?fields= at the child's segment path (items.product.name), walked by tabular export, and folded into the RebuildHash — so changing it without a Version(N) bump surfaces as DriftForgotToBump. Its recompose-ripple, and the covering index it requires, are the same ones a 1:1 root embed uses (see above). Its read-time twin — the same child-element enrichment computed per request instead of materialized — is LinkInChild on a ComposedView.

The enrichment is a single sub-document — there is no EmbedManyInChild. A one-to-many enrichment would nest an array inside a child-array element: a third collection level below the root, the grandchild shape aggregate persistence itself forbids. So each element holds one enriched sub-document, and the child array stays the view's deepest collection.

ComposedView — read-time composition

A ComposedView is not a view like the others. It is never materialized, never synced, never rebuilt: there is no Mongo collection, no Version(n), no schema-evolution entry, no recompose ripple. It is a read-time orchestration over views that already exist: a read against the composed name reads the primary view exactly as a direct read would, then enriches each returned item with data fetched by key, in batch, from the linked views (the legs) — the NoSQL-idiomatic join, resolved in code, not $lookup. Nothing to invalidate, nothing to keep in sync; the cost moves to the request path (one extra round-trip per leg per page, not per document).

It exists to give the developer JOIN power over views that share no write-side declaration — two aggregates connected by nothing but a foreign key — without hand-writing two reads and a merge loop, and without creating yet another materialized projection.

A ComposedView is SINGLE-LEVEL — there is NO link-of-link. Both the primary and every leg are plain views. A leg is always a materialized view (JoinView) or a locally materialized external collection (JoinUpstream) — never another ComposedView. The type system guarantees it: Link/LinkMany take a *Leg that can only be built from a view or an external schema, so a composition-of-composition does not compile — exactly as embed-of-embed does not. The only depth a leg carries is its OWN materialization: the leg's children, siblings, roles and embeds arrive just as a direct read of that view would — that is the leg view's shape, not a second join hop. To reach further, add more legs at the same level on one ComposedView, or push the data into the leg view's own aggregate.

Declaring one

// infra — same package and vocabulary as View / SharedBaseView / JoinUpstream.
func GadgetFullView() *query.ComposedViewDefinition {
    return query.ComposedView("gadgets_full").
        Primary(GadgetView()).                      // drives EVERYTHING row-shaped

        // 1:1 — the PRIMARY holds the FK (gadgets column "id" → the upstream
        // doc's _id). External leg: a locally materialized upstream collection,
        // described by its core.NewExternalSchema. Null segment when absent.
        Link(query.JoinUpstream(GadgetUpstreamMirrorSchema(),

        // gadget's _id). Internal leg: any registered view. Empty array when absent.

            OrderBy("text").                        // deterministic segment order (default: _id asc)
            MaxLinkManyLimit(3).                     // per-parent ceiling: link → yaml → 100

}

LinkInChild — the read-time twin of EmbedInChild

Where Link/LinkMany enrich the composed ROOT, LinkInChild(childSchema, leg).On(col) enriches one level down: every element of the PRIMARY's native child array gains a 1:1 sub-document, looked up by the element's own FK at read time — the exact shape EmbedInChild materializes, computed per request instead. childSchema MUST be a native child of the primary's schema (a shared-base primary targets the base's children), boot-validated; the leg is either kind (JoinUpstream or JoinView — read-time, so no upstream-only restriction). It obeys the same leg contract as every other link: filter and ?fields= address it at the nested path <childSeg>.<legSeg>.<field> and shape the enrichment per element — never which rows or child lines return — while sort, ?search=, pagination and cursors stay the primary's. Having no recompose ripple, it needs NO covering index (the one asymmetry with EmbedInChild). 1:1 only — there is no LinkManyInChild (the forbidden grandchild shape). 

ComposedView("catalog_full").
    Primary(CatalogView()).                                      // a view whose CatalogLines carry item_id
    LinkInChild(CatalogLineSchema(),
        query.JoinUpstream(UpstreamItemSchema(), "Item", "item")). // 1:1 leg; both segment names
        On("item_id")                                            // the element's FK → the leg's _id
// read time: each CatalogLine element gains an "item" sub-document, joined by the line's own item_id.

The core rule — the primary drives selection

Pagination, sort, ?search=, total and cursors belong exclusively to the primary view. Legs only enrich items already selected — they never add, remove or reorder primary rows. Keyset pagination is a tuple over one collection, sealed by a context hash; the moment a leg could decide which rows appear, pages would underfill with unbounded refill work and total would lie. Everything below derives from this:

  • Row-selecting filters target the primary — full 16-operator vocabulary via the same filter:"ops" allowlist, unchanged.
  • Segment filters never select rows. A filter addressed to a leg segment (?notes.text=b, declared as a nested group on the Request DTO whose Go field name matches the segment) filters what enters the segment — which documents appear in the array, whether the 1:1 sub-document attaches — never which primary items return. Segment filter paths resolve at every level of the linked document, with the same operators a direct read of that view would accept.
  • Sort targets the primary only. A ?sort= path into a segment is rejected with 400 SchemaViolationNotification — segment order is declared on the link, deterministically, precisely so truncation and array order never depend on wire input.
  • LEFT join always. 1:1 → explicit null; 1:N → empty array. There is no INNER mode — "require a match" would be a row-selecting filter in disguise.
  • total, onlyTotal, has_next/has_prev and both cursors are the primary's, byte-for-byte. ?onlyTotal=true short-circuits before any leg is fetched.
  • Cursors bind to the composed listing context — segment filters included (they shape the page's content). Changing any filter, row or segment, means requesting page 1 of the new context; a stale cursor is rejected with 400, never silently honored.

Read cost model — use it consciously

A composed read trades storage for request-path work, so its cost must be understood BEFORE declaring one — the framework bounds every axis, but the developer chooses the shape. With p = the page size (≤ the resolved maxLimit, the same universal ceiling every read obeys — plain, shared-base or composed) and c = a link's resolved MaxLinkManyLimit:

StepMongo queriesDocuments movedWhy it is bounded
Primary page O(1) — one find (+ one count) ≤ p maxLimit cascade; identical to a plain view read.
Each 1:1 leg O(1) — ONE $in batch ≤ p (one per distinct key) The page's FK values, deduplicated, nulls skipped; each key is a point lookup on the leg's _id — uniqueness caps the result at one doc per key. A batch of point lookups in one round-trip, never a scan.
Each 1:N leg O(p) — one indexed subquery per page parent, 8 in flight ≤ p × c Each subquery is find({fk: parent}) + declared order + LIMIT c. The per-parent ceiling is what forbids a single global-limit $in here — Mongo limits are per QUERY, not per group, so one fat parent would starve the others' segments.
By-id read O(1) — 1 + one fetch per leg ≤ 1 + legs × c The page has one parent.

Total per request: 1 + (#1:1 legs) + (#1:N legs × p) queries, every one index-driven, moving at most p + p·(#1:1) + p·c·(#1:N) documents. There is no unbounded axis: no query without a LIMIT, no N+1 that grows with the dataset (the query count grows with the PAGE, which you cap), no fan-out beyond the declared ceilings. What keeps each promise honest:

  • The 1:N FK must be index-covered — enforced at boot. Without an index whose first key is the FK column, each per-parent subquery is a full collection scan — O(p × leg collection size) per request, the classic silent monster. An internal leg whose view declares no covering index is a fatal boot; for an external leg (an upstream collection, whose indexes the operator owns) the same rule applies as a hard operational requirement. A compound index starting with the FK (e.g. (gadget_id, text)) additionally serves the declared order for free.
  • Deep pages multiply legs. Raising maxLimit raises the 1:N query count linearly (p subqueries per 1:N leg). A composed view meant for wide listings should keep its page ceiling modest — or the composition belongs on the materialization path.
  • Export is the deliberate heavy case. CSV/XLSX ignores pagination and walks the filtered set up to maxExportRows (default 10,000): the 1:1 $in batches thousands of keys and each 1:N leg runs thousands of subqueries. That is the read-time analogue of what the materialized path pays continuously in recompose — concentrated in the export request. The knobs are the existing ones: maxExportRows / per-view MaxExportRows (a composed export delegates to its primary's).
  • More legs = more round-trips, linearly. Every declared leg costs its row of the table above on EVERY read of the composed name. Declare the legs a surface actually renders — a "kitchen-sink" composition taxes every consumer for segments most never use; split it into two composed views instead.
Rule of thumb: a composed read costs O(1) extra round-trips per 1:1 leg and O(page) tiny indexed lookups per 1:N leg. If the read is hot enough that O(page) subqueries hurt, or consumers need to FILTER/SORT rows by the joined data, that is the signal the composition has outgrown read time — materialize it (Embed/SharedBaseView) and pay at write time instead. The two-paths table below is the decision matrix.

Per-leg authorization — the ToCriteria seam, unchanged

A composed view can reach, via join, a view the identity could not query directly — so gates matter. The seam is the one the read side already has: the Query's ToCriteria(ctx), with overlays addressed to a leg as segment-prefixed filter entries — the same channel wire segment filters travel. The framework guarantees mechanically that a segment filter can never select or leak primary rows; keeping a leg's data properly gated is fully the developer's responsibility in ToCriteria, exactly as tenant scoping is on every view today. 

func (q FindGadgetFullByIDQuery) ToCriteria(_ *configuration.AppContext) (fwqueries.ReadCriteria, error) {
    return fwqueries.ReadCriteria{
        IncludeArchived: q.IncludeArchived,
        // Per-leg overlay: the composed surface never exposes internal notes,
        // regardless of what the wire asked. Segment paths resolve at every
        // level of the linked document.
        Filter: map[string]any{"Notes.Kind": "public"},
    }, nil
}
Overlay filters participate in the cursor's listing context and compose freely with pagination: the authoritative context-hash validation runs at the reader, post-ToCriteria — the same context outgoing cursors are stamped with — so adding a security overlay (tenant, owner, business gate) to a paged query, plain or composed, never breaks ?after=/?before= navigation. The wire layer performs structural cursor checks only.

Archived gates and consistency

  • Cut at the source, not filtered afterwards: a leg's archived gate is added to the leg's own query, so an archived document is never fetched. The materialized twin reaches the same outcome one step later — it hides the archived segment on the fetched document — so both families answer ?includeArchived identically; they are compared under Two ways to compose.
  • One knob, every leg (R8): ?includeArchived=true lifts the primary's gate AND each leg's own gate. A schema is not required to declare SoftDelete — a leg without one has no archived concept; the knob is a silent no-op there, never an error.
  • No cross-leg snapshot: each view keeps its own CDC latency; a composed read inherits each leg's freshness individually and adds no cross-view guarantee. It is the same eventual-consistency class the read side already assumes — a segment can be one tick behind the primary.

How views stay current — the SyncEngine and recompose

Materialized views are driven by the write→read spine (see Architecture and the read lifecycle map): each write emits one outbox row in the same transaction; a CDC relay streams it to the broker; the SyncEngine consumes it and projects to Mongo. The event header carries an aggregate_type equal to the aggregate's root table name — the same string a view's schema declares — which is how one event finds its views.

Routing (the fan-out). At boot the SyncEngine builds an index keyed by table: a write to table X recomposes every view whose root is X (plain views), plus — for a role table — the shared-base identity documents that role feeds, plus — for an upstream collection — every dependent view that embeds it (the ripple). One write can therefore touch several documents across several collections, each projected independently.

The second index: view → view. Alongside the table index the SyncEngine builds one keyed by view NAME, listing the views that materialize each view through a query.JoinView embed. Every successful write to a view document consults it — "is this view embedded anywhere?" — and, when it is, runs the same recompose-ripple an upstream change runs. Four properties follow, and they are the whole contract:

  • Read-your-write. The signal fires AFTER the source document is stored and re-reads it, so the segment can never carry a state older than the event that triggered it. The write that a projection pipeline performs is partial (stages, not a whole document) — only the read-back knows the resulting document.
  • Chaining. The ripple's own writes land on view documents, so they consult the same index: a chain products → sales → dashboard propagates hop by hop with nothing extra declared. Termination is guaranteed by the acyclic-graph boot guard; each hop pays its own ripple.
  • Ordering under concurrent writers. A view has SEVERAL writers with different work partitioning (the projection loop keys workers by the view root's aggregate id; a ripple refreshing that same view is keyed by ITS source's id), so two refreshes of one source document can reach an embedder out of order. Every view-sourced edit therefore carries the source's _revision watermark and is applied only when the STORED segment is not newer — the same revision-guarded discipline the rest of the projection pipeline uses. (An upstream mirror needs no such guard: it has a single writer and per-id serialized events.)
  • Failure isolation. A ripple failure is logged, counted and recorded in the failure registry, then SKIPPED — the source's own projection always completes and the event is acknowledged. A deterministic recompose bug degrades one segment; it never becomes a poison pill that stops the projection loop. See the failure registry for the queries and the retry surface.

What does NOT signal. A rebuild writes the shadow slot directly, outside this path — deliberately: a rebuild of millions of documents must not fan out millions of ripples. That is why rebuilding a chain is ordered (source first, then dependents) and why a rebuild of an EMBEDDING view heals any drift by recomposing from the source's current collection.

Two projection paths, same document. The day-to-day path is payload-direct: for a plain entity-rooted view with no embeds, the SyncEngine turns the event's own payload into one atomic Mongo update pipeline — it does NOT re-read the relational source. For a SharedBaseView or a view with embeds it falls back to a consult recompose (the composer re-reads the relational closure). Both are engineered to produce a byte-identical document (the equivalence gate the blue-green rebuild verifies), and both are guarded by a monotonic _revision watermark so a stale or redelivered event is a no-op rather than a lost update — ordering per aggregate is preserved by hashing each aggregate id onto a fixed worker.

Archive by default. Mongo mirrors the relational backend: an ARCHIVED event keeps the document (with deleted_at populated, hidden on default reads, surfaced by ?includeArchived) unless the view opts into .DeleteOnArchive() — the hot-tier choice that drops archived rows from that collection. A hard DELETED always removes the document. The concrete lifecycle, the composer, the watermark guards and the tombstone handshake are detailed in the read lifecycle map.

Versioning and rebuild

Every materialized view declares a mandatory Version(N). Bump it whenever the view's rebuild-relevant declarative shape changes (root schema columns, embeds — including the Version of a view a JoinView leg embeds — DeleteOnArchive, $jsonSchema, collation, capped, time-series, or — for a SharedBaseView — the role set). The version participates in the rebuild hash: changing the shape WITHOUT bumping is detected at boot as DriftForgotToBump and aborts; bumping triggers an online blue-green rebuild — a fresh shadow collection is built from the source while the active one keeps serving, kept current by dual-apply, verified, then flipped atomically. Index-only changes take the fast path (re-apply indexes, no rebuild). The full control plane — drift detection, slots, the advisory lock, the verify — is Mongo schema evolution.

A view embedded in another carries its version there too. A query.JoinView leg folds the SOURCE view's Version(n) into the EMBEDDING view's rebuild hash, so bumping the source moves the embedder's hash as well: the forgot-to-bump guard fires on the embedder, and bumping both rebuilds the embedding projection against the source's new shape instead of leaving it holding copies of the old one. Deploy the two bumps together: the boot runs the resulting rebuilds in embed-dependency order (source before embedder, transitively), because a dependent rebuilt while its source is still mid-rebuild would read the source's pre-flip collection — the active-slot pointer switches only at the flip — and re-materialize the old content.
