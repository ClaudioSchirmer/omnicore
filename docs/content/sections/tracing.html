Distributed tracing

OpenTelemetry tracing is an opt-in overlay that reconstructs how a request flows through your services — the inbound call, the business handler, every database query, every outbound call, and the asynchronous projection that follows. It is off by default: an undeclared service installs the OTel no-op tracer and pays essentially nothing.

Tracing is an additional destination — spans leave over OTLP to a collector (Jaeger, Tempo, Datadog, …), never your stdout. Your logs and the audit echo are untouched, except that when tracing is enabled every context-carrying log line gains a traceId/spanId so you can pivot from a log straight to the trace.

Turning it on

Add the observability.tracing block to microservice.<profile>.yaml:

observability:
  tracing:
    enabled: true
    exporter: otlp          # otlp | stdout (debug-only) | none (none = propagate traceparent, export nothing)
    endpoint: "${OTEL_EXPORTER_OTLP_ENDPOINT:localhost:4317}"
    insecure: true          # plaintext OTLP/gRPC; profile default dev=true / else=false (TLS)
    headers: { x-api-key: "${OTEL_COLLECTOR_KEY:}" }   # added to every OTLP export (managed-collector auth); empty = none
    sampler: parentbased_traceratio   # dev default always_on; else this
    ratio: 0.1              # keep fraction for the *traceratio samplers
    serviceName: "${service}"         # defaults to the top-level service identity
    instrument: [http, pgx, mongo, kafka, httpclient]   # empty list = all
  • enabled — master switch. Off installs no SDK, no exporter, no propagation.
  • exporter — otlp ships spans to a collector; stdout prints them to the terminal (debug-only — see the note below); none records and propagates the traceparent to downstreams but exports nothing (a middle service with no collector of its own yet).
  • insecure — disables TLS on the OTLP/gRPC connection (plaintext). Profile-aware default: true in dev (a local sidecar collector such as Jaeger speaks plaintext), false elsewhere (a managed collector — Honeycomb, Grafana Cloud Tempo, … — requires TLS). An explicit value wins. Read only for exporter: otlp.
  • headers — a map added to every OTLP export request, the slot for a managed collector's auth token (e.g. x-api-key / x-honeycomb-team). Values support ${VAR:default} substitution; empty sends none. Read only for exporter: otlp.
  • sampler — always_on / always_off / traceratio / parentbased_traceratio. The profile default is always_on in dev and parentbased_traceratio elsewhere. Parent-based matters in a mesh: when a request already carries a trace, the keep/drop decision is honored, so a distributed trace is never split in half.
  • ratio — the keep fraction (0–1) for the *traceratio samplers. 0.1 = 10% of traces are recorded.
  • serviceName — the service.name shown in the collector; defaults to the top-level service identity. This is the one resource attribute the framework owns. The other resource attributes are not in this YAML: the OTLP resource merges resource.Default(), so the OTel SDK's standard OTEL_RESOURCE_ATTRIBUTES env var (e.g. deployment.environment=prod,service.version=1.4.2) plus host/SDK attributes flow through to the collector. They live in an env var rather than the versioned YAML because they vary per deploy/instance and the whole OTel toolchain (k8s operators, the Collector, auto-instrumentation) already reads that variable — the framework defers to the SDK's standard instead of re-wrapping it. The explicit serviceName still wins on the service.name key.
  • instrument — the edge-subsystem allowlist (the full set today is in the table below). An empty list enables all; drop pgx/mongo on a high-QPS service to cut the per-query span volume.

The complete set of toggles — listing all five enables the same as an empty list:

ToggleWhat it spansLayer
httpthe inbound server span (one per request)web
pgxone span per relational statement (Postgres via otelpgx, MySQL via otelsql) — the toggle name is a legacy artifact from the PG-only era and gates both enginesinfra
mongoone span per Mongo commandinfra
kafkaconsumer spans on the async paths (SyncEngine, integration Receiver, UpstreamSubscriber)infra
httpclientthe outbound client span + W3C traceparent injectioninfra

The business dispatch <Command/Query> span is NOT a toggle — it is always on when tracing is enabled. It is one span per request (cheap) and the highest-value level, so it is never opted out. The five toggles above are the edge spans, whose volume (a span per query for pgx/mongo) or library maturity warrants the fine-grained control.

exporter: stdout is debug-only — it is your right to use it, but it is not the recommended mode. It exists so you can confirm a trace is forming locally without standing up a collector. Two reasons to switch back to otlp once you have looked: (1) it writes spans to the same stdout stream as your application logs and the audit echo — the exact noise tracing otherwise keeps off stdout, and the thing that makes a trace hard to tell apart from a log line; (2) it writes synchronously, on the request path, whereas otlp exports asynchronously in batches and never makes a request wait. Use it for a quick local look, then go back to otlp (or a local Jaeger).

Cost is controlled and never on the hot path: export is asynchronous and batched, so a request never waits on the collector and a down collector simply drops the batch. A subsystem left out of instrument installs no tracer for that layer — the cost is zero, not merely a no-op.

Dropping http has one extra consequence beyond skipping the server span: the inbound W3C traceparent is no longer extracted at the edge and the CorrelationID == trace_id bridge does not run, so the dispatch span roots the trace locally instead of continuing an upstream one. Keep http enabled on any service that sits inside a distributed trace; drop it only on a true edge where no upstream traceparent ever arrives.

The synchronous trace

A request produces one continuous trace, automatically:

POST /users                         server span        (web)
  └─ dispatch InsertUserCommand     business unit       (application)
      ├─ pg INSERT users            query span          (pgx)
      ├─ pg INSERT outbox           query span          (pgx)
      ├─ call keycloak/getUser      client span → continues in the downstream service
      └─ mongo find                 command span        (mongo)

The dispatch <Command/Query> span is the business unit of work. Because every handler — Auto or manual, REST or GraphQL — funnels through pipeline.Dispatch, the span is inherited identically with no per-handler code. Outbound httpclient calls inject the W3C traceparent header, so the downstream service continues the very same trace.

The asynchronous trace (CDC relay → transport)

The eventually-consistent projection (outbox → CDC relay → transport → read model) is reconnected to its producing trace by a traceparent carried on the outbox and integration_events rows (inlined in the flattened framework migration 0001_framework, per dialect). The SyncEngine, the integration Receiver and the UpstreamSubscriber open a consumer span linked to the producing trace (the messaging convention — a link, not a parent, because producer and consumer are temporally far apart).

One operator step is required for the link to cross Debezium: map the column to a Kafka header in the Outbox Event Router config of your connector — 

"transforms.outbox.table.fields.additional.placement": "traceparent:header:traceparent"

Debezium itself is a separate process, so its latency is a blind spot — it shows as the time gap between the producer span ending and the consumer span starting, not as a measured span.

One id ties logs, traces and events together

The framework keeps AppContext.CorrelationID() equal to the active span's trace_id (a UUID is 128 bits — exactly an OTel trace id). So the same value appears as the traceId on your logs, the trace id in the collector, and the correlation_id column on integration_events. Read an error in stdout, copy its traceId, open the whole request in Jaeger.

For forensics, the audit event carries a trace_id mirrored to both destinations — the in-transaction audit_events.trace_id column and the traceId attribute on the slog audit echo — so an audit row or an echo line jumps to its trace. It is the 32-char hex id (not the full traceparent): audit is read, never re-consumed, so it needs the id to find the trace, not the producer span id a carrier needs to link it.

What is and isn't covered

  • Synchronous request — traced end to end, automatically, one continuous trace.
  • Asynchronous projection — reconnected via span links (not one giant trace), with the Debezium hop as a visible time gap.
  • Domain layer — no spans; it is pure CPU validation with no IO to measure.
