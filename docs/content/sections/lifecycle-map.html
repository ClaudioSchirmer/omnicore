Canonical write lifecycle — end-to-end layer map

Cross-layer reference: for each of the framework's 5 canonical write verbs, this table follows the request from the HTTP wrapper down through the Auto handler, the domain entry-point (Get* function + which IfXxx closures fire), the infra layer (SQL emitted + outbox event + Mongo operation on the read side), all the way to the audit event the consumer reads in slog/ELK (detailed in Audit). Everything is anchored in what the write did to the row's LIFECYCLE — identical lifecycle effect ⇒ identical audit verb ⇒ identical Mongo op — which is what makes PUT and PATCH share verb: "update": neither moves the row's archived state. The read-side counterpart is the Read lifecycle map.

Only the canonical surface (Auto handlers / UpdateCommandHandler-family) is shown to keep the map readable. Manual handlers have full control of every layer and can opt out of any step; what they cannot opt out of is what the persister does to the row, which is what the audit verb echoes.

$now in the SQL below denotes the write operation's app-clock stamp: one time.Now() instant (UTC, microsecond-truncated) minted in Go per operation and bound as an ordinary argument — like the Go-minted UUID v7 id, never a dialect NOW() expression. Root, children, siblings and the shared-base cascade of one operation all carry the same instant, known before COMMIT (see Table schema → managed columns).

Outbox payload — the event-carried-state contract, ONE row per write. Every body verb emits one self-sufficient JSON shape: all scalars column-keyed flat at the top (root/role fields ∪ sibling fields ∪ shared-base business fields ∪ the verb's managed timestamps — the EXACT app-clock values the DML bound: INSERTED carries created_at+updated_at; UPDATED only updated_at; ARCHIVED the DeletedAt stamp; UNARCHIVED an explicit null); an _ids structural block (id, and for SharedBase roles base_id + base_revision — the row-lock-serialized last-writer-wins token — plus base_purged on the purging DELETED); and _children/_base_children groups, each item column-keyed with an _op verb. On a body verb that is the OperationOf categorization the persister executed (insert/update/archive/delete/noop); on ARCHIVED/UNARCHIVED an item instead reports the CASCADE the root statement performed on ITS row — archive with the stamp the child UPDATE bound, or unarchive with an explicit null — and noop when the statement's own predicate did not reach it (already archived when the root archived; carrying a stamp that is not the one being undone), because the cascade is one set-based statement per child table, not a per-item decision. DELETED keeps the historical structural keys (ID + shared-base ParentID) and only ADDS _ids. A SharedBase write emits NO separate base-table row anymore — the SyncEngine fans out to the other roles' documents from the role event's _ids.base_id; the one base-table event left is the orphan purge's DELETED. Keys starting with _ are the framework's reserved namespace (a physical column may never claim them — boot failure at declaration).

Child cascade (aggregate)

Children of an AggregateRoot don't have their own outbox event or Mongo op — granularity B means one outbox row per aggregate operation, and the read side applies the root event's _children deltas surgically — per child row, keyed by ID, each carrying its own _op — never a whole-document recompose. What children DO have, per row, is per-op SQL emitted by writeChildren on a body verb, plus the SET-BASED cascade the soft verbs and the hard delete emit (one statement per child table, keyed on the ParentID — it reaches every child row of the aggregate, including any the caller never loaded), and a per-row audit op that echoes the child row's lifecycle effect exactly as the root verb echoes the root's. On an update, each child's operation is domain.OperationOf(OriginalStatus, CurrentStatus) — where it started (zero value, or DB-loaded as Constructor) against where it is now — not its current status in isolation.

The lifecycle-grounded vocabulary — one rule, no exceptions

Reading the two tables top-to-bottom, the rule the framework follows is:

Audit verb (root) and audit op (child) both echo what the write did to the row's LIFECYCLE — whether the row appeared, changed in place, retired, returned, or vanished. Identical lifecycle effect ⇒ identical audit token. Distinct effect ⇒ distinct token. Consumer intent (PUT vs PATCH, archive cascade vs PUT-replace DeletedAt) lives in the actionName field at the root and in the verb field on the surrounding event; the per-row op/verb stays anchored to what physically happened to the row.

Concretely, five effects and five tokens: the row was created (insert); it changed while its DeletedAt stayed where it was (update); its DeletedAt went from null to a stamp (archive); from a stamp back to null (unarchive); the row is gone (delete).

This rule used to be phrased against the SQL text — "identical SQL ⇒ identical audit token" — and that phrasing no longer holds. Archive, unarchive, PUT and PATCH all emit the SAME statement today: the entity's full field set, the managed timestamps, the revision bump and the guard. What separates them is one bound value — whether the DeletedAt column was written, and to what. So the statement TEXT can no longer tell the verbs apart, while the lifecycle effect always can. The tokens themselves did not change; only the rule that explains them.

This gives consumers a forensically honest record: an audit log entry saying op="archived" always means "this row still exists in the DB with deleted_at populated, can be restored", regardless of whether the trigger was a PATCH /archive or a PUT-replace. Same way op="deleted" always means "this row is gone, only the cascade/snapshot in the audit can reconstruct what it was". Tooling that reverses state changes (rebuilding the prior aggregate from audit) only needs to know the lifecycle contract, not the verb hierarchy of every endpoint that ever produced the change.

Optimistic concurrency — the revision guard

A write does not read the row it is about to change; it writes the FULL field set the entity carries. So a write built on a stale read would silently revert every column another writer changed in the meantime, and — worse — would put those reverted values on the outbox payload as though the row had held them. The framework refuses instead.

Every ROOT update pins the revision the entity was loaded with, in the statement's own WHERE: 

UPDATE tenants SET name = $1, updated_at = $2, revision = revision + 1
 WHERE id = $3 AND revision = $4   -- $4 = the revision the load returned

The guard costs nothing on the happy path — it rides the WHERE the statement already had, and the rows-affected count the framework already reads (WriteTx.ExecCount, uniform across every engine) answers it. Zero rows then has two causes, and ONE probe on that failure path tells them apart: the row is gone (RecordNotFoundNotification, 404) or it moved past the caller's revision (ConcurrentModificationNotification, 409 — the wrong-state flavor, so gRPC reports FAILED_PRECONDITION rather than ALREADY_EXISTS). The caller's recovery is to reload and reapply.

Row-level, not column-level. The revision belongs to the row, so two writes touching DISJOINT fields still conflict. That is the ordinary cost of optimistic locking, and it is deliberate: the framework cannot tell which columns a caller meant to change, because every write carries all of them.

What is guarded, and what is deliberately not:

  • The root / role row — always. Revision is mandatory on every root schema attached to a repository (the builder panics without it), so coverage is universal: there is no entity that is silently unprotected.
  • Aggregate children — no. A child declares no revision of its own (the schema builder REJECTS the call). It does not need one: the root's guarded UPDATE runs first and already proved nobody moved the aggregate under this write, so the root's token versions the whole aggregate, child edits included.
  • The shared base — no. Several roles converge on one identity and the base is last-write-wins by design; guarding it would turn an unrelated role's write into a conflict on this one.
  • Hard delete — no. It writes no business column, so a stale snapshot cannot revert anything.
  • An entity that never came from a load — no. A persisted row is always at revision ≥ 1 (an INSERT initializes it), so revision 0 means exactly one thing: this entity was assembled in memory or came from a repository outside the framework's read path. The write goes unguarded rather than failing forever. This is the same graceful degrade domain.Old makes.

The guard reads the revision from the LIVE entity, never from domain.Old: the old-state ghost is a JSON clone and the domain.Managed carrier is unexported, so the snapshot's revision is always 0. Nothing in memory changes the revision, so the live value IS the loaded value.

Archive and Unarchive are the update path

The framework has ONE rule about what reaches the database: the entity's field set at write time is what gets persisted. Archive and Unarchive used to be its only exception — they wrote a single column while the outbox payload announced every one of them. Anything the domain produced on the way there (a Command's ApplyTo, an r.IfArchive closure flipping a status) vanished from the system of record and appeared in the read model as though it had been stored.

They now emit the same UPDATE every other verb emits — full field set, managed timestamps, revision bump, guarded on the loaded revision — with the transition riding along as one more written column: the DeletedAt column bound to the operation's instant (archive) or to SQL NULL (unarchive). The payload then describes what the statement wrote, which is what makes it true.

A rule like r.IfArchive(func() { t.Status = Suspended }) is exactly what the DSL invites, and it now persists. So does anything a Command's ApplyTo changes on the loaded entity.

What the two verbs still own — the reason this is not simply Update:

  • The DeletedAt column is required. No column, no verb.
  • The one-active-role probe runs first. On unarchive it must fire BEFORE the row flips to active, or an active-only unique index vetoes the UPDATE itself with a raw constraint error instead of the canonical conflict.
  • The child cascade is set-based — one statement per child table (WHERE ParentID = root), not one per item. It reaches every child row of the aggregate, including any the caller never loaded, at a cost that does not grow with the collection.
  • The shared identity converges by lifecycle only. The base is archived once no active role remains and reactivated on unarchive; its business fields are NOT restated. Several roles share that row, it is last-write-wins and deliberately unguarded, so a bodyless verb must not rewrite it from a snapshot taken before the transaction.
  • The outbox event type stays ARCHIVED / UNARCHIVED, because the read side routes on it: DeleteOnArchive removal, the upstream mirror, the base-revision pull repair.

Two consequences worth planning for. Archiving now stamps updated_at — it is a mutation, and it shows up in "changed recently" listings. And archiving a row that is not there answers 404 instead of committing an event about nothing; the same row-count check the update verbs always had now covers the soft verbs too. Siblings are written as a PARTIAL update, so an archive never deletes a 1:1 facet because its columns happen to be all-nil.

The child cascade is visible to the read side

An aggregate archive flips the DeletedAt of every child row under the ParentID. The payload used to list those children as _op: "noop", which the projector skips — so the relational rows were archived while the projected array still claimed they were active, and a live document disagreed with one rebuilt from the source.

Each item now reports the cascade it took: _op: "archive" carrying the same stamp the child UPDATE bound, or _op: "unarchive" carrying an explicit null. Both are the same surgical edit — stamp the element's DeletedAt, leave every other field alone. A child table that declares no DeletedAt takes no cascade and stays noop — and so does a row the statement's predicate did not reach, because the restore brings back only what the root's own archive put to sleep (see What an unarchive brings back). The event and the rows therefore describe the same set, which is what keeps a live document and one rebuilt from the source in agreement.

During a rolling upgrade a consumer running the previous binary does not know the "unarchive" op and skips it — which is exactly what it did with "noop" before, so the child segment is no worse off than it was; the next event or a rebuild settles it.
