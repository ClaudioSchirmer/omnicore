Canonical write lifecycle — end-to-end layer map

Cross-layer reference: for each of the framework's 5 canonical write verbs, this table follows the request from the HTTP wrapper down through the Auto handler, the domain entry-point (Get* function + which IfXxx closures fire), the infra layer (SQL emitted + outbox event + Mongo operation on the read side), all the way to the audit event the consumer reads in slog/ELK (detailed in Audit). Everything is anchored in the SQL fingerprint — identical SQL ⇒ identical audit verb ⇒ identical Mongo op. This is what makes PUT and PATCH share verb: "update" in audit: the SQL is the same. The read-side counterpart is the Read lifecycle map.

Only the canonical surface (Auto handlers / UpdateCommandHandler-family) is shown to keep the map readable. Manual handlers have full control of every layer and can opt out of any step; what they cannot opt out of is the SQL the persister emits, which is what the audit verb echoes.

$now in the SQL below denotes the write operation's app-clock stamp: one time.Now() instant (UTC, microsecond-truncated) minted in Go per operation and bound as an ordinary argument — like the Go-minted UUID v7 id, never a dialect NOW() expression. Root, children, siblings and the shared-base cascade of one operation all carry the same instant, known before COMMIT (see Table schema → managed columns).

Outbox payload — the v2 event-carried-state contract, ONE row per write. Every body verb emits one self-sufficient JSON shape: all scalars column-keyed flat at the top (root/role fields ∪ sibling fields ∪ shared-base business fields ∪ the verb's managed timestamps — the EXACT app-clock values the DML bound: INSERTED carries created_at+updated_at; UPDATED only updated_at; ARCHIVED the soft-delete stamp; UNARCHIVED an explicit null); an _ids structural block (id, and for SharedBase roles base_id + base_revision — the row-lock-serialized last-writer-wins token — plus base_purged on the purging DELETED); and _children/_base_children groups, each item column-keyed with an _op verb (insert/update/archive/delete/noop) from the same OperationOf categorization the persister executed. DELETED keeps the historical structural keys (PK + shared-base FK) and only ADDS _ids. A SharedBase write emits NO separate base-table row anymore — the SyncEngine fans out to the other roles' documents from the role event's _ids.base_id; the one base-table event left is the orphan purge's DELETED. Keys starting with _ are the framework's reserved namespace (a physical column may never claim them — boot failure at declaration).

Child cascade (aggregate)

Children of an AggregateRoot don't have their own outbox event or Mongo op — granularity B means one outbox row per aggregate operation, and the read side re-composes the whole doc from the root's event. What children DO have, per row, is per-op SQL emitted by writeChildren + cascade SQL emitted by archiveAggregate/unarchiveAggregate/deleteAggregate, and a per-row audit op that mirrors the SQL fingerprint identically to the root verb. On an update, each child's operation is domain.OperationOf(OriginalStatus, CurrentStatus) — where it started (zero value, or DB-loaded as Constructor) against where it is now — not its current status in isolation.

The SQL-grounded vocabulary — one rule, no exceptions

Reading the two tables top-to-bottom, the rule the framework follows is:

Audit verb (root) and audit op (child) both echo the SQL fingerprint of the row-level change. Identical SQL ⇒ identical audit token. Distinct SQL ⇒ distinct audit token. Consumer intent (PUT vs PATCH, archive cascade vs PUT-replace soft-delete) lives in the actionName field at the root and in the verb field on the surrounding event; the per-row op/verb stays anchored to what physically hit the database.

This gives consumers a forensically honest record: an audit log entry saying op="archived" always means "this row still exists in the DB with deleted_at populated, can be restored", regardless of whether the trigger was a PATCH /archive or a PUT-replace. Same way op="deleted" always means "this row is gone, only the cascade/snapshot in the audit can reconstruct what it was". Future tooling for reversal of state changes (rebuilding the prior aggregate from audit) only needs to know the SQL contract, not the verb hierarchy of every endpoint that ever produced the change.
