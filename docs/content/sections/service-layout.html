Service layout & naming — the recommended standard

This page standardizes how a consumer service is laid out and named: directories, file granularity, naming patterns, and the placement rules for every framework concept. It deliberately contains no code — signatures, behavior and edge cases live in the mapped sections linked throughout, and each linked section remains the sole authority for its mechanics. This page owns only names, shapes and placement.

Who this page binds. For a developer, everything here is a baseline: the shape the framework's reference consumer uses and the shape every example assumes. You know your service — deviate deliberately whenever you have a reason; nothing here is enforced by the framework at boot. For a code generator (an AI scaffolder, a template tool), this page is normative: produce exactly this shape unless the developer explicitly instructs otherwise, and record any instructed deviation where the developer can see it. A generator has no taste of its own to exercise — the developer's freedom is not the generator's freedom.

Layer import rules (who may import whom) are defined in Architecture and are not repeated here. English everywhere — code, comments, identifiers, tests; the only non-English text is inside the seven translation catalogs.

Domain layer

  • One domain type per file, lowercase singular: the root in <entity>.go, each value object in its own file. A root file that also holds its children's types is a smell, not a style.
  • notifications.go is the single shared home of every custom notification, grouped per aggregate with a comment divider. Adding an entity appends to it — never a per-entity notifications file, never notification types inside the entity's file.
  • Notification type names follow <What>Notification; the type name is the translation key (Status mapping).
  • Every persisted field carries a labelKey tag; physical column names never appear in the domain (they live only in the schema).
  • Money is int64 minor units — never a float. Nullable means pointer.
  • A domain-service port (interface) is one more domain type, so it follows one-type-per-file: its own <entity>_service.go in the domain package — never embedded in the entity's file. The implementation lives in internal/infra/ (its own <entity>_service.go there). The interface stays with its consumer (the domain), never with its implementation.

Application layer

Commands — one per verb, file named <verb>_<entity>_command.go, Result co-located:

HTTP operationFile
POST (create)insert_<entity>_command.go
PUT (full update)update_<entity>_command.go
PATCH (partial update)patch_<entity>_command.go
DELETE (hard)delete_<entity>_command.go
Archive / Unarchivearchive_<entity>_command.go / unarchive_<entity>_command.go
Per-child operationsadd_<child>_command.go · update_<child>_command.go (or change_) · archive_<child>_command.go
  • Queries: by-id is singular, by-params is plural — find_<entity>_by_id_query.go and find_<entities>_by_params_query.go, one query type per file.
  • Write results mirror the post-write entity — the full aggregate, children and their persisted ids included, never an echo of the input. The contract is defined in Auto handlers (projection contract).
  • Translations: all seven catalogs, every custom notification key, every labelKey, and the entity name itself (its ContextName) — real translations in each language, not English copied seven times.

Web layer

  • Wire DTOs: one file per operation, request and response co-located — insert_<entity>.go, update_<entity>.go, find_<entity>_by_id.go, find_<entities>_by_params.go under internal/web/requests/. Not one file per entity, not one file per type: the unit is the operation, so its full wire surface reads in one place.
  • Routes: all of an entity's surfaces in one <entity>_routes.go — the REST mount plus the GraphQL and gRPC mounts when those surfaces exist. Never split one entity's surfaces across files; never put route registrations in bootstrap/.
  • The shared-identity read surface is its own bounded context: a SharedBaseView gets its own person_routes.go (or the identity's name), its own read-only route group, and its own permission — it is never folded into a role's routes, feature or permission.
  • Every request/response field carries an example: tag (it feeds the OpenAPI "try it out" body). JSON tags are camelCase of the field name.
  • List responses stay scalar (root fields only); the by-id response is where child collections nest.

HTTP surface conventions

  • The verb tells the truth. DELETE is exclusively a hard purge. A soft removal is PATCH …/archive, with its …/unarchive inverse. This applies to the root and to per-child operations alike.
  • Per-child editing is the add / update / archive trio — POST …/:id/<children>, PUT …/:id/<children>/:childId (404 when the child is not current), PATCH …/:id/<children>/:childId/archive — chosen per child over a destructive whole-collection replace.
  • A sibling facet never gets its own endpoint — it is part of the root's contract, written through the root's verbs; clearing it rides the root's PUT (Sibling tables).
  • Strict-vs-lenient body handling is decided per operation by its fields — a body with any optional field takes the lenient handler on add and update alike (Auto handlers).

Infra layer

  • schemas/: one schema function per file — the base, each role, each child, each sibling in its own <name>_schema.go. No bundling.
  • views/: one view definition per file — <entity>_view.go, and the identity view in its own person_view.go.
  • Repositories at the infra root: <entity>_repository.go, one per aggregate.
  • Outbound adapters (HTTP, gRPC clients) live under internal/infra/external/; handlers never import the toolboxes directly (Cross-service).

Migrations

  • The service's own sequence starts at 0001, independent of the framework's (Migrations).
  • One migration pair per scaffolded entity — all of the entity's tables (base, role, every child, every sibling) in a single 000N_<entity>.up.sql in FK-dependency order, with its .down.sql dropping in reverse. Not one pair per table: five files for one entity wastes version numbers and scatters one atomic schema.
  • Child and sibling tables are owner-prefixed — person_addresses, student_grades, student_scholarships — never bare generic names.
  • Unique constraints are named <table>_<col>_key, identically in every dialect, so the repository binds a single name.
  • Tables and columns are snake_case; the Go↔column type mapping per dialect is the TableSchema section's authority.

Bootstrap layer

  • One feature per aggregate — <entity>_feature.go holds that aggregate's repo + view and delegates mounting to internal/web/ in one line.
  • The identity view is its own feature — persons_feature.go (or the identity's name), never cargo inside a role's feature.
  • wire.go is the single registration site: instantiate features, contribute GraphQL/gRPC cumulatively, list features (their order is the OpenAPI sidebar order).

Cross-cutting names

ThingConvention
Permissionsresource:action, lowercase, resource = the entity (e.g. student:create, student:read); the identity read surface carries its own resource (e.g. person:read). Generic vs per-operation granularity is a modeling choice — pick one and apply it uniformly across REST, GraphQL and gRPC (Authorization).
Notification types<What>Notification; unique-field conflicts are <Field>AlreadyExists… with a conflict semantic (409).
Translation keysIdentical to the notification type name; field labels are <Entity><Field>Field; the entity name itself is a key too.
Route groupsPlural kebab-case of the entity (/students, /students/:id/grades); exports (when enabled) mount at the app root (/students.csv).
GraphQL fieldsList = plural entity; mutations = create<Entity> / update<Entity> / patch<Entity> / archive<Entity>… mirroring the REST verbs (GraphQL).
TestsBeside the source, <file>_test.go. Unit tests own what the entity adds (rules, mappers, criteria); handlers/wiring belong to end-to-end suites, not unit tests.
The generator contract. A scaffolder building on this framework: reads this page from the version the target service pins (the docs ship inside the module); produces exactly the layout above; takes every API signature from the mapped sections, never from memory or from this page; treats a developer's explicit instruction as the only license to deviate, and records the deviation.
