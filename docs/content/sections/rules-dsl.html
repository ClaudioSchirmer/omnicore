Rules DSL — IfXxx and actionName dispatch

Rules (domain/rules.go) exposes a mode-scoped DSL inside BuildRules: seven IfXxx closures, each gating its body on the current EntityMode. The framework picks the mode — one per verb, including a dedicated mode for the archive and unarchive state-transitions — so the closure you write IS the verb selector. The caller also picks the actionName (the last parameter on every Get* entry point — third for GetInsertable/GetArchivable/GetUnarchivable/GetDeletable, fourth for the closure-form GetUpdatable/GetPartialUpdatable). Auto handlers pass the canonical PascalCase string ("GetInsertable", etc.); manual handlers may pass any string. actionName is NOT how you select a verb — the mode is; it is a free-form label that reaches BuildRules and the audit event, used only to distinguish flavors within one mode (e.g. the shared-base upsert vs a cold insert, or "AdminCreate" vs canonical "GetInsertable").

r.IfInsert(func() { ... })
r.IfUpdate(func() { ... })          // PUT / PATCH only
r.IfDelete(func() { ... })
r.IfArchive(func() { ... })         // the archive state-transition
r.IfUnarchive(func() { ... })       // the unarchive state-transition
r.IfInsertOrUpdate(func() { ... })  // fires for Insert + Update (PUT/PATCH)
r.IfDisplay(func() { ... })         // see "key facts" below — inert today

Key facts

  • Archive and Unarchive have their own clauses — IfArchive and IfUnarchive. Each is a distinct verb: its own EntityMode (ModeArchive / ModeUnarchive), its own sealed ValidEntity (Archivable / Unarchivable), its own Get* entry point — so it dispatches its own closure. IfUpdate is PUT/PATCH exclusively and does NOT fire during a transition; r.Mode() reports the real mode. Put archive-only invariants (owner check, "cannot archive the primary account", …) in IfArchive; do NOT reach for an actionName string to tell archive from update — the clause already did.
  • The shared-base upsert fires IfInsert with actionName == "GetUpsertable" — there is no GetUpsertable function. The 7th Auto handler (SharedBaseInsertCommandHandler, the Party-Role upsert) still calls domain.GetInsertable in ModeInsert, but passes "GetUpsertable" instead of "GetInsertable" when the shared identity already existed (the warm path: load-first, apply on top, insert the role). So IfInsert sees one of two action names — "GetInsertable" for a cold first-time identity, "GetUpsertable" when an existing base is being re-used by a new role. This is the canonical case for an actionName branch: it is a genuine flavor within ModeInsert (no separate verb, mode, or sealed type), so branch on it in BuildRules to relax or tighten rules for the upsert (e.g. tolerate a shared field already set by a sibling role): if actionName == "GetUpsertable" { ... }. The shared base's natural key is immutable (it derives the deterministic identity), so a rule that guards it should treat a change as an error.
  • actionName is case-sensitive. The Get* family emits PascalCase ("GetInsertable"); IsValid emits lowercase "isValid". Custom callers passing their own actionName (e.g. "AdminCreate" for stricter validation) must match the string exactly inside BuildRules.
  • A rule rejects by FIELD REFERENCE — r.AddNotification(&e.Field, n, exposeValue). The reference is resolved deterministically (offset + pointer type) to the field it addresses; the wire name (acronym-aware lowerCamel, or the field's notifyAs:"..." tag), the labelKey:"..." catalog key and the echoed value (when exposeValue is true) are all read off the field itself — never guessed from a string. A typo is a compile error; a reference the resolver cannot honor (a non-pointer, a pointer field passed without &, a reference into a copy a helper made) panics on its first execution with the fix named. Helpers shared between rules therefore carry the FIELD POINTER, not the value. The explicit string seats that remain say so in their names: r.AddNotificationNamed("total", n) for cross-field rules, state rejections and synthetic tokens, and domain.ValidateEnumNamed where no bound Rules exists. Enum membership is domain.ValidateEnum(&e.Status, r). Full anatomy, precedence and the alias/tag interplay: Status mapping.
  • BuildRules is invoked on a POINTER — on the root and on every aggregate value object. The root already declares func (u *User) BuildRules(...); an AVO now does too (func (a *Address) BuildRules(...)), and the method is deliberately NOT part of the AggregateValueObject interface: children stay VALUE-stored in the tracker, and the framework materializes an addressable copy per validation pass, binds the child's *Rules to it and asserts the method on the copy's pointer — a child whose *T lacks BuildRules panics at first validation with the contract spelled out. Mutations a rule makes to the receiver hit the discarded copy, so validation still cannot alter a tracked child.
  • AggregateValueObject.BuildRules dispatches under the SAME mode as the root, and receives the SAME actionName. At the boundary, runAggregateValidations fires each child's closures under the root's mode (so an AVO's IfArchive fires when the aggregate is being archived) and propagates the root's actionName verbatim. The optional inline primitive domain.ValidateAggregateChild(root, item, mode, actionName, svc) takes the mode explicitly for the same reason.
  • IfDisplay is inert in the canonical dispatch. ModeDisplay is the resting mode after framework initialization (the EntityMode zero value is ModeUnknown), but no framework path calls NewRules(ModeDisplay, ctx, entityType). The closure exists in the DSL for symmetry; using it today produces dead code unless an external caller wires its own dispatch.
func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfArchive(func() {
        // archive-specific: e.g., "cannot archive the primary account",
        // or the Layer-2 owner check on the archive verb. No actionName
        // string branch — the clause IS the verb.
    })
}

Finishing an update as an archive

A rule can decide that the write it is validating should not leave the record active. Inside an IfUpdate closure, CompleteAsArchive() asks the framework to finish THIS update as an archive: 

func (t *Tenant) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfUpdate(func() {
        if t.Seats == 0 {
            t.CompleteAsArchive()
        }
    })
}

Past that point it IS the archive verb, carrying the update's field changes along: the row takes the entity's full field set plus the DeletedAt stamp, the child cascade runs, the shared identity converges, the outbox event is ARCHIVED (so DeleteOnArchive views, upstream mirrors and the base-revision repair all route correctly), and the audit entry is an archive — with actionName still naming the door it came through.

IfArchive does NOT fire on this path. The rules run once, in ModeUpdate. The rule that calls CompleteAsArchive() IS the decision, so its guard belongs in the same closure. What still applies is Modes(): an entity that does not declare ModeArchive cannot be archived through this door either.

Only the domain decides, and only once. The call is legal in exactly one place — an IfUpdate closure in the entity's own BuildRules. A Command's ApplyTo runs before the framework marks the mode; a handler runs after the rules window has closed; another verb's closure is the wrong mode. All of them panic with a message naming the misuse. And once GetUpdatable returns, the request is folded into what the write IS — the sealed Updatable.EntityMode(), ModeUpdate or ModeArchive, never anything to combine with the Go type — and cleared from the entity. The write path reads that one value, so nothing between the seal and the database can change the operation. Same guarantee IsPartial() has always had.

There is no inverse. The automatic edit path never loads an archived row — FindByID is active-scoped — so "finish as unarchived" would have nothing to act on. Changing fields WHILE restoring is the unarchive verb's job: it writes the entity's field set like every other verb, so a manual handler that loads the archived aggregate, applies its changes and calls GetUnarchivable persists both in one transaction.

Guard barriers — StopIfInvalid

Some rules are preconditions for the rules below them: an owner that must exist before it is dereferenced, a snapshot that must have been captured, a parse that must have succeeded. When one of those rejects, everything after it is validating a premise that is already false — noise in the response at best, a nil dereference at worst. r.StopIfInvalid() ends the pass right there: 

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Address == nil {
            r.AddNotification(&u.Address, domain.RequiredFieldNotification{}, false)
        }
    })

    r.StopIfInvalid()

    // nothing below this line runs once a rule above it rejected the write —
    // no closure, no hand-written if, no bare statement
    r.IfInsertOrUpdate(func() {
        if !validZip(u.Address.ZipCode) { ... }
    })
}

It takes nothing and returns nothing. Call it on its own line, between rules — there is no return to write around it and no value to test.

What it stops

Everything the pass has not done yet, which depends on where it is called — the pass is sequential (this owner's rules, then this owner's value objects, then each aggregate child in turn):

Called fromStops
a root's BuildRules the rest of that BuildRules; the root's automatic value-object validation; the BuildRules and value objects of every aggregate child
an AggregateValueObject's BuildRules the rest of that child's BuildRules; that child's own value objects; every sibling still queued behind it (both the discovered collection and the manually registered ValidateAggregateValueObject queue)

The framework's structural gates sit outside the barrier and always report: Modes() not declaring the verb, and a missing or invalid id. Those describe the frame of the write rather than its values, so a rejected write still says the verb was not allowed at all.

Where you may write it

Anywhere the line actually executes: at the top level of the body, inside a hand-written if, inside a loop, inside a method the rules call, inside nested anonymous functions, or inside a mode closure the current verb dispatches. It reads the same in an AggregateValueObject's BuildRules as in a root's. The one placement that does not stop is one the verb never reaches — written inside a mode closure that does not dispatch, the whole closure is skipped and the barrier with it, exactly as any other rule in that closure would be.

It can never skip validation

The barrier fires only when a notification has already been emitted — that is the whole condition. With a clean context it does nothing and the pass runs whole. So a stop cannot turn an invalid write into a valid one: it happens exclusively on a write that is already rejected, and the notification that triggered it is what the caller gets back. The sealed ValidEntity contract is untouched — the two exits are unchanged, a sealed entity or a domain.NotificationCarrier error.

What changes is how much is in that carrier. Without a barrier the response lists the guard's notification alongside every field the entity would also have failed on; with one it names the guard alone. That is the point, and it is a deliberate exception to the accumulate-everything default: reporting every violation at once is right when the violations are independent, and wrong when one rule already invalidated the question the others are answering.

The unwind is an ordinary Go unwind. A defer the rule itself registered still runs on the way out — that is correct and usually what you want. The one thing that breaks the barrier is a bare recover() inside BuildRules: it swallows the framework's internal stop signal and the pass continues. Do not write one. (The signal is a private type recovered by the framework at every BuildRules seat, so it never escapes the domain package, and a genuine panic in a rule still propagates with its value intact.)
