OpenAPI / Swagger UI

The framework generates an OpenAPI 3.1.0 document from the same Go types the HTTP wrappers already consume — Request DTOs (with json:/path:/query:/filter: tags), Response DTOs (with json:/view: tags), the pipeline.FullBody marker, the HasPathID interface assertions. No swag init, no hand-written YAML, no separate annotations: the spec is a reflection-driven projection of the routes the consumer already wired.

Enable the spec

One line on the wire callback opts in:

func Wire(d bootstrap.Deps) bootstrap.Wiring {
    return bootstrap.Wiring{
        Translations: []translation.Module{...},
        Features:     []bootstrap.Feature{NewUsersFeature(d)},
        OpenAPI: &openapi.Config{
            Title:       "My Service",
            Version:     "1.0.0",
            Description: "Reference microservice for the OmniCore framework.",
            Servers: []openapi.Server{
                {URL: "https://api.example.com", Description: "Production"},
            },
            Contact: &openapi.Contact{Name: "Maintainer", Email: "ops@example.com"},
            License: &openapi.License{Name: "Apache-2.0", URL: "https://apache.org/licenses/LICENSE-2.0"},
        },
    }
}

openapi.Config is the operator-facing identity of the generated document; the framework folds it into the spec's info + servers blocks at boot. Every field beyond Title + Version is optional and omitted from the rendered spec when zero:

FieldTypeOpenAPI placement
Titlestring (required)info.title
Versionstring (required)info.version
Descriptionstringinfo.description
Servers[]Server{URL, Description}servers[]
Contact*Contact{Name, Email, URL}info.contact
License*License{Name, URL}info.license

With OpenAPI set:

  • Deps.OpenAPIRegistry becomes a non-nil *openapi.Registry threaded into every Feature.Mount(app, deps) call.
  • The framework auto-registers GET /openapi.json + the Swagger UI route (default GET /docs; configurable via openapi.uiPath in the YAML — see "Operator-tunable serving" below) after every feature has mounted.
  • GET /livez and GET /readyz go through openapi.MountRaw automatically so they appear in the spec.
  • When auth.mode: jwt is active, the AuthMiddleware.publicRoutes list is auto-extended with GET /openapi.json + the resolved UI path, so the documentation surface never sits behind the bearer wall.

Leaving Wiring.OpenAPI nil keeps everything off: Deps.OpenAPIRegistry stays nil, no spec routes are registered, and openapi.Mount / MountRaw become Fiber-only passthroughs (zero documentation cost).

Operator-tunable serving

Wiring.OpenAPI carries the spec identity (Title, Version, Description, Servers, Contact, License) because that is code-time information about WHAT the service exposes. The operational bits — where the Swagger UI is mounted and whether / redirects to it — live in microservice.<profile>.yaml under openapi: so they can vary per environment without a recompile:

openapi:
  uiPath: /docs           # default: /docs. Path where Swagger UI is served.
  rootRedirect: false     # default: false. When true, GET / → 302 uiPath.
  • Block is optional. Absent → defaults (canonical /docs, no redirect). Present but Wiring.OpenAPI is nil → ignored (no spec means no UI to redirect to).
  • uiPath moves the Swagger UI route. /openapi.json stays canonical because it is internal plumbing the UI fetches — tooling that scrapes the spec relies on a predictable path. Validated at boot: must start with /; must not collide with /openapi.json, /livez or /readyz.
  • rootRedirect, when true, registers GET / → 302 uiPath. Registration happens AFTER feature mounts and BeforeServe, so a service that owns / wins by registration order; the framework logs slog.Warn and skips on collision. Under auth.mode: jwt the redirect route is added to publicRoutes automatically so opening the host root in a browser does not trigger a 401.

Language selector (Swagger UI dropdown)

By default Swagger UI does not let the operator choose what Accept-Language goes on the wire — every "Try it out" call ships whatever the browser sent. openapi.Config.LanguageSelector bool (default false) opts into a global dropdown at the top of the rendered page that injects Accept-Language into every request via Swagger UI's requestInterceptor. Useful to exercise translated error messages without juggling a curl command per language.

OpenAPI: &openapi.Config{
    Title:            "MyService API",
    Version:          "1.0.0",
    LanguageSelector: true, // turn it on; bootstrap fills the rest
}

Wiring.Translations is mandatory. Independent of LanguageSelector, the boot guard validateWiring rejects an empty Wiring.Translations slice — notifications, error envelopes (ErrorMessage.Message), and audit fields all flow through the Translator; running with an empty Translator silently produces blank strings in production. Loud-at-boot is the chosen failure mode: every consumer declares at least one translation.Module.

The dropdown content lives on openapi.Config.Languages []LanguageOption ({Label, Value} pairs). Under bootstrap.Run the slice is auto-populated from Wiring.Translations when LanguageSelector=true AND the consumer left Languages empty:

  • Bootstrap walks Wiring.Translations and dedupes by configuration.Language — a service that registers both the framework's CorePTBR and its own apptrans.PTBR() collapses to a single PT_BR entry.
  • The microservice has the final word on which languages appear in the dropdown — registering only apptrans.PTBR() shows only PT_BR, even though translation.Default() loads seven behind the scenes.
  • English-first default. When LangENG is among the surviving entries, the bootstrap rotates it to position 0 so HTML's natural <select> behavior makes English the dropdown's default selection. Declaration order is otherwise preserved (after the rotation). When ENG is absent, declaration order is preserved as-is — the first declared language wins the default slot.
  • Each surviving entry emits {Label: lang.String(), Value: lang.HTTPPrefix()} — Label is what the operator sees in the <option> tag (e.g. PT_BR, ENG), Value is what gets written to the Accept-Language header (e.g. pt, en) and matches the prefix AppContextMiddleware reads at the request boundary.
  • LangUnknown and any language with an empty HTTPPrefix() are skipped (an empty Accept-Language on the wire would be meaningless).

Adding a 5th language to the service is just "register a new translation.Module" — the dropdown picks it up on the next boot without touching openapi.Config.

Override path. An explicit non-empty Languages slice on openapi.Config bypasses auto-discovery — useful for manual Wire flows that bypass bootstrap.Run, or for relabeling entries. The framework does not apply ENG-first rotation on an explicit slice (the consumer is in control of order):

OpenAPI: &openapi.Config{
    Title:            "MyService API",
    Version:          "1.0.0",
    LanguageSelector: true,
    Languages: []openapi.LanguageOption{
        {Label: "English", Value: "en"},
        {Label: "Português", Value: "pt"},
    },
}

Empty Languages after auto-discovery → no selector rendered. A service that opts in but whose Translations all map to languages with an empty HTTPPrefix() still boots normally — the /docs page is byte-identical to the no-selector baseline (no extra CSS, no extra DOM, no requestInterceptor). Label/Value are HTML-escaped on render, so consumer-controlled strings cannot inject script into the page.

Two registration paths

Every documented route flows through one of two entry points:

PathUsed byCarries
openapi.Mount(registry, group, method, path, handler, spec, doc) Canonical wrappers (via the *Spec siblings) AND manual handlers that still parse a typed Request DTO RouteSpec (mechanical) + Doc (prose + examples)
openapi.MountRaw(registry, group, method, path, handler, raw) Routes without a typed Request DTO — auth identity demos, in-process upstreams, vendor-shaped showcase handlers RawSpec (everything inline)

Both helpers are nil-safe — calling them with a nil registry registers the handler on Fiber and short-circuits the documentation step, so consumers can pass d.OpenAPIRegistry uniformly without nil-checking.

Every field on every carrier, so a consumer building a route knows exactly what is available without grepping the framework source.

Helpers — type-parameterized shortcuts

Five helpers spare the consumer the verbose struct literals while still leaving the underlying types fully accessible when finer control is needed:

HelperReturnsUse when
RouteSpecOf[TReq, TResp any](status int) RouteSpec RouteSpec{RequestType, ResponseType, SuccessStatus} Manual Mount call with a typed Request + Response DTO. Saves reflect.TypeOf(T{}) at every site.
RouteSpecOfPaged[TReq, TResp any](status int) RouteSpec RouteSpec{RequestType, ResponseType, SuccessStatus, Paged: true} Manual Mount call for a paged GET that emits via fwweb.RespondPaged. Sibling of RouteSpecOf with the Paged flag flipped so the spec renders data: array<TResp> + pagination: $ref(PaginationInfo). Pairing with fwresponses.None panics at Mount.
ResponseOf[T any](description string) ResponseSpec ResponseSpec{Description, Type} Inside RawSpec.Responses[status] when the response carries a typed shape. Same intent on the raw side that RouteSpecOf has on the canonical side. Composable — assign Examples / ContentType on the returned value before storing.
PathParam(name, description string) Parameter Parameter{In: InPath, Name, Description, Required: true} Declaring path parameters on a MountRaw route. Defaults to {type: string}; for typed segments use the Parameter literal directly with Type: reflect.TypeOf(int64(0)).
QueryParam(name, description string, t reflect.Type) Parameter Parameter{In: InQuery, Name, Description, Type} Declaring query parameters on a MountRaw route. Required defaults to false — flip on the returned value when needed.

None of these is the ONLY path — every helper has an equivalent struct literal that produces the same result. They are the common-case shortcuts.

Spec-aware wrapper siblings

Every canonical wrapper has a *Spec sibling that returns (fiber.Handler, openapi.RouteSpec):

  • fwweb.CommandWithBodySpec
  • fwweb.CommandWithBodyIDSpec
  • fwweb.CommandByIDSpec
  • fwweb.QueryWithParamsSpec
  • fwweb.QueryByIDSpec
  • fwweb.QueryAsCSVSpec / fwweb.QueryAsXLSXSpec (and the generic QueryExportSpec) — return (handler, RouteSpec) with RequestType + FileResponse + OmittedQueryParams prefilled, so a tabular export mounts via the canonical Mount just like any JSON route

Same generics, same arguments, same handler behavior. The sibling extracts Strict via type-assertion to pipeline.FullBodyEnforcer and sets HasPathID=true for every wrapper that auto-binds the Fiber :id segment.

// Before — works, but does not appear in /openapi.json:
users.Post("/", fwweb.CommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[...]{...},
    fiber.StatusCreated))

// After — sibling + Mount; appears in the spec as well:
insertH, insertSpec := fwweb.CommandWithBodySpec(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[...]{...},
    fiber.StatusCreated)
fwopenapi.Mount(d.OpenAPIRegistry, users, fiber.MethodPost, "/",
    insertH, insertSpec,
    fwopenapi.Doc{Summary: "Create a user", Tags: []string{"Users"}})

Manual handlers with a typed Request DTO

A handler that hand-rolls its dispatch (Bind().Body() → NewQueryParser.Parse → BindPath → ToCommand → Pipeline.Dispatch) still owns the same kind of DTOs the canonical path owns. openapi.Mount covers them too — pair it with fwopenapi.RouteSpecOf[TReq, TResp](status) so the consumer just names the Request / Response DTOs:

fwopenapi.Mount(d.OpenAPIRegistry, group, fiber.MethodPost, "/",
    customInsertUser(d.Pipeline, repo, svc),
    fwopenapi.RouteSpecOf[requests.InsertUserCustomRequest, responses.UserCustomResponse](
        fiber.StatusCreated),
    fwopenapi.Doc{Summary: "Create (manual showcase)", Tags: []string{"Users — manual"}})

For state-transition endpoints (DELETE → 204, archive/unarchive returning the envelope without a data field), pass fwresponses.None as TResp — the spec assembler recognizes the sentinel and emits the envelope without data, mirroring the canonical wrappers' fwresults.None / fwresponses.NoBody pairing:

fwopenapi.Mount(d.OpenAPIRegistry, group, fiber.MethodDelete, "/:email",
    customDeleteUser(d.Pipeline, repo, svc),
    fwopenapi.RouteSpecOf[requests.UserCustomKeyRequest, fwresponses.None](
        fiber.StatusNoContent),
    fwopenapi.Doc{Summary: "Hard-delete (manual showcase)", Tags: []string{"Users — manual"}})

Consumers that need RouteSpec.Strict or RouteSpec.HasPathID (rare on the manual path — neither marker is auto-derivable from the hand-rolled handler) build a hand-written RouteSpec literal instead. RouteSpecOf is the common-case shortcut, not the only path.

For a manual paged GET that emits via fwweb.RespondPaged, pair the same openapi.Mount with the paged sibling fwopenapi.RouteSpecOfPaged[TReq, TResp]. The flag flips the success envelope to data: array<TResp> + pagination: $ref(PaginationInfo) so the rendered spec matches the wire shape — same flag the canonical QueryWithParamsSpec sets automatically:

fwopenapi.Mount(d.OpenAPIRegistry, group, fiber.MethodGet, "/",
    customListUsers(d.Pipeline, h, parser),
    fwopenapi.RouteSpecOfPaged[requests.FindUsersCustomRequest, requests.FindUsersCustomResponse](
        fiber.StatusOK),
    fwopenapi.Doc{Summary: "List users (manual showcase)", Tags: []string{"Users — manual"}})

The ?onlyTotal=true runtime variant (envelope collapses to pagination: TotalOnlyPagination{totalCount} and drops data) is documented in prose on each paged operation's Doc.Description — the spec's success schema stays the canonical listing shape so Swagger UI's default render isn't cluttered with a oneOf union on the common path.

Free-form routes via MountRaw

Routes without a typed Request DTO declare their shape inline. Parameters, request body and responses are explicit; the schema generator still walks the Go types passed under Type fields so primitives, pointers, structs, time/UUID, and named structs (via $ref) render consistently with the canonical path.

fwopenapi.MountRaw(d.OpenAPIRegistry, app, fiber.MethodGet, "/whoami",
    whoami,
    fwopenapi.RawSpec{
        Summary: "Returns the authenticated identity",
        Tags:    []string{"Auth"},
        Public:  true,
        Responses: map[int]fwopenapi.ResponseSpec{
            200: fwopenapi.ResponseOf[WhoamiResponse]("Authenticated identity or anonymous placeholder"),
        },
    })

fwopenapi.ResponseOf[T](description) is the symmetric counterpart of RouteSpecOf[TReq, TResp] on the canonical side — both spare the consumer the reflect.TypeOf(T{}) invocation by carrying the type through a generic parameter. For responses that need ContentType or Examples, capture the helper output in a variable and assign the extra fields before storing it in the map:

spec := fwopenapi.ResponseOf[WhoamiResponse]("Authenticated identity")
spec.Examples = map[string]fwopenapi.Example{"alice": {Value: WhoamiResponse{Subject: "alice-uuid"}}}
// Responses: map[int]fwopenapi.ResponseSpec{200: spec}

Use the ResponseSpec struct literal directly when keeping every field on screen is the preference — both paths coexist; the helper is the common-case shortcut, not the only path.

Parameter extraction — path, query, header

The framework derives parameters from the route's Fiber path AND the Request DTO's struct tags. Five mechanisms feed the rendered parameters[] block:

  1. Fiber path → {name} templating. Every :name segment in the route's Fiber path becomes {name} on the OpenAPI path. /users/:id/archive renders as /users/{id}/archive; /tenants/:tenantId/users/:id renders as /tenants/{tenantId}/users/{id}.
  2. Request DTO path:"X" tag. Each tagged field of the Request DTO emits one parameters[].in=path entry with the field's reflected type driving the schema. The same field is skipped from the body schema.
  3. Auto-stubbed :id. When RouteSpec.HasPathID is true (every framework wrapper that auto-binds :id) AND the Request DTO didn't tag path:"id", the spec assembler adds a string-typed id path parameter automatically. Combined with custom path tags so compound routes like /tenants/:tenantId/users/:id document every segment without per-route configuration.
  4. Request DTO query:"X" filter:"ops" tag. Each leaf emits one query parameter per declared operator: query:"name" filter:"eq,in,startswith" produces ?name, ?name.in, and ?name.startswith (the bare eq form has no suffix; every other operator surfaces as name.<op>). The same field is skipped from the body schema.
  5. Nested embed groups. A struct-typed Request field carrying query:"prefix" (no filter:) is an embed group — every leaf below contributes a wire key prefixed by its parent. Example: Addresses AddressFilter \`query:"addresses"\` with City *string \`query:"city" filter:"eq,istartswith"\` inside renders ?addresses.city + ?addresses.city.istartswith.
  6. RawSpec.Parameters. Raw routes declare each parameter inline via PathParam / QueryParam or a Parameter literal. The framework normalizes Required=true for every InPath entry at registration time.

Operator coverage — the operators a filter: tag may declare match the operators QueryWithParams recognizes at runtime: eq (default, no suffix), ne, in, nin, gte, lte, gt, lt, startswith, contains, ieq, ine, iin, inin, istartswith, icontains. Each surfaces as its own query parameter in the rendered spec.

Spec lifecycle — Registry, Components, lazy build

The framework builds the spec lazily and caches it for the lifetime of the service. The relevant types:

  • Registry — collects every Operation registered via Mount / MountRaw. One per service (constructed by bootstrap.Run when Wiring.OpenAPI is non-nil). Preserves insertion order so the rendered spec mirrors the order features were wired (useful for diff-friendly snapshots and for Swagger UI's sidebar layout). Last-write-wins on (METHOD, path) collisions.
  • Components — the dedup pool for named-struct schemas the schema generator encounters while walking the type graph. Owned by the Registry and shared across every route. Same named struct referenced from N different DTOs surfaces ONCE in components.schemas; every site emits a $ref: #/components/schemas/<Name> pointer.
  • Spec — the lazily-built document. Built on the first call to Build() or MarshalJSON(); subsequent calls return the cached byte slice. Safe for concurrent use; the spec is immutable for the lifetime of the value, matching the "registry assembled at boot, served forever" pattern.
  • Self-referential types. A struct that owns a pointer to itself (linked list, tree, anything with a *Self field) does not infinite-loop the generator. The first encounter inserts a placeholder under the type's name in Components BEFORE walking its fields; the recursive site finds the placeholder and emits the $ref on its way back up.

Boot-time guarantees

Everything that can be checked at boot, is — so the operator finds out about a broken declaration at start time, not when a consumer opens /docs:

  • OpenAPI uiPath validation. Must start with /; must not collide with /openapi.json, /livez or /readyz. Violations abort boot with a descriptive error.
  • Examples validated against types. Every Doc.RequestExamples + every success-status Doc.ResponseExamples + every RequestBody.Examples + every typed ResponseSpec.Examples is run through json.Marshal + json.Unmarshal with DisallowUnknownFields at Mount / MountRaw time. A typo aborts the boot with "openapi: example <name> on <METHOD path> <slot>: <reason>".
  • Error-status examples loosely validated. Examples on non-success statuses are only checked for JSON validity (the ErrorEnvelope shape is shared and accepts arbitrary errors[] content). The boot still rejects payloads that aren't JSON-marshalable.
  • Per-property example: tag parsing. Failure to parse the tag value against the field's reflected type → boot panic naming the struct + field.
  • Path parameter completeness. A struct field carrying path:"name" that does not match any :name segment on the route, OR a :name segment without a tag AND without HasPathID, surfaces a runtime parameter-stub mismatch (visible in the rendered spec) — the framework does not boot-validate the alignment today, but the runtime BindPath rejects the request at first call.

Required-field rule. Strict (handler embeds pipeline.FullBody): every kept field is required. Lenient: required when the field is non-pointer AND the json tag does not carry ,omitempty.

Per-property example: tag. Annotate scalar fields on Request and Response DTOs to seed concrete values into Swagger UI. The generator reads f.Tag.Get("example") in walkFields, converts the raw string via the field's reflected type, and sets the schema's example — Swagger UI then aggregates per-property examples into a composite object example automatically. Use this for the common case (one representative payload per DTO field). The Doc.RequestExamples / Doc.ResponseExamples map remains the path for N exemplos per status or shapes a single tag cannot express (arrays of structs with specific items, multi-field objects with cross-field semantics).

type InsertUserRequest struct {
    Name  string  `json:"name"            example:"Alice"`
    Email string  `json:"email"           example:"alice@example.com"`
    Phone *string `json:"phone,omitempty" example:"+5511999998888"`
}
type InsertUserResponse struct {
    ID    domain.ID `json:"id"    example:"7b3c1f10-3c7e-4a8d-9f0e-9d2a8e6d4b51"`
    Name  string    `json:"name"  example:"Alice"`
    Email string    `json:"email" example:"alice@example.com"`
}

N exemplos per route — Doc.RequestExamples / Doc.ResponseExamples

When a single tag per field is not enough — multiple representative payloads ("minimal", "withAddress", "edgeCase"), or shapes that compose nested arrays of structs that the tag cannot express — declare them on the Mount call's Doc. Each entry is an openapi.Example with optional Summary (dropdown label), optional Description (markdown), and the actual Value (any JSON-marshalable Go value or json.RawMessage):

fwopenapi.Mount(d.OpenAPIRegistry, users, fiber.MethodPost, "/", h, spec,
    fwopenapi.Doc{
        Summary: "Create a user",
        Tags:    []string{"Users"},
        RequestExamples: map[string]fwopenapi.Example{
            "minimal": {
                Summary: "Minimal valid payload",
                Value:   requests.InsertUserRequest{Name: "Alice", Email: "alice@example.com"},
            },
            "withAddress": {
                Summary: "With one address",
                Value: requests.InsertUserRequest{
                    Name: "Bob", Email: "bob@example.com",
                    Addresses: []requests.AddressInput{{Street: "Main St", ZipCode: "10001"}},
                },
            },
        },
        ResponseExamples: map[int]map[string]fwopenapi.Example{
            fiber.StatusCreated: {
                "happyPath": {
                    Summary: "Created — domain.ID assigned by the database",
                    Value:   requests.InsertUserResponse{ID: "u_abc123", Name: "Alice"},
                },
            },
            fiber.StatusUnprocessableEntity: {
                "duplicateEmail": {
                    Summary: "Email already in use",
                    Value:   json.RawMessage(`{"success":false,...}`),
                },
            },
        },
    })

Success status wraps; error status renders raw. The framework treats the operation's SuccessStatus as the "happy" envelope and automatically wraps each example's Value in the canonical Response envelope (success:true, status, description, data:<value>). The consumer only provides the inner data shape — same Go type the runtime handler emits via ResponseType. Every other status (404, 422, 409, …) is rendered verbatim — the consumer fully controls the envelope, typically success:false with a custom errors[] shape. Mirror behavior on MountRaw: RequestBody.Examples and ResponseSpec.Examples always render verbatim (raw routes are entirely consumer-controlled).

Auto-merge of canonical default on error statuses. When the consumer declares examples on a status the framework documents by default (400/401/403/404/422/500), the canonical entry auto-merges under the key "default" in the rendered examples map. The consumer can:

  • Coexist with the default: declare any number of named entries ("happyPath", "duplicateEmail", …) — the framework's canonical envelope appears alongside them under "default" in the dropdown.
  • Override the default: declare "default" explicitly with a custom Value — the explicit entry wins.
  • Remove the default: declare "default" with an empty Value (fwopenapi.Example{}) — the canonical entry is omitted from the rendered spec.

When the consumer declares nothing for an error status, the renderer emits the singular example field carrying the framework's canonical envelope (no examples dropdown) — the common case for routes that don't customize error bodies.

Boot-time validation. Every Value is validated once at Mount / MountRaw time. Request and success-status examples are checked strictly against the declared type via json.Marshal + json.Unmarshal with DisallowUnknownFields — a typo on a field name aborts the boot with a diagnostic naming the route + slot + example name + cause. Error-status examples are checked only for JSON validity (the ErrorEnvelope shape is shared and accepts arbitrary errors[] content). json.RawMessage passes through verbatim.

Public default-error registry — openapi.DefaultErrorExample(status). The canonical entry the framework auto-merges is exposed via two public helpers:

  • DefaultErrorExample(status int) (Example, bool) — the entry for one status. ok=false for statuses outside the framework's set (400/401/403/404/422/500).
  • DefaultErrorExamples() map[int]Example — a fresh copy of every entry, keyed by status. Mutating the returned map does not affect the framework's internal registry.

Use these when customizing the canonical entry without reauthoring its payload (override Description only), or when assembling a Responses map programmatically:

def, _ := fwopenapi.DefaultErrorExample(fiber.StatusUnprocessableEntity)
def.Description = "Falha de validação no campo `email`."

ResponseExamples: map[int]map[string]fwopenapi.Example{
    fiber.StatusUnprocessableEntity: {
        "default":     def,   // consumer-customized default
        "duplicate":   {Value: ...},
    },
}

Response envelope and standard errors

Successful responses wrap the consumer's ResponseType in the framework's web.Response envelope (success, status, description, data). When the projection lands on responses.None (the fwresults.None / fwresponses.NoBody default for Archive/Unarchive/Delete), the envelope is emitted WITHOUT the data field — matching the runtime behavior of respondWithProjection.

Standard error envelopes are added per route based on its shape:

StatusAdded when
400 Bad RequestRoute carries a request body (canonical RequestType with body fields OR RawSpec.RequestBody)
401 UnauthorizedAuth is enabled AND the route is not public
403 ForbiddenAuth is enabled AND the route is not public (any authenticated route can produce a Forbidden outcome via authorization Layer 2 / Layer 3)
404 Not FoundHasPathID=true OR RawSpec declares a path parameter
422 Unprocessable EntityAlways (every route can produce domain-validation rejections)
500 Internal Server ErrorAlways (recovered panic / escaped error)

Custom error status via Doc.ResponseExamples. A canonical route may emit a status outside the table above — typically when a service notification overrides Semantic() to Conflict/Unavailable/etc. Declaring Doc.ResponseExamples[N] for that status auto-creates the response entry on the rendered spec, reusing the shared ErrorEnvelope schema; the consumer's examples render under content.application/json.examples, and the description comes from http.StatusText(N). The default auto-merge described below applies only on statuses with a DefaultErrorExample entry (400/401/403/404/422/500); non-default statuses surface exactly the consumer's declared examples, no canonical merge.

All error responses share the single ErrorEnvelope schema in components/schemas — mirrors web/response.go::Response with errors[] populated and the typed ErrorMessage shape. Registered exactly once in the components pool; every error response references it via $ref:

{
  "ErrorEnvelope": {
    "type": "object",
    "required": ["description", "errors", "status", "success"],
    "properties": {
      "success":     {"type": "boolean"},
      "status":      {"type": "integer", "format": "int32"},
      "description": {"type": "string"},
      "errors": {
        "type": "array",
        "items": {
          "type": "object",
          "required": ["context", "messages"],
          "properties": {
            "context": {"type": "string"},
            "messages": {
              "type": "array",
              "items": {
                "type": "object",
                "required": ["message"],
                "properties": {
                  "notificationKey": {"type": "string"},
                  "field":           {"type": "string"},
                  "value":           {"type": "string"},
                  "funcName":        {"type": "string"},
                  "message":         {"type": "string"},
                  "semantic":        {"type": "string"}
                }
              }
            }
          }
        }
      }
    }
  }
}

The notificationKey + semantic fields propagate the typed identity through to the wire — clients can branch UI on the key (e.g. show an inline "duplicate email" warning) without parsing the HTTP status code. field uses the JSON path the consumer sent (addresses[0].zipCode for nested aggregate validation failures, email for root field failures), matching the wire shape exactly.

Concrete examples in Swagger UI. The framework populates examples so the rendered page shows realistic envelopes instead of the type-default placeholders (success: true, status: 0) that Swagger UI fabricates from bare types:

  • Success: per-property example on the inline envelope schema — success: true, status = the operation's SuccessStatus, description = the matching HTTP reason phrase. The data field's example is derived from the ResponseType schema.
  • Errors: a content-level example per status (400/401/403/404/422/500) overrides the shared $ref's default — success: false, status matching the response code, and a representative errors[] entry carrying the typed notification the framework actually emits for that status (SchemaViolationNotification on 400, RequiredFieldNotification on 422, InternalServerErrorNotification on 500, etc.). The ErrorEnvelope schema stays a single dedup'd entry in components/schemas.

Auth declarations

When auth.mode: jwt, the framework calls openapi.Register with WithAuth(AuthContext{PublicRoutes: ...}). The rendered document gains:

  • components.securitySchemes.bearerAuth (http / bearer / JWT).
  • security: [{bearerAuth: []}] on every operation that is NOT public.
  • Automatic 401 Unauthorized and 403 Forbidden entries in the operation's responses block (any authenticated route can produce a Forbidden outcome via authorization Layer 2 / Layer 3).

An operation is treated as public when Doc.Public / RawSpec.Public is true OR when its METHOD /path appears in auth.publicRoutes from microservice.<profile>.yaml — the same allowlist AuthMiddleware enforces at runtime.

Hidden vs Public

  • Hidden=true: the operation is excluded from the rendered spec entirely. Still registers on Fiber so the route works at runtime; only the documentation surface omits it. Use for internal upstream / scaffolding routes that have no business appearing in a public spec.
  • Public=true: the operation appears in the spec WITHOUT security: [{bearerAuth: []}] and WITHOUT the auto-added 401/403 entries. Use for routes that genuinely bypass auth (health probes, OIDC discovery proxies, identity demos).

Swagger UI HTML

The UI route (default /docs; overridable via openapi.uiPath) serves a minimal HTML page that loads swagger-ui-dist from the unpkg.com CDN and points at /openapi.json. Consumers needing fully offline operation override the UI route after Register returns (Fiber's last-write-wins) and serve their own HTML pointing at the same JSON endpoint.
