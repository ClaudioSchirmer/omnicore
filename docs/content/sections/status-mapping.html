HTTP Status Mapping

Status mapping is a pipeline-level concern, shared by both the write and read paths: every response — a 201 from a POST, a 422 from a failed BuildRules, a 404 from a missing view document, a 400 from a malformed query string — is shaped here, at the boundary where the pipeline's Result becomes an HTTP envelope. That is why it lives outside the Write side / Read side groups.

Each Notification declares its semantic nature via the Semantic() method. The framework maps Semantic → HTTP status automatically — there is no global registry anymore. RespondFromResult picks the first non-Validation Semantic found in the messages; if all are Validation, returns 422.

Who authors what. The table has two halves. Some rows the FRAMEWORK raises — the routing and transport statuses (400, 404, 405, 408, 413, 429, 431, 501) come out of fwweb.ErrorHandler, and the kernel domain notifications raise 404, 409 and 403 from the write path. The rest is vocabulary for the service: the framework ships no rate limiter, negotiates no media type, reads no conditional header, serves no byte ranges, holds no locks and never decides on your behalf that a resource is gone or withheld by law. Declaring Semantic() on your own notification is the whole opt-in — the same mechanism the 409 example below uses, over the full table.
Where the table stops, and why. The vocabulary is closed on purpose, and the line is not taste: a status is absent only when it is unreachable (nothing in this stack can author it — 411, which fasthttp never raises; 414, which collapses into ErrSmallBuffer and surfaces as 431; 417, which fasthttp writes straight to the socket without passing through the error handler; and the proxy/HTTP-2/TLS family 407, 421, 425, 426, 511), redundant (424 Failed Dependency, whose ground 502, 503 and 409 already cover), or structurally incompatible — which is the 304 case: it would have to answer with no body, and the canonical envelope always writes one. 418 is reserved by IANA as a joke and serves here as the standing "never mapped" sentinel the ErrorHandler fallthrough test asserts against.
SemanticSchema vs SemanticValidation: Schema = wire contract violated (consumer didn't honor the Request shape — malformed JSON, missing required field, wrong type). Validation = domain rejects values (business rules in BuildRules). The same RequiredFieldNotification struct appears in both worlds; the wire wrapper instantiates with WithSemantic(SemanticSchema) (per-instance override) → 400, and the domain emits default → 422.

Panic and routing — fwweb.ErrorHandler

bootstrap.Run wires fwweb.ErrorHandler(deps.Pipeline) into fiber.Config.ErrorHandler, so every error escaping a route, middleware, or panic recovery surfaces as the canonical Response envelope — same JSON shape consumers already see from RespondFromResult. Four branches:

  • NotificationCarrier escapes — translated against AppContext.Language() and emitted with the status derived from each notification's Semantic() (same path RespondFromResult uses on Failure).
  • Fiber 400 (the request could not be read as HTTP at all — Fiber's catch-all for a parse failure it has no more specific status for) → MalformedRequestNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticSchema → 400. Deliberately NOT SchemaViolationNotification: that type's contract is about the request PAYLOAD, and reusing it here would make a documented domain contract false. The underlying parse error stays off the wire.
  • A malformed :id segment (present, and not a UUID) is refused by the wrapper BEFORE the handler, in context "Request" with id echoed on field and the rejected segment on value. What the consumer hears follows the VERB, not the view's backing: a READ answers UnknownIDAddressNotification → SemanticNotFound → 404 (the consumer named no record), a WRITE answers MalformedIDNotification → SemanticSchema → 400 (the request shape was violated). The same rule governs an identity segment bound through a path: tag, so fwweb.BindPath classifies it identically for a hand-written handler. An EMPTY segment is not refused: it means the route was mounted without :id, which handlers.RequirePathID diagnoses as the developer error it is. Before this guard the segment reached the store, and the answer depended on where the view lived — a relational backing raised a driver error rendered as 500, while a Mongo-backed view of the same route answered 404 because the string matched no _id.
  • Fiber router 404 (no matching route) → RouteNotFoundNotification in context "Route" with METHOD /path echoed on field; mapped via SemanticNotFound → 404.
  • Fiber 405 (path matches but the HTTP method does not) → MethodNotAllowedNotification in context "Route" with METHOD /path echoed on field; mapped via SemanticMethodNotAllowed → 405.
  • Fiber 413 (body exceeds the configured BodyLimit) → PayloadTooLargeNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticPayloadTooLarge → 413.
  • Fiber 408 (the fasthttp read timeout http.readTimeoutSeconds fired while reading the request — the client was too slow) → ReadTimeoutNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticRequestTimeout → 408. Written best-effort before the connection closes.
  • Fiber 429 (a rate-limit middleware rejected the request through fiber.ErrTooManyRequests) → TooManyRequestsNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticTooManyRequests → 429. The framework ships no limiter — this branch exists so one plugged in by the service renders its refusal in the canonical envelope instead of the 500 an unrecognized code produces.
  • Fiber 431 (the header block or request line did not fit the read buffer — fasthttp's ErrSmallBuffer) → RequestHeaderFieldsTooLargeNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticRequestHeaderFieldsTooLarge → 431.
  • Fiber 501 (an HTTP request method this server implements nowhere) → NotImplementedNotification in context "Request" with METHOD /path echoed on field; mapped via SemanticNotImplemented → 501. Same notification the service-level emitter uses — "the server does not do this", read one layer down.
  • Any other error (recovered panic, unexpected error, any other *fiber.Error code) → InternalServerErrorNotification in context "Server"; mapped via SemanticInternal → 500. The panic value and stack trace are logged by fwweb.Recover() via slog.Error with method, path, panic, and stack attributes, and never reach the wire envelope. Services that need custom HTTP semantics MUST emit a NotificationCarrier with the appropriate Semantic() rather than calling fiber.NewError — the "one canonical path" rule still applies.
One status Fiber produces that we deliberately do NOT specialize. Fiber's serverErrorHandler raises ErrBadGateway (502) for a non-timeout net.Error while reading the request — a network failure on the CLIENT's connection. SemanticBadGateway means the opposite: an upstream this service depends on answered with something unusable. Rendering that as a 502 would make the envelope assert something false, so it falls through to 500, which is merely uninformative. A test locks this, so "completing" the switch fails the build and points back here.

The retry hint — Retry-After

A 429 (or a 503) without a retry hint is half an answer, and the canonical Response is a body: it carries success, status, description, data, pagination and errors, and no header slot. The guarantee the framework makes is the one it can keep — it never drops a header the request already set. Whoever knows when the window reopens sets it on the context before responding, and the envelope render leaves it alone.

With Fiber's own limiter that is free: the middleware sets Retry-After itself before calling LimitReached. Return the typed error from that hook instead of a bare status and the refusal lands in the canonical envelope with the hint intact: 

app.Use(limiter.New(limiter.Config{
    Max:        100,
    Expiration: 1 * time.Minute,
    // Default is c.SendStatus(429) — a bare status line outside the envelope.
    // Returning the typed error routes it through fwweb.ErrorHandler instead;
    // the Retry-After the limiter already set on the ctx survives.
    LimitReached: func(c fiber.Ctx) error { return fiber.ErrTooManyRequests },
}))

From a handler or a hand-written middleware the same two lines apply — set the header, then let the notification carry the status: 

c.Set(fiber.HeaderRetryAfter, strconv.Itoa(secondsUntilReset))
r.AddNotificationNamed("Requests", notifications.TooManyRequestsNotification{})

The symmetry is worth naming: Retry-After is exactly what the framework's own httpclient reads on the way back in (respectRetryAfter), so a service emitting the header is speaking the dialect its sibling services already understand.

Services that build the Fiber app manually via bootstrap.Build + bootstrap.Serve plug the handler in the same way: 

app := fiber.New(fiber.Config{
    ErrorHandler: fwweb.ErrorHandler(deps.Pipeline),
})
app.Use(fwweb.Recover())
app.Use(fwweb.AppContextMiddleware())

Service custom notification

The service declares the Semantic via method override on the notification itself — pick any member of the table above; nothing is registered anywhere: 

type EmailAlreadyExistsNotification struct{ domain.DomainNotificationBase }
func (EmailAlreadyExistsNotification) Semantic() domain.NotificationSemantic {
    return domain.SemanticConflict
}

No registration at startup. The framework maps the typed Semantic() declaration directly to the HTTP status at runtime.

The vocabulary is the framework's. Semantic() must return a member of the NotificationSemantic enum. A value invented outside it (domain.NotificationSemantic(99)) is not a compile error and not a boot failure — it simply misses semanticToStatus, and the response degrades to 422 with "semantic": "Validation" on the wire. In practice you should never need to: the table above is closed over every status something in this stack can actually author. If the status you need is not in the table, say so to the maintainer rather than inventing a value: the enum is the one place a new transport semantic is added, and adding it there is what keeps REST, gRPC and GraphQL telling the same story.
domain↔transport advantage: NotificationSemantic is a domain semantic enum (does not import net/http or Fiber). The GraphQL surface already maps the same enum to its own wire shape — Semantic().String() becomes errors[].extensions.semantic (alongside notificationKey, field, fieldLabel, value and funcName — the same fields the REST ErrorMessage carries) with HTTP always 200, per the GraphQL convention — without touching notification definitions. A future gRPC layer would map the identical enum to its status codes the same way.

Which base — the layer that raises it

Every notification embeds a base from the domain package, and there are three — one per layer that can author a rejection. They are markers: all three embed the same NotificationBase, so all three seal the interface and carry the same default Semantic() (SemanticValidation → 422), and no framework code branches on which one you picked. The choice is architectural, and it is not free-form: the base names the layer that RAISES the notification, and the type is declared in that same layer — never one layer's base on a type declared in another.

BaseRaised byDeclared in
domain.DomainNotificationBase a BuildRules rejection, a value object's IsValid, an aggregate invariant internal/domain/ — its notifications.go, or vos/ / aggregatevos/ for the types those packages emit (Service layout)
domain.ApplicationNotificationBase a hand-written command/query handler — a precondition the aggregate does not own, an orchestration refusal, an outbound failure translated into this service's vocabulary internal/application/, beside the handler that raises it
domain.InfrastructureNotificationBase an adapter — a unique violation classified by the dialect, a migration failure, a fixed upstream→semantic mapping the adapter owns as part of its contract internal/infra/, beside the adapter that raises it

The framework holds itself to the same rule, and reading it is the shortest way to see the split: the domain kernel notifications sit in domain/notification_core.go on DomainNotificationBase, the application kernel in application/notifications/core.go on ApplicationNotificationBase, the migration failures under infra/migration on InfrastructureNotificationBase.

An endpoint whose rules are not the aggregate's. When a request is validated by the handler rather than by BuildRules — an orchestration precondition, a cross-resource check the aggregate has no business knowing, a translated outbound failure — the rejection is an application notification: it takes ApplicationNotificationBase and it is declared in internal/application/. Moving it into internal/domain/notifications.go to sit beside the aggregate's own is the mistake this table exists to prevent — the aggregate never raises it, so the domain must not declare it, and a domain package that names a concern only the handler has stops being the zero-IO, self-contained layer the architecture depends on. Note that this is a placement rule, not a capability one: a persisted table still needs its type-anchored TableSchema over a domain struct even when that struct's BuildRules is empty (see Manual command handler). Worked example of the handler-side translation: httpclient · Outbound error handling.

The wire is identical whichever base you pick — NotificationKey is the struct name, so the translation key, the notificationKey the client branches on, and the status the Semantic() selects do not change with the layer. Only the placement does.

Root vs Aggregate Value Object uniformity

Validating root and AVO uses the same signature, the same DSL, and the same emit. actionName is propagated to both through the same chain (validateForInsert/Update/Delete → root's BuildRules → runAggregateValidations → each AVO's BuildRules). It allows rule branching by action flavor on both sides. 

// Root — User
func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Name == "" {
            r.AddNotification(&u.Name, domain.RequiredFieldNotification{}, false)
        }
        if u.Email != "" && !validEmail(u.Email) {
            // exposeValue=true echoes the FIELD's value as FieldValue in the response
            r.AddNotification(&u.Email, InvalidEmailNotification{}, true)
        }
        // An OPTIONAL field is referenced the same way (&u.Age, never u.Age):
        // the echo unwraps the pointer for you, and a nil one renders as "".
        if u.Age != nil && *u.Age > 150 {
            r.AddNotification(&u.Age, InvalidAgeNotification{}, true)
        }
    })
}

// Aggregate child — Address — identical signature, POINTER receiver
func (a *Address) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if a.Street == "" {
            r.AddNotification(&a.Street, domain.RequiredFieldNotification{}, false)
        }
        if actionName == "AdminCreate" && a.ZipCode == "" {
            // Branching by action — works identically on root and AVO.
            r.AddNotification(&a.ZipCode, domain.RequiredFieldNotification{}, false)
        }
    })
}

How it works — no new interface per entity

  1. Rules carries the ctx + entityType. NewRules(mode, ctx, entityType) packages the EntityMode + NotificationContext + the Go reflect.Type of the entity/VO that owns the Rules (the entityType lets AddNotification read the field's labelKey:"..." tag at emit). r.AddNotification/r.AddNotificationMessage delegate to the internal ctx. For root, the ctx is the entity's own e.NotificationContext(). For AVO, the ctx is a Scoped(NameSegment(collection), IndexSegment(i)) view of the root's ctx.
  2. Collection segment name is the JSON wire name. runAggregateValidations iterates root.AllAggregateItems() and renders the name the child declares in CollectionName() through toLowerCamel ("Addresses" → "addresses", "OrderLines" → "orderLines") — it is JSON wire output, so the convention is camelCase, not snake_case. The name itself is declared by the domain, never derived from the type.
  3. Acronym-aware toLowerCamel render: Name→name, URL→url, ZipCode→zipCode, URLPath→urlPath. Strings already in lowercase pass through ("id"→"id") — the legacy FieldName: "id" in mode validators remains intact.
  4. Wire layer (web/from_notifications.go, application/notifications/convert.go) reads m.ResolveFieldName() with precedence Override > rendered Path > FieldName.

One casing for every framework-raised field

The rule above is not limited to the domain rule path: everywhere the FRAMEWORK names a field in a notification, the wire field is the camelCase wire token — never a Go identifier, never a physical column. Emitters that hold a dotted Go field path (the read side's unresolved-path / invalid-filter-value 400s, the relational reader's unsupported-capability refusal, ReadCriteria.Restrict's 403) render it per segment through domain.WireFieldPath ("Addresses.ZipCode" → "addresses.zipCode"). Emitters that hold only a physical column (the not-found/concurrency probes, the shared-base duplicate and natural-key-immutable guards) resolve it to the schema's Go name first via TableSchema.WireFieldOf (user_id → "id"). Aggregate child rejections (EntityAlreadyAdded/EntityDoesNotExist/InvalidAggregateChild) name the child's declared CollectionName segment ("addresses"); the Go type name appears only as the value echo on the invalid-child rejection. What the framework does not touch: a FieldName the SERVICE supplies (SingleNotificationError, ConstraintBinding.Field, a manual NotificationMessage) travels verbatim — declare it in wire casing — and the deliberate non-field entries (the router fallbacks' "GET /path", the migration context) stay as they are.

Controlling the wire field name

Three paths feed ResolveFieldName(). Pick by lifetime of the rule — entity-wide and stable, per-request and conditional, or no override at all.

PathWhere it livesWhen to reach for it
Default emission r.AddNotification(&e.Field, n, expose) inside BuildRules The Go identifier already matches the wire name (after acronym-aware toLowerCamel). The most common case — no extra plumbing needed.
The notifyAs:"..." struct tag on the field The wire name differs from the camelized Go name as a property of the field itself — declared once on the OWNING entity's field (an aggregate value object declares its own fields' tags; a raw or enum value object is generic and shared, so its name always comes from the field that holds it), and honored by EVERY seat that emits about the field: a field-reference rule, the automatic value-object pass, an enum membership refusal and a named emission all render the same token, composing with scoped prefixes ("addresses[0].cep").
BaseEntity.AddFieldNameAlias(goFieldName, wireName) Domain method on the entity (declare it in the constructor so every instance carries it) The renaming is a stable rule of the instance — every message whose LEAF field is that GO name surfaces under wireName, overriding the notifyAs tag. Applied automatically inside checkAllNotifications via applyFieldAliases before contexts are collected.
NotificationContext.ChangeFieldName(orig, new) Imperative call in a manual handler (or anywhere the consumer holds the *NotificationContext) The renaming is conditional / per-endpoint — only this specific flow renames the field. Compares each message via ResolveFieldName() and sets Override = new on the ones that match. Path/FieldName originals stay preserved for diagnosis; only the wire changes.

Precedence, highest first: Override (set by ChangeFieldName, matching the RESOLVED name) > the leaf segment's wire token (instance alias > notifyAs tag) > the acronym-aware lowerCamel rendering of the Go name. The alias and the tag share the segment slot — declarative, per-field, prefix-composing; Override is the imperative, whole-string literal a handler reaches for per request. 

// Declarative — every emission about "Email" on this entity surfaces as "primaryEmail".
// orig is the RESOLVED wire name (post-render, "email"), not the Go identifier:
func NewUser(...) *User {
    u := &User{...}
    u.AddFieldNameAlias("email", "primaryEmail")
    return u
}

// Imperative — only this handler's response renames the field:
func (h *AdminPatchHandler) Handle(ctx *configuration.AppContext, cmd *AdminPatchCommand) (...) {
    // ... after Dispatch, before returning:
    if errCarrier, ok := err.(domain.NotificationCarrier); ok {
        for _, c := range errCarrier.NotificationContexts() {
            c.ChangeFieldName("archived", "status")
        }
    }
    // ...
}

Field labels — translated human identifier per field

The wire field and the audit field are technical identifiers — stable but not human-readable. Channels without a frontend (e-mail, SMS, push, audit read by compliance / ouvidoria / BI) consume the envelope directly and benefit from a translated label next to the technical identifier. "CEP é inválido" reads naturally; "addresses[0].zipCode é inválido" does not.

The mechanism reuses the existing Translator surface — no new translator, no boot phase, no schema endpoint. A labelKey:"<catalogKey>" struct tag on the field declares which catalog entry renders the human label. The framework reads the tag at notification emit time and at audit write time, then surfaces the rendered string (on the notification wire) and the raw key (on the audit row) so future audit readers can re-render in any locale.

Declaration on the domain struct

type User struct {
    domain.AggregateRoot
    Name  string  `labelKey:"UserNameField"`
    Email string  `labelKey:"UserEmailField"`
    Phone *string                            // no label tag — wire elides fieldLabel via omitempty
}

type Address struct {
    Street  string `labelKey:"AddressStreetField"`
    ZipCode string `labelKey:"AddressZipCodeField"`
}

→ 422 Unprocessable Entity

The same request under Accept-Language: en-US emits "fieldLabel": "ZIP Code". Fields without a label tag emit no fieldLabel at all — the omitempty elides the slot, so services without label declarations see byte-identical envelopes to the pre-feature behavior.

Audit row (update, root delta)

{
  "verb":   "update",
  "kind":   "delta",
  "changes": [{
    "field":          "Name",
    "fieldLabelKey": "UserNameField",
    "from":           "Jane Doe",
    "to":             "Jane Smith"
  }]
}

Audit stores the catalog key, not the rendered string — the row is immutable, but the catalog can evolve and the compliance team may read in any locale. Same shape on child cascade: children["Address"][0].changes[0].fieldLabelKey carries the key for the AVO field.

Reading audit rows — the audit.Reader port

See the consolidated Audit section for the full event shape, the two destinations, and the children cascade. Build a reader once over the relational engine with read.NewAuditReader(deps.DB) — it implements the application/audit Reader port (FindByID + FindByAggregate) and reads the audit_events table when the destinations list includes database: 

reader := read.NewAuditReader(deps.DB)   // backend-neutral; runs through the engine's Querier/Dialect

// Forensic single-row lookup — you saw an id in the slog echo and want the full row.
ev, err := reader.FindByID(ctx, eventID)   // eventID is a uuid.UUID
if errors.Is(err, audit.ErrAuditNotFound) {
    // no row with that id — pruned by a retention job? never audited?
}

// Timeline by aggregate — index-served (entity_type, aggregate_id, …), newest first.
events, err := reader.FindByAggregate(ctx, "User", userID.String())
for _, ev := range events {
    // walk the row's lifetime
}

The reader is backend-neutral: it issues its SELECT through the engine's Querier / Dialect, so the same code reads audit rows on every relational backend alike. The returned *AuditEvent mirrors what the persister wrote: top-level columns map directly; the payload JSON blob is unmarshaled back into Snapshot / Changes / Children.

Caveats: FindByID is a single primary-key lookup — audit_events is a plain table on every backend and the v7 id is time-ordered, so the common case (recent rows from a slog id) touches the hot pages. FindByAggregate returns every matching row; aggregates with very long timelines should slice the result downstream or call raw SQL with explicit LIMIT / OFFSET. JSON round-trip on the payload returns float64 / string / bool / map / slice — assert on stringified values, not on Go-typed scalars.

Reading the audit row — audit.RenderLabels and audit.RenderLabelsInJSON

The framework ships an in-place audit renderer that consumes fieldLabelKey and replaces it with fieldLabel rendered in any locale the catalog supports. The post-render shape matches the canonical notification wire (fieldLabel populated, fieldLabelKey elided via omitempty) so a UI / dashboard reads both surfaces uniformly. 

// Typed path — in-process Go reader holding *audit.AuditEvent.
audit.RenderLabels(ev, deps.Translator, configuration.LangPTBR)
//   ev.Changes[0].FieldLabelKey == ""
//   ev.Changes[0].FieldLabel    == "CEP"
//   ev.Children["Address"][0].Changes[0].FieldLabel == "CEP"

// JSON path — BI / SQL tools parsing the audit_events.jsonb payload as
// a generic map[string]any.
var doc map[string]any
_ = json.Unmarshal(jsonbBytes, &doc)
audit.RenderLabelsInJSON(doc, deps.Translator, configuration.LangPTBR)
//   doc["changes"][0]["fieldLabel"]    == "CEP"
//   doc["changes"][0]["fieldLabelKey"] is deleted

Both helpers mutate the input in place (one-shot read; no copy ceremony) and walk the same audit shape — top-level changes plus children.<typeName>[].changes. Catalog miss inherits the existing Translator.Render fallback: the raw key reaches fieldLabel and a slog.Warn("translation.key.missing", "lang", lang, "key", key) fires once per (lang, key) tuple. snapshot blocks (Insert / Delete events) are intentionally not touched — they carry map[goFieldName]value with no schema for labels.

Resolution rules

Tag formWhat happens
labelKey:"<catalogKey>" The field participates. MessageDTO.FieldLabel carries the rendered string in the actor's locale; FieldChange.FieldLabelKey carries the raw key on audit.
(no tag) Field is invisible to the label surface. Both wire fieldLabel and audit fieldLabelKey stay empty — omitempty elides them.
labelKey:"-" Explicit opt-out (mirror of json:"-"). Empty tag value behaves the same.
not declared in TableSchema (runtime-only) An undeclared exported field is runtime-only by construction — the persister and audit never see it, and label resolution skips it too. No tag is involved.
(catalog miss) Translator.Render falls back to the raw key as the rendered string and emits slog.Warn("translation.key.missing", "lang", lang, "key", key) once per (lang, key) tuple. Same posture Translator.Render already applies to MessageDTO.Message; no boot validator.

Catalog key naming (recommendation, not enforced)

<Entity><Field>Field mirrors the framework's existing <What>Notification convention. The framework does not validate the shape — service catalogs can use any string. The recommendation only matters for keeping the catalog navigable and avoiding collisions with notification keys (notification keys end in Notification; label keys end in Field).

Interaction with AddFieldNameAlias / ChangeFieldName

Label resolution operates on the Go field name the rule passed: r.AddNotification("Email", n) reads the label tag on the Email struct field. Wire renames affect only FieldName rendering — AddFieldNameAlias("Email", "primaryEmail") makes the wire say "field": "primaryEmail" while "fieldLabel" stays the translation of the tag on Email. The two surfaces are independent on purpose: alias renames the technical identifier; label translates the human identifier. Both reach the wire together but resolve through different paths.

Manual emission via AddNotificationMessage

Consumer code that builds a NotificationMessage directly (rare escape hatch for Err/FuncName/Override cases) carries LabelKey == "" by default and gets no fieldLabel on the wire. Setting msg.LabelKey = "<catalogKey>" explicitly on the manual message reaches the same render path the canonical r.AddNotification uses.

Why backend, not frontend

Frontends typically own the labels of their forms (offline-capable mobile apps ship with their own i18n bundle). Backend-side labels exist because notifications reach the user via channels other than the frontend — e-mail, SMS, push, audit logs — where there is no JS engine to interpolate. Frontend i18n bundles and backend label catalogs are independent surfaces with independent owners; they describe the same field from different sides. There is intentional, controlled duplication between them.
