Integration events

The cross-service async-messaging surface — the canonical write-side counterpart to the sync httpclient + the read-side UpstreamSubscription paths. Producers emit typed events into the local integration_events table (atomic with the data write when invoked from a BeforeCommit hook closure with WithTx(tx)); subscribers consume Kafka messages via the framework's Receiver registry, route each payload through the same pipeline.Handler[TCmd, TResult] HTTP routes consume, and dedup per consumer group via omnicore_integration_processed.

The package omnicore/infra/integration (imported as fwintegration) carries the full producer + subscriber surface. Vocabulary follows the canonical pub/sub literature: publishes (events this service emits) + subscribes (events this service consumes) layered on the same integration: YAML block.

Producer — fwintegration.Dispatch

fwintegration.Dispatch(ctx, "userActivated", UserActivatedPayload{Email: email},
    fwintegration.WithTx(tx),                  // atomic with data row + outbox + audit
    fwintegration.WithAggregateID(userID),     // required when YAML declares `aggregate:`
    fwintegration.WithCorrelation(corrID),     // optional — defaults to ctx.CorrelationID()
    fwintegration.WithCausation(causID),       // optional — defaults to ctx.CausationID()
)

YAML:

integration:
  publishes:
    events:
      userActivated:
        eventType: UserActivated   # wire header value
        aggregate: User            # optional — omit for standalone events
        version: 1                 # optional — defaults to 1

Lazy validation. An unknown eventKey at the first Dispatch call site surfaces as ErrIntegrationEventNotConfigured — same posture httpclient adopts for unknown service/endpoint references. The empty publishes block stays a valid steady state for services that only consume integration events; a typo on the producer side fails at the call site with a clear diagnostic rather than break the boot of an otherwise-functional service.

WithTx is the atomicity hook. Threaded from inside a BeforeCommit hook closure where the framework already opened the TX for the entity write. The integration_events row lands in the same Postgres TX as the data row + outbox + audit; any error from Dispatch aborts the entire TX (the persister's defer tx.Rollback(ctx) runs). Without WithTx, the row commits via single-statement autocommit on the package's PG pool — independent of any other write. Multiple Dispatch calls inside the same TX produce N rows in integration_events, all atomic with the data write; BIGSERIAL id reflects call order.

Framework auto-fills event_id (uuid.New() per row), thread_id (ctx.ID()), actor (ctx.ActorSubject() — non-empty by contract, falls back to "anonymous"), created_at (NOW()). correlation_id and causation_id default to ctx.CorrelationID() / ctx.CausationID() when the receiver pipeline populated them — events emitted inside a receiver handler automatically carry the inbound trace chain.

No domain coupling. Domain events (intra-context, observability) and integration events (cross-context, infra primitive) stay conceptually separate. The domain layer never imports fwintegration; the dev places the Dispatch call wherever in application/ or infra/ makes business sense — typically inside a Cmd's BeforeCommit closure for atomic emission, or at standalone call sites (system startup, background job completion) without WithTx.

Subscriber — Registry + Receiver + IntegrationFeature

A feature implements the opt-in bootstrap.IntegrationFeature interface (mirror of ReadableFeature). The framework calls MountReceivers(reg, deps) during Phase Receivers — runs AFTER Phase HTTP (Mount) so a single feature can register HTTP routes AND integration receivers from the same struct.

// bootstrap/users_feature.go
func (f *UsersFeature) MountReceivers(reg *fwintegration.Registry, d bootstrap.Deps) {
    appweb.MountUserReceivers(reg, f.repo, d)
}

// web/user_receivers.go — parallel to web/user_routes.go
func MountUserReceivers(reg *fwintegration.Registry, repo userRepo, d bootstrap.Deps) {
    insertHandler := &handlers.InsertCommandHandler[*appdomain.User, *appcommands.InsertUserCommand, appcommands.InsertUserResult]{
        Repo: repo,
    }
    reg.From("partners").
        On("partnerOnboarded", requests.PartnerOnboardedRequest{}, insertHandler)
}

YAML:

integration:
  defaults:
    consumerGroup: "${INTEGRATION_GROUP_ID:my-service-integration}"
    workers: 4
    startFrom: latest                          # latest | earliest
  subscribes:
    partners:                                  # source key (Go reference)
      topic: partners.integration.events       # Kafka topic name
      events:
        partnerOnboarded:                      # event key (Go reference)
          eventType: PartnerOnboarded          # wire header value

Eager validation (both directions). reg.From("X").On("Y", ...) during MountReceivers fails boot if integration.subscribes.X.events.Y does not exist in the loaded YAML — boot diagnostic names the missing key. The inverse is also enforced: a declared integration.subscribes.X.events.Y with no matching registered receiver aborts the boot (otherwise no goroutine would consume that topic and every message would be silently dropped). Mismatched sample / handler types panic at Mount time too (sample carries no ToCommand, ToCommand returns the wrong Cmd type for the handler, etc.). startFrom (per-source and defaults) is enum-validated at boot (earliest | latest) — a typo previously resolved silently to latest.

Handler invariance — HTTP and Kafka are interchangeable transports

The handler registered on the receiver is the same pipeline.Handler[TCmd, TResult] instance an HTTP route consumes. The sample DTO carries ToCommand() (same convention web Request.ToCommand follows). Migrate an endpoint from HTTP to async event-driven without rewriting the handler. Expose the same use case via both transports during a transition window. React to events with handlers proven via HTTP integration tests.

Per-message pipeline (no outer TX)

  1. Read event_id from header (or msg.Key).
  2. Pre-check omnicore_integration_processed — hit → ack Kafka, skip handler (already processed by this consumer group).
  3. Build a fresh *AppContext for the invocation: ID() = new UUID; ActorSubject() = inbound actor header (falls back to "anonymous"); CorrelationID() = inbound correlation_id header or event_id fallback; CausationID() = event_id.
  4. Unmarshal payload into a freshly-allocated sample DTO, call ToCommand(), dispatch the resulting Cmd via the registered handler.
  5. Handler success → INSERT INTO omnicore_integration_processed ... ON CONFLICT DO NOTHING → ack Kafka.
  6. Handler error → RecordIntegrationFailure(...) row written; Kafka offset still advances (failure isolation contract).

Each Repo.Method opens its own short TX as in the HTTP path — no framework-managed outer TX, no persister branch, no AppContext mutation for transaction injection. HTTP↔Receiver symmetry at the persistence layer.

Idempotency contract — at-least-once

Framework provides best-effort dedup via omnicore_integration_processed keyed by (event_id, consumer_group). The race window of milliseconds between handler COMMIT and the dedup INSERT may produce a double-invoke after a crash. Handlers consumed by a Receiver MUST be idempotent by design — recommended patterns:

  • UPSERT via INSERT ... ON CONFLICT DO UPDATE on PG writes (matches the framework's existing BaseRepository.ConstraintBindings posture).
  • Natural-key constraints on PG writes — the second invoke trips the unique violation and the framework translates it via the registered ConstraintBinding.
  • Idempotency keys at the external side for side effects to non-PG systems (email provider, payment provider, downstream HTTP API). Same pattern Stripe / Twilio / GitHub webhooks adopt — pass the event_id as the upstream idempotency key.

The architectural trade-off accepted: an outer TX wrapping handler execution + dedup INSERT would close the race window at the cost of long-lived TX, connection pool pressure, replication lag risk. Pinning idempotency to the handler design keeps the framework's per-Repo-Method short-TX discipline intact.

Failure registry — omnicore_integration_failures

Every handler failure is persisted to omnicore_integration_failures, mirroring omnicore_upstream_failures for parity in operator tooling. Schema:

CREATE TABLE omnicore_integration_failures (
    id              BIGSERIAL PRIMARY KEY,
    consumer_group  TEXT      NOT NULL,
    source_key      TEXT      NOT NULL,
    event_key       TEXT      NOT NULL,
    event_id        UUID      NOT NULL,
    payload         JSONB     NOT NULL,     -- preserved verbatim for replay
    error           TEXT      NOT NULL,
    attempt         INTEGER   NOT NULL DEFAULT 1,
    first_seen_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    last_attempt_at TIMESTAMP NOT NULL DEFAULT NOW(),
    resolved_at     TIMESTAMP,
    CONSTRAINT omnicore_integration_failures_natural_key
        UNIQUE (consumer_group, source_key, event_key, event_id)
);

Retry surface. Receiver.RetryPendingFailures(ctx, exec, pipe, logger) re-dispatches every pending row for the receiver's natural key — same posture upstream subscribers adopt. Idempotent: a successful re-dispatch calls ResolveIntegrationFailures so the row is marked resolved. The framework does NOT auto-retry; operators drive retry explicitly.

Canonical admin pattern in the consumer service: a mount-only AdminFeature registering two parallel routes behind RequirePermission("admin:retry"):

POST /admin/retries/upstream      → loops d.UpstreamSubscribers
POST /admin/retries/integration   → loops d.IntegrationRegistry.Receivers()

Both return {"retried": N}; both visible in the Swagger surface under tag Admin. The handlers read receivers / subscribers via closure at request time — registry is populated during Phase Receivers, before HTTP starts serving.

AppContext propagation

The receiver pipeline synthesizes a fresh *AppContext per invocation:

FieldSource
ctx.ID() (thread_id)new uuid.New()
ctx.Identity()synthetic Identity carrying Subject = event.actor; Issuer / Claims empty
ctx.ActorSubject()event.actor (guaranteed non-empty by producer-side contract)
ctx.Identity().HasPermission(...)always false (synthetic Identity has no permissions claim) — prevents accidental privilege escalation by handlers branching on permissions
ctx.CorrelationID()inbound correlation_id header if set, else event_id fallback
ctx.CausationID()inbound event_id
parent context.Contextreceiver loop context — cancellation propagates to in-flight handlers on shutdown

Outbound Dispatch calls emitted inside the receiver handler automatically carry the inbound trace chain — WithCorrelation / WithCausation options fall back to ctx.CorrelationID() / ctx.CausationID() when omitted.

Schema migration — sibling event keys

Breaking payload changes use sibling YAML entries (userActivated → userActivatedV2) with distinct eventType + version. Old and new coexist during the migration window; the receiver matches on the wire eventType via its eventKey, so two registered receivers can consume the old + new shapes in parallel during cutover.

Event DTO ownership — per-consumer copy

Each service owns its own Go types for integration event payloads. The wire format (JSON) is the contract between producer and consumer; the Go struct is implementation detail per side. JSON unmarshal silently ignores unmapped fields, so additive producer-side changes are non-breaking. Same posture industry APIs (Stripe, Twilio, GitHub webhooks) adopt — each consumer defines its own local client type.

Observability — slog lifecycle echoes

The framework emits structured slog lines at 5 lifecycle points. Operators tail logs with their existing tooling (Loki/promtail/Vector/ELK) and extract metric counters / histograms downstream — no separate Prometheus surface is introduced.

integration_events table IS the producer-side audit; audit_events is unchanged and never carries integration-event payload. Cross-reference between an audit row and a related integration event is via thread_id (carried by both tables).

Storage layout — three tables, separate from outbox

TableOwnerPurpose
integration_eventsproducerauthoritative store; written in-TX with the data row when WithTx supplied; forensic timeline indexed by (aggregate_type, aggregate_id, created_at)

All three tables ship via framework migration 0002_integration_events.{up,down}.sql. The outbox table stays UNTOUCHED — integration_events is a separate concept with its own retention semantics. Operator-driven pruning via DELETE WHERE created_at < NOW() - INTERVAL '30 days' on integration_events is recommended; framework does not auto-prune.

Professional shutdown

shutdown.drainTimeoutSeconds in YAML caps the parallel drain on SIGINT/SIGTERM (default 30s; aligns with kubernetes terminationGracePeriodSeconds). The framework drains HTTP server, integration consumer pool, upstream subscribers in parallel under the shared shutdownCtx. Per-stage drain timeouts surface as slog.Warn lines naming the stage so the operator knows what did not finish. Infra deps (Kafka, PG, Mongo) close after every drain finishes, in dependency order.
