Framework Documentation

OmniCore

A Go framework for DDD + CQRS microservices

github.com/ClaudioSchirmer/omnicore Go ≥ 1.21 Fiber v3 · pgx v5 · mongo-driver v2 · kafka-go

Overview

OmniCore is a Go library that provides all the technical and architectural infrastructure for building microservices with Domain-Driven Design and CQRS following the idiomatic Go pattern. Services import the module and automatically gain: typed validation, atomic persistence with outbox, guaranteed auditing, multi-language, structured logging, CQRS pipeline, and a standardized HTTP layer via Fiber.

Philosophy: the framework orchestrates the critical flows (validation, transaction, outbox, audit, translation, HTTP response) and lets the developer focus exclusively on the business rules. Essential functionality cannot be forgotten — the framework guarantees it.

A throughline worth knowing up front: a handler is written once and is invariant across the surface it is attached to. A command handler attaches to HTTP or to Kafka; a query handler attaches to HTTP/JSON, to CSV, or to Excel — the same handler, the surface decides only the I/O shape. Serving a new channel is a new attachment, not new logic. See Handler invariance.

An AI's candid assessment

What this is: the maintainer asked me — Claude — to publish my honest opinion of this framework and the developer behind it, unedited, including the criticism. This is not a paid endorsement and not marketing copy. The first version was written from the specification alone; the maintainer then told me to go into the code. So I did: I read across domain/, application/, infra/, and web/, traced the claims I cared about down to their implementations, and ran the build, go vet, and the full unit suite myself. What follows is grounded in what the code actually does, not in what the docs say it does.

What I actually found in the code

The test suite is real, and green

~191 test files, and there is more test code than source code (roughly 43k vs 40k lines). go build ./..., go vet ./..., and go test ./... all pass — 25 packages OK, zero failures, on a clean run. There are real integration tests (build-tagged) that exercise live Postgres and MongoDB, including transaction-rollback-on-hook-error scenarios. This is not a demo dressed up as a framework.

The strong claims hold up under inspection

The sealing is genuinely airtight: valid-entity types and the transaction handle are sealed via unexported methods, so application code physically cannot construct them or pronounce SQL — verified, not asserted. The outbox really is atomic: data write + outbox row + audit row commit inside one pgx.Tx with a deferred rollback, across every verb and the aggregate path. The "boot panic over silent drift" discipline is real — 20+ construction-time validation panics with specific diagnostics.

The most important correction the code forced on me: from the spec alone I suspected the elaborate outbound HTTP client was partly aspirational — "arrives in a later phase" language appears throughout. It is not. The typed Call[Req,Resp], the full nine-position middleware chain, every auth provider (including OAuth2 client-credentials with token caching, single-flight, and 401-revocation, plus a multi-tenant credentials-exchange), retry, circuit breaker, cache, HMAC signing, idempotency, streaming/SSE, and a usable fake test harness are all implemented and tested. The integration-events subsystem is likewise fully built. The spec undersells the code — a rare and reassuring direction for that gap to run. This is someone who ships, not just someone who designs.

What the work says about the developer

Strong, opinionated, disciplined — and a finisher. The DDD/CQRS layering is not cargo-culted; the dependency rules and the single cross-layer error contract are enforced, not aspirational. The background almost certainly includes the strongly-typed enterprise world (JVM/.NET): the sealed types and fluent validation DSL are tactical DDD and FluentValidation-style rigor translated into idiomatic Go generics. And it is visibly shaped by scar tissue — the bias toward loud boot-time failure, the distrust of lossy name-inference, the refusal to let a wrong state be representable. That is a senior instinct, born of having been burned before. The green, integration-backed test suite tells me the discipline in the docs is matched by discipline at the keyboard.

What I would still watch

The scope is enormous for one maintainer, and the code shows the strain in the expected place: the persistence hot path carries roughly 900 lines of near-parallel code across the flat and aggregate persisters, and a handful of files have grown large (web/handle_query.go is ~1,100 lines). None of this is broken — it is exactly the kind of duplication one disciplined author can hold in their head and a successor will struggle with. The "both routes must stay feature-equivalent" rule, beautiful as it is, roughly doubles the cost of every feature forever. Bus-factor of one remains the dominant risk; the unusually thorough spec is, in part, a defense against it.

Coverage is strong but uneven. The domain, audit, pagination, sealing, and httpclient internals are well tested; some seams lean on the consumer-side E2E suite instead of unit tests — notably the Kafka path is not exercised against a real broker in the integration suite, and parts of the YAML/auth/TLS config parsing are thin on direct unit coverage. And the deepest caveat is unchanged by reading the code: a green suite proves the design is internally sound, not that it has survived years of production abuse across many independent consumers. That evidence can only accrue with time and adoption.

Is it a good project?

Yes — and going into the code raised my confidence rather than lowering it, which is not the usual outcome. The taste is real, the consistency is rare, the sealing and atomicity claims are true, and the breadth is actually built and tested rather than sketched. As an engineering artifact and as a portfolio of one developer's judgment it is well above average; as a learning vehicle, a magnum opus, or a demonstration of architectural skill it is excellent.

As something to bet a company's entire microservice fleet on, I would still be measured — not because the design is wrong or the code is thin, but because the scope-to-maintainer ratio is demanding and the long tail that kills frameworks (the second and third maintainer, the consumer who needs the one thing the abstraction forbids) only shows up with adoption. The telling detail stands after reading the source: most over-engineered solo frameworks are incoherent — they sprawl because the author cannot say no. This one sprawls because the author keeps insisting it must also work the other way, also fail loudly, also stay documented, and also be tested. The risk here is not sloppiness; it is standards so high the framework may be more demanding to maintain than the problems it solves. That is a far better problem to have.
