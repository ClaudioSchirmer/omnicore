Read joins — reaching another aggregate from a query

A read join lets one aggregate's queries reach across a foreign key into another aggregate: filter by the customer's name while listing orders, sort by it, and bring a few of its columns back on the loaded entity. It is declared on the repository, applies to every read that repository's loader serves, and never touches the write side. 

func NewOrderRepository(eng core.RelationalEngine) *OrderRepository {
    r := &OrderRepository{}
    r.BaseAggregateRepository = *read.NewBaseAggregateRepository[*domain.Order](
        eng, func() *domain.Order { return &domain.Order{} },
    )
    r.WithSchema(schemas.OrderSchema())   // how THIS entity is read and written
    r.WithJoins(                          // what it may reach in a query
        read.InnerJoin(schemas.CustomerSchema()).On("customer_id").
            Field("CustomerName", "nome").
            Field("CustomerDoc", "documento"),

        read.LeftJoin(schemas.CarrierSchema()).On("carrier_id").
            Field("CarrierCode", "codigo"),
    )
    return r
}

The declared fields are ordinary Go fields of the entity, filled on read:

type Order struct {
    domain.AggregateRoot
    CustomerID domain.ID
    CarrierID  *domain.ID

    CustomerName string   // from the inner join — always matches
    CustomerDoc  string
    CarrierCode  *string  // from the left join — nil when there is no carrier
}

And they are addressable in a criteria under the Go name you chose:

orders, err := repo.Loader.FindAll(ctx, criteria.
    Where(criteria.Eq("CustomerName", "ana")).
    OrderBy("CustomerName").
    Limit(20))

Why the repository, and not the schema or the view

A TableSchema declares the form of one entity: its columns, its id, its managed slots and its own closure (children, siblings, shared base). A foreign key to another aggregate is already an ordinary column of that form — what a join adds is permission to traverse it. That is access, not storage, and the repository is where a developer would write the join by hand.

Declaring it on the repository also means the loader owns it, and the loader is what actually serves FindOne, FindAll, Exists and Aggregate. One declaration therefore reaches every consumer at once:

  • a service calling repo.Loader.FindAll(ctx, criteria) with no view in sight;
  • repo.FindByID(id) and the request-scoped repo.ScopedReader(ctx) the auto command handlers load through;
  • a relational view declared over that loader, which inherits the reach and declares nothing itself.

The two kinds

VerbA root with no counterpartWhen
read.LeftJoin(target) is still returned; the traversed fields read as NULL the relationship is optional — the foreign key is a *domain.ID
read.InnerJoin(target) is not returned the relationship is mandatory — the foreign key is a domain.ID
InnerJoin is legal only over a non-nullable foreign key. The declaration lives on the repository, so it applies to every read through that loader — FindByID included, which is what the write-side auto handlers load through. Over a nullable key an inner join would silently drop aggregates, turning a legitimate write into a 404. The framework refuses that combination at construction and names LeftJoin as the fix. Over a non-nullable key, referential integrity makes the two return the same roots, so the choice is one of intent and query plan.
A LeftJoin field must be able to hold NULL. With no counterpart the column comes back NULL; a non-pointer Go field would take its zero value and report a blank name where the truth is "there is no counterpart". Declare those fields as pointers — the framework refuses the combination at construction otherwise.

Mapping columns onto your own names

.Field(goField, column) takes the same two arguments, in the same order, as TableSchema.Field: the Go field on your entity, then the column on the joined table. The joined side's spelling never surfaces above infrastructure, so renaming is free: 

read.LeftJoin(schemas.ProfessorSchema()).On("professor_id").
    Field("Pessoa", "professor")     // criteria and DTOs speak "Pessoa"

Call it once per column. A join that maps no field reaches nothing and is refused at construction.

The predicate is always fk = target.id. .On(...) names the foreign key; the other side of the comparison is the target schema's declared id column, which the TableSchema already knows — so there is nothing else to declare, and no way to get the two halves out of step. The corollary is a deliberate limit: a traversal onto a non-id column of the target (matching a code against a natural key, say) is not expressible. Model that as a real foreign key, or read it with deps.DB.Querier().

Joining from an aggregate child

A join may also hang off one of the root's own aggregate children, declared with root.Child(...). The verb names the child; .To(...) names the target: 

r.WithJoins(
    read.LeftJoinInChild(schemas.EnderecoSchema()).To(schemas.CidadeSchema()).
        On("cidade_id").Field("NomeCidade", "nome"),
)

.On(...) names the foreign key on the joining table — the root's for a root join, the child's for a child join — and the mapped Go field lives on the child's struct.

A child join is load-only: its fields are filled on every loaded child, but they are not addressable in a criteria. Filtering the root by a field of a 1:N child is a pushdown a single root SELECT cannot express — the same boundary every child field has.

Inside a child, InnerJoin drops the CHILD element, not the root. The join rides the child's own batched SELECT, so the row it can eliminate is the child's: the aggregate still comes back, with that element missing from its collection — a silent hole in the child array rather than a missing aggregate. Over the non-nullable foreign key the framework already requires there is no such row, which is exactly why the requirement is enforced; prefer LeftJoinInChild whenever the relationship is genuinely optional.

Own children only. The child must be one the root's schema declares. A child of a shared base belongs to the base: declare the join on the base's own repository.

What a read join is not

  • Not a write path. A join field is not part of the TableSchema, so it never enters an INSERT or UPDATE, and the write repository holds a schema with no loader in sight. The write model remains exactly what the TableSchema says it is.
  • Not a collection. Joins are 1:1 and horizontal — one column mapped to one field at a time. There is no many-valued form: a 1:N join would multiply the root's rows and break the paged read.
  • Not a Mongo concept. The TableSchema is untouched by a join declaration, so a projected view over the same entity is unaffected. Where a Mongo view wants another aggregate's data it materializes it with Embed, or composes it at read time with ComposedView.

What it costs

A declared root join is always in the FROM, and its columns ride the root SELECT — so the values cost no extra round trip. Being always present is what makes the field trustworthy: a field that appeared only when some filter happened to mention it would leave the same entity populated on one call and blank on the next.

Each traversal is rendered under its own alias derived from the foreign key, so two joins may reach the same table — a billing and a shipping address both to customers — without colliding. That is also why one foreign key reaches one table: two joins sharing a key are refused at construction. The alias follows the table name bare, with no AS: the keyword is optional before a table alias in standard SQL and Oracle rejects it outright, so the bare form is the one all four backends accept. Everything resolved through a join reaches the statement under that alias — the WHERE, the ORDER BY, and the aggregate DSL's expressions and grouping keys alike — because two aggregates may perfectly well both have a name, and the joined side has no uniqueness guarantee against the anchor's columns the way a sibling or a shared base does.

What a NULL means, and what archived means

A LeftJoin with no counterpart is an absence, and it stays one all the way out: the column reads as NULL, the Go field stays nil, the served document carries nil under that name, and a Response DTO's pointer field stays nil so the wire omits it. That is the whole reason the framework insists on a pointer for a left join — a non-nullable field would report a blank name where the truth is "there is no counterpart", and the two are not the same answer.

A join is not gated on the archived state of the target. It answers "what is on the other side of this foreign key", and a soft-deleted counterpart is still what the key points at: an archived Customer keeps supplying CustomerName, and an InnerJoin keeps matching it. The read scope (?includeArchived, the criteria's Scope) governs which roots a read returns; it never governs the rows a declared traversal reaches across into. Where an archived counterpart must disappear from the answer, the honest expression is a filter the criteria states, not a join that silently drops rows.

Boot validation

Every declaration is checked against the schema at construction — a violation panics there, never on the first request:

  • WithSchema was called first;
  • the foreign key named by .On(...) is a column of the joining table, and no other join on that table already uses it;
  • the column named by .Field(...) is a column of the target;
  • the Go field exists on the owning struct and is exported;
  • the Go field does not shadow a name the schema already answers — its own, a sibling's or the shared base's;
  • InnerJoin is over a non-nullable foreign key, and a LeftJoin field is nullable;
  • at least one .Field(...) is declared;
  • a ...InChild child is one the root's schema declares.
