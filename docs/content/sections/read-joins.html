Read joins — reaching another aggregate from a query

A read join lets one aggregate's queries reach across a foreign key into another aggregate: filter by the customer's name while listing orders, sort by it, and bring a few of its columns back on the loaded entity. It is declared on the repository, applies to every read that repository's loader serves, and never touches the write side. 

func NewOrderRepository(eng core.RelationalEngine) *OrderRepository {
    r := &OrderRepository{}
    r.BaseAggregateRepository = *read.NewBaseAggregateRepository[*domain.Order](
        eng, func() *domain.Order { return &domain.Order{} },
    )
    r.WithSchema(schemas.OrderSchema())   // how THIS entity is read and written
    r.WithJoins(                          // what it may reach in a query
        read.InnerJoin(schemas.CustomerSchema().AsDirectSchema()).On("customer_id").
            Field("CustomerName", "nome").
            Field("CustomerDoc", "documento"),

        read.LeftJoin(schemas.CarrierSchema().AsDirectSchema()).On("carrier_id").
            Field("CarrierCode", "codigo"),
    )
    return r
}

The declared fields are ordinary Go fields of the entity, filled on read:

type Order struct {
    domain.AggregateRoot
    CustomerID domain.ID
    CarrierID  *domain.ID

    CustomerName string   // from the inner join — always matches
    CustomerDoc  string
    CarrierCode  *string  // from the left join — nil when there is no carrier
}

And they are addressable in a criteria under the Go name you chose:

orders, err := repo.Loader.FindAll(ctx, criteria.
    Where(criteria.Eq("CustomerName", "ana")).
    OrderBy("CustomerName").
    Limit(20))

The target is one table — a Direct schema

A traversal puts the target in the FROM as one table under one alias. So it takes a schema that is one table: a Direct schema. A schema carrying children, siblings or a shared base is refused at the declaration, because it could only be traversed in part — and that part used to be taken in silence, with a column of the target's own sibling accepted here and then qualified by the target's alias, where it does not exist.

Any schema becomes a target, at the call site, where the reduction is visible:

read.InnerJoin(schemas.CustomerSchema().AsDirectSchema()).On("customer_id").
    Field("CustomerName", "nome")

AsDirectSchema() returns a copy reduced to the schema's own table — the original is untouched, and an aggregate root, a child, a role, a shared base and a Direct schema all convert, so nothing you could join to before is out of reach. A sibling and an external schema do not convert, and say why (see Criteria). What the target declares about its own children or satellites simply is not part of what a join reads.

Why the repository, and not the schema or the view

A TableSchema declares the form of one entity: its columns, its id, its managed slots and its own closure (children, siblings, shared base). A foreign key to another aggregate is already an ordinary column of that form — what a join adds is permission to traverse it. That is access, not storage, and the repository is where a developer would write the join by hand.

Declaring it on the repository also means the loader owns it, and the loader is what actually serves FindOne, FindAll, Exists and Aggregate. One declaration therefore reaches every consumer at once:

  • a service calling repo.Loader.FindAll(ctx, criteria) with no view in sight;
  • repo.FindByID(id) and the request-scoped repo.ScopedReader(ctx) the auto command handlers load through;
  • a relational view declared over that loader, which inherits the reach and declares nothing itself.

The two kinds

read.LeftJoin(target) is still returned; the traversed fields read as NULL the relationship is optional — the foreign key is a *domain.ID

InnerJoin is legal only over a non-nullable foreign key. The declaration lives on the repository, so it applies to every read through that loader — FindByID included, which is what the write-side auto handlers load through. Over a nullable key an inner join would silently drop aggregates, turning a legitimate write into a 404. The framework refuses that combination at construction and names LeftJoin as the fix. Over a non-nullable key, referential integrity makes the two return the same roots, so the choice is one of intent and query plan.
A LeftJoin field must be able to hold NULL. With no counterpart the column comes back NULL; a non-pointer Go field would take its zero value and report a blank name where the truth is "there is no counterpart". Declare those fields as pointers — the framework refuses the combination at construction otherwise.

Mapping columns onto your own names

.Field(goField, column) takes the same two arguments, in the same order, as TableSchema.Field: the Go field on your entity, then the column on the joined table. The joined side's spelling never surfaces above infrastructure, so renaming is free: 

read.LeftJoin(schemas.ProfessorSchema().AsDirectSchema()).On("professor_id").
    Field("Pessoa", "professor")     // criteria and DTOs speak "Pessoa"

Call it once per column. A join that maps no field reaches nothing and is refused at construction — and so is a Go field two mappings claim, whether inside one declaration or across two traversals of the same owner: both columns would ride the SELECT and both would scan into the one field, so the second would overwrite the first on every row while a criteria naming it bound to the first. Give the second traversal its own field.

A nullable column needs a nullable field — whatever the join kind. An InnerJoin proves the joined row exists; it says nothing about whether every column of it is filled. If the target declares that column nullable, the field receiving it must be a pointer, or the first row carrying a NULL fails the read. The framework checks it at construction and names both halves — the field that cannot hold it, and the table and column that produce it. What it reads is the target's own Go declaration (a pointer field is the nullable one), off the schema the join already holds; a column the target's struct does not expose is left unenforced rather than guessed, and the database catalog is never consulted.

What a join field may be

A scalar, and only a scalar. A join field carries no domain type — no value object of any kind (scalar-backed, enum, composite) and no domain.ID. The framework refuses the declaration at construction, naming which kind it found.

The reason is not mechanical. The value belongs to another aggregate and arrives read-only: it is never written through this entity, so this domain never validates it. Reconstructing a domain type here would hand you an instance no rule ever approved — an enum converges an unknown value to Unknown without a word, and a composite spans several columns while a join field maps exactly one. Declare the scalar the column is stored as, and let the owning aggregate be the one that reconstructs its own types. 

type Order struct {
    domain.AggregateRoot
    CustomerID domain.ID    // a foreign key of THIS entity — a schema field, a domain type, fine

    CustomerName  string    // a join field — the scalar the column is stored as
    CustomerEmail string    // NOT vos.Email: the join brings the COLUMN, not the value object
}
An identity column is the exception the framework handles for you. A traversal often wants a foreign key of the target — the aggregate one hop further out. Declare that field string (*string when the target's column is nullable, or when the join is a LeftJoin) and the framework decodes the stored id form into the canonical text. This is not a convenience: mysql and sqlserver store an identity as BINARY(16) and oracle as RAW(16), which a bare string field would receive as 16 raw bytes without an error. The same typing governs the predicate, so a filter on that field binds in the form the target stores and actually matches. 
read.InnerJoin(schemas.CampusSchema().AsDirectSchema()).On("campus_id").
    Field("CampusOwnerID", "owner_id")   // owner_id is a domain.ID on the Campus schema

// on the entity — arrives as "0e5a1f6c-…", on all four engines:
CampusOwnerID string
The predicate is always fk = target.id. .On(...) names the foreign key; the other side of the comparison is the target schema's declared id column, which the TableSchema already knows — so there is nothing else to declare, and no way to get the two halves out of step. The corollary is a deliberate limit: a traversal onto a non-id column of the target (matching a code against a natural key, say) is not expressible. Model that as a real foreign key, or read it with deps.DB.Querier().

Reaching further: a chain of hops

A traversal is not limited to one aggregate. .Then(...) continues it from the one it just reached, and from there onward — there is no depth limit, because how far a read reaches is the caller's decision, not the framework's. 

read.LeftJoin(schemas.VendorSchema().AsDirectSchema()).On("vendor_id").
    Field("VendorName", "name").
    Then(read.InnerJoin(schemas.OwnerSchema().AsDirectSchema()).On("owner_id").
        Field("OwnerName", "name").
        Then(read.LeftJoin(schemas.TerritorySchema().AsDirectSchema()).On("territory_id").
            Field("TerritoryCode", "code")))

Two rules make the rest follow. A hop's .On(...) names a foreign key of the previous target — owner_id is a column of the vendor's table, not of the entity declaring the chain. And every hop's .Field(...), at every depth, lands on the same struct the head lands on: a join field carries no domain type, so a hop three tables out has no struct of its own. That is also why nothing above infrastructure has to learn about depth — a chain field is an ordinary field of the loaded entity, filterable, sortable, projectable and exportable exactly like a one-hop one.

A chain is emitted as a NESTED join, and that is what makes a mixed one mean what it reads as. LeftJoin(vendor).Then(InnerJoin(owner)) says: the vendor is optional; a vendor has an owner. Rendered as a flat join list — FROM orders LEFT JOIN vendors … INNER JOIN owners … — the trailing INNER would filter the whole result set and drop every order with no vendor at all, which the LeftJoin above it just promised to keep. Nested, the INNER binds its own block: 
FROM orders
LEFT JOIN (vendors j_vendor_id
           INNER JOIN owners j_vendor_id__owner_id
                   ON j_vendor_id__owner_id.id = j_vendor_id.owner_id)
       ON j_vendor_id.id = orders.vendor_id
A join of ONE hop has no block and is emitted exactly as it always was.
The block is atomic. A miss at any hop reports the whole chain absent — hop 1 included, even when hop 1 matched. That is the declaration honored rather than softened: the chain asked for a vendor with an owner, and a vendor without one is not that. What survives is the ROOT, which is what the LeftJoin at the head is for. Declare a second traversal over its own foreign key when you want the near hop reported independently of the far one.

What changes at depth, and what does not

  • Nullability follows the PATH. One LeftJoin anywhere above makes every field below it a pointer, whatever the deeper hops declare — the block that produces the NULL is the whole chain, not the last hop. A chain that is InnerJoin all the way through needs no pointer.
  • The nullable-foreign-key refusal narrows. An InnerJoin over a nullable key is refused when the path is inner all the way — there it silently drops roots, from FindByID included. Under a LeftJoin it drops nothing (the block simply does not match), so it is allowed, and it is precisely how you say "only when the counterpart has one".
  • Aliases come from the PATH of foreign keys reaching each hop — j_vendor_id__owner_id — so two chains may traverse a column of the same name in different branches without colliding. Past 48 characters the path is replaced by its hash, which keeps every engine's identifier limit satisfied.
  • Everything else is unchanged. A chain hangs off a root join or a ...InChild one on identical terms; a child chain stays load-only at every depth, for the same 1:N reason depth 1 was; and the whole set still goes in ONE WithJoins call.
A chain on an AGGREGATE repository logs one advisory at boot. Not a limit and not a deprecation — a reminder of where the cost lands: these joins ride every read the loader serves, FindByID included, which is the load the write-side Auto handlers go through. A chain declared for one screen is charged to every command the service serves. The line names the chain and suggests a read.DirectRepository when the reach is only ever read. That repository never logs one, at any depth: it carries no write path to charge.

Which columns of the target a join may name

Whatever the target's TableSchema answers on the read side, which is more than the columns it declares by hand. The framework's own managed slots resolve there too, under their fixed logical names — so a traversal may bring back when the counterpart was created, last touched or archived, without the target having to expose any of that as a domain field.

Never under the carrier's own spelling. A join field called CreatedAt, UpdatedAt or DeletedAt is refused — by the shadow rule where your own schema declares that slot, and for want of a field to write to where it does not: your managed slots live unexported inside domain.Managed and are read through GetCreatedAt() and its siblings, never as struct fields. Name the traversal's copy after what it is — CustomerArchivedAt — which is also the rule the rest of this section already follows.

A managed slot is nullable and the framework cannot see that — declare the pointer yourself. The nullability check reads the target's own Go declaration, and a managed slot is not a struct field there: domain.Managed keeps createdAt, updatedAt and deletedAt unexported. So the check finds nothing to read a pointer off and stays silent rather than guessing from the column's meaning — the same restraint it shows a type-less external schema. A LeftJoin still stops you, because a left-join field must be nullable whatever it maps; an InnerJoin does not. CustomerArchivedAt time.Time under an InnerJoin therefore compiles, boots, and fails on the first row whose counterpart is not archived — deleted_at is NULL on every live row, which is precisely the row you meant to read. Declare *time.Time and the case does not arise.

A managed column reached this way is a field like any other: it loads on every read, and on a root join it filters and orders under the name you gave it. That is also the honest way to write the thing the join deliberately will not do behind your back. A traversal never hides an archived counterpart (see What a NULL means, and what archived means, below), so where one must disappear from the answer, say so in the criteria: 

criteria.IsNull("CustomerArchivedAt")    // live counterparts only
criteria.NotNull("CustomerArchivedAt")   // archived ones only

Joining from an aggregate child

A join may also hang off one of the root's own aggregate children, declared with root.Child(...). The verb names the child; .To(...) names the target: 

r.WithJoins(
    read.LeftJoinInChild(schemas.EnderecoSchema()).To(schemas.CidadeSchema()).
        On("cidade_id").Field("NomeCidade", "nome"),
)

.On(...) names the foreign key on the joining table — the root's for a root join, the child's for a child join — and the mapped Go field lives on the child's struct.

A child join is load-only: its fields are filled on every loaded child, but they are not addressable in a criteria. Filtering the root by a field of a 1:N child is a pushdown a single root SELECT cannot express — the same boundary every child field has.

Inside a child, InnerJoin drops the CHILD element, not the root. The join rides the child's own batched SELECT, so the row it can eliminate is the child's: the aggregate still comes back, with that element missing from its collection — a silent hole in the child array rather than a missing aggregate. Over the non-nullable foreign key the framework already requires there is no such row, which is exactly why the requirement is enforced; prefer LeftJoinInChild whenever the relationship is genuinely optional.

Own children only. The child must be one the root's schema declares. A child of a shared base belongs to the base: declare the join on the base's own repository.

What a read join is not

  • Not a write path. A join field is not part of the TableSchema, so it never enters an INSERT or UPDATE, and the write repository holds a schema with no loader in sight. The write model remains exactly what the TableSchema says it is.
  • Not a collection. Joins are 1:1 and horizontal — one column mapped to one field at a time. There is no many-valued form: a 1:N join would multiply the root's rows and break the paged read.
  • Not a Mongo concept. The TableSchema is untouched by a join declaration, so a projected view over the same entity is unaffected. Where a Mongo view wants another aggregate's data it materializes it with Embed, or composes it at read time with ComposedView.

What it costs

A declared root join is always in the FROM, and its columns ride the root SELECT — so the values cost no extra round trip. Being always present is what makes the field trustworthy: a field that appeared only when some filter happened to mention it would leave the same entity populated on one call and blank on the next.

Each traversal is rendered under its own alias derived from the foreign key, so two joins may reach the same table — a billing and a shipping address both to customers — without colliding. That is also why one foreign key reaches one table: two joins sharing a key are refused at construction. The alias follows the table name bare, with no AS: the keyword is optional before a table alias in standard SQL and Oracle rejects it outright, so the bare form is the one all four backends accept. Everything resolved through a join reaches the statement under that alias — the WHERE, the ORDER BY, and the aggregate DSL's expressions and grouping keys alike — because two aggregates may perfectly well both have a name.

The anchor side is qualified too, and for the same reason read backwards. A sibling and a shared base share the entity's own namespace, where column names are unique by construction, so they need no prefix on their own; a joined aggregate is a foreign namespace, free to carry a name, a code, or the framework's own deleted_at. So the moment a declared join is in the FROM, every column the statement emits on the anchor side — the SELECT list, the predicate, the ordering, the aggregate expressions and grouping keys, and the archive gate on the root and on each child — carries the table it physically lives on. Without a declared join nothing changes: the statement is rendered exactly as it always was.

What a NULL means, and what archived means

A LeftJoin with no counterpart is an absence, and it stays one all the way out: the column reads as NULL, the Go field stays nil, the served document carries nil under that name, and a Response DTO's pointer field stays nil — so the wire carries null, or nothing at all where the Response declares ,omitempty (which the ?fields= contract boot-enforces on every field). Either way it is not the zero value, which is the distinction that matters. That is the whole reason the framework insists on a pointer for a left join — a non-nullable field would report a blank name where the truth is "there is no counterpart", and the two are not the same answer.

A join is not gated on the archived state of the target. It answers "what is on the other side of this foreign key", and a soft-deleted counterpart is still what the key points at: an archived Customer keeps supplying CustomerName, and an InnerJoin keeps matching it. The read scope (?includeArchived, the criteria's Scope) governs which roots a read returns; it never governs the rows a declared traversal reaches across into. Where an archived counterpart must disappear from the answer, the honest expression is a filter the criteria states, not a join that silently drops rows.

Boot validation

WithJoins takes the whole set, and is called once. A second call panics. Two of the rules below are about a collision between traversals — one foreign key reaches one table, one Go field receives one column — so neither can be answered from a declaration in isolation. A second call would validate its own argument against a schema that says nothing about what the first already claimed, and the collision would surface as a duplicate SQL alias on the first read, or as a field silently overwritten on every row. Declaring all of them in one call is what makes “validated at construction” true.

Every declaration is checked against the schema, and against the other declarations, at construction — a violation panics there, never on the first request:

  • WithSchema was called first;
  • the foreign key named by .On(...) is a column of the joining table, and no other join on that table already uses it;
  • the column named by .Field(...) is a column of the target — one it declares, its id, or one of its managed timestamp slots, but never revision;
  • the Go field exists on the owning struct and is exported;
  • the Go field does not shadow a name the schema already answers — its own, a sibling's or the shared base's;
  • the Go field is not already mapped by another traversal of the same owner (a root join and a child join land on different structs, so the same spelling there is two different fields and both are legal);
  • InnerJoin is over a non-nullable foreign key, and a LeftJoin field is nullable;
  • the Go field carries no domain type — no value object of any kind, and no domain.ID;
  • a field mapping an identity column of the target is string, or *string when that column is nullable or the join is a LeftJoin;
  • a field receiving a column the target declares nullable is a pointer, on any join kind — with the one gap this list will admit to: a managed slot of the target declares nothing here (the carrier's slots are unexported), so nullability goes unchecked for it and the pointer is yours to get right;
  • at least one .Field(...) is declared;
  • a ...InChild child is one the root's schema declares.
