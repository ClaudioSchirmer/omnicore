GraphQL

The framework exposes the same application handlers REST consumes through a single POST /graphql endpoint whose schema is reflected from the same Go types — Request DTOs (query:/filter: on the read side, json: on the write side) and Response/Result DTOs. A consumer attaches handlers to a registry; the SDL, the argument set (where / pagination / orderBy), the Relay connection envelope, the input objects, and the criteria translation are all derived automatically. There is no schema-first SDL to hand-write and no codegen step.

GraphQL is its own web surface. It does not go through the REST openapi.Mount/MountRaw machinery, it is never part of the Swagger/OpenAPI document, and it is not policed by the REST route scans. The only thing shared with REST is the application-layer handlers the resolvers dispatch to (pipeline.Handler[TQ, queries.Page] for reads, pipeline.Handler[*Cmd, TResult] for writes). The web layer is deliberately a different registry so each transport keeps its native shape — Relay connections + selection sets here, the JSON envelope + pagination block there. See Handler invariance.

Why the GraphQL surface looks different from REST

The two surfaces expose exactly the same capabilities — same filters, same sorting, same keyset pagination, same notifications, same authorization. What differs is only the shape of the request, and that difference is deliberate: REST and GraphQL come from two different schools of API design, and OmniCore follows each one's native conventions instead of bending one to look like the other.

REST is the open, URL-driven style. Everything is a query-string parameter: ?name.startswith=Bo, ?orderBy=-name, ?first=20&after=…. It is flexible and discoverable from a browser address bar — and intentionally loose: the server validates, but the wire has no schema of its own.

GraphQL follows the industry standard for graph APIs — the Relay Connection Specification, the convention popularized by Meta and adopted at scale by GitHub, Shopify, Atlassian, Stripe and most large public GraphQL APIs. A consumer who already speaks one big-company GraphQL API will recognize OmniCore's surface immediately: a typed where input, first/after connection arguments, an edges { node, cursor } / pageInfo envelope, and structured errors[]. Aligning to that convention is what makes the endpoint compatible with off-the-shelf GraphQL clients (Apollo, Relay, urql), code generators, and tooling — the payoff for the divergence.

Full parity, different syntax. Anything you can do on the REST read side you can do on GraphQL and vice-versa — the same filter: operator allowlist, the same ?orderBy= fields, the same keyset cursors, the same per-field authorization, the same typed notifications. The two surfaces share the same application handlers and the same ReadCriteria; only the wire dialect changes. A capability never lives on one surface alone — if it exists in REST it exists in GraphQL, expressed the way each ecosystem expects. The sections below describe each axis in detail.

Engine — gqlparser + a framework executor

Parsing and validation ride vektah/gqlparser/v2 (the parser gqlgen itself uses): the framework reflects the registry into an SDL document, loads it into a validated *ast.Schema, and per request gqlparser parses + validates the query against that schema. The framework owns only the executor — walking the selection set, dispatching through the registered handlers, mapping queries.Page / pipeline.Result to the wire, and answering introspection. A schema-first/codegen engine was rejected because it inverts the runtime "just attach" model; a frozen runtime-schema library was rejected as an unmaintained framework-core dependency.

Enable the endpoint

A feature opts into GraphQL by implementing bootstrap.GraphQLFeature — MountGraphQL(reg *graphql.Registry, deps Deps), the query/mutation twin of Mount. The framework discovers it (type assertion, like ReadableFeature), builds the single shared registry on the dispatch pipeline, and hands it to every opted-in feature so each registers its fields cumulatively into the same graph: 

// on the same feature struct that carries Mount / Views — reusing its repo + view
func (f *UsersFeature) MountGraphQL(reg *fwgraphql.Registry, d bootstrap.Deps) {
    reg.
        // read: one Query field per query handler → a Relay connection
        Register(fwgraphql.QueryWithParams[requests.FindUsersByParamsRequest,
                                 requests.FindUsersByParamsResponse](
            "users", "User",
            &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery]{
                Reader: d.ViewReader, View: f.view.Name()},
            fwgraphql.RequirePermission("users:read"))).
        // read: the singular by-id twin — same entity name, same node type
        Register(fwgraphql.QueryByID[requests.FindUserByIDRequest,
                                 requests.FindUserByIDResponse](
            "user", "User",
            &handlers.FindByIDQueryHandler[*queries.FindUserByIDQuery]{
                Reader: d.ViewReader, View: f.view.Name()},
            fwgraphql.RequirePermission("users:read"))).
        // write: one Mutation field per command handler
        Register(fwgraphql.MutationWithBody[requests.InsertUserRequest](
            "createUser", requests.InsertUserResponse{}.FromResult,
            &handlers.InsertCommandHandler[*User, *commands.InsertUserCommand, commands.InsertUserResult]{Repo: f.repo},
            fwgraphql.RequirePermission("users:write")))
}

// Wire declares only the feature — no registry construction, no GraphQL field on Wiring:
func Wire(d bootstrap.Deps) bootstrap.Wiring {
    return bootstrap.Wiring{
        Translations: []translation.Module{...},
        Features:     []bootstrap.Feature{NewUsersFeature(d)},
    }
}

With at least one GraphQLFeature present, bootstrap.Run builds the graph (surfaced on Deps.GraphQLRegistry) and mounts a single POST <path> (default /graphql) as its own surface, after the REST boot scans. The AuthMiddleware (matched by path at request time) still authenticates it when auth.mode: jwt; authorization is per-field in the resolver (see "Authorization" below). No feature implementing GraphQLFeature keeps everything off — no endpoint, zero cost. The interface declaration is the on/off switch; there is no Wiring/yaml enable-flag.

Operator-tunable serving

The serving knobs live in microservice.<profile>.yaml under graphql:, mirroring the OpenAPI posture — WHAT the schema exposes (the attached handlers) is code in each feature's MountGraphQL; HOW it is served is environment config: 

graphql:
  path: /graphql          # default. POST endpoint route.
  uiPath: /graphql/ui     # default. GET route for the GraphiQL playground (when playground: true).
  playground: false       # default off. Serve a GraphiQL page at uiPath.
  introspection: false    # default off. Answer __schema / __type queries.
  rootRedirect: false     # default off. GET / → 302 path. Both this and openapi.rootRedirect → boot panic.
  • Block optional. Absent → defaults. Present but no feature implements GraphQLFeature → ignored.
  • path validated at boot: must start with /, must not collide with /openapi.json, /livez, /readyz, or /docs.
  • playground serves GraphiQL at uiPath (loaded from a CDN, like the Swagger UI). Pair it with introspection: true so the playground can populate its schema docs / autocomplete. uiPath is validated (leading slash, no framework-route collision, must differ from path) only when playground is on.
  • introspection gates __schema / __type. Independent of the playground; off by default so a closed endpoint does not advertise its shape. Typically on in dev.
  • rootRedirect registers GET / → 302 path. The boot panics when both openapi.rootRedirect and graphql.rootRedirect are enabled (and both surfaces present) — only one surface can own /.

The registry — attach queries and mutations

The framework builds the registry (fwgraphql.New(pipe), surfaced on Deps.GraphQLRegistry) and passes it to each MountGraphQL; each reg.Register(...) adds one root field. The generic constructors capture the typed handler into the SDL emitter and the resolver; the only surface shared with REST is the pipeline.Handler instance.

ConstructorMapsGraphQL field
QueryWithParams[TReq, R]read handler pipeline.Handler[TQ, queries.Page]users(where, first, after, last, before, orderBy, search, includeArchived): UserConnection! — each argument present ONLY when the Request DTO declares its query:"…" key (see "The DTO cuts the schema")
QueryByID[TReq, R]by-id read handler pipeline.Handler[TQ, map[string]any]user(id: ID!, includeArchived: Boolean): User — the singular twin of the connection field (see "The singular by-id field"); includeArchived present only when the DTO declares it
MutationWithBody[TReq]insert-style command (body, no id)createUser(input: CreateUserInput!): CreateUserPayload!
MutationWithBodyID[TReq]update/patch (body + id)updateUser(id: ID!, input: UpdateUserInput!): UpdateUserPayload!
MutationByIDarchive/unarchive/delete (id, no body)archiveUser(id: ID!): ArchiveUserPayload! — the payload name derives from the field like every mutation; the body is the fixed bodyless shape { success: Boolean!, id: ID }

You name only the type params Go cannot infer. Those are the reflection-only ones — used inside the constructor via reflection but absent from every parameter: TReq (the Request DTO) on the body forms, plus R (the Response DTO / connection node) on QueryWithParams and QueryByID. Everything else — the command type, its pointer, the result, the response, the query type — is inferred from the handler argument and the DTO's ToCommand/ToQuery constraint, so MutationByID needs no type args at all. (QueryWithParams's and QueryByID's lists are ordered [TReq, R, TQ] precisely so the inferable TQ trails and is elided.) These are the same DTOs the REST wrappers anchor; canonical (Auto) and hand-rolled handlers attach identically because both implement the same pipeline.Handler interface — the registry cannot tell them apart, exactly as the REST wrappers cannot.

Why the read constructors take TWO names. "users" is the FIELD's identity; "User" is the identity of the SHARED node type the field returns — the coordination key that lets users, user and any further read field over the same entity converge on ONE object type (so client fragments work across all of them). A mutation derives its types from its single name because its input/payload are private to that field; a query's entity name is not derivable from the field name (plural↔singular, sibling fields sharing a type) — exactly as a hand-written SDL line spells both: users(...): UserConnection!.

A bad name cannot reach production. Field and entity names are validated against the GraphQL Name grammar at the constructor (panic at the exact Register line); the schema is built eagerly AT BOOT (a cross-feature duplicate field aborts the boot with an actionable error, never a lazy per-request failure); and an entity name colliding with a derived/infrastructure type (PageInfo, a sibling's Connection/Edge, an input or enum) — which would otherwise silently point the node at the wrong type — panics at build with the offending name. Sharing an entity name across read fields remains the supported contract.

Reflected schema

The SDL is generated once at boot from the registered DTOs and loaded into a validated schema:

  • Node object — the Response DTO becomes an object type named after the entity (User, not FindUsersByParamsResponse); fields are named by their json: wire name and resolved from the Go-field-keyed view document. Nested structs and slices recurse into nested object types. One entity name, one node type: when the plural (QueryWithParams) and singular (QueryByID) fields pass the same entity string, both map onto the ONE node object — the first registration walks its Response DTO and defines it; keep the two DTOs wire-aligned (a field only the later DTO carries is not selectable).
  • Relay connection — each read field returns { edges { node, cursor }, pageInfo { hasNextPage, hasPreviousPage, startCursor, endCursor }, totalCount }. edges[].cursor is the per-row keyset cursor (see "Pagination" below).
  • where input — one input field per filter leaf (the same query:"X" filter:"ops" allowlist the REST endpoint uses), each exposing the declared operators: where: { name: { startswith: "Bob" }, age: { gte: 18 } }. Nested embed leaves flatten (addresses.zipCode → addresses_zipCode). The operator set is the same one REST recognizes (eq, ne, in, nin, gte, lte, gt, lt, startswith, contains, ieq, ine, iin, inin, istartswith, icontains) — list operators take a list value.
  • Mutation input & payload — named from the FIELD, never from the Go DTO. The root input/payload type names derive from the registered mutation name — createUser yields CreateUserInput and CreateUserPayload — the Relay/GitHub mutation naming convention, so REST/Go vocabulary (Insert…, …Request, …Response) never leaks into the SDL. Only the NESTED input objects reached while walking the Request keep a Go-derived name (InsertUserAddressRequest → InsertUserAddressInput) — they have no field name to derive from. The bodyless mutations follow the same rule: each owns its field-derived payload (archiveUser → ArchiveUserPayload), all sharing the fixed { success: Boolean!, id: ID } shape — there is no generic shared result type. The write Request DTO's json tags drive the input's field names; nested structs become nested input objects. A field is NonNull when the handler embeds pipeline.FullBody (strict, every field required) or, leniently, when it is non-pointer and lacks ,omitempty — the same required rule the REST/OpenAPI side applies. Missing-required-field is enforced by gqlparser validation, not a separate runtime check.

    Assigning null through GraphQL — a structural limitation and the idiomatic way out. GraphQL has no "present but null" for a required field: NonNull is its only way to demand presence. So the strict (PUT-shaped) input cannot express the explicit null the REST PUT uses to clear a nullable field — sending null is rejected at parse time. The lenient (PATCH-shaped) input does not help either: an explicit null and an omitted field both decode into the same nil pointer on the Request, which the partial-update contract reads as "not sent, keep the current value" — on GraphQL AND on REST alike. The way out is the idiomatic GraphQL one: register an intent-specific mutation whose OPERATION carries the meaning instead of a field value, on the ordinary Auto path. Which handler that intent mounts depends on what is being cleared — a field and a whole facet are NOT the same case:
    • A nullable field → a "mini-PATCH" on PartialUpdateCommandHandler. Declare a dedicated Cmd whose ApplyPartiallyTo assigns the nil (e.g. clearEmployeePhone), pair it with a minimal (or empty) Request DTO, and register it via MutationByID/MutationWithBodyID. The partial update rewrites the owner row from the loaded entity, so the assigned nil lands as NULL. The same holds for a nullable field of a sibling facet whose OTHER fields stay populated — the facet row is upserted with that column cleared.
    • An ENTIRE sibling facet → an intent mutation on UpdateCommandHandler (the PUT-shaped handler). A partial update never removes a facet: a sibling whose mapped fields are all nil is left untouched on PATCH and deleted only on a full replace (the sibling write contract), so an ApplyPartiallyTo that nils every field of the facet is a SILENT NO-OP — the write succeeds and the row stays. Mount the intent (e.g. removeEmployeeBankAccount) on UpdateCommandHandler instead: its ApplyTo nils the facet's fields, GetUpdatable produces a non-partial Updatable, and the sibling row is deleted in the same transaction. The Cmd's method set is the one MutationByID/MutationWithBodyID already demand, and the FullBody marker only makes the input's fields NonNull — an intent Cmd carrying no body fields has nothing to require.
    No custom pipeline.Handler is required in either case, and the intent is explicit in the schema.
  • Order vocabulary — a typed enum, reflected like everything else. When the Request DTO declares query:"orderBy", the field takes orderBy: [<Entity>Order!] where <Entity>Order is { field: <Entity>OrderField!, direction: OrderDirection = ASC }. The <Entity>OrderField enum carries one SCREAMING_SNAKE value per sortable wire path of the Response DTO (userName → USER_NAME, nested addresses.zipCode → ADDRESSES_ZIP_CODE) — the SAME allowlist the REST ?orderBy= tokens are validated against, so the two surfaces cannot drift; the shared OrderDirection { ASC DESC } is emitted once. An undeclared field is not a runtime 400 here — it is not IN the enum, so introspection never advertises it and gqlparser rejects it before any resolver runs. The fold lands on the same sort terms as the REST tokens, so keyset cursors stay valid and interchangeable across surfaces. No Go type is involved: like the where input, the enum exists only in the SDL, reflected from the DTOs already attached. Two wire names colliding on one enum value (e.g. userName and user_name) is a Response modeling error and panics at boot. A response with no typed paths (RawDoc-style) omits the argument entirely.
  • scalar DateTime is declared when any time.Time field is reached; uuid.UUID / domain.ID map to ID.

The singular by-id field

Every large public GraphQL schema pairs the plural connection with a singular by-id field — GitHub's repository(…), Shopify's product(id:). QueryByID is that twin: it registers the SAME FindByIDQueryHandler (and the same Request/Response DTOs) the REST GET /users/:id route mounts, as user(id: ID!, includeArchived: Boolean): User. The field returns the node directly — no connection envelope — and the selection set trims it exactly like a connection node's.

  • Nullable on purpose. A missing document (or one an overlay filter hides) resolves the field to null with the canonical RecordNotFoundNotification (semantic: "NotFound") in errors[].extensions — the GraphQL translation of the REST 404, and the same null-plus-typed-error shape GitHub's API returns for a missing object.
  • includeArchived obeys the DTO like every reserved control: the argument is emitted only when the by-id Request DTO declares query:"includeArchived"; otherwise introspection never advertises it and gqlparser rejects it as an unknown argument — the twin of the REST by-id rule, where ?includeArchived is the only recognized query key.
  • No pagination, no where. The by-id read ignores criteria pagination/projection by design (ReadByID contract); the singular field therefore carries only id + the optional archived gate.
  • Same node type as the connection — pass the same entity string to QueryWithParams and QueryByID (see "Reflected schema"), so client fragments on User work on both fields.

The reflection core is shared with REST/OpenAPI

The operator vocabulary, the filter allowlist reflection, and the wire↔Go projection map all come from one internal package (web/queryschema) consumed by the REST wrappers, the OpenAPI generator, and the GraphQL schema builder. A new operator or a change to the wire↔Go translation lives in exactly one place — the GraphQL where input and the REST ?name.op= query parameter cannot drift apart. GraphQL's where folds through the identical criteria emission, so where: { name: { startswith: "Bo" } } produces the same Mongo clause as the REST ?name.startswith=Bo.

Execution

Per request the executor:

  1. lets gqlparser parse + validate the query against the schema (an undeclared field, operator, or argument is rejected here and surfaces in errors);
  2. builds a queries.ReadCriteria (read) or a Command input (write) from the GraphQL arguments, reusing the shared criteria emission;
  3. dispatches through the registered pipeline.Handler with the request *AppContext — so Query.ToCriteria(ctx) tenant/owner overlays, BuildRules, the outbox, and audit all apply unchanged;
  4. maps Page → Relay connection / Result → the projected Response, reshaped to the wire (json) names, then trims the tree to the selection set (fragments and inline fragments flattened). A field's nested selection becomes the effective projection.

Pagination — Relay connections + per-item cursor

The connection follows the Relay specification: first/after page forward and last/before page backward; first/last are the page size, after/before the opaque keyset cursor, orderBy: [{field: NAME, direction: DESC}] the typed sort terms (see "Reflected schema"), and totalCount the count. last: N returns the last N rows in canonical order (walking back from the end of the set), with pageInfo.hasNextPage: false and hasPreviousPage reflecting whether earlier rows remain. Strict Relay needs a cursor per edge, which cannot be reconstructed above the reader (the reader strips the physical keyset values from the returned Go-field-keyed items) — so the reader emits queries.Page.ItemCursors, the per-row keyset cursor, and the connection's edges[].cursor reads it. REST ignores ItemCursors.

One direction at a time. Forward (first/after) and backward (last/before) arguments are mutually exclusive — mixing them (first+last, last+after, an after+before pair), or passing a non-positive page size, is rejected before dispatch with a SchemaViolationNotification (semantic: "Schema", the offending argument as field), the same way REST rejects a contradictory query. Under the hood the GraphQL surface sets ReadCriteria.Backward for last (the only argument that carries direction without a cursor); the REST surface is unchanged — it has no last and keeps inferring backward purely from a non-empty before cursor. Both dialects converge on the same ReadCriteria and the same reader.

A stale or foreign cursor — one whose context hash no longer matches the current where / orderBy / search / includeArchived (the client changed the query mid-navigation), or that is malformed — is rejected with a legible SchemaViolationNotification (semantic: "Schema", field: "cursor") in errors[], not an opaque Internal. The REST wrapper pre-validates the cursor before dispatch; the GraphQL endpoint does not, so the reader itself returns the typed Schema rejection rather than a bare error — same notification either surface reports.

The DTO cuts the schema

The Request DTO governs this surface exactly as it governs REST and gRPC — and here the cut lands in the SCHEMA itself. queryFieldSDL emits a connection argument only when the DTO declares its query:"…" key (first, last, after, before, orderBy, search, includeArchived; the where input already follows the filter: tags). An undeclared argument is therefore absent from introspection and the playground's autocomplete, and gqlparser rejects it as an unknown argument BEFORE any resolver runs — the GraphQL self-translation of the same canonical rejection REST serves as a 400 and gRPC as INVALID_ARGUMENT, all three driven by the one control gateway (queryschema.ValidateControls). What the DTO cannot govern here is what the language expresses natively: the selection IS the projection (there is no fields argument to gate), and the only-total mode is a selection shape — both gate-exempt by nature.

Only-total — the REST ?onlyTotal=true short-circuit (skip the items, return just the count) maps to the natural GraphQL shape: a connection selection of only totalCount, with no edges and no pageInfo. When the endpoint's DTO declares query:"onlyTotal", the resolver detects the shape and sets ReadCriteria.OnlyTotal, so the reader short-circuits to its count primitive — no item materialization, no cursor work — exactly as the REST path does. Without the opt-in the same selection stays valid and returns the same totalCount through the un-optimized paged read: the total is intrinsic to every list envelope on every surface, so the DTO key governs only the optimization, never the information. The count still honors where / search / includeArchived. A pagination or ordering argument (first / last / after / before / orderBy) passed with a totalCount-only selection under the opt-in is a conflict — there is no page to order or seek into when only the count is asked — and is rejected with a SchemaViolationNotification (semantic: "Schema", field onlyTotal[<argument>]), the same matrix every surface runs.

The pagination probe — a selection of pageInfo with NO edges reads as "give me the window's boundaries, not its rows". The resolver narrows the read to the keyset essentials (the ordering-field values + _id — an unordered probe degenerates to {_id: 1}), so cursors, hasNextPage/hasPreviousPage and totalCount come from a minimal read that never materializes full documents. The window itself is still walked — boundaries cannot exist without it — so the probe is an optimization of the same read, invisible on the wire.

Authorization

Layers 2 (BuildRules) and 3 (tenant via ToCriteria) live below the dispatch boundary and apply unchanged — they are inherited the moment the resolver dispatches the same handler. Layer 1 (coarse resource:action permission) is route-shaped in REST (fwopenapi.RequirePermission); on a single GraphQL endpoint it moves into the resolver, per field, declared with fwgraphql.RequirePermission("resource:action") — a FieldOption on QueryWithParams / QueryByID / MutationWithBody / MutationWithBodyID / MutationByID, the GraphQL twin of fwopenapi.RequirePermission with the same resource:action validation (wildcards are the IdP's to grant, never the caller's to declare): 

reg.Register(fwgraphql.QueryWithParams[Req, Resp](
    "users", "User", readHandler,
    fwgraphql.RequirePermission("users:read")))

reg.Register(fwgraphql.MutationByID(
    "deleteUser", deleteHandler,
    fwgraphql.RequirePermission("users:delete")))

The gate is enforced behind the same master switch as REST — Registry.EnableAuthorization(cfg.Auth.Authorization.Enabled), wired by bootstrap next to EnableIntrospection — so a RequirePermission annotation is inert until auth.authorization.enabled (the same incremental-rollout posture as REST). When the switch is on and the request's Identity lacks the declared permission, the field resolves to a denial before the handler runs: HTTP 200 with the canonical MissingPermissionNotification (semantic: "Forbidden", field: "permission") in errors[].extensions — the same notification the REST gate returns as 403. The endpoint itself is authenticated by the AuthMiddleware when auth.mode: jwt (a valid bearer is required unless the operator lists POST /graphql in auth.publicRoutes); a missing bearer is rejected by the middleware with 401 before the gate is reached.

Field-level read access is enforced too. The read resolver maps the Relay node selection set (edges { node { … } }) to ReadCriteria.Projection before ToQuery, so a field a Query.ToCriteria restricts (via ReadCriteria.Restrict, e.g. an admin-only column) trips the same FieldAccessForbiddenNotification (semantic: "Forbidden") the REST ?fields= path returns when the field is explicitly selected. A passively unselected restricted field is simply scrubbed — never returned — so a non-privileged caller never sees it on either surface. As a side effect the projection is pushed down to Mongo: only the requested fields are read, exactly like the REST ?fields= path.

Errors

GraphQL always returns HTTP 200 with a { data, errors } body — request faults (parse/validation) and field faults (domain notifications) travel in errors, never the status line. Each domain notification becomes one errors[] entry carrying the typed identity in extensions: { "message": ..., "extensions": { "context": ..., "notificationKey": ..., "semantic": ..., "field": ..., "fieldLabel": ..., "value": ..., "funcName": ... } } — a faithful mirror of the REST envelope's ErrorMessage, so clients branch on the same typed identity and frontend-less channels read the same translated fieldLabel (from the labelKey tag) and echoed value. The REST envelope groups messages under a translated context (e.g. "User"); the flat GraphQL errors[] has no grouping level, so that context rides per message in extensions instead. context / fieldLabel / value / funcName are emitted only when present (omitempty parity), so services that don't use them keep a byte-identical envelope. A recovered panic surfaces as an opaque { semantic: "Internal" } error; the panic value and stack stay server-side, mirroring the REST 500 posture.

Introspection & playground

When introspection: true, the executor answers __schema / __type over the parsed schema so tooling (the playground, client codegen) can discover types. The introspection result is spec-compliant — the introspection meta-fields (__schema, __type, __typename) are not listed among an object type's fields, which the GraphQL spec forbids and GraphiQL's client-side schema validation hard-rejects — so the playground and codegen tools accept the schema. When playground: true, a GraphiQL page is served at uiPath (pinned React 18 + GraphiQL 3 UMD bundles from a CDN). Both are off by default and toggled independently in YAML, the same on/off posture as the Swagger UI. With introspection off, an __schema query simply does not resolve.
