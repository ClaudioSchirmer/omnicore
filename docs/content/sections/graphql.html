GraphQL

The framework exposes the same application handlers REST consumes through a single POST /graphql endpoint whose schema is reflected from the same Go types — Request DTOs (query:/filter: on the read side, json: on the write side) and Response/Result DTOs. A consumer attaches handlers to a registry; the SDL, the argument set (where / pagination / orderBy), the Relay connection envelope, the input objects, and the criteria translation are all derived automatically. There is no schema-first SDL to hand-write and no codegen step.

GraphQL is its own web surface. It does not go through the REST openapi.Mount/MountRaw machinery, it is never part of the Swagger/OpenAPI document, and it is not policed by the REST route scans. The only thing shared with REST is the application-layer handlers the resolvers dispatch to (pipeline.Handler[TQ, queries.Page] for reads, pipeline.Handler[*Cmd, TResult] for writes). The web layer is deliberately a different registry so each transport keeps its native shape — Relay connections + selection sets here, the JSON envelope + pagination block there. See Handler invariance.

Engine — gqlparser + a framework executor

Parsing and validation ride vektah/gqlparser/v2 (the parser gqlgen itself uses): the framework reflects the registry into an SDL document, loads it into a validated *ast.Schema, and per request gqlparser parses + validates the query against that schema. The framework owns only the executor — walking the selection set, dispatching through the registered handlers, mapping queries.Page / pipeline.Result to the wire, and answering introspection. A schema-first/codegen engine was rejected because it inverts the runtime "just attach" model; a frozen runtime-schema library was rejected as an unmaintained framework-core dependency.

Enable the endpoint

The consumer builds a registry on the dispatch pipeline and attaches it to the wire callback:

func Wire(d bootstrap.Deps) bootstrap.Wiring {
    gql := fwgraphql.New(d.Pipeline).
        // read: one Query field per query handler → a Relay connection
        Register(fwgraphql.Query[requests.FindUsersByParamsRequest,
                                 requests.FindUsersByParamsResponse](
            "users", "User",
            &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery]{
                Reader: d.ViewReader, View: view.Name()},
            fwgraphql.RequirePermission("users:read"))).
        // write: one Mutation field per command handler
        Register(fwgraphql.Mutation[requests.InsertUserRequest](
            "createUser", requests.InsertUserResponse{}.FromResult,
            &handlers.InsertCommandHandler[*User, *commands.InsertUserCommand, commands.InsertUserResult]{Repo: repo},
            fwgraphql.RequirePermission("users:write")))

    return bootstrap.Wiring{
        Translations: []translation.Module{...},
        Features:     []bootstrap.Feature{NewUsersFeature(d)},
        GraphQL:      gql,
    }
}

With Wiring.GraphQL set, bootstrap.Run mounts a single POST <path> (default /graphql) as its own surface, after the REST boot scans. The AuthMiddleware (matched by path at request time) still authenticates it when auth.mode: jwt; authorization is per-field in the resolver (see "Authorization" below). Leaving Wiring.GraphQL nil keeps everything off — no endpoint, zero cost.

Operator-tunable serving

The serving knobs live in microservice.<profile>.yaml under graphql:, mirroring the OpenAPI posture — WHAT the schema exposes (the attached handlers) is code on Wiring.GraphQL; HOW it is served is environment config: 

graphql:
  path: /graphql          # default. POST endpoint route.
  uiPath: /graphql/ui     # default. GET route for the GraphiQL playground (when playground: true).
  playground: false       # default off. Serve a GraphiQL page at uiPath.
  introspection: false    # default off. Answer __schema / __type queries.
  rootRedirect: false     # default off. GET / → 302 path. Both this and openapi.rootRedirect → boot panic.
  • Block optional. Absent → defaults. Present but Wiring.GraphQL nil → ignored.
  • path validated at boot: must start with /, must not collide with /openapi.json, /health, or /docs.
  • playground serves GraphiQL at uiPath (loaded from a CDN, like the Swagger UI). Pair it with introspection: true so the playground can populate its schema docs / autocomplete. uiPath is validated (leading slash, no framework-route collision, must differ from path) only when playground is on.
  • introspection gates __schema / __type. Independent of the playground; off by default so a closed endpoint does not advertise its shape. Typically on in dev.
  • rootRedirect registers GET / → 302 path. The boot panics when both openapi.rootRedirect and graphql.rootRedirect are enabled (and both surfaces wired) — only one surface can own /.

The registry — attach queries and mutations

fwgraphql.New(pipe) returns a registry; each Register(...) adds one root field. The generic constructors capture the typed handler into the SDL emitter and the resolver; the only surface shared with REST is the pipeline.Handler instance.

ConstructorMapsGraphQL field
Query[TReq, R]read handler pipeline.Handler[TQ, queries.Page]users(where, first, after, last, before, orderBy, search, includeArchived): UserConnection!
Mutation[TReq]insert-style command (body, no id)createUser(input: InsertUserInput!): InsertUserResponse!
MutationWithID[TReq]update/patch (body + id)updateUser(id: ID!, input: UpdateUserInput!): UpdateUserResponse!
MutationByIDarchive/unarchive/delete (id, no body)archiveUser(id: ID!): MutationResult!

You name only the type params Go cannot infer. Those are the reflection-only ones — used inside the constructor via reflection but absent from every parameter: TReq (the Request DTO) on the body forms, plus R (the Response DTO / connection node) on Query. Everything else — the command type, its pointer, the result, the response, the query type — is inferred from the handler argument and the DTO's ToCommand/ToQuery constraint, so MutationByID needs no type args at all. (Query's list is ordered [TReq, R, TQ] precisely so the inferable TQ trails and is elided.) These are the same DTOs the REST wrappers anchor; canonical (Auto) and hand-rolled handlers attach identically because both implement the same pipeline.Handler interface — the registry cannot tell them apart, exactly as the REST wrappers cannot.

Reflected schema

The SDL is generated once at boot from the registered DTOs and loaded into a validated schema:

  • Node object — the Response DTO becomes an object type named after the entity (User, not FindUsersByParamsResponse); fields are named by their json: wire name and resolved from the Go-field-keyed view document. Nested structs and slices recurse into nested object types.
  • Relay connection — each read field returns { edges { node, cursor }, pageInfo { hasNextPage, hasPreviousPage, startCursor, endCursor }, totalCount }. edges[].cursor is the per-row keyset cursor (see "Pagination" below).
  • where input — one input field per filter leaf (the same query:"X" filter:"ops" allowlist the REST endpoint uses), each exposing the declared operators: where: { name: { startswith: "Bob" }, age: { gte: 18 } }. Nested embed leaves flatten (addresses.zipCode → addresses_zipCode). The operator set is the same one REST recognizes (eq, ne, in, nin, gte, lte, gt, lt, startswith, contains, ieq, ine, iin, inin, istartswith, icontains) — list operators take a list value.
  • Mutation input — the write Request DTO becomes an ...Input object (json tags drive the field names; nested structs become nested input objects). A field is NonNull when the handler embeds pipeline.FullBody (strict, every field required) or, leniently, when it is non-pointer and lacks ,omitempty — the same required rule the REST/OpenAPI side applies. Missing-required-field is enforced by gqlparser validation, not a separate runtime check.
  • scalar DateTime is declared when any time.Time field is reached; uuid.UUID / domain.ID map to ID.

The reflection core is shared with REST/OpenAPI

The operator vocabulary, the filter allowlist reflection, and the wire↔Go projection map all come from one internal package (web/queryschema) consumed by the REST wrappers, the OpenAPI generator, and the GraphQL schema builder. A new operator or a change to the wire↔Go translation lives in exactly one place — the GraphQL where input and the REST ?name.op= query parameter cannot drift apart. GraphQL's where folds through the identical criteria emission, so where: { name: { startswith: "Bo" } } produces the same Mongo clause as the REST ?name.startswith=Bo.

Execution

Per request the executor:

  1. lets gqlparser parse + validate the query against the schema (an undeclared field, operator, or argument is rejected here and surfaces in errors);
  2. builds a queries.ReadCriteria (read) or a Command input (write) from the GraphQL arguments, reusing the shared criteria emission;
  3. dispatches through the registered pipeline.Handler with the request *AppContext — so Query.ToCriteria(ctx) tenant/owner overlays, BuildRules, the outbox, and audit all apply unchanged;
  4. maps Page → Relay connection / Result → the projected Response, reshaped to the wire (json) names, then trims the tree to the selection set (fragments and inline fragments flattened). A field's nested selection becomes the effective projection.

Pagination — Relay connections + per-item cursor

The keyset pagination the REST side exposes (?first/after/before + an opaque cursor with a context hash) maps to Relay: first → limit, after/before → the cursor, orderBy: ["-name"] → the sort terms, totalCount → the count. Strict Relay needs a cursor per edge, which cannot be reconstructed above the reader (the reader strips the physical keyset values from the returned Go-field-keyed items) — so the reader emits queries.Page.ItemCursors, the per-row keyset cursor, and the connection's edges[].cursor reads it. The cursor round-trips through the reader's after / before path unchanged. REST ignores ItemCursors.

A stale or foreign cursor — one whose context hash no longer matches the current where / orderBy / search / includeArchived (the client changed the query mid-navigation), or that is malformed — is rejected with a legible SchemaViolationNotification (semantic: "Schema", field: "cursor") in errors[], not an opaque Internal. The REST wrapper pre-validates the cursor before dispatch; the GraphQL endpoint does not, so the reader itself returns the typed Schema rejection rather than a bare error — same notification either surface reports.

Count-only — the REST ?onlyTotal=true short-circuit (skip the items, return just the count) maps to the natural GraphQL shape: a connection selection of only totalCount, with no edges and no pageInfo. The resolver detects it from the selection set and sets ReadCriteria.OnlyTotal, so the reader short-circuits to CountDocuments — no item materialization, no cursor work — exactly as the REST path does. The count still honors where / search / includeArchived. Selecting pageInfo alongside totalCount forces the full read, because its cursors derive from the page items. A pagination or sort argument (first / last / after / before / orderBy) passed with a totalCount-only selection is a conflict — there is no page to order or seek into when only the count is asked — and is rejected with a SchemaViolationNotification (semantic: "Schema", the offending argument as field), the GraphQL parity of REST's onlyTotal-vs-pagination 400.

Authorization

Layers 2 (BuildRules) and 3 (tenant via ToCriteria) live below the dispatch boundary and apply unchanged — they are inherited the moment the resolver dispatches the same handler. Layer 1 (coarse resource:action permission) is route-shaped in REST (fwopenapi.RequirePermission); on a single GraphQL endpoint it moves into the resolver, per field, declared with fwgraphql.RequirePermission("resource:action") — a FieldOption on Query / Mutation / MutationWithID / MutationByID, the GraphQL twin of fwopenapi.RequirePermission with the same resource:action validation (wildcards are the IdP's to grant, never the caller's to declare): 

reg.Register(fwgraphql.Query[Req, Resp](
    "users", "User", readHandler,
    fwgraphql.RequirePermission("users:read")))

reg.Register(fwgraphql.MutationByID(
    "deleteUser", deleteHandler,
    fwgraphql.RequirePermission("users:delete")))

The gate is enforced behind the same master switch as REST — Registry.EnableAuthorization(cfg.Auth.Authorization.Enabled), wired by bootstrap next to EnableIntrospection — so a RequirePermission annotation is inert until auth.authorization.enabled (the same incremental-rollout posture as REST). When the switch is on and the request's Identity lacks the declared permission, the field resolves to a denial before the handler runs: HTTP 200 with the canonical MissingPermissionNotification (semantic: "Forbidden", field: "permission") in errors[].extensions — the same notification the REST gate returns as 403. The endpoint itself is authenticated by the AuthMiddleware when auth.mode: jwt (a valid bearer is required unless the operator lists POST /graphql in auth.publicRoutes); a missing bearer is rejected by the middleware with 401 before the gate is reached.

Field-level read access is enforced too. The read resolver maps the Relay node selection set (edges { node { … } }) to ReadCriteria.Projection before ToQuery, so a field a Query.ToCriteria restricts (via ReadCriteria.Restrict, e.g. an admin-only column) trips the same FieldAccessForbiddenNotification (semantic: "Forbidden") the REST ?fields= path returns when the field is explicitly selected. A passively unselected restricted field is simply scrubbed — never returned — so a non-privileged caller never sees it on either surface. As a side effect the projection is pushed down to Mongo: only the requested fields are read, exactly like the REST ?fields= path.

Errors

GraphQL always returns HTTP 200 with a { data, errors } body — request faults (parse/validation) and field faults (domain notifications) travel in errors, never the status line. Each domain notification becomes one errors[] entry carrying the typed identity in extensions: { "message": ..., "extensions": { "notificationKey": ..., "semantic": ..., "field": ... } } — the GraphQL counterpart of the REST envelope's notificationKey / semantic, so clients branch on the same typed identity. A recovered panic surfaces as an opaque { semantic: "Internal" } error; the panic value and stack stay server-side, mirroring the REST 500 posture.

Introspection & playground

When introspection: true, the executor answers __schema / __type over the parsed schema so tooling (the playground, client codegen) can discover types. The introspection result is spec-compliant — the introspection meta-fields (__schema, __type, __typename) are not listed among an object type's fields, which the GraphQL spec forbids and GraphiQL's client-side schema validation hard-rejects — so the playground and codegen tools accept the schema. When playground: true, a GraphiQL page is served at uiPath (pinned React 18 + GraphiQL 3 UMD bundles from a CDN). Both are off by default and toggled independently in YAML, the same on/off posture as the Swagger UI. With introspection off, an __schema query simply does not resolve.
