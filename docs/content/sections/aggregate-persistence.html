Aggregate Persistence (transparent dispatch)

Entities that need to persist a root together with collections of child value objects opt-in by implementing domain.AggregateRootProvider. The framework then guarantees atomicity without changing the public API: the relational engine's Insert/Update/Archive/Delete/Unarchive (the core.RelationalEngine seam, backed by Postgres or MySQL) detect the metadata and dispatch to the aggregate-aware path automatically.

Opt-in interface

type AggregateRootProvider interface {
    GetAggregateRoot() *AggregateRoot

    // Explicitly declares which types belong to the aggregate.
    // Sample instances (zero value) are enough — framework reads classNameOf via reflect.
    AggregateChildren() []AggregateValueObject
}

The interface keeps table/FK declaration out of the domain — children types are discovered via reflection on root.AllAggregateItems(); the child table and FK are declared explicitly in the root's TableSchema via .Child(core.NewTableSchema[Address]("addresses").FK("user_id")...). There is no name inference — the TableSchema is the single mandatory map between each Go field and its physical column — see TableSchema.

The root holds authority over the aggregate boundary without infra leaking into the domain. AggregateChildren() declares which types belong to the aggregate — a domain definition (orthodox DDD), separated from "which table/FK" (infra, declared in the TableSchema). The top-level primitives AddAggregateChild, ChangeAggregateChild, RemoveAggregateChild and ReplaceAggregateChildrenOf consult this list and reject VOs of undeclared types by emitting InvalidAggregateChildNotification (422 Validation). The internal addAggregateItem/changeAggregateItem/removeAggregateItem methods are used only by AggregateConstructor (DB load path, with types coming from the child schemas declared via .Child(...) on the root's TableSchema) and by the top-level primitives after the type-guard.

AggregateValueObject requires BuildRules(actionName string, svc Service, r *Rules) — signature identical to Entity.BuildRules — plus GetID() domain.ID, backed by an exported ID domain.ID field (identity is a TYPE on children exactly as on references; the persister's minted-id write-back sets that field via reflection). Infra maps columns via the child's TableSchema; an undeclared exported field is runtime-only by construction (the schema simply does not list it, so it is never persisted/scanned/audited); ID is the PK (skipped on INSERT/UPDATE write list, used in the WHERE clause); the FK to the root is injected by infra (it is not a struct field).

Universal symmetric cascade

Operations on the root cascade symmetrically and universally — no per-child HardDelete flag:

  • Archive(root) → Archive on all active children
  • Unarchive(root) → Unarchive on all archived children (requires domain.ArchivedFinder on the Repository to hydrate the aggregate)
  • Delete(root) → an explicit DELETE on every declared child table (by FK), in the same TX, before the root DELETE — the framework owns the cascade in Go, not a database ON DELETE CASCADE
  • Update(root) with items StatusRemoved → Archive of those specific items

Each child is bucketed by domain.OperationOf(OriginalStatus, CurrentStatus) — comparing where the item started (zero value or DB-loaded) against where it is now — into one AggregateItemOp: OpInsert→INSERT, OpUpdate→UPDATE, OpDelete→Archive (UPDATE deleted_at; the row stays recoverable), OpNoop→skipped. Two cross-status cases follow from the pair: a DB-loaded child re-added (Constructor→Added) is an UPDATE, not an INSERT; a brand-new child added then removed before commit (Added→Removed) is OpNoop — no SQL, never persistedwriteChildren

Shared-base children are a variant of this path. When the aggregate root is backed by a shared base, some children belong to the base identity rather than the role root: their FK targets the base's deterministic id and they are shared by every role of that identity. They travel the same writeChildren bucketing above; on the warm upsert insert they hydrate as Constructor status, so an untouched base-child resolves to OpNoop and the diff machine leaves it alone. See Shared-base children and the shared-base insert handler.
Archive and Unarchive run BuildRules and consult Modes(). Archive and Unarchive are state transitions (touch deleted_at, not fields). They run BuildRules in ModeUpdate with a distinct actionName ("GetArchivable" / "GetUnarchivable") — so the existing IfUpdate DSL fires for state-transition verbs too — AND they consult Modes(): an entity that does not declare ModeArchive receives ArchiveNotAllowedNotification (403 Forbidden) when calling GetArchivable; same for ModeUnarchive/UnarchiveNotAllowedNotification. These modes are independent of ModeUpdate — declaring Update does not enable Archive.

Usage patterns: append-only declares [ModeDisplay, ModeInsert] and is immune to accidental archive; full CRUD with soft delete declares all 6 modes; "freeze-once" entity (configure once, archive when obsolete) declares [ModeDisplay, ModeInsert, ModeArchive, ModeUnarchive] without allowing Update/Delete.

Example

type User struct {
    domain.AggregateRoot
    Name, Email, Username, Phone string
}

func (u *User) Modes() []domain.EntityMode { return []domain.EntityMode{...} }
func (u *User) GetAggregateRoot() *domain.AggregateRoot { return &u.AggregateRoot }
func (u *User) BuildRules(...) { ... }

// Domain declares which types belong to the aggregate.
func (u *User) AggregateChildren() []domain.AggregateValueObject {
    return []domain.AggregateValueObject{Address{}}
}

// Domain vocabulary. Commands do not speak directly to primitives —
// they call root methods, which run invariants spanning children and delegate.
func (u *User) AddAddress(addr Address, svc domain.Service) {
    for _, existing := range domain.GetCurrentItemsOf[Address](&u.AggregateRoot) {
        if existing.sameBusinessIdentity(addr) {
            u.AddNotification("Address", DuplicateAddressNotification{})
            return
        }
    }
    domain.AddAggregateChild(u, addr)  // type-guard against AggregateChildren()
}

func (u *User) ChangeAddress(original, replacement Address) {
    domain.ChangeAggregateChild(u, original, replacement)
}

func (u *User) RemoveAddress(addr Address) {
    domain.RemoveAggregateChild(u, addr)
}

func (u *User) ReplaceAddresses(addrs []Address) {
    domain.ReplaceAggregateChildrenOf(u, addrs)
}

// Explicit schema map — every Go field names its physical column, the
// child table + FK are declared via .Child(...). No name inference anywhere.
func UserSchema() *core.TableSchema {
    return core.NewTableSchema[*User]("users").
        PK("id").
        Field("Name", "name").
        Field("Email", "email").
        Field("Username", "username").
        Field("Phone", "phone").
        SoftDelete("deleted_at").
        CreatedAt("created_at").
        UpdatedAt("updated_at").
        Child(core.NewTableSchema[Address]("addresses").
            FK("user_id").                 // injected by the persister, not a struct field
            PK("id").
            Field("Street", "street").
            Field("ZipCode", "zip_code").
            SoftDelete("deleted_at"))
}

// Declare once and thread it — WithSchema feeds the write binding AND the
// read loader (write SQL + criteria + auto-scan); children come from the
// schema's .Child(...) declarations.
r.WithSchema(UserSchema())
// Repository Insert/Update/etc are one-liners delegating to the relational engine.
// The aggregate path activates automatically because GetInsertable populated the metadata.

Domain methods on the root

Children mutations go through root methods named in the domain vocabulary (AddAddress, ChangeAddress, RemoveAddress, ReplaceAddresses) — never directly through the AddAggregateChild & co. primitives from commands. This is what makes the root the consistency boundary:

  • Tell, don't ask — command says "User, add this address", not "User, let me mess with your internal list"
  • Invariants spanning children live in root methods (duplicate, "cannot remove the last one", cross rules)
  • Ubiquitous vocabulary — AddAddress is business language; AddAggregateChild is framework jargon
  • Service injected per method when needed — no global plumbing in the framework. AddAddress's svc enables external lookups (e.g., "is this ZIP code already in use by another user?") without touching the primitives' contract
Construction-time notifications survive to the boundary. Root methods must call domain.EnsureInitialized(u) on the first line. Without it, notifications emitted in the constructor (e.g., duplicate detection in AddAddress) would be silently lost because BaseEntity.AddNotification is a no-op when notifCtx == nil (the natural state of an entity freshly constructed via &User{}; GetInsertable only initializes the context LATER). resetEntity called by getInsertable/getUpdatable/getDeletable does not clear the NotificationContext — notifications accumulated during construction survive until checkAllNotifications. IsValid (re-check) calls Clear() explicitly before re-validating. The type-guarded primitives also call ensureRootInit internally as defense in depth.

Replacing the children collection

For full-replace Update (replace all items), the root method delegates to the framework's generic helper:

func (c UpdateUserCommand) ApplyTo(_ *configuration.AppContext, u *appdomain.User) error {
    u.Name = c.Name
    addrs := make([]appdomain.Address, len(c.Addresses))
    for i, a := range c.Addresses { addrs[i] = a.toAddress() }
    u.ReplaceAddresses(addrs)  // delegates to domain.ReplaceAggregateChildrenOf(u, addrs)
    return nil
}

Equivalent to ClearAggregateItemsOfType("Address") + AddAggregateChild loop, but type-safe — every item goes through the type-guard, items of types not declared in AggregateChildren() are rejected with InvalidAggregateChildNotification.

Optional inline validation

By default, AVO's BuildRules runs at the boundary (GetInsertable/Update/Delete) via runAggregateValidations — same lifecycle as the root's BuildRules. Mutations accumulate, validation runs once. For those who want immediate feedback inside a root method, the framework provides domain.ValidateAggregateChild(root, item, actionName, svc) bool: runs item.BuildRules with a NotificationContext scoped just like the boundary would; returns true if it passed. Pitfall: if you use it inline AND the item enters the collection, the boundary runs BuildRules again and produces a duplicate notification. Use one path OR the other per item.

Children validation is also transparent

runAggregateValidations (called inside validateForInsert/Update/Delete) detects AggregateRootProvider and iterates root.AllAggregateItems() automatically: for each typeName present, it fires BuildRules(actionName, svc, r) on each item of the AggregateRoot with CurrentStatus != Removed, with r carrying a NotificationContext already scoped at [NameSegment(collection), IndexSegment(i)] — the collection segment is the JSON wire name, toLowerCamel(typeName) pluralized in camelCase (Address → addresses, OrderLine → orderLines). The root's BuildRules does not need to register children manually for the child's to run. Since the type-guard on the primitives ensures only types declared in AggregateChildren() enter the collection, iterating the map equals iterating the declared list.

Inside the AVO's BuildRules, r.IfInsert/IfUpdate/IfInsertOrUpdate/... dispatches by mode — same DSL as the root. For example, Address.BuildRules in omnicore-example-users only runs rules inside r.IfInsertOrUpdate, but the framework doesn't enforce that — entities may have Delete-specific rules (e.g., "cannot delete primary address"), or general cross-mode rules applied to the item.

AddAggregateValueObject remains available for typeNames outside the declared boundary (VOs without their own table, e.g.: tags serialized in a JSONB column). TypeNames covered by the automatic step are ignored in the manual slice to avoid double validation. 

// Root declares the aggregate boundary via AggregateChildren().
// Framework iterates root.AllAggregateItems() inside validateForInsert/Update/Delete
// and fires Address.BuildRules per item — no manual re-iteration needed.
func (u *User) AggregateChildren() []domain.AggregateValueObject {
    return []domain.AggregateValueObject{Address{}}
}

func (u *User) BuildRules(_ string, _ domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() { /* root fields only */ })
}
No separate aggregate write method. The consumer-facing write port is unchanged — repo.Scope(ctx).Insert(Insertable) / Update(Updatable) / etc. (the underlying engine Insert/Update/… also receive the *TableSchema + resolved hook, but the consumer never spells those out). Aggregate behavior is transparent — whoever implements AggregateRootProvider gains it (automatic persistence and validation of children); whoever doesn't follows the traditional single-table path.
