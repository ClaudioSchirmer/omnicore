Aggregate Persistence (transparent dispatch)

Entities that need to persist a root together with collections of child value objects opt-in by implementing domain.AggregateRootProvider. The framework then guarantees atomicity without changing the public API: the relational engine's Insert/Update/Archive/Delete/Unarchive (the core.RelationalEngine seam, backed by Postgres, MySQL, SQL Server or Oracle) detect the metadata and dispatch to the aggregate-aware path automatically.

Opt-in interface

type AggregateRootProvider interface {
    GetAggregateRoot() *AggregateRoot

    // Explicitly declares which types belong to the aggregate.
    // Sample instances (zero value) are enough — framework reads classNameOf via reflect.
    AggregateChildren() []AggregateValueObject
}

The interface keeps table/ParentID declaration out of the domain — children types are discovered via reflection on root.AllAggregateItems(); the child table and ParentID are declared explicitly in the root's TableSchema via .Child(core.NewTableSchema[Address]("addresses").ParentID("user_id")...). There is no name inference — the TableSchema is the single mandatory map between each Go field and its physical column — see TableSchema.

The root holds authority over the aggregate boundary without infra leaking into the domain. AggregateChildren() declares which types belong to the aggregate — a domain definition (orthodox DDD), separated from "which table/ParentID" (infra, declared in the TableSchema). The top-level primitives AddAggregateChild, ChangeAggregateChild, RemoveAggregateChild and ReplaceAggregateChildrenOf consult this list and reject VOs of undeclared types by emitting InvalidAggregateChildNotification (422 Validation). The internal addAggregateItem/changeAggregateItem/removeAggregateItem methods are used only by AggregateConstructor (DB load path, with types coming from the child schemas declared via .Child(...) on the root's TableSchema) and by the top-level primitives after the type-guard.

AggregateValueObject requires BuildRules(actionName string, svc Service, r *Rules) — signature identical to Entity.BuildRules — plus GetID() domain.ID, which comes promoted from an embedded domain.Managed carrier (identity is a TYPE on children exactly as on references; the id lives in the carrier, and the persister's minted-id write-back sets it through the promoted SetID). Embed domain.Managed in the value object; a load surfaces the id AND the managed timestamps/revision through the carrier's getters. Infra maps the business columns via the child's TableSchema; an undeclared exported field is runtime-only by construction (the schema simply does not list it, so it is never persisted/scanned/audited); the id column is declared with .ID(col) (skipped on the INSERT/UPDATE write list, used in the WHERE clause and read back as a trailing scan column); the ParentID to the root is injected by infra (it is not a struct field). It also requires IsSameBusinessIdentity(other AggregateValueObject) bool — see Child identity — and CollectionName() string, the declared name of the collection it occupies inside the aggregate — see Naming the collection.

Child identity

The framework matches an aggregate child against the tracked collection — for add / re-activate, change, remove, and the post-INSERT id write-back — exclusively through IsSameBusinessIdentity(other AggregateValueObject) bool, which every AggregateValueObject MUST implement. Only the domain can say when two children are "the same": two Address values are the same place by Country+ZipCode+Street+Number even if Label or Complement differ. (This replaced a whole-struct reflect.DeepEqual guess, which also compared the id and so treated an id-less re-sent child as brand new.)

When the aggregate's notion of identity is simply "every business field", delegate to the helper domain.IsSameByBusinessFields(a, other) — it compares every exported field except the framework-managed carrier. Prefer a hand-written natural key when the aggregate has one.

Contract — at most ONE active child per business identity. A second active child with the same identity is rejected as a duplicate (EntityAlreadyAddedNotification, SemanticConflict → 409); the four match sites rely on this uniqueness to resolve "the entry that matches".

Effect on a strict PUT (full replace). Replace clears the collection then re-adds; a re-sent child whose identity matches a just-cleared one re-activates it (UPDATE, id preserved) instead of archive-old + insert-new. With an id-agnostic identity (like Address), re-sending an unchanged child no longer churns its id; with a structural identity (IsSameByBusinessFields, which includes every field), a child re-sent with any changed field is a distinct value and is archived-then-reinserted — preserving the prior version as history. The choice is the aggregate's. 

func (a Address) IsSameBusinessIdentity(other domain.AggregateValueObject) bool {
    o, ok := other.(Address)
    return ok &&
        a.Country == o.Country && a.ZipCode == o.ZipCode &&
        a.Street == o.Street && a.Number == o.Number
}

// no natural key narrower than the full value → the structural helper:
func (d Dependent) IsSameBusinessIdentity(other domain.AggregateValueObject) bool {
    return domain.IsSameByBusinessFields(d, other)
}

Naming the collection — CollectionName()

Every AggregateValueObject MUST also declare CollectionName() string: the name of the collection it occupies inside its owning aggregate. It is the one name for that collection across the framework, with exactly two consumers:

  • The read side — it is the document segment the projection nests the collection under and the Go segment a filter/sort path walks (?addresses.city resolves as Addresses.City). It must therefore match the field your read DTO declares for the collection.
  • The notification wire path — rendered lower-camel, so a child's notification surfaces as addresses[0].zipCode without the AVO knowing it is a child.
func (Address) CollectionName() string { return "Addresses" }

// The domain's own language — the framework has no opinion:
func (Endereco) CollectionName() string { return "Enderecos" }

Declared, never derived. The framework applies no pluralization rule: an English heuristic cannot spell a Portuguese or German collection, it gets English irregulars wrong (Person, Child, Analysis), and a name that is merely derived is a name nobody declared — while it is, in fact, a persisted document key. This is the same posture as TableSchema: physical names are declared, complete, and checked.

Contract. A constant, valid as an exported Go field name — first rune an ASCII uppercase letter (A-Z), every other rune a letter or a digit (accented letters are fine: "Endereços"). The framework resolves it once per type from a zero value and caches it, so it must not depend on receiver state. Two children of one schema declaring the same name is a boot error, as is a child type that declares no name — both panic at the Child(...) declaration, never at runtime.

Changing a declared name changes the projection's shape — the collection moves to a new document key. Bump the view's Version(N) so the blue-green rebuild republishes it, and rename the matching field in the read DTO (see Mongo schema evolution).

Universal symmetric cascade

Operations on the root cascade symmetrically and universally — no per-child HardDelete flag:

  • Archive(root) → Archive on all active children
  • Unarchive(root) → Unarchive on the children this root's archive put to sleep — the ones carrying its archive stamp, never a child archived on its own (see What an unarchive brings back; requires domain.ArchivedFinder on the Repository to hydrate the aggregate)
  • Delete(root) → an explicit DELETE on every declared child table (by ParentID), in the same TX, before the root DELETE — the framework owns the cascade in Go, not a database ON DELETE CASCADE
  • Update(root) with items StatusRemoved → Archive of those specific items when the child declares DeletedAt; DELETE of those rows when it does not (see What a child's DeletedAt declares)

The UPDATE path

Update is load-first, and that is what makes it cheap: an untouched child resolves to OpNoop and emits no SQL at all. The root's own UPDATE carries the optimistic-concurrency guard; children and the shared base are deliberately unguarded, each for its own reason.

What an unarchive brings back

An unarchive restores the children the root's own archive put to sleep — not every archived child under the root. A child archived on its own (removed through a PUT replace-all or RemoveAggregateChild, weeks or years before) stays archived when the root comes back: nothing about the root's archive concerns it, so nothing about the root's unarchive should either. Bringing it back was the old behavior and it silently resurrected records the service had deliberately retired.

What tells the two apart is already in the data, and it costs no column: one operation, one instant. A write stamps a single DeletedAt value — the same time.Time — on the root row and on every child row its cascade reaches, and the archive cascade skips (deleted_at IS NULL) the children that were already archived, so those keep their own, older stamp. "Archived because of the root" therefore reads exactly as "carries the root's archive stamp":

archive at T1 root.deleted_at = T1 child A (active) = T1 ← the cascade stamped it child B (archived) = T0 ← untouched, it was already down unarchive UPDATE child SET deleted_at = NULL WHERE parent_id = ? AND deleted_at = (SELECT deleted_at FROM root WHERE id = ?) └─ A comes back · B stays archived, still carrying T0 └─ then the root row is cleared — in that order, because the sub-select IS the discriminator

The comparison is written column against column, on purpose. Reading the root's stamp into the application and binding it back as a parameter is the same comparison on paper and does not survive every driver: a bound timestamp carries a location, a driver is free to send it as a zoned value against a column declared without one, and the server then reconciles the two through its session time zone and matches nothing — no error, just a restore that reaches no row while the event says the children woke up. Inside the statement the values never leave the server.

The same rule governs a shared base: the base row and its native children go down with the triggering role operation's one instant, and the reactivation restores the native children carrying the base's own stamp. Those are two instants, not one, because they are not always the same write: archiving a role while a sibling role stays active leaves the identity up, so the base and its children only go down later, with the LAST role. Unarchiving the first role then restores its own children from its own stamp and the base's children from the base's — and an archive that left the identity up says nothing about the base's children at all, because no statement touched them.

The DeletedAt columns must carry sub-second precision, and root and child must agree on it. The discriminator is an equality between two stored timestamps, so it is only as sharp as the column type: TIMESTAMPTZ / TIMESTAMP(6) / DATETIME(6) / DATETIME2(6). A second-precision column (a bare MySQL DATETIME) collapses two operations that happened within the same second into one stamp; a child column coarser than the root's truncates the stamp it was given and stops matching it, which fails safe (nothing is restored) but silently.

What a child's DeletedAt declares

A child's removal is decided by one thing — whether the child's own schema declares DeletedAt, the same rule the root follows. A child that declares the column is archived: the row lingers, hidden from reads, and it comes back through its own re-add — the owner's unarchive restores only what the owner's own archive stamped (What an unarchive brings back). A child that declares none has no state to stamp, so the honest write is the DELETE — exactly the answer the root gives an entity without DeletedAt. Where the child lives makes no difference: a role's own child and a shared base's native child follow the identical rule.

The difference against the root is that the root has two verbs over the same table — DELETE and PATCH …/archive — while a child has a single primitive (RemoveAggregateChild), so the declaration is what chooses:

Two things follow that the framework cannot enforce for you. The route should tell the same truth as the declaration — DELETE …/:id/<children>/:childId for a child that declares no column, PATCH …/:id/<children>/:childId/archive for one that does; the framework mounts neither, so that one is yours to keep honest. And a hard-removed child is not lost history: the audit event carries the child's previous state as its snapshot under op = "deleted". Deleting the row removes the row, not the record of it.

Shared-base children are a variant of this path. When the aggregate root is backed by a shared base, some children belong to the base identity rather than the role root: their ParentID targets the base's deterministic id and they are shared by every role of that identity. They travel the same writeChildren bucketing above; on the warm upsert insert they hydrate as Constructor status, so an untouched base-child resolves to OpNoop and the diff machine leaves it alone. See Shared-base children and the shared-base insert handler.
Archive and Unarchive run BuildRules and consult Modes(). Archive and Unarchive are state transitions (touch deleted_at, not fields). They run BuildRules in ModeArchive / ModeUnarchive — each its own verb, dispatched by the IfArchive / IfUnarchive DSL closures (not IfUpdate, which is PUT/PATCH exclusively) — AND they consult Modes(): an entity that does not declare ModeArchive receives ArchiveNotAllowedNotification (403 Forbidden) when calling GetArchivable; same for ModeUnarchive/UnarchiveNotAllowedNotification. These modes are independent of ModeUpdate — declaring Update does not enable Archive.

Usage patterns: append-only declares [ModeDisplay, ModeInsert] and is immune to accidental archive; full CRUD with archive declares all 6 modes; "freeze-once" entity (configure once, archive when obsolete) declares [ModeDisplay, ModeInsert, ModeArchive, ModeUnarchive] without allowing Update/Delete.

Example

type User struct {
    domain.AggregateRoot
    Name, Email, Username, Phone string
}

func (u *User) Modes() []domain.EntityMode { return []domain.EntityMode{...} }
func (u *User) GetAggregateRoot() *domain.AggregateRoot { return &u.AggregateRoot }
func (u *User) BuildRules(...) { ... }

// Domain declares which types belong to the aggregate.
func (u *User) AggregateChildren() []domain.AggregateValueObject {
    return []domain.AggregateValueObject{Address{}}
}

// Domain vocabulary. Commands do not speak directly to primitives —
// they call root methods, which run invariants spanning children and delegate.
func (u *User) AddAddress(addr Address, svc domain.Service) {
    for _, existing := range domain.GetCurrentItemsOf[Address](&u.AggregateRoot) {
        if existing.sameBusinessIdentity(addr) {
            u.AddNotification("Address", DuplicateAddressNotification{})
            return
        }
    }
    domain.AddAggregateChild(u, addr)  // type-guard against AggregateChildren()
}

func (u *User) ChangeAddress(original, replacement Address) {
    domain.ChangeAggregateChild(u, original, replacement)
}

func (u *User) RemoveAddress(addr Address) {
    domain.RemoveAggregateChild(u, addr)
}

func (u *User) ReplaceAddresses(addrs []Address) {
    domain.ReplaceAggregateChildrenOf(u, addrs)
}

// Explicit schema map — every Go field names its physical column, the
// child table + ParentID are declared via .Child(...). No name inference anywhere.
func UserSchema() *core.TableSchema {
    return core.NewTableSchema[*User]("users").
        ID("id").
        Revision("revision").
        Field("Name", "name").
        Field("Email", "email").
        Field("Username", "username").
        Field("Phone", "phone").
        DeletedAt("deleted_at").
        CreatedAt("created_at").
        UpdatedAt("updated_at").
        Child(core.NewTableSchema[Address]("addresses").
            ParentID("user_id").                 // injected by the persister, not a struct field
            ID("id").
            Field("Street", "street").
            Field("ZipCode", "zip_code").
            DeletedAt("deleted_at"))
}

// read loader (write SQL + criteria + auto-scan); children come from the
// schema's .Child(...) declarations.
r.WithSchema(UserSchema())
// Repository Insert/Update/etc are one-liners delegating to the relational engine.
// The aggregate path activates automatically because GetInsertable populated the metadata.

Domain methods on the root

Children mutations go through root methods named in the domain vocabulary (AddAddress, ChangeAddress, RemoveAddress, ReplaceAddresses) — never directly through the AddAggregateChild & co. primitives from commands. This is what makes the root the consistency boundary:

  • Tell, don't ask — command says "User, add this address", not "User, let me mess with your internal list"
  • Invariants spanning children live in root methods (duplicate, "cannot remove the last one", cross rules)
  • Ubiquitous vocabulary — AddAddress is business language; AddAggregateChild is framework jargon
  • Service injected per method when needed — no global plumbing in the framework. AddAddress's svc enables external lookups (e.g., "is this ZIP code already in use by another user?") without touching the primitives' contract
Construction-time notifications survive to the boundary. A root method emits with no preparation of any kind: an entity built with &User{} already carries its NotificationContext, because BaseEntity allocates it on first use. So a duplicate detected inside AddAddress — long before GetInsertable ever sees the entity — is kept, not dropped. resetEntity, called by getInsertable/getUpdatable/getDeletable, does not clear the context: notifications accumulated during construction survive until checkAllNotifications. IsValid (re-check) calls Clear() explicitly before re-validating.
What the framework fills in later — and why you never see it. Two things about the context cannot be known at construction: the entity name it reports, and the type whose labelKey:"…" tags its emissions resolve against. A method whose receiver is *BaseEntity cannot see the type embedding it — reflect.TypeOf answers *BaseEntity, never *User. The framework therefore stamps both the first time it holds the concrete entity (every Get* entry point, plus the aggregate primitives), and backfills the field label of anything emitted in the meantime. Naming is a late concern; emitting never is.

Replacing the children collection

For full-replace Update (replace all items), the root method delegates to the framework's generic helper:

func (c UpdateUserCommand) ApplyTo(_ *configuration.AppContext, u *appdomain.User) error {
    u.Name = c.Name
    addrs := make([]appdomain.Address, len(c.Addresses))
    for i, a := range c.Addresses { addrs[i] = a.toAddress() }
    u.ReplaceAddresses(addrs)  // delegates to domain.ReplaceAggregateChildrenOf(u, addrs)
    return nil
}

Equivalent to ClearAggregateItemsOfType("Address") + AddAggregateChild loop, but type-safe — every item goes through the type-guard, items of types not declared in AggregateChildren() are rejected with InvalidAggregateChildNotification.

Optional inline validation

By default, AVO's BuildRules runs at the boundary (GetInsertable/Update/Delete) via runAggregateValidations — same lifecycle as the root's BuildRules. Mutations accumulate, validation runs once. For those who want immediate feedback inside a root method, the framework provides domain.ValidateAggregateChild(root, item, mode, actionName, svc) bool: runs item.BuildRules under the mode you pass (so the item's IfInsert/IfArchive/… dispatch correctly) with a NotificationContext scoped just like the boundary would; returns true if it passed. Pitfall: if you use it inline AND the item enters the collection, the boundary runs BuildRules again and produces a duplicate notification. Use one path OR the other per item.

Children validation is also transparent

runAggregateValidations (called inside validateForInsert/Update/Delete) detects AggregateRootProvider and iterates root.AllAggregateItems() automatically: for each typeName present, it fires BuildRules(actionName, svc, r) on each item of the AggregateRoot with CurrentStatus != Removed, with r carrying a NotificationContext already scoped at [NameSegment(collection), IndexSegment(i)] — the collection segment is the name the AVO declares in CollectionName(), rendered lower-camel for the wire ("Addresses" → addresses, "OrderLines" → orderLines). The framework applies no pluralization rule of its own — see Naming the collection. The root's BuildRules does not need to register children manually for the child's to run. Since the type-guard on the primitives ensures only types declared in AggregateChildren() enter the collection, iterating the map equals iterating the declared list.

Inside the AVO's BuildRules, r.IfInsert/IfUpdate/IfDelete/IfArchive/IfUnarchive/IfInsertOrUpdate dispatches by mode — same DSL as the root. For example, Address.BuildRules in omnicore-example-users only runs rules inside r.IfInsertOrUpdate, but the framework doesn't enforce that — entities may have Delete-specific rules (e.g., "cannot delete primary address"), or general cross-mode rules applied to the item.

ValidateAggregateValueObject remains available for typeNames outside the declared boundary (VOs without their own table, e.g.: tags serialized in a JSONB column). TypeNames covered by the automatic step are ignored in the manual slice to avoid double validation. 

// Root declares the aggregate boundary via AggregateChildren().
// Framework iterates root.AllAggregateItems() inside validateForInsert/Update/Delete
// and fires Address.BuildRules per item — no manual re-iteration needed.
func (u *User) AggregateChildren() []domain.AggregateValueObject {
    return []domain.AggregateValueObject{Address{}}
}

func (u *User) BuildRules(_ string, _ domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() { /* root fields only */ })
}
No separate aggregate write method. The consumer-facing write port is unchanged — repo.Scope(ctx).Insert(Insertable) / Update(Updatable) / etc. (the underlying engine Insert/Update/… also receive the *TableSchema + resolved hook, but the consumer never spells those out). Aggregate behavior is transparent — whoever implements AggregateRootProvider gains it (automatic persistence and validation of children); whoever doesn't follows the traditional single-table path.
