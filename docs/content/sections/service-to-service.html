Service-to-service communication

Four infrastructure surfaces carry traffic across service boundaries. The choice is driven by temporal coupling — whether the caller must block on the answer — and, on the synchronous side, by who owns the other end. Pick the mechanism by the question you are actually answering; the framework exposes exactly one canonical path for each.

I need to… Use Why
Get an answer now from another omnicore service grpcclient → the gRPC plane (sync, internal — the default) Synchronous service-to-service communication happens primarily over gRPC: designed contracts (.proto + buf breaking in CI), typed generated clients, deadline propagation, the shared resilience chain (retry/breaker/idempotency over infra/resilience), and the internal-plane posture (grpc.auth.mode: internal|mtls — anonymous trusted calls, user context forwarded as attribution when the flow needs it, µs local validation). Same pipeline.Handler on the other end as every surface.
Get an answer now from an external / third-party API httpclient (sync, edge) Third parties speak HTTP — request/response over the per-service registry (breaker, pool, TLS, oauth2/HMAC auth providers, response cache). It also works service-to-service when a team needs it, with the edge semantics that entails: strict token validation on the receiving side (expiry rejects — no attribution tolerance), permission gates always enforced, and none of the internal-plane conveniences. Internal sync traffic should default to gRPC and reserve httpclient for the boundary.
Read another service's state inside my own queries UpstreamSubscription + an external JoinUpstream embed (read-side) You do not need a call — you need the data local. The framework materializes the upstream collection from its event stream and ripples recompose into every view that embeds it. Reads never leave the process. See the TableSchema page for the external JoinUpstream embed wiring. This row is about ANOTHER service's data. To compose read models over your OWN aggregates there is no broker hop at all: embed the local view with query.JoinView (materialized, kept fresh in-process) or join it per request with a ComposedView.
Signal that something happened so other services can react integration events (async) Decouple in time: emit a typed event into integration_events (atomic with the data write) and let subscribers consume it on their own clock. No blocking, no fan-out coupling in the producer.

What about sending a command to another service — "do X", no return value? There is no fifth mechanism, by design. The instinct to issue a cross-service command is almost always a fact in disguise: instead of telling orders → email "send the confirmation", the orders service announces "order confirmed" and email reacts. Modeling it as an event keeps the producer from knowing who consumes it — add a second reactor (loyalty points, analytics) and the producer doesn't change. So a cross-service command collapses into the async path above: a subscriber's Receiver.On runs the same pipeline.Handler an HTTP route would, and the event DTO's ToCommand() is where the event becomes a local command inside the consumer. The imperative verb (InsertUser, SendEmail) still exists — but as B's internal detail, never as a contract between A and B. The genuinely-rare case where you do want a directed imperative (an explicit saga orchestrator, a "refund transaction X" addressed to one actor) travels the same integration-event path.

The read-side path and the event path share one spine. An external JoinUpstream embed is not a parallel universe to integration events — the upstream collection it reads is itself materialized by the framework consuming an event stream. "Read another service's state" and "react to another service's event" are two consumer-facing surfaces over the same CDC backbone; the difference is whether you want the data projected locally or a handler invoked.

Cache is orthogonal to all four — a cross-cutting accelerator for the edge sync path (httpclient response cache) and read amplification, never a transport in its own right. (The gRPC plane deliberately has no response cache — no GET/no-store vocabulary; heavy reads belong to the local projections above.)

The rule of thumb, in one line: sync internal → gRPC; sync external → httpclient; async facts/reactions → integration events; async view composition → UpstreamSubscription below. Everything else on this page is the detail of the fourth path.
