gRPC

The framework exposes the same application handlers REST and GraphQL consume through a gRPC surface served with Connect (connectrpc.com): one net/http endpoint on a dedicated listener that speaks three protocols — gRPC, gRPC-Web and Connect's JSON/HTTP mapping (plain curl-able POSTs). A feature opts in by implementing bootstrap.GRPCFeature and mounts generated Connect service handlers on the framework-built registry (Deps.GRPCRegistry); the framework provides the wrapper that adapts any pipeline.Handler to the generated interface, the server interceptor chain, and the notification-envelope mapping to google.rpc details.

Which channel? This plane is the default for synchronous communication between omnicore services — sync external goes through httpclient, async facts through integration events, async view composition through UpstreamSubscription. The full decision matrix lives in Service-to-service.

gRPC is its own web surface. Like GraphQL, it never goes through openapi.Mount/MountRaw, never appears in the Swagger document, and is not policed by the REST route scans. It also never shares the Fiber listener — Fiber is fasthttp-based and cannot host HTTP/2 services, so the surface runs on its own address (yaml grpc.addr, default :9090; h2c without TLS so the gRPC protocol works in dev). The only thing shared with the other surfaces is the application-layer handlers the wrappers dispatch to. See Handler invariance.

Contracts are hand-written

The .proto file is the designed, versioned contract — the primary reason this surface exists. There is no DTO→proto generator: deriving the contract from internal DTOs would re-invert the discipline to code-first, and field-number stability (the one protobuf rule that must be deliberate) cannot be owned by reflection. The quality gate is buf lint + buf breaking in CI. Codegen uses protoc-gen-go + protoc-gen-connect-go only — the classic protoc-gen-go-grpc stubs are 100% dead code under Connect and must not be generated.

Declare command fields optional (proto3 explicit presence): absent and zero-value stay distinct on the wire, mirroring the JSON body semantics — this is what the strict-presence check and presence-aware PATCH mappers build on.

Regenerating the stubs

Codegen is a plain protoc invocation with the two blessed plugins — there is no buf.gen.yaml and no //go:generate. buf is present only as the CI quality gate (buf lint + buf breaking), never as the generator. Install the plugins once (they land in ~/go/bin); pin them to the module versions in go.mod so the committed output never drifts on a re-run: 

go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.11        # tracks google.golang.org/protobuf
go install connectrpc.com/connect/cmd/protoc-gen-connect-go@v1.20.0     # tracks connectrpc.com/connect

A consumer regenerates its own service stubs from its .proto contracts. The reference service ships the canonical script at proto/generate.sh — one protoc call emitting both file kinds (*.pb.go from protoc-gen-go, *.connect.go from protoc-gen-connect-go) into a committed proto/gen/ tree. The second -I, into the framework checkout, is what resolves the shared read-side contract (omnicore/v1/query.proto): 

protoc \
  -I . \
  -I ../../omnicore/web/grpc/proto \
  --go_out=.. --go_opt=module=github.com/acme/my-service \
  --connect-go_out=.. --connect-go_opt=module=github.com/acme/my-service \
  users/v1/users.proto

The shared components live in the framework (web/grpc/proto/omnicore/v1/query.proto) and their Go is generated there, into web/grpc/pb, never in the consumer. That file is message-only (no service), so it needs protoc-gen-go alone — no Connect stubs: 

# from the framework module root
protoc -I web/grpc/proto \
  --go_out=. --go_opt=module=github.com/ClaudioSchirmer/omnicore \
  omnicore/v1/query.proto

Generated Go is committed — dependency-free and importable without a build step (in the reference service it sits outside internal/ precisely so both the web and infra layers, and other teams copying the contract, can import it). Regenerate only when a .proto changes; a diff in the generated tree that no .proto edit explains is a plugin-version drift, not a contract change.

Attaching handlers — reg.Register + the constructor family

Attachment is a constructor family producing a Procedure, registered on the surface's single registry, one declarative call per RPC. The family speaks the SAME vocabulary as REST and GraphQL — CommandWithBody (create), CommandWithBodyID (update: body + id, SetPathID injected after ToCommand), CommandByID (archive/delete: id only), QueryWithParams (list) and QueryByID (get one) — and consumes exactly the REST Spec ingredients: the same Request DTO (its ToCommand/ToQuery seat) and the same Response{}.FromResult projection — on the read side func(TResult) R, the identical seat the REST, export and GraphQL constructors take. The pb message types ride as explicit type parameters (message VALUE types — Go cannot infer them from a procedure string); the id extractor is the generated getter passed as a method expression, e.g. (*usersv1.ArchiveUserRequest).GetId. 

reg.Register(fwgrpc.CommandWithBody[usersv1.CreateUserRequest, usersv1.CreateUserResponse](
    usersv1connect.UsersServiceCreateUserProcedure,
    requests.InsertUserRequest{},                  // the SAME DTO the REST POST binds → ToCommand
    requests.InsertUserResponse{}.FromResult,      // the SAME projection the REST POST renders
    &handlers.SharedBaseInsertCommandHandler[…]{Repo: repo},  // the SAME handler REST uses
    fwgrpc.RequirePermission("users:write")))

The framework crosses the pb ↔ DTO boundary mechanically. At Register time (boot) it compiles a bridge plan: proto fields match DTO fields by case- and underscore-insensitive name (user_name ≈ userName ≈ UserName, id ≈ ID; json:/query: tags honored, and where an embedded struct and the outer struct declare the same name the outer one wins — the field encoding/json itself binds), recursing into nested messages and repeated fields, presence-aware (an absent proto3 optional lands as a nil pointer — the JSON absent-vs-set distinction), google.protobuf.Timestamp ↔ time.Time. A request field the DTO cannot receive, or a response field the DTO never fills, ABORTS BOOT — the wire contract never carries a silently dead field. fwgrpc.Alias("wire_field", "GoField") declares the exceptional pairing.

The two JSON dialects are reconciled for you. The bridge runs on protojson in one direction and encoding/json in the other, and they agree on every scalar form but one: the proto3 JSON mapping renders 64-bit integers (int64, sint64, sfixed64, uint64, fixed64) as quoted strings, while encoding/json wants a bare number for a numeric Go field. The compiled plan marks those paths and unquotes them on the way in — scalar, repeated and nested alike — carrying the digits as a raw literal, so a value beyond 253 (money in minor units, a snowflake id) crosses exactly. The consequence is the point: you declare money once, as int64, and the same DTO serves REST, GraphQL and gRPC — no gRPC-specific DTO, no json:",string" tag that would change what REST emits. Declaring the seat as a string is still valid and means what it says: the digits arrive as text. The way out needs no inverse — protojson accepts the bare number encoding/json writes.

Three consequences worth knowing. An enum travels as its member NAME, so its DTO seat is a string — pairing one with a numeric seat on a REQUEST aborts boot (on a response it is accepted, since protojson takes a number for an enum). A value that is not a legal 64-bit integer on the wire — text, fractional, out of range — still rejects as SchemaViolationNotification/INVALID_ARGUMENT; the exponent form ("1e3") is legal proto3 JSON and normalizes to 1000. And a non-finite float (NaN, Infinity, -Infinity, which the mapping also renders as strings) is the one gap that CANNOT be closed — JSON has no literal for them, so encoding/json neither reads one into a float field nor writes one back. The bridge rejects it naming the field and the value; a contract that genuinely must carry one belongs to a MountRaw procedure.

Promoted DTO fields follow encoding/json's collision rules. A name declared both on the struct and on an embedded one binds the SHALLOWER field — the one the codec fills. Two equally deep promotions are ambiguous and the codec fills neither, so the bridge treats that name as unbindable: the proto field that wanted it then fails the "no counterpart" check and aborts boot, rather than binding a seat that would silently stay at its zero value. Semantic transformation (computed fields, enum ↔ domain vocabulary, combining/splitting) stays where it always lived: ToCommand, ToQuery and FromResult. A contract whose shape genuinely cannot mirror DTOs is a MountRaw procedure (a hand-written Connect handler — the same seam the transport fixtures use).

  • fwgrpc.RequirePermission("users:write") is the Layer-1 permission gate — the twin of fwopenapi.RequirePermission and fwgraphql.RequirePermission: enforced against Identity.HasPermission under auth.authorization.enabled, inert otherwise (annotate ahead of the operator flip). Rejection is PERMISSION_DENIED carrying the canonical MissingPermissionNotification envelope (field permission).
  • fwgrpc.Strict("name", "kind") is the FullBody sibling: every named field must be PRESENT on the wire (protoreflect over proto3 optional presence); missing ones reject with the same RequiredFieldNotification / SemanticSchema envelope the REST strict-body check emits.
  • CommandByID shapes are enforced at boot: the request carries only the id field and the response is an EMPTY message (the 204 sibling) — a byID contract that answers with data is a CommandWithBody-family shape.
  • A request-side bridge failure (wire data the DTO cannot carry) is a wire-contract violation → SchemaViolationNotification (INVALID_ARGUMENT), mirroring the REST body-parse rejection; a ToCommand/ToQuery error carrying domain notifications keeps its own semantics; a response-side bridge failure is a server bug and stays an opaque INTERNAL.
  • Every constructor accepts any pipeline.Handler — auto and hand-written application handlers ride identically; there is ONE attachment API. Registering per procedure is exactly what the generated New<Service>Handler does internally, so generated clients, the gRPC protocol and the reflection service work unchanged.

Registration and serving

A feature declares MountGRPC and mounts its services on the framework-built registry — the GraphQL pattern applied to gRPC (the framework discovers the feature, builds the registry, and passes it in): 

// on the same feature struct that carries Mount / Views
func (f *UsersFeature) MountGRPC(reg *fwgrpc.Registry, d bootstrap.Deps) {
    reg.Register(fwgrpc.CommandWithBody[usersv1.CreateUserRequest, usersv1.CreateUserResponse]( … ))
    // … the rest of the UsersService constructors …
}

// Wire declares only the feature — no registry construction, no GRPC field on Wiring:
return bootstrap.Wiring{ …, Features: []bootstrap.Feature{users} }

With at least one GRPCFeature present, bootstrap builds the registry (Deps.GRPCRegistry), then injects the runtime policy from the yaml grpc: block and serves it: addr (default :9090), certFile/keyFile (both-or-neither; without TLS the listener is h2c), reflection (serves gRPC server reflection for the mounted services), requestTimeoutSeconds (the DEADLINE_EXCEEDED sibling of http.requestTimeoutSeconds; composes with the client's protocol deadline — earlier wins), and publicProcedures (the auth bypass list, e.g. "/users.v1.UsersService/Health"). The listener joins the coordinated graceful-shutdown drain as its own stage (grpc), by explicit dependency like every other stage.

Interceptor chain

Outermost → innermost, mirroring the inbound Fiber middleware:

  1. Recovery — a panic becomes an opaque INTERNAL (never leaks the panic value).
  2. AppContext — per-RPC configuration.AppContext from metadata: X-Request-ID → ctx.ID (falls back to the httpclient's threadID key, then a fresh UUID; always echoed on the response), Accept-Language → ctx.Language. The RPC context (protocol deadline included) is the cancellation parent. With the http tracing instrument enabled, an inbound server span continues the W3C traceparent and the correlation-id bridges to the trace id, exactly like the HTTP surface.
  3. Auth — the gRPC shell over web/authcore, the transport-neutral JWT core EXTRACTED from the Fiber middleware: one validation (JWKS/PEM key source, alg/iss/aud pinning, leeway, the optional external revocation check), two transport shells. Bearer from the authorization metadata → Identity on the AppContext; failures reject with the same MissingAuthorization/InvalidToken/ExpiredToken notifications (UNAUTHENTICATED) and the same tenant gate (TenantMissingNotification → PERMISSION_DENIED). Enabled by auth.mode: jwt — the same yaml switch as REST.

Internal-plane posture — grpc.auth.mode

The gRPC plane exists for trusted internal communication — the synchronous sibling of the integration-events posture (the broker sits on a private network, no per-message auth). The listener therefore has its own security posture, independent of the edge:

  • inherit (default) — the global auth: block governs, exactly like the HTTP surface. Zero migration.
  • internal — the trusted plane: a call WITHOUT a bearer passes as an anonymous call (the framework's existing vocabulary — audit actor: "anonymous", like public routes and background jobs). Trust = the private network (NetworkPolicy / cluster isolation — a deliberate, documented choice, the same premise the broker plane makes).
  • mtls — internal plus cryptographic caller proof: the listener requires a client certificate from the internal CA (grpc.clientCAFile + the TLS pair); an anonymous call carries a synthetic Identity from the certificate (Subject = SAN), so the audit trail names the calling service.
A forwarded bearer is ATTRIBUTION, not an entry credential. On the internal plane the caller decides per upstream (grpcClient auth: {mode: forward} or omit): with a bearer, signature/issuer/audience are verified locally (cached-JWKS crypto, microseconds) and the Identity populates — an expired-but-authentic token still passes, carrying the user who entered the main door plus a synthetic attribution: "stale-token" claim on the audited identity; a forged token rejects (lying attribution is worse than none). Two structural guarantees: the tolerance NEVER reaches the main door (the edge keeps its own strict validator), and attribution never calls the external validator (Keycloak introspection belongs to the edge). RequirePermission gates PASS on anonymous internal calls — the posture is the trust declaration, and what an internal chain may do is the flow designer's responsibility; a forwarded user is evaluated normally.

Kubernetes topology and connection recycling

Real-world exposure: one k8s Service carries both ports; the Ingress/LoadBalancer routes only :8080; :9090 stays cluster-internal (DNS users.<ns>.svc:9090 as the grpcClient baseURL) with a NetworkPolicy as the internal mode's wall. kube-proxy balances per NEW connection, and keep-alive clients hold pipes — so the producer recycles them: grpc.idleTimeoutSeconds (default 120: above the Go client's 90s idle so the client closes first — no reuse race; below NAT/conntrack floors ~350s — no zombie pipes) closes idle keep-alives, callers re-dial transparently, traffic redistributes and scale-up pods join. One producer knob protects against every untuned consumer. High-concurrency callers can additionally tune their own side with the optional grpcClient.services.<name>.pool block (maxIdleConnsPerHost, connMaxLifetimeSeconds — a background sweep recycling the caller's idle pipes).

Read-side criteria — the shared omnicore/v1/query.proto

List RPCs are per-view typed request messages composed from shared framework components (web/grpc/proto/omnicore/v1/query.proto, generated Go in web/grpc/pb): PaginationRequest (first/last/after/before/only_total/include_archived/search — the same reserved keys the REST query string speaks, snake_cased; every field is proto3 optional, so PRESENCE and value separate exactly as on the query string — an explicit only_total: false / include_archived: false still requires the DTO declaration and stays a no-op, the ?onlyTotal=false semantics), repeated OrderByField (conventional field name order_by, the ?orderBy= sibling), a google.protobuf.FieldMask fields (the ?fields= sibling), and the typed operator wrappers — StringFilter (the full 12-operator REST vocabulary, case-insensitive variants included), Int64Filter/DoubleFilter/TimestampFilter (eq/ne/in/nin/gt/gte/lt/lte) and BoolFilter (eq/ne). A filter field carries repeated conditions that AND-combine (the proto sibling of ?age.gte=18&age.lte=65). The per-view filters message IS the allowlist — a field not declared there is not filterable, and buf breaking polices view changes.

Every control obeys the endpoint's Request DTO. The shared proto shows every control field — it cannot narrow per RPC — so the cut is enforced at RUNTIME by the same canonical gateway every surface runs (queryschema.ValidateControls): a control set on the wire without its query:"…" declaration on the Request DTO rejects as SchemaViolation → INVALID_ARGUMENT, with the error detail naming the missing declaration so the consumer reads the fix off the rejection. The directional rule (forward first/after × backward last/before, one direction at a time; last with no cursor = the LAST N of the set) and the only-total conflict matrix (only_total=true with any page-shaping control → onlyTotal[<key>]) reject identically on every surface. 

message UserFilters {
  omnicore.v1.StringFilter user_name = 1;
  omnicore.v1.StringFilter name = 2;
}
message ListUsersRequest {
  omnicore.v1.PaginationRequest pagination = 1;
  repeated omnicore.v1.OrderByField order_by = 2;
  google.protobuf.FieldMask fields = 3;
  UserFilters filters = 4;
}

The list response composes the mirror envelope: exactly one repeated items message plus omnicore.v1.PaginationInfo — the Relay connection vocabulary shared verbatim with the REST pagination block and the GraphQL pageInfo, snake_cased: total_count, end_cursor, start_cursor, has_next_page, has_previous_page. The cursors are WINDOW EDGES (echo them into PaginationRequest.before/after to walk). The framework locates both components BY TYPE, so field naming stays the service's choice — the convention is pagination, which also makes the Connect/gRPC-Web JSON form read exactly like the REST envelope: 

message ListUsersResponse {
  repeated User items = 1;
  omnicore.v1.PaginationInfo pagination = 2;
}

QueryWithParams converts all of it for you. At boot the constructor discovers the components on the request descriptor and binds each filter field to the SAME Request DTO the REST list consumes — the DTO's filter: tags are the operator allowlist on both wires: an operator outside the leaf's tag rejects as SchemaViolation (INVALID_ARGUMENT), exactly the REST 400, and a proto filter with no tagged DTO leaf aborts boot. fields and order_by speak wire names (the item message's proto fields, snake_case — FieldMask's canonical form; protojson converts the JSON camelCase spelling for you), resolved against the response projection's Response DTO — an undeclared path fails as SchemaViolation and never reaches the reader, where an unresolved spelling would pass through as a physical column and bypass ToCriteria overlays such as Restrict. The assembled INPUT criteria (filter keys = Go field paths) then reaches the Request DTO's ToQuery(criteria) — the same one-liner the REST wrapper calls — and the query type's ToCriteria(ctx) keeps applying identity overlays on top, exactly like every other surface. 

// Type params: [PB, RPB, TReq, TQ, TResult, R] — only the two pb message
// types are spelled; TReq comes from the sample, TResult/R from the
// response projection and TQ from the handler.
reg.Register(fwgrpc.QueryWithParams[usersv1.ListUsersRequest, usersv1.ListUsersResponse](
    usersv1connect.UsersServiceListUsersProcedure,
    requests.FindUsersByParamsRequest{},                    // filter: tags = the operator allowlist
    requests.FindUsersByParamsResponse{}.FromResult,        // mask/sort vocabulary + wire projection
    &handlers.FindByParamsQueryHandler[*appqueries.FindUserByParamsQuery,
                                       appqueries.FindUsersByParamsResult]{
        Reader: d.ViewReader, View: view.Name()},
    fwgrpc.RequirePermission("users:read")))

// The by-id twin adds the generated id getter after the procedure:
reg.Register(fwgrpc.QueryByID[usersv1.GetUserRequest, usersv1.GetUserResponse](
    usersv1connect.UsersServiceGetUserProcedure,
    (*usersv1.GetUserRequest).GetId,
    requests.FindUserByIDRequest{},
    requests.FindUserByIDResponse{}.FromResult,
    &handlers.FindByIDQueryHandler[*appqueries.FindUserByIDQuery,
                                   appqueries.FindUserByIDResult]{
        Reader: d.ViewReader, View: view.Name()},
    fwgrpc.RequirePermission("users:read")))

The read constructors take the projection as responseProjection func(TResult) R: QueryWithParams's handler returns queries.PageOf[TResult] and QueryByID's returns TResult, and the framework maps each value through that seat before the pb ↔ DTO bridge runs. The bridge, the criteria plan and the FieldMask/sort vocabulary are all expressed over R — so the pb contract mirrors the same Response DTO the REST body, the CSV/XLSX columns and the GraphQL node render.

One emitter, two wires. Conversion delegates to queryschema.ApplyFilterValues — the same clause emitter the REST/OpenAPI/GraphQL path uses (unit-locked byte-identical), so operator semantics cannot drift. Proto's repeated values ride verbatim into list operators, so the gRPC plane has no comma-in-value limitation; Timestamp values convert to the RFC3339 string form the REST string-leaf coercion produces. A hand-rolled MountRaw list reuses the same core via fwgrpc.NewCriteria() (Fields allowlist + Page/OrderBy/FieldMask/typed filters + Build) — the raw path never re-implements operator emission.

Computed Response fields on the proto wire

A Response field declared computed:"Src1,Src2" carries no column: the Query's FromQueryResult derives it after the read from the named Result fields. The pb contract still exposes it like any other item field — it is selectable — but the two controls that reach the store are adjusted, so the proto wire behaves exactly as the REST one:

  • read_mask pushes the SOURCES. A mask path naming a computed field resolves through the same vocabulary allowlist and then substitutes its declared sources into the projection; the computed path itself never goes down, because no column would resolve it. Sources the Response does not declare are read and dropped at the wire boundary, exactly as on ?fields= — and a source that IS a declared Response field is blanked on each Result before projection when the mask did not name it, so a mask naming only the computed field answers the computed field alone, never its ingredients.
  • order_by is refused. Ordering happens in the store and the keyset cursor is built from stored ordering values, so a derived value is not expressible. The refusal is INVALID_ARGUMENT carrying ComputedFieldNotSortableNotification — translated per the request language, with one google.rpc.BadRequest field violation per offending entry. The field name is the sort entry verbatim as the proto spelled it (e.g. label), not REST's orderBy[label] bracket form: order_by is already a typed field on the request message, so the prefix would name nothing on this wire.

On the Auto path the cut is compiled at Register from the Response DTO — nothing to wire per call. A hand-rolled MountRaw list gets the same parity by declaring the map on the raw builder beside its Fields allowlist: 

crit, err := fwgrpc.NewCriteria().
    Fields(wireToGo).                                        // the mask/sort vocabulary
    ComputedFields(map[string][]string{"label": {"Code", "Name"}}). // wire → Result sources
    Page(msg.GetPagination()).
    OrderBy(msg.GetOrderBy()).
    FieldMask(msg.GetFields()).
    Build()

A nil map keeps the previous behavior, so a raw procedure with no computed field declares nothing. After Build, b.HiddenComputedSources() names the Result Go paths the mask read only to feed a computed field — the raw handler blanks them on each Result before its own projection (queryschema.BlankResultPaths), which is exactly what the Auto path does, so a hand-mounted list keeps the mask-shapes-the-wire parity.

The outbound side — infra/grpcclient

The write half of this section's story is the server; the read-from-elsewhere half is infra/grpcclient — the outbound toolbox, sibling of httpclient for the gRPC plane. One Client is built at boot from the yaml grpcClient: block and exposed on Deps.GRPCClient; per service it carries a pooled HTTP client and a connect interceptor chain, outermost → innermost: correlation (threadID/X-Request-ID from the AppContext — the framework convention: the AppContext IS the call ctx) → tracing (client span + W3C inject, gated by the httpclient instrument) → auth (forward re-sends the inbound caller's bearer, failing loudly when absent; static attaches a fixed token) → idempotency (UUIDv7 on a configurable header, generated once per logical call and STABLE across retry attempts) → deadline (per-service default when the caller set none; becomes the protocol timeout the server observes) → logging (one slog line per call: service, procedure, code, elapsed) → retry (Connect-code triggers — default ["unavailable"] — plus transport dial errors; backoff curves shared with httpclient via infra/resilience) → circuit breaker (per service+procedure state machine, also from infra/resilience — one implementation, two transports, semantics that cannot drift). 

grpcClient:
  defaults: { timeoutSeconds: 10 }
  services:
    users:
      baseURL: "http://users:9090"
      retry: { maxAttempts: 3, backoff: exponential-jitter, retryOn: ["unavailable"] }
      circuitBreaker: { enabled: true, failureThreshold: 5, successThreshold: 2, openForMS: 3000 }
      auth: { mode: forward }
      idempotency: { enabled: true }
users, err := grpcclient.For(deps.GRPCClient, "users", usersv1connect.NewUsersServiceClient)
res, err := users.GetUser(appCtx, connect.NewRequest(&usersv1.GetUserRequest{Id: proto.String(id)}))

Application handlers never import the package — the adapter lives in the service's infra/, exactly like httpclient consumers. Auth providers shipping now: forward and static; the oauth2 family follows once its acquisition core is extracted transport-neutrally.

What deliberately does not cross over

  • CSV/XLSX export — file-download semantics, REST-only.
  • Streaming RPCs — the surface is unary; async flows stay on the broker (service-to-service / integration events).
  • httpclient's cache and HMAC signing (outbound side) — the gRPC protocol has no GET/no-store vocabulary, and there is no official request-signing scheme in the gRPC/Connect world; service-to-service authenticity on this plane is mTLS (grpc.certFile/keyFile + client certs). Third parties that mandate a signing scheme are HTTP parties — call them via httpclient.
