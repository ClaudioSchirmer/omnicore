Token issuance

The framework can mint its own JWT access and refresh tokens, so a service can be its own IdP instead of depending on Keycloak/Auth0/Entra — while every service's inbound authentication (the middleware, authcore.Validator) stays exactly as it is today. Issuance is a new, additive surface that happens to produce standards-compliant JWTs; it is never a prerequisite for validation, and it works with any IdP a deployment already trusts.

The framework ships methods, never HTTP endpoints. POST /auth/login, POST /auth/refresh, an introspection endpoint — all of it is built by the consuming service on top of Issuer. The one exception is the JWKS document itself: publishing a public key is infrastructure, not a business endpoint, and it follows the same opt-in, self-mounted pattern as GraphQL/OpenAPI.

Validate vs. issue — two independent surfaces

Nothing about inbound validation changes. A token minted by Issuer.Issue must validate through the unmodified Validator, using a Validator built from the issuer's own published JWKS and zero issuer-specific code paths — that round-trip is the framework's own test for this feature. Consumers keep choosing between the two shapes auth.jwt already supports:

  • Self-validation — auth.jwt.jwksUrl points at the issuer's JWKS document; nobody exchanges a shared secret, the public key is enough.
  • Validate-against-issuer — auth.jwt.externalValidator calls an introspection endpoint the issuing service builds itself; the public key never has to touch the network at all.

No consumer service needs a framework change to accept a self-issued token — pointing either knob at an in-house issuer is configuration.

The Issuer

web/authcore.Issuer lives in the same package as Validator on purpose: the JWKS document it produces must be directly consumable by BuildKeyfunc in the same compile unit, so divergence between what's published and what's accepted is a compile-unit-local concern, not an integration surprise.

func NewIssuer(opts IssuerOptions) (*Issuer, error)

func (i *Issuer) Issue(ctx context.Context, req TokenRequest) (IssuedToken, error)
func (i *Issuer) JWKS() ([]byte, error)

func (i *Issuer) IssueWithRefresh(ctx context.Context, req TokenRequest) (IssuedToken, RefreshToken, error)
func (i *Issuer) RedeemRefreshToken(ctx context.Context, value string, claims map[string]any) (IssuedToken, RefreshToken, error)

TokenRequest.Claims is where groups, permissions, tenant_id, or any other RBAC shape ride — the framework never interprets it, that vocabulary belongs to the issuing service's own domain. Reserved claims (iss/aud/exp/iat/nbf/jti) are owned by the Issuer: supplying one in Claims is a rejected call, not a silent override.

Refresh tokens

Refresh tokens follow the pattern every mature IdP uses (Keycloak, Auth0, Okta): opaque, never a JWT, single-use, rotated on every redemption, with reuse detection. The Issuer owns that algorithm — it is security-critical logic that must not be copy-pasted per service — but not the storage:

type RefreshTokenStore interface {
    Save(ctx context.Context, rec RefreshTokenRecord) error
    Lookup(ctx context.Context, hash string) (RefreshTokenRecord, error)
    MarkUsed(ctx context.Context, hash string) error
    RevokeFamily(ctx context.Context, familyID string) error
}

The service supplies the implementation (SQL table, Redis, whatever fits) via Wiring.RefreshTokenStore; only a SHA-256 hash of the opaque value ever crosses this seam — never the raw secret, never claims. Reuse of an already-redeemed value revokes the entire family (the session and every token descended from it) and returns ErrRefreshTokenReused — the standard signal a stolen refresh token was replayed.

RedeemRefreshToken takes claims fresh from the caller at redemption time — the same shape Issue takes — so a permission revoked between logins reaches the mesh on the next refresh (minutes), not only on the next full login. A refresh token can only ever be redeemed at the issuing service — not by rule, but structurally: it is opaque, so no other process can even attempt to interpret it, and only whoever holds the RefreshTokenStore can look it up.

Key rotation

Keys carry a KeyState: KeyNext (published in the JWKS, not signing yet), KeyCurrent (published and signing — exactly one, enforced at construction), KeyPrevious (published, no longer signing, still validates tokens already in flight). This exists because of how the underlying JWKS client libraries behave: periodic refresh runs every hour, and a refresh triggered by an unknown kid is rate-limited to once per five minutes — so a key that starts signing before it is published can make the whole mesh serve 401s for up to five minutes.

Runbook for promoting a key, entirely a config change plus redeploy (no scheduler in the framework):

  1. Add the new key as next. It appears in the JWKS immediately; nothing signs with it.
  2. Wait the propagation window — conservatively 5+ minutes, or one refresh interval to be safe.
  3. Promote: next → current, old current → previous.
  4. After the longest access-token TTL has elapsed, drop previous.

Configuration

New auth.issuer: block, sibling of auth.jwt: (see the full yaml reference):

auth:
  mode: jwt
  jwt:                                    # VALIDATE — unchanged
    algorithms: [RS256]
    issuer: "http://auth"
    audience: "users-api"
    jwksUrl: "http://auth/.well-known/jwks.json"

  issuer:                                 # ISSUE — new
    enabled: true
    selfUrl: "http://auth"                # the `iss` this service signs with
    audience: ["users-api", "orders-api"]
    tokenTtlSeconds: 900
    maxTokenTtlSeconds: 3600
    refreshTokenTtlSeconds: 2592000        # 30 days; 0 or omitted disables refresh tokens
    keys:
      - kid: "2026-08-a"
        algorithm: RS256
        state: current
        privateKeyPem: "${JWT_SIGNING_KEY}"
      - kid: "2026-05-b"
        algorithm: RS256
        state: previous
        privateKeyPem: "${JWT_SIGNING_KEY_PREVIOUS}"
    jwks:                                 # OPT-IN — see below
      path: /.well-known/jwks.json

selfUrl is deliberately not named issuer — that word already labels the block — and is never inherited from auth.jwt.issuer: always explicit, since a service may issue without ever validating locally. When both blocks are configured on the same service, selfUrl must equal auth.jwt.issuer — a service that issues and validates cannot disagree with itself about who it is.

Signing material (privateKeyPem) is expected via ${ENV_VAR} substitution, the same operational convention every other secret in a microservice.<profile>.yaml follows (DSNs, API keys, …) — never a literal PEM block committed to the file. This is not machine-enforced: interpolation runs on the raw file text before the yaml is parsed, so by the time the config struct exists, a literal and a substituted value are indistinguishable.

JWKS route

Follows the same shape GraphQLConfig uses: no bare enabled bool, a configurable path with a sensible default, collision-checked against reserved framework routes. The block's presence on auth.issuer.jwks is the switch — absent means the public key never touches the network (validate-against-issuer only); present mounts GET <path> as a public route automatically (a JWKS document that required a bearer to fetch would be a contradiction — nothing could ever bootstrap trust in it). The service mounts nothing for it.

In-process revocation

authcore.TokenChecker is the same post-validation revocation seam the middleware already uses for auth.jwt.externalValidator — today reachable only by routing through HTTP. Wiring.TokenChecker plugs a direct Go implementation instead (e.g. consulting the same store a refresh-token family lives in, or a denylist), with no HTTP hop; it takes priority over externalValidator when both are set. The HTTP path stays available for the cross-process case (a different service checking this one's revocations) — this is the same-process fast path.

Security

  • Asymmetric only — RS256/ES256/EdDSA, enforced at construction; RSA keys under 2048 bits are rejected. Validators never hold signing material, only the issuing service does, and it holds a private key whose public half is safe to publish.
  • Every access token carries jti (random), iat, exp, iss. exp is never caller-controlled beyond maxTokenTtlSeconds.
  • Refresh tokens are opaque, single-use, stored only as a hash.
  • The signing key never appears in logs, the audit trail, or any error string — Issuer has no getter for it.
  • Issuer authenticates nobody. Issue/IssueWithRefresh mint for a subject the service already decided is authentic; the framework does not and will not verify passwords.

What stays in the consumer service

User/credential entity, password hashing, lockout and rate limiting, login UI, consent, account lifecycle, and every HTTP route — POST /auth/login, POST /auth/refresh, an introspection endpoint, whatever shape the service wants. All of it is domain, built with the normal scaffolding on top of Issuer's methods.

Multi-service topology

Per consumer service, the entire integration is configuration — no framework change:

auth:
  mode: jwt
  jwt:
    algorithms: [RS256]
    issuer: "http://users"
    audience: "orders-api"
    jwksUrl: "http://users/.well-known/jwks.json"
    # OR, for validate-against-issuer:
    # externalValidator: { url: "http://users/auth/introspect", ... }

Service-to-service calls need nothing new either: type: forward (see httpclient) propagates the end user's bearer for attribution, type: oauth2 with a service-built token endpoint covers machine-to-machine with the existing cache and 401 re-acquisition.
