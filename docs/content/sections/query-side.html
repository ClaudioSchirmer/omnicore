QueryHandler · CQRS

The QueryHandler is the processing unit for a read (GET), symmetric to the CommandHandler on the write side: Request → Query → Handler on the read path mirrors Request → Command → Handler on the write path. Reads come from MongoDB (a pre-composed view) and support dynamic filters, cursor pagination, sorting, field projection, and text search — all expressed as one transport-agnostic value, queries.ReadCriteria, and resolved through the queries.ViewReader port (ReadPage / ReadByID).

This page is the shared trunk of the read side: the concept, the end-to-end flow of a GET, the shape every read carries (ReadCriteria), the filter operator vocabulary, and the ToCriteria(ctx) seam where security overlays and field-level read authorization live. Everything here applies identically whether the route is wired through the framework's wrappers or hand-rolled — the two branches only differ in how the ReadCriteria gets assembled and how the result is projected:

  • Auto query handlers — the canonical path: declare the Request DTO allowlist + Response shape, get the wrapper that parses the query string, enforces the allowlist, assembles the criteria, calls the reader, paginates, and projects. Zero handler code.
  • Custom query handler — the same read built from scratch (a hand-written pipeline.Handler + explicit route wiring), for an alternate identifier (:email), a vendor-shaped envelope, or any wiring the wrapper does not cover. Same pipeline, same criteria, same projection — the escape hatch is for wiring control, not a poorer tier.

The end-to-end layer trace (wrapper → handler → ToCriteria → ViewReader → Mongo → envelope) lives in the Read lifecycle map.

What a read carries — ReadCriteria

Every read — list or by-id, auto or custom — is one value: queries.ReadCriteria. The Request DTO declares which parts of it the wire may set (the allowlist); the Query's ToCriteria(ctx) finalizes it; the handler hands it to ViewReader.ReadPage / ReadByID. Nothing below the application layer invents criteria — it is the single contract the read side passes around.

FieldCarries

Sort []SortFieldordered list of {Field, Desc} (Go field paths). From ?sort=.

The reserved control keys (?fields=, ?sort=, ?after=/?before=, ?limit=, ?search=, ?includeArchived=, ?onlyTotal=) and their edge cases are documented on the Auto query handlers page — the wrapper is where they are parsed and enforced. The two items below — the filter operator vocabulary and ToCriteria — are the parts shared verbatim by the custom path, so they live here on the trunk.

Filter operators

A filterable field declares the operators it accepts with the filter:"ops" struct tag on the Request DTO; the wire form is ?field.op=value (no suffix for eq). An operator outside the declared set is rejected with 400 SchemaViolationNotification. The same tag and the same vocabulary drive both paths — the auto wrapper (HandleQueryWithParams) and the custom parser (fwweb.NewQueryParser / fwweb.ParseCriteria) read it identically. 

// Operator constants — used in the filter tag (defined in web/queryschema/operators.go; re-exported as fwweb.Op* via web/operators_alias.go).
const (
    OpEq          = "eq"           // exact equality (the default — no .op suffix on the wire)
    OpNe          = "ne"           // inequality
    OpIn          = "in"           // in list (comma-separated)
    OpNin         = "nin"          // not in list
    OpGte         = "gte"          // ≥   (ordinal — no case-insensitive variant)
    OpLte         = "lte"          // ≤
    OpGt          = "gt"           // >
    OpLt          = "lt"           // <
    OpStartsWith  = "startswith"   // prefix      (case-sensitive)
    OpContains    = "contains"     // substring   (case-sensitive)
    OpIEq         = "ieq"          // case-insensitive equality
    OpINe         = "ine"          // case-insensitive inequality
    OpIIn         = "iin"          // case-insensitive in-list
    OpINin        = "inin"         // case-insensitive not-in-list
    OpIStartsWith = "istartswith"  // case-insensitive prefix
    OpIContains   = "icontains"    // case-insensitive substring
)

String operators come in case-sensitive and case-insensitive twins — the i prefix is the case-folded variant. The consumer declares whichever set the endpoint accepts (filter:"eq,startswith,icontains" = exact, prefix, and case-insensitive substring). The ordinal operators (gte/lte/gt/lt) have no i variant — case-folding is meaningless on comparisons.

Multiple operators on one field are AND-ed. When the wire delivers more than one operator for the same field (?age.gte=18&age.lte=65, ?name.startswith=Bob&name.icontains=ob), the clauses fold into a queries.MultiClause sentinel that MongoViewReader expands into a top-level $and — every declared operator is honored. A single operator stays the plain {field: value} shape so Mongo indexes remain usable.

Values are always escaped. User input feeding the regex operators (startswith/contains and their i twins) is passed through regexp.QuoteMeta, so ?name.contains=a.b*c matches the literal string a.b*c, never a pattern. The iin/inin operators emit a queries.RegexMatchList sentinel the reader expands into {$in:[bson.Regex,…]}.

ToCriteria(ctx) — overlays and field restriction

The Query owns ToCriteria(ctx) (ReadCriteria, error) — the read-side twin of the write side's ToEntity(ctx), and the only layer below the web boundary that may consume *AppContext. Both the framework's Auto handlers and a hand-written handler call it before hitting the reader, so this seam works the same on both paths. It does two jobs.

1. Security overlays. Layer identity-derived filters onto crit.Filter — multi-tenant scope, owner-only reads, business overlays. The keys are Go field names declared in the view TableSchema; the reader translates them to columns. Infra never pronounces a tenant or owner — it executes what the Query assembled.

2. Field-level read authorization — crit.Restrict(goFieldPath). Removes a field from the read entirely: it is not projected (never on the wire or the CSV/XLSX export, header included), not sorted by, not filtered on. The behavior depends on whether the request actively referenced the field:

Request referenced the field via…Restrict returnsEffect
nothing (passive — just not asked for)nilsilently omitted; nothing leaks
?fields=phone, ?sort=phone, or ?phone.eq=… (active)403 FieldAccessForbiddenNotificationfield scrubbed first, then the read is refused

Refusing the active reference (rather than silently ignoring the knob) is the honest answer and closes the inference leak a silently-dropped sort/filter would leave. The field is scrubbed from the criteria on both paths, so nothing leaks even on the 403. ToCriteria returning an error routes through pipeline.Run via errors.As with no special wiring — the carrier's SemanticForbidden becomes a 403. 

func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,
) (fwqueries.ReadCriteria, error) {
    crit := q.Criteria
    var err error

    // Field-level read authorization: a non-admin caller may not see Phone.
    // Active reference (?fields=phone / ?sort=phone / ?phone.eq=…) → 403;
    // passive → silently omitted. Infra stays authz-blind either way.
    if id := ctx.Identity(); id != nil && !id.HasPermission("users:admin") {
        err = crit.Restrict("Phone")
    }

    // Security overlay: scope every read to the requesting tenant.
    if id := ctx.Identity(); id != nil {
        if tenant, _ := id.Claims["tenant_id"].(string); tenant != "" {
            if crit.Filter == nil {
                crit.Filter = map[string]any{}
            }
            crit.Filter["TenantID"] = tenant
        }
    }
    return crit, err
}
The same ToCriteria(ctx) is consumed by the Auto FindByParamsQueryHandler and by any hand-written handler — so tenant scoping and field restriction never require going manual. Overlays also compose with cursor pagination: cursors are stamped from — and validated against — the post-ToCriteria context at the reader, so a security filter added here never invalidates ?after=/?before= navigation. Going manual buys an arbitrary identifier (e.g. :email) or a bespoke envelope, not the authz seam. See Authorization for the three-layer model.

Composition types on the read side

A read-side document can be more than the flat projection of one table. These are the composition kinds a consumer can read from — each summarized here by what the reader gets and how fresh it is, with the full contract in its canonical section. All of them are served through the same ViewReader port, the same wrappers, the same filter vocabulary.

Aggregate projection The aggregate's own data — root fields flat, siblings merged flat, 1:N children nested — derived automatically from the TableSchema; nothing is declared on the view beyond the schema. Materialized at write time (CDC → SyncEngine compose) TableSchema
Embed / EmbedMany An EXTERNAL collection (an upstream projection or a derived local view) nested into the document under a declared segment, joined by FK at compose time. Materialized at write time; recompose-ripple on source changes TableSchema

The three view constructors — and the join each speaks

Every read model is declared through one of three constructors. Two materialize (a CDC-fed Mongo collection kept in sync by the SyncEngine); the third joins at read time and stores nothing:

ConstructorRootWhat it projectsMaterialized?
query.View(name) A regular table — an aggregate root or a role table. The aggregate's own data, decomposed automatically from its TableSchema — root fields flat, .Sibling tables merged flat, 1:N .Child children nested — plus any Embed/EmbedMany of EXTERNAL sources. Yes — write time
query.SharedBaseView(base, name) A shared base (core.NewSharedBase). The all-in-one identity: base fields flat, base children nested, one sub-document per .Role(...) (each role's siblings flat, children nested) — plus any Embed/EmbedMany of EXTERNAL sources. Yes — write time
query.ComposedView(name) A Primary(...) view — regular OR shared-base. The primary read exactly as a direct read would, enriched at read time with Link/LinkMany legs — internal views AND external collections, mixed freely. No new collection. No — read time

Why embeds are external-only. An aggregate's own children, siblings and shared base already decompose out of the declarative schema, so the two materialized constructors reach OTHER data only through an external Embed/EmbedMany — a write-anchored (internal) embed source is a fatal boot error. Joining an internal view that already exists is precisely what the read-time ComposedView adds. That is why the join vocabulary splits by constructor, and why one family has a single source constructor while the other has two:

Constructor(s)Method2nd argBuilt from — and reach
View / SharedBaseViewEmbed(seg, src) — 1:1*Sourcequery.FromSchema(core.NewExternalSchema(…)) — EXTERNAL only; FK on the parent.
View / SharedBaseViewEmbedMany(seg, src) — 1:N*Sourcequery.FromSchema(core.NewExternalSchema(…)) — EXTERNAL only; FK on the child schema.
ComposedViewLink(seg, leg) — 1:1*Legquery.JoinView(view) (INTERNAL registered view) or query.JoinUpstream(core.NewExternalSchema(…)) (EXTERNAL); FK on the primary.
ComposedViewLinkMany(seg, leg) — 1:N*LegSame two constructors; FK on the leg (leg.fk → primary._id); OrderBy + MaxLinkManyLimit apply.

Both families share .FK(column) — the FK always points at the other side's PK/_id; the 1:1 side that holds it is the parent/primary, the 1:N side is the child/leg — and .As(goSegment), mandatory on every external source (a type-less schema has no Go type to derive the segment from). Note the symmetry: FromSchema and JoinUpstream take the SAME thing (a core.NewExternalSchema); only JoinView has no embed counterpart, because embedding an internal view would duplicate data the schema already projects. The embed surface is detailed under TableSchema; the Link surface is below.

ComposedView — query-time composition

A ComposedView is not a view like the others. It is never materialized, never synced, never rebuilt: there is no Mongo collection, no Version(n), no schema-evolution entry, no recompose ripple. It is a read-time orchestration over views that already exist: a read against the composed name reads the primary view exactly as a direct read would, then enriches each returned item with data fetched by key, in batch, from the linked views (the legs) — the NoSQL-idiomatic join, resolved in code, not $lookup. Nothing to invalidate, nothing to keep in sync; the cost moves to the request path (one extra round-trip per leg per page, not per document).

It exists to give the developer JOIN power over views that share no write-side declaration — two aggregates connected by nothing but a foreign key — without hand-writing two reads and a merge loop, and without creating yet another materialized projection.

Declaring one

// infra — same package and vocabulary as View / SharedBaseView / FromSchema.
func GadgetFullView() *query.ComposedViewDefinition {
    return query.ComposedView("gadgets_full").
        Primary(GadgetView()).                      // drives EVERYTHING row-shaped

        // 1:1 — the PRIMARY holds the FK (gadgets column "id" → the upstream
        // doc's _id). External leg: a locally materialized upstream collection,
        // described by its core.NewExternalSchema. Null segment when absent.
        Link("upstreamMirror", query.JoinUpstream(GadgetUpstreamMirrorSchema()).
            FK("id").
            As("UpstreamMirror")).                  // Go segment — mandatory on external legs

        // 1:N — the LEG holds the FK (gadget_notes column "gadget_id" → the
        // gadget's _id). Internal leg: any registered view. Empty array when absent.
        LinkMany("notes", query.JoinView(GadgetNotesView()).
            FK("gadget_id").
            As("Notes").
            OrderBy("text").                        // deterministic segment order (default: _id asc)
            MaxLinkManyLimit(3))                    // per-parent ceiling: link → yaml → 100
}

// Registration — the bootstrap opt-in, mirroring ReadableFeature:
func (f *GadgetFeature) ComposedViews() []*query.ComposedViewDefinition {
    return []*query.ComposedViewDefinition{GadgetFullView()}
}

One join vocabulary — PK/FK only. Every relationship declares one FK(column); the FK always points at the other side's PK/_id; who holds it follows the multiplicity: on a 1:1 Link the primary holds it (primary.fk → leg._id), on a 1:N LinkMany the leg holds it (leg.fk → primary._id). This is the same rule the whole schema system speaks (TableSchema.FK for children, Source.FK for embeds). The builder speaks physical columns, like Indexes and every other view declaration.

BuilderMeaning
ComposedView(name)The read-side identity — goes wherever a view name goes. Must not collide with any view or composed name.
Primary(view)Exactly one, always an internal registered view (regular or shared-base). Its MaxLimit, indexes, text search, archived gate apply unchanged.
Link(segment, leg)1:1 — sub-document under segment; explicit null when absent.
LinkMany(segment, leg)1:N — array under segment, in the declared order, capped per parent; empty array when absent.
JoinView(view)Internal leg: any registered view — it arrives exactly as a direct read of that view would (children, embeds, roles, archived strip included).
JoinUpstream(schema)External leg: a locally materialized UpstreamSubscription collection described by its NewExternalSchema. A leg NEVER reads another service's live storage — materialize first, then compose.
FK(column)The join column (see the multiplicity rule above). Mandatory on every leg.
As(goSegment)The Go segment criteria/Responses refer to. Mandatory on external legs; optional override on internal ones (default: the leg root type name, pluralized on a LinkMany).

At the ceiling the segment truncates silently and deterministically: "the first N in the declared order" — payload protection, not validation. The full set lives on the leg's own view, paginated.
Fatal boot, never silent. Every declaration exceeding the contract aborts the boot with an explanatory message: unknown FK/OrderBy columns, an unregistered primary or leg view, an external leg without a matching UpstreamSubscription, a LinkMany FK without a covering index on the leg view, a segment colliding with a primary field or another segment, OrderBy/MaxLinkManyLimit on a 1:1 link, .Desc() without OrderBy, a composed name shadowing a view. Depth is 1 by design: a leg is a plain view (as deep as its own materialization goes), never another composition.

The core rule — the primary drives selection

Pagination, sort, ?search=, total and cursors belong exclusively to the primary view. Legs only enrich items already selected — they never add, remove or reorder primary rows. Keyset pagination is a tuple over one collection, sealed by a context hash; the moment a leg could decide which rows appear, pages would underfill with unbounded refill work and total would lie. Everything below derives from this:

  • Row-selecting filters target the primary — full 16-operator vocabulary via the same filter:"ops" allowlist, unchanged.
  • Segment filters never select rows. A filter addressed to a leg segment (?notes.text=b, declared as a nested group on the Request DTO whose Go field name matches the segment) filters what enters the segment — which documents appear in the array, whether the 1:1 sub-document attaches — never which primary items return. Segment filter paths resolve at every level of the linked document, with the same operators a direct read of that view would accept.
  • Sort targets the primary only. A ?sort= path into a segment is rejected with 400 SchemaViolationNotification — segment order is declared on the link, deterministically, precisely so truncation and array order never depend on wire input.
  • LEFT join always. 1:1 → explicit null; 1:N → empty array. There is no INNER mode — "require a match" would be a row-selecting filter in disguise.
  • total, onlyTotal, has_next/has_prev and both cursors are the primary's, byte-for-byte. ?onlyTotal=true short-circuits before any leg is fetched.
  • Cursors bind to the composed listing context — segment filters included (they shape the page's content). Changing any filter, row or segment, means requesting page 1 of the new context; a stale cursor is rejected with 400, never silently honored.

Read cost model — use it consciously

A composed read trades storage for request-path work, so its cost must be understood BEFORE declaring one — the framework bounds every axis, but the developer chooses the shape. With p = the page size (≤ the resolved maxLimit, the same universal ceiling every read obeys — plain, shared-base or composed) and c = a link's resolved MaxLinkManyLimit:

StepMongo queriesDocuments movedWhy it is bounded
Primary page O(1) — one find (+ one count) ≤ p maxLimit cascade; identical to a plain view read.
Each 1:1 leg O(1) — ONE $in batch ≤ p (one per distinct key) The page's FK values, deduplicated, nulls skipped; each key is a point lookup on the leg's _id — uniqueness caps the result at one doc per key. A batch of point lookups in one round-trip, never a scan.
Each 1:N leg O(p) — one indexed subquery per page parent, 8 in flight ≤ p × c Each subquery is find({fk: parent}) + declared order + LIMIT c. The per-parent ceiling is what forbids a single global-limit $in here — Mongo limits are per QUERY, not per group, so one fat parent would starve the others' segments.
By-id read O(1) — 1 + one fetch per leg ≤ 1 + legs × c The page has one parent.

Total per request: 1 + (#1:1 legs) + (#1:N legs × p) queries, every one index-driven, moving at most p + p·(#1:1) + p·c·(#1:N) documents. There is no unbounded axis: no query without a LIMIT, no N+1 that grows with the dataset (the query count grows with the PAGE, which you cap), no fan-out beyond the declared ceilings. What keeps each promise honest:

  • The 1:N FK must be index-covered — enforced at boot. Without an index whose first key is the FK column, each per-parent subquery is a full collection scan — O(p × leg collection size) per request, the classic silent monster. An internal leg whose view declares no covering index is a fatal boot; for an external leg (an upstream collection, whose indexes the operator owns) the same rule applies as a hard operational requirement. A compound index starting with the FK (e.g. (gadget_id, text)) additionally serves the declared order for free.
  • Deep pages multiply legs. Raising maxLimit raises the 1:N query count linearly (p subqueries per 1:N leg). A composed view meant for wide listings should keep its page ceiling modest — or the composition belongs on the materialization path.
  • Export is the deliberate heavy case. CSV/XLSX ignores pagination and walks the filtered set up to maxExportRows (default 10,000): the 1:1 $in batches thousands of keys and each 1:N leg runs thousands of subqueries. That is the read-time analogue of what the materialized path pays continuously in recompose — concentrated in the export request. The knobs are the existing ones: maxExportRows / per-view MaxExportRows (a composed export delegates to its primary's).
  • More legs = more round-trips, linearly. Every declared leg costs its row of the table above on EVERY read of the composed name. Declare the legs a surface actually renders — a "kitchen-sink" composition taxes every consumer for segments most never use; split it into two composed views instead.
Rule of thumb: a composed read costs O(1) extra round-trips per 1:1 leg and O(page) tiny indexed lookups per 1:N leg. If the read is hot enough that O(page) subqueries hurt, or consumers need to FILTER/SORT rows by the joined data, that is the signal the composition has outgrown read time — materialize it (Embed/SharedBaseView) and pay at write time instead. The two-paths table below is the decision matrix.

Per-leg authorization — the ToCriteria seam, unchanged

A composed view can reach, via join, a view the identity could not query directly — so gates matter. The seam is the one the read side already has: the Query's ToCriteria(ctx), with overlays addressed to a leg as segment-prefixed filter entries — the same channel wire segment filters travel. The framework guarantees mechanically that a segment filter can never select or leak primary rows; keeping a leg's data properly gated is fully the developer's responsibility in ToCriteria, exactly as tenant scoping is on every view today. 

func (q FindGadgetFullByIDQuery) ToCriteria(_ *configuration.AppContext) (fwqueries.ReadCriteria, error) {
    return fwqueries.ReadCriteria{
        IncludeArchived: q.IncludeArchived,
        // Per-leg overlay: the composed surface never exposes internal notes,
        // regardless of what the wire asked. Segment paths resolve at every
        // level of the linked document.
        Filter: map[string]any{"Notes.Kind": "public"},
    }, nil
}
Overlay filters participate in the cursor's listing context and compose freely with pagination: the authoritative context-hash validation runs at the reader, post-ToCriteria — the same context outgoing cursors are stamped with — so adding a security overlay (tenant, owner, business gate) to a paged query, plain or composed, never breaks ?after=/?before= navigation. The wire layer performs structural cursor checks only.

Archived gates and consistency

  • One knob, every leg (R8): ?includeArchived=true lifts the primary's gate AND each leg's own gate. A schema is not required to declare SoftDelete — a leg without one has no archived concept; the knob is a silent no-op there, never an error.
  • No cross-leg snapshot: each view keeps its own CDC latency; a composed read inherits each leg's freshness individually and adds no cross-view guarantee. It is the same eventual-consistency class the read side already assumes — a segment can be one tick behind the primary.

Two ways to compose — materialize or query

The framework now has two roads to a composed document, and the reference service ships both over the SAME upstream-mirror data so they can be compared side by side (gadgets_embedded vs gadgets_full in the QA fixtures):
