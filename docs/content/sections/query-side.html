QueryHandler · CQRS

The QueryHandler is the processing unit for a read (GET), symmetric to the CommandHandler on the write side: Request → Query → Handler on the read path mirrors Request → Command → Handler on the write path. The framework's generic FindByParamsQueryHandler / FindByIDQueryHandler implement pipeline.Handler[*Q, R] and resolve the read through the queries.ViewReader port (ReadPage / ReadByID), so the consumer writes no handler code for the common case. Reads come from MongoDB (pre-composed view) and support dynamic filters, cursor pagination, sorting, field projection, and text search — all derived from the query string and the ViewDefinition.

This page covers the QueryHandler concept, the end-to-end flow of a GET, the canonical wiring example, and the manual escape hatch. The query-string capabilities the wrappers enforce — the field/operator allowlist, nested embed groups, ?fields=, ?sort=, keyset pagination with the per-view ?limit= ceiling, and ?onlyTotal=true — are documented under Auto query handlers. The end-to-end layer trace (wrapper → handler → ToCriteria → ViewReader → Mongo → envelope) lives in the Read lifecycle map.

The wire boundary lives in two HTTP wrappers in web/:

  • fwweb.HandleQueryWithParams(pipe, sample, projector, h) — paged listing (GET /users). Validates the query string against the Request DTO's query:"X" filter:"ops" tags, assembles a queries.ReadCriteria, calls req.ToQuery(criteria) — pure body mapping at the boundary, no ctx. AppContext reaches the application layer through q.ToCriteria(ctx), which the framework's FindByParamsQueryHandler[*Q] calls before forwarding to ViewReader.ReadPage — where JWT-derived overlays (tenant id, owner id) layer onto the criteria. Success projects each page.Items document via projector and returns the standard Response envelope with data as the projected items array and pagination as a top-level field.
  • fwweb.HandleQueryWithID(pipe, sample, projector, h) — by-id lookup (GET /users/:id). Only ?includeArchived=true is reserved; any other query parameter produces 400. Calls req.ToQuery() (no ctx), injects the path id via q.SetPathID(...), dispatches via FindByIDQueryHandler[*Q] which calls q.ToCriteria(ctx) and forwards both id + criteria (IncludeArchived flag + any JWT overlay) to ViewReader.ReadByID — symmetric DTO with ReadPage. Projects result.Value() via projector; not-found produces 404 with RecordNotFoundNotification. An overlay filter that filters the doc out is indistinguishable from absence at this layer: both surface as 404.

The projector (third argument) is mandatory and has signature func(map[string]any) R. Three canonical projectors ship with the framework:

ProjectorUse when
fwresponses.AutoFromDoc[R] Tag-driven projection — the default. R is a typed Response struct with json:"<wire>" tags only. The doc handed to the projector is already Go-keyed (the reader translated columns → Go field names via the view's TableSchema), so AutoFromDoc keys by the Go field name and the json: tag governs only the wire shape — there is no source-key override. Recursive through nested structs, slices of structs, and pointer-to-struct fields. Normalizes top-level _id → id and nil slices → empty typed slices at every depth. Drop it in place of a manually-written FromDoc whenever the projection is mechanical.
fwresponses.RawDoc Identity passthrough — func(map[string]any) map[string]any. Use when the view doc shape IS the wire contract and a typed Response would just mirror it.
Consumer-declared R{}.FromDoc method Custom logic — derived fields, conditional projection, ctx-aware shaping, or anything beyond tag-driven. The wrapper signature accepts any func(map[string]any) R.

The Response carries json: only — no source-key override exists. The typed Response struct declares json:"<wire>" tags and nothing else. The document handed to AutoFromDoc is already Go-keyed: the reader (MongoViewReader) translated each physical column to its Go field name using the view's TableSchema tree before the doc ever reaches the projector. So there is no view: tag and no PascalToSnake at the Response layer — the json: tag governs the wire shape (Go field → JSON), and the TableSchema on the infra side governs the column shape (Go field → column): 

type AddressOutput struct {
    Street     string `json:"street"`        // Go field Street → wire "street"
    ZipCode    string `json:"zipCode"`       // Go field ZipCode → wire "zipCode"
    PostalArea string `json:"postalArea"`    // Go field PostalArea → wire "postalArea"
}

A column whose physical name diverges from the Go field is handled entirely on the infra side: TableSchema.Field("PostalArea", "cep") maps the Go field PostalArea to the legacy column cep. The Response stays oblivious — it only ever pronounces the Go field name and its wire name.

Consumers typically declare a typed FindXxxResponse struct in web/requests/find_xxx_request.go (co-located with the Request) and pair it with fwresponses.AutoFromDoc[FindXxxResponse] at the route. The Response type carries the wire contract; the helper carries the projection logic.

Full example

1. Define the ViewDefinition

Every view is declared explicitly with the fluent View(name) builder. The root .Schema(...) and each embed's fwinfra.FromSchema(...) carry the TableSchema (the Go↔column map the reader uses to translate documents back to Go field names); from the schema the framework also derives the embed's table/collection, store kind, and — for an EmbedMany — the join FK. For a local embed the parent-side Go segment (what the Response and criteria refer to, versus the EmbedMany doc field "addresses") is derived from the schema's Go type, pluralized — .As(...) is an optional override. The same schemas that drive the PG write side drive the Mongo view. 

// internal/views/customer.go
package views

import (
    "github.com/ClaudioSchirmer/omnicore/infra"
    appdomain "github.com/ClaudioSchirmer/myservice/domain"
)

// Explicit declaration. The root .Schema(...) and each embed's FromSchema(...)
// carry the Go↔column map; the same schemas drive the PG write side. The local
// embed's segment ("Addresses") is derived from AddressSchema()'s Go type.
var CustomerView = infra.View("customers").
    Version(1).
    Root("customers").
    Schema(views.CustomerSchema()).
    EmbedMany("addresses", infra.FromSchema(views.AddressSchema()))

// Custom pattern — fluent when crossing bounded contexts via UpstreamSubscription
// (cross-service Embed is NOT derivable from the aggregate). An external FromSchema
// (built from a type-less NewExternalSchema) resolves to the local Mongo collection
// materialized by the framework's UpstreamSubscriber on each upstream event (see
// "Cross-service composition" below). External embeds need .As(...) (no Go type to
// derive the segment from); .On(...) names the parent doc FK on a one-to-one Embed.
var SaleView = infra.View("sales_view").
    Version(1).
    Root("sales").
    Schema(views.SaleSchema()).
    Embed("customer", infra.FromSchema(views.CustomerProjection()).
        On("customer_id").As("Customer")).
    EmbedMany("items", infra.FromSchema(views.SaleItemSchema()).
        Embed("product", infra.FromSchema(views.ProductProjection()).
            On("product_id").As("Product")),
    ).
    Indexes(infra.Index("customer_id"))   // boot guard §8.1 requires the join field index

// Drop archived rows from the projection — opt in via .DeleteOnArchive().
// Default behavior (flag absent): ARCHIVED outbox events compose+upsert the
// document (survives with deleted_at populated, mirroring PostgreSQL
// symmetrically) and the composer omits the WHERE deleted_at IS NULL filter
// on every fetch. With .DeleteOnArchive(): ARCHIVED removes the document
// from Mongo and the composer applies the deleted_at filter on the root
// AND on every embed source — the flag governs the whole aggregate
// projection (no per-embed override). The hot-tier choice for services
// that don't need archived data on the read side.
//
// Reader semantics are unchanged: ReadByID / ReadPage default to
// IncludeArchived=false at the Mongo layer, so consumers still have to
// pass ?includeArchived=true (or the equivalent on their Request DTO) to see
// archived documents. On a default (keep) view the document is present
// and returns; on a DeleteOnArchive view the document is absent and the
// reader returns 404 — the explicit consequence of opting into hot-tier.
//
// Hard DELETE always removes the document from Mongo regardless of the
// flag (it covers soft delete only).
var HotTierUserView = infra.View("users").
    Version(1).
    Root("users").
    Schema(views.UserSchema()).
    EmbedMany("addresses", infra.FromSchema(views.AddressSchema())).
    DeleteOnArchive()

2. Declare the Request DTO (allowlist) + Query (transport)

The Request DTO lives in web/requests/ and declares the wire allowlist through struct tags. ToQuery is pure body mapping with no ctx — the web→application boundary stays dumb. The Query lives in application/queries/ and owns its persistence shape end to end via ToCriteria(ctx) — that is where *AppContext is consumed and where JWT-derived overlays (tenant id, owner id) layer onto the ReadCriteria.Filter. 

// internal/web/requests/find_users_by_params_request.go
package requests

type FindUsersByParamsRequest struct {
    // Allowlist (consumer declares which fields and operators are accepted).
    Name  *string `query:"name"  filter:"eq"`
    Email *string `query:"email" filter:"eq,in"`
    City  *string `query:"city"  filter:"eq"`

    // Reserved pagination/control keys — no filter tag.
    Limit           *int64  `query:"limit"`
    After           *string `query:"after"`
    Before          *string `query:"before"`
    Sort            *string `query:"sort"`
    Fields          *string `query:"fields"`
    Search          *string `query:"search"`
    IncludeArchived *bool   `query:"includeArchived"`
}

// ToQuery is the web→application boundary — pure body mapping, no ctx.
// The wrapper has already parsed the query string into `criteria`.
func (r FindUsersByParamsRequest) ToQuery(
    criteria queries.ReadCriteria,
) *appqueries.FindUserByParamsQuery {
    return &appqueries.FindUserByParamsQuery{Criteria: criteria}
}

// internal/application/queries/find_user_by_params_query.go
package queries

type FindUserByParamsQuery struct {
    pipeline.QueryBase
    Criteria fwqueries.ReadCriteria
}

// ToCriteria(ctx) is the read-side equivalent of the write-side
// ToEntity(ctx) — the only layer below the web boundary that may consume
// *AppContext. JWT-derived overlays (tenant id, owner id) layer here onto
// the wire criteria; the framework's FindByParamsQueryHandler calls
// ToCriteria(ctx) and forwards the result to ViewReader.ReadPage.
func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,
) fwqueries.ReadCriteria {
    crit := q.Criteria
    // Example: tenant_id is a custom claim attached to ctx.Identity().Claims
    //   if id := ctx.Identity(); id != nil {
    //       if v, ok := id.Claims["tenant_id"]; ok {
    //           if crit.Filter == nil { crit.Filter = map[string]any{} }
    //           crit.Filter["tenant_id"] = v
    //       }
    //   }
    return crit
}

// By-id companion — same pattern. The Query owns IncludeArchived + JWT overlays
// inside its ToCriteria(ctx); the Request boundary is body-only.
type FindUserByIDRequest struct {
    IncludeArchived *bool `query:"includeArchived"`
}
func (r FindUserByIDRequest) ToQuery() *FindUserByIDQuery {
    arch := false
    if r.IncludeArchived != nil { arch = *r.IncludeArchived }
    return &FindUserByIDQuery{IncludeArchived: arch}
}

type FindUserByIDQuery struct {
    fwqueries.QueryBaseWithID
    IncludeArchived bool
}

// ToCriteria(ctx) returns the same DTO used by FindByParamsQuery — the
// ViewReader port has a single ReadCriteria contract. ReadByID honors
// Filter (overlays) + IncludeArchived; Limit/Sort/After/Before/Search/
// Projection are ignored by ReadByID by design.
func (q FindUserByIDQuery) ToCriteria(
    _ *configuration.AppContext,
) fwqueries.ReadCriteria {
    return fwqueries.ReadCriteria{IncludeArchived: q.IncludeArchived}
}

// ContextName seeds the NotificationContext of the 404 emitted when the
// document is missing. Returning "User" aligns the read 404 with the
// singular identity the write side already emits (Insert/Update/Delete
// notifications carry the same "User" context). Returning "" lets the
// handler fall back to the view name.
func (q FindUserByIDQuery) ContextName() string { return "User" }

3. Wire the routes

The application/queries layer does not know about Fiber or Mongo. The framework's generic handlers consume d.ViewReader directly — no consumer-side handler code. 

// internal/web/routes.go
// The third arg (projector) is mandatory. Pass fwresponses.AutoFromDoc[R]
// for tag-driven projection (the default), fwresponses.RawDoc to pass the
// view document through verbatim, or a consumer-declared Response{}.FromDoc
// method for custom projection logic.
users.Get("/", fwweb.HandleQueryWithParams(d.Pipeline,
    requests.FindUsersByParamsRequest{},
    fwresponses.AutoFromDoc[requests.FindUsersByParamsResponse],
    &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery]{
        Reader: d.ViewReader, View: views.CustomerView.Name(),
    }))

users.Get("/:id", fwweb.HandleQueryWithID(d.Pipeline,
    requests.FindUserByIDRequest{},
    fwresponses.AutoFromDoc[requests.FindUserByIDResponse],
    &handlers.FindByIDQueryHandler[*queries.FindUserByIDQuery]{
        Reader: d.ViewReader, View: views.CustomerView.Name(),
    }))

4. Configure the SyncEngine at boot

// cmd/service/main.go
pg, _ := infra.NewPostgres(ctx, postgresDSN)
mongo, _ := infra.NewMongoDB(ctx, mongoURI, "salesdb")

sync := infra.NewSyncEngine(pg, mongo,
    []string{"kafka:9092"},  // brokers
    "svc-sales",             // groupID
    []*infra.ViewDefinition{ // views of this service
        views.SaleView,
    },
    runtime.NumCPU(),        // workers: pool bucketed by aggregate_id
                             // (per-aggregate ordering preserved).
                             // In bootstrap.Run, comes from yaml kafka.syncWorkers.
                             // Use 1 to opt out (serial mode).
)
sync.Start(ctx)
// SyncEngine.Start is fire-and-forget. Internally the engine pre-creates the
// Kafka topics (idempotent CreateTopics, ignores TopicAlreadyExists) before
// instantiating the reader — necessary because kafka-go with GroupTopics gets
// stuck on JoinGroup when the topic does not exist in the broker metadata at
// subscribe time. Internal 30s retry covers the typical docker-compose boot
// race (Kafka coming up while the service has already started). Topics
// pre-created in production via external tooling return TopicAlreadyExists and
// are respected — defaults (1 partition / RF=1) only matter for dev.

// Cross-service composition via UpstreamSubscription (yaml-declared in
// microservice.<profile>.yaml; manual Wiring form shown for illustration).
// bootstrap.Run spins one infra.UpstreamSubscriber per entry and ripples
// recompose to every view embedding the materialized collection via an
// external FromSchema embed.
return bootstrap.Wiring{
    UpstreamSubscriptions: []bootstrap.UpstreamSubscription{
        {Topic: "people.customers.events", Collection: "customers",
         Filter: []string{"id", "name", "username"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
        {Topic: "catalog.products.events", Collection: "products",
         Filter: []string{"id", "name", "price"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
    },
}

Persistent failure registry. Every ripple failure (discover / compose / upsert stage) is upserted into the framework PG table omnicore_upstream_failures alongside the slog line and the in-memory counter. The natural key (subscription_topic, view_name, upstream_id, local_id, stage) turns retries into attempt increments — the table mirrors live state, never grows monotonically. A recompose round that finishes without errors for (view, upstream_id) automatically marks any pending rows under that coordinate as resolved (resolved_at = NOW()). Writes are best-effort: any PG error on Record/Resolve is logged at slog.Warn and discarded — the consumer's Kafka offset still advances, preserving the failure-isolation contract.

Operational queries (SQL on B's framework PG):

-- Currently stale entities:
SELECT subscription_topic, view_name, upstream_id, local_id, stage, attempt,
       last_attempt_at, error
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
ORDER BY last_attempt_at ASC;

-- Top offending views (recurring failures may indicate a deterministic Composer bug):
SELECT view_name, count(*) AS pending
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
GROUP BY view_name
ORDER BY pending DESC;

Retry surface. UpstreamSubscriber.RetryPendingFailures(ctx) (retried int, err error) is the public runtime API: it lists pending failures by the subscriber's topic, deduplicates by upstream_id, and re-runs ripple for each unique id. Idempotent — a successful re-ripple calls ResolveUpstreamFailures, so the next call against a drained slate is a no-op. The framework owns the primitive; the consumer decides how to expose it (in-process ticker, authenticated HTTP endpoint, or admin RPC).

Inspection CLI. omnicore-admin upstream-list-failures [--topic <name>] [--view <name>] [--format text|json] [--limit N] is the read-only triage tool: runs in B's process (loads microservice.${APP_PROFILE}.yaml), reads the table, prints text or JSON. The CLI binary has no Wiring of B and cannot call RetryPendingFailures — actual retry lives on the runtime API above.

5. Client does GET with dynamic filters

GET /users?email.in=a@x.com,b@y.com&sort=-created_at&limit=20

→ filters emails by inclusion ($in applied)
→ orders by created_at descending
→ returns 20 + cursor for the next page

GET /users/<id>?includeArchived=true

→ returns even if soft-deleted (deleted_at IS NOT NULL)

GET /users?role=admin

→ 400 SchemaViolationNotification — "role" is not in the allowlist
Result: with a Request DTO that declares the allowlist via struct tags, a thin Query that owns its persistence shape via ToCriteria(ctx), and two route lines, the developer gets the read side wired end-to-end. Unknown fields and operators are rejected at the wire boundary; not-found surfaces as 404; pagination lives top-level in the envelope; and AppContext-derived security filters layer onto the criteria inside ToCriteria(ctx) without changing any other signature.

Manual query handlers — same building blocks

Routes that need a custom shape (alternative identifier, vendor-specific lookup, bespoke envelope) opt out of the wrapper but still get the canonical allowlist + envelope by composing the building blocks the wrapper itself uses. Two helpers cover the query-string allowlist depending on whether the Response is typed:

  • fwweb.NewQueryParser[Req, Resp]() — typed Mount-time parser when the Request opts into ?fields= / ?sort= AND the Response is typed. Construction runs the same boot scan HandleQueryWithParams runs internally: sparse-render guard on the Response (panic when any field at any depth is not *T or a slice/map with ,omitempty), slog.Warn advisory listing every sortable wire path so operators can compare against the Mongo view's index declaration, plus extractProjectionSchema for runtime wire→doc translation. Per-request parser.Parse(c) returns the same (criteria, badField, ok) shape as ParseCriteria but with allowlist enforcement and translation enabled. Constructed once per route and reused; schema caches are shared with the canonical wrapper.
  • fwweb.ParseCriteria(c, requestDTO) — un-typed escape hatch for handlers that have no typed Response (RawDoc projectors, vendor-shaped envelopes) OR whose Request does not opt into ?fields= / ?sort=. Same reflection-based allowlist applies, but the projection schema is nil so reserved keys land in pass-through mode (tokens verbatim, no _id:0 auto-exclusion, no snake_case translation).

Canonical manual list shape (typed Response opting into ?fields= / ?sort=):

// At Mount time — once per route. Boot scan fires here:
// fields-side guard + sort-side slog.Warn + projection-schema build.
listParser := fwweb.NewQueryParser[requests.FindXxxCustomRequest, requests.FindXxxCustomResponse]()

g.Get("/", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindXxxCustomRequest
    // Same allowlist + wire→doc translation HandleQueryWithParams runs
    // internally.
    crit, badField, ok := listParser.Parse(c)
    if !ok {
        // Canonical 400 envelope with SchemaViolationNotification — same
        // shape consumers already parse from the auto path.
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }

    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if !result.IsSuccess() {
        return fwweb.RespondFromResult(c, result, fiber.StatusOK)
    }
    // Same envelope HandleQueryWithParams emits — items projected per doc,
    // top-level pagination block.
    return fwweb.RespondPaged(c, fiber.StatusOK, result.Value(),
        fwresponses.AutoFromDoc[requests.FindXxxCustomResponse])
})

    // Same path-binding the wrappers run internally — populates fields
    // tagged `path:"<name>"` from c.Params("<name>").
    if badField, ok := fwweb.BindPath(c, &req); !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    crit, badField, ok := byEmailParser.Parse(c)
    if !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if result.IsSuccess() {
        return fwweb.RespondWithSuccess(c, fiber.StatusOK,
            fwresponses.AutoFromDoc[requests.FindXxxByEmailResponse](result.Value()))
    }
    return fwweb.RespondFromResult(c, result, fiber.StatusOK)
})

Projection is shared infrastructure. Manual query handlers should pair with fwresponses.AutoFromDoc[R] (tag-driven default) or fwresponses.RawDoc (passthrough) — the same projectors the canonical wrappers consume. Hand-rolling a FromDoc that walks doc["id"], doc["name"], etc. is a redundant rewrite of what AutoFromDoc already does (json: tags, _id → id fallback, Go-keyed doc from the reader, nil→empty-slice normalization). Declare a consumer R{}.FromDoc method only when the projection needs logic AutoFromDoc cannot express (derived fields computed from multiple doc keys, conditional shaping, ctx-aware projection).

For envelopes that need sidecar fields (custom keys outside data/pagination), use fwweb.ProjectPage instead of RespondPaged and build the Response struct by hand — the projector and the pagination cursor are still framework-managed.

path: tag — universal URL-segment binding

Every Request DTO field tagged path:"<name>" is populated from the matching Fiber URL segment (c.Params("<name>")) before ToCommand / ToQuery runs. Closes the asymmetry between the canonical wrappers (which only auto-bind :id via the pipeline.CommandWithID / queries.FindByIDQuery interface) and routes with custom identifier segments (:email, :tenantId, …) or compound paths (/tenants/:tenantId/users/:id). 

// Read by-email — single segment route
type FindUserByEmailRequest struct {
    Email           string `path:"email"`
    IncludeArchived *bool  `query:"includeArchived"`
}
func (r FindUserByEmailRequest) ToQuery(crit fwqueries.ReadCriteria) *queries.FindUserByEmailQuery { ... }

// Compound route — both segments via tag
type UpdateOnTenantRequest struct {
    TenantID string `path:"tenantId"`   // /tenants/:tenantId/users/:id — :id still via interface on WithBodyID
    Name     string `json:"name"`
}

Per-wrapper behavior — :id-binding wrappers (HandleCommandWithBodyID, HandleQueryWithID) panic at boot if the Request declares path:"id" (it would set the same value twice); Group A wrappers (HandleCommandWithBody, HandleQueryWithParams) accept path:"id" for compound routes — map cmd.SetPathID(r.ID) inside ToCommand. HandleCommandWithID has no Request DTO and is excluded from path-binding entirely.

Manual fiber.Handler closures opt out of the wrappers — call fwweb.BindPath(c, &req) explicitly (same helper as ParseCriteria). See omnicore-example-users/web/user_custom_routes.go for the canonical example of BindPath → Bind().Body() → ToCommand → Dispatch.

Supported field types: string, signed/unsigned ints of any width, float32/float64, bool, uuid.UUID, domain.ID. Pointer/slice/struct types are rejected at boot. Conversion failure returns 400 SchemaViolationNotification with the segment name.

FullBody interaction. The strict-body check in HandleCommandWithBody{,ID} skips fields carrying a path: tag — their value comes from the URL, not the body. Declaring both path:"X" and json:"X" on the same field is a boot panic; the same value cannot come from two sources.

Group A wrapper + ID-requiring handler warning. When HandleCommandWithBody / HandleQueryWithParams (no :id auto-bind) is paired with an ID-requiring auto handler (Update/PartialUpdate/Archive/Unarchive/Delete) AND the Request DTO declares no path: tag at all, the wrapper logs a single slog.Warn at construction time. Catches the misconfiguration of "I expected the wrapper to populate the ID" — the runtime guard handlers.RequirePathID still catches the actual failure if the warning is ignored. FindByIDQueryHandler is excluded from the warning because its Group A wrapper does not compile with the handler's constraint.

Runtime guard. Each ID-requiring auto handler calls handlers.RequirePathID(<pathID>, "<HandlerName>") as the first line of Handle. Empty path ID → developer-focused panic, caught by pipeline.Run's defer/recover, surfaced to the wire as 500 InternalServerErrorNotification; full diagnostic on slog. Each handler also embeds pipeline.PathIDRequired so the wrappers can detect the requirement via type assertion at construction time (zero per-request cost).
