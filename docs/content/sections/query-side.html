Query side (CQRS)

The query side serves reads (GET) symmetric to the command side: Request → Query → Handler on the read path mirrors Request → Command → Handler on the write path. Reads come from MongoDB (pre-composed view) and support dynamic filters, cursor pagination, sorting, field projection, and text search — all derived from the query string and the ViewDefinition.

The wire boundary lives in two HTTP wrappers in web/:

  • fwweb.HandleQueryWithParams(pipe, sample, projector, h) — paged listing (GET /users). Validates the query string against the Request DTO's query:"X" filter:"ops" tags, assembles a queries.ReadCriteria, calls req.ToQuery(criteria) — pure body mapping at the boundary, no ctx. AppContext reaches the application layer through q.ToCriteria(ctx), which the framework's FindByParamsQueryHandler[*Q] calls before forwarding to ViewReader.ReadPage — where JWT-derived overlays (tenant id, owner id) layer onto the criteria. Success projects each page.Items document via projector and returns the standard Response envelope with data as the projected items array and pagination as a top-level field.
  • fwweb.HandleQueryWithID(pipe, sample, projector, h) — by-id lookup (GET /users/:id). Only ?includeArchived=true is reserved; any other query parameter produces 400. Calls req.ToQuery() (no ctx), injects the path id via q.SetPathID(...), dispatches via FindByIDQueryHandler[*Q] which calls q.ToCriteria(ctx) and forwards both id + criteria (IncludeArchived flag + any JWT overlay) to ViewReader.ReadByID — symmetric DTO with ReadPage. Projects result.Value() via projector; not-found produces 404 with RecordNotFoundNotification. An overlay filter that filters the doc out is indistinguishable from absence at this layer: both surface as 404.

The projector (third argument) is mandatory and has signature func(map[string]any) R. Three canonical projectors ship with the framework:

ProjectorUse when
fwresponses.AutoFromDoc[R] Tag-driven projection — the default. R is a typed Response struct with json:"<wire>" (wire name) and optional view:"<docKey>" (source-key override) tags. Recursive through nested structs, slices of structs, and pointer-to-struct fields. Normalizes top-level _id → id and nil slices → empty typed slices at every depth. Drop it in place of a manually-written FromDoc whenever the projection is mechanical.
fwresponses.RawDoc Identity passthrough — func(map[string]any) map[string]any. Use when the view doc shape IS the wire contract and a typed Response would just mirror it.
Consumer-declared R{}.FromDoc method Custom logic — derived fields, conditional projection, ctx-aware shaping, or anything beyond tag-driven. The wrapper signature accepts any func(map[string]any) R.

The view: tag — explicit source-key override (rare). The projector consumes two tags on the Response struct. json:"<wire>" is the standard encoding/json contract — names the field on the outgoing JSON. view:"<docKey>" is the explicit override — names the field inside the view document when the framework default does not fit. The default doc key is domain.PascalToSnake(jsonName), the same convention the framework uses on the Postgres write side (ZipCode → column zip_code). So json:"zipCode" defaults to doc field zip_code, matching the composer's snake_case output without any tag declaration. Declare view: only for exotic schemas where the doc name truly diverges: 

type AddressOutput struct {
    Street     string `json:"street"`                        // doc["street"]
    ZipCode    string `json:"zipCode"`                       // doc["zip_code"] (auto-snake)
    PostalArea string `json:"postalArea" view:"cep"`         // doc["cep"]      (legacy schema)
}

When view: is absent, the helper applies PascalToSnake to the json: name (or to the Go field name when there's no json tag). view:"-" is treated as absent — json:"-" already covers "skip this field" semantics.

Consumers typically declare a typed FindXxxResponse struct in web/requests/find_xxx_request.go (co-located with the Request) and pair it with fwresponses.AutoFromDoc[FindXxxResponse] at the route. The Response type carries the wire contract; the helper carries the projection logic.

Allowlist via struct tags

Each filter field on the Request DTO declares its set of allowed operators via the filter:"eq,in" tag. The wrapper inspects the type (cached by reflect.Type in a module-level sync.Map) and rejects any query-string key outside the declared set with 400 SchemaViolationNotification. Reserved pagination/control keys (limit, after, before, sort, fields, search, includeArchived) are declared with only the query:"..." tag (no filter tag) — recognized only at the top level, never inside an embed group.

Nested embed groups

A struct-typed field carrying query:"prefix" (no filter:) is an embed group — the walker recurses, and every leaf below it produces a wire key prefixed by prefix.. Symmetric with the Response side, where nested structs project nested doc paths via AutoFromDoc. 

type FindUsersByParamsRequest struct {
    Name      *string             `query:"name"  filter:"eq,startswith"`
    Email     *string             `query:"email" filter:"eq,in"`
    Addresses AddressFilterParams `query:"addresses"`

    Limit *int64 `query:"limit"`
}

type AddressFilterParams struct {
    City    *string `query:"city"    filter:"eq,istartswith"`
    ZipCode *string `query:"zipCode" filter:"eq,startswith"`  // auto-snake → addresses.zip_code
}

Wire shape: ?addresses.city=Berlin, ?addresses.zipCode.startswith=10001. Doc path: derived per-leaf via domain.PascalToSnake (the same convention applied to Postgres column names) — zipCode defaults to doc field zip_code; no view: tag needed for the common camelCase case. Declare view:"<name>" per-leaf only when the convention does not fit (legacy schemas, vendor-shaped projections). Pointer-to-struct embed groups (*AddressFilterParams) recurse identically.

Sparse responses via ?fields=

Opt-in field projection — the consumer asks for a subset of the Response shape and the framework strips everything else end to end. The Request DTO opts in by declaring Fields *string `query:"fields"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, three things happen automatically:

  1. Boot guard. At wrapper construction (HandleQueryWithParams / HandleQueryWithParamsSpec), the framework walks R recursively and panics if any exported field is not *T (or a slice/map) and does not carry ,omitempty in its json tag. The panic diagnostic names every offending field path (FindXxxResponse.addresses.zipCode: missing ,omitempty…) — fail loud at boot so the contract cannot ship.
  2. Allowlist + wire→doc translation. Each comma-separated token in ?fields= is validated against the Response DTO's declared wire paths and translated to the corresponding Mongo doc path via the same convention used elsewhere on the read side (domain.PascalToSnake by default, view: tag override per segment). Unknown tokens emit 400 with SchemaViolationNotification on field fields[<bad>]. Nested paths are walked segment-by-segment, so ?fields=addresses.zipCode projects to Mongo as {"addresses.zip_code":1}, and ?fields=addresses projects the whole subtree.
  3. Auto-exclusion of _id. Mongo always returns _id unless excluded. When the wire fields list does not include id, the framework adds _id: 0 to the projection so the typed Response stays clean (no phantom id the consumer didn't ask for). When id is among the tokens, no _id: 0 is added — Mongo returns both id and _id, and AutoFromDoc's existing fallback (id ← _id when id absent) keeps the wire output stable across both cases. Mongo's projection rules allow _id: 0 to be mixed with inclusion entries — it is the only permitted exclusion in an otherwise- inclusion projection.

Why the boot guard? Mongo strips the unwanted columns from the document; the projector (AutoFromDoc[R] by default) populates only the fields it finds in the doc; the remaining fields stay at their zero value. For pointer fields with omitempty, encoding/json elides them on the wire. For non-pointer fields (or pointer fields missing omitempty), the zero value still renders ("name":"", "addresses":[]), defeating the point of ?fields=. The contract enforced at boot is the cheapest way to keep wire output coherent with what the consumer asked for.

The boot guard is opt-in by declaration: a Request DTO that does not carry query:"fields" imposes no constraint on its Response type; the HandleQueryWithParams wrapper paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the guard — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?fields= token becomes an inclusion entry verbatim, no allowlist, no translation, no _id: 0 auto-exclusion. The canonical surface is the HandleQueryWithParams wrapper. 

// Request DTO opts in to the parameter.
type FindUsersByParamsRequest struct {
    Name   *string `query:"name"   filter:"eq"`

Sortable response paths via ?sort=

Symmetric to ?fields=: the consumer asks the framework to order results by Response-declared paths and the wrapper validates + translates the tokens end to end. The Request DTO opts in by declaring Sort *string `query:"sort"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, two things happen automatically:

  1. Allowlist + wire→doc translation. Each comma-separated token is stripped of an optional - prefix (descending; bare token = ascending), validated against the Response DTO's declared wire paths, and translated to the corresponding Mongo doc path via the same convention used by ?fields= (domain.PascalToSnake by default, view: tag override per segment). Unknown tokens emit 400 with SchemaViolationNotification on field sort[<token>]; the rejected token is surfaced verbatim including any - prefix the consumer sent. The resulting SortField{Field: docPath, Desc: bool} entries land on ReadCriteria.Sort and the canonical MongoViewReader emits the corresponding bson.D on findOpts.SetSort.
  2. Boot warning when sort is declared. The wrapper has no way to verify from its construction site that the Mongo view declares indexes covering the sortable paths — the ViewDefinition lives in the consumer's ReadableFeature.Views(), separated from the route registration. When Sort opt-in is detected and a typed Response is in scope, the framework emits a single slog.Warn at boot listing every sortable wire path so the operator can compare it against the view's .Indexes(…) declaration in the same boot pass and add covering indexes (fwinfra.Index / fwinfra.Compound) where missing — sort queries against non-indexed fields scale poorly on large collections.

There is no boot guard analogous to fields' pointer + omitempty rule. ?sort= only consumes the wire→doc path map; the Response shape is not constrained by it. When fields is also opt-in, the existing guard still fires — it is the fields-side rule, untouched by sort.

The allowlist is opt-in by declaration: a Request DTO without query:"sort" does not get the allowlist (and does not consume the ?sort= wire key); HandleQueryWithParams paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the allowlist — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?sort= token becomes a SortField verbatim (no allowlist, no translation, no boot warning). The canonical surface is the HandleQueryWithParams wrapper.

Keyset pagination via ?after= / ?before= + per-view ?limit= ceiling

The read side is keyset-paginated over (sort_value..., _id). The cursor encodes the value tuple of the boundary doc (last for forward, first for backward) and the reader walks from that point. The reader always appends _id ASC as the stable tiebreaker so the result set is deterministic across pages even when the underlying collection is being written to concurrently; consumer-declared ?sort= fields layer in front of the _id slot. The ?before= path queries Mongo in inverted sort order and reverses the slice in Go so the caller always sees the canonical requested order.

Cursor format. Opaque to consumers — base64(URLEncoding) of {"v":1, "k":[<sort_values..>, "<_id>"], "h":"<context_sha256>"}. URL-safe so + / / are never produced in the encoded string. The v field carries the schema version (currently 1); a future bump rejects older cursors with the same 400 envelope so the consumer surfaces the drift instead of navigating against a stale layout. The h field is the canonical SHA-256 of the issuing call's full listing context (queries.HashContext) — every axis that shapes the result set the cursor walks: Filter + Sort (field + Desc per entry, declaration order matters) + Search + IncludeArchived. Empty (omitted on the wire) when the issuing call carried the canonical default context (no filter, no sort, no search, archived excluded).

Cursors are scoped to the full listing context. A cursor only navigates correctly inside the result set that issued it. The wrapper validates len(cursor.K)-1 == len(criteria.Sort) (structural pre-check protecting the reader's keyset builder) AND cursor.H == HashContext(filter, sort, search, includeArchived) (covers every listing axis) after parsing the query string. Any mismatch — sort field added/removed/ reordered, sort direction flipped, filter value changed, ?search= value changed, ?includeArchived= flipped — is rejected with 400 SchemaViolationNotification on the cursor's wire key (after or before). Stateless by design: there is no server-side session, no per-cursor TTL, no token store. The whole "is this cursor still valid?" check runs in the wrapper against the wire request alone. Cursors persist arbitrarily — across requests, across browser tabs, across user devices — as long as the deploy's schema version and the full listing context match.

The strict check exists to convert silent consumer-side bugs (frontend changes one knob, server returns wrong/empty results, user blames the data) into loud, explicit failures with a clear remediation: "request page 1 of the new context".

Symmetric envelope. The reader emits NextCursor and PrevCursor on every non-terminal page in both forward and backward navigation, so a UI can drive both "next" and "previous" buttons symmetrically. HasNext / HasPrev reflect the actual presence of more docs in either direction.

Per-view ?limit= ceiling — single cascade, three levels. Every paged GET is bounded by a resolved-at-read-time ceiling computed in this order:

  1. ViewDefinition.MaxLimit(N) — declarative per-view override (fwinfra.View("users").MaxLimit(500)). Applies uniformly to every endpoint consulting the view, regardless of how many handlers point at it — the cap describes the cost of reading this specific dataset, not of any single endpoint.
  2. cfg.Query.MaxLimit — yaml-supplied service-wide default (microservice.<profile>.yaml: query: { maxLimit: 200 }).
  3. Framework constant 100 — conservative fallback when neither is declared.

The resolved ceiling is always > 0. When the consumer sends no ?limit=, the reader returns up to that ceiling (no separate hardcoded default page size). When the consumer sends ?limit=N and N ≤ resolvedMax, that value wins. When N > resolvedMax, the reader rejects with 400 LimitExceededNotification carrying the effective ceiling as FieldValue so the consumer can show "max is X" without parsing the translated message.

MaxLimit(N) does NOT participate in RebuildHash / ArtifactHash — the cap is operational state, not projection shape. Bumping it neither triggers a Mongo rebuild nor requires a Version(N) bump.

Compound cursor + ?fields= interaction. When the consumer requests ?fields=name AND ?sort=created_at, the doc would otherwise not carry created_at (projected away) and the reader could not assemble the cursor. The reader transparently re-includes every active sort field path in the Mongo projection, then strips them from the returned doc after the cursor is built. The wire shape stays exactly as the consumer requested via ?fields=.

Count-only mode via ?onlyTotal=true

Boolean reserved control key. When set to true the wrapper short-circuits the read into a count primitive — the reader runs CountDocuments against the assembled Filter (including identity-derived overlays, the archived gate, and any ?search=) and the wire envelope carries solely pagination.total. No documents are materialized, no projection is applied, no cursor is decoded. The use case is a frontend that needs the total count of a filtered subset (pagination calculation, "matches" badge) without paying for the document fetch.

Like every reserved control key on the read side, ?onlyTotal= is opt-in per endpoint: the consumer declares OnlyTotal *bool `query:"onlyTotal"` on the Request DTO. Endpoints that did not declare it reject the wire key with the canonical 400 — same posture as ?fields= / ?sort= / ?includeArchived=.

Conflict matrix. The listing-only reserved controls have no meaningful effect when no documents are emitted, so combining them with onlyTotal=true is a consumer-side bug. The wrapper rejects the combination with 400 SchemaViolationNotification on field onlyTotal[<conflict>]. Filter leaves (declared via filter:"ops") plus ?search= and ?includeArchived= stay valid — counting a filtered subset is the canonical use case.

On the response side, the Response.Pagination slot is typed any precisely because it carries two legitimate Go shapes: *PaginationInfo on listing requests (has_next/has_prev/cursors + total) and *TotalOnlyPagination on count-only requests (only total). Both are typed structs — no untyped map ever reaches the wire. The dedicated shape exists so the JSON does NOT carry zero-value has_next: false / empty cursors that would mislead the consumer in count mode.

Manual handlers via fwweb.ParseCriteria get the same treatment: the OnlyTotal flag flows into ReadCriteria.OnlyTotal and conflicts are rejected with the same field shape, so the canonical wire contract is shared with the canonical wrapper path. The downstream branch on queries.Page.OnlyTotal is what RespondPaged consumes to pick the envelope shape; manual handlers that assemble the envelope by hand can read the same field on the returned Page.

const (

    OpINe          = "ine"          // case-insensitive inequality
    OpIIn          = "iin"          // case-insensitive in-list
    OpINin         = "inin"         // case-insensitive not-in-list

    OpIContains    = "icontains"    // case-insensitive substring
)

String operators come in case-sensitive and case-insensitive variants — the i prefix is the case-folded twin. The consumer declares whichever set the endpoint accepts (filter:"eq,startswith,icontains" means exact, prefix, and case-insensitive substring); operators outside the declared list are rejected with 400. Numeric operators (gte/lte/gt/lt) have no i variant by design — case-folding has no meaning on ordinal comparisons.

User-supplied values feeding the regex operators are escaped via regexp.QuoteMeta so wire metacharacters are treated as literals — ?name.contains=a.b*c matches the literal string a.b*c, never the regex pattern. The iin and inin operators emit a queries.RegexMatchList sentinel that MongoViewReader translates into {$in: [bson.Regex, ...]} / {$nin: [bson.Regex, ...]} — Mongo requires the native regex type inside $in, so the translation is owned by the infra adapter rather than emitted from the wire layer.

Multiple operators on the same field are AND-ed. When the wire delivers more than one operator targeting the same field (e.g. ?age.gte=18&age.lte=65 or ?name.startswith=Bob&name.icontains=ob), the wrapper folds the clauses into a queries.MultiClause sentinel on ReadCriteria.Filter[field] instead of overwriting the previous entry on the map. MongoViewReader expands the sentinel into a top-level $and array — each clause becomes a {field: translatedValue} entry so every declared operator is honored simultaneously. A single operator on a field stays as the plain {field: value} shape so Mongo indexes remain usable without an outer $and.

Full example

1. Define the ViewDefinition

Canonical case (single aggregate, convention matches): fwinfra.ViewOf[*T]() infers Mongo collection, root table, and EmbedMany from the children declared in T.AggregateChildren(). Custom pattern (cross-service via cache, external materialized view) still via fluent View(name).Root(...).EmbedMany(...) — they coexist. 

// internal/views/customer.go
package views

import (
    "github.com/ClaudioSchirmer/omnicore/infra"
    appdomain "github.com/ClaudioSchirmer/myservice/domain"
)

// Canonical path — 1 line. Infers collection "customers", root table
// "customers" and EmbedMany from the children declared in
// Customer.AggregateChildren().
var CustomerView = infra.ViewOf[*appdomain.Customer]()

// Custom pattern — fluent when crossing bounded contexts via UpstreamSubscription
// (cross-service Embed is NOT derivable from the aggregate). FromMongo resolves to
// the local Mongo collection materialized by the framework's UpstreamSubscriber on
// each upstream event (see "Cross-service composition" below).
var SaleView = infra.View("sales_view").
    Root("sales").
    Embed("customer", infra.FromMongo("customers").On("customer_id")).
    EmbedMany("items", infra.From("sale_items").On("sale_id").
        Embed("product", infra.FromMongo("products").On("product_id")),
    ).
    Indexes(infra.Index("customer_id"))   // boot guard §8.1 requires the join field index

// Drop archived rows from the projection — opt in via .DeleteOnArchive().
// Default behavior (flag absent): ARCHIVED outbox events compose+upsert the
// document (survives with deleted_at populated, mirroring PostgreSQL
// symmetrically) and the composer omits the WHERE deleted_at IS NULL filter
// on every fetch. With .DeleteOnArchive(): ARCHIVED removes the document
// from Mongo and the composer applies the deleted_at filter on the root
// AND on every embed source — the flag governs the whole aggregate
// projection (no per-embed override). The hot-tier choice for services
// that don't need archived data on the read side.
//
// Reader semantics are unchanged: ReadByID / ReadPage default to
// IncludeArchived=false at the Mongo layer, so consumers still have to
// pass ?includeArchived=true (or the equivalent on their Request DTO) to see
// archived documents. On a default (keep) view the document is present
// and returns; on a DeleteOnArchive view the document is absent and the
// reader returns 404 — the explicit consequence of opting into hot-tier.
//
// Hard DELETE always removes the document from Mongo regardless of the
// flag (it covers soft delete only).
var HotTierUserView = infra.ViewOf[*appdomain.User]().DeleteOnArchive()

2. Declare the Request DTO (allowlist) + Query (transport)

The Request DTO lives in web/requests/ and declares the wire allowlist through struct tags. ToQuery is pure body mapping with no ctx — the web→application boundary stays dumb. The Query lives in application/queries/ and owns its persistence shape end to end via ToCriteria(ctx) — that is where *AppContext is consumed and where JWT-derived overlays (tenant id, owner id) layer onto the ReadCriteria.Filter. 

// internal/web/requests/find_users_by_params_request.go
package requests

type FindUsersByParamsRequest struct {
    // Allowlist (consumer declares which fields and operators are accepted).
    Name  *string `query:"name"  filter:"eq"`
    Email *string `query:"email" filter:"eq,in"`
    City  *string `query:"city"  filter:"eq"`

    // Reserved pagination/control keys — no filter tag.
    Limit           *int64  `query:"limit"`
    After           *string `query:"after"`
    Before          *string `query:"before"`
    Sort            *string `query:"sort"`
    Fields          *string `query:"fields"`
    Search          *string `query:"search"`
    IncludeArchived *bool   `query:"includeArchived"`
}

// ToQuery is the web→application boundary — pure body mapping, no ctx.
// The wrapper has already parsed the query string into `criteria`.
func (r FindUsersByParamsRequest) ToQuery(
    criteria queries.ReadCriteria,
) *appqueries.FindUserByParamsQuery {
    return &appqueries.FindUserByParamsQuery{Criteria: criteria}
}

// internal/application/queries/find_user_by_params_query.go
package queries

type FindUserByParamsQuery struct {
    pipeline.QueryBase
    Criteria fwqueries.ReadCriteria
}

// ToCriteria(ctx) is the read-side equivalent of the write-side
// ToEntity(ctx) — the only layer below the web boundary that may consume
// *AppContext. JWT-derived overlays (tenant id, owner id) layer here onto
// the wire criteria; the framework's FindByParamsQueryHandler calls
// ToCriteria(ctx) and forwards the result to ViewReader.ReadPage.
func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,
) fwqueries.ReadCriteria {
    crit := q.Criteria
    // Example: tenant_id is a custom claim attached to ctx.Identity().Claims
    //   if id := ctx.Identity(); id != nil {
    //       if v, ok := id.Claims["tenant_id"]; ok {
    //           if crit.Filter == nil { crit.Filter = map[string]any{} }
    //           crit.Filter["tenant_id"] = v
    //       }
    //   }
    return crit
}

// By-id companion — same pattern. The Query owns IncludeArchived + JWT overlays
// inside its ToCriteria(ctx); the Request boundary is body-only.
type FindUserByIDRequest struct {
    IncludeArchived *bool `query:"includeArchived"`
}
func (r FindUserByIDRequest) ToQuery() *FindUserByIDQuery {
    arch := false
    if r.IncludeArchived != nil { arch = *r.IncludeArchived }
    return &FindUserByIDQuery{IncludeArchived: arch}
}

type FindUserByIDQuery struct {
    fwqueries.QueryBaseWithID
    IncludeArchived bool
}

// ToCriteria(ctx) returns the same DTO used by FindByParamsQuery — the
// ViewReader port has a single ReadCriteria contract. ReadByID honors
// Filter (overlays) + IncludeArchived; Limit/Sort/After/Before/Search/
// Projection are ignored by ReadByID by design.
func (q FindUserByIDQuery) ToCriteria(
    _ *configuration.AppContext,
) fwqueries.ReadCriteria {
    return fwqueries.ReadCriteria{IncludeArchived: q.IncludeArchived}
}

// ContextName seeds the NotificationContext of the 404 emitted when the
// document is missing. Returning "User" aligns the read 404 with the
// singular identity the write side already emits (Insert/Update/Delete
// notifications carry the same "User" context). Returning "" lets the
// handler fall back to the view name.
func (q FindUserByIDQuery) ContextName() string { return "User" }

3. Wire the routes

The application/queries layer does not know about Fiber or Mongo. The framework's generic handlers consume d.ViewReader directly — no consumer-side handler code. 

// internal/web/routes.go
// The third arg (projector) is mandatory. Pass fwresponses.AutoFromDoc[R]
// for tag-driven projection (the default), fwresponses.RawDoc to pass the
// view document through verbatim, or a consumer-declared Response{}.FromDoc
// method for custom projection logic.
users.Get("/", fwweb.HandleQueryWithParams(d.Pipeline,
    requests.FindUsersByParamsRequest{},

        Reader: d.ViewReader, View: views.CustomerView.Name(),

users.Get("/:id", fwweb.HandleQueryWithID(d.Pipeline,

5. Manual query handlers — same building blocks

Routes that need a custom shape (alternative identifier, vendor-specific lookup, bespoke envelope) opt out of the wrapper but still get the canonical allowlist + envelope by composing the building blocks the wrapper itself uses. Two helpers cover the query-string allowlist depending on whether the Response is typed:

  • fwweb.NewQueryParser[Req, Resp]() — typed Mount-time parser when the Request opts into ?fields= / ?sort= AND the Response is typed. Construction runs the same boot scan HandleQueryWithParams runs internally: sparse-render guard on the Response (panic when any field at any depth is not *T or a slice/map with ,omitempty), slog.Warn advisory listing every sortable wire path so operators can compare against the Mongo view's index declaration, plus extractProjectionSchema for runtime wire→doc translation. Per-request parser.Parse(c) returns the same (criteria, badField, ok) shape as ParseCriteria but with allowlist enforcement and translation enabled. Constructed once per route and reused; schema caches are shared with the canonical wrapper.
  • fwweb.ParseCriteria(c, requestDTO) — un-typed escape hatch for handlers that have no typed Response (RawDoc projectors, vendor-shaped envelopes) OR whose Request does not opt into ?fields= / ?sort=. Same reflection-based allowlist applies, but the projection schema is nil so reserved keys land in pass-through mode (tokens verbatim, no _id:0 auto-exclusion, no snake_case translation).

Canonical manual list shape (typed Response opting into ?fields= / ?sort=):

// At Mount time — once per route. Boot scan fires here:
// fields-side guard + sort-side slog.Warn + projection-schema build.
listParser := fwweb.NewQueryParser[requests.FindXxxCustomRequest, requests.FindXxxCustomResponse]()

g.Get("/", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindXxxCustomRequest
    // Same allowlist + wire→doc translation HandleQueryWithParams runs
    // internally.
    crit, badField, ok := listParser.Parse(c)
    if !ok {
        // Canonical 400 envelope with SchemaViolationNotification — same
        // shape consumers already parse from the auto path.
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }

    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if !result.IsSuccess() {
        return fwweb.RespondFromResult(c, result, fiber.StatusOK)
    }
    // Same envelope HandleQueryWithParams emits — items projected per doc,
    // top-level pagination block.
    return fwweb.RespondPaged(c, fiber.StatusOK, result.Value(),
        fwresponses.AutoFromDoc[requests.FindXxxCustomResponse])
})

By-email lookup shape — chain BindPath before the parser:

byEmailParser := fwweb.NewQueryParser[requests.FindXxxByEmailRequest, requests.FindXxxByEmailResponse]()

g.Get("/:email", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindXxxByEmailRequest
    // Same path-binding the wrappers run internally — populates fields
    // tagged `path:"<name>"` from c.Params("<name>").
    if badField, ok := fwweb.BindPath(c, &req); !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    crit, badField, ok := byEmailParser.Parse(c)
    if !ok {
        return fwweb.RespondSchemaViolation(c, pipe, badField)
    }
    q := req.ToQuery(crit)
    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if result.IsSuccess() {
        return fwweb.RespondWithSuccess(c, fiber.StatusOK,
            fwresponses.AutoFromDoc[requests.FindXxxByEmailResponse](result.Value()))
    }
    return fwweb.RespondFromResult(c, result, fiber.StatusOK)
})

Projection is shared infrastructure. Manual query handlers should pair with fwresponses.AutoFromDoc[R] (tag-driven default) or fwresponses.RawDoc (passthrough) — the same projectors the canonical wrappers consume. Hand-rolling a FromDoc that walks doc["id"], doc["name"], etc. is a redundant rewrite of what AutoFromDoc already does (json:/view: tags, _id → id fallback, PascalToSnake source-key translation, nil→empty-slice normalization). Declare a consumer R{}.FromDoc method only when the projection needs logic AutoFromDoc cannot express (derived fields computed from multiple doc keys, conditional shaping, ctx-aware projection).

For envelopes that need sidecar fields (custom keys outside data/pagination), use fwweb.ProjectPage instead of RespondPaged and build the Response struct by hand — the projector and the pagination cursor are still framework-managed.

6. path: tag — universal URL-segment binding

Every Request DTO field tagged path:"<name>" is populated from the matching Fiber URL segment (c.Params("<name>")) before ToCommand / ToQuery runs. Closes the asymmetry between the canonical wrappers (which only auto-bind :id via the pipeline.CommandWithID / queries.FindByIDQuery interface) and routes with custom identifier segments (:email, :tenantId, …) or compound paths (/tenants/:tenantId/users/:id). 

// Read by-email — single segment route
type FindUserByEmailRequest struct {
    Email           string `path:"email"`
    IncludeArchived *bool  `query:"includeArchived"`
}
func (r FindUserByEmailRequest) ToQuery(crit fwqueries.ReadCriteria) *queries.FindUserByEmailQuery { ... }

// Compound route — both segments via tag
type UpdateOnTenantRequest struct {
    TenantID string `path:"tenantId"`   // /tenants/:tenantId/users/:id — :id still via interface on WithBodyID
    Name     string `json:"name"`
}

Per-wrapper behavior — :id-binding wrappers (HandleCommandWithBodyID, HandleQueryWithID) panic at boot if the Request declares path:"id" (it would set the same value twice); Group A wrappers (HandleCommandWithBody, HandleQueryWithParams) accept path:"id" for compound routes — map cmd.SetPathID(r.ID) inside ToCommand. HandleCommandWithID has no Request DTO and is excluded from path-binding entirely.

Manual fiber.Handler closures opt out of the wrappers — call fwweb.BindPath(c, &req) explicitly (same helper as ParseCriteria). See omnicore-example-users/web/user_custom_routes.go for the canonical example of BindPath → Bind().Body() → ToCommand → Dispatch.

Supported field types: string, signed/unsigned ints of any width, float32/float64, bool, uuid.UUID, domain.ID. Pointer/slice/struct types are rejected at boot. Conversion failure returns 400 SchemaViolationNotification with the segment name.

FullBody interaction. The strict-body check in HandleCommandWithBody{,ID} skips fields carrying a path: tag — their value comes from the URL, not the body. Declaring both path:"X" and json:"X" on the same field is a boot panic; the same value cannot come from two sources.

Group A wrapper + ID-requiring handler warning. When HandleCommandWithBody / HandleQueryWithParams (no :id auto-bind) is paired with an ID-requiring auto handler (Update/PartialUpdate/Archive/Unarchive/Delete) AND the Request DTO declares no path: tag at all, the wrapper logs a single slog.Warn at construction time. Catches the misconfiguration of "I expected the wrapper to populate the ID" — the runtime guard handlers.RequirePathID still catches the actual failure if the warning is ignored. FindByIDQueryHandler is excluded from the warning because its Group A wrapper does not compile with the handler's constraint.

Runtime guard. Each ID-requiring auto handler calls handlers.RequirePathID(<pathID>, "<HandlerName>") as the first line of Handle. Empty path ID → developer-focused panic, caught by pipeline.Run's defer/recover, surfaced to the wire as 500 InternalServerErrorNotification; full diagnostic on slog. Each handler also embeds pipeline.PathIDRequired so the wrappers can detect the requirement via type assertion at construction time (zero per-request cost).

4. Configure the SyncEngine at boot

// cmd/service/main.go
pg, _ := infra.NewPostgres(ctx, postgresDSN)
mongo, _ := infra.NewMongoDB(ctx, mongoURI, "salesdb")

sync := infra.NewSyncEngine(pg, mongo,
    []string{"kafka:9092"},  // brokers
    "svc-sales",             // groupID
    []*infra.ViewDefinition{ // views of this service
        views.SaleView,
    },
    runtime.NumCPU(),        // workers: pool bucketed by aggregate_id
                             // (per-aggregate ordering preserved).
                             // In bootstrap.Run, comes from yaml kafka.syncWorkers.
                             // Use 1 to opt out (serial mode).
)
sync.Start(ctx)
// SyncEngine.Start is fire-and-forget. Internally the engine pre-creates the
// Kafka topics (idempotent CreateTopics, ignores TopicAlreadyExists) before
// instantiating the reader — necessary because kafka-go with GroupTopics gets
// stuck on JoinGroup when the topic does not exist in the broker metadata at
// subscribe time. Internal 30s retry covers the typical docker-compose boot
// race (Kafka coming up while the service has already started). Topics
// pre-created in production via external tooling return TopicAlreadyExists and
// are respected — defaults (1 partition / RF=1) only matter for dev.

// Cross-service composition via UpstreamSubscription (yaml-declared in
// microservice.<profile>.yaml; manual Wiring form shown for illustration).
// bootstrap.Run spins one infra.UpstreamSubscriber per entry and ripples
// recompose to every view embedding the materialized collection via FromMongo.
return bootstrap.Wiring{
    UpstreamSubscriptions: []bootstrap.UpstreamSubscription{
        {Topic: "people.customers.events", Collection: "customers",
         Filter: []string{"id", "name", "cpf"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
        {Topic: "catalog.products.events", Collection: "products",
         Filter: []string{"id", "name", "price"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
    },
}

Persistent failure registry. Every ripple failure (discover / compose / upsert stage) is upserted into the framework PG table omnicore_upstream_failures alongside the slog line and the in-memory counter. The natural key (subscription_topic, view_name, upstream_id, local_id, stage) turns retries into attempt increments — the table mirrors live state, never grows monotonically. A recompose round that finishes without errors for (view, upstream_id) automatically marks any pending rows under that coordinate as resolved (resolved_at = NOW()). Writes are best-effort: any PG error on Record/Resolve is logged at slog.Warn and discarded — the consumer's Kafka offset still advances, preserving the failure-isolation contract.

Operational queries (SQL on B's framework PG):

-- Currently stale entities:
SELECT subscription_topic, view_name, upstream_id, local_id, stage, attempt,
       last_attempt_at, error
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
ORDER BY last_attempt_at ASC;

-- Top offending views (recurring failures may indicate a deterministic Composer bug):
SELECT view_name, count(*) AS pending
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
GROUP BY view_name
ORDER BY pending DESC;

Retry surface. UpstreamSubscriber.RetryPendingFailures(ctx) (retried int, err error) is the public runtime API: it lists pending failures by the subscriber's topic, deduplicates by upstream_id, and re-runs ripple for each unique id. Idempotent — a successful re-ripple calls ResolveUpstreamFailures, so the next call against a drained slate is a no-op. The framework owns the primitive; the consumer decides how to expose it (in-process ticker, authenticated HTTP endpoint, or admin RPC).

Inspection CLI. omnicore-admin upstream-list-failures [--topic <name>] [--view <name>] [--format text|json] [--limit N] is the read-only triage tool: runs in B's process (loads microservice.${APP_PROFILE}.yaml), reads the table, prints text or JSON. The CLI binary has no Wiring of B and cannot call RetryPendingFailures — actual retry lives on the runtime API above.

5. Client does GET with dynamic filters

GET /users?email.in=a@x.com,b@y.com&sort=-created_at&limit=20

→ filters emails by inclusion ($in applied)
→ orders by created_at descending
→ returns 20 + cursor for the next page

GET /users/<id>?includeArchived=true

→ returns even if soft-deleted (deleted_at IS NOT NULL)

GET /users?role=admin

→ 400 SchemaViolationNotification — "role" is not in the allowlist
Result: with a Request DTO that declares the allowlist via struct tags, a thin Query that owns its persistence shape via ToCriteria(ctx), and two route lines, the developer gets the read side wired end-to-end. Unknown fields and operators are rejected at the wire boundary; not-found surfaces as 404; pagination lives top-level in the envelope; and AppContext-derived security filters layer onto the criteria inside ToCriteria(ctx) without changing any other signature.
