TableSchema — Go ↔ column mapping (PG + Mongo views)

Everything above infrastructure speaks the Go field name (PascalCase) — domain, application, and web. The criteria you write is criteria.Eq("Email", v); the audit timeline says Email; repository signatures speak the domain. The only place a physical column or table name appears is the persistence boundary, and it appears in exactly one artifact: TableSchema. A schema is the mandatory, explicit, complete map between a Go type's fields and its physical columns — Go field on one side, DB column on the other. There is no convention, no name-inference, no transient tag: every persisted field is declared, and an undeclared exported field is simply never persisted, scanned, or audited.

One TableSchema drives three consumers from a single declaration: the write path (INSERT/UPDATE/archive SQL), the criteria engine (the WHERE a Go-named criterion compiles to), and the auto-scan read-back (column → Go field). The same schema is reused by the read-side ViewDefinition, so the Mongo projection speaks the same names. Because every name is declared in one place, a column rename round-trips everywhere automatically — write, criteria, scan, and the Mongo view all move together.

Why it exists — and why it is mandatory

The schema is declared by hand, and is required. That is a deliberate design stance, not an oversight — it buys four things a convention-based scheme cannot:

  • A pure DDD domain. The domain (and the application and web layers above it) never pronounce a table or a column — they speak only business vocabulary (Email, ZipCode). The single place a physical name exists is the TableSchema, which lives in infra/. The entity stays an expression of the business, not a mirror of the database.
  • Real, transparent mapping flexibility. The developer maps each Go field to any column name explicitly, and that mapping is transparent to every line of implemented code: handlers, commands, queries and BuildRules are written against the Go field and never change when a column is named differently. A rename lives in exactly one place and round-trips across the write path, the criteria engine, the scan-back and the Mongo view at once.
  • Mapping columns whose names you do not control. Because the map is explicit, you can point the framework at a table whose physical names you did not choose — a column renamed away from its Go field, or an upstream service's collection via NewExternalSchema — declaring field by field how each maps to your domain. What this buys is freedom over names (column and table), not over structural shape: the table must still fit the framework's assumptions — a single-column non-composite primary key, a timestamp-based soft-delete column when the entity is archivable, and one of the supported column shapes. Adopting a schema that breaks those assumptions is explicitly out of scope.
  • No failed, tiring conventions. Name-inference (PascalToSnake + pluralize) is lossy and acronym-hostile: UserID and UserId both collapse to user_id; URLPath, IPv4, HTTPStatus mangle; and the moment the real column diverges from the guess, the failure is silent. An explicit map removes the guessing entirely — a wrong field name is a boot panic, not a column that silently never persists.

Those four together are why the declaration is obligatory and manual: the map is the single, lossless, unambiguous source of truth the whole persistence + read membrane depends on, so the framework refuses to fabricate it from a fragile convention.

The three-name model

A field can carry up to three independent names, resolved at two membranes:

SurfaceNameDeclared by
Wire (JSON / query string)myEmailjson:"…" / query:"…" tags in web/
App / domain (Go field)Emailthe Go struct field — the single name every layer above infra uses
Physical (PG column / Mongo doc key)mailTableSchema.Field("Email", "mail") in infra/

The wire name and the physical name are invisible to the developer manipulating data — handlers, commands, queries, and BuildRules only ever say Email. The web membrane (json/query tags) translates JSON ↔ Go; the infra membrane (TableSchema) translates Go ↔ column. Mongo mirrors PostgreSQL physically (the composer writes columns verbatim), and the reader translates each column back to its Go field name before the typed Response projects to the wire — so the wire surface speaks Go names without any per-Response source-key override.

Declaring a schema

A type-anchored schema validates every field against the Go type at construction — a Field naming a missing or unexported field panics immediately, which is the enforcement that replaces convention. A type-less external schema describes an upstream service's columns for an external FromSchema embed source (there is no local struct to validate against). 

// Type-anchored — validated against *User at call time.
func UserSchema() *fwinfra.TableSchema {
    return fwinfra.NewTableSchema[*User]("users").
        PK("id").                       // column "id" — Go side fixed to ID (single-column PK)
        Field("Name", "name").
        Field("Email", "mail").         // renamed column
        Field("Phone", "phone").
        SoftDelete("deleted_at").       // managed: presence enables the predicate
        CreatedAt("created_at").        // managed: framework stamps NOW() on INSERT
        UpdatedAt("updated_at").        // managed: framework stamps NOW() on INSERT + UPDATE
        Child(AddressSchema())          // aggregate child, keyed by Go type name
}

func AddressSchema() *fwinfra.TableSchema {
    return fwinfra.NewTableSchema[Address]("addresses").
        PK("id").
        FK("user_id").                  // FK to the root — injected by the persister
        Field("Street", "street").
        Field("ZipCode", "zip_code").
        SoftDelete("deleted_at").
        CreatedAt("created_at").
        UpdatedAt("updated_at")
}

// Type-less — for an upstream-projected external FromSchema source (no local struct).
fwinfra.NewExternalSchema("users").PK("id").Field("Email", "mail")

The Go-side primary-key field is fixed to ID by the BaseEntity/AVO contract (an aggregate root carries it privately and exposes GetID/SetID; an AVO exposes the exported field ID), so PK("col") declares only the column. FK names the child's foreign-key column referencing the root — it is injected by the persister and is not a struct field. Every other persisted field is a Field("Go", "column") pair.

Field labels on external schemas — Field(go, col, labelKey). The human-facing field label (consumed by notifications, audit, and the tabular export's column headers) normally comes from a labelKey:"<catalogKey>" struct tag on the domain field. A type-less NewExternalSchema has no struct to carry that tag, so it declares the label inline as an optional third argument: NewExternalSchema("users").Field("Name", "name", "PartnerNameField"). This is the "mini-domain" for upstream columns that have no real domain home. It is external-only: passing a label on a type-anchored NewTableSchema[T] is a boot panic — that schema declares the label through the field's labelKey: tag, and the framework never offers two ways to express one domain concept.
Aggregate depth is exactly one — no grandchildren in the schema. A root may declare any number of child types (one Child(...) per AggregateValueObject type) and each child may have any number of instances — width is unlimited. Depth is not: calling Child(...) on a schema that is itself a child (a grandchild) is a boot panic. Aggregate persistence is root + one level in a single transaction; a grandchild would silently never persist. Model the sub-collection as a separate aggregate (its own root + FK). Need nesting on the read side? That is supported — but through nested EmbedMany(...) / Embed(...) on the view's embed source, never through the schema's Child(...); an embed source whose schema carries Child(...) is a fatal view-validation error at boot.

The three managed columns — by presence, not a flag

Soft-delete, created-at, and updated-at are declared by calling the matching builder method with the column name. Omitting the call disables the behavior — there is no boolean knob.

BuilderDeclaredOmitted
SoftDelete(col) the read scope-gate uses col IS NULL; Archive/Unarchive write col = NOW() / col = NULL no scope-gate; Archive/Unarchive unavailable (boot check + runtime guard)
CreatedAt(col) the framework stamps col = NOW() on INSERT no creation timestamp stamped
UpdatedAt(col) the framework stamps col = NOW() on INSERT and UPDATE buildUpdate omits the SET

The framework actively generates these timestamps — it never relies on a DB DEFAULT NOW() it does not own. The soft-delete predicate shape is fixed (nullable timestamp: IS NULL = active); the schema controls only the column's name and presence. On the read path these three columns are also readable under fixed logical Go names (CreatedAt, UpdatedAt, DeletedAt) so a view can project them without a domain Go field.

One declaration, every consumer — WithSchema

Declare the schema once and thread it with BaseAggregateRepository.WithSchema(schema): it feeds BOTH the write binding and the read loader, so the write path, the criteria translator, and the scan-back all agree on the same columns. The Modes() ⟺ SoftDelete boot check runs here; the field-existence and bijection checks already ran while the schema was built. A misconfiguration panics at construction, not on the first request. 

func NewUserRepository(pg *fwinfra.Postgres) *UserRepository {
    r := &UserRepository{
        BaseAggregateRepository: fwinfra.NewBaseAggregateRepository[*User](
            pg, func() *User { return &User{} },
        ),
    }
    r.Constraints = map[string]fwinfra.ConstraintBinding{ /* … */ }
    r.WithSchema(UserSchema())   // one schema → write + criteria + scan + children
    return r
}

The same schema drives the Mongo view

The read-side ViewDefinition reuses the very same schemas. The root schema is attached via .Schema(...); each embed source is constructed from a schema via fwinfra.FromSchema(...) — the single embed source constructor. From the schema the framework derives the table/collection (ts.Table()), the store kind (a type-anchored NewTableSchema[T] → a local Postgres source; a type-less NewExternalSchema → an external/Mongo source), and — for an EmbedMany — the join FK (ts.FKColumn()). The composer writes physical columns to Mongo; the reader translates each leaf back to its Go field name using these schemas (so mail → Email, zip_code → ZipCode). For a local (type-anchored) embed the parent-side Go segment is derived from the schema's Go type — pluralized for an EmbedMany (Address → Addresses), the type name for a one-to-one Embed — so .As(...) is only an optional override. The view also honors the schema's soft-delete column when DeleteOnArchive is set. 

func UserView() *fwinfra.ViewDefinition {
    return fwinfra.View("users").
        Version(1).
        Root("users").
        Schema(UserSchema()).
        EmbedMany("addresses", fwinfra.FromSchema(AddressSchema())).  // segment derived → "Addresses"
        Indexes( /* … */ )
}

Filter keys on the read side are always Go paths (the request DTO's filter: leaves resolve to Go field names, translated to columns by the schema). Sort and projection translate Go → column only when a typed Response is in scope; RawDoc / ParseCriteria callers pass through verbatim. The typed Response projector (AutoFromDoc) keys by the Go field name — the reader already translated the doc — so the view: source-key override is gone; the only tag that governs the wire shape is json:.

External (cross-service) embeds — no local struct. When a view embeds data owned by another service (materialized locally via an UpstreamSubscription), there is no Go struct in this service to anchor the embed's schema. Build the source from a type-less NewExternalSchema(collection) and pass it to fwinfra.FromSchema(...) — the schema being type-less is the very signal that makes it an external/Mongo source (no separate FromMongo constructor). The left side of each Field is the logical Go name the local view's Response/criteria speak; the right side names the upstream's physical column. It is validated by bijection (no two fields share a column) but not against any type — there is none. Because an external source has no Go type to derive a segment from, .As(...) is required (a fatal boot error otherwise). .On(...) is the parent document's FK column pointing at the source's PK — used only on a one-to-one Embed. 

// Cross-service embed — buyer projected from the upstream users service.
func OrdersView() *fwinfra.ViewDefinition {
    return fwinfra.View("orders").
        Version(1).
        Root("orders").
        Schema(OrderSchema()).
        Embed("buyer", fwinfra.FromSchema(
            fwinfra.NewExternalSchema("users").  // type-less: names the UPSTREAM's columns
                PK("id").
                Field("Name", "name").
                Field("Email", "mail")).         // logical Go name ↔ upstream column
            On("buyer_id").                      // parent doc FK pointing at the source PK
            As("Buyer")).                        // REQUIRED — external embeds have no Go type to derive from
        Indexes(fwinfra.Index("buyer_id"))       // boot guard requires the join-field index
}

Schema is mandatory on every view. The root (ViewDefinition.Schema(ts)) and every embed (FromSchema always carries one) must declare a schema. A missing root schema, or an external embed missing .As(...), is a fatal boot error via infra.ValidateViewSchemas(views) (called by bootstrap.Run). There is no optional / pass-through / schema-less mode. Local (type-anchored) embeds derive their parent-side Go segment from the schema's Go type, so .As(...) is an optional override there; external (type-less) embeds inherit nothing from Go and must declare the segment via .As(...).

Boot checks

  • Field exists on the type — NewTableSchema[T] + Field panic at construction when the named field is absent, unexported, or promoted from an embed. This is what replaces convention: a typo is a boot panic, not a silent miss.
  • Bijection over the whole column set — across each source's mapped fields + the PK column + every declared managed column, no two map to the same physical column. The collision panic names both offenders.
  • Modes() ⟺ SoftDelete — an entity declaring ModeArchive/ModeUnarchive without SoftDelete panics; a runtime guard backs it up.
  • PK is mandatory (no default) + single-column — every schema (root, child, embed source) must declare its PK column via PK(column), which rejects an empty column. The Go side is fixed to the Entity contract's ID (never guessed from the column name). A schema reaching WithSchema / Child / ValidateViewSchemas without a declared PK is a boot failure. Single-column only.
  • FK on children + embed join keys — an aggregate Child(...) without .FK(col) panics (the persister injects the root id into it). On the read side, an EmbedMany source without .FK(col), and a one-to-one Embed without .On(col), are fatal ValidateViewSchemas errors.
  • Aggregate depth = 1 (no grandchildren) — a child schema that declares its own Child(...) panics at WithSchema (write side); an embed source whose schema carries Child(...) is a fatal error in ValidateViewSchemas (read side). Width is unlimited; depth is one.
  • Aggregate boundary agreement — the types the domain declares via AggregateChildren() and the types the schema declares via .Child(...) must name the same set. BaseAggregateRepository.WithSchema panics naming any type declared on only one side: a .Child(...) with no AggregateChildren() entry would be silently load-only; an AggregateChildren() entry with no .Child(...) would error per-write deep in the persister.

These checks run inside WithSchema on both repository shapes: BaseAggregateRepository.WithSchema (aggregate) and BaseRepository.WithSchema (flat, non-aggregate) each run the PK-declared, aggregate-depth, and Modes() ⟺ SoftDelete checks at construction (the aggregate path additionally runs the boundary-agreement check and threads the schema into the read loader). Calling WithSchema also surfaces a nil NewEntity factory at construction. Assigning r.Schema directly still works as the unchecked escape hatch — WithSchema is the validated canonical entry.

Audit stays in the domain vocabulary

Audit does not consume the schema. The timeline's snapshot keys and changes[].field are the faithful Go field name (Email, ZipCode), never the physical column. A column rename therefore never disturbs the audit history. The labelKey:"…" field labels resolve by Go field name too.

Manual scanners bypass the schema by design

WithRootScanner / WithChildScanner hand the SELECT and the scan to the developer, who owns the column names directly. The schema governs the auto-scan path; the manual path stays a full escape hatch (a manual root scanner used with FindOne/FindAll must populate the id itself).

Supported column shapes — Go ↔ PostgreSQL

The framework is fixed to two engines — PostgreSQL and MongoDB. There is no pluggable database layer today. PostgreSQL is the authoritative write store and the only backend the SQL/criteria engine emits for: the executor (INSERT/UPDATE/archive), the entity-search criteria engine, and the auto-scan read-back are all PostgreSQL-specific (driven by pgx v5). MongoDB is the only read-side projection store — the composer, the ViewDefinition surface, the Mongo schema-evolution control plane, and the ?fields / ?sort / keyset-pagination reader all target MongoDB exclusively. The criteria package keeps a backend-neutral Visitor seam (the IR a future translator could implement), but the only translator that ships is the PostgreSQL one. Everything below describes the Go ↔ PostgreSQL column shapes the write/criteria/scan engine handles.

The schema declares which Go field maps to which column; this section is about what types those columns may be. The engine does no custom type registration: on write, TableSchema.writeFields binds the raw Go value (reflect Field(i).Interface()) straight to pgx; on read, the auto-scanner passes the address of the Go field straight to pgx.Scan; in the criteria engine, only domain.ID is unwrapped (to its string value) before binding. So the supported set is exactly pgx v5's default codec set — nothing the framework adds, nothing it takes away.

string  (domain.ID at the entity boundary) UUID the framework's canonical UUID representation. The PK and every FK are bound and scanned as Go strings — pgx parses the textual form into / out of the uuid column. There is no google/uuid.UUID field mapping (see the note below).

Nullability is a pointer. A column declared NULL-able maps to a Go pointer (*string, *int64, *time.Time, …): pgx writes NULL for a nil pointer and reads NULL back as nil. There is no wrapper type — the pointer is the canonical nullable form. A non-pointer field on a nullable column will fail to scan a NULL row.

The escape hatch for anything pgx does not know natively. Because the engine registers no custom codecs, a Go type pgx cannot encode/decode out of the box — google/uuid.UUID, a typed Go enum, a PostGIS geometry, a bespoke domain type — cannot be a persisted field as-is. Two supported ways out: (1) map the column to one of the pgx-native Go types above (a UUID column → Go string, an enum → its underlying string/int); or (2) drop to a manual scanner (WithRootScanner / WithChildScanner), where you own the SELECT and the Scan and can decode any shape pgx supports through an explicit target.

Out of scope

  • Adapting to non-conforming structural conventions. The schema maps names, it does not reshape a schema. Mapping a renamed column on an otherwise-conforming legacy table is supported; adapting to a shape the framework does not manage is not — predicate-shaped soft-delete (a boolean/enum flag instead of a timestamp column), a composite PK, and exotic column types outside the supported shapes are all rejected. The scope is "an explicit map over the schema the framework manages", not "adapt to any arbitrary schema".
