TableSchema — Go ↔ column mapping & normalization

Everything above infrastructure speaks the Go field name (PascalCase) — domain, application, and web. The criteria you write is criteria.Eq("Email", v); the audit timeline says Email; repository signatures speak the domain. The only place a physical column or table name appears is the persistence boundary, and it appears in exactly one artifact: TableSchema. A schema is the mandatory, explicit, complete map between a Go type's fields and its physical columns — Go field on one side, DB column on the other. There is no convention, no name-inference, no transient tag: every persisted field is declared, and an undeclared exported field is simply never persisted, scanned, or audited.

One TableSchema drives three consumers from a single declaration: the write path (INSERT/UPDATE/archive SQL), the criteria engine (the WHERE a Go-named criterion compiles to), and the auto-scan read-back (column → Go field). The same schema is reused by the read-side ViewDefinition, so the Mongo projection speaks the same names. Because every name is declared in one place, a column rename round-trips everywhere automatically — write, criteria, scan, and the Mongo view all move together.

Why it exists — and why it is mandatory

The schema is declared by hand, and is required. That is a deliberate design stance, not an oversight — it buys three things a convention-based scheme cannot, and unlocks a fourth capability convention could never express: automatic third-normal-form modeling, called out on its own below.

  • A pure DDD domain. The domain (and the application and web layers above it) never pronounce a table or a column — they speak only business vocabulary (Email, ZipCode). The single place a physical name exists is the TableSchema, which lives in infra/. The entity stays an expression of the business, not a mirror of the database.
  • Transparent mapping flexibility — including names you do not control. The developer maps each Go field to any column name explicitly, and that mapping is transparent to every line of implemented code: handlers, commands, queries and BuildRules speak the Go field and never change when a column is named differently — a rename lives in exactly one place and round-trips across the write path, the criteria engine, the scan-back and the Mongo view at once. Because the map is explicit rather than inferred, you can just as well point the framework at a table whose physical names you did not choose — a legacy column renamed away from its Go field, or an upstream service's collection via NewExternalSchema — declaring field by field how each maps to your domain. What this buys is freedom over names (column and table), not over structural shape: the table must still fit the framework's assumptions — a single-column non-composite primary key, a timestamp-based DeletedAt column when the entity is archivable, and one of the supported column shapes. Adopting a schema that breaks those assumptions is explicitly out of scope.
  • No failed, tiring conventions. Name-inference (PascalToSnake + pluralize) is lossy and acronym-hostile: UserID and UserId both collapse to user_id; URLPath, IPv4, HTTPStatus mangle; and the moment the real column diverges from the guess, the failure is silent. An explicit map removes the guessing entirely — a wrong field name is a boot panic, not a column that silently never persists.

Those three together are why the declaration is obligatory and manual: the map is the single, lossless, unambiguous source of truth the whole persistence + read membrane depends on, so the framework refuses to fabricate it from a fragile convention. And because that source of truth is explicit and complete, it can carry far more than a flat name-for-name mapping — which is where the fourth, headline capability comes in.

The headline capability — one flat domain entity, automatically modeled in third normal form.

This is the thing no convention-based mapper can offer, and it is where the explicit schema stops being a concession and becomes an advantage. You model your entity the way the business reads it — one linear, natural Go struct, with none of the foreign keys, join tables, or surrogate-key bookkeeping a normalized store implies. The TableSchema alone then declares how that single struct decomposes into a fully normalized (3NF) physical layout across as many tables as the design needs, and the framework runs the decomposition both ways: it normalizes on write — splitting the entity across those tables inside one transaction — and denormalizes on read — re-joining them into the exact flat struct you modeled on FindOne/FindAll. The domain never sees a seam: no DAO to hand-write, no join to keep in step, no mapping code to drift out of sync with the struct. When the question is a scalar rather than an entity — does one exist, how many, what do they total or average — the same criteria surface carries the hydration-free primitives: Exists and the aggregate DSL Aggregate(ctx, q, specs…) (any combination of Count/SumInt/Sum/Avg/MinInt/MaxInt/Min/Max specs in one SELECT): same schema resolution and scope gate, no re-join, no loading — see Custom command handler → Loading by criteria.

Three declarative partitioning tools cover the three cardinalities a third-normal-form decomposition ever needs, and you compose them freely on a single schema:

  • .Child — 1 : N. A repeating collection lifts out of the entity into its own table, linked back by a foreign key the persister injects — the aggregate child, in its own row.
  • .Sibling — 1 : 1. A disjoint slice of the same entity's fields moves to a secondary table sharing the primary key: peel bulky, optional, or rarely-read facets off a hot row with zero change to the domain type.
  • .SharedBase — N : 1. Fields that describe a shared identity (the party-role pattern) collapse into one deduplicated identity table referenced by every role — the transitive-dependency removal at the heart of 3NF.

The SharedBase case is the sharpest demonstration of how deep this goes. The framework derives the identity's primary key as a deterministic UUIDv5 of its natural key, so two writes carrying the same identity reach the same row with no read-back and no round-trip — the persister and the application compute the same id independently, before either touches the database. Deduplication stops being a query you remember to write and becomes a structural property of the key itself.

And none of it leaks upward. The decomposition is declared on the very same schema the write path, the criteria engine, and the Mongo read-view already consume, so it stays invisible to every layer above infra/ and round-trips identically on PostgreSQL, on MySQL, and into the composed read model. You get textbook-normalized storage and a clean, aggregate-shaped domain at the same time — with the schema, not a hand-written data-access layer, as the single source of truth. See “Normalizing a flat entity” below for the full mechanics.

The three-name model

A field can carry up to three independent names, resolved at two membranes:

The wire name and the physical name are invisible to the developer manipulating data — handlers, commands, queries, and BuildRules only ever say Email. The web membrane (json/query tags) translates JSON ↔ Go; the infra membrane (TableSchema) translates Go ↔ column. The trap this table exists to kill — the Result's field NAME is the lookup key; the Response's json: tag is not. queries.ResultFromDoc fills a Result by reading doc[<GoFieldName>] from the Go-keyed document, so a field named after the physical column reads nothing — and stays zero silently (the fill is by name; absence is legal). core.NewTableSchema[*Order]("orders").

// this field reads doc["ArchivedOn"], finds nothing, stays null. No error.
type OrderResult struct {
    ArchivedOn *time.Time
}
type OrderResponse struct {
    ArchivedOn *time.Time `json:"archivedOn"`   // aligned with the Result, but fed by nothing
}

type OrderResult struct {
    DeletedAt *time.Time
}
type OrderResponse struct {
    DeletedAt *time.Time `json:"archivedOn"`
}

Symptom → cause. A wire field that is always null/zero with no error: the Result's Go name does not match the view's logical name — a managed slot renamed (as above) or a Field Go name typo. The Request side fails LOUDLY for the same mistake: a ?filter/?orderBy/?fields= token that resolves to no logical name is 400 SchemaViolationNotification. Silent on the way out, loud on the way in — if a filter on the field 400s, the Response field with that name is empty for the same reason.

Declaring a schema

A type-anchored schema validates every field against the Go type at construction — a Field naming a missing or unexported field panics immediately, which is the enforcement that replaces convention. A type-less external schema describes an upstream service's columns for an external JoinUpstream embed source (there is no local struct to validate against). 

// Type-anchored — validated against *User at call time.
func UserSchema() *core.TableSchema {
    return core.NewTableSchema[*User]("users").
        ID("id").                       // column "id" — Go side fixed to ID (single-column ID)
        Revision("revision").           // managed: MANDATORY commit-order token (BIGINT NOT NULL DEFAULT 0)
        Field("Name", "name").
        Field("Email", "mail").         // renamed column
        Field("Phone", "phone").
        DeletedAt("deleted_at").       // managed: presence enables the predicate
        CreatedAt("created_at").        // managed: framework stamps the operation's instant on INSERT
        UpdatedAt("updated_at").        // managed: framework stamps the operation's instant on INSERT + UPDATE
        Child(AddressSchema())          // aggregate child, keyed by Go type name
}

func AddressSchema() *core.TableSchema {
    return core.NewTableSchema[Address]("addresses").
        ID("id").
        ParentID("user_id").                  // ParentID to the root — injected by the persister
        Field("Street", "street").
        Field("ZipCode", "zip_code").
        DeletedAt("deleted_at").
        CreatedAt("created_at").
        UpdatedAt("updated_at")
}

// Type-less — for an upstream-projected external JoinUpstream source (no local struct).
core.NewExternalSchema("users").ID("id").Field("Email", "mail")

The Go-side primary-key field is fixed to ID by the BaseEntity/AVO contract (root and AVO alike carry it privately through the embedded domain.Managed carrier — the root via BaseEntity — and expose GetID/SetID; an AVO declares no id field of its own, its id is set with domain.WithID/SetID), so ID("col") declares only the column. ParentID names the child's foreign-key column referencing the root — it is injected by the persister and is not a struct field. Every other persisted field is a Field("Go", "column") pair. Because the persister owns the ParentID column (the write cascade sets it to the parent's id on every save), that column cannot ALSO be a mapped Field — the write would silently overwrite the field's value — so declaring both, in either order, is a boot panic. The shared-ID model, where the ID column IS the ParentID, is unaffected: the ID is never a mapped field, so the guard never fires on it.

Exposing the ParentID on read — ParentID, the read-only twin of ID. Symmetric with the primary key, the foreign key is exposed read-only under the fixed logical Go name ParentID: a view/DTO that declares a ParentID field (its json: tag chooses the wire name) receives the parent link, and a filter / orderBy / ?fields= on it is a real query, not a dead field — it resolves to the physical ParentID column. You never map it: it is projected automatically whenever the schema declares a ParentID, exactly as ID is projected from the ID. Like ID, ParentID is a reserved Go name — Field("ID", …) and Field("ParentID", …) are both boot panics. A schema carries at most one ParentID (an aggregate child's ParentID to its root, or a SharedBase role's ParentID to its base — declaring ParentID(...) and SharedBase(...) together is a boot panic), so ParentID is unambiguous.

Field labels on external schemas — Field(go, col, labelKey). The human-facing field label (consumed by notifications, audit, and the tabular export's column headers) normally comes from a labelKey:"<catalogKey>" struct tag on the domain field. A type-less NewExternalSchema has no struct to carry that tag, so it declares the label inline as an optional third argument: NewExternalSchema("users").Field("Name", "name", "PartnerNameField"). This is the "mini-domain" for upstream columns that have no real domain home. It is external-only: passing a label on a type-anchored NewTableSchema[T] is a boot panic — that schema declares the label through the field's labelKey: tag, and the framework never offers two ways to express one domain concept.

A NewSharedBaseSchema is type-less too, so it accepts the inline form — but it rarely needs it: the shared columns live flat on the ROLE struct, which already declares them with a labelKey: tag, and every label consumer (audit deltas, CSV/XLSX headers) composes the base with the role type to recover them by field name. Declare the inline label on the base only for a shared column no role tags, or to override every role at once — an inline label wins over the role's tag.
Aggregate depth is exactly one — no grandchildren in the schema. A root may declare any number of child types (one Child(...) per AggregateValueObject type) and each child may have any number of instances — width is unlimited. Depth is not: calling Child(...) on a schema that is itself a child (a grandchild) is a boot panic. Aggregate persistence is root + one level in a single transaction; a grandchild would silently never persist. Model the sub-collection as a separate aggregate (its own root + ParentID). On the read side, a schema's own children (like a shared base's children) project automatically into the Mongo view — the composer nests each declared Child(...) wherever the schema is used, so a child on a view root or on an embed leg is materialized, not ignored. Each collection lands under the segment its type declares in CollectionName() — a child type that declares none is a boot panic at the Child(...) call, as are two children of one schema declaring the same name. An embed leg cannot declare a further Embed(...) / EmbedMany(...), though — a leg exposes no such builder, so embed-of-embed does not compile (embeds are single-level per declaration; depth beyond one hop comes from a JoinView source's own embeds, from a second top-level embed, or from a read-time ComposedView). A redundant explicit embed of a child the schema already projects (same derived segment) is still a boot error.

A child's DeletedAt declares how that child is removed, the same way it does on a root: declared, and removing an item archives the row; absent, and removing it deletes the row (its sibling rows first). The rule, its three consequences and what it means for the child's route are in What a child's DeletedAt declares.

Decomposing a composite value object

A composite value object — a struct that owns its rule and declares no Value(), so its value spans several fields — cannot be a single column. The schema is the only place that knows it is stored across several: it resolves the entity field by type, and each part is a field ↔ column pair like any other. 

NewTableSchema[Contract]("contracts").
    ID("id").
    Field("Code", "code").
    Composite(core.NewCompositeValueObject[vos.Money]().
        Field("Amount",   "salary_amount").As("SalaryAmount").
        Field("Currency", "salary_currency").As("SalaryCurrency")).
    Composite(core.NewCompositeValueObject[vos.Period]().
        Field("From", "trial_from").As("TrialFrom").
        Field("To",   "trial_to").As("TrialTo")).
    CreatedAt("created_at")

It is declared the way every other sub-object of a schema is — a constructor builds the whole thing with its own Field chain and the owner attaches it, exactly like Sibling(NewSiblingSchema[T](…).Field(…)):

  • core.NewCompositeValueObject[VO]() starts the declaration. The type is a parameter rather than a value, and the KIND is verified right here: passing a scalar or enum value object (one that declares Value()) fails pointing at this line.
  • Field(goName, column) declares one field of that value object. goName is the field's name inside it; the part is validated against the closed persistable set and typed exactly like a schema Field — value-object parts unwrapped to their underlying, a domain.ID part getting the identity treatment.
  • As(exposedName) renames the field declared immediately before it.
  • Composite(...) attaches the finished declaration, locating the entity field BY TYPE — vos.Money or *vos.Money, the optional form.

Because the parts are methods of the value object's own declaration, a part cannot escape it: calling Field/As of a part anywhere else does not compile.

Each part is registered under its exposed logical name: the part's own name by default, which is what reads right when the value object is specific (Address{Street, City, ZipCode} → street, city, zipCode), so most declarations never call As. Rename when the value object is generic — Money{Amount, Currency} on a salary field would otherwise expose ?amount=, and an entity carrying both a Money and a Discount would collide on Amount with no way out, since a part's name belongs to the value object rather than to the consumer. The alias moves the exposed name only; the labelKey still comes from the tag inside the value object, because the value object owns its own vocabulary for every entity that uses it.

Those exposed names are the same keys a hand-flattened field would produce, and that identity is the whole design: criteria, the audit timeline, the projected document, the read DTO, filters, orderBy, ?fields=, OpenAPI, GraphQL, gRPC and the tabular export never learn that a composite exists.

The once rule. Each composite value object type appears exactly once in an entity's schema graph — one Composite(...) across the root, every sibling and the shared base. What is capped is the number of appearances of one type, not the number of composites: an entity may carry as many different ones as its model calls for, and the same value object used by other entities is untouched.

Splitting one across two schemas is rejected because the read side cannot honor it: a sibling is loaded by a separate statement, and an absent sibling row leaves its half of the value object zeroed, so a split composite reconstructs half-built — and an optional composite's "every part NULL ⇒ absent" verdict cannot be reached by either half alone. The check runs at the boot checkpoint rather than at the declaration call, so the order between Composite and Sibling/SharedBase does not matter.

Every misuse is a boot panic that names the fix:

  • A composite declared with Field(...) → it spans more than one column; decompose it. Conversely, a scalar or enum value object passed to NewCompositeValueObject[VO]() → it occupies exactly one column; declare it with Field(...). The discriminator is the presence of Value().
  • A type that declares no IsValid → not a value object. Decomposition is not a way to flatten an arbitrary struct, and this is what keeps an entity from being modeled inside an entity. (A rule declared on the POINTER is called out separately — the framework validates the value.)
  • An entity carrying two fields of one composite type → resolution is by type, so there is nothing to pick from.
  • Part outside a decomposition; As not following a Part; a decomposition with no parts; a part that is not an exported field of the value object; a part's type outside the closed set.
  • A part tagged json:"-", or a composite type implementing json.Marshaler/ json.Unmarshaler — both poison the domain.Old() snapshot, which is a JSON round-trip of the entity. A custom marshaler is far more common on a value object than on an entity, which is why the guard exists.
  • A decomposition on a NewExternalSchema — it describes an upstream service's columns, not a local materialization. It is the only schema kind that cannot decompose: the root, a sibling, an aggregate child and a shared base all can. (A shared base is type-less, so its parts resolve against each role's struct at SharedBase(...) time — the role must carry the composite field itself.)

Mapping is partial by default, exactly like any undeclared field: a part you do not declare is not persisted, not scanned and not audited, and reconstructs as its zero value. Absence semantics for the value object as a whole — mandatory versus optional, and what "every part NULL" means — are in Value objects.

The managed columns — by presence, not a flag

The archive timestamp (deleted-at), created-at, and updated-at are declared by calling the matching builder method with the column name. Omitting the call disables the behavior — there is no boolean knob. The exception is Revision(col): on an entity schema (NewTableSchema[T] attached to a repository) and on a shared base (NewSharedBaseSchema) it is mandatory — omitting it is a boot failure; on a sibling or aggregate child it is forbidden — declaring it panics at construction, because their rows are guarded by the owner's token.

BuilderDeclaredOmitted
Revision(col) the framework owns the column end to end: INSERT binds col = 1; UPDATE, Archive and Unarchive append col = col + 1 to their own statement, under the row lock — so the value is the row's real commit order. It travels on the outbox payload (_ids.revision; a shared base's as _ids.base_revision) and the projection refuses any document write carrying an older value (the last-writer-wins guard) entity schema / shared base: boot failure (at the repository's WithSchema / at the role's .SharedBase(...) attach) — DDL required: revision BIGINT NOT NULL DEFAULT 0. Sibling or aggregate child: omitting is the ONLY valid state — declaring it panics at construction (Revision(...) itself, or the Child(...) attach)
DeletedAt(col) the read scope-gate uses col IS NULL; Archive/Unarchive write col = $now / col = NULL. The column needs sub-second precision — see the note below no scope-gate; Archive/Unarchive unavailable (boot check + runtime guard)
CreatedAt(col) the framework stamps col = $now on INSERT no creation timestamp stamped
UpdatedAt(col) the framework stamps col = $now on INSERT and UPDATE buildUpdate omits the SET

The framework actively generates these timestamps in Go — $now above is one application-clock instant minted per write operation (UTC, truncated to microseconds — the precision every supported backend stores) and bound as an ordinary argument, exactly like the Go-minted UUID v7 ids. No dialect NOW() expression appears in the data DML and the framework never relies on a DB DEFAULT NOW() it does not own; every statement of one operation (root, children, siblings, shared-base cascade) carries the SAME instant, known before COMMIT. The DeletedAt predicate shape is fixed (nullable timestamp: IS NULL = active); the schema controls only the column's name and presence. On the read path these columns surface under their FIXED logical Go names (CreatedAt, UpdatedAt, DeletedAt) whatever the physical column — the full naming contract, including the Response-DTO trap this creates, is The three-name model.

The DeletedAt column must carry sub-second precision, and a root and its children must agree on it. The stamp is not only a flag: it is the identity of the archive operation. One write mints one instant and binds it on the root row AND on every child row its cascade reaches, so the unarchive can bring back exactly those children — the ones carrying that instant — and leave a child archived on its own where it is (What an unarchive brings back). That discriminator is an equality between two stored timestamps, so it is only as sharp as the column type.

Declare TIMESTAMPTZ / TIMESTAMP(6) (Postgres, Oracle), DATETIME(6) (MySQL), DATETIME2(6) (SQL Server), TEXT holding RFC 3339 (SQLite) — what the framework's own migrations declare. Two shapes break the restore, both quietly:
  • Second resolution (a bare MySQL DATETIME) folds two operations that happened within the same second into one stamp, so a child archived on its own moments before the root would come back with it.
  • A child column coarser than the root's truncates the very instant it was given and stops matching it, so the restore reaches nothing — it fails safe, but silently.
Nothing else in the framework depends on this precision: it is the archive cascade's discriminator, and only that.

Stamped fields — the domain says WHEN, the framework says with what

CreatedAt/UpdatedAt date the row — written, last touched — on a schedule the framework fixes. A stamped field dates a fact the business decides has just happened: signed, paid, approved, cancelled. Nothing but a rule knows when that is, so the framework cannot schedule it; and nothing but the framework should choose the instant, because a value read from the writing process is a per-replica clock reading that drifts (see relational.clock above). So the two halves are split, deliberately: 

// infra — the WHAT
core.NewTableSchema[*Order]("orders").
    ID("id").
    Field("Status", "status").
    StampedTimeField("PaidAt", "paid_at").
    CreatedAt("created_at").
    UpdatedAt("updated_at")

// domain — the WHEN
func (o *Order) MarkPaid() { o.Stamp("PaidAt") }        // promoted from domain.Managed

// direct — the WHEN
w.Update(ctx, write.Values{"Status": "PAID", "PaidAt": write.Stamp}, q)

The Go field is *time.Time and the column is nullable: until a rule stamps it the fact has not happened, and nil says exactly that where a zero time.Time would report year 1 as the moment something was signed. Everything else about the field is ordinary — it joins the bijection like any Field, and it filters, orders, projects into views and hydrates on load the same way.

What the framework guarantees. The column is never written from the struct, so setting it by hand does nothing — that is what makes it trustworthy. A write that did not request it leaves the column out of the statement entirely: not bound, not set, not nulled, which is also why an already-stamped row keeps its value with nobody having to remember to preserve it. A requested one binds the write operation's single instant — the same value the managed timestamps carry — and that value is written back onto the entity, so the audit event, the outbox payload, the response and the caller's in-memory entity all agree with the row (the same move the framework already makes with a minted child id). Requesting twice is requesting once, and the emitted columns follow declaration order, so the SQL is stable however the rules happened to fire.

Where it works, and where it is refused. Every schema that WRITES can carry stamped fields: an entity root, an aggregate child, a shared-base role, the shared base itself, and a Direct schema. Two of those are worth a line each. An aggregate child travels as a value in the aggregate map, so the framework writes the filled value back there — the copy every post-write reader sees — exactly as it writes back a minted child id through AssignAggregateItemID. A shared base has no Go type of its own, but its columns map to the ROLE's Go fields, so the role's entity is what carries the request; the one consequence is that the field's TYPE cannot be checked at declaration and is validated at .SharedBase(...) instead, where a struct finally exists (and two declarations of one base must agree on which columns are stamped).

Refused at declaration on the two schemas that could not honor it: a sibling (it carries no framework-owned columns of its own — the owner dates the row) and an external schema (it never writes). At write time: a Stamp naming a field that is unknown, or mapped but plain, is a typed error rather than a silent no-op — the domain cannot see the schema, so there is no boot moment to catch it at. On the Direct side, binding a real value into a stamped slot is refused too, with the diagnostic teaching write.Stamp: the caller may ask for the column, never dictate it.

The second member of the family — StampedCounterField. Same marker, different meaning: filling the column means col = col + 1 instead of the operation's instant. 

StampedTimeField("LastAt", "last_at")             // fills with the instant
StampedCounterField("TotalCount", "total_count")  // fills with existing + 1

o.Stamp("TotalCount")                             // same request, either way

It counts per row: one row's counter counts that row's own events and never interacts with another's. That is what makes it portable on every engine (col = col + 1, evaluated under the row's lock) and what makes it not a sequence — a shared generator handing out values unique across a whole table (an invoice number) needs a SEQUENCE object MySQL and SQLite do not have. Declared int64, never a pointer: a row that was just created has counted one thing, so there is no absence for nil to describe. It binds 1 on an INSERT and becomes the server-side increment on an UPDATE — computed by the database precisely so two writers that both read the value and both wrote back read+1 cannot lose one of the increments silently.

A counter is deliberately absent from the outbox payload and from the write-back onto the entity: its new value is the server's, and the framework does not read it back, so there is no honest value to state — the entity keeps the value it was loaded with until the next load. The projection is unaffected, since the SyncEngine re-reads the row.

Reading the managed columns back — the domain.Managed carrier

A relational load (FindOne/FindAll on a BaseAggregateRepository) surfaces the framework-owned columns onto the typed entity — the id AND revision + created_at/updated_at/deleted_at — on the root and every aggregate child alike. They ride an embedded carrier, domain.Managed, which BaseEntity carries for you (roots) and which every aggregate value object embeds (children). After a load the getters answer:

Revision and the three timestamps are get-only by design: the write path is untouched — created_at/updated_at are stamped from the operation's instant (whose source the service declares, see the box below), revision by the framework, and deleted_at moves only through Archive/Unarchive — so a public setter on them would be a lie the write would ignore. The carrier is populated by the loader through a package-visible seal; the timestamps are honest *time.Time (nil, never a misleading zero, when a column is undeclared or a row is not yet persisted). The carrier's fields are unexported, so it never participates in business identity (IsSameByBusinessFields skips it), never enters the audit delta (GoFieldValues walks only declared fields), and is not cloned into the Old() ghost (the JSON snapshot ignores unexported fields). revision surfaces here as a read getter only — it never flows onto the WriteResult or the outbox from this path.

Which clock stamps them — relational.clock, declared, never assumed. The managed timestamps carry the instant of the write operation, and where that instant is read from is a mandatory declaration in the service's yaml (no default — see yaml-reference):
  • clock: app — the writing process (time.Now().UTC()). No round-trip. With several replicas writing, timestamp quality is only as good as the cluster's clock sync: keep every node on NTP. Under skew, two consecutive writes of one row from different replicas can leave updated_at going backwards.
  • clock: db — the relational backend, read once per write transaction through the dialect's UTC now expression. Every replica then shares one clock, which is the point: no amount of care in the write path can fix a wrong reading at the source. Costs one extra round-trip per write transaction. (On SQLite the engine is embedded, so the database clock is the process clock — the setting is honored, it simply buys no fleet-wide agreement.)
Either way the value is minted once per operation and bound as an ordinary argument — never a NOW() inside the DML — so every statement of one write (root, children, siblings, base cascade) carries the same instant, and the value is known in Go before COMMIT: the outbox payload, the audit event, the lifecycle hooks and the response all agree on it. That single-instant property is load-bearing, not cosmetic: the unarchive cascade tells the children this archive put to sleep from the ones already archived on their own by comparing exactly that stamp.

Neither setting makes updated_at an ordering token. Ordering between concurrent writes is carried by Revision, the commit-order token incremented under the row lock; updated_at is a display timestamp, and clock: db makes it a trustworthy one, not a different kind of thing.

One declaration, every consumer — WithSchema

Declare the schema once and thread it with BaseAggregateRepository.WithSchema(schema): it feeds BOTH the write binding and the read loader, so the write path, the criteria translator, and the scan-back all agree on the same columns. The Modes() ⟺ DeletedAt boot check runs here; the field-existence and bijection checks already ran while the schema was built. A misconfiguration panics at construction, not on the first request.

The same schema drives the Mongo view

The read-side ViewDefinition reuses the very same schemas. The root schema is attached via .Schema(...); the aggregate's own data — root fields flat, .Sibling tables merged flat, 1:N .Child children nested — projects automatically from it, nothing declared on the view beyond the schema. Internal data is never embedded: it already decomposes through the declarative schema (.Child(...) for 1:N children, .Sibling(...) for 1:1 secondary tables, a SharedBaseView for the shared base + roles).

Embed / EmbedMany exist for data the aggregate does not own: another service's mirrored collection, whose leg is built via query.JoinUpstream(...) over a type-less core.NewExternalSchema, or another LOCAL view, whose leg is query.JoinView(view, …) (see Views). A write-anchored NewTableSchema[T] as an embed leg panics at JoinUpstream — an aggregate's OWN closure already auto-projects, and declaring it twice is the redundant path the split removes. From an external schema the framework derives the collection (ts.Table()); the join column is named on the verb via .On(...). The composer writes physical columns to Mongo; the reader translates each leaf back to its Go field name (so mail → Email, zip_code → ZipCode). Because an external source has no Go type to derive them from, both segment names are mandatory on the JoinUpstream constructor. The schema's declared DeletedAt column is what switches on the archived-entry strip for the embedded segment on default reads (see Views, the archived rule). This holds identically for a regular query.View and a SharedBaseView — both may embed material sources; neither may embed the aggregate's own data.

The same schemas also drive the second view kind — query.SharedBaseView, rooted at a shared base with one sub-document per role: the shared-base view below.

Filter keys on the read side are always Go paths (the request DTO's filter: leaves resolve to Go field names, translated to columns by the schema), and sort keys reach the reader the same way — from the request DTO's sort: leaves. Projection translates Go → column through the Response DTO's projection schema, the ?fields= vocabulary every surface speaks. Either way the schema has the last word: a Go path it cannot resolve is the canonical 400. The application Result keys by the Go field name — the reader already translated the doc — so there is no view: source-key override; the only tag that governs the wire shape is json:, on the Response.

External (cross-service) embeds — no local struct. When a view embeds data owned by another service (materialized locally via an UpstreamSubscription), there is no Go struct in this service to anchor the embed's schema. Build the source from a type-less NewExternalSchema(collection) and pass it to query.JoinUpstream(...) — the schema being type-less is the very signal that makes it an external/Mongo source (no separate FromMongo constructor). The left side of each Field is the logical Go name the local view's Response/criteria speak; the right side names the upstream's physical column. It is validated by bijection (no two fields share a column) but not against any type — there is none. Because an external source has no Go type to derive them from, both segment names are required on the JoinUpstream/JoinView constructor (a declaration-time panic otherwise). The join column is named on the verb via .On(...) — the parent document's ParentID column pointing at the leg's ID on a one-to-one Embed/Link. 

// Cross-service embed — buyer projected from the upstream users service.
func OrdersView() *query.ViewDefinition {
    return query.View("orders").

Every declared column must survive the subscription fields: — the DeletedAt column included. The UpstreamSubscription fields: is a string allowlist over the raw upstream payload and consults no schema (at ingestion time no class is materialized), so a column this schema declares that the non-empty fields: omits could never reach the mirror — a dead declaration, and a fatal boot error naming the subscription and the column, checked for EVERY consumer of the mirror (a view that embeds it, an EmbedInChild and a ComposedView that links it). The archive case is the one to design consciously: declare .DeletedAt("deleted_at") AND keep the column in fields: and the mirror reflects the upstream's archive; omit BOTH and the mirror deliberately ignores it (rows keep looking active — the upstream-side counterpart of the JoinView Fields archive switch). A mirror whose consuming schemas declare no DeletedAt column draws only an advisory log, because the consumer often cannot know whether the upstream archives. This rule governs columns reaching the mirror; the embed still carries the whole mirror document, so hiding an archived sub-document at read time is a separate, schema-driven concern.

Schema is mandatory on every view. The root (ViewDefinition.Schema(ts)) and every embed (JoinUpstream always carries one) must declare a schema. A missing root schema is a fatal boot error via query.ValidateViewSchemas(views) (called by bootstrap.Run). There is no optional / pass-through / schema-less mode. Every embed leg is external/type-less (an embed composes EXTERNAL data only — see above), so it inherits no Go type to derive its segment names from: both names are mandatory on the JoinUpstream constructor (a declaration-time panic), never an optional override.

Two writers, one document — field ownership. A view with external embeds is kept current by two independent consumers: the SyncEngine recomposes it on the entity's own events, and the recompose-ripple reacts to the upstream collection's events. Neither write can regress the other's data: each is one atomic pipeline upsert claiming only the fields its writer read freshly — the ripple owns the embed segments, the SyncEngine owns everything else — and whichever arrives first materializes the complete document (the other's next update then touches only its own fields). Cross-topic event ordering therefore never matters for correctness: an embed array always converges to the upstream mirror's current state even when the parent's own event and the embedded rows' events race across CDC topics.

Ripples are per-element edits, not snapshots. Within its embed segments the ripple applies the event's own change surgically: the one array element keyed by the changed upstream id is stripped/appended (and a 1:1 sub-document conditionally set — the explicit null when the source was deleted or the ParentID is unset). Edits for different upstream ids touch disjoint elements and commute, so concurrent ripples — multiple subscription workers, partitions spread across pods — converge to the same array regardless of interleaving, and events for the same id are serialized end to end by broker partitioning and the subscriber's keyed worker dispatch. The ripple's hot path reads no relational data; a parent whose document does not exist yet is materialized by a full recompose instead. During a blue-green rebuild every ripple write also dual-applies to the shadow slot, exactly like the SyncEngine's writes, so the flipped collection never misses a mid-window upstream event. A 1:1 segment additionally self-repairs after every document write that carries its ParentID: the writer re-reads the mirror fresh and sets the segment under a double guard (ParentID still matches, stored element not already that id) — so a document created before its referenced mirror doc existed, or a ParentID changed by an entity update, converges through whichever side runs last, and the repair can never regress the element's own fresher ripple.

Boot checks

  • Write-backed schema is type-anchored — WithSchema rejects a type-less NewExternalSchema as a repository root: a schema that backs the write path must be anchored to a Go type, since the persister reflects the entity to build the INSERT/UPDATE and the read-side composer reflects it (BoolColumns) to restore type fidelity when it materializes the Mongo view. A type-less schema describes an upstream service's Mongo collection and is only ever a view embed source (JoinUpstream), never a root. The composer routes by the view root table name, not by the schema's kind, so a type-less root naming a real local table would otherwise compose relationally with an empty BoolColumns and silently lose boolean fidelity on a backend without a native bool (MySQL TINYINT(1) → number). Aggregate children are covered at declaration — Child(...) rejects a type-less child — so the invariant root + every child type-anchored is complete.
  • Field exists on the type — NewTableSchema[T] + Field panic at construction when the named field is absent, unexported, or promoted from an embed. This is what replaces convention: a typo is a boot panic, not a silent miss.
  • Field type belongs to the closed persistable set — or is a value object over it — Field panics at construction when the Go type is neither in the exact set the framework composes on every supported relational engine (the "Supported column shapes" tables below) NOR a value object (a named type — raw ValueObject or EnumValueObject — whose Value() underlying belongs to that set). A value-object field is persisted as its underlying scalar (unwrapped on write, reconstructed on read), so the driver never sees the named type and the cross-engine guarantee holds by the unwrap — see the Value objects manual section. A google/uuid.UUID field gets the dedicated hint — declare domain.ID — and every other unknown type (a non-VO named type included) gets the fix and a pointer back to this page.
  • Bijection over the whole column set — across each source's mapped fields + the ID column + every declared managed column, no two map to the same physical column. The collision panic names both offenders.
  • Modes() ⟺ DeletedAt — an entity declaring ModeArchive/ModeUnarchive without DeletedAt panics; a runtime guard backs it up.
  • Old-clone safety — no json:"-" on a persisted field, no custom json.Marshaler/json.Unmarshaler on the entity — the framework builds the domain.Old() snapshot by cloning the root entity through a JSON round-trip (see Old-state snapshot), so a persisted field tagged json:"-" would silently vanish from the ghost (transition rules and the transition auditor would read the zero value as the prior state), and a custom (un)marshaler takes the round-trip over entirely. Both panic at WithSchema, naming the offender. The scope is every field persisted through the root struct — the root's declared fields, each sibling's partition, and shared-base fields (resolved on the role's type); aggregate children are exempt (cloned by value, never through JSON). Ordinary renaming tags (json:"name") stay allowed — the round-trip marshals and unmarshals the same type, so renames are symmetric. Wire names belong on the web-layer DTOs regardless.
  • ID is mandatory (no default) + single-column — every schema (root, child, embed source) must declare its ID column via ID(column), which rejects an empty column. The Go side is fixed to the Entity contract's ID (never guessed from the column name). A schema reaching WithSchema / Child / ValidateViewSchemas without a declared ID is a boot failure. Single-column only.
  • ParentID on children + embed join keys — an aggregate Child(...) without .ParentID(col) panics (the persister injects the root id into it). On the read side, every embed/link names its join column on the verb via .On(col) — mandatory and compile-time enforced (the verb's binding routes back to the builder only through .On); an empty .On("") is a fatal ValidateViewSchemas error.
  • Aggregate depth = 1 (no grandchildren) — a child schema that declares its own Child(...) panics at WithSchema (write side); an embed source whose schema carries Child(...) is a fatal error in ValidateViewSchemas (read side). Width is unlimited; depth is one.
  • Every single-column slot is declared once — ID, ParentID, DeletedAt, CreatedAt, UpdatedAt, Revision and NaturalID each reject a SECOND declaration with a boot panic: a repeat call would otherwise silently overwrite the first (the bijection check deliberately skips a slot's own value so an idempotent same-column re-set is allowed — which is exactly what let a DIFFERENT column slip through unnoticed).
  • One child collection per Go type — aggregate children are keyed by Go type name, so a second Child(...) of the SAME type panics at declaration rather than silently dropping the first (two collections of one type are unsupported — they would share one derived segment and one key).
  • Only a root/role schema may reference a SharedBase — passing a child schema that itself declared .SharedBase(...) to .Child(...) panics at declaration. Write and load resolve the shared base from the schema they are handed (the root's SharedBaseRef), never from a child, so a SharedBase on a child would be silently ignored — never persisted, never loaded. Declare the shared identity on the root, or model the child as its own role aggregate. Holds for a root's own child and a base-child alike.
  • Aggregate boundary agreement — the types the domain declares via AggregateChildren() and the types the schema declares via .Child(...) must name the same set. BaseAggregateRepository.WithSchema panics naming any type declared on only one side: a .Child(...) with no AggregateChildren() entry would be silently load-only; an AggregateChildren() entry with no .Child(...) would error per-write deep in the persister.

These checks run inside WithSchema on both repository shapes: BaseAggregateRepository.WithSchema (aggregate) and BaseRepository.WithSchema (flat, non-aggregate) each run the type-anchored, ID-declared, aggregate-depth, old-clone safety, and Modes() ⟺ DeletedAt checks at construction (the aggregate path additionally runs the boundary-agreement check and threads the schema into the read loader). Calling WithSchema also surfaces a nil NewEntity factory at construction. WithSchema is the only way to bind the schema — the field is unexported, so there is no direct-assignment path that bypasses these checks.

Audit stays in the domain vocabulary

Audit does not consume the schema. The timeline's snapshot keys and changes[].field are the faithful Go field name (Email, ZipCode), never the physical column. A column rename therefore never disturbs the audit history. The labelKey:"…" field labels resolve by Go field name too.

Normalizing a flat entity — children, siblings, and shared bases

The schema is also where a flat Go entity becomes a normalized relational layout and back again. You model one linear struct in the domain; the schema declares how its fields partition across physical tables; and the framework normalizes on write (splitting the entity across those tables in a single transaction) and denormalizes on read (re-joining them into the one flat struct on FindOne/FindAll). The domain never sees the seams — the entity you load is the entity you modeled, with the shared/secondary columns merged straight into its Go fields. Three partitioning tools cover the three cardinalities a third-normal-form decomposition needs:

ToolCardinalityShape
.Child(NewTableSchema[C](...))1 : Naggregate children in their own table, linked by a ParentID to the root (see "Declaring a schema" above)
.Sibling(NewSiblingSchema[T](...))1 : 1a disjoint slice of the same entity's fields in a secondary table sharing the root's ID (no ParentID)
.SharedBase(NewSharedBaseSchema(...), fk)N : 1an identity table shared by several independent role tables, deduplicated by a natural key

All three are declared on the same TableSchema the write path, the criteria engine, and the Mongo view already consume, so the normalization stays invisible to every layer above infra/.

Sibling tables — 1 : 1 specialization (shared primary key)

A sibling stores a disjoint subset of the same Go type's fields in a separate table that shares the owner's primary key — a 1 : 1 specialization (a "vertical split"). Use it to peel rarely-read, bulky, or optional facets off a hot table without inventing a child collection or a second aggregate. Build it with core.NewSiblingSchema[T](table) — anchored to the same T as its owner — and attach it with .Sibling(...): 

core.NewTableSchema[*Person]("person").
    ID("id").
    Field("Name", "name").
    Field("Email", "email").
    DeletedAt("deleted_at").
    Sibling(core.NewSiblingSchema[*Person]("person_profile").
        Field("Bio", "bio").              // disjoint fields — never declared on the owner
        Field("AvatarURL", "avatar_url"))

A sibling has no identity or lifecycle of its own: it declares no ID (it borrows the owner's), no ParentID (the shared ID is the link), no DeletedAt, no managed timestamps (the owner's CreatedAt/UpdatedAt already date the 1 : 1 row), no children, and no nested sibling — the owner owns all of that. Calling ID/ParentID/DeletedAt/CreatedAt/UpdatedAt/Child/Sibling on a sibling schema fails at boot, at the declaration call, with a message naming the contract — none of them is supported on a sibling. Width is unlimited (a node may declare many siblings) but the partition is strict: every Go field and every column belongs to exactly one of {owner, siblings}. An overlap is a boot panic (ValidateSiblings, run inside WithSchema). Both a root and an aggregate child may carry siblings.

The DDL contract that follows: the sibling table's physical ID column carries the SAME NAME as the owner's ID column (usually id). The framework writes the sibling row and compiles every join/lookup using the owner's ID column name against the sibling table — there is no seam to declare a different one. Naming the column ParentID-style (person_profile.person_id) compiles and boots, but fails at the first write with the backend's Unknown column error: a sibling is not a foreign entity linked by ParentID — it is the same row, partitioned.

On write, the persister splits the entity across the owner row and each sibling row in the same transaction. A sibling whose mapped fields are all nil is materialized conditionally: skipped on INSERT, left untouched on a PATCH, and deleted on a full PUT (the absent facet means "remove it"). A hard delete removes the sibling rows by shared ID before the owner. On read, the loader LEFT JOINs each sibling on the shared ID and scans its columns straight into the flat struct (an absent sibling row leaves those fields at their zero value); a criteria predicate on a sibling field triggers the same LEFT JOIN.

A sibling belongs to this entity; another aggregate does not. A sibling and a shared base are part of the schema's own closure, so the framework loads them as part of the entity and resolves their fields under the same Go names. Reaching across a foreign key into a different aggregate — filtering orders by the customer's name, say — is a separate concern with its own declaration on the repository: see read joins.

Shared base — identity shared across roles (party-role)

A shared base models the party-role pattern: one identity table (e.g. person) whose data is shared by several independent role tables (student, teacher, user), each linking to it by a foreign key. Unlike a sibling (1 : 1, private), a base is referenced by N roles (N : 1) and is deduplicated by a natural key. Declare the base type-less with core.NewSharedBaseSchema(table), its dedup column with .NaturalID(col), its mandatory revision column with .Revision(col) (below), and its orphan lifecycle with .OrphanPolicy(p); each role references it with .SharedBase(base, parentIDColumn). Sharing one base instance across the role files is idiomatic but not required: at repository construction (WithSchema) the engine registers every role on a registry keyed by the base's table, so N identical NewSharedBaseSchema declarations behave exactly like one — no consumer-side singleton. Two divergent declarations of the same table (different natural key, policy, DeletedAt, fields, or children) panic at boot:

Managed columns on the base are optional and honored when declared. A base that declares .CreatedAt(col)/.UpdatedAt(col) gets them stamped by the framework exactly like any other table: on the identity's creation (the cold insert) and — UpdatedAt — on every role-driven change of the shared fields (the warm upsert and a role's update both write the base row). A base that declares neither is never touched: keep a database DEFAULT on the DDL columns if you only want a creation timestamp. Lifecycle convergence (archive/unarchive of the identity) touches the DeletedAt column and bumps the revision.

Revision(col) is mandatory on EVERY root schema — the last-writer-wins token of the read side. Declare it on every root NewTableSchema (and on every shared base, below); a repository attach without it is a boot failure. Siblings and aggregate children declare none — their rows are guarded by the owner's token. For the shared base specifically: a framework-managed BIGINT advanced by every write that touches the identity — the write path initializes it to 1 on the identity's creation and increments (revision = revision + 1) under the base row's lock on EVERY write that touches the identity: the shared-field upsert, the lifecycle convergence, a role's archive/unarchive even without a base transition, a role's hard-delete (except the purge — the row is gone) and the batch role verbs. Concurrent writes of one identity therefore serialize in real relational commit order, and the value (carried on the outbox payload as _ids.base_revision) totally orders the identity's closure — shared scalars, base children, the SharedBaseView segment pick and the role rows themselves — so every read-model write of identity data is deterministically last-writer-wins, regardless of consumer latency, worker interleaving, pod count or redelivery. Attaching a base without Revision is a boot failure. DDL: revision BIGINT NOT NULL DEFAULT 0 (the framework never reads the DEFAULT — it always binds/increments explicitly).

Every projection write is guarded by these tokens — including consult recomposes, and including deletes. The payload-direct pipeline, the shared-identity fan-out, every consult-composed write (SharedBaseView documents, views with external embeds, the base-event fan-out) and the rebuild/verify backfill all apply as revision-guarded pipelines: a writer that read earlier but lands later is a no-op, never a lost update. Absence is guarded too: a DELETED event records the row's last revision as a tombstone in the omnicore_projection_state registry before a guarded delete, and every document-creating upsert re-checks it after writing — a zombie consumer's older upsert racing a delete removes its own write instead of resurrecting the document — scoped to the dead row's incarnation by its created_at, so a deterministic id (shared-ID role, base) re-created under the same natural key is never mistaken for a zombie of the dead life. The same registry carries the base-revision handshake that heals a role document born concurrently with a fan-out that could not see it (the fan-out stamps its base revision before probing; the newborn document's writer re-checks after writing and repairs by one guarded consult when a newer base revision proves a fan-out already passed). Tombstones expire after 24 h (TTL index, provisioned at SyncEngine start); base-revision records live for the identity's lifetime and are dropped by the purge. 

var person = core.NewSharedBaseSchema("person").
    ID("id").                                      // the deterministic UUIDv5 lands here
    Field("Name", "name").
    Field("Document", "document").                 // the natural-key column
    NaturalID("document").
    Revision("revision").                          // MANDATORY — BIGINT NOT NULL DEFAULT 0 in the migration
    DeletedAt("deleted_at").
    OrphanPolicy(core.KeepOrphan)                  // default; destruction is opt-in via core.DeleteWhenUnreferenced

// *Student's Go struct carries Name + Document (the shared fields, validated
// against the base) AND Enrollment. The role SCHEMA declares only its OWN
// columns — the shared fields live on the base above and are persisted to the
// person table, never to student.
func StudentSchema() *core.TableSchema {
    return core.NewTableSchema[*Student]("student").
        ID("id").
        Field("Enrollment", "enrollment").         // role-private column (the only one student stores)
        DeletedAt("deleted_at").
        SharedBase(person, "person_id")            // role ParentID → base's deterministic id
}

The role→base link is the developer's choice: a separate ParentID column, or the role's own primary key. Passing a distinct column — .SharedBase(person, "person_id") above — gives the role its own surrogate key (a fresh UUIDv7 per row) alongside a person_id ParentID. Passing the role's ID column instead — .SharedBase(person, "id") — selects the shared primary key model: the role's own id IS the base's deterministic id (role.id == base.id == UUIDv5(document)), there is no separate ParentID column, and the primary key itself caps the table at one row per identity (a second role for the same identity collides on the ID — an archived remnant included). The framework detects the mode from the schema — when the SharedBase column equals the ID column it writes the id once, as the ID, carrying the base id; otherwise it writes a separate ParentID — so choosing between the two is a one-line schema change with no code impact.

Under the separate-ParentID model, row multiplicity is a second choice — expressed in your DDL. The framework invariant is about active rows only: at most ONE ACTIVE role row per identity per role table, enforced on POST (an existing active role is a 409) and on /unarchive (reviving a row while another row of the same role table is active is the same 409). How many TOTAL rows an identity may accumulate is your uniqueness contract on the ParentID column:

  • Full UNIQUE(person_id) — 0 : 1 rows per identity, period. An archived remnant physically blocks a new POST for the same identity (the index vetoes it; the repository's ConstraintBinding maps the violation, typically to the same 409). Reviving the remnant via /unarchive is the only way back. Pick this when a role's history should never fork.
  • Active-only uniqueness — archived remnants may accumulate NEXT TO one active row: keep the old archived role and open a fresh active one for the same identity. The shape is per dialect. On Postgres it is a partial unique index — CREATE UNIQUE INDEX ... ON student(person_id) WHERE deleted_at IS NULL — and SQLite supports the identical statement (the framework's own embedded SQLite migrations use partial indexes); SQL Server's equivalent is a filtered unique index — the same statement, same WHERE clause. MySQL has no partial indexes; use a generated column instead — active_person_id BINARY(16) GENERATED ALWAYS AS (IF(deleted_at IS NULL, person_id, NULL)) STORED, UNIQUE(active_person_id) — multiple NULLs are admitted by a MySQL unique index, so every archived remnant passes and the one active row is enforced. Oracle has neither; use a function-based unique index — CREATE UNIQUE INDEX ... ON student (CASE WHEN deleted_at IS NULL THEN person_id END) — a row whose index expression is entirely NULL gets no index entry, so every archived remnant drops out of the index and the one active row is enforced.

Declare one of the two — the index, not the framework's probe, is the arbiter under concurrency. The write path probes for an active role before inserting (a fast, friendly 409), but two concurrent POSTs can both pass the probe; the uniqueness index is what guarantees the invariant when they race. The shared-ID model gets this for free (the primary key is the index).

The natural-key column MUST be a UNIQUE, NOT NULL index — this is mandatory, not advisory. The natural key is not just a lookup column: its value derives the shared base's primary key. The framework computes base.id = UUIDv5(fixed-namespace, naturalIDValue) — a deterministic hash — so the application and the persister reach the same id with no read-back, and equal natural keys necessarily produce the same primary key. That single mechanism is what makes the dedup work, and it is exactly why the column is required to be a unique, non-null index:
  • NOT NULL. An empty / null natural key hashes to a constant id, so every key-less record would collapse into one shared-base row — silent identity corruption (interpolated data colliding on a single id). The framework guards this at runtime (a write whose natural key resolves empty fails loudly), but the database must still enforce NOT NULL so the invariant holds for every writer.
  • UNIQUE. Because equal natural keys derive the equal deterministic ID, uniqueness of the identity is structurally self-enforced by that ID: a second write carrying a natural-key value that already exists resolves to the same id and UPSERTs the one identity row (last-write-wins on the shared fields) instead of inserting a duplicate. Declaring the column UNIQUE NOT NULL makes that invariant explicit at the schema level — guarding against any non-framework writer that might insert a duplicate key under a different id — and gives the dedup and reference-count probes an index (performance).
  • IMMUTABLE — enforced by the write layer. The natural key never changes after insert: every SharedBase derivation (the identity upsert, the refcount, the lifecycle convergence, the CDC fan-out, the lifecycle-payload FKs) re-derives the base id from the value on the entity, so a mutated key would silently aim all of them at a different identity — up to last-write-wins overwriting a third party's shared fields while the role row keeps pointing at the old base. A role UPDATE whose natural-key value diverges from the persisted identity is rejected with NaturalIDImmutableNotification (422): under shared-ID by pure arithmetic (the role id IS UUIDv5(naturalKey), so the id derived from the request must equal the row id), under separate-ParentID by one ID-indexed in-TX probe comparing the stored ParentID with the request-derived id — which also covers a hand-rolled manual handler that skipped load-first. Keeping the field off your update DTOs (as the reference consumer does) remains good hygiene; the guard makes it an invariant rather than a convention.

Why this matters. The natural-key → deterministic-ID mapping is what lets the framework automatically normalize a DDD business entity into third normal form and denormalize it back: you model a flat role entity that carries the shared fields, declare the TableSchema, and the framework writes the shared columns into the one identity row (deduplicated by the natural key) and the role-private columns into the role row — then re-joins them into the flat entity on FindOne/FindAll. No read-back, no surrogate-key juggling in the domain.

Lifecycle is driven by the roles. The base has none of its own: each role controls its own DeletedAt, and the base converges — a role becoming or staying active keeps the base active; archiving the last active role archives the base (and its native children); hard-deleting the last referencing role row converges the base per its OrphanPolicy. Under KeepOrphan (the default) the identity is never destroyed: with DeletedAt declared on the base, the orphaned identity archives (with its native children) — dormant and revived automatically if the same natural key returns; without DeletedAt it simply stays. DeleteWhenUnreferenced is the explicit opt-in for physical erasure (e.g. right-to-be-forgotten): once no role row of any type references the identity, the purge removes the native children and the base row in the same transaction — and it is never invisible: an actual purge writes its own audit event (the base table as entityType, kind snapshot with the shared fields) and its own DELETED outbox row, alongside the role's. A role INSERT upserts the identity and then applies a two-level existence matrix on the role row: an existing active role for that identity is a conflict (409); an archived role is invisible to the insert — DeletedAt is delete here like on every other read/write path — so the insert proceeds and your uniqueness contract on the ParentID column arbitrates the collision with the physical remnant (in the shared-ID model the primary key vetoes it, mapped by the repository's ConstraintBinding — typically to the same 409; under a full UNIQUE(fk) the index vetoes it the same way; under active-only uniqueness the insert lands next to the remnant — see the two contracts above). Bringing an archived role back is the explicit /unarchive verb's job, never a POST side effect — and that verb carries the same active-conflict veto: unarchiving a remnant while another row of the same role table is active for the identity is a 409, so the one-active-role invariant holds on every path that can produce an active row. The BASE is different: its lifecycle is derived (it converges from its roles), so the identity row is found — and reactivated by a new active role — regardless of its own archived state; that automatic revival is what keeps the KeepOrphan dormancy contract honest.

On the read side, the per-role views each project ONE specialization; the composed aggregate — the whole identity with every role in a single document — is the shared-base view below.

Merging base children on the warm upsert — reject or merge is the consumer's call, and it changes the endpoint's behavior. On a warm insert the loaded aggregate carries the identity's existing base-children as Constructor items, and the Cmd's ApplyTo is the hook where that re-sent duplicate is resolved — but the resolution itself belongs in a root method that ApplyTo delegates to, not inline in the mapper. The invariant spans the aggregate's children, so orthodox DDD puts it on the root; ApplyTo stays a pure mapper that just calls it. A root method that rejects with a notification (e.g. a duplicate-address rule) turns the warm POST into a 422 whenever a client re-sends a child the identity already has — correct for "this request is malformed" semantics, but it makes the cross-role POST non-idempotent. A root method that silently skips the duplicate (merge) keeps the POST idempotent for known children — the recommended shape for roles over a shared base. The reference consumer demonstrates both: User.AddAddress rejects (its surface cannot reach the warm path — the role 409s first), Employee.AddAddress merges — and each command's ApplyTo only calls its root's AddAddress, so the reject-vs-merge logic lives in the entity, not in the command.

The purge is database-vetoable — declare real foreign keys and the database gets the last word. The framework can only enumerate the roles registered in this service; it cannot know about a table another system created in the same database. So the purge never trusts the refcount alone: it runs under a savepoint, and a foreign-key violation from ANY referencing table — registered or not — cancels the purge (the base stays; the role delete still commits). The same veto closes the probe-then-delete race: a role inserted concurrently between the probe and the DELETE blocks it. For this protection to exist physically, declare the role→base FKs in your migrations as plain / ON DELETE RESTRICT constraints — that is ordinary relational hygiene, and it is what lets other systems share the database safely. Two things no framework can see, and the reason KeepOrphan is the default: a reference held without a foreign-key constraint, and a copy of the id stored in another database. Note that a foreign table declaring ON DELETE CASCADE opts itself into the destruction — that is that schema's explicit choice, not a veto.

The composed read-model document is ROLE-scoped on its managed columns. The base's business fields merge FLAT into each role's Mongo document, but its managed columns (DeletedAt, created_at, updated_at) never overwrite the role's own: the document represents the role, so its lifecycle timestamp is the role's (an archived role stays visibly archived on its doc even while the identity remains active for a sibling role) and its timestamps are the role row's, not the person's.

Wiring. Because the insert must load any pre-existing identity before writing, a shared-base role uses read.NewSharedBaseRoleRepository[T] (which provides LoadForSharedBaseInsert) together with the SharedBaseInsertCommandHandler; the upsert path is marked by the "GetUpsertable" action name, and a guard rejects a blind insert that would duplicate an existing identity's shared data. On the read-model side, a write through one role emits a base event that recomposes the Mongo projections of every role of that identity (fanOutSharedBase), so a shared-field change is reflected across all roles' views.

Shared-base children — 1 : N shared by every role

A shared base can own native children of its own — a 1 : N collection that belongs to the identity, not to any single role, so every role of that identity sees the same children (e.g. a Person's addresses, shared by its Student and Teacher roles). They are declared with the ordinary .Child(...) builder — the same one a normal aggregate uses — but called on the NewSharedBaseSchema(...) value instead of a root schema. There is no separate base-child constructor: 

var person = core.NewSharedBaseSchema("person").
    ID("id").
    Field("Name", "name").
    Field("Document", "document").
    NaturalID("document").
    DeletedAt("deleted_at").
    Child(core.NewTableSchema[Address]("person_address").  // child of the BASE, shared by all roles
        ID("id").
        ParentID("person_id").                                  // ParentID → the base's deterministic UUIDv5 id
        Field("Street", "street").
        DeletedAt("deleted_at"))

The child's ParentID targets the base's deterministic id (not a role id), so the one child row is reachable from every role of that identity. The role's Go struct carries the child collection (the same AggregateChildren() declaration a normal aggregate root uses) — checked when .SharedBase(...) is attached. On read, the children nest into every role's document; on the warm upsert insert they load as Constructor status, so an unchanged base-child is a no-op (the dev merges/dedups in the Cmd's ApplyTo).

Base-children obey the same partition discipline as the rest of the schema, enforced at boot by ValidateSharedBaseChildren:

  • A type is a base-child OR a role-child, never both. The framework dispatches each declared child type to exactly one owner (the base or the role) when it injects the ParentID; a type claimed by both is a boot panic.
  • A base-child cannot declare an archived state its base can never drive. A base-child that declares DeletedAt requires the base itself to declare DeletedAt: the shared lifecycle converges as a unit (archiving the last active role archives the base and its native children), so under a non-archivable base that column would never be cascaded onto. The opposite pairing is legal and has its own meaning — a base-child that declares no column under an archivable base removes by DELETE and takes no part in the base's cascade, exactly like a role's own child (What a child's DeletedAt declares).
  • Depth stays at one. A base-child is a leaf — it carries no sibling and no grandchild .Child(...), exactly like an aggregate child (model a separate aggregate for deeper nesting).

Shared-base view — the all-in-one identity projection

The read-side projection of a shared base — the SharedBaseView (SharedBaseView(name).Schema(base).Role(...)): one Mongo document per identity with the base fields flat and one sub-document per role, plus its document shape, role selection (active-first), lifecycle and reading — is declared and documented under Views → SharedBaseView. The write-side base schema it composes (the core.NewSharedBaseSchema identity) is above.

RedactedField — sensitive data that stays in the source of record

Declaring a field persists it — and, by the same declaration, sends it to the outbox payload (and from there to the topic, to every consuming service and to the projected document) and to the audit event. For a bank account, a recovery phrase or a taxpayer id that is exactly one declaration too many: the value has to be stored, and it has no business being replicated into a log aggregator, a broker with days of retention, and a second datastore.

RedactedField is the same mapping as Field — same bijection, same boot checks, same panics — plus a declaration of how the value appears in each copy the framework makes of the row. The relational column and the hydrated entity always keep the real value: 

core.NewTableSchema[*Employee]("employees").
    ID("id").
    Field("Name", "name").
    RedactedField("BankAccount", "bank_account",
        core.InSync(core.RedactKeepLast(4)),      // "****3312" in the derived copies
        core.InAudit(core.RedactWith("***")),     // the trail says THAT it changed
    ).
    DeletedAt("deleted_at")

The line the feature draws is who makes the copy. The framework copies a row by itself, and those copies are its responsibility — that is what a redactor governs. Exposure on a read surface is the developer's: the Response DTO is the wire authority, filter:/sort: are opt-in tags, and per-identity field authorization is ReadCriteria.Restrict. Nothing on the read side is refused because a field is redacted. Filters, ordering, ?search= and the aggregate DSL keep working exactly as they do for any other field; the framework offers the mechanism and does not decide the project's policy.

A nil value means the column is SQL NULL, and substituting for it would both lie about nullability and break the payload's all-null rule in the dangerous direction: a 1 : 1 sibling row that the write DELETED would arrive with a non-null column and the projector would keep the stale sub-document alive forever. The symmetric rule binds a hook: returning empty for a non-empty input panics, because an empty scalar reads as that same removed row.

There is no Omit. An absent key is not spare vocabulary — it already means "the 1 : 1 sibling row was removed" in the payload contract, so dropping a key would delete a live sub-document from the projection; and in the audit an absent entry is exactly the information a delta exists to carry. Every redactor therefore keeps the key and changes the value, which also means the whole feature leaves the document's shape untouched — the property every invariant of the projection subsystem is built on.

The hook, and why it must be pure

func maskPhrase(s string) string { return fmt.Sprintf("phrase:%d", len(s)) }

RedactedField("RecoveryPhrase", "recovery_phrase",
    core.InSync(core.RedactUsing(maskPhrase)),
    core.InAudit(core.RedactWith("***")),
)

RedactUsing is the escape hatch that keeps the family small — the local half of an e-mail, a formatted document number, a length fingerprint. It receives the underlying scalar, not the value object (WriteFields and GoFieldValues unwrap first), so a vos.Document arrives as a string.

f MUST BE PURE. It runs at two independent points: assembling the payload inside the write transaction, and composing the document in the composer — which is also the rebuild path, possibly months later in a different binary. A function that reads the clock, randomness or mutable config makes a rebuilt document diverge from the one the sync wrote, and the framework cannot verify purity: what it has is a late backstop (the verify shape check and the payload/composer equivalence gate). A panic inside f is deliberately not recovered — it unwinds into the persister's deferred rollback, so the write is abandoned rather than completed with an unredacted value. Failure closes; it never opens.

What it does and does not protect

The threat it addresses is the copies: whoever reads the log aggregator, the broker, the read model or the audit endpoint. Three limits belong in the same breath, because a reader who assumes otherwise is worse off than one who never used the feature.

1. It does not protect the database. The column holds the real value by design — that is the point. A DBA, a backup and a SELECT * see everything. Encryption at rest is a different control and this is not it.

2. It is forward-only. Declaring a field redacted protects future writes; it does not clean topics already emitted, audit_events rows already written, failure-ledger payloads or log archives. What it does clean is the read model: the declaration participates in the view's RebuildHash, so declaring or changing one is DriftForgotToBump → a Version bump → a rebuild, and the rebuild recomposes every document through the composer. See Views → redaction and the rebuild hash. One consequence to know: a RedactUsing hook contributes only its kind to the hash, because a closure has no portable identity — the framework cannot see that the function's body changed, so changing what a hook returns is a shape change you announce with a Version bump.

3. The natural key of a shared base cannot be redacted — the framework refuses it. A shared base id is UUIDv5(fixed namespace, natural key): an unsalted SHA-1 of the plaintext, with the namespace a constant in the framework's source. That id travels as _ids.base_id in every payload and is the _id of the projected document, so masking the column would hide nothing — an offline brute force over a small candidate space (an 11-digit taxpayer id is ≈2³⁷) recovers the value from the id alone. Declaring RedactedField on the NaturalID column is therefore a construction panic, in either declaration order: the framework will not accept a declaration it cannot honor. If the value is sensitive it is not the identity — keep the natural key on a non-sensitive (or synthetic) column and declare the sensitive value as an ordinary redacted field beside it.

RedactedField REPLACES Field; it is not complementary. A column is declared once, through exactly one slot. Every framework-owned slot — ID, ParentID, Revision, DeletedAt, CreatedAt, UpdatedAt — is already mutually exclusive with any field declaration, in both orders, and a second declaration of the same Go name or the same column is the usual bijection panic. Redaction is for the developer's own mapped fields: the ones that would otherwise be a plain Field. The one slot that coexists with a field declaration is NaturalID (the natural key is a business column the base writes like any other) — and that is exactly why it needs the dedicated refusal above.

Supported column shapes

The relational store is PostgreSQL, MySQL, SQL Server, Oracle, or SQLite; the read projection is MongoDB — except for a relational view, which serves straight from the relational store. The write path, the entity-search criteria engine, and the auto-scan read-back run against the relational backend selected by relational.dialect (postgres | mysql | sqlserver | oracle), emitting dialect-specific SQL through the engine's Dialect seam (placeholders, identifier quoting, the UUID value codec, upsert syntax, the current-timestamp expression, the row cap). MongoDB is the only read-side projection store — the composer, the ViewDefinition surface, the Mongo schema-evolution control plane, and the ?fields / ?orderBy / keyset-pagination reader all target MongoDB. The set of column types each relational dialect handles is its driver's default codec set plus the framework's UUID handling; because that set is not identical across backends, the tables below describe each dialect on its own — read the one for your relational.dialect.

The schema declares which Go field maps to which column; this section is about what types those columns may be. The engine does no custom type registration: on write it binds the raw Go value, on read it scans into the address of the Go field. So the supported set is exactly the driver's default codec set for the selected dialect — nothing the framework adds, nothing it takes away — with one framework-owned convention: identity is a TYPE. A field holding an id — a cross-aggregate reference like a BuyerID/TenantID — is declared domain.ID (nullable ⇒ *domain.ID), and the field's Go type alone drives every leg: the write bind, the criteria probe lift, and the scan decode all render it in the dialect's native id form (UUID on Postgres, BINARY(16) on MySQL and SQL Server, RAW(16) on Oracle), with nil ⇄ SQL NULL on the pointer. A string field is text, ALWAYS — even when the value happens to look like a uuid — pairing with CHAR(36)/VARCHAR(36) columns; nothing is ever guessed from a value's shape. The ID and the child ParentID are framework-managed slots, always stored in the native id form. (domain.ID validates nothing on its own — IsValid stays the explicit seam; a non-uuid id value degrades to its text form and the column, not the codec, rejects it.)

Supported column shapes — Go ↔ SQL Server

A string field binds and scans as plain text, whatever the value's shape. Everything else passes through to the driver's default conversions.

Requires Oracle Database 23ai or higher. The engine adopts the native BOOLEAN and JSON column types, which earlier releases (19c/21c) do not have — the floor is deliberate, not incidental. Supported column shapes — Go ↔ SQLite

The pure-Go, single-node, MVP/self-executable backend. On SQLite the engine is driven by database/sql + the cgo-free modernc.org/sqlite driver, so CGO_ENABLED=0 go build -tags sqlite produces a single static binary. Placeholders are ?; identifiers are double-quoted ("users"). SQLite is dynamically typed (type affinity, not declared types), so the closed persistable field-type set maps onto affinities: a domain.ID stores as TEXT (the canonical uuid string — identity codecs like Postgres, no 16-byte round-trip); a bool stores as INTEGER 0/1 (scanned back to Go bool natively); a time.Time stores as TEXT (RFC3339 for Go-authored values, strftime millisecond for the NowExpr control-plane stamps — the scanner tolerates both); integers/floats use INTEGER/REAL affinity. The upsert is ON CONFLICT … DO UPDATE (the Postgres shape, not a MERGE); the savepoint trio is standard (SQLite HAS RELEASE). Single-writer: the pool is pinned to one perennial connection (an MVP / single-node / low-concurrency posture).

Out of scope

  • Adapting to non-conforming structural conventions. The schema maps names, it does not reshape a schema. Mapping a renamed column on an otherwise-conforming legacy table is supported; adapting to a shape the framework does not manage is not — predicate-shaped DeletedAt (a boolean/enum flag instead of a timestamp column), a composite primary key, and exotic column types outside the supported shapes are all rejected. The scope is "an explicit map over the schema the framework manages", not "adapt to any arbitrary schema".
  • Many-to-many (N : N) inside a single entity. The schema decomposes one entity into a normalized layout, and it covers exactly the three cardinalities that decomposition needs — .Child (1 : N), .Sibling (1 : 1), and .SharedBase (N : 1). There is no N : N partitioning tool, and by design: a many-to-many is not a decomposition of one entity, it is a relationship between two independent aggregates (each with its own lifecycle and boundary). Modeling it inside a single TableSchema would violate the aggregate boundary the framework rests on — root plus one level of children, each row with a single owner (a child owned by its root, a sibling by its shared ID, a base identity by the roles that reference it). The idiomatic expression is the DDD one: the two aggregates reference each other by domain.ID, and the join itself — when it carries any data of its own (a role, a date, a quantity) — becomes an associative entity of its own (its own aggregate, holding the two foreign keys). On the read side a view composes the relationship with a top-level Embed/EmbedMany (single-level — an embed source cannot nest a further embed) or a read-time ComposedView across those aggregates; there is no junction/through-table primitive that materializes both sides automatically.
