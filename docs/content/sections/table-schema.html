TableSchema — Go ↔ column mapping & normalization

Everything above infrastructure speaks the Go field name (PascalCase) — domain, application, and web. The criteria you write is criteria.Eq("Email", v); the audit timeline says Email; repository signatures speak the domain. The only place a physical column or table name appears is the persistence boundary, and it appears in exactly one artifact: TableSchema. A schema is the mandatory, explicit, complete map between a Go type's fields and its physical columns — Go field on one side, DB column on the other. There is no convention, no name-inference, no transient tag: every persisted field is declared, and an undeclared exported field is simply never persisted, scanned, or audited.

One TableSchema drives three consumers from a single declaration: the write path (INSERT/UPDATE/archive SQL), the criteria engine (the WHERE a Go-named criterion compiles to), and the auto-scan read-back (column → Go field). The same schema is reused by the read-side ViewDefinition, so the Mongo projection speaks the same names. Because every name is declared in one place, a column rename round-trips everywhere automatically — write, criteria, scan, and the Mongo view all move together.

Why it exists — and why it is mandatory

The schema is declared by hand, and is required. That is a deliberate design stance, not an oversight — it buys three things a convention-based scheme cannot, and unlocks a fourth capability convention could never express: automatic third-normal-form modeling, called out on its own below.

  • A pure DDD domain. The domain (and the application and web layers above it) never pronounce a table or a column — they speak only business vocabulary (Email, ZipCode). The single place a physical name exists is the TableSchema, which lives in infra/. The entity stays an expression of the business, not a mirror of the database.
  • Transparent mapping flexibility — including names you do not control. The developer maps each Go field to any column name explicitly, and that mapping is transparent to every line of implemented code: handlers, commands, queries and BuildRules speak the Go field and never change when a column is named differently — a rename lives in exactly one place and round-trips across the write path, the criteria engine, the scan-back and the Mongo view at once. Because the map is explicit rather than inferred, you can just as well point the framework at a table whose physical names you did not choose — a legacy column renamed away from its Go field, or an upstream service's collection via NewExternalSchema — declaring field by field how each maps to your domain. What this buys is freedom over names (column and table), not over structural shape: the table must still fit the framework's assumptions — a single-column non-composite primary key, a timestamp-based soft-delete column when the entity is archivable, and one of the supported column shapes. Adopting a schema that breaks those assumptions is explicitly out of scope.
  • No failed, tiring conventions. Name-inference (PascalToSnake + pluralize) is lossy and acronym-hostile: UserID and UserId both collapse to user_id; URLPath, IPv4, HTTPStatus mangle; and the moment the real column diverges from the guess, the failure is silent. An explicit map removes the guessing entirely — a wrong field name is a boot panic, not a column that silently never persists.

Those three together are why the declaration is obligatory and manual: the map is the single, lossless, unambiguous source of truth the whole persistence + read membrane depends on, so the framework refuses to fabricate it from a fragile convention. And because that source of truth is explicit and complete, it can carry far more than a flat name-for-name mapping — which is where the fourth, headline capability comes in.

The headline capability — one flat domain entity, automatically modeled in third normal form.

This is the thing no convention-based mapper can offer, and it is where the explicit schema stops being a concession and becomes an advantage. You model your entity the way the business reads it — one linear, natural Go struct, with none of the foreign keys, join tables, or surrogate-key bookkeeping a normalized store implies. The TableSchema alone then declares how that single struct decomposes into a fully normalized (3NF) physical layout across as many tables as the design needs, and the framework runs the decomposition both ways: it normalizes on write — splitting the entity across those tables inside one transaction — and denormalizes on read — re-joining them into the exact flat struct you modeled on FindOne/FindAll. The domain never sees a seam: no DAO to hand-write, no join to keep in step, no mapping code to drift out of sync with the struct. When the question is a scalar rather than an entity — does one exist, how many, what do they total or average — the same criteria surface carries the hydration-free primitives: Exists and the aggregate DSL Aggregate(ctx, q, specs…) (any combination of Count/SumInt/Sum/Avg/MinInt/MaxInt/Min/Max specs in one SELECT): same schema resolution and scope gate, no re-join, no loading — see Custom command handler → Loading by criteria.

Three declarative partitioning tools cover the three cardinalities a third-normal-form decomposition ever needs, and you compose them freely on a single schema:

  • .Child — 1 : N. A repeating collection lifts out of the entity into its own table, linked back by a foreign key the persister injects — the aggregate child, in its own row.
  • .Sibling — 1 : 1. A disjoint slice of the same entity's fields moves to a secondary table sharing the primary key: peel bulky, optional, or rarely-read facets off a hot row with zero change to the domain type.
  • .SharedBase — N : 1. Fields that describe a shared identity (the party-role pattern) collapse into one deduplicated identity table referenced by every role — the transitive-dependency removal at the heart of 3NF.

The SharedBase case is the sharpest demonstration of how deep this goes. The framework derives the identity's primary key as a deterministic UUIDv5 of its natural key, so two writes carrying the same identity reach the same row with no read-back and no round-trip — the persister and the application compute the same id independently, before either touches the database. Deduplication stops being a query you remember to write and becomes a structural property of the key itself.

And none of it leaks upward. The decomposition is declared on the very same schema the write path, the criteria engine, and the Mongo read-view already consume, so it stays invisible to every layer above infra/ and round-trips identically on PostgreSQL, on MySQL, and into the composed read model. You get textbook-normalized storage and a clean, aggregate-shaped domain at the same time — with the schema, not a hand-written data-access layer, as the single source of truth. See “Normalizing a flat entity” below for the full mechanics.

The three-name model

A field can carry up to three independent names, resolved at two membranes:

SurfaceNameDeclared by
Wire (JSON / query string)myEmailjson:"…" / query:"…" tags in web/
App / domain (Go field)Emailthe Go struct field — the single name every layer above infra uses
Physical (relational column / Mongo doc key)mailTableSchema.Field("Email", "mail") in infra/

The wire name and the physical name are invisible to the developer manipulating data — handlers, commands, queries, and BuildRules only ever say Email. The web membrane (json/query tags) translates JSON ↔ Go; the infra membrane (TableSchema) translates Go ↔ column. Mongo mirrors the relational store physically (the composer writes columns verbatim), and the reader translates each column back to its Go field name before the typed Response projects to the wire — so the wire surface speaks Go names without any per-Response source-key override.

Declaring a schema

A type-anchored schema validates every field against the Go type at construction — a Field naming a missing or unexported field panics immediately, which is the enforcement that replaces convention. A type-less external schema describes an upstream service's columns for an external FromSchema embed source (there is no local struct to validate against). 

// Type-anchored — validated against *User at call time.
func UserSchema() *core.TableSchema {
    return core.NewTableSchema[*User]("users").
        PK("id").                       // column "id" — Go side fixed to ID (single-column PK)
        Field("Name", "name").
        Field("Email", "mail").         // renamed column
        Field("Phone", "phone").
        SoftDelete("deleted_at").       // managed: presence enables the predicate
        CreatedAt("created_at").        // managed: framework stamps NOW() on INSERT
        UpdatedAt("updated_at").        // managed: framework stamps NOW() on INSERT + UPDATE
        Child(AddressSchema())          // aggregate child, keyed by Go type name
}

func AddressSchema() *core.TableSchema {
    return core.NewTableSchema[Address]("addresses").
        PK("id").
        FK("user_id").                  // FK to the root — injected by the persister
        Field("Street", "street").
        Field("ZipCode", "zip_code").
        SoftDelete("deleted_at").
        CreatedAt("created_at").
        UpdatedAt("updated_at")
}

// Type-less — for an upstream-projected external FromSchema source (no local struct).
core.NewExternalSchema("users").PK("id").Field("Email", "mail")

The Go-side primary-key field is fixed to ID by the BaseEntity/AVO contract (an aggregate root carries it privately and exposes GetID/SetID; an AVO exposes the exported field ID), so PK("col") declares only the column. FK names the child's foreign-key column referencing the root — it is injected by the persister and is not a struct field. Every other persisted field is a Field("Go", "column") pair.

Field labels on external schemas — Field(go, col, labelKey). The human-facing field label (consumed by notifications, audit, and the tabular export's column headers) normally comes from a labelKey:"<catalogKey>" struct tag on the domain field. A type-less NewExternalSchema has no struct to carry that tag, so it declares the label inline as an optional third argument: NewExternalSchema("users").Field("Name", "name", "PartnerNameField"). This is the "mini-domain" for upstream columns that have no real domain home. It is external-only: passing a label on a type-anchored NewTableSchema[T] is a boot panic — that schema declares the label through the field's labelKey: tag, and the framework never offers two ways to express one domain concept.
Aggregate depth is exactly one — no grandchildren in the schema. A root may declare any number of child types (one Child(...) per AggregateValueObject type) and each child may have any number of instances — width is unlimited. Depth is not: calling Child(...) on a schema that is itself a child (a grandchild) is a boot panic. Aggregate persistence is root + one level in a single transaction; a grandchild would silently never persist. Model the sub-collection as a separate aggregate (its own root + FK). On the read side, a schema's own children (like a shared base's children) project automatically into the Mongo view — the composer nests each declared Child(...) wherever the schema is used, so a child on a view root or on an embed source is materialized, not ignored. Deeper cross-source nesting still composes through nested EmbedMany(...) / Embed(...); a redundant explicit embed of a child the schema already projects (same derived segment) is a boot error.

The three managed columns — by presence, not a flag

Soft-delete, created-at, and updated-at are declared by calling the matching builder method with the column name. Omitting the call disables the behavior — there is no boolean knob.

BuilderDeclaredOmitted
SoftDelete(col) the read scope-gate uses col IS NULL; Archive/Unarchive write col = NOW() / col = NULL no scope-gate; Archive/Unarchive unavailable (boot check + runtime guard)
CreatedAt(col) the framework stamps col = NOW() on INSERT no creation timestamp stamped
UpdatedAt(col) the framework stamps col = NOW() on INSERT and UPDATE buildUpdate omits the SET

The framework actively generates these timestamps — it never relies on a DB DEFAULT NOW() it does not own. The soft-delete predicate shape is fixed (nullable timestamp: IS NULL = active); the schema controls only the column's name and presence. On the read path these three columns are also readable under fixed logical Go names (CreatedAt, UpdatedAt, DeletedAt) so a view can project them without a domain Go field.

One declaration, every consumer — WithSchema

Declare the schema once and thread it with BaseAggregateRepository.WithSchema(schema): it feeds BOTH the write binding and the read loader, so the write path, the criteria translator, and the scan-back all agree on the same columns. The Modes() ⟺ SoftDelete boot check runs here; the field-existence and bijection checks already ran while the schema was built. A misconfiguration panics at construction, not on the first request. 

// eng is the backend-neutral relational engine (Deps.DB, a core.RelationalEngine);
// the SQL backend is a relational.dialect change in YAML, not an edit here.
func NewUserRepository(eng core.RelationalEngine) *UserRepository {
    r := &UserRepository{
        BaseAggregateRepository: read.NewBaseAggregateRepository[*User](
            eng, func() *User { return &User{} },
        ),
    }
    r.Constraints = map[string]write.ConstraintBinding{ /* … */ }
    r.WithSchema(UserSchema())   // one schema → write + criteria + scan + children
    return r
}

The same schema drives the Mongo view

The read-side ViewDefinition reuses the very same schemas. The root schema is attached via .Schema(...); the aggregate's own data — root fields flat, .Sibling tables merged flat, 1:N .Child children nested — projects automatically from it, nothing declared on the view beyond the schema. Internal data is never embedded: it already decomposes through the declarative schema (.Child(...) for 1:N children, .Sibling(...) for 1:1 secondary tables, a SharedBaseView for the shared base + roles).

Embed / EmbedMany exist for one thing only — EXTERNAL data — so each embed source is constructed via query.FromSchema(...) (the single embed source constructor) over a type-less core.NewExternalSchema; a write-anchored NewTableSchema[T] as an embed source is a fatal boot error (ValidateViewSchemas) — local data has no business being embedded when it already auto-projects. From the schema the framework derives the collection (ts.Table()) and — for an EmbedMany — the join FK (ts.FKColumn()). The composer writes physical columns to Mongo; the reader translates each leaf back to its Go field name (so mail → Email, zip_code → ZipCode). Because an external source has no Go type to derive a segment from, .As(...) is mandatory on every embed. The view also honors the schema's soft-delete column when DeleteOnArchive is set. This holds identically for a regular query.View and a SharedBaseView — both may embed external sources; neither may embed internal data. 

func UserView() *query.ViewDefinition {
    return query.View("users").
        Version(1).
        Root("users").
        Schema(UserSchema()).   // addresses (a .Child of UserSchema) auto-project as "Addresses"
        Indexes( /* … */ )
}

The same schemas also drive the second view kind — query.SharedBaseView, rooted at a shared base with one sub-document per role: the shared-base view below.

Filter keys on the read side are always Go paths (the request DTO's filter: leaves resolve to Go field names, translated to columns by the schema). Sort and projection translate Go → column only when a typed Response is in scope; RawDoc / ParseCriteria callers pass through verbatim. The typed Response projector (AutoFromDoc) keys by the Go field name — the reader already translated the doc — so the view: source-key override is gone; the only tag that governs the wire shape is json:.

External (cross-service) embeds — no local struct. When a view embeds data owned by another service (materialized locally via an UpstreamSubscription), there is no Go struct in this service to anchor the embed's schema. Build the source from a type-less NewExternalSchema(collection) and pass it to query.FromSchema(...) — the schema being type-less is the very signal that makes it an external/Mongo source (no separate FromMongo constructor). The left side of each Field is the logical Go name the local view's Response/criteria speak; the right side names the upstream's physical column. It is validated by bijection (no two fields share a column) but not against any type — there is none. Because an external source has no Go type to derive a segment from, .As(...) is required (a fatal boot error otherwise). .FK(...) is the parent document’s FK column pointing at the source’s PK — used only on a one-to-one Embed. 

// Cross-service embed — buyer projected from the upstream users service.
func OrdersView() *query.ViewDefinition {
    return query.View("orders").
        Version(1).
        Root("orders").
        Schema(OrderSchema()).
        Embed("buyer", query.FromSchema(
            core.NewExternalSchema("users").  // type-less: names the UPSTREAM's columns
                PK("id").
                Field("Name", "name").
                Field("Email", "mail")).         // logical Go name ↔ upstream column
            FK("buyer_id").                      // parent doc FK pointing at the source PK
            As("Buyer")).                        // REQUIRED — external embeds have no Go type to derive from
        Indexes(query.Index("buyer_id"))       // boot guard requires the join-field index
}

Schema is mandatory on every view. The root (ViewDefinition.Schema(ts)) and every embed (FromSchema always carries one) must declare a schema. A missing root schema, or an external embed missing .As(...), is a fatal boot error via query.ValidateViewSchemas(views) (called by bootstrap.Run). There is no optional / pass-through / schema-less mode. Every embed source is external/type-less (an embed composes EXTERNAL data only — see above), so it inherits no Go type to derive its segment from: .As(...) is always required, never an optional override.

Boot checks

  • Write-backed schema is type-anchored — WithSchema rejects a type-less NewExternalSchema as a repository root: a schema that backs the write path must be anchored to a Go type, since the persister reflects the entity to build the INSERT/UPDATE and the read-side composer reflects it (BoolColumns) to restore type fidelity when it materializes the Mongo view. A type-less schema describes an upstream service's Mongo collection and is only ever a view embed source (FromSchema), never a root. The composer routes by the view root table name, not by the schema's kind, so a type-less root naming a real local table would otherwise compose relationally with an empty BoolColumns and silently lose boolean fidelity on a backend without a native bool (MySQL TINYINT(1) → number). Aggregate children are covered at declaration — Child(...) rejects a type-less child — so the invariant root + every child type-anchored is complete.
  • Field exists on the type — NewTableSchema[T] + Field panic at construction when the named field is absent, unexported, or promoted from an embed. This is what replaces convention: a typo is a boot panic, not a silent miss.
  • Field type belongs to the closed persistable set — Field panics at construction when the Go type is outside the exact set the framework composes on every supported relational engine (the "Supported column shapes" tables below). A google/uuid.UUID field gets the dedicated hint — declare domain.ID — and every other unknown type gets the fix and a pointer back to this page. Identity matching is literal (a named type over a supported underlying is rejected), so the cross-engine guarantee never depends on driver-specific reflection behavior.
  • Bijection over the whole column set — across each source's mapped fields + the PK column + every declared managed column, no two map to the same physical column. The collision panic names both offenders.
  • Modes() ⟺ SoftDelete — an entity declaring ModeArchive/ModeUnarchive without SoftDelete panics; a runtime guard backs it up.
  • PK is mandatory (no default) + single-column — every schema (root, child, embed source) must declare its PK column via PK(column), which rejects an empty column. The Go side is fixed to the Entity contract's ID (never guessed from the column name). A schema reaching WithSchema / Child / ValidateViewSchemas without a declared PK is a boot failure. Single-column only.
  • FK on children + embed join keys — an aggregate Child(...) without .FK(col) panics (the persister injects the root id into it). On the read side, an EmbedMany source without .FK(col), and a one-to-one Embed without .FK(col), are fatal ValidateViewSchemas errors.
  • Aggregate depth = 1 (no grandchildren) — a child schema that declares its own Child(...) panics at WithSchema (write side); an embed source whose schema carries Child(...) is a fatal error in ValidateViewSchemas (read side). Width is unlimited; depth is one.
  • Only a root/role schema may reference a SharedBase — passing a child schema that itself declared .SharedBase(...) to .Child(...) panics at declaration. Write and load resolve the shared base from the schema they are handed (the root's SharedBaseRef), never from a child, so a SharedBase on a child would be silently ignored — never persisted, never loaded. Declare the shared identity on the root, or model the child as its own role aggregate. Holds for a root's own child and a base-child alike.
  • Aggregate boundary agreement — the types the domain declares via AggregateChildren() and the types the schema declares via .Child(...) must name the same set. BaseAggregateRepository.WithSchema panics naming any type declared on only one side: a .Child(...) with no AggregateChildren() entry would be silently load-only; an AggregateChildren() entry with no .Child(...) would error per-write deep in the persister.

These checks run inside WithSchema on both repository shapes: BaseAggregateRepository.WithSchema (aggregate) and BaseRepository.WithSchema (flat, non-aggregate) each run the type-anchored, PK-declared, aggregate-depth, and Modes() ⟺ SoftDelete checks at construction (the aggregate path additionally runs the boundary-agreement check and threads the schema into the read loader). Calling WithSchema also surfaces a nil NewEntity factory at construction. Assigning r.Schema directly still works as the unchecked escape hatch — WithSchema is the validated canonical entry.

Audit stays in the domain vocabulary

Audit does not consume the schema. The timeline's snapshot keys and changes[].field are the faithful Go field name (Email, ZipCode), never the physical column. A column rename therefore never disturbs the audit history. The labelKey:"…" field labels resolve by Go field name too.

Manual scanners bypass the schema by design

WithRootScanner / WithChildScanner hand the SELECT and the scan to the developer, who owns the column names directly. The schema governs the auto-scan path; the manual path stays a full escape hatch (a manual root scanner used with FindOne/FindAll must populate the id itself).

Normalizing a flat entity — children, siblings, and shared bases

The schema is also where a flat Go entity becomes a normalized relational layout and back again. You model one linear struct in the domain; the schema declares how its fields partition across physical tables; and the framework normalizes on write (splitting the entity across those tables in a single transaction) and denormalizes on read (re-joining them into the one flat struct on FindOne/FindAll). The domain never sees the seams — the entity you load is the entity you modeled, with the shared/secondary columns merged straight into its Go fields. Three partitioning tools cover the three cardinalities a third-normal-form decomposition needs:

ToolCardinalityShape
.Child(NewTableSchema[C](...))1 : Naggregate children in their own table, linked by an FK to the root (see "Declaring a schema" above)
.Sibling(NewSiblingSchema[T](...))1 : 1a disjoint slice of the same entity's fields in a secondary table sharing the root's PK (no FK)
.SharedBase(NewSharedBase(...), fk)N : 1an identity table shared by several independent role tables, deduplicated by a natural key

All three are declared on the same TableSchema the write path, the criteria engine, and the Mongo view already consume, so the normalization stays invisible to every layer above infra/.

Sibling tables — 1 : 1 specialization (shared primary key)

A sibling stores a disjoint subset of the same Go type's fields in a separate table that shares the owner's primary key — a 1 : 1 specialization (a "vertical split"). Use it to peel rarely-read, bulky, or optional facets off a hot table without inventing a child collection or a second aggregate. Build it with core.NewSiblingSchema[T](table) — anchored to the same T as its owner — and attach it with .Sibling(...): 

core.NewTableSchema[*Person]("person").
    PK("id").
    Field("Name", "name").
    Field("Email", "email").
    SoftDelete("deleted_at").
    Sibling(core.NewSiblingSchema[*Person]("person_profile").
        Field("Bio", "bio").              // disjoint fields — never declared on the owner
        Field("AvatarURL", "avatar_url"))

A sibling has no identity or lifecycle of its own: it declares no PK (it borrows the owner's), no FK (the shared PK is the link), no soft-delete, no managed timestamps (the owner's CreatedAt/UpdatedAt already date the 1 : 1 row), no children, and no nested sibling — the owner owns all of that. Calling PK/FK/SoftDelete/CreatedAt/UpdatedAt/Child/Sibling on a sibling schema fails at boot, at the declaration call, with a message naming the contract — none of them is supported on a sibling. Width is unlimited (a node may declare many siblings) but the partition is strict: every Go field and every column belongs to exactly one of {owner, siblings}. An overlap is a boot panic (ValidateSiblings, run inside WithSchema). Both a root and an aggregate child may carry siblings.

The DDL contract that follows: the sibling table's physical PK column carries the SAME NAME as the owner's PK column (usually id). The framework writes the sibling row and compiles every join/lookup using the owner's PK column name against the sibling table — there is no seam to declare a different one. Naming the column FK-style (person_profile.person_id) compiles and boots, but fails at the first write with the backend's Unknown column error: a sibling is not a foreign entity linked by FK — it is the same row, partitioned.

On write, the persister splits the entity across the owner row and each sibling row in the same transaction. A sibling whose mapped fields are all nil is materialized conditionally: skipped on INSERT, left untouched on a PATCH, and deleted on a full PUT (the absent facet means "remove it"). A hard delete removes the sibling rows by shared PK before the owner. On read, the loader LEFT JOINs each sibling on the shared PK and scans its columns straight into the flat struct (an absent sibling row leaves those fields at their zero value); a criteria predicate on a sibling field triggers the same LEFT JOIN.

Shared base — identity shared across roles (party-role)

A shared base models the party-role pattern: one identity table (e.g. person) whose data is shared by several independent role tables (student, teacher, user), each linking to it by a foreign key. Unlike a sibling (1 : 1, private), a base is referenced by N roles (N : 1) and is deduplicated by a natural key. Declare the base type-less with core.NewSharedBase(table), its dedup column with .NaturalKey(col), and its orphan lifecycle with .OrphanPolicy(p); each role references it with .SharedBase(base, fkColumn). Sharing one base instance across the role files is idiomatic but not required: at repository construction (WithSchema) the engine registers every role on a registry keyed by the base's table, so N identical NewSharedBase declarations behave exactly like one — no consumer-side singleton. Two divergent declarations of the same table (different natural key, policy, soft-delete, fields, or children) panic at boot:

Managed columns on the base are optional and honored when declared. A base that declares .CreatedAt(col)/.UpdatedAt(col) gets them stamped by the framework exactly like any other table: on the identity's creation (the cold insert) and — UpdatedAt — on every role-driven change of the shared fields (the warm upsert and a role's update both write the base row). A base that declares neither is never touched: keep a database DEFAULT on the DDL columns if you only want a creation timestamp. Lifecycle convergence (archive/unarchive of the identity) touches only the soft-delete column, on the base as on every other table. 

var person = core.NewSharedBase("person").
    PK("id").                                      // the deterministic UUIDv5 lands here
    Field("Name", "name").
    Field("Document", "document").                 // the natural-key column
    NaturalKey("document").
    SoftDelete("deleted_at").
    OrphanPolicy(core.KeepOrphan)                  // default; destruction is opt-in via core.DeleteWhenUnreferenced

// *Student's Go struct carries Name + Document (the shared fields, validated
// against the base) AND Enrollment. The role SCHEMA declares only its OWN
// columns — the shared fields live on the base above and are persisted to the
// person table, never to student.
func StudentSchema() *core.TableSchema {
    return core.NewTableSchema[*Student]("student").
        PK("id").
        Field("Enrollment", "enrollment").         // role-private column (the only one student stores)
        SoftDelete("deleted_at").
        SharedBase(person, "person_id")            // role FK → base's deterministic id
}

The role→base link is the developer's choice: a separate FK column, or the role's own primary key. Passing a distinct column — .SharedBase(person, "person_id") above — gives the role its own surrogate key (a fresh UUIDv7 per row) alongside a person_id FK. Passing the role's PK column instead — .SharedBase(person, "id") — selects the shared primary key model: the role's own id IS the base's deterministic id (role.id == base.id == UUIDv5(document)), there is no separate FK column, and the primary key itself caps the table at one row per identity (a second role for the same identity collides on the PK — an archived remnant included). The framework detects the mode from the schema — when the SharedBase column equals the PK column it writes the id once, as the PK, carrying the base id; otherwise it writes a separate FK — so choosing between the two is a one-line schema change with no code impact.

Under the separate-FK model, row multiplicity is a second choice — expressed in your DDL. The framework invariant is about active rows only: at most ONE ACTIVE role row per identity per role table, enforced on POST (an existing active role is a 409) and on /unarchive (reviving a row while another row of the same role table is active is the same 409). How many TOTAL rows an identity may accumulate is your uniqueness contract on the FK column:

  • Full UNIQUE(person_id) — 0 : 1 rows per identity, period. An archived remnant physically blocks a new POST for the same identity (the index vetoes it; the repository's ConstraintBinding maps the violation, typically to the same 409). Reviving the remnant via /unarchive is the only way back. Pick this when a role's history should never fork.
  • Active-only uniqueness — archived remnants may accumulate NEXT TO one active row: keep the old archived role and open a fresh active one for the same identity. On Postgres this is a partial unique index — CREATE UNIQUE INDEX ... ON student(person_id) WHERE deleted_at IS NULL. MySQL has no partial indexes; use a generated column instead — active_person_id CHAR(36) GENERATED ALWAYS AS (IF(deleted_at IS NULL, person_id, NULL)) STORED, UNIQUE(active_person_id) — multiple NULLs are admitted by a MySQL unique index, so every archived remnant passes and the one active row is enforced.

Declare one of the two — the index, not the framework's probe, is the arbiter under concurrency. The write path probes for an active role before inserting (a fast, friendly 409), but two concurrent POSTs can both pass the probe; the uniqueness index is what guarantees the invariant when they race. The shared-PK model gets this for free (the primary key is the index).

The natural-key column MUST be a UNIQUE, NOT NULL index — this is mandatory, not advisory. The natural key is not just a lookup column: its value derives the shared base's primary key. The framework computes base.id = UUIDv5(fixed-namespace, naturalKeyValue) — a deterministic hash — so the application and the persister reach the same id with no read-back, and equal natural keys necessarily produce the same primary key. That single mechanism is what makes the dedup work, and it is exactly why the column is required to be a unique, non-null index:
  • NOT NULL. An empty / null natural key hashes to a constant id, so every key-less record would collapse into one shared-base row — silent identity corruption (interpolated data colliding on a single id). The framework guards this at runtime (a write whose natural key resolves empty fails loudly), but the database must still enforce NOT NULL so the invariant holds for every writer.
  • UNIQUE. Because equal natural keys derive the equal deterministic PK, uniqueness of the identity is structurally self-enforced by that PK: a second write carrying a natural-key value that already exists resolves to the same id and UPSERTs the one identity row (last-write-wins on the shared fields) instead of inserting a duplicate. Declaring the column UNIQUE NOT NULL makes that invariant explicit at the schema level — guarding against any non-framework writer that might insert a duplicate key under a different id — and gives the dedup and reference-count probes an index (performance).
  • IMMUTABLE — enforced by the write layer. The natural key never changes after insert: every SharedBase derivation (the identity upsert, the refcount, the lifecycle convergence, the CDC fan-out, the lifecycle-payload FKs) re-derives the base id from the value on the entity, so a mutated key would silently aim all of them at a different identity — up to last-write-wins overwriting a third party's shared fields while the role row keeps pointing at the old base. A role UPDATE whose natural-key value diverges from the persisted identity is rejected with NaturalKeyImmutableNotification (422): under shared-PK by pure arithmetic (the role id IS UUIDv5(naturalKey), so the id derived from the request must equal the row id), under separate-FK by one PK-indexed in-TX probe comparing the stored FK with the request-derived id — which also covers a hand-rolled manual handler that skipped load-first. Keeping the field off your update DTOs (as the reference consumer does) remains good hygiene; the guard makes it an invariant rather than a convention.

Why this matters. The natural-key → deterministic-PK mapping is what lets the framework automatically normalize a DDD business entity into third normal form and denormalize it back: you model a flat role entity that carries the shared fields, declare the TableSchema, and the framework writes the shared columns into the one identity row (deduplicated by the natural key) and the role-private columns into the role row — then re-joins them into the flat entity on FindOne/FindAll. No read-back, no surrogate-key juggling in the domain.

Lifecycle is driven by the roles. The base has none of its own: each role controls its own soft-delete, and the base converges — a role becoming or staying active keeps the base active; archiving the last active role archives the base (and its native children); hard-deleting the last referencing role row converges the base per its OrphanPolicy. Under KeepOrphan (the default) the identity is never destroyed: with SoftDelete declared on the base, the orphaned identity archives (with its native children) — dormant and revived automatically if the same natural key returns; without SoftDelete it simply stays. DeleteWhenUnreferenced is the explicit opt-in for physical erasure (e.g. right-to-be-forgotten): once no role row of any type references the identity, the purge removes the native children and the base row in the same transaction — and it is never invisible: an actual purge writes its own audit event (the base table as entityType, kind snapshot with the shared fields) and its own DELETED outbox row, alongside the role's. A role INSERT upserts the identity and then applies a two-level existence matrix on the role row: an existing active role for that identity is a conflict (409); an archived role is invisible to the insert — soft-delete is delete here like on every other read/write path — so the insert proceeds and your uniqueness contract on the FK column arbitrates the collision with the physical remnant (in the shared-PK model the primary key vetoes it, mapped by the repository's ConstraintBinding — typically to the same 409; under a full UNIQUE(fk) the index vetoes it the same way; under active-only uniqueness the insert lands next to the remnant — see the two contracts above). Bringing an archived role back is the explicit /unarchive verb's job, never a POST side effect — and that verb carries the same active-conflict veto: unarchiving a remnant while another row of the same role table is active for the identity is a 409, so the one-active-role invariant holds on every path that can produce an active row. The BASE is different: its lifecycle is derived (it converges from its roles), so the identity row is found — and reactivated by a new active role — regardless of its own archived state; that automatic revival is what keeps the KeepOrphan dormancy contract honest.

On the read side, the per-role views each project ONE specialization; the composed aggregate — the whole identity with every role in a single document — is the shared-base view below.

Merging base children on the warm upsert — reject or merge is the consumer's call, and it changes the endpoint's behavior. On a warm insert the loaded aggregate carries the identity's existing base-children as Constructor items, and the Cmd's ApplyTo is the hook where that re-sent duplicate is resolved — but the resolution itself belongs in a root method that ApplyTo delegates to, not inline in the mapper. The invariant spans the aggregate's children, so orthodox DDD puts it on the root; ApplyTo stays a pure mapper that just calls it. A root method that rejects with a notification (e.g. a duplicate-address rule) turns the warm POST into a 422 whenever a client re-sends a child the identity already has — correct for "this request is malformed" semantics, but it makes the cross-role POST non-idempotent. A root method that silently skips the duplicate (merge) keeps the POST idempotent for known children — the recommended shape for roles over a shared base. The reference consumer demonstrates both: User.AddAddress rejects (its surface cannot reach the warm path — the role 409s first), Employee.AddAddress merges — and each command's ApplyTo only calls its root's AddAddress, so the reject-vs-merge logic lives in the entity, not in the command.

The purge is database-vetoable — declare real foreign keys and the database gets the last word. The framework can only enumerate the roles registered in this service; it cannot know about a table another system created in the same database. So the purge never trusts the refcount alone: it runs under a savepoint, and a foreign-key violation from ANY referencing table — registered or not — cancels the purge (the base stays; the role delete still commits). The same veto closes the probe-then-delete race: a role inserted concurrently between the probe and the DELETE blocks it. For this protection to exist physically, declare the role→base FKs in your migrations as plain / ON DELETE RESTRICT constraints — that is ordinary relational hygiene, and it is what lets other systems share the database safely. Two things no framework can see, and the reason KeepOrphan is the default: a reference held without a FK constraint, and a copy of the id stored in another database. Note that a foreign table declaring ON DELETE CASCADE opts itself into the destruction — that is that schema's explicit choice, not a veto.

The composed read-model document is ROLE-scoped on its managed columns. The base's business fields merge FLAT into each role's Mongo document, but its managed columns (soft-delete, created_at, updated_at) never overwrite the role's own: the document represents the role, so its lifecycle timestamp is the role's (an archived role stays visibly archived on its doc even while the identity remains active for a sibling role) and its timestamps are the role row's, not the person's.

Wiring. Because the insert must load any pre-existing identity before writing, a shared-base role uses read.NewSharedBaseRoleRepository[T] (which provides LoadForSharedBaseInsert) together with the SharedBaseInsertCommandHandler; the upsert path is marked by the "GetUpsertable" action name, and a guard rejects a blind insert that would duplicate an existing identity's shared data. On the read-model side, a write through one role emits a base event that recomposes the Mongo projections of every role of that identity (fanOutSharedBase), so a shared-field change is reflected across all roles' views.

Shared-base children — 1 : N shared by every role

A shared base can own native children of its own — a 1 : N collection that belongs to the identity, not to any single role, so every role of that identity sees the same children (e.g. a Person's addresses, shared by its Student and Teacher roles). They are declared with the ordinary .Child(...) builder — the same one a normal aggregate uses — but called on the NewSharedBase(...) value instead of a root schema. There is no separate base-child constructor: 

var person = core.NewSharedBase("person").
    PK("id").
    Field("Name", "name").
    Field("Document", "document").
    NaturalKey("document").
    SoftDelete("deleted_at").
    Child(core.NewTableSchema[Address]("person_address").  // child of the BASE, shared by all roles
        PK("id").
        FK("person_id").                                  // FK → the base's deterministic UUIDv5 id
        Field("Street", "street").
        SoftDelete("deleted_at"))

The child's FK targets the base's deterministic id (not a role id), so the one child row is reachable from every role of that identity. The role's Go struct carries the child collection (the same AggregateChildren() declaration a normal aggregate root uses) — checked when .SharedBase(...) is attached. On read, the children nest into every role's document; on the warm upsert insert they load as Constructor status, so an unchanged base-child is a no-op (the dev merges/dedups in the Cmd's ApplyTo).

Base-children obey the same partition discipline as the rest of the schema, enforced at boot by ValidateSharedBaseChildren:

  • A type is a base-child OR a role-child, never both. The framework dispatches each declared child type to exactly one owner (the base or the role) when it injects the FK; a type claimed by both is a boot panic.
  • Soft-delete is all-or-nothing per base. A base-child that declares SoftDelete requires the base itself to declare SoftDelete — the shared lifecycle converges as a unit (archiving the last active role archives the base and its native children), so a child cannot be archivable under a non-archivable base.
  • Depth stays at one. A base-child is a leaf — it carries no sibling and no grandchild .Child(...), exactly like an aggregate child (model a separate aggregate for deeper nesting).

Shared-base view — the all-in-one identity projection

A second read-side view kind, alongside query.View: a view rooted at a SharedBase (the deduplicated identity table — see the shared base above). Where each role view projects ONE specialization (a users document, an employees document), a SharedBaseView projects the WHOLE composed aggregate: one Mongo document per shared identity, carrying the base's shared fields flat at the root, the base's native children nested at the root, and one sub-document per declared role — the read-side mirror of the write side's third-normal-form normalization, denormalized back into a single "everything about this person" document. 

func PersonView() *query.ViewDefinition {
    return query.SharedBaseView(personBase(), "persons").
        Role(UserSchema()).                    // repeatable — the role set is open-ended
        Role(EmployeeSchema()).
        Version(1).
        Indexes(
            query.Index("document"),           // the natural key
            query.TextIndex("name", "email").DefaultLanguage("english"),
        )
}

Document shape

{
  "_id":      "<UUIDv5(document)>",          // the base's deterministic PK
  "document": "52998224725",                  // base fields — FLAT at the root
  "name":     "Ana Souza",
  "Addresses": [ ... ],                       // base-children — nested at the ROOT (shared across roles)
  "User":     { "user_name": "ana", "email_notification": true },   // role segment: fields + siblings flat
  "Employee": { "employee_number": "E-77",                          // role segment
                "Dependents":   [ { "dep_name": "Rita", ... } ],    // role children — nested INSIDE the segment
                "JobHistories": [ ... ] }
}
  • _id = the base PK — UUIDv5(naturalKey), stable under both role link models (shared-PK and separate-FK).
  • Role segments are named by the role's Go type ("User", "Employee") — the same derivation rule nested children use, minus the pluralization: a role is a single optional sub-document, not a collection. The wire name comes from your Response DTO's json tag (json:"user"), exactly like every other field.
  • An absent role is an explicit null segment — the store upserts via $set, so a vanished role must overwrite its stale segment. Response DTOs declare role fields as pointers with omitempty (the sparse-render contract), so a null segment simply disappears from the wire.
  • Base fields never repeat inside a segment; a role's siblings merge flat inside its segment; a role's own children nest inside it, keyed on the role row's own PK.

Role selection — deterministic under separate-FK multiplicity

Under the separate-FK model with active-only uniqueness (see the two DDL uniqueness contracts above), an identity may carry archived role remnants NEXT TO one active row. The composer picks the row that represents the specialization's current state:

  1. the ACTIVE row (fk = baseID AND deleted_at IS NULL) — the one-active-role invariant caps it at one;
  2. otherwise the most recently archived remnant (ORDER BY deleted_at DESC), stored WITH its soft-delete timestamp — hidden on default reads, surfaced by ?includeArchived=true;
  3. otherwise the explicit null segment.

Remnant HISTORY is deliberately not enumerated in the person document — the role views with ?includeArchived cover it. A role without SoftDelete has no archived state; a single FK fetch decides its segment.

Lifecycle & sync

  • Document gate = the base's soft-delete. The base archives only when its last active role archives (write-side convergence), so the root deleted_at gate hides the person exactly when every specialization is archived. DeleteOnArchive() means "drop the document when the BASE archives" — and archived role rows stop composing at all.
  • Role events recompose the person document. The SyncEngine subscribes to every role table's topic (mandatory: a role's ARCHIVE/UNARCHIVE emits only the role event — the base convergence is SQL without its own outbox row). The base id resolves per link model: shared-PK → the event's aggregate_id IS the base id; separate-FK → the role row is consulted, except on DELETED, where the row is gone and the id comes from the event payload's structural keys (the write side records {pk, shared-base fk} on every role DELETE for exactly this moment). The payload is a routing hint only — state is always re-read from the relational source.
  • Purge convergence. When the last role's DELETE also purges the identity (DeleteWhenUnreferenced), the recompose finds no base row and removes the person document.
  • Base events route as root events (the base IS this view's root table): INSERTED/UPDATED upsert, DELETED removes, ARCHIVED honors DeleteOnArchive().

Reading it

Everything a regular view offers applies unchanged — the same Auto query handlers, filter-operator vocabulary, keyset pagination, ?fields= sparse render, ?includeArchived, field-level Restrict(), GraphQL exposure and CSV/XLSX export. Role sub-fields address through the segment: ?user.userName=ana, ?employee.dependents.relationship=daughter, sort and projection likewise. On a default read an ARCHIVED role's whole segment is hidden (the single-map counterpart of the archived-entry strip on child collections); ?includeArchived=true surfaces it with its deletedAt. Exports render each role as a nested branch (role fields + siblings, then its child collections), never repeating the base columns.

Rules & validation

  • The root must be a core.NewSharedBase schema; each Role must be a type-anchored schema declaring .SharedBase(...) back to the SAME base table with an equivalent declaration — violations panic at declaration, and a role-less view is a boot error.
  • Segment collisions (role vs base-child vs embed) are boot errors, like every other double-producer segment.
  • The role set participates in the rebuild hash: adding/removing a role, or changing any part of a role's schema closure, without bumping Version(N) is detected as forgot-to-bump and aborts boot — same contract as every rebuild-relevant change (see Mongo schema evolution).
  • Embed/EmbedMany still compose external data only, joined on the base PK at the root.
When to declare one. A SharedBaseView complements — never replaces — the role views: keep users/employees for the per-role surfaces and add the person view when a consumer needs the whole identity in one read (a 360° profile, a back-office screen, a data export). It is one more projection over the same CDC stream: no extra writes, one more recompose per role event.

Supported column shapes

The relational store is PostgreSQL, MySQL, or SQL Server; the read projection is always MongoDB. The write path, the entity-search criteria engine, and the auto-scan read-back run against the relational backend selected by relational.dialect (postgres | mysql | sqlserver), emitting dialect-specific SQL through the engine's Dialect seam (placeholders, identifier quoting, the UUID value codec, upsert syntax, the current-timestamp expression, the row cap). MongoDB is the only read-side projection store — the composer, the ViewDefinition surface, the Mongo schema-evolution control plane, and the ?fields / ?sort / keyset-pagination reader all target MongoDB. The set of column types each relational dialect handles is its driver's default codec set plus the framework's UUID handling; because that set is not identical across backends, the tables below describe each dialect on its own — read the one for your relational.dialect.

The schema declares which Go field maps to which column; this section is about what types those columns may be. The engine does no custom type registration: on write it binds the raw Go value, on read it scans into the address of the Go field. So the supported set is exactly the driver's default codec set for the selected dialect — nothing the framework adds, nothing it takes away — with one framework-owned convention: identity is a TYPE. A field holding an id — a cross-aggregate reference like a BuyerID/TenantID — is declared domain.ID (nullable ⇒ *domain.ID), and the field's Go type alone drives every leg: the write bind, the criteria probe lift, and the scan decode all render it in the dialect's native id form (UUID on Postgres, BINARY(16) on MySQL and SQL Server), with nil ⇄ SQL NULL on the pointer. A string field is text, ALWAYS — even when the value happens to look like a uuid — pairing with CHAR(36)/VARCHAR(36) columns; nothing is ever guessed from a value's shape. The PK and the child FK are framework-managed slots, always stored in the native id form. (domain.ID validates nothing on its own — IsValid stays the explicit seam; a non-uuid id value degrades to its text form and the column, not the codec, rejects it.)

Out of scope

  • Adapting to non-conforming structural conventions. The schema maps names, it does not reshape a schema. Mapping a renamed column on an otherwise-conforming legacy table is supported; adapting to a shape the framework does not manage is not — predicate-shaped soft-delete (a boolean/enum flag instead of a timestamp column), a composite PK, and exotic column types outside the supported shapes are all rejected. The scope is "an explicit map over the schema the framework manages", not "adapt to any arbitrary schema".
  • Many-to-many (N : N) inside a single entity. The schema decomposes one entity into a normalized layout, and it covers exactly the three cardinalities that decomposition needs — .Child (1 : N), .Sibling (1 : 1), and .SharedBase (N : 1). There is no N : N partitioning tool, and by design: a many-to-many is not a decomposition of one entity, it is a relationship between two independent aggregates (each with its own lifecycle and boundary). Modeling it inside a single TableSchema would violate the aggregate boundary the framework rests on — root plus one level of children, each row with a single owner (a child owned by its root, a sibling by its shared PK, a base identity by the roles that reference it). The idiomatic expression is the DDD one: the two aggregates reference each other by domain.ID, and the join itself — when it carries any data of its own (a role, a date, a quantity) — becomes an associative entity of its own (its own aggregate, holding the two foreign keys). On the read side a view can still traverse the relationship through nested EmbedMany/Embed across those aggregates; there is no junction/through-table primitive that materializes both sides automatically.
