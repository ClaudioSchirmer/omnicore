Custom query handler

The Auto query handlers hide every read step behind a one-line generic handler. This page builds the same read from scratch — a hand-written pipeline.Handler and explicit route wiring — and names the facilitator the framework offers at each step. It is the escape hatch for wiring control: an alternate identifier (:email instead of :id), a vendor-shaped envelope, a bespoke lookup the ViewReader.ReadByID primary-key path does not cover. It is not a lesser tier — the same ReadCriteria, the same ViewReader, the same pagination and projection apply, byte-for-byte identical to the canonical path.

Every step below maps onto the full flow of a GET. The shared vocabulary — what ReadCriteria carries, the filter operators, and the ToCriteria(ctx) overlay + field-restriction seam — lives on the QueryHandler · CQRS trunk and is not repeated here. For a complete runnable reference, see omnicore-example-users/web/user_custom_routes.go and the hand-written query handlers under application/queries/handlers/*_custom_handler.go.

Full example — read a user by email

The canonical GET /users/:id is keyed by the document's primary key, so its FindByIDQueryHandler dispatches to ViewReader.ReadByID. Switching the public identifier to email needs an arbitrary filter — which is exactly what ReadPage already supports. Going manual on the read side is the whole motivation. The Mongo view is unchanged (it already denormalizes the root's email into the document).

1. Reuse the read model

Nothing new on the read model — the custom route reads the same ViewDefinition, the same Mongo collection, the same SyncEngine subscription. POSTing on the canonical surface and reading here returns the same persisted state. The only things that change below are the application handler and the wire shape.

2. Define the Result + the Query (ToCriteria / FromQueryResult)

The Query is the transport carrying the alternate key, and it declares the Result the read produces. ToCriteria(ctx) turns the Query into a ReadCriteria — here Filter[Email]=<value> with Limit:1 — and is the seam where the overlays + Restrict would layer on; FromQueryResult is where read-side computation belongs. Facilitator: embed pipeline.QueryBase; the Query owns its persistence shape AND its output shape end to end, so the wire never knows how the lookup is shaped at the Mongo layer. 

// application/queries/find_user_by_email_custom_query.go
package queries

// The Result — application-pure, no wire tags, names = the document's Go keys.
type FindUserByEmailResult struct {
    ID    *string
    Name  *string
    Email *string
}

type FindUserByEmailQuery struct {
    pipeline.QueryBase
    Email           string
    IncludeArchived bool
}

// ToCriteria(ctx) is the only layer below the web boundary that consumes
// *AppContext. Email becomes a Filter clause; Limit:1 makes it a single-item
// read. Tenant/owner overlays and crit.Restrict(...) would layer here — same
// seam the Auto handlers honor (see QueryHandler · CQRS).
func (q FindUserByEmailQuery) ToCriteria(
    _ *configuration.AppContext,
) (fwqueries.ReadCriteria, error) {
    return fwqueries.ReadCriteria{
        Filter:          map[string]any{"Email": q.Email},
        Limit:           1,
        IncludeArchived: q.IncludeArchived,
    }, nil
}

// FromQueryResult — the read-side twin of a command's FromEntity. Nothing to derive
// here, so the filled Result passes through unchanged.
func (q FindUserByEmailQuery) FromQueryResult(
    _ *configuration.AppContext, r FindUserByEmailResult,
) (FindUserByEmailResult, error) {
    return r, nil
}

3. Write the QueryHandler by hand

The handler implements pipeline.Handler[*Q, R] directly. It calls ToCriteria(ctx), runs the read through the same ViewReader port the framework uses (d.ViewReader), and maps an empty result to the canonical 404 — the same status the canonical by-id surface emits for a missing row. Facilitator: queries.ViewReader.ReadPage (the read engine) + queries.ResultFromDoc (the doc→Result fill) + domain.NotFoundError (the typed 404 carrier). The handler returns the typed Result — the canonical document stops here, exactly as it does on the canonical path; wire naming happens at the web layer. 

// application/queries/handlers/find_user_by_email_custom_handler.go
package handlers

type FindUserByEmailCustomQueryHandler struct {
    Reader queries.ViewReader
    View   string
}

func (h *FindUserByEmailCustomQueryHandler) Handle(
    ctx *configuration.AppContext, q *appqueries.FindUserByEmailQuery,
) (appqueries.FindUserByEmailResult, error) {
    var zero appqueries.FindUserByEmailResult

    criteria, err := q.ToCriteria(ctx)
    if err != nil {
        return zero, err  // e.g. a Restrict 403 — errors.As routes it at pipeline.Run
    }

    // ─── Row-level access-control seam (the reason this manual handler exists) ──
    // Filter keys are Go field names; the MongoViewReader translates each to its
    // physical column via the view schema. Typical overlays:
    //   criteria.Filter["TenantID"] = ctx.Identity().TenantID()   // multi-tenant
    //   criteria.Filter["OwnerID"]  = ctx.ActorSubject()          // owner-only
    // If the overlay rejects the row, ReadPage returns 0 items → canonical 404.
    // ───────────────────────────────────────────────────────────────────────────

    page, err := h.Reader.ReadPage(ctx, h.View, criteria)
    if err != nil {
        return zero, err
    }
    if len(page.Items) == 0 {
        return zero, domain.NotFoundError("User", "email", q.Email)  // → 404
    }
    // The same fill + hook the framework handlers run.
    r := fwqueries.ResultFromDoc[appqueries.FindUserByEmailResult](page.Items[0])
    return q.FromQueryResult(ctx, r)
}

4. Declare the Request DTO (allowlist) + Response

The Request DTO carries the wire allowlist exactly like the canonical surface. The :email URL segment binds via the path:"email" tag; ?includeArchived is the only other recognized key. ToQuery(criteria) is the pure body→application boundary (no ctx). Facilitator: the path: tag (URL-segment binding) + query: tags (allowlist). The Response is a plain struct with json: tags carrying a FromResult method over the Query's Result — the same wire seat the canonical surface uses (see Projection is shared infrastructure). 

// web/requests/find_user_by_email_custom_request.go
package requests

type FindUserByEmailCustomRequest struct {
    Email           string `path:"email"`              // bound from c.Params("email")
    IncludeArchived *bool  `query:"includeArchived"`   // the only allowed query key
}

// ToQuery — pure body mapping, no ctx. Reads req.Email (populated by BindPath
// from the URL) and the validated criteria from the parser.
func (r FindUserByEmailCustomRequest) ToQuery(crit fwqueries.ReadCriteria) *queries.FindUserByEmailQuery {
    return &queries.FindUserByEmailQuery{Email: r.Email, IncludeArchived: crit.IncludeArchived}
}

// Reduced wire shape — id + name + email only (phone/addresses absent from
// the Result, so they reach no surface). *string + ,omitempty keeps it ready
// to opt into ?fields= later.
type FindUserByEmailCustomResponse struct {
    ID    *string `json:"id,omitempty"`
    Name  *string `json:"name,omitempty"`
    Email *string `json:"email,omitempty"`
}

// The wire mapping seat — same method the canonical wrappers take.
func (FindUserByEmailCustomResponse) FromResult(
    r queries.FindUserByEmailResult,
) FindUserByEmailCustomResponse {
    return fwresponses.Map[FindUserByEmailCustomResponse](r)
}

5. Wire the route by hand

This is the step the wrapper hides — and the point of going manual. The Fiber closure performs, in order, every move QueryByID would: build the AppContext and propagate cancellation, bind the path segment, validate the query string against the allowlist, map to the Query, dispatch, and project on success. Facilitators (each replaces one hidden wrapper step):

  • fwweb.BindPath(c, &req) — fills path:-tagged fields from c.Params. Returns nil when every segment bound, or the *queryschema.Violation that explains the first one that did not.
  • fwweb.NewQueryParser[Req, Resp]() — constructed once at Mount; parser.Parse(c) applies the same allowlist + wire→doc translation the wrapper runs (see building blocks).
  • fwweb.RespondViolation(c, pipe, violation) — the canonical envelope for a rejected read control OR a path segment, carrying the notification its producer chose. The STATUS comes from that notification, not from this call: a read control is the canonical 400, while a malformed IDENTITY segment (uuid.UUID / domain.ID) answers 404 on a read and 400 on a write. A manual handler therefore writes no status literal for a refusal.
  • fwweb.RespondSchemaViolation(c, pipe, badField) — the same envelope for a plain bad key, when the handler itself names the offending field.
  • Resp{}.FromResult — the shared wire mapping seat (over fwresponses.Map[Resp]).
// web/user_custom_routes.go — parser built ONCE at Mount (runs the boot scan).
byEmailParser := fwweb.NewQueryParser[requests.FindUserByEmailCustomRequest,
    requests.FindUserByEmailCustomResponse]()

g.Get("/:email", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)                          // propagate request cancellation

    var req requests.FindUserByEmailCustomRequest
    if v := fwweb.BindPath(c, &req); v != nil {         // :email → req.Email
        return fwweb.RespondViolation(c, pipe, v)
    }
    crit, violation, ok := byEmailParser.Parse(c)       // allowlist + translation
    if !ok {
        return fwweb.RespondViolation(c, pipe, violation)
    }

    q := req.ToQuery(crit)
    h := &appquery.FindUserByEmailCustomQueryHandler{Reader: reader, View: "users"}

    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if result.IsSuccess() {
        // result.Value() is the typed Result; FromResult names the wire.
        return fwweb.RespondWithSuccess(c, fiber.StatusOK,
            requests.FindUserByEmailCustomResponse{}.FromResult(result.Value()))
    }
    return fwweb.RespondFromResult(c, result, fiber.StatusOK)  // honors Semantic → 404/403/500
})

Paged-list variant

A list is the same chain with two differences: the handler returns queries.PageOf[TResult] (so the cursor envelope survives alongside the typed items), and the route assembles the paged envelope with fwweb.RespondPaged — which applies the response projection per item and emits data + top-level pagination, exactly the wrapper's output. The list handler's Handle converts the reader's Page in one call: 

func (h *FindUsersCustomQueryHandler) Handle(
    ctx *configuration.AppContext, q *appqueries.FindUsersCustomQuery,
) (fwqueries.PageOf[appqueries.FindUsersCustomResult], error) {
    criteria, err := q.ToCriteria(ctx)
    if err != nil {
        return fwqueries.PageOf[appqueries.FindUsersCustomResult]{}, err
    }
    page, err := h.Reader.ReadPage(ctx, h.View, criteria)
    if err != nil {
        return fwqueries.PageOf[appqueries.FindUsersCustomResult]{}, err
    }
    // PageOfFrom fills one Result per document and runs FromQueryResult on each,
    // copying the envelope (cursors, totals, projection echo) verbatim.
    return fwqueries.PageOfFrom(page,
        fwqueries.FromQueryResultFiller[appqueries.FindUsersCustomResult](ctx, q))
}
listParser := fwweb.NewQueryParser[requests.FindUsersCustomRequest,
    requests.FindUsersCustomResponse]()   // fields-guard + the sortable-paths advisory fire here at boot

g.Get("/", func(c fiber.Ctx) error {
    appCtx := fwweb.AppContext(c)
    appCtx.SetParent(c)

    var req requests.FindUsersCustomRequest
    crit, violation, ok := listParser.Parse(c)
    if !ok {
        return fwweb.RespondViolation(c, pipe, violation)
    }

    q := req.ToQuery(crit)
    h := &appquery.FindUsersCustomQueryHandler{Reader: reader, View: "users"}

    result := pipeline.Dispatch(pipe, appCtx, q, h)
    if !result.IsSuccess() {
        return fwweb.RespondFromResult(c, result, fiber.StatusOK)
    }
    // RespondPaged projects each item + assembles the canonical paged envelope.
    return fwweb.RespondPaged(c, fiber.StatusOK, result.Value(),
        requests.FindUsersCustomResponse{}.FromResult)
})

The building blocks

These are the helpers the canonical wrappers are themselves made of — pick the ones the manual route needs. fwweb.NewQueryParser is the one query-string parsing seat:

HelperReplaces wrapper stepNotes
fwweb.NewQueryParser[Req, Resp]() query-string allowlist + ?fields=/?orderBy= translation Construct once at Mount. Construction runs the same boot scan the wrapper runs: the sparse-render guard on Resp (panic when any field at any depth is not *T/slice/map with ,omitempty, when ?fields= is opted in), the slog.Warn advisory listing every wire path the Request DTO declared orderable (when it declared any), and the wire→doc projection schema. parser.Parse(c) → (criteria, *queryschema.Violation, ok) with allowlist + translation. The violation carries the wire spelling of the offending control AND the notification that explains it, so a refusal reaches the consumer as a translated message here exactly as on the canonical wrapper. Schema caches are shared with the canonical wrapper, so there is no per-route memory penalty for going manual.

Projection is shared infrastructure

"Manual" means controlling the wiring, not re-implementing primitives the framework already ships. A manual read walks the same two steps the canonical one does, in the same order: fwqueries.ResultFromDoc fills the typed Result from the canonical document (name-based — the identity is the Go field ID like any other, no store key in sight — with nil→empty-slice normalization and enum convergence) and the Query's FromQueryResult hook adjusts it; then Resp{}.FromResult — over fwresponses.Map[Resp] — names the wire. Hand-rolling a mapper that walks doc["id"], doc["name"], … rewrites both for no gain. Write FromResult by hand only when the wire shape needs more than the json: tags express, and put read-side COMPUTATION in FromQueryResult, where every surface inherits it. For envelopes that need sidecar fields outside data/pagination, use fwweb.ProjectPage and build the Response by hand — the projection and the pagination cursor stay framework-managed.

path: tag — universal URL-segment binding

Every Request DTO field tagged path:"<name>" is populated from the matching Fiber URL segment (c.Params("<name>")) before ToCommand / ToQuery runs. It closes the asymmetry between the canonical wrappers (which only auto-bind :id) and routes with custom identifier segments (:email, :tenantId, …) or compound paths (/tenants/:tenantId/users/:id). It works the same on the write and read sides. 

// Read by-email — single segment route
type FindUserByEmailRequest struct {
    Email           string `path:"email"`
    IncludeArchived *bool  `query:"includeArchived"`
}

// Compound route — both segments via tag
type UpdateOnTenantRequest struct {
    TenantID string `path:"tenantId"`   // /tenants/:tenantId/users/:id — :id still via interface on WithBodyID
    Name     string `json:"name"`
}

Manual fiber.Handler closures opt out of the wrappers — call fwweb.BindPath(c, &req) explicitly (the same helper NewQueryParser sits beside). See omnicore-example-users/web/user_custom_routes.go for the canonical BindPath → Parse → ToQuery → Dispatch chain.

Supported field types: string, signed/unsigned ints of any width, float32/float64, bool, uuid.UUID, domain.ID. Pointer/slice/struct types are rejected at boot. Conversion failure returns 400 SchemaViolationNotification with the segment name.

Per-wrapper behavior. The :id-binding wrappers (QueryByID, CommandWithBodyID) panic at boot if the Request declares path:"id" (it would set the same value twice); the no-:id wrappers (QueryWithParams, CommandWithBody) accept path:"id" for compound routes. FullBody interaction: the strict-body check skips fields carrying a path: tag — their value comes from the URL, not the body; declaring both path:"X" and json:"X" on one field is a boot panic.

Result: with a thin Query owning its ToCriteria, a hand-written handler that calls the same ViewReader, a Request DTO declaring the allowlist, and a Fiber closure chaining the building blocks, you get a read keyed by any identifier you like — with the same allowlist enforcement, the same cursor pagination, the same projection, and the same 404/403/500 semantics the canonical wrappers produce.
