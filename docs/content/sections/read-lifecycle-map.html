Canonical read lifecycle — end-to-end layer map

Cross-layer reference, symmetric to the Write lifecycle map: for each canonical read shape this table follows the request from the HTTP wrapper down through the Auto query handler, the Query entry points (ToQuery at the web boundary + ToCriteria(ctx) in the application layer, where JWT-derived overlays land), the queries.ViewReader port, the MongoDB operation, all the way up to the response envelope the wrapper emits. Everything is anchored in the criteria → bson translation — identical ReadCriteria ⇒ identical Mongo query ⇒ identical result set.

Only the canonical surface (the two Auto query wrappers + the FindBy*QueryHandler family) is shown to keep the map readable. Manual handlers (QueryHandler · CQRS → manual query handlers) hand-roll the dispatch but consume the same ViewReader port and emit the same envelope.

Query-string axes — the criteria → bson translation

Each wire axis the Auto query handlers validate lands on a field of queries.ReadCriteria; the canonical MongoViewReader emits the matching bson. The list endpoint composes all axes into one Find; the by-id endpoint honors only Filter (overlays) + IncludeArchived by design.

Wire axisReadCriteria fieldMongo emission
?name.in=a,b (filter leaf) Filter[field] = value / MultiClause / RegexMatchList sentinel {name: {$in: ["a","b"]}}; multiple operators on one field fold into a top-level $and
?sort=-created_at Sort []SortField (+ _id ASC appended) findOpts.SetSort(bson.D{{"created_at",-1},{"_id",1}})
?fields=name,email Projection findOpts.SetProjection({name:1, email:1, _id:0}) — _id:0 added when id not requested
?after= / ?before= decoded cursor tuple (sort_values…, _id) + context hash h $or cascade with $gt (asc) / $lt (desc) per slot; ?before= runs inverted + reverses in Go
?search=foo Search {$text: {$search: "foo"}} — requires a TextIndex on the view
?includeArchived=true IncludeArchived omits the {deleted_at: null} gate (default applies it)

The criteria-grounded contract — one rule, no exceptions

The result set is a deterministic function of the assembled ReadCriteria. Identical criteria ⇒ identical bson ⇒ identical page. The reader always appends _id ASC as the last sort key, so the +1 overflow trick that powers has_next stays meaningful even under concurrent writes, and a cursor emitted on one page applies cleanly on the next.

Because the read side is stateless (no server-side session, no cursor store), the cursor carries a SHA-256 hash of its issuing full listing context (Filter + Sort + Search + IncludeArchived). The wrapper rejects a cursor whose context hash no longer matches the current request with 400 SchemaViolationNotification — converting a silent "frontend changed one knob, results look wrong" bug into a loud failure with a clear remediation: request page 1 of the new context. This is the read-side analogue of the write side's SQL-fingerprint discipline: the contract is anchored in what physically shapes the query, not in the endpoint's intent.
