Bootstrap — main.go in 10 lines

The omnicore/bootstrap package orchestrates the whole service boot from the microservice.<profile>.yaml + a Wire callback returning Wiring.

Environment variables

The framework reads exactly four process environment variables at boot. Every other env var that may appear inside a YAML value via the ${VAR:default} interpolation pattern (e.g. DATABASE_URL, MONGO_URI, KC_URL) is consumer-defined — see the YAML subsection below for the interpolation syntax. The four framework-reserved vars are:

Variable Required Default What it controls Read by
APP_PROFILE yes — (boot aborts if empty) Selects the YAML config: ./microservice.${APP_PROFILE}.yaml. dev and prd are the canonical pair; any other non-empty string (prd-pem, prd-external, qa-canary, …) is also accepted so QA suites and ops setups can swap whole configurations without competing with the canonical pair. dev is the only profile under which auth.mode=disabled is allowed; every other profile rejects boot on that combination. bootstrap.LoadConfig
OMNICORE_CONFIG_PATH no ./microservice.${APP_PROFILE}.yaml Overrides the YAML path. Useful for tests, sidecar layouts, custom directories where the file does not live next to the binary's CWD. Still requires APP_PROFILE set, because profile-aware guards (e.g. auth.mode=disabled) consult it independently. bootstrap.LoadConfig
OMNICORE_MONGO_FORCE_REBUILD no unset (= strict) When the literal value is "true", mongo.ApplyMongoSpecs drops divergent indexes and recreates them from the declared spec. Operator escape for index conflicts surfacing at boot. Scope is intentionally narrow: does NOT authorize dropping collections (collection-level divergence on collation / capped / time-series is always strict — operator owns the migration) and does NOT trigger the document rebuild path (that is controlled by mongo.rebuild.autoRun). Comparison is exact: "True", "1", "yes" all leave the strict default in place — eliminates the "I thought I had turned it on" failure mode. mongo.ApplyMongoSpecs (called by bootstrap.Run after collectViews)
OMNICORE_CODE_VERSION no unset (= empty) Optional build-time identifier (typically a git SHA injected at compile) stamped on the code_version column of omnicore_mongo_views when the registry row is written (init / artifact-only refresh / rebuild end). Useful for "which deploy ran this?" forensics. Empty when unset; never a boot blocker. query.InitViewRegistry / query.EndRebuild (called by SyncEngine.InitRegistryOnly / RefreshRegistryArtifactOnly / ExecuteRebuild)

Why these are env vars and not YAML fields. The YAML is checked into git → carrying a one-shot override like forceRebuild: true there would deploy the override into the next release by accident. Env vars are scoped to the process lifetime; a reboot without them returns to the canonical posture. The same posture explains the auth.mode=disabled guard: a loose-auth knob exists in the YAML schema, but the loader rejects boot on any non-dev profile — destructive / loose decisions stay out of versioned artifacts. OMNICORE_CONFIG_PATH is env-only for a different reason: it tells the loader where the YAML lives, so it logically cannot itself live in the YAML.

How operators set them. Three canonical patterns, picked by deployment shape:

# Local shell — one run (the -tags engine selector is mandatory at build/run):
APP_PROFILE=dev go run -tags postgres ./bootstrap
OMNICORE_MONGO_FORCE_REBUILD=true APP_PROFILE=prd ./bootstrap

# docker-compose.yml — service environment block:
services:
  api:
    image: my-service:1.4.0
    environment:
      - APP_PROFILE=prd
      - OMNICORE_MONGO_FORCE_REBUILD=true

# Kubernetes Deployment — spec.template.spec.containers[].env:
env:
  - name: APP_PROFILE
    value: prd
  - name: OMNICORE_MONGO_FORCE_REBUILD
    value: "true"

Relational engine build tag

The relational engine is selected by a Go build tag, and at least one tag is mandatory — there is no default. Each engine self-registers in the engine registry (core.RegisterEngine, database/sql-style) and brings its own driver stack (pgx for Postgres, go-sql-driver for MySQL) plus its dialect-bound boot wiring (audit partitions, the migration runner). Three valid shapes:

  • -tags postgres — links only the Postgres engine.
  • -tags mysql — links only the MySQL engine.
  • -tags 'postgres mysql' — links both engines into one binary; the active dialect is chosen at boot from relational.dialect, so the same binary serves a Postgres profile and a MySQL profile without a rebuild.

Building with neither tag registers no engine, so boot aborts (core.NewEngine: no engine registered for the configured dialect). Whichever tag set you pick, pass it to every go build / go test / go run, and make sure the linked engine(s) cover the relational.dialect the YAML selects:

# Postgres-only binary
go build -tags postgres ./...
APP_PROFILE=dev go run -tags postgres .

# MySQL-only binary
go build -tags mysql ./...
APP_PROFILE=dev go run -tags mysql .

# Dual-engine binary — dialect chosen at runtime from relational.dialect
go build -tags 'postgres mysql' ./...
APP_PROFILE=dev go run -tags 'postgres mysql' .

microservice.<profile>.yaml

Each service declares infra config in a profile-specific YAML file at the root. bootstrap.LoadConfig reads the APP_PROFILE environment variable (required, non-empty) and loads ./microservice.${APP_PROFILE}.yaml — override the path via OMNICORE_CONFIG_PATH when needed (tests, custom layouts). dev and prd are the canonical pair; any other non-empty string (prd-pem, prd-external, qa-canary, ...) is also accepted so QA suites and ops setups can swap whole configurations via extra files without competing with the canonical pair. See Environment variables for the complete list of framework-reserved env vars.

Separate files per profile is intentional: the artifact deployed to prd does not carry dev configuration at all, so a service cannot accidentally ship with a dev knob enabled. The profile is also not a YAML field — its source of truth is the environment, and the loader rejects boot with auth.mode=disabled under any profile other than dev (canonical-prd and every QA variant are treated identically by this guard — only dev unlocks the disabled-auth shortcut).

# microservice.prd.yaml
service: my-service

    issuer: https://idp.example.com
    audience: my-service
    leewaySeconds: 30  # optional; clock skew tolerance for exp/nbf
    jwksUrl: https://idp.example.com/.well-known/jwks.json

    # publicKeyPem: |
    #   -----BEGIN PUBLIC KEY-----
    #   ...

    sampler: parentbased_traceratio      # dev default always_on; else parentbased_traceratio
    ratio: 0.1                           # keep fraction for the *traceratio samplers
    instrument: [http, pgx, mongo, kafka, httpclient]   # empty → all five

Audit routing — audit.destinations

Every successful write produces one AuditEvent (granularity B: the aggregate is the event unit, identical to the outbox row). audit.destinations controls where it lands:

  • database → audit.InsertAuditEvent writes a row to the audit_events table inside the same transaction as the data row + outbox row. The row IS the audit — atomic with the write by construction. Source of truth for compliance and forensics: if COMMIT succeeded, the audit exists in the relational store.
  • slog → audit.EchoSlog emits a flat top-level slog line after COMMIT. Read-side echo for observability; lossy if the shipper drops events, but the relational row remains the authority. Format is unchanged from the previous best-effort posture — ELK pipelines and dashboards continue working without changes.
YAMLEffect
destinations: [slog, database] (default; block absent) Both active — recommended posture. Atomic durability + cross-service ELK consolidation.
destinations: [database]Only the PG row. Lowest log volume; pair with SQL dashboards.
destinations: [slog]Only the slog line. Matches the framework's pre-redesign best-effort posture.
destinations: []Explicitly disables audit. Table stays provisioned by migration 0001 but no row is written; no slog line is emitted.

Unknown destination tokens (destinations: [kafka]) and duplicates (destinations: [slog, slog]) abort the boot with a diagnostic naming the offender — operator typos surface at startup, not as silent runtime drift. audit.destinations is the only audit knob; the auth.auditClaims allowlist controls which JWT claims appear inside the AuditEvent's payload and stays under auth: because it is a security concern (whitelist what leaves the JWT envelope), not a routing concern.

Interpolation supports three forms inside ${...}:

  • ${VAR} / ${VAR:default} — environment variable (Spring Boot style). Env value wins when set and non-empty; otherwise the default after : is used. Default may contain : freely (regex [^}]*). No :default and env unset → empty string. Env misses are silent — they support dev defaults.
  • ${file:/abs/path} — file contents read once at boot. A trailing \n or \r\n is trimmed; everything else is preserved verbatim, so PEM blocks and similar multi-line payloads round-trip. Missing file or any I/O failure aborts the boot with the path in the error.
  • ${vault:store/path#field} — delegated to the registered bootstrap.SecretResolver. Without a registered resolver the default returns ErrUnsupportedResolver and the boot aborts. Plug a real implementation (HashiCorp Vault, AWS Secrets Manager, …) via bootstrap.RegisterSecretResolver(impl) at process init.

The reserved names file and vault shadow same-named env vars inside ${...} — env-var conventions are uppercase, so the collision is theoretical. file: and vault: failures are strict (boot aborts) on purpose: a missing file or unresolved secret in production is an operational bug, not a silent empty-string default.

Mandatory fields: service, relational.dialect, relational.dsn, mongo.uri, mongo.database, kafka.brokers, kafka.syncGroupId. bootstrap.LoadConfig fails with an error listing missing ones.

The auth: block is optional and defaults to {mode: disabled} when absent — convenient for local development under APP_PROFILE=dev, but rejected at boot under any other profile so prd cannot ship without authentication wired. When mode: jwt, the schema requires issuer + audience + exactly one of jwksUrl / publicKeyPem; the externalValidator sub-block is optional. The external-validator cache is opt-in via cacheTtlSeconds and default off — see the Authentication section for the revocation-vs-throughput trade-off.

Limitations: no recursion (${A:${B:c}} doesn't work — 1 pass); default cannot contain literal }; when the value can be ambiguous with bool/null in YAML, use double quotes.

Programmatic load (rarely needed — bootstrap.Run does it under the hood):

cfg, err := bootstrap.LoadConfig()         // reads APP_PROFILE, selects microservice.<profile>.yaml
cfg, err := bootstrap.LoadConfigFrom(path) // explicit path; no profile guard

API

  • bootstrap.Run(wire func(Deps) Wiring) error — default path. Loads yaml, builds singletons, calls wire, registers default middlewares, brings up HTTP, runs until SIGINT/SIGTERM.
  • bootstrap.Build() (Deps, *Config, error) — only builds deps, without serving. Useful for tests or custom lifecycle.
  • bootstrap.Serve(ctx context.Context, deps Deps, wiring Wiring) error — uses pre-built deps. Does not import translations nor start the SyncEngine — those using manual Build/Serve handle that.

Types

bootstrap.Deps — built singletons: Config, Logger, DB (the core.RelationalEngine — the build-tag-selected engine, already configured with audit destinations + claims via WithAudit), Mongo, Translator, Pipeline, ViewReader (queries.ViewReader), Export (web.ExportDeps{Translator, MaxExportRows} — the bundle every tabular-export route threads alongside the view; always populated), HttpClient (*httpclient.HttpClient; nil when microservice.<profile>.yaml carries no httpClient: block), OpenAPIRegistry (*openapi.Registry; nil when Wiring.OpenAPI is unset — openapi.Mount / openapi.MountRaw treat a nil registry as a Fiber-only passthrough), Cache / SharedCache (cache.Cache; the service-private and cross-service instances, nil unless the cache: / cache.shared: blocks are declared), IntegrationRegistry (*integration.Registry — collects every receiver and backs the admin retry surface), and UpstreamSubscribers ([]*query.UpstreamSubscriber — the live cross-service composition subscribers; nil when none are declared). Audit is not an explicit dependency — every write through the relational engine (Insert/Update/Archive/Unarchive/Delete) emits the configured destinations automatically (in-TX audit_events row for database, post-commit slog line for slog).

bootstrap.Wiring — service declarations: Translations []translation.Module, Features []bootstrap.Feature, BeforeServe func(*fiber.App, Deps) error (optional), OnShutdown func(context.Context) error (optional), OpenAPI *openapi.Config (optional — opt-in to /openapi.json + Swagger UI; see "OpenAPI / Swagger UI").

bootstrap.Feature — interface every service capability implements: Mount(app *fiber.App, deps Deps). Each feature knows how to register its own routes.

bootstrap.ReadableFeature — opt-in for the read side: Feature + Views() []*query.ViewDefinition. Bootstrap automatically collects the views from every ReadableFeature declared in Wiring.Features and passes them to the SyncEngine. A slice (not a single view) covers the case where a feature exposes multiple projections (e.g.: users + users_summary).

Canonical main.go

// service main — any package main, in any directory
func main() {
    if err := bootstrap.Run(Wire); err != nil {
        log.Fatal(err)
    }
}

// Wire — function (Deps) Wiring, in any package
func Wire(d bootstrap.Deps) bootstrap.Wiring {
    return bootstrap.Wiring{
        Translations: []translation.Module{apptrans.PTBR(), apptrans.ENG(), apptrans.ESP(), apptrans.FRA(), apptrans.DEU(), apptrans.ITA(), apptrans.NLD()},
        Features: []bootstrap.Feature{
            NewUsersFeature(d),
        },
    }
}

// Feature struct per aggregate — implements bootstrap.ReadableFeature
type UsersFeature struct {
    repo *appinfra.UserRepository
    view *query.ViewDefinition
}

func NewUsersFeature(d bootstrap.Deps) *UsersFeature {
    return &UsersFeature{
        repo: appinfra.NewUserRepository(d.DB),
        view: appinfra.UserView(), // called ONCE
    }
}

// Views satisfies bootstrap.ReadableFeature (opt-in read side).
func (f *UsersFeature) Views() []*query.ViewDefinition {
    return []*query.ViewDefinition{f.view}
}

// Mount satisfies bootstrap.Feature — delegates HTTP registration to the web/ package.
func (f *UsersFeature) Mount(app *fiber.App, d bootstrap.Deps) {
    appweb.MountUsers(app, f.repo, f.view, d)
}

The composition layer (Feature struct + Wire + main) is separated from the DDD layers: domain/ (pure rules), application/ (commands/handlers), infra/ (domain ports implementation), web/ (owner of the routes). The feature's Mount delegates to web.MountXxx instead of registering routes directly — preserves the DDD ruler "web owns the routes". Where the composition layer lives in the filesystem is the service's decision — the framework only wires up via bootstrap.Run(wireFn).

Common layouts (all supported, none required):

  • Consolidated: bootstrap/ (package main) with main.go + wire.go + <aggregate>_feature.go side by side. Run: go run ./bootstrap. It's the layout used by omnicore-example-users (canonical reference)
  • Go cmd/ convention: cmd/<binary>/main.go + separate package (app/, boot/, etc.) for Wire and Features. Useful for services with multiple binaries
  • Flat: main.go at the root + Wire/Features in a sibling package. Useful for small services

Migrations and CDC artifacts (Debezium connector JSONs, registration scripts) may live at the root (migrations/, debezium/) or co-located with the owning layer (infra/migrations/, infra/debezium/). The example uses the co-located form — semantically they are infra concerns (relational schema, CDC config); Go ignores non-.go files in package directories. Override the path via migrations.dir in microservice.<profile>.yaml.

What the framework does behind the scenes

  1. Reads APP_PROFILE from the environment and loads ./microservice.${APP_PROFILE}.yaml (or $OMNICORE_CONFIG_PATH override); rejects boot if auth.mode=disabled under any profile other than dev
  2. signal.NotifyContext(SIGINT, SIGTERM)
  3. core.NewEngine(dialect, …) (the relational engine for relational.dialect) + mongo.NewMongoDB (defer Close in reverse order)
  4. translation.Default(), pipeline.New(tr).WithLogger(logger), mongo.NewMongoViewReader; configures audit on the relational engine via WithAudit(&cfg.Audit, logger, cfg.Auth.AuditClaims)
  5. wire(deps) returns the service's Wiring
  6. validateWiring — rejects boot if Features == nil && BeforeServe == nil (nothing to serve), and also rejects an empty Wiring.Translations slice (every consumer declares at least one translation.Module)
  7. Translator.Import of modules in Wiring.Translations
  8. Migrations — when cfg.Migrations.AutoRun resolves to true, ValidateDownExists then Up; when it resolves to check, a strict drift check (reads Status + Pending, aborts on a dirty or pending migration); when false, skipped (the check | true | false enum is profile-aware: dev defaults to true, any other profile to check). See "Migrations".
  9. collectViews(wiring.Features) — aggregates Views from ReadableFeatures; rejects boot if 2 features declare the same view name (captures Mongo collection collision)
  10. Log "feature registered" per feature with flag readable: true|false
  11. SyncEngine.Start only if there are collected views (services without CDC don't connect Kafka)
  12. Fiber app + default middlewares fwweb.Recover(), logger.New() (Fiber's request logger), fwweb.AppContextMiddleware(), and fwweb.AuthMiddleware when auth.mode: jwt
  13. GET /health registered automatically (response {"status":"ok"}) — k8s/docker liveness probe without the service programming anything
  14. f.Mount(app, deps) for each feature in declaration order
  15. Wiring.BeforeServe(app, deps) if set (escape hatch for routes/middlewares outside the Feature model)
  16. once every route is registered, each auth.publicRoutes entry is validated against the registered route set — a typo / wrong method / trailing slash (no matching route) or a path parameter / wildcard (which the exact-match auth middleware can never honor — mark the route Doc.Public=true instead) aborts the boot
  17. app.Listen(cfg.HTTP.Addr) in a goroutine; awaits ctx.Done()
  18. HTTP drain (app.ShutdownWithContext) capped at shutdown.drainTimeoutSeconds (default 30s); then Wiring.OnShutdown if set

Custom health (DB ping, external dependencies) must be exposed on another route (/healthz, /ready) via feature or BeforeServe — the framework's /health is pure liveness.

JSON logger on stdout at Info level is the only default. Anyone needing a custom logger (file, datadog) uses Build() + Serve() with their own slog.Logger in Deps, or registers in BeforeServe.

Manual lookup

Most translation in OmniCore is automatic — the Pipeline runs Translator.GetOr on every NotificationKey of the response envelope using AppContext.Language(), and the consumer writes zero lookup code. The escape hatch — for strings that flow outside the Notification path (email subjects, audit lines, human-readable messages on a custom Response, fallback copy for a missing UI string, etc.) — is to call the Translator directly.

The Translator is a process-wide singleton

translation.Default() returns a singleton guarded by sync.Once. On the first call it builds an empty *Translator and imports the seven built-in Core* Modules (CorePTBR, CoreENG, CoreES, CoreFR, CoreDE, CoreIT, CoreNL) — at that point it only knows framework Notification keys.

bootstrap.Run calls translation.Default() once and then imports every translation.Module declared in Wiring.Translations into the same instance. After boot the singleton carries framework + service catalogs in a single map; any code path that needs to translate fetches it without going through dependency injection:

import fwtranslation "github.com/ClaudioSchirmer/omnicore/application/translation"

// In any place that has *AppContext on hand:
subject := fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailSubject", "Welcome")

The fwtranslation alias follows the workspace's fw<segment> convention (fwinfra, fwweb, fwqueries, fwresults, fwresponses) — used whenever the framework's short package name could collide with a consumer package of the same name. The reference example uses the plural translations package and therefore needs no alias in its existing files; doc examples here adopt fwtranslation for unambiguity.

The three lookup methods

MethodSignatureWhen to use
GetOr(lang, key, fallback string) stringDefault. Missing key → returns the fallback silently. Most handlers want this.
Get(lang, key string) (string, error)You want to know a key is missing — for alerting on incomplete catalogs, or when the fallback is expensive to build. Error is always *NotFoundError (carries Language + Key).
Has(lang, key string) boolYou're branching code based on existence (e.g. "if there is a rich HTML version, send rich; otherwise plain text").
 
// GetOr — common case
subject := fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailSubject", "Welcome")

// Get — alert on missing key, build fallback dynamically
subject, err := fwtranslation.Default().Get(ctx.Language(), "WelcomeEmailSubject")
if err != nil {
    var nf *fwtranslation.NotFoundError
    if errors.As(err, &nf) {
        slog.Warn("missing translation", "key", nf.Key, "lang", nf.Language)
    }
    subject = buildFallbackSubject(user)
}

// Has — branch on existence
if fwtranslation.Default().Has(ctx.Language(), "WelcomeEmailBodyHTML") {
    body = renderHTML(fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailBodyHTML", ""))
} else {
    body = renderPlain(fwtranslation.Default().GetOr(ctx.Language(), "WelcomeEmailBody", "Welcome."))
}

Where to call from

  • Manual handler — directly inside Handle(ctx, cmd). ctx.Language() is the request's language; the handler does not need to receive the Translator via DI.
  • Auto Command Handler — the canonical hook is the Command at both boundaries: Cmd.ToEntity(ctx) (T, error) / ApplyTo(ctx, t) error / ApplyPartiallyTo(ctx, t) error on the input side, and Cmd.FromEntity(ctx, t) (TResult, error) on the output side. All four receive *AppContext, return an error so a mapper can raise (the handler routes a NotificationCarrier to Failure, any other error to Exception), and live in the application layer (Cmd is the only layer allowed to translate ctx-derived data into business fields). The handler exposes no projection field — the projection method lives on the Cmd alongside its input mapping.
  • Background job / outbox consumer — no *AppContext. Pass the language explicitly: fwtranslation.Default().GetOr(configuration.LangPTBR, key, fb). The recipient's preferred language usually comes from the entity (e.g. user.PreferredLanguage), not from a request header.
  • Domain BuildRules — do not. The domain layer cannot import application/translation; emit a typed Notification and let the Pipeline translate it via the same singleton on the way out. This keeps domain/ pure (zero IO, zero application imports).

Keys live where the Notifications do

The singleton has no separate "manual keys" bucket — adding one is a single line in any translation.Module the service already registers. The same customerENG.Translations() map that carries "EmailAlreadyExistsNotification" for the Notification path also carries "WelcomeEmailSubject" for the manual path:

func (customerENG) Translations() map[string]string {
    return map[string]string{
        // Notification key — consumed automatically by the Pipeline
        "EmailAlreadyExistsNotification": "Email already registered.",

        // Manual key — consumed by Translator.GetOr / Get / Has
        "WelcomeEmailSubject":            "Welcome to our service",
    }
}

Keys are arbitrary strings — the framework only imposes a convention for Notifications (struct name via reflection). Manual keys can follow any naming scheme; a common pattern is a domain-style prefix (EmailSubject.Welcome, Audit.UserRestored) to keep them visibly distinct from Notification keys in the catalog. To add a key to N languages, add the same key with translated values to each language's Module — boot importing all of them populates the singleton with one combined map.

No DI, no extra fields on the handler struct, no extra parameter on Mount. Default() after boot is the canonical access point — there is one Translator per process and it already knows everything Wiring.Translations declared.

Parameterized notifications

Notifications carry runtime-driven variables into their translated messages without exploding the catalog into one entry per value. Canonical use case: a length / count / amount that varies per tenant or per request configuration, surfaced verbatim inside the user-facing message ("excede o tamanho máximo de 100 caracteres", where 100 comes from per-tenant config).

Declaration — tvar struct tag

The framework reflects over the notification's exported fields tagged tvar:"<name>" and exposes them as the variables {<name>} substitutes against in the catalog string. The struct field name is irrelevant; only the tag value matters.

type NameMaxLengthExceededNotification struct {
    domain.DomainNotificationBase
    MaxLength int `tvar:"maxLength"`
}
// ENG catalog
"NameMaxLengthExceededNotification": "Name exceeds the maximum allowed length of {maxLength} characters.",
// PTBR catalog
"NameMaxLengthExceededNotification": "O nome excede o tamanho máximo permitido de {maxLength} caracteres.",

Multiple fields produce multiple placeholders. Pointer fields are dereferenced (nil renders as empty string). Unexported fields are skipped — the framework can only walk the exported surface. The reflection plan is cached per reflect.Type in a module-level sync.Map, so repeated emissions of the same notification type pay one type lookup + field reads.

Escape hatch — TranslationVars() method

When the variables cannot be expressed as tvar tags (unexported state, computed values, ctx-aware shaping), declare an optional method:

type SensitiveLimitNotification struct {
    domain.DomainNotificationBase
    threshold int  // unexported — invisible to tag reflection
}
func (n SensitiveLimitNotification) TranslationVars() map[string]string {
    return map[string]string{"threshold": strconv.Itoa(n.threshold)}
}

The method replaces (does not merge with) the tag-based extraction. Detected via type assertion (domain.TranslationVarsProvider), so notifications without it pay nothing.

Per-emit override — Vars on NotificationMessage

When the same notification type ships with default vars from its tags but a specific call site needs to inject additional or overriding values, pass them via the per-emit Vars map. The Rules DSL exposes the helper:

r.AddNotificationWithVars(
    "Name",
    NameMaxLengthExceededNotification{MaxLength: u.NameMaxLength},
    map[string]string{"context": "premium-plan"},
    u.Name,                                  // optional value variadic — same as AddNotification
)

Resolution order at render time (per-emit wins on key collision): tag-derived vars (or TranslationVars() output) ← per-message Vars.

Context label vars — SetVars on NotificationContext

The wrapping context label ("User", "Order") goes through the same Translator as messages. Carry runtime variables for the label itself via:

ctx := domain.NewNotificationContext("UserOf{tenantId}")
ctx.SetVars(map[string]string{"tenantId": "acme"})
// catalog: "UserOf{tenantId}": "Usuário de {tenantId}"
// resolved label on the wire: "Usuário de acme"

Empty map and nil both clear the slot. Scoped views forward to the root — ContextVars() always reads from the root of the chain, mirroring how the message Path prefix composes.

Translation surface — Render and Interpolate

func (t *Translator) Render(lang configuration.Language, key string, vars map[string]string) string
func Interpolate(s string, vars map[string]string) string
  • Render(lang, key, vars) resolves the catalog message + interpolates. Scanner accepts the literal placeholder {<name>} where <name> matches [A-Za-z_][A-Za-z0-9_]*; sequences that do not match ({1bad}, {not closed, isolated {) are written verbatim. Missing catalog key → returns key as fallback AND emits slog.Warn("translation.key.missing", ...) once per (lang, key) tuple. Missing placeholder in vars → leaves the literal {name} in the output AND emits slog.Warn("translation.var.missing", ...) once per (lang, key, placeholder) tuple. Both warns dedupe via a process-level sync.Map. vars == nil and vars == {} behave identically: no substitution, no missing-var warn.
  • Interpolate(s, vars) is the substitution-only step (no catalog lookup). Missing placeholders are left literal without firing warn-once — Interpolate has no (lang, key) context to attribute the miss to.
  • Get(lang, key) and GetOr(lang, key, fallback) remain the canonical no-interpolation lookups, for synthetic notifications without vars (e.g., MissingPermissionNotification in PermissionGate, InternalServerErrorNotification in RespondWithInternalServerError).

Pipeline integration

application/notifications/convert.go::ToContextDTOs resolves vars automatically through domain.MessageVars(msg) and ctx.ContextVars(), then renders via Translator.Render instead of Get. Auto Command Handlers, manual handlers, and audit/events paths inherit the new behavior without code changes — the substitution lives at the boundary that already translates.

Backwards compatibility

Notifications without tvar tags AND without TranslationVars() produce nil from ExtractVarsFromTags → Render behaves identically to Get. Catalog entries without placeholders pass through the scanner unchanged. The new Vars field on NotificationMessage and contextVars on NotificationContext default to nil. No existing call site needs editing.
