The write→read data flow

Cutting across the four layers runs the framework's spine: CQRS with event-driven projections, wired through a transactional outbox and an external CDC relay. A write commits one relational transaction holding the data write(s), exactly one outbox row per aggregate operation, and the audit row — atomically. From there the change travels to the read side without the framework ever producing to the broker itself: 

relational TX (one COMMIT)      data write(s) + outbox row + audit row — atomic
        │
        │   CDC relay tails the outbox (reference: Debezium)
        ▼
     broker                     Kafka/Redpanda or NATS JetStream
        │
        ▼
   SyncEngine                   read-side consumer — at-least-once, per-aggregate ordering
        │
        ▼
    composer                    re-reads CURRENT state from the relational source
        │
        ▼
   Mongo view                   the pre-composed projection the query side reads
This is not event sourcing. The relational database remains the single source of truth. The outbox event's payload is a routing hint, not a state carrier: on each event the composer re-reads the aggregate's current state from the relational source and upserts the projection. State is never derived by folding an event log — which is exactly what makes the read side self-healing and every view rebuildable from the system of record at any time (see Mongo schema evolution).

The step-by-step traces live in the write lifecycle map and the read lifecycle map; the broker leg (adapters, the CDC relay, delivery semantics) is documented under Message transport.

The relational engine seam

The relational layer is backend-agnostic by design. PostgreSQL, MySQL, SQL Server, and Oracle (Oracle Database 23ai or higher — the engine adopts the native BOOLEAN/JSON column types) are all first-class: a build tag links each engine (-tags postgres / -tags mysql / -tags sqlserver / -tags oracle; any combination links those engines into one binary, and the active dialect is picked at runtime via relational.dialect). Every engine is a consumer of a single engine seam — the domain and application layers never name a vendor, write raw SQL, or pronounce a physical identifier (those live only in infra/, behind TableSchema). A service's business code is therefore identical whichever engine backs it.

Adding an engine is an isolated seam implementation, not a rewrite. Because every backend plugs into the same seam — dialect-specific SQL generation, type mapping, and error translation behind one interface — introducing a new relational backend does not ripple into consumer services or the layers above infra/. SQL Server joined PostgreSQL and MySQL through exactly this seam, and Oracle followed the same way: one more engine package each, zero change to the layers above.

The message-transport seam

The async message transport is a seam of the same shape as the engine one. The three consumers that read a broker — the read-side SyncEngine, the integration ConsumerPool, and the UpstreamSubscriber — depend on a backend-neutral transport.Subscriber port (infra/transport), never on a concrete client. Selection works exactly like the engine registry: each adapter self-registers in init() behind its build tag, and the composition root resolves it by name — so a build links only the one adapter its tag selects (-tags kafka for Kafka/Redpanda, -tags nats for NATS JetStream), with no default. And, like the engine, the seam is on the consumer side only: a write still lands its outbox row in the domain transaction and a CDC relay ships it, so the at-least-once, dedup and per-aggregate ordering semantics are identical whichever broker backs it.

Adding a transport is an isolated adapter, not a rewrite — the full subsystem (the port, the Kafka/Redpanda and NATS adapters, build-tag selection, the transport: connection config, durability, and the CDC-relay relationship) is documented under Message transport.

Dependency rules

Layer May import NEVER imports
domain stdlib + google/uuid only everything else
application/* domain, other application/* infra, web
infra domain, application/persistence (infra implements the ScopedRepository write binding + TxHandle/hook interfaces; audit emission is owned by infra itself) web
web domain, application/* infra directly
How errors traverse layers without cross-imports: the domain.NotificationCarrier interface (error + NotificationContexts() []*NotificationContext) is implemented by DomainError, ApplicationError, and InfrastructureError. The Pipeline uses errors.As(err, &carrier) and handles any of them uniformly — without needing to import specific packages.
