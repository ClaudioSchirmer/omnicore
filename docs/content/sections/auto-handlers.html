Auto Command Handlers

For trivial CRUD — the logic fits entirely on the Entity via BuildRules — the framework provides ready-made generic handlers. The service writes only the Command — ToEntity(ctx) / ApplyTo(ctx, t) / ApplyPartiallyTo(ctx, t) on the way in AND FromEntity(ctx, t) TResult on the way out, both as methods on the Cmd struct. The wire layer finishes the projection with Response.FromResult(Result) Response. No handler struct to write.

For CRUD with extra rules (cross-service IO, injected domain services), keep writing a manual Handler — they coexist in the same API.

The 6 handlers

Every Cmd implements input boundary + output boundary as methods on its own struct. FromEntity(ctx, T) TResult is required on all 6 verbs — bodyless verbs (Archive/Unarchive/Delete) typically declare TResult = fwresults.None and have FromEntity return fwresults.None{}.

Each Command declares FromEntity(ctx *AppContext, t T) TResult as a method on the Cmd struct (symmetric with the input boundary ToEntity/ApplyTo). The handler calls it after the Writer's write succeeds (for Insert: with the DB-assigned ID set back on the entity via entity.SetID(id)). The Fiber wrapper then runs the consumer's responseProjection func(TResult) TResp to map the Result into the wire Response. For endpoints that do not want to expose anything beyond the success envelope, the Cmd's FromEntity simply returns fwresults.None{} and the wrapper takes fwresponses.NoBody — the runtime detects responses.None and emits the success envelope WITHOUT a "data" field (matches "204 No Content"-style shape).

PUT vs PATCH is HTTP rule, not convention. PUT replaces the entire resource → all fields mandatory; PATCH updates partially → each field optional. The framework enforces it via type: UpdateCommand[T, TResult] (PUT, ApplyTo) and PartialUpdateCommand[T, TResult] (PATCH, ApplyPartiallyTo) are distinct interfaces, consumed by distinct handlers. UpdateCommandHandler embeds the pipeline.FullBody marker that activates strict body check in the Fiber wrapper — missing field → 400 with one RequiredFieldNotification per field before dispatch.

Strict body via marker pipeline.FullBody

Handlers that need to require all Cmd fields present in the JSON body embed the empty struct pipeline.FullBody. The enforceFullBody() method is unexported — only those embedding the marker satisfy the FullBodyEnforcer interface, preventing accidental satisfaction outside the package. 

type UpdateCommandHandler[T, Cmd, TResult] struct {
    pipeline.FullBody  // marker — wrapper activates strict body check
    Repo    persistence.ScopedRepository[T]
    Service domain.Service     // optional — see "Domain Service via Auto handler"
    // No Auditor field — audit is owned by infra.Postgres, configured at boot.
    // No Project field — projection lives on the Cmd as cmd.FromEntity(ctx, T) TResult.
    // In-TX side effects opt in via Cmd's optional AfterBegin / BeforeCommit
    // methods — the handler detects them via type assertion and threads them as
    // WriteOption[T] to the Repo.Update call.
}

The wrappers HandleCommandWithBody{,ID} type-assert to FullBodyEnforcer at construction and, when present, reflect on *TReq (Request DTO) once (cached by reflect.Type) to list exported fields (skipping anonymous embedded and json:"-" tags). Per request: json.Unmarshal of the body into map[string]json.RawMessage + set diff; missing field → 400 with 1 RequiredFieldNotification per field via the normal pipeline (semantic SemanticSchema).

Closed rule — no per-field opt-out. Those who want flexibility use PATCH (handler without marker). PUT is the strict contract.

Fiber route wrappers

Wire format (JSON) is separated from application vocabulary: web/requests/ in the service carries the Request DTOs with json:"..." tags and a ToCommand() method (no ctx — web boundary is dumb mapping); application/commands/ carries the pure Commands without JSON. AppContext reaches the application layer through cmd.ToEntity(ctx) / ApplyTo(ctx, T) / ApplyPartiallyTo(ctx, T) — symmetric with the read side's Query.ToCriteria(ctx). The Command (or Query) is the only layer that may translate identity-derived claims into business-named entity fields (or persistence criteria). The current wrappers:

  • fwweb.HandleCommandWithBody(pipe, sample, responseProjection, h, status) — endpoint with body, without path ID (POST). Allocates TReq via new, validates schema, calls req.ToCommand() on the web→application boundary (no ctx — Request DTO is body-only), Dispatch (handler receives ctx and forwards to cmd.ToEntity(ctx)).
  • fwweb.HandleCommandWithBodyID(pipe, sample, responseProjection, h, status) — endpoint with body, with path ID (PUT/PATCH). Same + cmd.SetPathID(c.Params("id")) before Dispatch.
  • fwweb.HandleCommandWithID(pipe, responseProjection, h, status) — endpoint without body, with path ID (Archive/Unarchive/Delete). Does not call Bind().Body(), does not inspect FullBody.

The responseProjection is a func(TResult) TResp — typically a method value like requests.InsertUserResponse{}.FromResult. For endpoints with no projection, pass fwresponses.NoBody (a func(fwresults.None) fwresponses.None) and use fwresults.None as the handler's TResult.

The whole family starts with HandleCommand — suffixes communicate what the endpoint accepts (body, ID, both). The wrapper always dispatches a Command; Request is only the wire DTO that becomes a Command via ToCommand(ctx) at the boundary.

Body behavior in HandleCommandWithBody{,ID}:

  • Strict handler (FullBody marker): missing body → 400 (all fields missing, semantic Schema); malformed JSON → 400 with SchemaViolationNotification; type mismatch → 400 with SchemaViolationNotification carrying the field's JSON path; missing field → 400 with one RequiredFieldNotification per field.
  • Lenient handler (no marker): missing body OK (Request zero-value); malformed JSON → 400 with SchemaViolationNotification; partial body OK.
HTTP error semantics: 400 = wire contract violated (Request schema doesn't match); 422 = domain rejects values (notifications via BuildRules). Semantic distinction in the notification type: SemanticSchema → 400, SemanticValidation → 422. Wire notifications: SchemaViolationNotification (always Schema) + RequiredFieldNotification{}.WithSemantic(SemanticSchema) (same domain struct, semantic overridden per-instance).

End-to-end example

// 1. Command + Result co-located — application/commands/insert_user.go
package commands

// Input
type InsertUserCommand struct {
    pipeline.CommandBase
    Name  string
    Email string
    Phone *string
}
// ToEntity receives *AppContext — Command is the only layer that translates
// ctx into business-named entity fields. Domain sees only business fields.
func (c *InsertUserCommand) ToEntity(_ *configuration.AppContext) *User {
    return &User{Name: c.Name, Email: c.Email, Phone: c.Phone}
}

// Output method ON THE CMD (symmetric with ToEntity on the input side).
// Receives ctx — same boundary, same translation point.
func (c InsertUserCommand) FromEntity(_ *configuration.AppContext, u *User) InsertUserResult {
    return InsertUserResult{ID: *u.GetID(), Name: u.Name, Email: u.Email, Phone: u.Phone}
}

// Output shape — pure data, no methods.
type InsertUserResult struct {
    ID    domain.ID
    Name  string
    Email string
    Phone *string
}

// 2. Request + Response co-located — web/requests/insert_user_request.go
package requests

// Input (wire format — JSON tags)
type InsertUserRequest struct {
    Name  string  `json:"name"`
    Email string  `json:"email"`
    Phone *string `json:"phone,omitempty"`
}
// ToCommand is body-only — no ctx parameter. Web layer stays free of
// identity interpretation.
func (r InsertUserRequest) ToCommand() *commands.InsertUserCommand {
    return &commands.InsertUserCommand{Name: r.Name, Email: r.Email, Phone: r.Phone}
}

// Output (wire format — JSON tags)
type InsertUserResponse struct {
    ID    domain.ID `json:"id"`
    Name  string    `json:"name"`
    Email string    `json:"email"`
    Phone *string   `json:"phone,omitempty"`
}
func (InsertUserResponse) FromResult(r commands.InsertUserResult) InsertUserResponse {
    return InsertUserResponse{ID: r.ID, Name: r.Name, Email: r.Email, Phone: r.Phone}
}

// 3. Route — sample Request + responseProjection function value anchor generic inference.
// The handler has NO Project field — projection lives on the Cmd as
// `func (c InsertUserCommand) FromEntity(ctx *AppContext, u *User) InsertUserResult`,
// declared in the same file as the Cmd (symmetric with ToEntity on the input side).
users.Post("/", fwweb.HandleCommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[*User, *InsertUserCommand, commands.InsertUserResult]{
        Repo: repo,
    },
    fiber.StatusCreated))

Request ≡ Command shape ruler: required field → string on both (absence in JSON triggers 400 before dispatch); optional field → *string on both (ToCommand is 1:1 assignment without normalization). Consumer sends "" explicitly → Request stores *"" → Command receives *"" → domain decides whether to reject. No silent "" → nil normalization at the boundary.

Uniform pointer Cmd pattern

The handler's second type param is always *Cmd (not Cmd by value). Reason: SetPathID needs a pointer receiver to mutate; using uniform *Cmd (even on Insert) keeps a single mental model. ToEntity/ApplyTo may have a value-receiver OR a pointer-receiver — Go promotes value-receiver methods to the pointer type.

Manual path (cross-service, side effects)

Handler with external IO, injected domain service, or complex orchestration: continues to be a struct that implements pipeline.Handler[*Cmd, TResult] — exactly as before. TResult is whatever application-layer value the handler returns; the route's responseProjection then maps it to the wire TResp. It is registered on the route with the same HandleCommand/HandleCommandWithID.

Domain Service via Auto handler (optional Service field)

The 6 Auto handlers expose an optional Service domain.Service field. When set, it is propagated to the entity's BuildRules (which receives the service as the second argument). This enables infra-dependent queries inside domain rules without falling back to the manual path — e.g., uniqueness invariant that needs a DB query. 

// Domain — interface declarada no pacote da entity, embeda ServiceBase.
type UserService interface {
    domain.Service
    EmailExists(email string, excludeID domain.ID) bool
}

func (u *User) RequiresService() bool { return true }

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Email != "" {
            if us, ok := svc.(UserService); ok && us.EmailExists(u.Email, *u.GetID()) {
                r.AddNotification("Email", EmailAlreadyExistsNotification{}, u.Email)
            }
        }
    })
}

// Wire-up — handler gets the service injected.
users.Post("/", fwweb.HandleCommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[*User, *InsertUserCommand, commands.InsertUserResult]{
        Repo: repo, Service: userService,
    }, fiber.StatusCreated))

Compat: leaving Service nil keeps default behavior (entity receives nil in BuildRules). Pre-existing handlers don't break.

Where Service is consumed: BuildRules runs on every write — Insert (mode Insert), PUT / PATCH (mode Update), Archive and Unarchive (also mode Update with distinct actionName values "GetArchivable"/"GetUnarchivable" — service branches on actionName inside IfUpdate when an archive-specific rule is needed), and Delete (mode Delete). The Service field is the same on all 6 handlers; RequiresService() true on the entity raises ServiceIsRequiredNotification when the field is nil and the handler is invoked.

Defense in depth: the BuildRules check does not replace unique constraints in the DB — between EmailExists and the COMMIT there is room for a race condition. The unique index + ConstraintBinding on the Repository remains the atomic enforcement. The domain check gives a cleaner error message on the happy path and keeps the rule declared where one would expect.

UnarchiveCommandHandler asymmetry

UnarchiveCommandHandler does NOT call FindByID (record is archived; Repository.FindByID filters WHERE deleted_at IS NULL by convention). Instead, it obtains an empty sample via Repo.New(), sets the path ID, and generates Unarchivable. Cascade of archived children is via direct SQL in aggregate_persister.unarchiveAggregate.

The asymmetry is internal to the handler: the wire-up in routes.go is identical to the other Auto handlers — only Repo (audit emission is handled automatically by infra.Postgres). Repo.New() T is a mandatory method of the domain.Reader[T] read port (carried by persistence.ScopedRepository[T]); anyone using BaseRepository[T] injects a single NewEntity func() T into the constructor (typically the same factory shared with the AggregateLoader) and New() comes promoted via embed. 

// UnarchiveUserCommand declares the bodyless verb shape:
//   func (*UnarchiveUserCommand) ApplyTo(_ *AppContext, _ *User) {}
//   func (*UnarchiveUserCommand) FromEntity(_ *AppContext, _ *User) fwresults.None { return fwresults.None{} }
users.Patch("/:id/unarchive", fwweb.HandleCommandWithID(d.Pipeline,
    fwresponses.NoBody,
    &handlers.UnarchiveCommandHandler[*User, *UnarchiveUserCommand, fwresults.None]{
        Repo: repo,
        // Service: userService,  // optional — see "Domain Service via Auto handler"
    }, fiber.StatusOK))
