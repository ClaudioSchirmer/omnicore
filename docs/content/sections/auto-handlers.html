Auto Command Handlers

For trivial CRUD — the logic fits entirely on the Entity via BuildRules — the framework provides ready-made generic handlers. The service writes only the Command — ToEntity(ctx) / ApplyTo(ctx, t) / ApplyPartiallyTo(ctx, t) on the way in AND FromEntity(ctx, t) (TResult, error) on the way out, both as methods on the Cmd struct. The wire layer finishes the projection with Response.FromResult(Result) Response. No handler struct to write.

For CRUD with extra rules (cross-service IO, injected domain services), keep writing a manual Handler (see Custom command handler) — they coexist in the same API.

The full flow of a POST runs the same on both paths; this table maps each responsibility to who owns it — what the framework automates versus what your code provides.

The 6 handlers

Every Cmd implements input boundary + output boundary as methods on its own struct. FromEntity(ctx, T) (TResult, error) is required on all 6 verbs — bodyless verbs (Archive/Unarchive/Delete) typically declare TResult = fwresults.None and have FromEntity return fwresults.None{}.

Mappers raise notifications by return. Every mapper returns error: a fallible step inside ToEntity / ApplyTo / FromEntity (e.g. an external-service lookup, or a field-access reject in a query's ToCriteria) raises a notification through the idiomatic Go return path — the handler propagates it and errors.As at pipeline.Run turns the carrier into a Failure envelope with the notification's HTTP semantic. A mapper that cannot fail returns nil. This is the application-layer counterpart of the domain's accumulate-then-gate: only the sealed domain (a ValidEntity cannot be hand-built) keeps the gate; the open application/infra layers raise by return.

Each Command declares FromEntity(ctx *AppContext, t T) (TResult, error) as a method on the Cmd struct (symmetric with the input boundary ToEntity/ApplyTo). The handler calls it after the Writer's write succeeds (for Insert: with the DB-assigned ID set back on the entity via entity.SetID(id)). The Fiber wrapper then runs the consumer's responseProjection func(TResult) TResp to map the Result into the wire Response. For endpoints that do not want to expose anything beyond the success envelope, the Cmd's FromEntity simply returns fwresults.None{} and the wrapper takes fwresponses.NoBody — the runtime detects responses.None and emits the success envelope WITHOUT a "data" field (matches "204 No Content"-style shape).

Projection contract — read the ENTITY, mirror the post-write state. FromEntity runs on the same instance that BuildRules validated (and possibly normalized) and the persister stored — the domain has the final word, and the response is how the caller learns it. Build the Result only from the entity parameter, never by echoing the Cmd's own fields: an input-echo silently hides every domain transformation. For an aggregate root, the natural Result is the full post-write mirror: every root field (a sibling facet's pointer fields included) plus the child collections read via domain.GetCurrentItemsOf[Child] — populated with the ids the persister minted and wrote back into the aggregate map, so the caller can address each child immediately, without waiting for the read model.

PUT vs PATCH is HTTP rule, not convention. PUT replaces the entire resource → all fields mandatory; PATCH updates partially → each field optional. The framework enforces it via type: UpdateCommand[T, TResult] (PUT, ApplyTo) and PartialUpdateCommand[T, TResult] (PATCH, ApplyPartiallyTo) are distinct interfaces, consumed by distinct handlers. UpdateCommandHandler embeds the pipeline.FullBody marker that activates strict body check in the Fiber wrapper — missing field → 400 with one RequiredFieldNotification per field before dispatch.

The 7th handler — shared-base insert (upsert)

An entity backed by a shared base (a party-role like Customer/Supplier sharing one Person base, keyed by a deterministic UUIDv5 over a natural key) gets a dedicated insert handler: handlers.SharedBaseInsertCommandHandler[T, *Cmd, TResult] (application/handlers/shared_base_insert.go). It is a POST handler that is upsert-aware on the base: when the base identity already exists (another role already created that Person), it does not fail with a unique violation — it loads the existing base and attaches a new role to it. The plain InsertCommandHandler is the wrong tool for a shared-base root — it rejects a SharedBase-backed repository up front with a directive error (the symmetric guard to SharedBaseInsertCommandHandler refusing a non-shared repo), rather than issuing a cold INSERT.

The Cmd declares ApplyTo, not ToEntity. The contract is pipeline.SharedBaseInsertCommand[T, TResult] — Command + ApplyTo(ctx, T) error + FromEntity(ctx, T) (TResult, error). The handler allocates a fresh entity, runs ApplyTo to populate it (so it can read the natural key), then probes the base. Because ApplyTo may run more than once — a throwaway call on a fresh entity to read the natural key, then again on the loaded identity on the warm path — it must be a pure mapper with no side effects:

Base identityactionName passed to the domainEffect
does not exist (cold)"GetInsertable"INSERT base + this role in one TX
already exists (warm)"GetUpsertable"reuse base, INSERT this role; base columns + base-children converge

Both run in ModeInsert — only the actionName differs, so BuildRules can branch on actionName == "GetUpsertable" to relax/adjust rules for the warm path (e.g. tolerate a base field already set by a sibling role). There is no GetUpsertable domain function — it is the same domain.GetInsertable call with a distinct verb string. The blind-insert guard is symmetric: if the base already exists but the entity's actionName is not "GetUpsertable", the write aborts — a forgotten upsert intent never silently overwrites a shared base.

Two-way capability marriage. The handler requires its Repo to also implement persistence.SharedBaseInsertLoader[T] (LoadForSharedBaseInsert(ctx, fresh T) (entity T, existed bool, err error)); a repo that does not satisfy it is rejected at the top of Handle, pointing the caller back at InsertCommandHandler. The canonical repo is read.NewSharedBaseRoleRepository[T](engine, newEntity), whose WithSchema asserts the schema declares .SharedBase(...). Base-children loaded during the warm probe arrive as Constructor status, so the dev dedups/merges them inside ApplyTo (the diff machine treats untouched ones as no-ops).

Wiring is identical to a plain insert — it is a body-with-no-id POST, so it mounts through fwweb.CommandWithBody: 

people.Post("/customers", fwweb.CommandWithBody(d.Pipeline,
    requests.InsertCustomerRequest{}, requests.InsertCustomerResponse{}.FromResult,
    &handlers.SharedBaseInsertCommandHandler[*Customer, *commands.InsertCustomerCommand, commands.InsertCustomerResult]{
        Repo: customerRepo,   // read.NewSharedBaseRoleRepository[*Customer](engine, newCustomer)
    },
    fiber.StatusCreated))

Strict body via marker pipeline.FullBody

Handlers that need to require all Cmd fields present in the JSON body embed the empty struct pipeline.FullBody. The enforceFullBody() method is unexported — only those embedding the marker satisfy the FullBodyEnforcer interface, preventing accidental satisfaction outside the package. 

type UpdateCommandHandler[T, Cmd, TResult] struct {
    pipeline.FullBody       // marker — wrapper activates strict body check
    pipeline.PathIDRequired // marker — ID-requiring handler (wrapper detects; RequirePathID enforces)
    Repo    persistence.ScopedRepository[T]
    Service domain.Service     // optional — see "Domain Service via Auto handler"
    // No Auditor field — audit is owned by the relational engine, configured at boot.
    // No Project field — projection lives on the Cmd as cmd.FromEntity(ctx, T) (TResult, error).
    // In-TX side effects opt in via Cmd's optional AfterBegin / BeforeCommit
    // methods — the handler detects them via type assertion and threads them as
    // WriteOption[T] to the Repo.Update call.
}

The wrappers CommandWithBody{,ID} type-assert to FullBodyEnforcer at construction and, when present, reflect on *TReq (Request DTO) once (cached by reflect.Type) to list exported fields (skipping anonymous embedded and json:"-" tags). Per request: json.Unmarshal of the body into map[string]json.RawMessage + set diff; missing field → 400 with 1 RequiredFieldNotification per field via the normal pipeline (semantic SemanticSchema).

Closed rule — no per-field opt-out. Those who want flexibility use PATCH (handler without marker). PUT is the strict contract.

Fiber route wrappers

Wire format (JSON) is separated from application vocabulary: web/requests/ in the service carries the Request DTOs with json:"..." tags and a ToCommand() method (no ctx — web boundary is dumb mapping); application/commands/ carries the pure Commands without JSON. AppContext reaches the application layer through cmd.ToEntity(ctx) / ApplyTo(ctx, T) error / ApplyPartiallyTo(ctx, T) error — symmetric with the read side's Query.ToCriteria(ctx). The Command (or Query) is the only layer that may translate identity-derived claims into business-named entity fields (or persistence criteria). The current wrappers:

  • fwweb.CommandWithBody(pipe, sample, responseProjection, h, status) — endpoint with body, without path ID (POST). Allocates TReq via new, validates schema, calls req.ToCommand() on the web→application boundary (no ctx — Request DTO is body-only), Dispatch (handler receives ctx and forwards to cmd.ToEntity(ctx)).
  • fwweb.CommandWithBodyID(pipe, sample, responseProjection, h, status) — endpoint with body, with path ID (PUT/PATCH). Same + cmd.SetPathID(c.Params("id")) before Dispatch.
  • fwweb.CommandByID(pipe, responseProjection, h, status) — endpoint without body, with path ID (Archive/Unarchive/Delete). Does not call Bind().Body(), does not inspect FullBody.

The responseProjection is a func(TResult) TResp — typically a method value like requests.InsertUserResponse{}.FromResult. For endpoints with no projection, pass fwresponses.NoBody (a func(fwresults.None) fwresponses.None) and use fwresults.None as the handler's TResult.

The whole family starts with Command — suffixes communicate what the endpoint accepts (body, ID, both). The wrapper always dispatches a Command; Request is only the wire DTO that becomes a Command via ToCommand() at the boundary. Deterministic rule: the base to embed on the Command is the constructor name plus the Base suffix — CommandWithBody → pipeline.CommandWithBodyBase, CommandWithBodyID → pipeline.CommandWithBodyIDBase, CommandByID → pipeline.CommandByIDBase. The two id-carrying bases are the same underlying struct under two names ("WithBody" describes the wire input, the DTO's job; "ByID" describes how the command is addressed), so a command that serves both shapes compiles against either. The same names are also the generic constraints the constructors demand — embed the right base and the compiler settles the rest. The rule holds verbatim on GraphQL (MutationWithBody, MutationWithBodyID, MutationByID) and gRPC (grpc.CommandWithBody, grpc.CommandWithBodyID, grpc.CommandByID).

Body behavior in CommandWithBody{,ID}:

  • Strict handler (FullBody marker): missing body → 400 (all fields missing, semantic Schema); malformed JSON → 400 with SchemaViolationNotification; type mismatch → 400 with SchemaViolationNotification carrying the field's JSON path; missing field → 400 with one RequiredFieldNotification per field.
  • Lenient handler (no marker): missing body OK (Request zero-value); malformed JSON → 400 with SchemaViolationNotification; partial body OK. An explicit JSON null is indistinguishable from an absent field (both decode to the nil pointer), so a PATCH can never assign NULL — it means "keep the current value". Assigning NULL to a nullable field is the strict PUT's job (field present as explicit null), or an intent-specific mini-PATCH command whose ApplyPartiallyTo assigns the nil.
HTTP error semantics: 400 = wire contract violated (Request schema doesn't match); 422 = domain rejects values (notifications via BuildRules). Semantic distinction in the notification type: SemanticSchema → 400, SemanticValidation → 422. Wire notifications: SchemaViolationNotification (always Schema) + RequiredFieldNotification{}.WithSemantic(SemanticSchema) (same domain struct, semantic overridden per-instance).

End-to-end example

// 1. Command + Result co-located — application/commands/insert_user.go
package commands

// Input
type InsertUserCommand struct {
    pipeline.CommandWithBodyBase
    Name  string
    Email string
    Phone *string
}
// ToEntity receives *AppContext — Command is the only layer that translates
// ctx into business-named entity fields. Domain sees only business fields.
func (c *InsertUserCommand) ToEntity(_ *configuration.AppContext) (*User, error) {
    return &User{Name: c.Name, Email: c.Email, Phone: c.Phone}, nil
}

// Output method ON THE CMD (symmetric with ToEntity on the input side).
// Receives ctx — same boundary, same translation point.
func (c InsertUserCommand) FromEntity(_ *configuration.AppContext, u *User) (InsertUserResult, error) {
    return InsertUserResult{ID: *u.GetID(), Name: u.Name, Email: u.Email, Phone: u.Phone}, nil
}

// Output shape — pure data, no methods.
type InsertUserResult struct {
    ID    domain.ID
    Name  string
    Email string
    Phone *string
}

// 2. Request + Response co-located — web/requests/insert_user_request.go
package requests

// Input (wire format — JSON tags)
type InsertUserRequest struct {
    Name  string  `json:"name"`
    Email string  `json:"email"`
    Phone *string `json:"phone,omitempty"`
}
// ToCommand is body-only — no ctx parameter. Web layer stays free of
// identity interpretation.
func (r InsertUserRequest) ToCommand() *commands.InsertUserCommand {
    return &commands.InsertUserCommand{Name: r.Name, Email: r.Email, Phone: r.Phone}
}

// Output (wire format — JSON tags)
type InsertUserResponse struct {
    ID    domain.ID `json:"id"`
    Name  string    `json:"name"`
    Email string    `json:"email"`
    Phone *string   `json:"phone,omitempty"`
}
func (InsertUserResponse) FromResult(r commands.InsertUserResult) InsertUserResponse {
    return InsertUserResponse{ID: r.ID, Name: r.Name, Email: r.Email, Phone: r.Phone}
}

// 3. Route — sample Request + responseProjection function value anchor generic inference.
// The handler has NO Project field — projection lives on the Cmd as
// `func (c InsertUserCommand) FromEntity(ctx *AppContext, u *User) (InsertUserResult, error)`,
// declared in the same file as the Cmd (symmetric with ToEntity on the input side).
users.Post("/", fwweb.CommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[*User, *InsertUserCommand, commands.InsertUserResult]{
        Repo: repo,
    },
    fiber.StatusCreated))

Request ≡ Command shape ruler: required field → string on both (absence in JSON triggers 400 before dispatch); optional field → *string on both (ToCommand is 1:1 assignment without normalization). Consumer sends "" explicitly → Request stores *"" → Command receives *"" → domain decides whether to reject. No silent "" → nil normalization at the boundary.

Uniform pointer Cmd pattern

The handler's second type param is always *Cmd (not Cmd by value). Reason: SetPathID needs a pointer receiver to mutate; using uniform *Cmd (even on Insert) keeps a single mental model. ToEntity/ApplyTo may have a value-receiver OR a pointer-receiver — Go promotes value-receiver methods to the pointer type.

Domain Service via Auto handler (optional Service field)

The 6 Auto handlers expose an optional Service domain.Service field. When set, it is propagated to the entity's BuildRules (which receives the service as the second argument). This enables infra-dependent queries inside domain rules without falling back to the manual path — e.g., uniqueness invariant that needs a DB query. 

// Domain — interface declared in the entity package, embeds ServiceBase.
type UserService interface {
    domain.Service
    EmailExists(email string, excludeID domain.ID) bool
}

func (u *User) RequiresService() bool { return true }

func (u *User) BuildRules(actionName string, svc domain.Service, r *domain.Rules) {
    r.IfInsertOrUpdate(func() {
        if u.Email != "" {
            // GetID() is nil on Insert (the id is minted after validation) —
            // a zero excludeID excludes nothing, which is right for a new entity.
            var excludeID domain.ID
            if id := u.GetID(); id != nil {
                excludeID = *id
            }
            if us, ok := svc.(UserService); ok && us.EmailExists(u.Email, excludeID) {
                r.AddNotification("Email", EmailAlreadyExistsNotification{}, u.Email)
            }
        }
    })
}

// Wire-up — handler gets the service injected.
users.Post("/", fwweb.CommandWithBody(d.Pipeline,
    requests.InsertUserRequest{},
    requests.InsertUserResponse{}.FromResult,
    &handlers.InsertCommandHandler[*User, *InsertUserCommand, commands.InsertUserResult]{
        Repo: repo, Service: userService,
    }, fiber.StatusCreated))

Compat: leaving Service nil keeps default behavior (entity receives nil in BuildRules). Pre-existing handlers don't break.

Where Service is consumed: BuildRules runs on every write — Insert (mode Insert), PUT / PATCH (mode Update), Archive and Unarchive (modes Archive/Unarchive, each dispatched by its own IfArchive/IfUnarchive clause when an archive-specific rule is needed), and Delete (mode Delete). The Service field is the same on all 6 handlers; RequiresService() true on the entity raises ServiceIsRequiredNotification when the field is nil and the handler is invoked.

Defense in depth: the BuildRules check does not replace unique constraints in the DB — between EmailExists and the COMMIT there is room for a race condition. The unique index + ConstraintBinding on the Repository remains the atomic enforcement. The domain check gives a cleaner error message on the happy path and keeps the rule declared where one would expect.

UnarchiveCommandHandler asymmetry

UnarchiveCommandHandler does NOT call FindByID (record is archived; Repository.FindByID filters WHERE deleted_at IS NULL by convention). Instead, when the Repository implements domain.ArchivedFinder[T] it hydrates the archived aggregate via FindArchivedByID (so the cascade SQL sees the archived children via root.AllAggregateItems()); when it does not, it falls back to an empty sample via Repo.New() + SetID. It then runs cmd.ApplyTo and generates Unarchivable via GetUnarchivable. Cascade of archived children is via direct SQL in aggregate_persister.unarchiveAggregate.

The asymmetry is internal to the handler: the wire-up in routes.go is identical to the other Auto handlers — only Repo (audit emission is handled automatically by the relational engine). Repo.New() T is a mandatory method of the domain.Reader[T] read port (carried by persistence.ScopedRepository[T]); anyone using BaseRepository[T] injects a single NewEntity func() T into the constructor (typically the same factory shared with the AggregateLoader) and New() comes promoted via embed. 

// UnarchiveUserCommand declares the bodyless verb shape:
//   func (*UnarchiveUserCommand) ApplyTo(_ *AppContext, _ *User) error { return nil }
//   func (*UnarchiveUserCommand) FromEntity(_ *AppContext, _ *User) (fwresults.None, error) { return fwresults.None{}, nil }
users.Patch("/:id/unarchive", fwweb.CommandByID(d.Pipeline,
    fwresponses.NoBody,
    &handlers.UnarchiveCommandHandler[*User, *UnarchiveUserCommand, fwresults.None]{
        Repo: repo,
        // Service: userService,  // optional — see "Domain Service via Auto handler"
    }, fiber.StatusOK))
