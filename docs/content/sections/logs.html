Logs

The framework writes one structured JSON object per line to stdout — a log/slog JSON handler installed at boot. That is the entire contract on the framework's side: it is always on, there is no YAML to enable it, and it never ships logs anywhere itself. Everything downstream — collecting the stream, indexing it, querying it in a UI — is external architecture you assemble with off-the-shelf tools, configured entirely outside the service. This page shows what the emitted line looks like and sketches the observability stack you can grow from it (Elasticsearch + Kibana as the worked example), so a reader who has never stood one up knows what each piece is and where a working reference config lives.

This is a devops guide, not a framework surface. The framework's only involvement is the JSON line on stdout — none of the tools below are configured in microservice.<profile>.yaml, imported, or known to the service. Logs are the always-on observability channel; distributed tracing is the opt-in spans channel, and audit is the compliance channel that also echoes to this one.

What a log line looks like

Every line is a JSON object with the slog basics — time, level, msg — plus the structured attributes of that event. When observability.tracing is enabled, context-carrying lines also gain a traceId/spanId, so a log pivots straight to its trace. Three representative lines:

An audit echo (emitted when audit.destinations includes slog):

{
  "time":       "2026-06-09T12:00:00.123Z",
  "level":      "INFO",
  "msg":        "audit",
  "threadId":   "5f25e8b0-…",
  "traceId":    "4bf92f3577b34da6a3ce929d0e0e4736",
  "entityType": "User",
  "entityId":   "abc-123-…",
  "verb":       "insert",
  "actor":      "user-42",
  "actorClaims":{ "tenant_id": "acme", "roles": ["admin"] }
}

An outbound HTTP call (httpclient, msg: "http.outbound"):

{
  "level":        "INFO",
  "msg":          "http.outbound",
  "threadId":     "5f25e8b0-…",
  "service":      "keycloak-public",     // the UPSTREAM called — see the collector note below
  "method":       "GET",
  "url":          "https://idp.example/realms/…/users/42",
  "status":       200,
  "durationMs":   37,
  "attempt":      1,
  "cacheStatus":  "miss",
  "breakerState": "closed"
}

An internal event (each subsystem names its own msg):

{ "level": "INFO", "msg": "integration.event.emitted", "threadId": "5f25e8b0-…", "eventType": "user.created", "eventId": "…" }

The stable anchors you will filter on are msg (the event name), threadId (the per-request id, = AppContext.ID()), traceId, and — on writes — entityType/verb/actor. The full audit field list is in Audit → The event shape.

Why this drops straight into Elasticsearch (or Loki, or …)

Because each line is structured JSON, a collector decodes every key to a top-level field — status, verb, traceId become queryable columns with no fragile regex/grok parsing. Unstructured text logs force you to pattern-match at ingest; structured logs skip that entirely. That is the whole reason the emitted line is JSON rather than a formatted string.

The external pipeline you build around it has four stages:

  your service            a collector              a store + index          a query UI
 (stdout: JSON)   ─────▶  (tails the stream) ─────▶ (indexes each field) ────▶ (filter / dashboard)

  the framework           Filebeat, Fluent Bit,     Elasticsearch,            Kibana,
  (always on,             Vector, Promtail, …       OpenSearch, Loki, …       Grafana, …
   zero config)
  • Collector — an agent that reads the process's stdout (or a file it is redirected to) and forwards each line. It is the only piece that touches your service, and it does so from the outside.
  • Store + index — Elasticsearch (or OpenSearch, its fork) is a document store that indexes every field so millions of lines are searchable in milliseconds; Loki is a lighter, label-oriented alternative.
  • Query UI — Kibana is the web UI over Elasticsearch where you filter, chart, and dashboard those fields; Grafana plays the same role over Loki.

The collector reads the stream directly

Nothing in the service knows the store exists. The service writes JSON to stdout; the collector, a separate process, tails that stream and forwards it. The reference bench ships a working Filebeat config in omnicore-example-users/devops/elk/ (filebeat.yml + es-template.json + a Kibana setup) — copy it as a starting point. The essential part is the JSON decode: 

parsers:
  - ndjson:                      # each stdout line is one JSON object → decoded to the document root
      target: ""
      overwrite_keys: true
      add_error_key: false       # non-JSON lines (the Fiber request logger) stay as a plain `message`
      ignore_decoding_error: true

Two things the reference config does, worth copying: it stamps the emitting service name onto every line and renames the http.outbound line's service field (which names the upstream) to upstream, so service means one thing across all logs; and its es-template.json maps the polymorphic audit payloads (snapshot/changes/children) as flattened so they never trigger a mapping conflict.

Querying in Kibana

Once the lines are indexed, you filter by field (Kibana's KQL). A few examples:

GoalQuery
All errors from this serviceservice: "omnicore-example-users" and level: "ERROR"
Every line of one requesttraceId: "4bf92f3577b34da6a3ce929d0e0e4736"
Failing outbound callsmsg: "http.outbound" and status >= 500
One request across servicesthreadId: "5f25e8b0-*"

With tracing on, the traceId on any line is the same id you paste into Jaeger to open the whole request as a span tree — the log finds the trace, the trace shows the timing.

Auditing in Kibana

Audit needs no extra plumbing to reach this pipe. When audit.destinations includes slog, each write emits an msg: "audit" line that flows through the very same collector → store → Kibana path. So the same stack that browses application logs also filters the audit trail:

GoalQuery
Every audited write on Usersmsg: "audit" and entityType: "User"
Deletes by one actormsg: "audit" and verb: "delete" and actor: "user-42"
Everything a tenant touchedmsg: "audit" and actorClaims.tenant_id: "acme"

Kibana is for observability, not the system of record. The slog echo fires post-commit and is best-effort — lossy if the shipper drops a line. The authoritative, in-transaction audit trail is the database destination (Audit → Two destinations); point compliance queries there and use Kibana to explore. As on any line, the audit traceId jumps to its trace.

It is optional — the store is the heavy part

Emitting logs costs essentially nothing; it is already happening. The consumption stack is the weight — Elasticsearch in particular is memory-hungry. The reference bench keeps the whole ELK stack (Elasticsearch + Kibana + Filebeat) behind a Docker Compose elk profile, off by default, precisely to free ~1.6 GiB for the other lanes; you opt in with --profile elk up -d when you want to browse. A real deployment does the same at scale: it points a managed or shared logging platform at the same unchanged stdout — the service, and the JSON line it emits, stay exactly as they are.
