Migrations

Framework manages numbered SQL migration files, with up/down, versioning via its own table, and dirty state recovery. Wrapper over golang-migrate/migrate v4 — we don't reimplement lock/recovery/parsing. The migration policy (filenames, tracking tables, strict mode) is dialect-neutral; only the runner that opens the connection and the embedded framework SQL are per-dialect.

Filename convention

migrations/
  0001_init.up.sql          # service schema — the service's OWN sequence starts here
  0001_init.down.sql        # reverse (mandatory)
  0002_add_phone.up.sql
  0002_add_phone.down.sql

A service's own migrations are an independent sequence starting at 0001. They do not continue the framework's numbering: the framework's embedded 0001_framework is tracked in a separate table (omnicore_framework_migrations), so the service's 0001 in omnicore_migrations never collides with it (see Tracking). Because each backend speaks a different SQL dialect, a service that targets more than one backend keeps a directory per dialect (migrations/postgres/, migrations/mysql/, migrations/sqlserver/, migrations/oracle/) and points migrations.dir at the one matching relational.dialect. On Oracle, migration files carry plain SQL statements separated by semicolons — the runner feeds them to the server one by one (Oracle's protocol takes a single statement per execute), so PL/SQL blocks (BEGIN…END with internal semicolons) are not supported in migration files.

An empty sequence is a legitimate state, not an error. A freshly scaffolded service has no migrations of its own yet — migrations.dir is missing or holds no versioned *.up.sql (e.g. only a .gitkeep). Up (the autoRun: true path) then applies the framework's embedded control plane and skips the service stage; Pending and ValidateDownExists already treat the same state as "nothing to do". The service's real 0001 arrives with its first entity.

Tables behind the relational specialization mechanisms have shape requirements your migration must satisfy — a sibling table shares the owner's ID and declares no ParentID and no deleted_at (the owner owns the lifecycle); a shared base stores a deterministic UUIDv5 ID with its natural-key column UNIQUE NOT NULL and no soft-delete, and each role table carries a UNIQUE ParentID to it. The authoritative column-by-column shapes (per engine) live in TableSchema.

The framework's embedded control plane

The framework ships its own embedded, per-dialect migration sequence (infra/migration/embedded/{postgres,mysql,sqlserver,oracle}/, injected via embed.FS), tracked separately from the service's files. It currently holds three migrations. 0001_framework.{up,down}.sql creates the whole control plane in one flattened migration — six tables:

  • outbox — the Debezium CDC source.
  • omnicore_mongo_views — the Mongo view registry.
  • audit_events — the audit trail (a plain table on every backend; the id is a time-ordered UUID v7, so the primary key alone gives append-only insert locality — no partitioning). Retention and any forensic index (by actor / tenant / thread / time) are operational concerns owned by devops.
  • integration_events — producer-side integration-event store.
  • omnicore_integration_failures / omnicore_integration_processed — the consumer failure registry + dedup table.

The distributed-tracing carrier columns (outbox.traceparent, integration_events.traceparent, audit_events.trace_id) are inlined into that first migration, and every table + column carries a COMMENT. 0002_view_slots.{up,down}.sql then adds the online blue-green rebuild pointers (active_collection / shadow_collection) to omnicore_mongo_views; every pre-blue-green row is already in the NULL-active state, so it needs no data backfill (see Mongo schema evolution). 0003_projection_failures.{up,down}.sql adds omnicore_projection_failures — the read-side's unified failure ledger (parked projection events + failed embed-segment ripples), replayed by the mongo.parkedRetry loop. The whole framework sequence is tracked in its own table (omnicore_framework_migrations), fully separate from the service's own table (omnicore_migrations) — so the service's files are numbered independently and start at 0001 with no collision. The per-dialect embedded source is selected at boot by frameworkSourceFor(dialect) (the embedded/<dialect> subdirectory). Do not write the framework SQL manually; the framework guarantees an identical signature across all services on each backend (Debezium depends on the outbox shape).

Default behavior at boot

  • bootstrap.Run applies all pending migrations before serving HTTP when cfg.Migrations.AutoRun resolves to true (profile-aware default — see below)
  • Order: wire(deps) → ValidateDownExists → Up(framework) → Up(service) → SyncEngine → serve
  • Migration failure prevents the service from starting (boot returns error)
  • Each migration runs in an isolated transaction — failure = rollback + dirty=true persisted in the tracking table
  • .down.sql mandatory (validated at startup); may be a no-op when reverse is technically infeasible
  • filenames must carry a parseable {version}_{name} prefix (0001_init) — a file like init.up.sql or v2_init.up.sql is silently ignored by the migration loader, so the same startup validation rejects it rather than letting the SQL never run while boot reports success

Tracking

Two separate tables, created automatically by golang-migrate on first execution (no embed SQL for them):

TableWho writesContains
omnicore_framework_migrationsFramework (embedded)the framework sequence — 0001_framework (control plane) + 0002_view_slots (blue-green pointers)
omnicore_migrationsService (files in cfg.Migrations.Dir)version 1+ (the service's own sequence)

Separate tables avoid version collision — the framework table and the service table each carry their own independent sequence, both starting at version 1 (the framework's 0001_framework and the service's 0001_init) without conflict. This is exactly why a service numbers its files from 0001: the framework's own migrations (0001_framework, 0002_view_slots, and any it adds later) live in a different table and never consume a slot in the service's sequence.

Each table stores only (version BIGINT PRIMARY KEY, dirty BOOLEAN). The .down.sql is not stored — it is read from disk/embed at Down(N) time.

API — one Manager, a per-dialect constructor

The migration.Manager is dialect-neutral; only its constructor (and the connection it opens) is dialect-bound, and each constructor lives behind its engine build tag. Pick the one matching relational.dialect:

// Postgres — opens its own *sql.DB from the DSN (build tag: postgres)
mgr := migration.NewPostgres(dsn, "./migrations/postgres")

// MySQL — opens its own *sql.DB from the DSN (build tag: mysql)
mgr := migration.NewMySQL(dsn, "./migrations/mysql")

// SQL Server — opens its own *sql.DB from the DSN (build tag: sqlserver)
mgr := migration.NewSQLServer(dsn, "./migrations/sqlserver")

// Oracle — opens its own *sql.DB from the DSN (build tag: oracle)
mgr := migration.NewOracle(dsn, "./migrations/oracle")

// Same surface on either Manager:
mgr.Up(ctx)              // applies pending (framework then service)
mgr.Down(ctx, 1)         // reverts N service migrations
mgr.Status(ctx)          // (version uint, dirty bool, err error) — service only
mgr.Pending(ctx)         // ([]uint, error) — versions on disk but not yet applied
mgr.Force(ctx, 5)        // recovery: marks version=5, dirty=false
mgr.ValidateDownExists() // checks .down.sql counterpart for each .up.sql

bootstrap.Run builds the right Manager automatically from the selected engine — services normally never call these directly.

Profile-aware default and strict mode

cfg.Migrations.AutoRun is a closed-set AutoRunMode enum — check | true | false — sharing the same three-mode semantic as mongo.rebuild.autoRun (true = validate + apply pending; check = validate only, abort boot on pending/dirty; false = skip both validation and application). A bare YAML bool (true/false) normalizes to the matching string. When the YAML leaves it unset it resolves to true under APP_PROFILE=dev and to check (the strict validation mode) under any other profile. An explicit YAML value wins regardless of profile.

Under the strict check default in non-dev profiles, bootstrap.Run does NOT apply migrations automatically. Instead it reads mgr.Status and mgr.Pending and:

  • If dirty=true: aborts boot with a diagnostic naming the version + the Force recovery option.
  • If Pending returns non-empty: aborts boot with a diagnostic listing every pending version + the current DB version + the operator's recovery options (flip autoRun=true + restart, or run the migration out of band).
  • Otherwise: logs "migrations up to date (strict mode)" and proceeds.

Recovery (dirty state)

A migration that fails mid-way leaves dirty=true persisted. Subsequent Up calls fail until Force(version) is called. Force does not create/undo schema — it only resets the tracking pointer. The operator must manually fix the DB state first.

How each runner opens its connection

  • Postgres — adapts the live pgxpool.Pool to a *sql.DB via pgx/v5/stdlib.OpenDBFromPool. The package guarantees that Close() on that sql.DB does not close the pool, so every open/close of migrate.Migrate is isolated and the engine's pool stays alive for the rest of the service.
  • MySQL — opens its own *sql.DB from the DSN (closed when each migrate instance closes), rather than sharing the engine's live pool. It also ensures the DSN carries multiStatements=true so the flattened multi-statement framework migration runs regardless of the operator's DSN config.
  • SQL Server — opens its own *sql.DB from the DSN (closed when each migrate instance closes), like MySQL. No DSN massaging is needed: go-mssqldb executes multi-statement batches natively.
  • Oracle — opens its own *sql.DB from the DSN, like MySQL/SQL Server, over a framework-owned migrate driver (golang-migrate ships no Oracle driver): statements are split on top-level semicolons and executed one by one, the tracking row lives in a version NUMBER(19) + dirty BOOLEAN table, and concurrent migration runs serialize on a DBMS_LOCK session lock. Operational requirement: the application user needs GRANT EXECUTE ON SYS.DBMS_LOCK — not a default grant; it powers both the migration lock and the Mongo-view rebuild lock.
