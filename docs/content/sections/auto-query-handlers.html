Auto query handlers

Symmetric to the Auto command handlers on the write side: for the common read — a paged listing or a by-id lookup served straight from a pre-composed Mongo view — the framework ships ready-made generic query handlers plus the HTTP wrappers that wire them. The consumer writes zero handler code; it declares the Request DTO allowlist (which fields and operators the endpoint accepts), the application Result and the Response shape, and the framework owns the rest: query-string parsing, allowlist enforcement, the ReadCriteria assembly, the ViewReader call, the Result fill, pagination, and the wire projection.

The QueryHandler · CQRS page covers the concept, the end-to-end flow of a GET and the Result anatomy; the Custom query handler page covers the manual escape hatch. This page is the full reference for the automatic path: the two wrappers and the response-projection seat, the Automatic × Manual split, the query-string capabilities the wrappers enforce, and the complete end-to-end example.

The wrappers and the response projection

The wire boundary lives in two HTTP wrappers in web/:

  • fwweb.QueryWithParams[TReq, TQ, TResult, TResp](pipe, sample, responseProjection, h) — paged listing (GET /users). Validates the query string against the Request DTO's query:"X" filter:"ops" tags, assembles a queries.ReadCriteria, calls req.ToQuery(criteria) — pure body mapping at the boundary, no ctx. AppContext reaches the application layer through q.ToCriteria(ctx), which the framework's FindByParamsQueryHandler[*Q, TResult] calls before forwarding to ViewReader.ReadPage — where JWT-derived overlays (tenant id, owner id) layer onto the criteria. The handler returns a typed queries.PageOf[TResult]; on success the wrapper maps each item through responseProjection and returns the standard Response envelope with data as the projected items array and pagination as a top-level field.
  • fwweb.QueryByID[TReq, TQ, TResult, TResp](pipe, sample, responseProjection, h) — by-id lookup (GET /users/:id). Only ?includeArchived=true is reserved — and it obeys the DTO like every control: honored only when the Request DTO declares query:"includeArchived", rejected as the canonical NotDeclared 400 otherwise. Any other query parameter produces 400. Calls req.ToQuery(criteria) (no ctx) — the same seat the paged wrapper feeds, over the same ReadCriteria; a by-id read's wire vocabulary is simply smaller, so the criteria carries IncludeArchived and nothing else. It goes through the SAME assembler a listing does — each surface reads the control in its own idiom (REST off the query string, gRPC off the bound DTO via queryschema.ReadIncludeArchivedControl, GraphQL off its argument) and the canonical opt-in gate answers for all three, so a control the endpoint never declared is refused here exactly as it is on the listing. It then injects the path id via q.SetPathID(...), dispatches via FindByIDQueryHandler[*Q, TResult] which calls q.ToCriteria(ctx) and forwards both id + criteria (IncludeArchived flag + any JWT overlay) to ViewReader.ReadByID — symmetric DTO with ReadPage. The handler returns TResult, which the wrapper maps through responseProjection; not-found produces 404 with RecordNotFoundNotification. An overlay filter that filters the doc out is indistinguishable from absence at this layer: both surface as 404.

Both wrappers have *Spec siblings — QueryWithParamsSpec / QueryByIDSpec — carrying the same type parameters and the same argument order, and returning (handler, openapi.RouteSpec) for the canonical fwopenapi.Mount path.

Deterministic rule, same as the write side: the base to embed on the Query is the constructor name plus the Base suffix — QueryWithParams → queries.QueryWithParamsBase, QueryByID → queries.QueryByIDBase. The same names are the role interfaces the constructors demand, each generic over the Result (queries.QueryWithParams[TResult] requires ToCriteria(ctx) and FromQueryResult(ctx, r); queries.QueryByID[TResult] adds SetPathID/PathID() — the exact pair pipeline.CommandByID carries on the write side — plus ContextName()). The rule holds on GraphQL (graphql.QueryWithParams, graphql.QueryByID) and gRPC (grpc.QueryWithParams, grpc.QueryByID).

The response projection (third argument) is mandatory and has signature func(TResult) TResp — the exact seat the command wrappers already take. It is the ONE place the wire shape is decided, and every other surface (the CSV/XLSX export, GraphQL, gRPC) takes the same seat, so a Response is projected identically everywhere:

Response projectionUse when
Response{}.FromResult delegating to fwresponses.Map[Response] Tag-driven mapping — the default. fwresponses.Map[TResp](result) is the generic name-based mapper: it reads each Response field's same-named Result field and writes it under the field's json: wire name, recursing through nested structs, slices of structs and pointer fields, normalizing nil slices to empty typed slices and converging out-of-set enum values to Unknown. Wire naming is the only thing the Response decides.
A hand-written Response{}.FromResult Renaming or reshaping the tags cannot express — flattening a nested Result segment, folding two Result fields into one wire field. The constructors accept any func(TResult) TResp, so the method body is yours.
Read-side COMPUTATION does not belong in FromResult. Derived fields, ctx-aware shaping and anything that can fail live in the Query's FromQueryResult hook, in the application layer — so REST, the exports, GraphQL and gRPC all render the same values. FromResult is wire naming, nothing more.

Result↔Response alignment is boot-guarded. At wrapper construction queryschema.ValidateResultAlignment walks the Response recursively: every exported, non-json:"-" field must have a same-named field on the Result, and the Result must carry no json tags at all (wire naming belongs to web/). Either violation is a boot panic naming every offending field path — a Response field with no Result backing can never ship as a silently-null column.

Auto mapping — fwresponses.Auto and the boot guard

Every mapping seat in this framework is hand-written by default — ToCommand, ApplyTo, FromEntity, ToCriteria, FromResult. fwresponses.AutoFromResult is the framework's offer to write FromResult for you, and a Response ACCEPTS the offer by embedding fwresponses.Auto: 

type FindUsersByParamsResponse struct {
    fwresponses.Auto                       // opt-in: the framework maps this

    ID   *string `json:"id,omitempty"`
    Name *string `json:"name,omitempty"`
}

func (FindUsersByParamsResponse) FromResult(r appqueries.FindUsersResult) FindUsersByParamsResponse {
    return fwresponses.AutoFromResult[FindUsersByParamsResponse](r)
}

What the declaration buys, and what it costs:

  • AutoFromResult becomes callable. Without the marker it does not COMPILE — the generic constraint rejects the type — so a Response can never silently ride a mapping it did not ask for. The marker's method is sealed (unexported, granted only by the embed), so the opt-in cannot be forged either.
  • The pair is validated at Mount (boot). Every Response field must have a same-named Result field, and every mapped pair must be directly assignable. A violation is a boot panic naming the field — never a wire field that renders null forever, and never a silent per-request serialization cost.
Where the check happens — and where it cannot

The Mount-time check lives in the CANONICAL route constructors (QueryWithParams, QueryByID, CommandByID, CommandWithBody, CommandWithBodyID): they receive both the Result and the Response as type parameters, so they can check the pair before the service serves anything. Every OTHER call site maps on its own and has no such seat — a hand-written fiber.Handler that projects the Result itself, the GraphQL and gRPC surfaces, the CSV/XLSX export, or any surface added later.

There, the identical contract is enforced on FIRST USE instead: the mapper refuses the pair and the recovered panic surfaces as a 500. The failure is not different and the endpoint was never partly working — the pair could never have been mapped; only the moment of discovery moved, which is why it can appear on a rarely-hit endpoint long after deploy. The panic text says so in as many words, and carries the same diagnosis, the same three ways out and the same table of what travels, so the reader never has to come back here to act on it.

Want boot-time (or CI-time) detection on those surfaces? Assert the pairs yourself: responses.AutoFromResultReason(resultType, respType) and requests.AutoRequestReason(reqType, cmdType) return the empty string when the pair travels and the diagnosis when it does not. A unit test sweeping your service's pairs turns a production 500 into a red build — and it covers the canonical routes too, which unit tests otherwise never exercise, since nothing mounts the routes there.

A Response WITHOUT the marker keeps the default posture: no guard, no generic mapper, FromResult written by hand — free to rename (Result.Name → Response.Nickname), flatten a nested segment, or fold two Result fields into one wire value. That escape hatch is the reason the marker is opt-in rather than automatic.

The one rule, on both seats

The same contract governs the write side ( fwrequests.Auto), and it is easiest to remember by LAYER:

A type in web/ (Request, Response) must be fully connected. A type in application/ (Command, Result) may carry more.

Both refusals protect the same thing: a wire field that is not connected to anything. Both allowances say the same thing: the application side is free to carry state that does not make that particular trip.

What travels

A pair maps automatically when every mapped field is one of:

Field shapeExample
Identical typesstring → string, time.Time → time.Time, a value object → itself
Pointer wrapping / unwrappingstring → *string (a nil source leaves the field zero, as an absent value does)
Same-family numeric conversionint32 → int64, float32 → float64 (out of range leaves the field zero)
domain.ID ↔ stringthe ID's value IS its string form
Struct → struct, slice → sliceresolved recursively by the same rules
Map → map, same key typemap[string][]ChildResult → map[string][]ChildOutput — the values travel by the same rules. A different KEY type is refused: the key is what a consumer indexes by, so converting it would change the shape the caller reads.

What forces the hand-written seat is a field whose two sides DIFFER while one of them owns its own JSON or text codec — time.Time → string is the common one, since only MarshalJSON knows the RFC 3339 rendering — or a conversion the framework will not invent, such as float64 → int64 (whose rounding belongs to the codec). The boot panic names the field and the cause; the remedy is to align the two types and let the Query's FromQueryResult hook produce the rendered value — which is where read-side computation belongs anyway.

The Response carries json: only — no source-key override exists. The typed Response struct declares json:"<wire>" tags (plus the optional exportLabelKey header key the tabular export reads) and nothing else. The Result it maps from is keyed by Go field name, and the reader (MongoViewReader) already translated each physical column to its Go field name using the view's TableSchema tree. So there is no view: tag and no PascalToSnake at the Response layer — the json: tag governs the wire shape (Go field → JSON), and the TableSchema on the infra side governs the column shape (Go field → column): 

type AddressOutput struct {
    Street     string `json:"street"`        // Go field Street → wire "street"
    ZipCode    string `json:"zipCode"`       // Go field ZipCode → wire "zipCode"
    PostalArea string `json:"postalArea"`    // Go field PostalArea → wire "postalArea"
}

A column whose physical name diverges from the Go field is handled entirely on the infra side: TableSchema.Field("PostalArea", "cep") maps the Go field PostalArea to the legacy column cep. The Response stays oblivious — it only ever pronounces the Go field name and its wire name.

Managed slots have FIXED Go names — whatever the physical column. The document key is the field's Go name, and for ID, ParentID, CreatedAt, UpdatedAt and DeletedAt that name is locked by the framework: a Result field named after the column (ArchivedOn for DeletedAt("archived_on")) reads nothing and stays silently null. The full naming contract lives in The three-name model.

Consumers typically declare a typed FindXxxResponse struct in web/requests/find_xxx.go (co-located with the Request) with a FromResult method over the Query's FindXxxResult, and pass requests.FindXxxResponse{}.FromResult at the route. The Result owns field existence, the Response owns the wire names.

Allowlist via struct tags

Each filter field on the Request DTO declares its set of allowed operators via the filter:"eq,in" tag — the operator vocabulary itself (the Op* constants, case-insensitive twins, AND-ing, regex escaping) is documented once on the QueryHandler · CQRS trunk, since the custom path reads the same tag. The wrapper inspects the type (cached by reflect.Type in a module-level sync.Map) and rejects any query-string key outside the declared set with 400 SchemaViolationNotification. Reserved pagination/control keys (first, last, after, before, orderBy, fields, search, includeArchived, onlyTotal) are declared with only the query:"..." tag (no filter tag) — recognized only at the top level, never inside an embed group. orderBy is the one control that does not stand alone: it is the SWITCH of a pair whose other half is the sort: declarations that fill its vocabulary, and either half without the other is a boot fail of its own. The control vocabulary is closed: a query-tagged scalar carrying neither filter: nor sort: whose key is not one of the nine canonical controls is a boot fail (panic at wrapper construction naming the DTO, the offending tag and the canonical list) — a typo like query:"orderby" or a stale spelling like query:"limit" would otherwise opt nothing in while OpenAPI advertised the dead parameter. A leaf that carries sort: and no filter: is the third legal shape: it names a path ?orderBy= may use and takes no value of its own, so it emits no query parameter either.

The boolean controls accept exactly true or false. ?includeArchived= and ?onlyTotal= refuse every other spelling — 1, t, TRUE, yes — with the canonical 400 on the control's own key. Strictness is the point: the same value has to mean the same thing on every connector, and the other two enforce it by wire format already (a proto bool and a GraphQL Boolean cannot carry "1"). A parser that quietly read anything-but-true as false is what let ?includeArchived=1 be false on a listing and true on a by-id read of the same entity.

PRESENCE is the key being on the query string, not the value being non-empty. ?onlyTotal= is the control asked for with no answer, and it is refused on the value — not read as "absent", which would rebuild the same list-vs-by-id disagreement on a different spelling. A control the endpoint never declared is refused either way, on the same key.

Behind the allowlist, the view has the last word. The allowlist validates a request against the DTO; the reader then resolves each Go field path against the view's TableSchema tree. A path the view cannot resolve — a DTO field that does not match any column or segment the view projects, typically a collection field spelled differently from the child's CollectionName() — is rejected with the same canonical 400 SchemaViolationNotification, naming the offending dotted Go path. This covers ?filter, ?orderBy= and ?fields= alike, on the Mongo and relational backings equally. It is deliberately not a silent fallback: passing an unresolvable path through to the store would answer 200 with an empty page for a mistyped filter, and 200 unsorted for a mistyped sort. (An UNREGISTERED view name has no schema to check against, so its paths still pass through untouched.)

The DTO governs every surface. The Request DTO is the single source of truth for what a list endpoint exposes: a reserved control the DTO does not declare is rejected on EVERY surface — REST answers 400 with the control key as the field; GraphQL cuts the argument out of the generated schema (introspection and the playground never advertise it, and the validator rejects it as an unknown argument); gRPC rejects at runtime with INVALID_ARGUMENT naming the missing declaration (the shared proto cannot narrow per RPC). All three run the same canonical validation gateway (queryschema.ValidateControls) BEFORE the handler: the opt-in gate, the directional rule (forward first/after × backward last/before, sizes positive), and the only-total conflict matrix — one implementation, three idiomatic renderings, zero drift. A developer reads the attached Request DTO and knows exactly what the endpoint speaks; a new surface plugs into the same gateway.

Nested embed groups

A struct-typed field carrying query:"prefix" (no filter:) is an embed group — the walker recurses, and every leaf below it produces a wire key prefixed by prefix.. Symmetric with the Response side, where a nested struct maps from the same-named nested Result segment. 

type FindUsersByParamsRequest struct {
    Name      *string             `query:"name"  filter:"eq,startswith"`
    Email     *string             `query:"email" filter:"eq,in"`
    Addresses AddressFilterParams `query:"addresses"`

    First *int64 `query:"first"`
    Last  *int64 `query:"last"`
}

type AddressFilterParams struct {
    City    *string `query:"city"    filter:"eq,istartswith"`
    ZipCode *string `query:"zipCode" filter:"eq,startswith"`  // wire zipCode → Go ZipCode; reader maps to column zip_code via the view TableSchema
}

Wire shape: ?addresses.city=Berlin, ?addresses.zipCode.startswith=10001. Translation is a two-hop pivot through the Go field name. At the web boundary the wire token maps to the Go field path via the DTO's query: tags (zipCode → Addresses.ZipCode) — filter keys are always Go field paths. The reader (MongoViewReader) then translates the Go path to the physical Mongo column via the view's TableSchema tree (ZipCode → zip_code). There is no PascalToSnake and no view: tag on this path — the physical column name lives only in the TableSchema. Pointer-to-struct embed groups (*AddressFilterParams) recurse identically.

Sibling and shared-base fields are flat

A field that physically lives in a sibling table or a shared base (the relational specialization mechanisms — a 1 : 1 vertical split, or a party-role identity shared across roles) is not an embed group. The framework partitions the row across those tables on write and merges them back flat at the owner's level on read (the composer's mergeOwnerSiblings / the role carrying every base field), so on the read side they behave exactly like the owner's own columns. Declare them as top-level fields on the Request and Response DTOs — no prefix — and filter: / ?orderBy= / ?fields= work identically to a native field. The TableSchema field resolver is sibling-aware (columnForRead / goNameForRead route a Go field to its sibling's column), and the relational aggregate loader LEFT JOINs the sibling table only when a criteria actually references one of its fields. The wire / DTO author never sees the partition — it is an infra concern.

Sparse responses via ?fields=

Opt-in field projection — the consumer asks for a subset of the Response shape and the framework strips everything else end to end. The Request DTO opts in by declaring Fields *string `query:"fields"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type TResp is a struct, three things happen automatically:

  1. Boot guard — on BOTH shapes. At wrapper construction (QueryWithParams / QueryWithParamsSpec / the export wrappers), the framework walks the pair recursively: queryschema.ValidateFieldsResponse panics when any exported TResp field is not *T (or a slice/map) and carrying ,omitempty in its json tag, and ValidateFieldsResult panics when any exported TResult field is not a pointer, slice or map (the tagless Result carries no omitempty — it only has to distinguish absent from zero). Each diagnostic names every offending field path (FindXxxResponse.addresses.zipCode: missing ,omitempty…) — fail loud at boot so the contract cannot ship.
  2. Allowlist + two-hop translation. Each comma-separated token in ?fields= is validated against the Response DTO's declared wire paths and mapped to the Go field path via the Response struct's json: tags at the web boundary; the reader then translates the Go path to the physical Mongo column via the view's TableSchema tree. Unknown tokens emit 400 with SchemaViolationNotification on field fields[<bad>]. Nested paths are walked segment-by-segment, so ?fields=addresses.zipCode (Go path Addresses.ZipCode) projects to Mongo as {"addresses.zip_code":1} because the view's TableSchema maps ZipCode → zip_code, and ?fields=addresses projects the whole subtree.
  3. The identity is a path like any other. An inclusion selection returns exactly the paths it names, the root id included: ask for it and you get it, leave it out and the typed Response stays clean — no phantom id the consumer did not request. What each store has to do to honor that is the store's own business, decided below the read seam and invisible on the wire.

Why the boot guard? Mongo strips the unwanted columns from the document; the Result fill populates only the fields it finds in the doc and the response projection carries them across; the remaining fields stay at their zero value. For pointer fields with omitempty, encoding/json elides them on the wire. For non-pointer fields (or pointer fields missing omitempty), the zero value still renders ("name":"", "addresses":[]), defeating the point of ?fields=. Enforcing the same rule on the Result closes the other half: a non-pointer Result field would fill as a zero the Response could not tell from an absence. The contract enforced at boot is the cheapest way to keep wire output coherent with what the consumer asked for.

The boot guard is opt-in by declaration: a Request DTO that does not carry query:"fields" imposes no constraint on the Result/Response pair. When it does, the guard applies on every surface that mounts the pair — the JSON listing, the *Spec siblings and the CSV/XLSX exports run the same boot scan.

Computed fields — a wire field with no column

Not every value a consumer needs is stored. A Response field may be DERIVED after the read: declare it on the Response with computed:"Src1,Src2" beside its json tag, and produce it in the Query's FromQueryResult hook from the named Result fields. Because the derivation happens in the application layer, before any transport sees the value, every surface renders the same result — the JSON listing, the CSV/XLSX columns, the GraphQL node and the gRPC item. 

// application — the Result carries the sources AND the derived field
type FindUsersResult struct {
    Name     *string
    UserName *string          // a source the Response need not declare
    Display  *string          // derived below; no column backs it
}

func (q FindUsersQuery) FromQueryResult(_ *configuration.AppContext, r FindUsersResult) (FindUsersResult, error) {
    if r.Name != nil && r.UserName != nil {
        s := *r.Name + " (@" + *r.UserName + ")"
        r.Display = &s
    }
    return r, nil
}

// web — the Response names the Result fields that feed it
type FindUsersResponse struct {
    Name    *string `json:"name,omitempty"`
    Display *string `json:"display,omitempty" computed:"Name,UserName"`
}

The sources are optional on the Response. One that is declared there (like Name above) also renders on the wire and stays individually selectable; one that is not (UserName) is read so the derivation has data and then never leaves the application layer. What is mandatory is that every source exists on the Result — the boot guard rejects a tag naming a field the Result does not carry, and rejects a source that is itself computed.

  • ?fields=display pushes the SOURCES. A computed path has no column to project, so the framework sends Name and UserName to the store in its place. A source read only to feed the derivation is then blanked before the Response projection, so the answer carries display alone — the parameter keeps shaping the wire even when a source shares the Response.
  • ?orderBy=display is refused with 400. Ordering speaks the Request DTO's sort: vocabulary, and a computed field backs no column to order by — the keyset cursor is built from stored values — so it is never declared there. The refusal is the canonical SchemaViolationNotification on the wire token (orderBy[display]), the same one any undeclared token gets, while a declared field on the same endpoint keeps sorting normally.
  • A filter: tag over a computed field is a boot panic. Filtering is evaluated in the store, so the predicate could never run: the framework fails at construction rather than shipping an endpoint that 400s on every call. Filter one of the sources instead, or materialize the value as a real view column.
  • The tabular exports keep the column. Its header comes from exportLabelKey like any other, and selecting only the computed field keeps its column: the projection echo names the sources, so the pruning is told about the computed selection explicitly.
When NOT to compute. A computed field is read-time derivation: it cannot be filtered, cannot be ordered by, and its sources are read on every request that selects it. A value consumers routinely filter or sort by belongs in the view as a real column — the write side materializes it, and every control works on it unchanged.

The ordering pair — query:"orderBy" and sort:

Ordering is a store operation, like filtering. Its vocabulary therefore lives where the endpoint declares what it accepts on the wire — the Request DTO — and never on the Response, which governs what comes out (the shape, the export columns, and the one ?fields= vocabulary).

It is declared in two halves, which answer different questions and must travel together:

  • query:"orderBy" is the SWITCH. Like every other reserved control, it decides whether the endpoint accepts the parameter at all — on every connector — and it is where a description: for the parameter lives.
  • sort:"asc,desc" on a leaf is the VOCABULARY. It decides WHICH paths the parameter accepts and in which directions. The tag mirrors filter:: the name states the capability, the value lists the operations admitted.
type FindGadgetsRequest struct {
    ID    *string `query:"id"                              sort:"asc"`
    Code  *string `query:"code"    filter:"eq,startswith"   sort:"asc,desc"`
    Name  *string `query:"name"    filter:"eq,icontains"`
    Notes *string `query:"notes"   filter:"contains"`

    Addresses AddressFilterParams `query:"addresses"`

    First   *int64  `query:"first"`
    Fields  *string `query:"fields"`
    OrderBy *string `query:"orderBy" description:"catalog order; default is by code"`
}

type AddressFilterParams struct {
    ZipCode *string `query:"zipCode" filter:"eq" sort:"asc,desc"`
    City    *string `query:"city"    filter:"eq"`
}
  • The grammar is closed. Each sort: entry is asc or desc, listed at most once. Anything else — including sort:"true" or an empty tag — is a boot panic, which keeps room to widen the tag later without silently reinterpreting a value that used to be rejected.
  • The tag rides on any leaf, at any depth. On a filter leaf the field is filterable AND orderable; alone (ID above) the leaf is a vocabulary leaf — orderable, not filterable, carrying no value on the wire. A leaf inside an embed group contributes its dotted path (addresses.zipCode → Addresses.ZipCode) exactly as a filter leaf does.
  • Half a declaration is a boot failure, and each half has its own diagnostic. The switch with no vocabulary would accept ?orderBy= and then refuse every token it could be given; a vocabulary with no switch declares paths orderable on an endpoint that does not take the parameter, so the tags reach no wire. The second diagnostic names the offending leaves.
  • Nothing is orderable until a leaf says so. An unindexed sort is a blocking sort whose cost is proportional to the matching set, not to the page, so the switch alone grants nothing.

Translation and refusal. Each comma-separated token is stripped of an optional - prefix (descending; bare token = ascending), looked up in the declared vocabulary, and mapped to the leaf's Go field path — which the reader then translates to a physical column through the view's TableSchema, the same two hops a filter leaf takes. A token outside the vocabulary, or one asking for a direction the declaration does not admit, is refused with the canonical SchemaViolationNotification on orderBy[<token>], the token verbatim including any - prefix. There is no ordering-specific notification: a path either resolves to a column and was declared for that direction, or it does not. An endpoint that declares no SWITCH rejects the parameter itself, reported on orderBy by the canonical control gate.

Every surface, one vocabulary. The canonical wrappers, the *Spec siblings, the CSV/XLSX exports and a manual route built with fwweb.NewQueryParser[Req, Resp]() all consume it. GraphQL emits the orderBy argument when the DTO declares the control, over an <Entity>OrderField enum built from the vocabulary, so introspection advertises exactly the declared paths; a direction the declaration does not admit is cut in the resolver instead, because an enum cannot express per-member directions. gRPC resolves order_by against the same set folded to proto snake_case, via CriteriaBuilder.Sortable(...) — which has no fallback, so a MountRaw consumer that does not call it orders by nothing. OpenAPI emits the parameter from the control field and, unless that field carries a description: of its own, fills the description with the accepted tokens and their directions.

Index coverage — read this before declaring a vocabulary. Every view sort carries _id as its trailing tiebreak, so ?orderBy=name reaches Mongo as {name: 1, _id: 1}. Mongo serves a sort from an index only when the sort is a prefix of the key pattern (or its exact inverse), which means query.Index("name") does not cover it — query.Compound("name","_id") does. A mixed-direction multi-key sort (?orderBy=name,-email → {name:1, email:-1, _id:1}) cannot be covered at all: IndexSpec.Desc() flips only the trailing key. The framework emits one slog.Warn at boot per Request DTO listing the declared paths, because the wrapper cannot see the ViewDefinition from its construction site — compare that list against the view's .Indexes(…) in the same boot pass.

A default ordering that the consumer does not choose belongs on Query.ToCriteria(ctx) instead: what it writes into ReadCriteria.OrderBy is a Go field path the reader resolves directly, so it passes no wire gate and may name any column of the view.

Keyset pagination — the Relay direction pair first/after × last/before

The pagination vocabulary is the Relay connection pair, on every surface: first=N pages FORWARD (optionally from an after cursor), last=N pages BACKWARD (optionally from a before cursor — and with no cursor, last=N yields the LAST N of the set, the tail window). One rule governs the pair: forward and backward never mix — first+last, first+before, last+after and after+before all reject 400 on the backward-side key, and a non-positive size rejects on the size key. The response envelope mirrors the same Relay vocabulary: pagination.startCursor / endCursor are WINDOW EDGES (the first and last row of THIS page — echo them into ?before=/?after= to walk) and hasNextPage/hasPreviousPage state whether rows exist beyond each edge; totalCount always carries the full filtered count. An edge cursor is emitted only where its neighbouring page exists — endCursor exactly when hasNextPage, startCursor exactly when hasPreviousPage — so the first page of a forward walk carries no startCursor and the last carries no endCursor: an empty edge cursor means "nothing to walk to on this side", never a contradiction with the flag beside it.

Under the wire, the read side is keyset-paginated over (ordering_value..., _id). The cursor encodes the value tuple of the boundary doc and the reader walks from that point. The reader always appends _id ASC as the stable tiebreaker so the result set is deterministic across pages even when the underlying collection is being written to concurrently; consumer-declared ?orderBy= fields layer in front of the _id slot. The backward path queries Mongo in inverted order and reverses the slice in Go so the caller always sees the canonical requested order.

Cursor format. Opaque to consumers — base64(URLEncoding) of {"v":1, "k":[<sort_values..>, "<_id>"], "h":"<context_sha256>"}. URL-safe so + / / are never produced in the encoded string. The v field carries the schema version (currently 1); a future bump rejects older cursors with the same 400 envelope so the consumer surfaces the drift instead of navigating against a stale layout. The h field is the canonical SHA-256 of the issuing call's full listing context (queries.HashContext) — every axis that shapes the result set the cursor walks: Filter + OrderBy (field + Desc per entry, declaration order matters) + Search + IncludeArchived. Empty (omitted on the wire) when the issuing call carried the canonical default context (no filter, no ordering, no search, archived excluded).

Cursors are scoped to the full listing context. A cursor only navigates correctly inside the result set that issued it. The wrapper validates len(cursor.K)-1 == len(criteria.OrderBy) (structural pre-check protecting the reader's keyset builder) AND cursor.H == HashContext(filter, orderBy, search, includeArchived) (covers every listing axis) after parsing the query string. Any mismatch — ordering field added/removed/ reordered, direction flipped, filter value changed, ?search= value changed, ?includeArchived= flipped — is rejected with 400 SchemaViolationNotification on the cursor's wire key (after or before). Stateless by design: there is no server-side session, no per-cursor TTL, no token store. The whole "is this cursor still valid?" check runs in the wrapper against the wire request alone. Cursors persist arbitrarily — across requests, across browser tabs, across user devices — as long as the deploy's schema version and the full listing context match.

The strict check exists to convert silent consumer-side bugs (frontend changes one knob, server returns wrong/empty results, user blames the data) into loud, explicit failures with a clear remediation: "request page 1 of the new context".

Symmetric envelope. Forward and backward navigation are served the same way, so a UI can drive both "next" and "previous" buttons off one envelope: hasNextPage / hasPreviousPage reflect the actual presence of more docs beyond each window edge, and startCursor / endCursor are emitted exactly where those flags are true. A button is therefore driven by the flag and fed by the cursor on the same side — both go quiet together at the ends of the set. This holds on EVERY backing: flipping a view between the projected Mongo collection and the read backing does not change the envelope a consumer parses.

Per-view ?first= ceiling — single cascade, three levels. Every paged GET is bounded by a resolved-at-read-time ceiling computed in this order:

  1. ViewDefinition.MaxLimit(N) — declarative per-view override (query.View("users").MaxLimit(500)). Applies uniformly to every endpoint consulting the view, regardless of how many handlers point at it — the cap describes the cost of reading this specific dataset, not of any single endpoint.
  2. cfg.Query.MaxLimit — yaml-supplied service-wide default (microservice.<profile>.yaml: query: { maxLimit: 200 }).
  3. Framework constant 100 — conservative fallback when neither is declared.

The resolved ceiling is always > 0. When the consumer sends no ?first=, the reader returns up to that ceiling (no separate hardcoded default page size). When the consumer sends ?first=N and N ≤ resolvedMax, that value wins. When N > resolvedMax, the reader rejects with 400 LimitExceededNotification carrying the effective ceiling as FieldValue so the consumer can show "max is X" without parsing the translated message.

MaxLimit(N) does NOT participate in RebuildHash / ArtifactHash — the cap is operational state, not projection shape. Bumping it neither triggers a Mongo rebuild nor requires a Version(N) bump.

Compound cursor + ?fields= interaction. When the consumer requests ?fields=name AND ?orderBy=created_at, the doc would otherwise not carry created_at (projected away) and the reader could not assemble the cursor. The reader transparently re-includes every active ordering field path in the Mongo projection, then strips them from the returned doc after the cursor is built. The wire shape stays exactly as the consumer requested via ?fields=.

Only-total mode via ?onlyTotal=true

Boolean reserved control key. When set to true the wrapper short-circuits the read into a count primitive — the reader runs CountDocuments against the assembled Filter (including identity-derived overlays, the archived gate, and any ?search=) and the wire envelope carries solely pagination.totalCount. No documents are materialized, no projection is applied, no cursor is decoded. The use case is a frontend that needs the total count of a filtered subset (pagination calculation, "matches" badge) without paying for the document fetch.

Like every reserved control key on the read side, ?onlyTotal= is opt-in per endpoint: the consumer declares OnlyTotal *bool `query:"onlyTotal"` on the Request DTO. Endpoints that did not declare it reject the wire key with the canonical 400 — same posture as ?fields= / ?orderBy= / ?includeArchived=.

Conflict matrix. The listing-only reserved controls have no meaningful effect when no documents are emitted, so combining them with onlyTotal=true is a consumer-side bug. The wrapper rejects the combination with 400 SchemaViolationNotification on field onlyTotal[<conflict>]. Filter leaves (declared via filter:"ops") plus ?search= and ?includeArchived= stay valid — counting a filtered subset is the canonical use case.

Manual handlers via fwweb.NewQueryParser get the same treatment: the OnlyTotal flag flows into ReadCriteria.OnlyTotal and conflicts are rejected with the same field shape, so the canonical wire contract is shared with the canonical wrapper path. Tabular export — CSV / Excel (format-pluggable)

Alongside the JSON list, a view can be exposed as a downloadable flat file. The OpenAPI-aware wrapper fwweb.QueryAsCSVSpec[TReq, TQ, TResult, TResp] (and QueryAsXLSXSpec) reuses the same Request DTO, the same query handler, the same Result AND the same Response DTO as QueryWithParams — no second handler, no second query, no hand-written CSV — and returns (handler, openapi.RouteSpec), so it mounts on the canonical fwopenapi.Mount exactly like the JSON list. The returned RouteSpec carries RequestType (so the filters render in Swagger) and FileResponse (so the 200 is documented as a download), keeping MountRaw out of the picture: 

csvH, csvSpec := fwweb.QueryAsCSVSpec(d.Pipeline,
    requests.FindUsersByParamsRequest{},               // same Request DTO as the JSON list → filters in Swagger
    requests.FindUsersByParamsResponse{}.FromResult,   // same response projection → same columns, same values
    view,                                              // web.ExportView → row ceiling + filename (view.Name())
    d.Export,                                          // web.ExportDeps{Translator, MaxExportRows} from Deps
    &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery, queries.FindUsersResult]{
        Reader: d.ViewReader, View: view.Name(),
    },
    export.WithDelimiter(';'))                         // CSV-specific option, fixed at mount
fwopenapi.Mount(d.OpenAPIRegistry, app, fiber.MethodGet, "/users.csv", csvH, csvSpec,
    fwopenapi.Doc{Summary: "Export users as CSV", Tags: []string{"Users"}},
    fwopenapi.RequirePermission("users:read"))
// Excel is the same shape: QueryAsXLSXSpec(..., export.WithSheetName("Users")) → fwopenapi.Mount

The success response is declared via RouteSpec.FileResponse (a typed download descriptor on the canonical path) — see OpenAPI / Swagger UI. The plain QueryAsCSV / QueryAsXLSX (handler-only) remain for services without OpenAPI.

Inputs. Every export wrapper takes the view as a web.ExportView interface — { ResolveMaxExportRows(int64) int64; Name() string }, which the *ViewDefinition satisfies structurally, so web never imports infra — plus a web.ExportDeps{Translator, MaxExportRows} bundle pre-packaged on Deps.Export (the Translator for the header labels + the yaml query.maxExportRows default). The view supplies exactly two things: the effective row ceiling (view.ResolveMaxExportRows(...)) and the download filename base (view.Name()). The columns come from the Response DTO, not from the view — so a route passes just view, d.Export instead of spelling those out by hand at every export endpoint.

Columns are the Response DTO's — one wire authority, one ?fields= vocabulary. The column plan is derived from TResp (export.PlanFor): each json: tag is the wire token, each struct or slice-of-struct field a nested level, to the DTO's full depth. Three consequences follow, and they are the point of the design:

  • A field outside the Response DTO exports nowhere. A column the view projects but the Response does not declare has no wire name and therefore no column — exactly as it has no JSON key.
  • ?fields= and ?orderBy= speak the SAME tokens as the JSON listing, each against its own authority — ?fields= against the Response's projection schema (queryschema.ParseProjection), ?orderBy= against the Request's declared ordering vocabulary (queryschema.BuildCriteria) — and rejecting with the same canonical 400 spelling (fields[<token>] / orderBy[<token>]). id is a legal ?fields= token and an exported column whenever the Response declares it.
  • Cells carry the projected Response values, so the Query's FromQueryResult computation and the Response's FromResult shaping both reach the spreadsheet — including the enum convergence to Unknown. Value objects are unwrapped to their underlying scalar, the same form the JSON renders.

Columns then follow the effective read projection — ToCriteria is the single source of truth. The export prunes that plan to page.Projection (the projection the read actually used, echoed by MongoViewReader.ReadPage from the post-ToCriteria criteria) via Plan.PruneToProjection. So a field a Query removes from the criteria — a ReadCriteria.Restrict call, a tenant/owner overlay, or just ?fields= — drops its CSV/XLSX column and header, not only its cell values. JSON and the tabular export narrow by the same source, so they never disagree on which fields surface.

Hierarchical layout — one column per nesting level. The Response DTO's tree is rendered depth-first: root columns start at column A, each nested segment one column to the right (addresses at column B, a grandchild collection at column C, …), to the DTO's full depth. For each parent row the wrapper emits the parent's data, then — offset one column — a header row plus a data row per child, recursively. A struct that renders as a single cell (time.Time, domain.ID, a value object — anything self-marshaling, and any struct with no exported fields) stays a column instead of becoming a segment. A blank separator line follows each item's cascade once it concludes, so every aggregate (and sub-aggregate) is visually delimited; consecutive blanks from several levels concluding at once collapse into one. This applies identically to locally-mapped embeds and cross-service external (JoinUpstream) embeds, in both CSV (an empty record) and Excel (an empty worksheet row).

Headers — the exportLabelKey tag. A column's header is the translation-catalog key declared on the Response field as exportLabelKey:"<catalog key>", rendered through the Translator in the request's Accept-Language. A field carrying no such tag falls back to its json wire name — the same token the consumer would pass to ?fields=. Reusing the entity's own labelKey value on the tag converges the export header on the same translation the write side already uses for notifications and the audit timeline: 

type FindUsersByParamsResponse struct {
    ID    *string `json:"id,omitempty"`                                            // header: "id"
    Name  *string `json:"name,omitempty"  exportLabelKey:"UserNameField"`           // header: translated
    Email *string `json:"email,omitempty" exportLabelKey:"UserEmailField"`          // header: translated
}

Scope. Filters, ?search, ?orderBy, and ?includeArchived behave like the JSON list. User pagination (?first / ?last / ?after / ?before / ?onlyTotal) is ignored — an export returns the full filtered set, capped at the resolved ceiling sent as the read limit. The ceiling resolves per-view (ViewDefinition.MaxExportRows(n)) > yaml (query.maxExportRows) > framework default query.DefaultMaxExportRows (10000), via ResolveMaxExportRows. Those four pagination keys are also omitted from the generated OpenAPI parameters (the export *Spec wrappers list them on RouteSpec.OmittedQueryParams), so Swagger never advertises a knob the export does not honor — the filters, ?fields, ?orderBy, ?search and ?includeArchived still render, exactly as on the JSON list.

Format is pluggable. The walk, the per-level offset, the translated headers, and the ?fields= pruning are format-neutral — an export.Plan plus the projected Response values are turned into a stream of export.Row events that an export.Encoder serializes. Two encoders ship: export.CSV(export.WithDelimiter(r)) (delimiter chosen at mount) and export.XLSX(export.WithSheetName(s)) (Excel — bold header rows, numeric/typed cells kept typed, built on excelize's streaming writer). The matching convenience wrappers are fwweb.QueryAsCSV and fwweb.QueryAsXLSX; a further format is a new Encoder, with no change to the plan, the generator, or the HTTP wrapper. Attaching the same query handler to JSON, CSV, and Excel is one half of a broader pattern — see Handler invariance (queries → JSON/CSV/Excel, commands → HTTP/broker).

Full example

1. Define the ViewDefinition

View declaration — the three constructors, the external NewExternalSchema, Embed/EmbedMany, SharedBaseView, ComposedView and the SyncEngine/recompose fan-out — is covered canonically under Views. The example below shows it in the context of wiring an auto query handler; note the embed sources (the customer and shipments mirrors) are EXTERNAL upstream projections of OTHER services (the customers and logistics services — see Service-to-service), each a type-less NewExternalSchema. A local view embeds through a query.JoinView leg instead (see Views), and an embed source may not nest a further embed inline (single-level per declaration — depth comes from a JoinView source's own embeds, or from a read-time ComposedView).

Every view is declared explicitly with the fluent View(name) builder. The root .Schema(...) is the aggregate's own write TableSchema — the same one the repository uses — so the whole internal closure (root / siblings / SharedBase / children) projects automatically. Each embed's query.JoinUpstream(...) carries an external (type-less NewExternalSchema) schema describing an upstream collection's columns, plus its two mandatory segment names (Go, then doc field); the framework derives the collection from the schema. The join column is named on the verb via .On(...) — the parent ParentID on a 1:1 Embed, the leg ParentID on an EmbedMany.

One canonical path per case: the aggregate's own data is automatic, an embed composes a MATERIAL source. The aggregate's own data — root columns, siblings and SharedBase (FLAT), and every Child(...) collection (each child's siblings folded in FLAT) — projects into the document automatically from the TableSchema, a faithful mirror of the write closure. You declare nothing for it; a nested collection lands under the segment its child type declares in CollectionName(), filterable/sortable by its dotted Go path (Items.SKU). EmbedMany/Embed compose data the aggregate does not own, from either material source: another service's read model (UpstreamSubscription + JoinUpstream over a type-less NewExternalSchema) or another LOCAL view (JoinView — see Views). A write-anchored embed source is a boot error (an aggregate's own closure projects automatically — never declare it twice), as is a redundant embed whose segment clashes with a child the schema already projects. Everything the document carries — siblings, SharedBase, nested children, embed segments — is filterable and sortable; what SURFACES on any wire (JSON, CSV/XLSX, GraphQL, gRPC) is what the Result and the Response DTO declare.

        "Shipments", "shipments")).
        On("sale_id").                                   // leg ParentID → sale._id (1:N)
    Indexes(query.Index("customer_id"))                  // boot guard: covering index for the 1:1 embed join

// Drop archived rows from the projection — opt in via .DeleteOnArchive().
// Default behavior (flag absent): ARCHIVED outbox events compose+upsert the
// document (survives with deleted_at populated, mirroring the relational
// backend symmetrically) and the composer omits the WHERE deleted_at IS NULL filter
// on every fetch of the aggregate's own closure. With .DeleteOnArchive():
// ARCHIVED removes the document from Mongo and the composer applies the
// deleted_at filter across that closure (root, child collections, the role
// pick) — no per-child override. An embed segment is untouched by the flag:
// it mirrors its SOURCE's own archive state (see Views, the archived rule).
// The hot-tier choice for services that don't need archived data on the
// read side.
//
// Reader semantics are unchanged: ReadByID / ReadPage default to
// IncludeArchived=false at the Mongo layer, so consumers still have to
// pass ?includeArchived=true (or the equivalent on their Request DTO) to see
// archived documents. On a default (keep) view the document is present
// and returns; on a DeleteOnArchive view the document is absent and the
// reader returns 404 — the explicit consequence of opting into hot-tier.
//
// Hard DELETE always removes the document from Mongo regardless of the
// flag (it covers archive only).
var HotTierUserView = query.View("users").
    Version(1).
    Schema(views.UserSchema()).   // addresses (a .Child of UserSchema) auto-project
    DeleteOnArchive()

2. Declare the Request DTO (allowlist) + Query + Result + Response

The Request DTO lives in web/requests/ and declares the wire allowlist through struct tags. ToQuery is pure body mapping with no ctx — the web→application boundary stays dumb. The Query lives in application/queries/ alongside its Result, and owns its persistence shape end to end via ToCriteria(ctx) — that is where *AppContext is consumed and where JWT-derived overlays (tenant id, owner id) layer onto the ReadCriteria.Filter — plus its output shape via FromQueryResult. The Response DTO sits next to the Request and owns the wire names.

// ToEntity(ctx) — the only layer below the web boundary that may consume
// *AppContext. It returns (ReadCriteria, error) so field-level read
// authorization and overlay assembly can fail the read; the framework's
// FindByParamsQueryHandler calls ToCriteria(ctx), propagates the error
// (pipeline.Run is unchanged — errors.As still routes it), and forwards the
// criteria to ViewReader.ReadPage.
func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,

    // e.g. tenant_id read from a custom claim on ctx.Identity().Claims.

// SyncEngine.Start is fire-and-forget. Internally the engine ensures its topics
// exist (via the adapter's idempotent EnsureTopics) before subscribing —
// necessary because a consumer-group reader can block on subscribe when a topic
// does not yet exist. Internal 30s retry covers the typical docker-compose boot
// race (the broker coming up while the service has already started).

// Cross-service composition via UpstreamSubscription (yaml-declared in
// microservice.<profile>.yaml; manual Wiring form shown for illustration).
// bootstrap.Run spins one query.UpstreamSubscriber per entry and ripples
// recompose to every view embedding the materialized collection via an
// external JoinUpstream embed.
return bootstrap.Wiring{
    UpstreamSubscriptions: []bootstrap.UpstreamSubscription{
        {Topic: "people.customers.events", Collection: "customers",
         Filter: []string{"id", "name"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
        {Topic: "logistics.shipments.events", Collection: "shipments",
         Filter: []string{"id", "sale_id", "status", "tracking_code"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
    },
}

What each upstream event does to the local collection. The subscriber dispatches on the outbox event_type: INSERTED/UPDATED/UNARCHIVED upsert the (filtered) payload into the collection and ripple recompose; ARCHIVED with deleteOnArchive: false (the default) upserts too — the upstream payload carries the DeletedAt column populated, so the local document survives with deleted_at set, symmetric with the producer's own read side — while deleteOnArchive: true removes the document; DELETED is dispatched on the aggregate id alone, before any payload decode (its keys-only payload — ID + shared-base ParentID — is available to bespoke consumers, but the framework's cascade / anonymize / keep handling needs only the id, which also keeps replays of historical NULL-payload rows working). When declaring a filter allowlist, include the DeletedAt column if the collection keeps archived documents — a filter that drops it would strip the archive marker from the ARCHIVED upsert.

The unified failure ledger. Every ripple failure (discover / compose / upsert stage — plus signal, the post-write re-read of the source that feeds the ripple) is upserted into omnicore_projection_failures as a kind='ripple' row, alongside the slog line and the in-memory counter — the SAME ledger that parks failed projection events (kind='event'), so one table answers "what read-side work is deferred right now?". The topic column holds the source coordinate: the subscription topic for an upstream mirror, or view:<source view name> for a LOCAL view source (a query.JoinView embed — see Views), a namespaced label that cannot collide with a topic. aggregate_type holds the DEPENDENT view, aggregate_id the source document's _id; stage and local_id describe the latest failure. A ripple row stores NO payload — its replay recomposes from the source's CURRENT document, never from a stale copy. One row per (consumer_group, kind, topic, aggregate_type, aggregate_id); repeats increment attempt — the ledger mirrors live state, never grows monotonically. A recompose round that finishes without errors for (view, source id) automatically marks pending rows under that coordinate as resolved. Writes are best-effort: any relational error on Record/Resolve is logged at slog.Warn and discarded — the consumer's transport offset/ack still advances, preserving the failure-isolation contract.

Operational queries (SQL on B's framework relational store):

-- Currently stale segments:
SELECT topic, aggregate_type AS view_name, aggregate_id AS source_id,
       local_id, stage, attempt, last_attempt_at, error
FROM omnicore_projection_failures
WHERE kind = 'ripple' AND resolved_at IS NULL
ORDER BY last_attempt_at ASC;

-- Top offending views (recurring failures may indicate a deterministic Composer bug):
SELECT aggregate_type AS view_name, count(*) AS pending
FROM omnicore_projection_failures
WHERE kind = 'ripple' AND resolved_at IS NULL
GROUP BY aggregate_type
ORDER BY pending DESC;

Replay is automatic. The SyncEngine's parked-retry loop (the mongo.parkedRetry knob — on by default) sweeps BOTH kinds on its cadence: ripple rows are deduplicated per source id and re-run through the same recompose a live event would drive — an upstream row through its subscriber, a view: row through the view fan-out — resolving on a clean pass. A row whose source no longer exists in the topology (the subscription or embed was removed) is resolved as moot with a log line. SyncEngine.RetryPendingProjectionFailures(ctx) forces one immediate sweep when an operator does not want to wait for the next tick.

Pending rows under a view: label that never clear point at a deterministic compose or index problem in the embedding view — read the error column and the stage; a rebuild of the EMBEDDING view also forces convergence (it recomposes every segment from the source's current collection).

Inspection CLI. omnicore-admin list-failures [--kind event|ripple] [--topic <source>] [--view <name>] [--format text|json] [--limit N] is the read-only triage tool: runs in B's process (loads microservice.${APP_PROFILE}.yaml), reads the ledger, prints text or JSON. The CLI binary has no Wiring of B and cannot replay — replay belongs to the runtime loop above.

5. Client does GET with dynamic filters

GET /users?email.in=a@x.com,b@y.com&orderBy=-created_at&first=20

→ filters emails by inclusion ($in applied)
→ orders by created_at descending
→ returns 20 + cursor for the next page

GET /users/<id>?includeArchived=true

→ returns even if archived (deleted_at IS NOT NULL)

GET /users?role=admin

→ 400 SchemaViolationNotification — "role" is not in the allowlist
Result: with a Request DTO that declares the allowlist via struct tags, a thin Query that owns its persistence shape via ToCriteria(ctx), and two route lines, the developer gets the read side wired end-to-end. Unknown fields and operators are rejected at the wire boundary; not-found surfaces as 404; pagination lives top-level in the envelope; and AppContext-derived security filters layer onto the criteria inside ToCriteria(ctx) without changing any other signature.

Wire deltas on a composed name

A ComposedView name goes wherever a view name goes — same wrappers, same Request DTO reflection, same envelope. The wire behaves identically except for the segment-shaped additions:

  • Segment filters are declared as a nested group on the Request DTO whose Go field name matches the link's Go segment (e.g. a Notes group with query:"notes"); the wire form is ?notes.text.contains=b. They pass the same allowlist machinery, but shape only the segment's content — never which primary items return.
  • ?orderBy= into a segment path is 400 — sortable paths remain primary-only; the segment's order is fixed on the link declaration.
  • ?fields= projects into segments (?fields=code,notes.text): an inclusion projection that names no path of a given segment omits that segment entirely from the wire shape.
  • ?includeArchived=true propagates to every leg — one send, one meaning; a leg whose schema has no DeletedAt simply has no gate.
  • Cursors bind to the composed listing context — segment filters included: changing ?notes.text= mid-navigation invalidates the cursor (400) exactly like changing a row filter does; request page 1 of the new context.
  • Exports carry the leg branches: declare each leg as a nested struct (or slice of structs) on the Response DTO and it renders as one further nested level in the CSV/XLSX, exactly the shape an embed produces.
