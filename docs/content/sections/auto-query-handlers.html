Auto query handlers

Symmetric to the Auto command handlers on the write side: for the common read — a paged listing or a by-id lookup served straight from a pre-composed Mongo view — the framework ships ready-made generic query handlers plus the HTTP wrappers that wire them. The consumer writes zero handler code; it declares the Request DTO allowlist (which fields and operators the endpoint accepts) and the Response shape, and the framework owns the rest: query-string parsing, allowlist enforcement, the ReadCriteria assembly, the ViewReader call, pagination, and projection.

By-id lookup (GET /users/:id)fwweb.HandleQueryWithIDFindByIDQueryHandler[*Q]ReadByID

The two wrappers, the Query/Request wiring, the projector contract, the SyncEngine that keeps the view populated, and the manual escape hatch all live on the QueryHandler · CQRS page — including the full end-to-end example. This page documents the features the auto wrappers enforce on the query string: the allowlist, nested embed groups, sparse responses (?fields=), sortable response paths (?sort=), keyset pagination (?after= / ?before=) with the per-view ?limit= ceiling, and count-only mode (?onlyTotal=true). They are the read-side counterpart to the FullBody strict-body marker on the write side — capabilities the canonical wrapper provides out of the box, which the manual path opts into via fwweb.NewQueryParser / fwweb.ParseCriteria (see the manual query handlers section on the QueryHandler · CQRS page).

Allowlist via struct tags

Each filter field on the Request DTO declares its set of allowed operators via the filter:"eq,in" tag. The wrapper inspects the type (cached by reflect.Type in a module-level sync.Map) and rejects any query-string key outside the declared set with 400 SchemaViolationNotification. Reserved pagination/control keys (limit, after, before, sort, fields, search, includeArchived) are declared with only the query:"..." tag (no filter tag) — recognized only at the top level, never inside an embed group.

Nested embed groups

A struct-typed field carrying query:"prefix" (no filter:) is an embed group — the walker recurses, and every leaf below it produces a wire key prefixed by prefix.. Symmetric with the Response side, where nested structs project nested doc paths via AutoFromDoc. 

type FindUsersByParamsRequest struct {
    Name      *string             `query:"name"  filter:"eq,startswith"`
    Email     *string             `query:"email" filter:"eq,in"`
    Addresses AddressFilterParams `query:"addresses"`

    Limit *int64 `query:"limit"`
}

type AddressFilterParams struct {
    City    *string `query:"city"    filter:"eq,istartswith"`
    ZipCode *string `query:"zipCode" filter:"eq,startswith"`  // wire zipCode → Go ZipCode; reader maps to column zip_code via the view TableSchema
}

Wire shape: ?addresses.city=Berlin, ?addresses.zipCode.startswith=10001. Translation is a two-hop pivot through the Go field name. At the web boundary the wire token maps to the Go field path via the DTO's query: tags (zipCode → Addresses.ZipCode) — filter keys are always Go field paths. The reader (MongoViewReader) then translates the Go path to the physical Mongo column via the view's TableSchema tree (ZipCode → zip_code). There is no PascalToSnake and no view: tag on this path — the physical column name lives only in the TableSchema. Pointer-to-struct embed groups (*AddressFilterParams) recurse identically.

Sparse responses via ?fields=

Opt-in field projection — the consumer asks for a subset of the Response shape and the framework strips everything else end to end. The Request DTO opts in by declaring Fields *string `query:"fields"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, three things happen automatically:

  1. Boot guard. At wrapper construction (HandleQueryWithParams / HandleQueryWithParamsSpec), the framework walks R recursively and panics if any exported field is not *T (or a slice/map) and does not carry ,omitempty in its json tag. The panic diagnostic names every offending field path (FindXxxResponse.addresses.zipCode: missing ,omitempty…) — fail loud at boot so the contract cannot ship.
  2. Allowlist + two-hop translation. Each comma-separated token in ?fields= is validated against the Response DTO's declared wire paths and mapped to the Go field path via the Response struct's json: tags at the web boundary; the reader then translates the Go path to the physical Mongo column via the view's TableSchema tree. Unknown tokens emit 400 with SchemaViolationNotification on field fields[<bad>]. Nested paths are walked segment-by-segment, so ?fields=addresses.zipCode (Go path Addresses.ZipCode) projects to Mongo as {"addresses.zip_code":1} because the view's TableSchema maps ZipCode → zip_code, and ?fields=addresses projects the whole subtree.
  3. Auto-exclusion of _id. Mongo always returns _id unless excluded. When the wire fields list does not include id, the framework adds _id: 0 to the projection so the typed Response stays clean (no phantom id the consumer didn't ask for). When id is among the tokens, no _id: 0 is added — Mongo returns both id and _id, and AutoFromDoc's existing fallback (id ← _id when id absent) keeps the wire output stable across both cases. Mongo's projection rules allow _id: 0 to be mixed with inclusion entries — it is the only permitted exclusion in an otherwise- inclusion projection.

Why the boot guard? Mongo strips the unwanted columns from the document; the projector (AutoFromDoc[R] by default) populates only the fields it finds in the doc; the remaining fields stay at their zero value. For pointer fields with omitempty, encoding/json elides them on the wire. For non-pointer fields (or pointer fields missing omitempty), the zero value still renders ("name":"", "addresses":[]), defeating the point of ?fields=. The contract enforced at boot is the cheapest way to keep wire output coherent with what the consumer asked for.

The boot guard is opt-in by declaration: a Request DTO that does not carry query:"fields" imposes no constraint on its Response type; the HandleQueryWithParams wrapper paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the guard — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?fields= token becomes an inclusion entry verbatim, no allowlist, no translation, no _id: 0 auto-exclusion. The canonical surface is the HandleQueryWithParams wrapper. 

// Request DTO opts in to the parameter.
type FindUsersByParamsRequest struct {
    Name   *string `query:"name"   filter:"eq"`
    Email  *string `query:"email"  filter:"eq,in"`

    Limit  *int64  `query:"limit"`
    Fields *string `query:"fields"`   // declares the parameter
}

// Response satisfies the sparse-render contract: every field — at every
// depth — is *T (or a slice) and carries ,omitempty. Slice fields can stay
// []T because omitempty already handles nil/empty slices.
type FindUsersByParamsResponse struct {
    ID        *string                          `json:"id,omitempty"`
    Name      *string                          `json:"name,omitempty"`
    Email     *string                          `json:"email,omitempty"`
    Phone     *string                          `json:"phone,omitempty"`
    Addresses []FindUsersByParamsAddressOutput `json:"addresses,omitempty"`
}

type FindUsersByParamsAddressOutput struct {
    ID      *string `json:"id,omitempty"`
    City    *string `json:"city,omitempty"`
    ZipCode *string `json:"zipCode,omitempty"` // column zip_code via the view TableSchema
}

Empty slices follow the omitempty rule: a ?fields=name request returns {"name":"…"} on the wire — the addresses field is absent entirely (omitempty elides nil/empty slices). The framework does not synthesize an empty "addresses":[] when the consumer did not ask for it; consistent with the sparse-render contract.

Sortable response paths via ?sort=

Symmetric to ?fields=: the consumer asks the framework to order results by Response-declared paths and the wrapper validates + translates the tokens end to end. The Request DTO opts in by declaring Sort *string `query:"sort"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, two things happen automatically:

  1. Allowlist + two-hop translation. Each comma-separated token is stripped of an optional - prefix (descending; bare token = ascending), validated against the Response DTO's declared wire paths, mapped to the Go field path via the Response's json: tags, and finally translated by the reader to the physical Mongo column via the view's TableSchema — the same two-hop pivot ?fields= uses. Unknown tokens emit 400 with SchemaViolationNotification on field sort[<token>]; the rejected token is surfaced verbatim including any - prefix the consumer sent. The resulting SortField{Field: docPath, Desc: bool} entries land on ReadCriteria.Sort and the canonical MongoViewReader emits the corresponding bson.D on findOpts.SetSort.
  2. Boot warning when sort is declared. The wrapper has no way to verify from its construction site that the Mongo view declares indexes covering the sortable paths — the ViewDefinition lives in the consumer's ReadableFeature.Views(), separated from the route registration. When Sort opt-in is detected and a typed Response is in scope, the framework emits a single slog.Warn at boot listing every sortable wire path so the operator can compare it against the view's .Indexes(…) declaration in the same boot pass and add covering indexes (fwinfra.Index / fwinfra.Compound) where missing — sort queries against non-indexed fields scale poorly on large collections.

There is no boot guard analogous to fields' pointer + omitempty rule. ?sort= only consumes the wire→doc path map; the Response shape is not constrained by it. When fields is also opt-in, the existing guard still fires — it is the fields-side rule, untouched by sort.

The allowlist is opt-in by declaration: a Request DTO without query:"sort" does not get the allowlist (and does not consume the ?sort= wire key); HandleQueryWithParams paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the allowlist — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?sort= token becomes a SortField verbatim (no allowlist, no translation, no boot warning). The canonical surface is the HandleQueryWithParams wrapper.

Keyset pagination via ?after= / ?before= + per-view ?limit= ceiling

The read side is keyset-paginated over (sort_value..., _id). The cursor encodes the value tuple of the boundary doc (last for forward, first for backward) and the reader walks from that point. The reader always appends _id ASC as the stable tiebreaker so the result set is deterministic across pages even when the underlying collection is being written to concurrently; consumer-declared ?sort= fields layer in front of the _id slot. The ?before= path queries Mongo in inverted sort order and reverses the slice in Go so the caller always sees the canonical requested order.

Cursor format. Opaque to consumers — base64(URLEncoding) of {"v":1, "k":[<sort_values..>, "<_id>"], "h":"<context_sha256>"}. URL-safe so + / / are never produced in the encoded string. The v field carries the schema version (currently 1); a future bump rejects older cursors with the same 400 envelope so the consumer surfaces the drift instead of navigating against a stale layout. The h field is the canonical SHA-256 of the issuing call's full listing context (queries.HashContext) — every axis that shapes the result set the cursor walks: Filter + Sort (field + Desc per entry, declaration order matters) + Search + IncludeArchived. Empty (omitted on the wire) when the issuing call carried the canonical default context (no filter, no sort, no search, archived excluded).

Cursors are scoped to the full listing context. A cursor only navigates correctly inside the result set that issued it. The wrapper validates len(cursor.K)-1 == len(criteria.Sort) (structural pre-check protecting the reader's keyset builder) AND cursor.H == HashContext(filter, sort, search, includeArchived) (covers every listing axis) after parsing the query string. Any mismatch — sort field added/removed/ reordered, sort direction flipped, filter value changed, ?search= value changed, ?includeArchived= flipped — is rejected with 400 SchemaViolationNotification on the cursor's wire key (after or before). Stateless by design: there is no server-side session, no per-cursor TTL, no token store. The whole "is this cursor still valid?" check runs in the wrapper against the wire request alone. Cursors persist arbitrarily — across requests, across browser tabs, across user devices — as long as the deploy's schema version and the full listing context match.

The strict check exists to convert silent consumer-side bugs (frontend changes one knob, server returns wrong/empty results, user blames the data) into loud, explicit failures with a clear remediation: "request page 1 of the new context".

Symmetric envelope. The reader emits NextCursor and PrevCursor on every non-terminal page in both forward and backward navigation, so a UI can drive both "next" and "previous" buttons symmetrically. HasNext / HasPrev reflect the actual presence of more docs in either direction.

Per-view ?limit= ceiling — single cascade, three levels. Every paged GET is bounded by a resolved-at-read-time ceiling computed in this order:

  1. ViewDefinition.MaxLimit(N) — declarative per-view override (fwinfra.View("users").MaxLimit(500)). Applies uniformly to every endpoint consulting the view, regardless of how many handlers point at it — the cap describes the cost of reading this specific dataset, not of any single endpoint.
  2. cfg.Query.MaxLimit — yaml-supplied service-wide default (microservice.<profile>.yaml: query: { maxLimit: 200 }).
  3. Framework constant 100 — conservative fallback when neither is declared.

The resolved ceiling is always > 0. When the consumer sends no ?limit=, the reader returns up to that ceiling (no separate hardcoded default page size). When the consumer sends ?limit=N and N ≤ resolvedMax, that value wins. When N > resolvedMax, the reader rejects with 400 LimitExceededNotification carrying the effective ceiling as FieldValue so the consumer can show "max is X" without parsing the translated message.

MaxLimit(N) does NOT participate in RebuildHash / ArtifactHash — the cap is operational state, not projection shape. Bumping it neither triggers a Mongo rebuild nor requires a Version(N) bump. 

// Per-view override — applies to every endpoint reading "users":
fwinfra.View("users").
    Version(1).
    Root("users").
    Schema(UserSchema()).
    EmbedMany("addresses", fwinfra.FromSchema(AddressSchema())).
    MaxLimit(500)

# that does NOT declare its own MaxLimit):

Compound cursor + ?fields= interaction. When the consumer requests ?fields=name AND ?sort=created_at, the doc would otherwise not carry created_at (projected away) and the reader could not assemble the cursor. The reader transparently re-includes every active sort field path in the Mongo projection, then strips them from the returned doc after the cursor is built. The wire shape stays exactly as the consumer requested via ?fields=.

Count-only mode via ?onlyTotal=true

Boolean reserved control key. When set to true the wrapper short-circuits the read into a count primitive — the reader runs CountDocuments against the assembled Filter (including identity-derived overlays, the archived gate, and any ?search=) and the wire envelope carries solely pagination.total. No documents are materialized, no projection is applied, no cursor is decoded. The use case is a frontend that needs the total count of a filtered subset (pagination calculation, "matches" badge) without paying for the document fetch.

Like every reserved control key on the read side, ?onlyTotal= is opt-in per endpoint: the consumer declares OnlyTotal *bool `query:"onlyTotal"` on the Request DTO. Endpoints that did not declare it reject the wire key with the canonical 400 — same posture as ?fields= / ?sort= / ?includeArchived=.

Conflict matrix. The listing-only reserved controls have no meaningful effect when no documents are emitted, so combining them with onlyTotal=true is a consumer-side bug. The wrapper rejects the combination with 400 SchemaViolationNotification on field onlyTotal[<conflict>]. Filter leaves (declared via filter:"ops") plus ?search= and ?includeArchived= stay valid — counting a filtered subset is the canonical use case.

On the response side, the Response.Pagination slot is typed any precisely because it carries two legitimate Go shapes: *PaginationInfo on listing requests (has_next/has_prev/cursors + total) and *TotalOnlyPagination on count-only requests (only total). Both are typed structs — no untyped map ever reaches the wire. The dedicated shape exists so the JSON does NOT carry zero-value has_next: false / empty cursors that would mislead the consumer in count mode.

Manual handlers via fwweb.ParseCriteria get the same treatment: the OnlyTotal flag flows into ReadCriteria.OnlyTotal and conflicts are rejected with the same field shape, so the canonical wire contract is shared with the canonical wrapper path. The downstream branch on queries.Page.OnlyTotal is what RespondPaged consumes to pick the envelope shape; manual handlers that assemble the envelope by hand can read the same field on the returned Page. 

// Operator constants — used in the filter tag.
const (
    OpEq           = "eq"
    OpNe           = "ne"
    OpIn           = "in"
    OpNin          = "nin"
    OpGte          = "gte"
    OpLte          = "lte"
    OpGt           = "gt"
    OpLt           = "lt"
    OpStartsWith   = "startswith"
    OpContains     = "contains"
    OpIEq          = "ieq"          // case-insensitive equality
    OpINe          = "ine"          // case-insensitive inequality
    OpIIn          = "iin"          // case-insensitive in-list
    OpINin         = "inin"         // case-insensitive not-in-list
    OpIStartsWith  = "istartswith"  // case-insensitive prefix
    OpIContains    = "icontains"    // case-insensitive substring
)

String operators come in case-sensitive and case-insensitive variants — the i prefix is the case-folded twin. The consumer declares whichever set the endpoint accepts (filter:"eq,startswith,icontains" means exact, prefix, and case-insensitive substring); operators outside the declared list are rejected with 400. Numeric operators (gte/lte/gt/lt) have no i variant by design — case-folding has no meaning on ordinal comparisons.

User-supplied values feeding the regex operators are escaped via regexp.QuoteMeta so wire metacharacters are treated as literals — ?name.contains=a.b*c matches the literal string a.b*c, never the regex pattern. The iin and inin operators emit a queries.RegexMatchList sentinel that MongoViewReader translates into {$in: [bson.Regex, ...]} / {$nin: [bson.Regex, ...]} — Mongo requires the native regex type inside $in, so the translation is owned by the infra adapter rather than emitted from the wire layer.

Multiple operators on the same field are AND-ed. When the wire delivers more than one operator targeting the same field (e.g. ?age.gte=18&age.lte=65 or ?name.startswith=Bob&name.icontains=ob), the wrapper folds the clauses into a queries.MultiClause sentinel on ReadCriteria.Filter[field] instead of overwriting the previous entry on the map. MongoViewReader expands the sentinel into a top-level $and array — each clause becomes a {field: translatedValue} entry so every declared operator is honored simultaneously. A single operator on a field stays as the plain {field: value} shape so Mongo indexes remain usable without an outer $and.
