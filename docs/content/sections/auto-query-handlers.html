Auto query handlers

Symmetric to the Auto command handlers on the write side: for the common read — a paged listing or a by-id lookup served straight from a pre-composed Mongo view — the framework ships ready-made generic query handlers plus the HTTP wrappers that wire them. The consumer writes zero handler code; it declares the Request DTO allowlist (which fields and operators the endpoint accepts) and the Response shape, and the framework owns the rest: query-string parsing, allowlist enforcement, the ReadCriteria assembly, the ViewReader call, pagination, and projection.

The QueryHandler · CQRS page covers the concept and the end-to-end flow of a GET; the Custom query handler page covers the manual escape hatch. This page is the full reference for the automatic path: the two wrappers and the projector contract, the Automatic × Manual split, the query-string capabilities the wrappers enforce, and the complete end-to-end example.

The wrappers and the projector contract

The wire boundary lives in two HTTP wrappers in web/:

  • fwweb.QueryWithParams(pipe, sample, projector, h) — paged listing (GET /users). Validates the query string against the Request DTO's query:"X" filter:"ops" tags, assembles a queries.ReadCriteria, calls req.ToQuery(criteria) — pure body mapping at the boundary, no ctx. AppContext reaches the application layer through q.ToCriteria(ctx), which the framework's FindByParamsQueryHandler[*Q] calls before forwarding to ViewReader.ReadPage — where JWT-derived overlays (tenant id, owner id) layer onto the criteria. Success projects each page.Items document via projector and returns the standard Response envelope with data as the projected items array and pagination as a top-level field.
  • fwweb.QueryByID(pipe, sample, projector, h) — by-id lookup (GET /users/:id). Only ?includeArchived=true is reserved; any other query parameter produces 400. Calls req.ToQuery() (no ctx), injects the path id via q.SetPathID(...), dispatches via FindByIDQueryHandler[*Q] which calls q.ToCriteria(ctx) and forwards both id + criteria (IncludeArchived flag + any JWT overlay) to ViewReader.ReadByID — symmetric DTO with ReadPage. Projects result.Value() via projector; not-found produces 404 with RecordNotFoundNotification. An overlay filter that filters the doc out is indistinguishable from absence at this layer: both surface as 404.
Deterministic rule, same as the write side: the base to embed on the Query is the constructor name plus the Base suffix — QueryWithParams → queries.QueryWithParamsBase, QueryByID → queries.QueryByIDBase. The same names are the role interfaces the constructors demand (queries.QueryWithParams requires ToCriteria(ctx); queries.QueryByID adds SetPathID/PathID() — the exact pair pipeline.CommandByID carries on the write side — plus ContextName()). The rule holds on GraphQL (graphql.QueryWithParams; by-id reads are a where filter on the connection, by design) and gRPC (grpc.QueryWithParams, grpc.QueryByID).

The projector (third argument) is mandatory and has signature func(map[string]any) R. Three canonical projectors ship with the framework:

ProjectorUse when
fwresponses.AutoFromDoc[R] Tag-driven projection — the default. R is a typed Response struct with json:"<wire>" tags only. The doc handed to the projector is already Go-keyed (the reader translated columns → Go field names via the view's TableSchema), so AutoFromDoc keys by the Go field name and the json: tag governs only the wire shape — there is no source-key override. Recursive through nested structs, slices of structs, and pointer-to-struct fields. Normalizes top-level _id → id and nil slices → empty typed slices at every depth. Drop it in place of a manually-written FromDoc whenever the projection is mechanical.
fwresponses.RawDoc Identity passthrough — func(map[string]any) map[string]any. Use when the view doc shape IS the wire contract and a typed Response would just mirror it.
Consumer-declared R{}.FromDoc method Custom logic — derived fields, conditional projection, ctx-aware shaping, or anything beyond tag-driven. The wrapper signature accepts any func(map[string]any) R.

The Response carries json: only — no source-key override exists. The typed Response struct declares json:"<wire>" tags and nothing else. The document handed to AutoFromDoc is already Go-keyed: the reader (MongoViewReader) translated each physical column to its Go field name using the view's TableSchema tree before the doc ever reaches the projector. So there is no view: tag and no PascalToSnake at the Response layer — the json: tag governs the wire shape (Go field → JSON), and the TableSchema on the infra side governs the column shape (Go field → column): 

type AddressOutput struct {
    Street     string `json:"street"`        // Go field Street → wire "street"
    ZipCode    string `json:"zipCode"`       // Go field ZipCode → wire "zipCode"
    PostalArea string `json:"postalArea"`    // Go field PostalArea → wire "postalArea"
}

A column whose physical name diverges from the Go field is handled entirely on the infra side: TableSchema.Field("PostalArea", "cep") maps the Go field PostalArea to the legacy column cep. The Response stays oblivious — it only ever pronounces the Go field name and its wire name.

Consumers typically declare a typed FindXxxResponse struct in web/requests/find_xxx_request.go (co-located with the Request) and pair it with fwresponses.AutoFromDoc[FindXxxResponse] at the route. The Response type carries the wire contract; the helper carries the projection logic.

Allowlist via struct tags

Each filter field on the Request DTO declares its set of allowed operators via the filter:"eq,in" tag — the operator vocabulary itself (the Op* constants, case-insensitive twins, AND-ing, regex escaping) is documented once on the QueryHandler · CQRS trunk, since the custom path reads the same tag. The wrapper inspects the type (cached by reflect.Type in a module-level sync.Map) and rejects any query-string key outside the declared set with 400 SchemaViolationNotification. Reserved pagination/control keys (limit, after, before, sort, fields, search, includeArchived, onlyTotal) are declared with only the query:"..." tag (no filter tag) — recognized only at the top level, never inside an embed group.

Nested embed groups

A struct-typed field carrying query:"prefix" (no filter:) is an embed group — the walker recurses, and every leaf below it produces a wire key prefixed by prefix.. Symmetric with the Response side, where nested structs project nested doc paths via AutoFromDoc. 

type FindUsersByParamsRequest struct {
    Name      *string             `query:"name"  filter:"eq,startswith"`
    Email     *string             `query:"email" filter:"eq,in"`
    Addresses AddressFilterParams `query:"addresses"`

    Limit *int64 `query:"limit"`
}

type AddressFilterParams struct {
    City    *string `query:"city"    filter:"eq,istartswith"`
    ZipCode *string `query:"zipCode" filter:"eq,startswith"`  // wire zipCode → Go ZipCode; reader maps to column zip_code via the view TableSchema
}

Wire shape: ?addresses.city=Berlin, ?addresses.zipCode.startswith=10001. Translation is a two-hop pivot through the Go field name. At the web boundary the wire token maps to the Go field path via the DTO's query: tags (zipCode → Addresses.ZipCode) — filter keys are always Go field paths. The reader (MongoViewReader) then translates the Go path to the physical Mongo column via the view's TableSchema tree (ZipCode → zip_code). There is no PascalToSnake and no view: tag on this path — the physical column name lives only in the TableSchema. Pointer-to-struct embed groups (*AddressFilterParams) recurse identically.

Sibling and shared-base fields are flat

A field that physically lives in a sibling table or a shared base (the relational specialization mechanisms — a 1 : 1 vertical split, or a party-role identity shared across roles) is not an embed group. The framework partitions the row across those tables on write and merges them back flat at the owner's level on read (the composer's mergeOwnerSiblings / the role carrying every base field), so on the read side they behave exactly like the owner's own columns. Declare them as top-level fields on the Request and Response DTOs — no prefix — and filter: / ?sort= / ?fields= work identically to a native field. The TableSchema field resolver is sibling-aware (columnForRead / goNameForRead route a Go field to its sibling's column), and the relational aggregate loader LEFT JOINs the sibling table only when a criteria actually references one of its fields. The wire / DTO author never sees the partition — it is an infra concern.

Sparse responses via ?fields=

Opt-in field projection — the consumer asks for a subset of the Response shape and the framework strips everything else end to end. The Request DTO opts in by declaring Fields *string `query:"fields"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, three things happen automatically:

  1. Boot guard. At wrapper construction (QueryWithParams / QueryWithParamsSpec), the framework walks R recursively and panics if any exported field is not *T (or a slice/map) and does not carry ,omitempty in its json tag. The panic diagnostic names every offending field path (FindXxxResponse.addresses.zipCode: missing ,omitempty…) — fail loud at boot so the contract cannot ship.
  2. Allowlist + two-hop translation. Each comma-separated token in ?fields= is validated against the Response DTO's declared wire paths and mapped to the Go field path via the Response struct's json: tags at the web boundary; the reader then translates the Go path to the physical Mongo column via the view's TableSchema tree. Unknown tokens emit 400 with SchemaViolationNotification on field fields[<bad>]. Nested paths are walked segment-by-segment, so ?fields=addresses.zipCode (Go path Addresses.ZipCode) projects to Mongo as {"addresses.zip_code":1} because the view's TableSchema maps ZipCode → zip_code, and ?fields=addresses projects the whole subtree.
  3. Auto-exclusion of _id. Mongo always returns _id unless excluded. When the wire fields list does not include id, the framework adds _id: 0 to the projection so the typed Response stays clean (no phantom id the consumer didn't ask for). When id is among the tokens, no _id: 0 is added — Mongo returns both id and _id, and AutoFromDoc's existing fallback (id ← _id when id absent) keeps the wire output stable across both cases. Mongo's projection rules allow _id: 0 to be mixed with inclusion entries — it is the only permitted exclusion in an otherwise- inclusion projection.

Why the boot guard? Mongo strips the unwanted columns from the document; the projector (AutoFromDoc[R] by default) populates only the fields it finds in the doc; the remaining fields stay at their zero value. For pointer fields with omitempty, encoding/json elides them on the wire. For non-pointer fields (or pointer fields missing omitempty), the zero value still renders ("name":"", "addresses":[]), defeating the point of ?fields=. The contract enforced at boot is the cheapest way to keep wire output coherent with what the consumer asked for.

The boot guard is opt-in by declaration: a Request DTO that does not carry query:"fields" imposes no constraint on its Response type; the QueryWithParams wrapper paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the guard — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?fields= token becomes an inclusion entry verbatim, no allowlist, no translation, no _id: 0 auto-exclusion. The canonical surface is the QueryWithParams wrapper. 

// Request DTO opts in to the parameter.
type FindUsersByParamsRequest struct {

Sortable response paths via ?sort=

Symmetric to ?fields=: the consumer asks the framework to order results by Response-declared paths and the wrapper validates + translates the tokens end to end. The Request DTO opts in by declaring Sort *string `query:"sort"` (no filter: tag — it's a reserved control key, not a filter leaf). When the parameter is declared and the wrapper's Response type R is a struct, two things happen automatically:

  1. Allowlist + two-hop translation. Each comma-separated token is stripped of an optional - prefix (descending; bare token = ascending), validated against the Response DTO's declared wire paths, mapped to the Go field path via the Response's json: tags, and finally translated by the reader to the physical Mongo column via the view's TableSchema — the same two-hop pivot ?fields= uses. Unknown tokens emit 400 with SchemaViolationNotification on field sort[<token>]; the rejected token is surfaced verbatim including any - prefix the consumer sent. The resulting SortField{Field: docPath, Desc: bool} entries land on ReadCriteria.Sort and the canonical MongoViewReader emits the corresponding bson.D on findOpts.SetSort.
  2. Boot warning when sort is declared. The wrapper has no way to verify from its construction site that the Mongo view declares indexes covering the sortable paths — the ViewDefinition lives in the consumer's ReadableFeature.Views(), separated from the route registration. When Sort opt-in is detected and a typed Response is in scope, the framework emits a single slog.Warn at boot listing every sortable wire path so the operator can compare it against the view's .Indexes(…) declaration in the same boot pass and add covering indexes (query.Index / query.Compound) where missing — sort queries against non-indexed fields scale poorly on large collections.

There is no boot guard analogous to fields' pointer + omitempty rule. ?sort= only consumes the wire→doc path map; the Response shape is not constrained by it. When fields is also opt-in, the existing guard still fires — it is the fields-side rule, untouched by sort.

The allowlist is opt-in by declaration: a Request DTO without query:"sort" does not get the allowlist (and does not consume the ?sort= wire key); QueryWithParams paired with a custom projector returning map[string]any (e.g. fwresponses.RawDoc) also bypasses the allowlist — there is no typed Response shape to enforce. Manual handlers via fwweb.ParseCriteria operate in pass-through mode: each ?sort= token becomes a SortField verbatim (no allowlist, no translation, no boot warning). The canonical surface is the QueryWithParams wrapper.

Keyset pagination via ?after= / ?before= + per-view ?limit= ceiling

The read side is keyset-paginated over (sort_value..., _id). The cursor encodes the value tuple of the boundary doc (last for forward, first for backward) and the reader walks from that point. The reader always appends _id ASC as the stable tiebreaker so the result set is deterministic across pages even when the underlying collection is being written to concurrently; consumer-declared ?sort= fields layer in front of the _id slot. The ?before= path queries Mongo in inverted sort order and reverses the slice in Go so the caller always sees the canonical requested order.

Cursor format. Opaque to consumers — base64(URLEncoding) of {"v":1, "k":[<sort_values..>, "<_id>"], "h":"<context_sha256>"}. URL-safe so + / / are never produced in the encoded string. The v field carries the schema version (currently 1); a future bump rejects older cursors with the same 400 envelope so the consumer surfaces the drift instead of navigating against a stale layout. The h field is the canonical SHA-256 of the issuing call's full listing context (queries.HashContext) — every axis that shapes the result set the cursor walks: Filter + Sort (field + Desc per entry, declaration order matters) + Search + IncludeArchived. Empty (omitted on the wire) when the issuing call carried the canonical default context (no filter, no sort, no search, archived excluded).

Cursors are scoped to the full listing context. A cursor only navigates correctly inside the result set that issued it. The wrapper validates len(cursor.K)-1 == len(criteria.Sort) (structural pre-check protecting the reader's keyset builder) AND cursor.H == HashContext(filter, sort, search, includeArchived) (covers every listing axis) after parsing the query string. Any mismatch — sort field added/removed/ reordered, sort direction flipped, filter value changed, ?search= value changed, ?includeArchived= flipped — is rejected with 400 SchemaViolationNotification on the cursor's wire key (after or before). Stateless by design: there is no server-side session, no per-cursor TTL, no token store. The whole "is this cursor still valid?" check runs in the wrapper against the wire request alone. Cursors persist arbitrarily — across requests, across browser tabs, across user devices — as long as the deploy's schema version and the full listing context match.

The strict check exists to convert silent consumer-side bugs (frontend changes one knob, server returns wrong/empty results, user blames the data) into loud, explicit failures with a clear remediation: "request page 1 of the new context".

Symmetric envelope. The reader emits NextCursor and PrevCursor on every non-terminal page in both forward and backward navigation, so a UI can drive both "next" and "previous" buttons symmetrically. HasNext / HasPrev reflect the actual presence of more docs in either direction.

Per-view ?limit= ceiling — single cascade, three levels. Every paged GET is bounded by a resolved-at-read-time ceiling computed in this order:

  1. ViewDefinition.MaxLimit(N) — declarative per-view override (query.View("users").MaxLimit(500)). Applies uniformly to every endpoint consulting the view, regardless of how many handlers point at it — the cap describes the cost of reading this specific dataset, not of any single endpoint.
  2. cfg.Query.MaxLimit — yaml-supplied service-wide default (microservice.<profile>.yaml: query: { maxLimit: 200 }).
  3. Framework constant 100 — conservative fallback when neither is declared.

The resolved ceiling is always > 0. When the consumer sends no ?limit=, the reader returns up to that ceiling (no separate hardcoded default page size). When the consumer sends ?limit=N and N ≤ resolvedMax, that value wins. When N > resolvedMax, the reader rejects with 400 LimitExceededNotification carrying the effective ceiling as FieldValue so the consumer can show "max is X" without parsing the translated message.

MaxLimit(N) does NOT participate in RebuildHash / ArtifactHash — the cap is operational state, not projection shape. Bumping it neither triggers a Mongo rebuild nor requires a Version(N) bump. 

// Per-view override — applies to every endpoint reading "users":
query.View("users").

    Root("users").

Compound cursor + ?fields= interaction. When the consumer requests ?fields=name AND ?sort=created_at, the doc would otherwise not carry created_at (projected away) and the reader could not assemble the cursor. The reader transparently re-includes every active sort field path in the Mongo projection, then strips them from the returned doc after the cursor is built. The wire shape stays exactly as the consumer requested via ?fields=.

Count-only mode via ?onlyTotal=true

Boolean reserved control key. When set to true the wrapper short-circuits the read into a count primitive — the reader runs CountDocuments against the assembled Filter (including identity-derived overlays, the archived gate, and any ?search=) and the wire envelope carries solely pagination.total. No documents are materialized, no projection is applied, no cursor is decoded. The use case is a frontend that needs the total count of a filtered subset (pagination calculation, "matches" badge) without paying for the document fetch.

Like every reserved control key on the read side, ?onlyTotal= is opt-in per endpoint: the consumer declares OnlyTotal *bool `query:"onlyTotal"` on the Request DTO. Endpoints that did not declare it reject the wire key with the canonical 400 — same posture as ?fields= / ?sort= / ?includeArchived=.

Conflict matrix. The listing-only reserved controls have no meaningful effect when no documents are emitted, so combining them with onlyTotal=true is a consumer-side bug. The wrapper rejects the combination with 400 SchemaViolationNotification on field onlyTotal[<conflict>]. Filter leaves (declared via filter:"ops") plus ?search= and ?includeArchived= stay valid — counting a filtered subset is the canonical use case.

On the response side, the Response.Pagination slot is typed any precisely because it carries two legitimate Go shapes: *PaginationInfo on listing requests (has_next/has_prev/cursors + total) and *TotalOnlyPagination on count-only requests (only total). Both are typed structs — no untyped map ever reaches the wire. The dedicated shape exists so the JSON does NOT carry zero-value has_next: false / empty cursors that would mislead the consumer in count mode.

Manual handlers via fwweb.ParseCriteria get the same treatment: the OnlyTotal flag flows into ReadCriteria.OnlyTotal and conflicts are rejected with the same field shape, so the canonical wire contract is shared with the canonical wrapper path. The downstream branch on queries.Page.OnlyTotal is what RespondPaged consumes to pick the envelope shape; manual handlers that assemble the envelope by hand can read the same field on the returned Page.

The filter operator vocabulary — the Op* constants, the case-insensitive i-twins, the AND-ing of multiple operators on one field, and the regexp.QuoteMeta escaping — lives on the QueryHandler · CQRS trunk, since it applies verbatim to the custom path too. This page covers only what is specific to the automatic wrapper: the allowlist enforcement above and the reserved control keys below.

Tabular export — CSV / Excel (format-pluggable)

Alongside the JSON list, a view can be exposed as a downloadable flat file. The OpenAPI-aware wrapper fwweb.QueryAsCSVSpec[TReq, TQ] (and QueryAsXLSXSpec) reuses the same Request DTO and the same query handler as QueryWithParams — no second handler, no second query, no hand-written CSV — and returns (handler, openapi.RouteSpec), so it mounts on the canonical fwopenapi.Mount exactly like the JSON list. The returned RouteSpec carries RequestType (so the filters render in Swagger) and FileResponse (so the 200 is documented as a download), keeping MountRaw out of the picture: 

csvH, csvSpec := fwweb.QueryAsCSVSpec(d.Pipeline,
    requests.FindUsersByParamsRequest{},   // same Request DTO as the JSON list → filters in Swagger
    view,                                  // web.ExportView → plan, row ceiling, filename (view.Name())
    d.Export,                              // web.ExportDeps{Translator, MaxExportRows} pre-packaged on Deps
    &handlers.FindByParamsQueryHandler[*queries.FindUserByParamsQuery]{
        Reader: d.ViewReader, View: view.Name(),
    },
    export.WithDelimiter(';'))             // CSV-specific option, fixed at mount
fwopenapi.Mount(d.OpenAPIRegistry, app, fiber.MethodGet, "/users.csv", csvH, csvSpec,
    fwopenapi.Doc{Summary: "Export users as CSV", Tags: []string{"Users"}},
    fwopenapi.RequirePermission("users:read"))
// Excel is the same shape: QueryAsXLSXSpec(..., export.WithSheetName("Users")) → fwopenapi.Mount

The success response is declared via RouteSpec.FileResponse (a typed download descriptor on the canonical path) — see OpenAPI / Swagger UI. The plain QueryAsCSV / QueryAsXLSX (handler-only) remain for services without OpenAPI.

Inputs. Every export wrapper takes the view as a web.ExportView interface — the *ViewDefinition satisfies it structurally, so web never imports infra — plus a web.ExportDeps{Translator, MaxExportRows} bundle pre-packaged on Deps.Export (the Translator for labelKey headers + the yaml query.maxExportRows default). The wrapper resolves the column plan (view.ExportPlan()), the effective row ceiling (view.ResolveMaxExportRows(...)), and the download filename base (view.Name()) internally — so a route passes just view, d.Export instead of spelling those out by hand at every export endpoint.

Columns follow the effective read projection — ToCriteria is the single source of truth. The export prunes its column plan to page.Projection (the projection the read actually used, echoed by MongoViewReader.ReadPage from the post-ToCriteria criteria) via ExportPlan.PruneToProjection. So a field a Query removes from the criteria — a ReadCriteria.Restrict call, a tenant/owner overlay, or just ?fields= — drops its CSV/XLSX column and header, not only its cell values. JSON and the tabular export narrow by the same source, so they never disagree on which fields surface.

Hierarchical layout — one column per nesting level. The view's embed tree is rendered depth-first: root columns start at column A, each embed one column to the right (addresses at column B, a grandchild collection at column C, …), to the view's full depth. For each parent row the wrapper emits the parent's data, then — offset one column — a header row plus a data row per child, recursively. A column's header is its labelKey rendered through the Translator in the request's Accept-Language, falling back to the Go field name when a column carries no label. A blank separator line follows each item's cascade once it concludes, so every aggregate (and sub-aggregate) is visually delimited; consecutive blanks from several levels concluding at once collapse into one. This applies identically to locally-mapped embeds and cross-service external (FromSchema) embeds, in both CSV (an empty record) and Excel (an empty worksheet row).

Columns. By default every business column the view's TableSchema declares (the surrogate id and the framework-managed created_at/updated_at/deleted_at are excluded). ?fields= narrows them, exactly like the JSON list — the allowlist is driven by the view schema (not a Response DTO), so ?fields=name,addresses.zipCode keeps only those columns at their proper depth, and an unknown token returns 400 SchemaViolationNotification{field:"fields[<token>]"}.

Scope. Filters, ?search, ?sort, and ?includeArchived behave like the JSON list. User pagination (?limit / ?after / ?before / ?onlyTotal) is ignored — an export returns the full filtered set, capped at the resolved ceiling sent as the read limit. The ceiling resolves per-view (ViewDefinition.MaxExportRows(n)) > yaml (query.maxExportRows) > framework default query.DefaultMaxExportRows (10000), via ResolveMaxExportRows. Those four pagination keys are also omitted from the generated OpenAPI parameters (the export *Spec wrappers list them on RouteSpec.OmittedQueryParams), so Swagger never advertises a knob the export does not honor — the filters, ?fields, ?sort, ?search and ?includeArchived still render, exactly as on the JSON list.

Format is pluggable. The walk, the per-level offset, the labelKey headers, and the ?fields= pruning are format-neutral — a queries.ExportPlan plus the read documents are turned into a stream of export.Row events that a export.Encoder serializes. Two encoders ship: export.CSV(export.WithDelimiter(r)) (delimiter chosen at mount) and export.XLSX(export.WithSheetName(s)) (Excel — bold header rows, numeric/typed cells kept typed, built on excelize's streaming writer). The matching convenience wrappers are fwweb.QueryAsCSV and fwweb.QueryAsXLSX; a further format is a new Encoder, with no change to the plan, the generator, or the HTTP wrapper. Attaching the same query handler to JSON, CSV, and Excel is one half of a broader pattern — see Handler invariance (queries → JSON/CSV/Excel, commands → HTTP/broker).

Full example

1. Define the ViewDefinition

Every view is declared explicitly with the fluent View(name) builder. The root .Schema(...) is the aggregate's own write TableSchema — the same one the repository uses — so the whole internal closure (root / siblings / SharedBase / children) projects automatically. Each embed's query.FromSchema(...) carries an external (type-less NewExternalSchema) schema describing an upstream collection's columns; the framework derives its collection, store kind, and — for an EmbedMany — the join FK from it. An external embed declares its parent-side Go segment via .As(...) (no Go type to derive it from); .FK(...) names the parent doc FK on a one-to-one Embed.

One canonical path per case: internal data is automatic, embeds are external-only. The aggregate's own data — root columns, siblings and SharedBase (FLAT), and every Child(...) collection (each child's siblings folded in FLAT) — projects into the document automatically from the TableSchema, a faithful mirror of the write closure. You declare nothing for it; a nested collection lands under its pluralized child-type segment, filterable/sortable by its dotted Go path (Items.SKU). EmbedMany/Embed compose only EXTERNAL data the aggregate does not own — another service's read model (UpstreamSubscription / external FromSchema over a type-less NewExternalSchema) or a derived projection. A write-anchored embed source is a boot error (there is no relational cross-aggregate embed — compose the read model instead), as is a redundant embed whose segment clashes with a child the schema already projects. Tabular export (CSV/XLSX) walks the same full tree — siblings, SharedBase, and nested children all contribute columns. 
// internal/views/customer.go
package views

import (
    "github.com/ClaudioSchirmer/omnicore/infra"
    appdomain "github.com/ClaudioSchirmer/myservice/domain"
)

// Internal data is automatic. CustomerSchema declares .Child(AddressSchema()),
// so the addresses collection projects into the document with NO embed — a
// faithful mirror of the write closure. The view declares only its root schema.
var CustomerView = query.View("customers").
    Version(1).
    Root("customers").
    Schema(views.CustomerSchema())   // addresses (a .Child of CustomerSchema) auto-project

// Custom pattern — fluent when crossing bounded contexts via UpstreamSubscription
// (cross-service Embed is NOT derivable from the aggregate). An external FromSchema
// (built from a type-less NewExternalSchema) resolves to the local Mongo collection
// materialized by the framework's UpstreamSubscriber on each upstream event (see
// "Cross-service composition" below). External embeds need .As(...) (no Go type to
// derive the segment from); .FK(...) names the parent doc FK on a one-to-one Embed.
var SaleView = query.View("sales_view").
    Version(1).
    Root("sales").
    Schema(views.SaleSchema()).
    Embed("customer", query.FromSchema(views.CustomerProjection()).
        FK("customer_id").As("Customer")).
    EmbedMany("items", query.FromSchema(views.SaleItemSchema()).
        Embed("product", query.FromSchema(views.ProductProjection()).
            FK("product_id").As("Product")),
    ).
    Indexes(query.Index("customer_id"))   // boot guard §8.1 requires the join field index

// Drop archived rows from the projection — opt in via .DeleteOnArchive().
// Default behavior (flag absent): ARCHIVED outbox events compose+upsert the
// document (survives with deleted_at populated, mirroring the relational
// backend symmetrically) and the composer omits the WHERE deleted_at IS NULL filter
// on every fetch. With .DeleteOnArchive(): ARCHIVED removes the document
// from Mongo and the composer applies the deleted_at filter on the root
// AND on every embed source — the flag governs the whole aggregate
// projection (no per-embed override). The hot-tier choice for services
// that don't need archived data on the read side.
//
// Reader semantics are unchanged: ReadByID / ReadPage default to
// IncludeArchived=false at the Mongo layer, so consumers still have to
// pass ?includeArchived=true (or the equivalent on their Request DTO) to see
// archived documents. On a default (keep) view the document is present
// and returns; on a DeleteOnArchive view the document is absent and the
// reader returns 404 — the explicit consequence of opting into hot-tier.
//
// Hard DELETE always removes the document from Mongo regardless of the
// flag (it covers soft delete only).
var HotTierUserView = query.View("users").
    Version(1).
    Root("users").
    Schema(views.UserSchema()).   // addresses (a .Child of UserSchema) auto-project
    DeleteOnArchive()

2. Declare the Request DTO (allowlist) + Query (transport)

The Request DTO lives in web/requests/ and declares the wire allowlist through struct tags. ToQuery is pure body mapping with no ctx — the web→application boundary stays dumb. The Query lives in application/queries/ and owns its persistence shape end to end via ToCriteria(ctx) — that is where *AppContext is consumed and where JWT-derived overlays (tenant id, owner id) layer onto the ReadCriteria.Filter. 

// internal/web/requests/find_users_by_params_request.go
package requests

type FindUsersByParamsRequest struct {
    // Allowlist (consumer declares which fields and operators are accepted).
    Name  *string `query:"name"  filter:"eq"`
    Email *string `query:"email" filter:"eq,in"`
    City  *string `query:"city"  filter:"eq"`

    // Reserved pagination/control keys — no filter tag.
    Limit           *int64  `query:"limit"`
    After           *string `query:"after"`
    Before          *string `query:"before"`
    Sort            *string `query:"sort"`
    Fields          *string `query:"fields"`
    Search          *string `query:"search"`
    IncludeArchived *bool   `query:"includeArchived"`
}

// ToQuery is the web→application boundary — pure body mapping, no ctx.
// The wrapper has already parsed the query string into `criteria`.
func (r FindUsersByParamsRequest) ToQuery(
    criteria queries.ReadCriteria,
) *appqueries.FindUserByParamsQuery {
    return &appqueries.FindUserByParamsQuery{Criteria: criteria}
}

// internal/application/queries/find_user_by_params_query.go
package queries

type FindUserByParamsQuery struct {
    fwqueries.QueryWithParamsBase
    Criteria fwqueries.ReadCriteria
}

// ToCriteria(ctx) is the read-side equivalent of the write-side
// ToEntity(ctx) — the only layer below the web boundary that may consume
// *AppContext. It returns (ReadCriteria, error) so field-level read
// authorization and overlay assembly can fail the read; the framework's
// FindByParamsQueryHandler calls ToCriteria(ctx), propagates the error
// (pipeline.Run is unchanged — errors.As still routes it), and forwards the
// criteria to ViewReader.ReadPage.
func (q FindUserByParamsQuery) ToCriteria(
    ctx *configuration.AppContext,
) (fwqueries.ReadCriteria, error) {
    crit := q.Criteria
    var err error
    // Field-level read authorization: drop "Phone" from the projection/sort/
    // filter unless the caller holds users:admin. ReadCriteria.Restrict returns
    // a 403 (FieldAccessForbiddenNotification) if the request actively
    // referenced the field, or silently omits it otherwise — infra stays
    // authz-blind.
    if id := ctx.Identity(); id != nil && !id.HasPermission("users:admin") {
        err = crit.Restrict("Phone")
    }
    // JWT-derived overlays (tenant id, owner id) also layer here onto crit.Filter,
    // e.g. tenant_id read from a custom claim on ctx.Identity().Claims.
    return crit, err
}

// By-id companion — same pattern. The Query owns IncludeArchived + JWT overlays
// inside its ToCriteria(ctx); the Request boundary is body-only.
type FindUserByIDRequest struct {
    IncludeArchived *bool `query:"includeArchived"`
}
func (r FindUserByIDRequest) ToQuery() *FindUserByIDQuery {
    arch := false
    if r.IncludeArchived != nil { arch = *r.IncludeArchived }
    return &FindUserByIDQuery{IncludeArchived: arch}
}

type FindUserByIDQuery struct {
    fwqueries.QueryByIDBase
    IncludeArchived bool
}

// ToCriteria(ctx) returns the same DTO used by QueryWithParams — the
// ViewReader port has a single ReadCriteria contract. ReadByID honors
// Filter (overlays) + IncludeArchived; Limit/Sort/After/Before/Search/
// Projection are ignored by ReadByID by design.
func (q FindUserByIDQuery) ToCriteria(
    _ *configuration.AppContext,
) (fwqueries.ReadCriteria, error) {
    return fwqueries.ReadCriteria{IncludeArchived: q.IncludeArchived}, nil
}

// ContextName seeds the NotificationContext of the 404 emitted when the
// document is missing. Returning "User" aligns the read 404 with the
// singular identity the write side already emits (Insert/Update/Delete
// notifications carry the same "User" context). Returning "" lets the
// handler fall back to the view name.
func (q FindUserByIDQuery) ContextName() string { return "User" }

4. Configure the SyncEngine at boot

// cmd/service/main.go
pg, _ := postgres.NewPostgres(ctx, postgresDSN)   // *postgres.Postgres satisfies core.RelationalEngine
mongoDB, _ := mongo.NewMongoDB(ctx, mongoURI, "salesdb")

// The linked transport adapter (blank-import infra/transport/kafka or …/nats)
// self-registers; resolve it by name. bootstrap.Run does this from cfg.Transport.
sub, _ := transport.NewSubscriber("kafka", transport.Config{Endpoints: []string{"kafka:9092"}})

sync := query.NewSyncEngine(pg, mongoDB,
    sub,                     // transport.Subscriber — the seam, not a concrete client
    "svc-sales",             // syncGroup
    []*query.ViewDefinition{ // views of this service
        views.SaleView,
    },
    runtime.NumCPU(),        // workers: pool bucketed by aggregate_id
                             // (per-aggregate ordering preserved).
                             // In bootstrap.Run, comes from yaml transport.syncWorkers.
                             // Use 1 to opt out (serial mode).
)
sync.Start(ctx)
// SyncEngine.Start is fire-and-forget. Internally the engine ensures its topics
// exist (via the adapter's idempotent EnsureTopics) before subscribing —
// necessary because a consumer-group reader can block on subscribe when a topic
// does not yet exist. Internal 30s retry covers the typical docker-compose boot
// race (the broker coming up while the service has already started).

// Cross-service composition via UpstreamSubscription (yaml-declared in
// microservice.<profile>.yaml; manual Wiring form shown for illustration).
// bootstrap.Run spins one query.UpstreamSubscriber per entry and ripples
// recompose to every view embedding the materialized collection via an
// external FromSchema embed.
return bootstrap.Wiring{
    UpstreamSubscriptions: []bootstrap.UpstreamSubscription{
        {Topic: "people.customers.events", Collection: "customers",
         Filter: []string{"id", "name", "username"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
        {Topic: "catalog.products.events", Collection: "products",
         Filter: []string{"id", "name", "price"},
         OnUpstreamDelete: bootstrap.UpstreamDeleteCascade},
    },
}

What each upstream event does to the local collection. The subscriber dispatches on the outbox event_type: INSERTED/UPDATED/UNARCHIVED upsert the (filtered) payload into the collection and ripple recompose; ARCHIVED with deleteOnArchive: false (the default) upserts too — the upstream payload carries the soft-delete column populated, so the local document survives with deleted_at set, symmetric with the producer's own read side — while deleteOnArchive: true removes the document; DELETED is dispatched on the aggregate id alone, before any payload decode (its keys-only payload — PK + shared-base FK — is available to bespoke consumers, but the framework's cascade / anonymize / keep handling needs only the id, which also keeps replays of historical NULL-payload rows working). When declaring a filter allowlist, include the soft-delete column if the collection keeps archived documents — a filter that drops it would strip the archive marker from the ARCHIVED upsert.

Persistent failure registry. Every ripple failure (discover / compose / upsert stage) is upserted into the framework relational table omnicore_upstream_failures alongside the slog line and the in-memory counter. The natural key (subscription_topic, view_name, upstream_id, local_id, stage) turns retries into attempt increments — the table mirrors live state, never grows monotonically. A recompose round that finishes without errors for (view, upstream_id) automatically marks any pending rows under that coordinate as resolved (resolved_at = NOW()). Writes are best-effort: any relational error on Record/Resolve is logged at slog.Warn and discarded — the consumer's transport offset/ack still advances, preserving the failure-isolation contract.

Operational queries (SQL on B's framework relational store):

-- Currently stale entities:
SELECT subscription_topic, view_name, upstream_id, local_id, stage, attempt,
       last_attempt_at, error
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
ORDER BY last_attempt_at ASC;

-- Top offending views (recurring failures may indicate a deterministic Composer bug):
SELECT view_name, count(*) AS pending
FROM omnicore_upstream_failures
WHERE resolved_at IS NULL
GROUP BY view_name
ORDER BY pending DESC;

Retry surface. UpstreamSubscriber.RetryPendingFailures(ctx) (retried int, err error) is the public runtime API: it lists pending failures by the subscriber's topic, deduplicates by upstream_id, and re-runs ripple for each unique id. Idempotent — a successful re-ripple calls ResolveUpstreamFailures, so the next call against a drained slate is a no-op. The framework owns the primitive; the consumer decides how to expose it (in-process ticker, authenticated HTTP endpoint, or admin RPC).

Inspection CLI. omnicore-admin upstream-list-failures [--topic <name>] [--view <name>] [--format text|json] [--limit N] is the read-only triage tool: runs in B's process (loads microservice.${APP_PROFILE}.yaml), reads the table, prints text or JSON. The CLI binary has no Wiring of B and cannot call RetryPendingFailures — actual retry lives on the runtime API above.

5. Client does GET with dynamic filters

GET /users?email.in=a@x.com,b@y.com&sort=-created_at&limit=20

→ filters emails by inclusion ($in applied)
→ orders by created_at descending
→ returns 20 + cursor for the next page

GET /users/<id>?includeArchived=true

→ returns even if soft-deleted (deleted_at IS NOT NULL)

GET /users?role=admin

→ 400 SchemaViolationNotification — "role" is not in the allowlist
Result: with a Request DTO that declares the allowlist via struct tags, a thin Query that owns its persistence shape via ToCriteria(ctx), and two route lines, the developer gets the read side wired end-to-end. Unknown fields and operators are rejected at the wire boundary; not-found surfaces as 404; pagination lives top-level in the envelope; and AppContext-derived security filters layer onto the criteria inside ToCriteria(ctx) without changing any other signature.

Wire deltas on a composed name

A ComposedView name goes wherever a view name goes — same wrappers, same Request DTO reflection, same envelope. The wire behaves identically except for the segment-shaped additions:

  • Segment filters are declared as a nested group on the Request DTO whose Go field name matches the link's Go segment (e.g. a Notes group with query:"notes"); the wire form is ?notes.text.contains=b. They pass the same allowlist machinery, but shape only the segment's content — never which primary items return.
  • ?sort= into a segment path is 400 — sortable paths remain primary-only; the segment's order is fixed on the link declaration.
  • ?fields= projects into segments (?fields=code,notes.text): an inclusion projection that names no path of a given segment omits that segment entirely from the wire shape.
  • ?includeArchived=true propagates to every leg — one send, one meaning; a leg whose schema has no soft-delete simply has no gate.
  • Cursors bind to the composed listing context — segment filters included: changing ?notes.text= mid-navigation invalidates the cursor (400) exactly like changing a row filter does; request page 1 of the new context.
  • Exports carry the leg branches: the composed export plan is the primary's tree plus one nested level per leg, exactly the shape an embed produces.
