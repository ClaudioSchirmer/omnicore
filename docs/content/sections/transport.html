Message transport

The async message transport is the broker the framework's read-side consumes from. It is a build-time-pluggable seam of the same shape as the relational engine: the three consumers that read a broker — the read-side SyncEngine, the integration ConsumerPool, and the UpstreamSubscriber — depend on a backend-neutral transport.Subscriber port in infra/transport, never on a concrete client. A build tag links exactly one adapter; the upper layers and the consumer loops are identical whichever broker backs them. Two adapters ship today: Kafka/Redpanda and NATS JetStream.

The seam is on the consumer side; the producer path is unchanged. A write still lands its outbox row inside the domain transaction, and an external CDC relay tails the outbox and publishes to the broker — the framework never produces to the broker itself. The transport seam abstracts only how the framework reads, so the at-least-once delivery, dedup (omnicore_integration_processed), and per-aggregate ordering semantics are identical whichever broker backs it.

The port

type Message struct {
    Topic   string            // source topic/subject (diagnostics)
    Key     []byte            // partition/ordering key = aggregate_id
    Value   []byte            // raw payload (the outbox JSON)
    Headers map[string]string // aggregate_type, event_type, traceparent, …
}

type Subscription interface {
    Read(ctx context.Context) (Message, error) // FIFO within a partition/subject
    Close() error                              // leave the group; sent after the workers drain
}

type Subscriber interface {
    Subscribe(ctx, SubscribeConfig) (Subscription, error) // group, topics, startFrom, commitInterval
    EnsureTopics(ctx, []TopicSpec) error                  // best-effort, idempotent provisioning
}

Per-aggregate ordering is enforced inside the consumer (an FNV-1a hash of aggregate_id routes to a fixed worker), so the transport only has to guarantee FIFO within a partition/subject — a requirement both Kafka and JetStream satisfy trivially.

Selection — the build tag

Selection mirrors the engine registry (the database/sql driver pattern): each adapter self-registers under a name in init() (transport.RegisterSubscriber) behind its own build tag, and the composition root resolves it by name (transport.NewSubscriber). So bootstrap never imports a broker client, and a build links only the one adapter its tag selects:

  • -tags kafka — the Kafka/Redpanda adapter.
  • -tags nats — the NATS JetStream adapter.

There is no default: a build with no transport tag compiles (the neutral bootstrap binding is tagless) but aborts at boot with “no transport linked”, mirroring the no-engine case. So a runnable build always carries two axes, e.g. -tags 'postgres kafka' or -tags 'mysql nats'. See Bootstrap → Message transport build tag.

Connection config

The transport: YAML block is neutral — the build tag, not the YAML, chooses the adapter:

transport:
  endpoints:                       # Kafka/Redpanda bootstrap servers, OR NATS URL(s)
    - "localhost:9092"
  syncGroup: "my-service-sync"     # SyncEngine consumer group / NATS durable name
  syncWorkers: 0                   # 0 → runtime.NumCPU(); 1 → serial per-aggregate

Adapters

Kafka / Redpanda (infra/transport/kafka) wraps segmentio/kafka-go — the only place the framework imports it. Because Redpanda speaks the Kafka wire protocol, this single adapter backs both brokers: the choice is the endpoints value, not a code path or a different tag. It normalizes header values so it is decoupled from the relay's header format — bare (Kafka Connect's SimpleHeaderConverter) or JSON-quoted (Debezium Server's Kafka sink) both arrive as the bare value consumers expect.

NATS JetStream (infra/transport/nats) reads through a durable pull consumer over a single file-backed stream (subjects omnicore.>). Durability matches Kafka: the stream survives a broker restart, the durable consumer's ack state survives a consumer restart (resuming from the last ack), unacked messages redeliver, and limits retention keeps the log for replay. Because a JetStream message has no Kafka-style key, the adapter maps the relay's aggregate_id header into Message.Key and JSON-unwraps the header values — so the consumers are byte-for-byte identical to the Kafka path. Acks are batched on the commitInterval, mirroring the Kafka async-commit window.

Start position (fresh consumers)

The start position applies only the first time a consumer group / durable is created; on every later restart it resumes from its committed position regardless. Both adapters honour the same contract: earliest replays the retained log from the beginning (Kafka FirstOffset / JetStream DeliverAll), while latest — and an omitted start position — begins at new messages only (Kafka LastOffset / JetStream DeliverNew). The empty default is latest on both transports, so a consumer that leaves it unset behaves identically whichever broker is linked. The read-side SyncEngine pins earliest (it must replay the outbox to build the projection); integration consumers and upstream subscriptions default to latest and expose startFrom to override.

The CDC relay (producer side)

The framework does not publish to the broker; a CDC relay tails the outbox tables and publishes each event to the broker under the topic/subject the consumers expect (<aggregate_type>.events; the NATS adapter maps this to an omnicore.-prefixed subject). The reference relay is Debezium with the Outbox Event Router:

  • To a Kafka/Redpanda broker: Debezium via Kafka Connect, or standalone Debezium Server.
  • To NATS: Debezium Server (≥ 3.2 for header forwarding) with the JetStream sink. One instance tails every outbox table via predicate-gated EventRouter transforms.

The relay carries the routing metadata as message headers (aggregate_type, event_type, traceparent, aggregate_id); the payload is a routing hint only — the composer re-reads current state from the relational source on each event, which is why the read side is self-healing and tolerant of at-least-once redelivery. The reference consumer wires this end to end; see its bench for a concrete NATS + Debezium Server setup.
