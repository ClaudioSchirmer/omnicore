Message transport

The async message transport is the broker the framework's read-side consumes from. It is a build-time-pluggable seam of the same shape as the relational engine: the three consumers that read a broker — the read-side SyncEngine, the integration ConsumerPool, and the UpstreamSubscriber — depend on a backend-neutral transport.Subscriber port in infra/transport, never on a concrete client. A build tag links exactly one adapter; the upper layers and the consumer loops are identical whichever broker backs them. Two adapters ship today: Kafka/Redpanda and NATS JetStream.

The seam is on the consumer side; the producer path is unchanged. A write still lands its outbox row inside the domain transaction, and an external CDC relay tails the outbox and publishes to the broker — the framework never produces to the broker itself. The transport seam abstracts only how the framework reads, so the at-least-once delivery, dedup (omnicore_integration_processed), and per-aggregate ordering semantics are identical whichever broker backs it.

The port

type Message struct {
    Topic   string            // source topic/subject (diagnostics)
    Key     []byte            // partition/ordering key = aggregate_id
    Value   []byte            // raw payload (the outbox JSON)
    Headers map[string]string // aggregate_type, event_type, traceparent, …
}

type Completion interface {
    Done(ctx context.Context) error   // the work finished; the message may be confirmed
    Failed(ctx context.Context) error // the work did NOT finish; the message must come back
}

type Subscription interface {
    Read(ctx context.Context) (Message, Completion, error) // FIFO within a partition/subject
    Close() error                                          // leave the group; confirms nothing pending
}

type Subscriber interface {
    Subscribe(ctx, SubscribeConfig) (Subscription, error) // group, topics, startFrom, commitInterval
    EnsureTopics(ctx, []TopicSpec) error                  // best-effort, idempotent provisioning
}

Per-aggregate ordering is enforced inside the consumer (a stable hash of aggregate_id routes to a fixed worker), so the transport only has to guarantee FIFO within a partition/subject — a requirement both Kafka and JetStream satisfy trivially.

The Completion handle is what makes at-least-once true. A message's position advances only when whoever processed it reports Done; Failed guarantees redelivery (on the next rebalance/restart for Kafka, after the ack deadline for JetStream). The handle travels with the message through the consumer's worker queues, so the outcome is reported by the worker that finished the work — never by the reader that merely saw the message. Both methods are once-only: the first outcome settles the message, a second call reports ErrAlreadyCompleted. There is deliberately no Retry outcome and no Ack(message) shape: Kafka has no in-session redelivery to express a retry with, and an ack-by-message API would encode the NATS model and force Kafka to commit past a failed message — relocating a loss instead of removing it. The consumers retry in-process and park exhausted events in the relational failure ledger (see Read lifecycle).

Delivery & fan-out — consumer groups and the three consumers

Every topic is broadcast: the broker delivers one copy per consumer group. Within a single group the topic's partitions/subjects are split across the group's members, so a service running N replicas (pods) still processes each message once — replicas share the load, they do not duplicate it. Two independent groups, by contrast, each receive the full stream. So the unit of fan-out is the distinct group id, never the process count.

Same group → one reaction; different groups → one reaction each. Adding replicas of a service never multiplies its reactions (they join the same group and divide the partitions). Adding a second service does (it joins under its own group and gets its own copy). Per-aggregate ordering survives the split because the partition key is aggregate_id — the same aggregate always lands on the same partition, hence the same replica.

Each of the three consumers owns its group id differently, and that is what makes the read-side projection singular while cross-service composition fans out:

  • SyncEngine — one group per service (transport.syncGroup), and it subscribes only to the <table>.events topics of the service's own views. On a producer's topic there is therefore exactly one sync group: the owner's.
  • UpstreamSubscriber — one group per subscription (default <service>-upstream-<topic>). Any number of downstream services can each declare a subscription to the same upstream <table>.events, so that one topic carries N upstream groups — one per consuming service.
  • Integration ConsumerPool — one group per subscribing service (default <service>-integration). Each service that declares subscribes for an event reacts under its own group.

The producer is oblivious to all of it: it only writes its outbox and lets the CDC relay publish. A consumer subscribes unilaterally and declaratively — it names itself (service:, which prefixes the default group) and the topic it wants (upstreamSubscriptions[].topic or integration.subscribes); nothing registers with, or changes on, the producer. See Service-to-service communication for the upstream declaration and Integration events for the event path.

Selection — the build tag

Selection mirrors the engine registry (the database/sql driver pattern): each adapter self-registers under a name in init() (transport.RegisterSubscriber) behind its own build tag, and the composition root resolves it by name (transport.NewSubscriber). So bootstrap never imports a broker client, and a build links only the one adapter its tag selects:

  • -tags kafka — the Kafka/Redpanda adapter.
  • -tags nats — the NATS JetStream adapter.

There is no default, but unlike the engine axis a tagless build is valid: it compiles and boots with a no-op transport — the infra-free / zero-broker posture, where nothing subscribes and the write/outbox path is unaffected. A consumer that does need messaging (a Mongo-projected view's sync, an integration consumer, an upstream subscription) then fails at the point of use with “transport: no transport registered … (build with the transport's build tag?)” — not at boot. So a messaging build always carries two axes, e.g. -tags 'postgres kafka', -tags 'mysql nats', -tags 'sqlserver kafka' or -tags 'oracle nats'; the transport tag follows the transport: block in the yaml, not the engine. See Bootstrap → Message transport build tag.

Connection config

The transport: YAML block is neutral — the build tag, not the YAML, chooses the adapter:

transport:
  endpoints:                       # Kafka/Redpanda bootstrap servers, OR NATS URL(s)
    - "localhost:9092"
  syncGroup: "my-service-sync"     # SyncEngine consumer group / NATS durable name
  syncWorkers: 0                   # 0 → runtime.NumCPU(); 1 → serial per-aggregate

Adapters

Kafka / Redpanda (infra/transport/kafka) wraps segmentio/kafka-go — the only place the framework imports it. Because Redpanda speaks the Kafka wire protocol, this single adapter backs both brokers: the choice is the endpoints value, not a code path or a different tag. It consumes through the low-level consumer-group API (a group generation with explicit per-partition readers), because the outcome contract requires explicit commits: per partition it tracks the contiguous prefix of completed offsets and commits only that, on the commitInterval. The consumer dispatches by aggregate hash, so a partition completes out of order by design — committing the highest completed offset would silently confirm the gaps below it. A Failed message is simply never completed: the prefix stops there, the group's offset never passes it, and the message returns on the next rebalance or restart. A revoked partition's late completions are dropped, and a commit from an ended generation is rejected by the coordinator on its generation id — rebalance safety rests on that check, not on timing. It normalizes header values so it is decoupled from the relay's header format — bare (Kafka Connect's SimpleHeaderConverter) or JSON-quoted (Debezium Server's Kafka sink) both arrive as the bare value consumers expect.

NATS JetStream (infra/transport/nats) reads through a durable pull consumer over a single file-backed stream (subjects omnicore.>). The outcome maps directly onto JetStream's protocol: Done → Ack, Failed → Nak (immediate redelivery eligibility), and a message that stays in flight heartbeats InProgress on half the ack deadline — AckWait is a lease, and the consumer's in-process retry budget can legitimately outlive one lease term. A consumer that crashes mid-work stops heartbeating and the delivery expires into redelivery, which is the at-least-once guarantee working. Durability matches Kafka: the stream survives a broker restart, the durable consumer's ack state survives a consumer restart (resuming from the last ack), unacked messages redeliver, and limits retention keeps the log for replay. Because a JetStream message has no Kafka-style key, the adapter maps the relay's aggregate_id header into Message.Key and JSON-unwraps the header values — so the consumers are byte-for-byte identical to the Kafka path. commitInterval is a Kafka-side flush cadence and is deliberately unused here — JetStream acks are per-message by protocol.

Start position (fresh consumers)

The start position applies only the first time a consumer group / durable is created; on every later restart it resumes from its committed position regardless. Both adapters honour the same contract: earliest replays the retained log from the beginning (Kafka FirstOffset / JetStream DeliverAll), while latest — and an omitted start position — begins at new messages only (Kafka LastOffset / JetStream DeliverNew). The empty default is latest on both transports, so a consumer that leaves it unset behaves identically whichever broker is linked. The read-side SyncEngine pins earliest (it must replay the outbox to build the projection); integration consumers and upstream subscriptions default to latest and expose startFrom to override.

The CDC relay (producer side)

The framework does not publish to the broker; a CDC relay tails the outbox tables and publishes each event to the broker under the topic/subject the consumers expect (<aggregate_type>.events; the NATS adapter maps this to an omnicore.-prefixed subject). The reference relay is Debezium with the Outbox Event Router:

  • To a Kafka/Redpanda broker: Debezium via Kafka Connect, or standalone Debezium Server.
  • To NATS: Debezium Server (≥ 3.2 for header forwarding) with the JetStream sink. One instance tails every outbox table via predicate-gated EventRouter transforms.

The relay carries the routing metadata as message headers (aggregate_type, event_type, traceparent, aggregate_id); the payload is the event-carried-state snapshot itself — an entity-rooted view projects its Mongo document straight from it, touching no relational source on the event path, while SharedBaseView and external-embed views recompose through the composer. Either way the read side is idempotent under at-least-once redelivery (the per-document revision guards reject a stale replay). The reference consumer wires this end to end; see its bench for a concrete NATS + Debezium Server setup.

Relay config contract — pass the payload through as opaque text; never let the relay type it. Because the read side decodes the payload itself (the relay must never reinterpret it), the Event Router's JSON expansion must stay off: table.expand.json.payload=false, with the value format set to the pass-through converter (Debezium Server: debezium.format.value=simplestring; Kafka Connect: value.converter=org.apache.kafka.connect.storage.StringConverter). The wire bytes are then exactly the JSON text the write recorded in the outbox row. With expansion on, Debezium infers a typed schema from each event's JSON text — and JSON number shapes are not stable types: Go marshals the float 3.0 as 3, so a numeric array like [3.7, 3] infers FLOAT64 from the first element and then rejects the second as Integer, failing the expansion and crashing the relay (a poison message that halts ALL read-model refresh until the relay restarts — and re-crashes on the same event). The expansion buys nothing here — no OmniCore consumer reads the typed structure — and it is the only stage of the pipeline that assigns types to the payload at all.
