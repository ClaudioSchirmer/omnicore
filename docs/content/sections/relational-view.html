Relational View — a query.View read straight from the SoR

OmniCore is built for fully distributed CQRS — a relational view is a deliberate exception to that model. It does not expose every capability a Mongo-projected view has, and — because it composes the aggregate at read time — it can degrade in performance as the shape grows. The canonical, recommended path is always SQL → CDC → MongoDB. Relational views exist for a narrow purpose: surfacing the freshest possible data for monitoring dashboards and operational queries, where the eventual-consistency lag of the projection pipeline — which relies on external auxiliary infrastructure and, subject to hardware and the DevOps configuration, may carry a brief temporary inconsistency — is unacceptable. They are also a pragmatic way to stand up an MVP, abstracting away the whole architectural apparatus the relational → non-relational synchronization requires, until that pipeline is in place.

A relational view is an ordinary query.View marked with .RelationalSource(loader). Instead of reading its document from the Mongo projection, the framework loads the aggregate directly from the relational System of Record through the loader the view carries, maps it to the same column-keyed document a Mongo-backed view would store, and serves it through the same read surfaces — REST, GraphQL and gRPC, plus CSV / Excel export of the listing. Nothing above infrastructure changes: the QueryHandler, the auto query handlers, the ReadCriteria/Page contract and the response DTOs are identical — the SyncEngine read backing is simply selected by name behind the ViewReader port. The view/schema mechanics themselves are unchanged and are documented under Views and TableSchema; this page covers only what is specific to serving a view from the SoR.

The immediate consequence is read-your-writes with no CDC lag: a row committed to the SoR is visible on a relational view on the very next read, before the outbox → CDC → SyncEngine hop has even begun. That immediacy is the whole point — and its cost is everything the warning above spells out.

When to use it — and when not to

  • Use it for monitoring dashboards and operational queries that must reflect the SoR now — a paged listing, or a CSV / Excel export of it, pulls the freshest-possible rows straight from the source with no projection lag — and for MVPs that need a working read side before the projection infrastructure exists.
  • Do not use it as the general read path. A Mongo-projected view is an O(1) document fetch; a relational view re-composes the aggregate on every request. For anything hot, high-fan-out, or embed/link-shaped, stay on SQL → CDC → MongoDB.

Declaring one — pass the loader in

.RelationalSource(reader) takes a query.RelationalReader — the port read.AggregateLoader[T] already satisfies (FindAllEntities / CountEntities / BoundTable). You do not build a loader for the view: every aggregate repository built on read.BaseAggregateRepository[T] already holds one, schema-bound, as its public repo.Loader field. Create the loader once — the repository owns it — and thread that same instance into the view. 

// infra — the view is a plain query.View plus the marker; the loader arrives from the caller.
func GadgetRelView(loader query.RelationalReader) *query.ViewDefinition {
    return query.View("gadgets_rel").
        Version(1).
        Schema(GadgetSchema()).          // the SAME schema the repository declares
        RelationalSource(loader)         // ← served from the SoR through this loader
}

// bootstrap feature — build the repo ONCE, reuse repo.Loader for the view.
func NewGadgetFeature(d bootstrap.Deps) *GadgetFeature {
    repo := infra.NewGadgetRepository(d.DB)     // repo.Loader is created here, schema-bound
    return &GadgetFeature{
        repo:    repo,
        relView: infra.GadgetRelView(repo.Loader),   // ← one loader, shared by repo and view
    }
}

One loader per aggregate. Constructing a second AggregateLoader inside the view constructor works, but it is redundant — the repository's loader is already bound to the right schema and is the intended source. Pass repo.Loader; do not re-build it.

Boot guard — the loader must read the view's own table. At boot the framework asserts loader.BoundTable() == schema.Table(). A view handed a different aggregate's loader (e.g. the User loader on a Gadget view) would silently serve the wrong aggregate, so the mismatch is a hard boot panic naming both tables. A relational view with no .Schema(...) is rejected the same way.

Feature parity — what a relational view can and cannot do

A relational view serves a single plain aggregate loaded from the SoR. Anything that a single aggregate load cannot express — a multi-source join, a read-time enrichment, a cross-document search — is unavailable. The read-side controls that operate on the aggregate's own root and its 1:1 satellites (a sibling, the shared base) reach full parity — those the loader reaches with a LEFT JOIN. Only a 1:N child field is out of reach (a root SELECT cannot filter or sort by it).

The structural unsupported shapes — the Embed family and SharedBaseView — fail at boot when combined with the marker (a multi-source / read-time-join shape a single relational load cannot serve). ComposedView and the Link family are a different declaration type entirely (ComposedViewDefinition) and carry no RelationalSource() method, so the combination cannot even be written. The escape hatch, in every case, is to drop the marker and serve the view from Mongo.

The restriction runs in the other direction too: a relational view cannot be the source of another view. A relational view has no Mongo collection, so embedding it (Embed / EmbedMany / EmbedInChild) or using it as a ComposedView primary or leg would silently read empty — the framework rejects the combination at boot, naming the offending source and the same escape hatch (drop RelationalSource() from that source so it materializes). A materialized view may of course still embed or compose ordinary Mongo-backed views; only a relational source is refused.

A subtlety worth calling out: it is only the SharedBaseView view kind that is refused at boot. A plain query.View rooted at a shared-base role (an aggregate whose schema declares a SharedBase) IS a valid relational source. Its served document carries the full aggregate — the role's own fields, the shared base's fields flattened, root- and child-level siblings, the role's own children AND the base's native children — because the loader reaches all of them in one aggregate load (the 1:1 base and siblings by LEFT JOIN, the children by their own keyed reads). So a base field is both filterable/sortable and projected back, and the read surface matches the flat shape a Mongo view of the same role would carry.

Unsupported capabilities return 400, not 500

The runtime unsupported cases — ?search=, and a filter or sort on a 1:N child field (a dotted child path, or a child-level sibling like parts.tag), or an unknown field — are rejected with a typed RelationalCapabilityNotification. It carries SemanticSchema, so the web wrappers turn it into a 400 Bad Request (never a generic 500) on every surface, with the offending field named and the escape hatch — remove RelationalSource() to serve the view from Mongo — in the translated message. The rule is precise: a relational view serves a filter or sort on any field the aggregate reaches with a 1:1 load — a root column, a sibling, or a shared-base field (the last two joined in) — and rejects only what would need a 1:N pushdown a single root SELECT cannot express.

The managed slots count as root columns. Both readers resolve a Go field name through the same read-path translator, so CreatedAt, UpdatedAt, DeletedAt and the read-only ParentID projection are filterable and sortable here exactly as they are on a Mongo view — under the fixed logical names the three-name contract gives them, and only when the schema actually DECLARES that slot (a view with no DeletedAt has no archived state to address, so the name is as unknown as any other). This is a matter of the two backings answering one question the same way; it grants nothing by itself. Whether an END USER may address a field is the Request DTO's declaration — filter: and sort:, nothing implicit — and whether the SERVICE addresses one is Query.ToCriteria's call, which writes Go paths straight onto the criteria and passes no wire gate on either backing. A default OrderBy: CreatedAt desc written there behaves the same whichever backing serves the view.

?fields= shapes the answer here, it does not narrow the query. The Mongo reader pushes the projection into the find; this loader composes the aggregate as declared and prunes the served document afterwards. The WIRE result is identical on both — the same tokens, the same validation, the same 400 on an unknown one — so nothing a consumer can observe differs. What differs is the cost: a narrow ?fields= buys no I/O on this backing. Plan for it where it matters, and note the same holds for ReadCriteria.Restrict: the restricted column is read from the SoR and dropped before the document is served, so the field never reaches the wire (and an active reference still answers 403), but it is not withheld from the SELECT. A column whose VALUE must not leave the database belongs behind a view that does not project it, not behind a read-time restriction — on either backing.

Pagination is a camouflaged offset

The wire API is identical to a Mongo view — ?first=, ?after=, ?before=, and the returned endCursor / startCursor — but the mechanics underneath are the relational idiom, offset (skip/count), not keyset. The envelope RULE is identical too: an edge cursor is emitted only where its neighbour exists (endCursor iff hasNextPage, startCursor iff hasPreviousPage), so flipping a view's backing does not change the shape a consumer parses — and a cursor the reader refuses (undecodable, or issued under a different filter/sort/archived context) is the same 400 SchemaViolationNotification the Mongo backing raises, never a 500. Each cursor carries an absolute row index rather than a sort-key tuple: after walks forward from that index, before walks back from it, and a bare backward page (GraphQL last:N with no cursor) anchors at the end via a single COUNT. A deterministic ORDER BY … , id tiebreak makes the ordering total, so paging a static result set visits every row exactly once. Absolute-offset paging is not insertion-stable, though: a row inserted or removed ahead of the window shifts every later page by one, so a concurrent write during a walk can make a row skip or repeat — the price of offset over keyset. The Mongo view's keyset cursors do not have this exposure. For the freshest-read / dashboard / MVP use cases this backing targets, it is the right trade; a walk that must be stable under heavy concurrent writes wants the Mongo projection.

Wire-compatible by design. The offset is encoded in a cursor tuple padded to the same length the keyset wire layer validates (len(tuple) − 1 == number of sort fields), so the identical after/before contract round-trips on every surface — the consumer never sees the difference. A before or bare-backward page pays one extra COUNT; forward pages do not.

Evolution — flipping the backing is a shape change

A relational view participates in Mongo schema evolution like any other view, with one rule that follows from how drift is detected: adding or removing RelationalSource() changes the view's rebuild hash (the backing is part of the shape), so — exactly like any shape change — it must be accompanied by a Version(N) bump. On the next boot the drift engine decides:

TransitionDrift decisionEffect
Mongo view → gains RelationalSource() (bumped)DriftRelationalSyncRegistry synced to the new spec, no rebuild — the view is now served from the SoR, and the old Mongo collection is dropped (a relational view holds none), so relational ⇒ no collection stays true.
Relational view → loses the marker (bumped)DriftRebuildRequiredA full online blue-green rebuild materializes the Mongo projection from scratch off the current SoR (zero-downtime) — there is no prior collection to resume; the shadow slot is provisioned fresh.
New relational view over an aggregate that already holds dataDriftFreshInitRegistry row only, no rebuild, no collection — reads come from the SoR immediately.
New Mongo view over an aggregate that already holds dataDriftFreshBackfillA rebuild backfills the pre-existing rows (a fresh Mongo view never comes up empty over populated history).
The round-trip Mongo → SoR → Mongo rebuilds from scratch — there is no stale collection to resume. Flipping a view to relational drops its Mongo collection: the view is served from the SoR and holds none, so the invariant relational ⇒ no collection holds. When the marker is later dropped and the view returns to Mongo, DriftRebuildRequired drives a full online blue-green rebuild — a shadow slot is materialized from the current SoR, verified, and the active pointer flips atomically (zero-downtime) — so every write made during the relational phase is captured. The projection is always rebuilt whole from the source of record, never reconciled from stale documents.

A relational view has no live Mongo collection of its own: the SyncEngine projection pass, the Mongo spec (index) pass and the reconciliation sweep all skip it by name, a change to its SoR table raises no projection work, and the flip that made it relational dropped any collection it used to have. Its registry row exists purely to certify the declared shape so the drift engine can reason about the transitions above. Keeping relational ⇒ no collection true is also what makes a manual registry-row delete safe: with no collection, a subsequent boot resolves to DriftFreshInit (record the row again, no work), never DriftAlienData — the abort a populated collection with no registry row would trigger.
