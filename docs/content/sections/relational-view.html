Relational View — a read model served straight from the SoR

OmniCore is built for fully distributed CQRS — a relational view is a deliberate exception to that model. It does not expose every capability a Mongo-projected view has, and — because it composes the aggregate at read time — it can degrade in performance as the shape grows. The canonical, recommended path is always SQL → CDC → MongoDB. Relational views exist for a narrow purpose: surfacing the freshest possible data for monitoring dashboards and operational queries, where the eventual-consistency lag of the projection pipeline — which relies on external auxiliary infrastructure and, subject to hardware and the DevOps configuration, may carry a brief temporary inconsistency — is unacceptable. They are also a pragmatic way to stand up an MVP, abstracting away the whole architectural apparatus the relational → non-relational synchronization requires, until that pipeline is in place.

A relational view is declared with query.RelationalView(name, loader). Instead of reading its document from the Mongo projection, the framework loads the aggregate directly from the relational System of Record through the loader the view carries, and serves it through the same read surfaces — REST, GraphQL and gRPC, plus CSV / Excel export of the listing. Nothing above infrastructure changes: the QueryHandler, the auto query handlers, the ReadCriteria/Page contract and the response DTOs are identical — the read backing is selected by name behind the ViewReader port.

The immediate consequence is read-your-writes with no CDC lag: a row committed to the SoR is visible on a relational view on the very next read, before the outbox → CDC → SyncEngine hop has even begun. That immediacy is the whole point — and its cost is everything the warning above spells out.

Its own declaration type

RelationalViewDefinition is a different type from ViewDefinition, and that separation is the design. A relational view carries no version, no registry row, no rebuild, no drift, no collection and no Mongo spec — and the projection machinery takes *ViewDefinition concretely, so a relational view cannot be handed to the index provisioner, the SyncEngine, the drift detector, the rebuild or the reconciler. Nothing is skipped at runtime because nothing can arrive.

The same holds for the declaration itself: Version, Indexes, TextIndex, Collation, Capped, JSONSchema, TimeSeries, DeleteOnArchive, the Embed family and Role are not methods on this type, so combining them with a relational view does not compile.

When to use it — and when not to

  • Use it for monitoring dashboards and operational queries that must reflect the SoR now — a paged listing, or a CSV / Excel export of it, pulls the freshest-possible rows straight from the source with no projection lag — and for MVPs that need a working read side before the projection infrastructure exists.
  • Do not use it as the general read path. A Mongo-projected view is an O(1) document fetch; a relational view re-composes the aggregate on every request. For anything hot, high-fan-out, or embed/link-shaped, stay on SQL → CDC → MongoDB.

Declaring one — the loader is the only input

query.RelationalView(name, loader) takes a query.AggregateReader — the port read.AggregateLoader[T] already satisfies (FindAllEntities / CountEntities / Schema / JoinFields). You do not build a loader for the view: every aggregate repository built on read.BaseAggregateRepository[T] already holds one, schema-bound, as its public repo.Loader field.

There is no .Schema(...). The view takes its schema from the loader, because the loader already has it — the repository threads it in with WithSchema. One source means the two cannot disagree, so the mismatch a separate schema argument would make possible (a view handed another aggregate's loader) is not a boot guard here: it is not expressible. 

// infra — the view's only structural input is the loader.
func GadgetRelView(loader query.AggregateReader) *query.RelationalViewDefinition {
    return query.RelationalView("gadgets_rel", loader)
}

// bootstrap feature — build the repo ONCE, reuse repo.Loader for the view.
func NewGadgetFeature(d bootstrap.Deps) *GadgetFeature {
    repo := infra.NewGadgetRepository(d.DB)     // repo.Loader is created here, schema-bound
    return &GadgetFeature{repo: repo}
}

// the read-side opt-in — the sibling of ReadableFeature
func (f *GadgetFeature) RelationalViews() []*query.RelationalViewDefinition {
    return []*query.RelationalViewDefinition{infra.GadgetRelView(f.repo.Loader)}
}

One loader per aggregate. Constructing a second AggregateLoader inside the view constructor works, but it is redundant — the repository's loader is already bound to the right schema and is the intended source. Pass repo.Loader; do not re-build it.

The two options it accepts

Beyond the name and the loader, a relational view declares exactly two things, both operational and both resolved in the same cascade a Mongo view uses — the per-view override, then the yaml default (query.maxLimit / query.maxExportRows), then the framework constant: 

query.RelationalView("gadgets_capped_rel", loader).
    MaxLimit(5).           // ?first= / ?last= ceiling
    MaxExportRows(3)       // CSV / XLSX row ceiling

Both backings are wired with the same resolver, so a view's ceiling applies identically whichever engine serves it.

Feature parity — what a relational view can and cannot do

A relational view serves a single aggregate loaded from the SoR. The read-side controls that operate on the aggregate's own root and its 1:1 satellites (a sibling, the shared base) reach full parity — those the loader reaches with a LEFT JOIN — plus any field a declared read join added. Only a 1:N child field is out of reach: a root SELECT cannot filter or sort by it.

A subtlety worth calling out: it is only the SharedBaseView view kind that is out of reach. A relational view over a shared-base role (an aggregate whose schema declares a SharedBase) is perfectly valid. Its served document carries the full aggregate — the role's own fields, the shared base's fields flattened, root- and child-level siblings, the role's own children AND the base's native children — because the loader reaches all of them in one aggregate load (the 1:1 base and siblings by LEFT JOIN, the children by their own keyed reads). So a base field is both filterable/sortable and projected back.

Read joins come from the loader, not from the view

A relational view declares no join of its own. It carries a loader, and the loader carries whatever read joins the repository declared with WithJoins — so the view inherits them. A field a root join added is filterable, sortable and served in the document exactly like a schema field; a field a child join added is served in that child's elements but is not addressable at the root, which is the same 1:N boundary every child field has.

This is deliberate: the view is not the source of truth for FindOne/FindAll — the loader is. Declaring the traversal on the repository means a service calling repo.Loader.FindAll(ctx, criteria) with no view in sight gets the same reach, and the view is simply one more consumer of it.

Unsupported capabilities return 400, not 500

The unsupported cases — ?search=, and a filter or sort on a 1:N child field (a dotted child path, or a child-level sibling like parts.tag), or an unknown field — are rejected with a typed UnsupportedCapabilityNotification. It carries SemanticSchema, so the web wrappers turn it into a 400 Bad Request (never a generic 500) on every surface, with the offending capability or Go field path named.

The notification names no backing on purpose: every read engine raises this same one, so the four surfaces render one refusal whatever serves the view, and adding an engine adds no vocabulary. The refusal is also raised at the engine's entry point, before any IO — a rejected request costs no connection and no partial work.

The managed slots count as root columns. Both readers resolve a Go field name through the same read-path translator, so CreatedAt, UpdatedAt, DeletedAt and the read-only ParentID projection are filterable and sortable here exactly as they are on a Mongo view — under the fixed logical names the three-name contract gives them, and only when the schema actually DECLARES that slot (a view with no DeletedAt has no archived state to address, so the name is as unknown as any other). This is a matter of the two backings answering one question the same way; it grants nothing by itself. Whether an END USER may address a field is the Request DTO's declaration — filter: and sort:, nothing implicit — and whether the SERVICE addresses one is Query.ToCriteria's call, which writes Go paths straight onto the criteria and passes no wire gate on either backing. A default OrderBy: CreatedAt desc written there behaves the same whichever backing serves the view.

?fields= shapes the answer here, it does not narrow the query. The Mongo reader pushes the projection into the find; this loader composes the aggregate as declared and prunes the served document afterwards. The WIRE result is identical on both — the same tokens, the same validation, the same 400 on an unknown one — so nothing a consumer can observe differs. What differs is the cost: a narrow ?fields= buys no I/O on this backing. Plan for it where it matters, and note the same holds for ReadCriteria.Restrict: the restricted column is read from the SoR and dropped before the document is served, so the field never reaches the wire (and an active reference still answers 403), but it is not withheld from the SELECT. A column whose VALUE must not leave the database belongs behind a view that does not project it, not behind a read-time restriction — on either backing.

Pagination is a camouflaged offset

The wire API is identical to a Mongo view — ?first=, ?after=, ?before=, and the returned endCursor / startCursor — but the mechanics underneath are the relational idiom, offset (skip/count), not keyset. The envelope RULE is identical too: an edge cursor is emitted only where its neighbour exists (endCursor iff hasNextPage, startCursor iff hasPreviousPage), so a consumer parses the same shape on either backing — and a cursor the reader refuses (undecodable, or issued under a different filter/sort/archived context) is the same 400 SchemaViolationNotification the Mongo backing raises, never a 500. Each cursor carries an absolute row index rather than a sort-key tuple: after walks forward from that index, before walks back from it, and a bare backward page (GraphQL last:N with no cursor) anchors at the end via a single COUNT. A deterministic ORDER BY … , id tiebreak makes the ordering total, so paging a static result set visits every row exactly once. Absolute-offset paging is not insertion-stable, though: a row inserted or removed ahead of the window shifts every later page by one, so a concurrent write during a walk can make a row skip or repeat — the price of offset over keyset. The Mongo view's keyset cursors do not have this exposure. For the freshest-read / dashboard / MVP use cases this backing targets, it is the right trade; a walk that must be stable under heavy concurrent writes wants the Mongo projection.

Wire-compatible by design. The offset is encoded in a cursor tuple padded to the same length the keyset wire layer validates (len(tuple) − 1 == number of sort fields), so the identical after/before contract round-trips on every surface — the consumer never sees the difference. Every page runs a COUNT — the envelope carries the full match count, not the page size — but a forward page runs it concurrently with the row fetch, so it costs no extra round trip in wall-clock terms. A bare-backward page (last:N with no cursor) is the one that has to serialize: its offset is anchored ON the total, so the count must land before the window is even known.

No version, no drift, no rebuild

A relational view materializes nothing, so there is nothing to keep in step and nothing to version. It has no row in omnicore_mongo_views, takes no part in Mongo schema evolution, and raises no projection work when its SoR table changes. Changing what it serves — a new column on the schema, a new read join — needs no Version bump and no rebuild: the next read simply reads the new shape.

Boot validation

Everything a Mongo view needs a boot guard for is enforced by the type system here. What remains is checked at boot and aborts with an actionable message:

  • the loader is not nil, and it has a schema bound (the repository called WithSchema);
  • the name does not end in __0 or __1 — the framework reserves those for the blue-green slots a projected view's two physical collections are addressed by, and the rule holds in every read-model family because the namespace is one;
  • the name does not collide with any other read model — a query.View, a SharedBaseView or a ComposedView. A read-model name is unique across the service whatever backs it, because the name is what a surface reads by.
Converting an existing Mongo view: drop its collection by hand. Changing a declaration from query.View(...) to query.RelationalView(...) removes the name from the projected set, so the framework no longer claims that collection — and, because a RelationalViewDefinition never reaches the SyncEngine at all, nothing cleans it up for you either. The DB-per-service guard then sees the collection as foreign: a warn under the dev profile, a boot abort in every other. So the conversion is two steps, not one — change the declaration, then drop the collection(s) it left behind (the bare name and whichever blue-green slot was active) and delete its omnicore_mongo_views row — and the second step has to happen before the service reaches an environment that aborts, not after. If it does abort, the message is the runbook: it names the database and every unclaimed collection, calls out this exact conversion as the usual cause, and prints both statements to run — the mongosh drop and the DELETE FROM omnicore_mongo_views WHERE view_name = '…' (keyed by the VIEW name, not the slot collection). Leaving that registry row behind aborts the next boot for a different reason. Converting the other way needs no special step: a Mongo view with no registry row over a populated table resolves to DriftFreshBackfill, which rebuilds and backfills the pre-existing history.
